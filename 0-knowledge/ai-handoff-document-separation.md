# AI 交接文件分工

> 一句話：長期 AI 專案需要把「如何操作」「目前是什麼」「過去為什麼這樣決定」分開，避免新 AI 把不同性質的資訊混成同一套規則。

## 核心原理

AI Handoff（AI 交接）不是單純的摘要，而是讓下一個 AI 快速恢復正確工作狀態的控制資訊。

不同文件回答不同問題：

```text
README
→ 這個 repository 是什麼？從哪裡開始？

RULES
→ 現在應該怎麼操作？

HANDOFF
→ 目前狀態是什麼？有哪些重要歷史決策與轉折？

正式內容
→ 真正保存了哪些 Knowledge / System / Application？
```

文件分工的目的不是增加文件數量，而是避免一份文件同時承擔互相衝突的責任。

## 適用情境

- 多個 AI 輪流接手同一個長期專案。
- 專案歷史很長，單靠當前對話無法恢復脈絡。
- 架構曾經反覆修改，容易重新走回已否決路線。
- 需要讓不同 AI 依同一套現行規則工作時。

## 不適用情境

- 一次性短任務，不存在交接問題時。
- 文件數量極少、沒有歷史決策與長期狀態時，不需要建立完整 Handoff 體系。

## 實務方法／注意事項

Handoff 應保留會影響下一次決策的重要背景，例如：

- 當前狀態。
- 已確立的架構邊界。
- 重要設計轉折。
- 已否決或暫緩方向及其原因。
- 下一步真正應做的工作。

但 Handoff 不應複製整個 Knowledge repository，也不應取代正式 Rules。

如果 Handoff 與正式操作規則衝突，應由明確指定的規則文件取得操作優先權。

## 我的補充

真正有效的交接文件不是「把所有東西都塞進去」，而是防止下一個 AI 在沒有前情時犯已經犯過的錯，同時讓它知道哪些內容必須回到正式文件確認。
