# 新內容未問題化處理失效紀錄

日期：2026-09-17
狀態：【已確認；已納入流程修正】

## 一、實際問題

本輪新增的工程要求本身也是新的重要內容，但 AI 沒有先把它當成工程問題處理，而是直接進入規則／文件補強。

缺失的處理鏈是：

```text
新內容
→ 問題識別
→ 問題拆解
→ 既有能力檢查
→ 外部研究
→ 同類工具／方法／案例比較
→ 漏洞與失效模式
→ 反方案
→ 結論
→ 規劃
→ 建立
```

實際卻接近：

```text
新要求
→ 直接修改既有流程／建立規則
```

## 二、這不是單純「少搜尋一次」

真正缺口在入口層。

原有「正確成立方案與系統方案」已要求建立前研究、既有能力盤點、外部研究、比較、反方案與 Gate；但它假設 AI 已經知道「現在有一個方案建立問題需要進入該流程」。

本次證明仍存在更早的失效可能：

```text
AI 甚至沒有先判斷「這個新內容是不是問題／需求／證據／限制／候選方案」
```

因此後續即使 Preflight 很完整，也可能在進入 Preflight 前就把錯誤方向方案化。

## 三、問題拆解

本問題至少包含五個子問題：

1. 新內容如何被辨識為工程事件，而不是普通討論內容？
2. 何時必須拆解成問題、需求、限制、假設、證據或候選方案？
3. 何時需要搜尋外部方法、工具、產品與案例？
4. 研究結果如何避免直接變成採用結論？
5. 如何讓下一個 AI 在不增加逐步回傳成本的前提下，仍能知道這個入口已經處理過？

## 四、外部方法比對

AWS Architectural Decision Record（ADR）要求重大架構決策保留 context、decision、consequences，並經過 Proposed／Accepted／Rejected 等狀態；其目的包括避免沒有理由的決策與重複討論。

Microsoft Azure Well-Architected Framework 的 ADR 亦要求問題與背景、考慮過的選項、決策、取捨、狀態與被排除的替代方案，並以持續的決策紀錄保留方向變化原因。

本工程不直接複製 ADR，而是把其「先保留問題、選項、理由、取捨，再形成重大決策」的精神前移成入口控制：

```text
ADR 核心：為重大決策留下可追溯理由
本工程補強：在形成重大決策之前，先確認「到底發生了什麼問題」
```

## 五、根因

1. 把「新內容」與「新方案」的邊界設得太晚。
2. 現有流程重點集中在「方案建立前」，沒有明確管理「方案候選形成前」。
3. 已有規則沒有形成 Problem Intake Gate，AI 可以直接把討論內容轉成施工內容。
4. 過去的成功案例容易讓 AI 誤以為「使用者已經明確說出需求，就可以直接補規則」。
5. 為控制回傳成本，原流程強調批次化，但沒有把「批次內部必須完成問題化與研究」明確寫成必要工作。

## 六、修正原則

正式生命週期增加：

```text
新內容／新要求／新發現
↓
Problem Intake Gate
↓
問題識別與拆解
↓
既有知識／系統／規則檢查
↓
缺口判定
↓
外部研究與比較
↓
漏洞／失效模式／反方案
↓
結論
↓
建立規劃
```

只有結論確認值得進入方案工程後，才建立規劃。

## 七、與狀態／回傳成本的關係

這個修正不是要求每一步建立紀錄或回傳。

```text
微步驟：內部處理，不回傳
研究批次：內部整批完成
問題成立：Checkpoint
結論／是否進入規劃：Checkpoint
規劃成立：同步狀態＋待辦＋依賴＋入口
Gate：Checkpoint
```

因此增加的是「必須完成的思考與研究」，不是「必須增加的訊息數量」。

## 八、正式結論

今後任何可能改變知識、規則、系統、方案、工程流程或架構方向的新內容，都不得直接方案化。

必須先回答：

```text
這是什麼？
為什麼是問題？
問題怎麼拆？
已有什麼？
缺什麼？
外部怎麼做？
有哪些替代方案？
哪裡可能失效？
反方案是否成立？
最後才是：要不要建立？
```

本紀錄保留本次失效，作為後續自然工作驗證的反向測試案例。
