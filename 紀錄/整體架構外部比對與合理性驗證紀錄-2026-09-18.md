## 一、目的

將第一版「AI 單人工作室整體系統企劃書－無 API 版本」中的完整架構責任拆解為功能，逐項與目前外部 Agent Memory、Harness Engineering、Repository-based AI 工作環境及 Agent Runtime 的實務方向進行比對。

本次目的不是尋找一個可以直接複製的外部產品，而是確認：

1. 核心理念是否合理。
2. 功能責任是否缺漏。
3. 是否存在明顯錯誤的架構假設。
4. 哪些能力應現在保留。
5. 哪些能力應延後自動化。
6. 哪些舊式架構形式應在未來重製時淘汰。

## 二、第一版企劃書的核心架構

第一版企劃書不是單純的「使用者 → GPT → GitHub」。

完整概念包含：

- Entry／入口
- Intent／意圖解析
- Response Contract／回應契約
- Orchestration／統御
- Library／圖書館
- Knowledge／知識
- Systems Registry／系統庫
- Plans Registry／方案庫
- Trigger／觸發管理
- Blueprint／藍圖
- GPT Execution／執行
- Verification／驗證
- Evidence & History／證據與歷史
- Evolution／演化與蒸餾

核心工作閉環：

```text
使用者
↓
Intent
↓
Orchestration
↓
Library / Systems / Plans
↓
Knowledge / Capability
↓
Blueprint
↓
GPT Execution
↓
Verification
↓
Evidence / History
↓
Evolution / Distillation
↓
Repository
```

## 三、本次外部比對的主要結果

### 1. GitHub／Repository 作為長期外部記憶

判定：【高度支持】

外部 Agent Memory 與 Harness Engineering 實踐普遍支持：

- Repository-local knowledge
- Markdown / text 作為可檢查來源
- Git versioning
- Repository 作為長期工程記憶
- Index／Cache 作為 derived layer，而非唯一真實來源
- Progressive Disclosure／按需載入

因此本系統的：

> GPT = 短期工作記憶與推理  
> GitHub = 長期外部記憶、狀態、證據、歷史

方向合理。

---

### 2. 大記憶、小 Context

判定：【高度支持】

外部成熟實踐並不要求每次將整個 Repository 載入模型。

較合理模式為：

```text
入口
↓
目前狀態
↓
任務相關系統／方案
↓
必要知識
↓
證據／歷史
```

因此「Repository 可以很大，但單次上下文必須最小充分」是正確原則。

---

### 3. CURRENT／HISTORY 分離

判定：【必要】

外部 Agent Memory 系統普遍需要處理：

- Current truth
- Superseded information
- Archive
- Provenance
- Historical context

因此：

```text
CURRENT
PENDING
DEPRECATED
SUPERSEDED
HISTORICAL
```

應作為資料狀態，而不是單純資料夾分類。

真正需要控制的是「歷史是否污染目前工作 Context」，不是歷史檔案數量本身。

---

### 4. Knowledge ≠ Library

判定：【正確且必要】

Knowledge：

> 知道什麼。

Library：

> 知道有哪些資料，以及如何定位、檢索、組裝資料。

因此：

```text
Knowledge
↓
Library Index / Retrieval
↓
相關性／狀態／衝突檢查
↓
最小充分 Context
```

圖書館不是知識本體，而是知識的定位與取用層。

---

### 5. Knowledge ≠ System

判定：【正確】

```text
Knowledge = 知道什麼
System = 能做什麼
Plan = 如何解決
Rule = 必須遵守什麼
```

系統應引用／依賴知識，而不複製知識。

---

### 6. Plan 作為一級資產

判定：【高度支持】

外部 Harness Engineering 已將 execution plans、completed plans、technical debt 等視為 Repository 中的一級工程資料。

因此「方案庫」不是附屬文件，而是可重用的問題解決能力資產。

---

### 7. Intent／意圖解析

判定：【必要】

單純關鍵詞不能決定工作。

例如：

```text
「方案四現在怎樣？」
→ STATUS

「重新研究方案四。」
→ RESEARCH
```

因此：

```text
Keyword
↓
Candidate Recall
↓
Intent
↓
Context
↓
Orchestration
```

合理。

---

### 8. Trigger 不等於自動執行

判定：【保留目前定義】

Trigger 應主要負責候選能力召回，而不是直接控制完整工作流程。

因此：

```text
Trigger = Candidate Recall
```

而不是：

```text
Trigger = Execution Engine
```

這可以避免關鍵詞誤觸發與責任集中。

---

### 9. Orchestration／統御

判定：【合理，但必須保持薄】

統御的責任是：

> 根據目標、狀態、能力、限制、證據與風險決定下一步。

可以選擇：

- 查知識
- 查系統
- 查方案
- 研究
- 規劃
- 執行
- 驗證
- 交接
- 保存

但不得演化為：

> 所有系統資料、所有業務邏輯、所有執行功能的中央全能控制器。

---

### 10. Blueprint／藍圖

判定：【合理】

小任務不需要完整 Blueprint。

應依任務規模：

```text
小型 → 直接處理
中型 → 簡易規劃
大型 → 完整 Blueprint
```

這可以避免治理系統本身成為工作負擔。

---

### 11. Verification／驗證

判定：【必要】

「文件存在」不能證明「能力成立」。

至少應區分：

- 結果正確性
- 行為正確性
- 架構健康性

並保留：

- 測試
- 實測
- 回歸
- Observation
- Evidence

---

### 12. Evidence／證據

判定：【必要】

重要結論不應只有：

> GPT 說正確。

應保存：

- 來源
- 研究結果
- 測試結果
- 回歸結果
- 決策理由
- 修改內容
- 驗證結果

目的：

> 讓未來 GPT 能理解「這個結論為什麼存在」。

---

### 13. Continuous Distillation／持續蒸餾

判定：【核心能力】

長期主要風險不是資料不足，而是：

```text
資料增加
+
舊規則增加
+
例外增加
+
重複系統增加
+
責任漂移
+
版本漂移
↓
系統熵增加
```

因此：

```text
使用
↓
Observation
↓
問題
↓
改善
↓
蒸餾
↓
重構
↓
歷史保存
```

是必要閉環。

## 五、外部比對後確認的三個核心原則

### 原則一：概念責任可以很多，實體系統必須少

目前可以有：

- Intent
- Trigger
- Library
- Orchestration
- Blueprint
- Verification

等責任。

但不代表每個責任都必須建立一個獨立軟體。

應維持：

> 大架構，小實體化。

---

### 原則二：資料、狀態、Context Loading 是三個不同維度

#### Data Entity

```text
Knowledge
System
Plan
Rule
Decision
Project
Evidence
Test
History
```

#### Data State

```text
CURRENT
PENDING
DEPRECATED
SUPERSEDED
HISTORICAL
UNCERTAIN
CONTESTED
```

#### Context Loading

```text
L0 Entry
L1 Current
L2 Task System / Plan
L3 Necessary Knowledge
L4 Evidence / History
L5 Cross-project
```

不得把三者混成單一分類樹。

---

### 原則三：Canonical Source 不等於唯一文件

合理模型：

```text
Canonical Source
↓
Derived Views
├── Index
├── Summary
├── Handoff
├── Navigation
└── Search Index
```

真正要求的是：

> 每一項正式事實必須有清楚的權威來源。

而不是禁止任何摘要、索引或交接文件存在。

## 六、外部比對後確認的實體架構

將第一版企劃書重新抽象後，可分成五個運行責任層。

### 1. 理解層

```text
Entry
Intent
Response Contract
Work Mode
```

回答：

> 使用者現在到底想做什麼？

### 2. 調度層

```text
Trigger
Orchestration
Blueprint
```

回答：

> 現在應使用什麼能力、讀什麼資料、先做什麼？

### 3. 資產層

```text
Library
Knowledge
Systems
Plans
Rules
Projects
```

回答：

> 我們有什麼？

### 4. 工作閉環

```text
GPT Execution
Verification
Evidence
History
```

回答：

> 做了什麼？是否正確？證據在哪？

### 5. 演化層

```text
Observation
Distillation
Refactoring
Deprecation
Archive
```

回答：

> 系統如何避免越用越複雜、越用越錯？

## 七、確認不應提前建立的能力

目前沒有足夠實際瓶頸，不應提前建立：

- Vector Database
- Embedding Server
- 完整 RAG Pipeline
- Agent Framework
- Multi-Agent Runtime
- Event Bus
- Scheduler
- Background Worker
- 大型 Trigger Engine
- 大型 Intent Engine
- 自動 Orchestrator
- 自動蒸餾平台

未來應採：

```text
人工流程
↓
實際使用
↓
觀察瓶頸
↓
確認瓶頸重複出現
↓
設計自動化
↓
驗證收益
↓
再正式化
```

---

## 八、確認未來重製時應淘汰的舊架構形式

目前已有足夠證據判定下列形式不應成為新版正式架構：

1. 以檔名／路徑作正式身份。
2. 以單一 status 欄位承擔所有狀態。
3. 以「建立文件」判斷「系統成立」。
4. 由中央統御分支保存所有系統完整資料。
5. Trigger Registry 直接承擔完整執行邏輯。
6. 中央統御同時負責問題解決、方案策略與業務執行。
7. 所有知識任務固定使用同一套舊系統流水線。
8. 因為未來可能需要，就提前建立大型基礎設施。

注意：

> 淘汰的是舊架構形式，不是刪除歷史能力與歷史證據。

## 九、目前正式設計判定

### 已確認

1. 第一版無 API 企劃書的核心理念合理。
2. GPT + GitHub 可以形成可長期工作的外部記憶環境。
3. Repository 應作為重要 Canonical Source。
4. Knowledge、Library、System、Plan 的責任區分成立。
5. Intent、Trigger、Orchestration、Blueprint 的概念有必要，但不應全部實體化。
6. Verification、Evidence、History 是必要閉環。
7. Continuous Distillation 是長期必要能力。
8. CURRENT 與 HISTORY 應分離。
9. 大 Repository + 小 Context 是合理方向。
10. 無 API 階段不需要 Vector DB／Multi-Agent Runtime 等大型基礎設施。
11. 未來 API 應自動化已證明的人工瓶頸，而不是重新定義資料語義。
12. 不需要因本次外部研究重新設計整套架構。

### 仍屬推論

1. 目前各功能最終應實體化到什麼程度。
2. 最佳入口需要幾個檔案。
3. 最終 Library Index 的最佳格式。
4. 哪些 GPT 判斷應正式轉成規則。
5. 未來何時真正需要 Vector／Hybrid Search。
6. API 後最適合的 Agent Runtime 結構。

### 待實際驗證

1. 第一次真正蒸餾後，日常工作介面是否明顯降低複雜度。
2. 新 GPT 無歷史記憶是否能正確接手。
3. GPT 是否能正確定位 Library / Knowledge / System / Plan。
4. 最小 Context 是否足以完成常見工作。
5. 是否出現自然的檢索、路由或 Context bottleneck。
6. FIELD 是否在自然工作中產生。

## 十、設計決定

### 決定

**保留核心架構，停止概念性擴張，進入實體化與實際驗證階段。**

### 不採用

不因外部工具已有：

- Vector Search
- Multi-Agent
- Agent Runtime
- Scheduler
- Event Bus
- Automated Memory

就提前移植。

### 理由

目前最重要的未知量不是：

> 「我們還缺多少功能？」

而是：

> 「現有核心架構在真正工作時是否能以低 Context 成本正確運作？」

因此現在應取得實際證據，而不是繼續增加抽象層。

## 十四、最終結論

本次外部研究沒有發現足以推翻第一版企劃書核心架構的證據。

相反地，外部實踐對以下原則提供了相當程度的交叉支持：

```text
Repository 作長期外部記憶
+
Canonical Source
+
Progressive Disclosure
+
Knowledge / System / Plan 分離
+
Intent / Routing
+
Verification / Evidence
+
Current / History 分離
+
Continuous Distillation
+
需求驅動自動化
```

因此正式判定：

> **整體架構合理，核心方向保留，不進行架構重設。**

目前真正需要驗證的是「實體化後是否好用」，而不是再證明「概念上是否完整」。

本紀錄完成後，工程焦點正式回到：

> **第一次實際蒸餾 → 清理 CURRENT → 無記憶 GPT 接手 → 自然工作驗證。**
