# 舊模式重疊能力重製映射 v1.0

日期：2026-09-17
狀態：【已建立；作為未來整體大重製輸入；不代表新架構已正式採用】

## 一、文件定位

本文件不是新方案，也不是新系統規格。

用途只有一個：

> 將目前 Repository 中已存在的舊模式能力完整盤點，保存其歷史位置、目前價值與重製方向，供未來整體大重製時進行彙整、融合、疊代與淘汰判定。

本文件不修改舊能力、不把候選能力提前升格為正式架構，也不因「新候選能力」欄位存在就代表已完成設計。

---

## 二、判定詞定義

| 欄位 | 定義 |
|---|---|
| 保留 | 舊能力的核心目的／已驗證價值在重製後仍應存在；不代表保留原文件或原實作。 |
| 融合 | 舊能力本身有價值，但與其他能力存在責任、資料或流程重疊，重製時應合併成較少、更清楚的能力。 |
| 淘汰 | 舊能力的獨立存在沒有必要；其價值應由其他能力吸收、推導或直接移除。 |
| 歷史保留 | 舊文件／案例保留作為證據與演化紀錄，但不再作為新版架構直接來源。 |
| 待判定 | 目前證據不足，不提前決定。 |

注意：

```text
保留能力 ≠ 保留舊檔案
融合能力 ≠ 現在就合併檔案
淘汰能力 ≠ 刪除歷史
```

## 四、目前盤點後的主要融合群

### G1：系統身份與目錄群

```text
系統管理統御分支
＋
System Registry
＋
小系統列表
＋
系統／方案／知識索引
```

重製候選：

> `System Identity + System Catalog + Typed Relationships + Lifecycle View`

原則：一個正式系統只有一個穩定 System ID；不同分支可以建立 View / Index，不複製正式身份。

### G2：觸發與啟動安全群

```text
觸發條件管理
＋
Event ID
＋
防二次啟動
＋
冪等
＋
防循環
＋
多重匹配歧義
```

重製候選：

> `Trigger Registry + Activation Safety Guard`

原則：Trigger Registry 找到可能的能力；Safety Guard 決定是否需要補充啟動；實際工作仍由目標系統／方案執行。

### G3：變更與更新群

```text
更新監控
＋
定期審查
＋
外部依賴變更
＋
更新影響分析
＋
成本判斷
```

重製候選：

> `Change Detection / Intake → Impact Analysis → Evolution Decision`

原則：偵測、影響分析、更新決策不應全部塞進一個系統。

### G4：驗證與證據群

```text
後續工作觸發式順便驗證
＋
實測結果回寫檢查
＋
驗證狀態
＋
Evidence / Receipt
```

重製候選：

> `Validation Model + Evidence / Receipt + Natural-work Validation`

原則：自然工作驗證是一種驗證策略，不必永久作為獨立大型系統。

### G5：知識處理群

```text
分類
＋
搜尋
＋
來源／證據
＋
比較／衝突
＋
整合
＋
更新
```

重製候選：

> `Task-dependent Knowledge Operations`

原則：保留能力，不保留舊有固定串接。分類、搜尋、證據、比較、整合、更新應依任務需求組合。

### G6：方案組合群

```text
方案管理
＋
方案紀錄
＋
系統組合
＋
方案驗證
```

重製候選：

> `Solution Composition + Solution Record + Lifecycle / Validation`

原則：方案是目的導向的能力組合，不是中央工作流引擎。

### G7：異常與問題解決群

```text
Expected / Actual
＋
異常偵測
＋
嚴重程度
＋
問題解決路由
＋
問題解決系統
```

重製候選：

> `State/Anomaly Detection → Problem-Solving Routing → Problem-Solving Capability`

原則：統御負責發現與路由；問題解決負責研究與解法；不可合併成中央全能控制器。

## 五、確定淘汰的不是「能力」，而是舊架構形式

目前已有足夠證據可以直接列入重製淘汰：

1. 以檔名／路徑作為正式身份。
2. 以單一 status 欄位承擔所有狀態。
3. 以「建立文件」判斷「系統成立」。
4. 以統御分支保存所有系統完整內容。
5. 讓 Trigger Registry 直接承擔完整執行邏輯。
6. 讓中央統御分支同時承擔問題解決、方案策略與業務執行。
7. 以固定舊系統流水線作為所有知識任務的唯一流程。
8. 因資料量增加就預先建立多層管理系統。

這些淘汰的是「架構形式」，不是把歷史資料刪掉。

## 六、目前保留但不得提前正式化的能力

以下能力目前值得保留，但在大重製前仍須重新做共同資料契約與實際驗證：

- System Identity
- Thin System Catalog
- Trigger Registry
- Activation Safety
- Change Detection
- Impact Analysis
- Validation / Evidence
- Natural-work Validation
- Problem Solving
- Anomaly Detection / Routing
- Search / Retrieval
- Provenance / Evidence Analysis
- Comparison / Conflict Analysis
- Knowledge Synthesis
- Solution Composition
- Lifecycle Management

「保留」代表保留問題與能力價值，不代表目前文件中的責任邊界、欄位或流程原封不動搬入新版。

## 七、未來整體大重製的使用方式

大重製開始時，不直接逐檔改寫舊系統。

應使用本映射作為第一層輸入：

```text
舊 Repository
↓
舊能力盤點
↓
本重製映射
↓
能力去重／融合
↓
共同資料契約
↓
責任重新分配
↓
新候選架構
↓
外部方法再次比對
↓
候選方案確認
↓
新系統建立
↓
最小實測
↓
舊能力逐項退役／保留歷史
```

每一項舊能力在重製時必須能落到以下其中一種結果：

```text
保留
融合
重新拆分
部分取代
完全取代
淘汰
歷史證據保留
```

不得直接以「新版本」覆蓋舊能力而失去演化理由。

## 八、目前結論

目前 Repository 的舊模式不是單純「錯誤架構」。它包含大量仍有價值的能力，但早期模式傾向：

```text
集中式索引
＋
集中式觸發
＋
集中式管理
＋
固定系統流水線
```

未來整體重製的主要方向不是把這些能力全部推翻，而是：

```text
集中式「目錄／身份／最小路由」
        ↓
保留

集中式「完整管理／完整執行」
        ↓
拆分／融合／淘汰

舊系統各自重複保存的資料與責任
        ↓
共同資料契約／共同關係模型

固定流水線
        ↓
依任務動態組合能力
```

因此，本文件的主要價值不是決定現在要改什麼，而是防止未來大重製時「因為舊架構不好，就把舊架構中已經證明有價值的能力一起丟掉」。
