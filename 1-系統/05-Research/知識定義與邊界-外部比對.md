# 知識定義與邊界－外部比對紀錄

> 狀態：**【已完成外部比對；待實際資料驗證】**
> 日期：2026-09-16

## 一、稽核目標

檢查 Ai-knowledge 原本對「知識」的定義是否過度簡化，並確認其與知識管理標準、研究與成熟知識工具的核心做法是否一致。

## 二、原有做法

原文件將知識定義為：經過整理、可獨立理解、能在不只一個具體情境中重複使用的基本原理、判斷或方法；並把尚未驗證的原始資訊、單一專案設定、一次性決定等排除在知識之外。

## 三、外部研究

### 1. ISO 30401

類型：標準／知識管理系統

ISO 30401 將 knowledge 定義為能支援在情境中有效決策與行動的 understanding，並指出知識可以存在於個人、團隊與組織之間，也有 tacit、expressible、codified、embedded 等不同形式。標準同時指出知識會隨時間、關係與外部事件改變。來源：

- https://www.iso.org/standard/68683.html
- https://www.iso.org/obp/ui?_escaped_fragment_=iso:std:iso:30401:dis:ed-2:v1:en

### 2. 知識管理研究

Davenport 與 Prusak 的實務性定義把 knowledge 描述為經驗、情境資訊、價值與專業洞見的組合，能支援評估與吸收新的經驗與資訊。相關研究也指出 knowledge 的定義本身存在多種觀點，不宜假定單一普遍定義。來源：

- https://www.sciencedirect.com/science/article/pii/S1053482211000507

### 3. Capacities

Capacities 把 object 與 object type 分開；object type 描述某一類內容的結構，properties 提供結構化資訊，tags 則用於跨內容主題連結，並可透過 filter、sort、group、query 建立不同檢視。這表示「內容」「結構」「分類」「關聯」「查詢」不是同一個概念。來源：

- https://docs.capacities.io/reference/content-types
- https://docs.capacities.io/reference/properties
- https://docs.capacities.io/reference/organizational-structures

### 4. Obsidian

Obsidian 以 Markdown 作為主要筆記媒介，同時提供 properties 保存結構化資訊，以及 internal links 建立筆記間的關聯。這同樣說明「檔案」與「知識關係」可以分開處理。來源：

- https://obsidian.md/help/properties
- https://obsidian.md/help/links

## 四、比較矩陣

| 項目 | 原 Ai-knowledge | 外部共通觀察 | 稽核結果 |
|---|---|---|---|
| 知識核心 | 可重用的原理／判斷／方法 | 支援理解、決策、行動、know-how、insight | 原方向正確，但範圍過窄 |
| 情境 | 強調跨場景 | ISO 明確強調 context-specific | 必須保留適用情境，不要求跨場景 |
| 文件 | 容易把知識與文件綁在一起 | 工具通常把內容、型別、屬性分開 | 分離 |
| 驗證 | 尚未驗證通常不直接成為知識 | KM 強調知識可有不同形式與狀態 | 分離「知識」與「可信程度／狀態」 |
| 結構 | 主要靠正文 | 成熟工具使用 properties / object types / links | 未來應保留結構化欄位的可能性 |
| 關聯 | 原定義沒有充分處理 | Obsidian、Capacities 都重視 links / object relations | 不把知識視為孤立文件 |
| 資料階梯 | 隱含資料→資訊→知識的方向 | 此模型存在爭議 | 不作硬規則 |
| 知識形式 | 偏向可書寫原理 | ISO 包含 tacit、codified、embedded 等 | 文件只是可保存的一部分 |

## 五、核心發現

### 1. 原定義最大的問題不是錯，而是太窄

「可重用」仍然是 Ai-knowledge 很重要的工程判準，但「跨場景」過強；特定遊戲、特定工具、特定流程中的穩定 know-how 仍然可能是知識。

### 2. 知識與文件必須分開

Markdown 檔案是保存媒介，不是知識本體。這一點與成熟工具的 object/type/property 模型一致。

### 3. 知識與可信程度必須分開

某個內容可以是目前最佳可用理解，但仍然有不確定性。因此「是不是知識」與「目前有多大把握」應由不同機制處理。

### 4. 情境不是缺陷，而是知識的一部分

知識的適用條件本身就是知識內容的一部分。錯誤地把條件拿掉，反而容易造成錯用。

## 六、過度簡化檢查

原版本的以下表述需要修正：

- 「知識必須跨場景」→ 過強。
- 「核心內容必須能獨立理解」→ 過於絕對；應要求內容足以支援正確使用，必要時可以依賴明確關聯的其他知識。
- 「尚未驗證就不算知識」→ 混淆知識內容與知識狀態。

## 七、過度工程化檢查

目前沒有發現需要新增資料庫、知識圖譜、複雜知識 ID 或自動可信度評分的證據。

因此只修正概念模型，不新增複雜基礎設施。

## 八、設計決定

**修改原文件。**

採用新的工作定義：

> 知識是經過理解、整理或驗證後，能在明確情境與適用條件下支持後續理解、判斷、決策或行動的可重用內容。

保留「降低未來重新理解、研究與判斷成本」作為 Ai-knowledge 的工程目的。

## 九、實際驗證計畫

使用現有知識文件進行案例測試：

1. 一般基礎原理。
2. 專案限定規則。
3. 一次性決策。
4. 尚未完全驗證的候選結論。
5. 來源資料。
6. AI 討論紀錄。
7. 經驗／案例。
8. 可重複使用的方法。

檢查新的定義能否穩定區分這些內容，而不產生大量人工分類爭議。

## 十、結論

本輪外部比對支持保留「知識具有可重用價值」的核心方向，但要求把「情境、文件、證據、狀態、關聯」從原本的單一知識定義中拆開。
