# 方案管理－外部比對

狀態：**【已完成第一輪外部方法比對；待實際資料驗證】**

## 一、比對目的

確認「多系統組合成方案」需要哪些管理資訊，避免 Ai-knowledge 只依自身設計直覺增加管理欄位。

## 二、對照對象

### 1. Architecture Decision Record（ADR）

Microsoft Azure Well-Architected Framework 的 ADR 方法指出，架構決策應記錄問題背景、考慮的選項、決策結果、重要取捨、信心與狀態；重大方向改變時，保留新的取代關係，而不是抹除舊決策。

可吸收：

- 背景／問題
- 候選選項
- 決策
- 取捨
- 狀態
- 影響／後果
- 重大變更歷史

不直接照搬：

- 不建立獨立 ADR 系統
- 不要求所有小決策都建立紀錄
- 不建立正式 ID

### 2. Azure Well-Architected / Solution Architecture

Microsoft 的架構指引同時強調需求、限制、取捨、風險、概念驗證（PoC）、實際觀察與後續優化。這支持方案紀錄不能只描述「怎麼設計」，還要有驗證與實際結果。

可吸收：

- 必要條件／限制
- 重大取捨
- 高風險部分的驗證
- 實際結果
- 依觀察進行後續更新

不直接照搬：

- 不建立完整企業架構治理流程
- 不建立成本、合規、團隊等與目前需求無關的欄位

### 3. Notion Database

Notion 使用 Database Templates 建立固定紀錄結構，並以 Properties、Relations、Rollups 等機制補充狀態、分類、關係與彙整能力。

可吸收：

- 固定模板
- 狀態
- 關係
- 必要時的屬性
- 必要時的篩選與排序

不直接照搬：

- 不預先建立資料庫
- 不預先建立大量欄位
- 不建立 Rollup 類自動彙整機制，除非實際需求出現

## 五、重要結論

### 已支持

1. 方案需要記錄「為什麼這樣組合」，不能只記系統清單。
2. 方案需要記錄實際驗證與結果。
3. 重大決策需要保留背景、取捨與變更歷史。
4. 固定模板能降低重複建立成本。
5. 關係與結構化屬性有價值，但應在資料量或搜尋成本真正增加後導入。

### 尚未證明需要

- 方案評分
- 自動推薦
- 自動依賴分析
- 自動影響分析
- 複雜版本管理
- 專用資料庫
- 完整工作流引擎
