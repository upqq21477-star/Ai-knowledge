# 系統管理統御分支 v1.0

日期：2026-09-17
狀態：正式建立；待實際運作驗證

## 一、定位

本分支是 Ai-knowledge 的 System Registry / System Catalog（系統目錄與系統關係索引）。

核心目的：

> 用最少資訊掌握所有正式系統的身分、位置、狀態、所屬方案與主要關係，讓其他系統能快速找到並理解應交給誰。

本分支不是所有系統的總控制器，不執行各系統的業務邏輯。

## 二、系統最小資料

每個正式系統原則上只有一個 System ID。

目錄記錄至少包含：

| 欄位 | 說明 |
|---|---|
| System ID | 系統唯一識別碼 |
| 系統名稱 | 正式名稱與版本資訊 |
| 分類 | 粗略功能分類 |
| 系統文件位置 | 正式系統文件目錄 |
| 所屬方案 | 目前正式歸屬；未歸屬可標記待歸屬 |
| 知識關係 | 系統依賴／承載的主要知識書 ID 或位置 |
| 功能摘要 | 一至數句描述核心功能 |
| 狀態 | 候選／建立中／驗證中／可用／停用／廢棄 |
| 更新狀態 | 是否需要重新檢查 |

詳細系統內容仍保留在系統本體文件，不複製進目錄。

## 三、核心工作

1. 維持全域系統清單。
2. 維持 System ID 與系統文件位置。
3. 維持系統與方案的關係。
4. 維持系統與主要知識的關係索引。
5. 提供系統名稱、分類、狀態等快速搜尋入口。
6. 接收 Trigger Registry 找到的 System ID，查詢其所屬方案與目前狀態。
7. 在系統新增、改名、搬移、升級、整合、停用、廢棄時維持目錄一致性。

## 四、路由位置

```text
事件
↓
觸發條件管理系統
↓
System ID
↓
系統管理統御分支
↓
確認系統身分、狀態、所屬方案
↓
方案
↓
相關系統
```

## 五、與觸發條件管理系統的關係

觸發條件不再作為本分支的主要資料欄位。

原因：

- 觸發條件屬於「事件 → 能力」的路由索引。
- 系統目錄屬於「系統 → 關係」的索引。
- 兩者更新原因不同。
- 兩者查詢目的不同。
- 分離後可避免系統目錄逐漸膨脹成規則引擎。

因此：

```text
Trigger Registry
= 找系統

System Registry
= 認識系統
```

## 六、粗略分層

初期只採粗略分類，不建立過深階層。

建議分類維度包括：

- 核心運作
- 管理
- 搜尋／研究
- 知識
- 驗證
- 問題解決
- 更新
- 其他

分類主要服務於搜尋與閱讀，不代表新的架構層級。

## 七、資料規模策略

初期使用：

```text
一份全域系統目錄
+
粗分類
+
metadata
+
搜尋／篩選
```

不預先按數量拆成多個管理系統。

只有當以下問題實際出現時才考慮分片：

- 搜尋成本明顯上升
- 更新責任開始分化
- 不同分類需要不同維護週期
- 資料同步開始產生錯誤
- 單一目錄已無法被 AI 有效讀取
- 不同分支需要不同管理規則

分片後仍使用同一個 System ID；分支目錄應是視圖或索引，不應複製正式系統身分。

## 八、禁止事項

- 不執行其他系統的實際工作。
- 不保存所有系統的完整內容。
- 不取代方案。
- 不取代問題解決系統。
- 不把所有 Trigger 邏輯重新集中到本分支。
- 不因系統數量增加而自動建立更多管理層。
- 不以目錄摘要取代系統的正式狀態來源。

## 九、驗證要求

第一階段驗證：

```text
新增／既有系統
→ 系統目錄能定位
→ 能找到所屬方案
→ 能找到主要知識關係
→ 能確認狀態
```

第二階段驗證：

```text
Trigger 命中
→ System ID
→ 系統管理統御分支
→ 方案
→ 系統
```

第三階段再檢查：

- 系統改名／搬移後關係是否維持
- 系統升版後 Trigger 是否需要更新
- 系統停用後是否仍被錯誤路由
- 一個事件命中多系統時是否能正確處理

## 十、與未來「統御應用」的關係

本分支目前只處理「系統目錄與路由所需的最低管理能力」。

未來若建立更高層級的「統御應用」，可以把本分支作為其中一個能力分支，但不得因此提前把所有治理、協調、監控、異常處理等能力全部塞入本分支。
