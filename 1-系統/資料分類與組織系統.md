# 資料分類與組織系統

狀態：**【建立中；已完成外部方法比較；待第二輪實際案例驗證】**

## 一、系統目的

本系統負責回答：

> **資料應如何組織，才能在目前與未來的工作中被理解、維護、探索、定位與重用？**

本系統不是單純建立資料夾，也不是替每份資料決定唯一分類，而是建立一套可重複使用的組織決策流程。

核心目標是降低：

- 找不到資料的成本。
- 判斷資料歸屬的成本。
- AI 理解資料結構的成本。
- 後續維護與擴充成本。
- 因分類錯誤造成的探索與搜尋成本。

外部方法比較顯示，成熟知識工具通常不只使用階層目錄，而會同時利用內容、屬性、標籤、關係、篩選與查詢。故本系統將「分類」與「可檢索性」分開處理。

## 二、系統邊界

本系統處理：

- 分類目的。
- 分類對象。
- 分類依據與維度。
- 分類結果。
- 目錄是否應承擔某分類。
- 文件名稱與必要描述是否有助於定位。
- 其他維度是否應以內容、命名、屬性、標籤或關係表示。
- 分類結構是否增加或降低實際管理、探索與搜尋成本。

本系統不直接負責：

- 從大量未知資料中尋找候選內容（資料探索）。
- 針對具體問題取得候選資料（資料搜尋）。
- 對搜尋結果進行最終內容正確性裁決（來源與證據分析）。
- 更新既有知識內容（知識更新）。

分類可以支援探索與搜尋，但分類本身不是探索或搜尋。

## 三、核心模型：組織不等於資料夾

成熟工具的共同做法可以抽象為：

```text
資料
│
├─ 結構位置
├─ 文件名稱
├─ 內容
├─ 屬性／描述
├─ 標籤
├─ 關係
└─ 其他可檢索特徵
```

因此：

```text
分類 ≠ 資料夾
目錄 = 分類的一種實作
```

資料可能具有多個維度，但不應把所有維度都變成目錄層級。

例如同一份文件可能同時具有：

```text
功能：搜尋
資料性質：知識
領域：AI 知識管理
物件：系統
狀態：待驗證
```

這些是不同維度。`0-知識` 的目錄主要承擔功能維度，其餘維度是否結構化，應由實際使用需求決定。

## 四、輸入

主要輸入包括：

1. 待組織的資料或文件。
2. 組織目的。
3. 資料之間已知的差異。
4. 實際需要的瀏覽、探索、搜尋與維護方式。
5. 現有目錄與分類結構。
6. 搜尋失敗、結果過多、定位困難等實際案例。
7. 已知的文件名稱、術語與關聯。

## 五、輸出

系統輸出不一定是新資料夾，可能包括：

- 保留目前分類。
- 將資料移入既有分類。
- 建立新的功能分類。
- 改變分類依據。
- 調整文件名稱，使其更容易定位。
- 補充必要的文件摘要或描述。
- 將某些資訊留在文件內容中。
- 建議以屬性、標籤、關係或查詢表達其他維度。
- 判定目前資料不足以支持新的分類。
- 發現目前分類造成實際成本，需要重新設計。

## 六、分類決策流程

```text
開始
↓
確認組織目的
↓
確認分類對象
↓
確認分類要回答的問題
↓
列出可能分類維度
↓
判斷目前目的最需要哪個維度
↓
檢查現有分類能否合理容納
├─ 可以 → 使用既有分類
└─ 不可以
      ↓
    判斷是否真的存在新的功能需求
      ├─ 否 → 不建立新分類
      └─ 是 → 建立最小必要分類
↓
檢查文件名稱與描述是否足以定位
├─ 足夠 → 保留
└─ 不足 → 改善名稱／必要描述
↓
判斷是否需要落實為目錄
├─ 不需要 → 留在內容／名稱／屬性／關係
└─ 需要 → 建立或調整目錄
↓
實際使用
↓
觀察瀏覽／探索／搜尋／維護成本
↓
必要時重新分類
```

## 七、功能分類與目錄

目前 `0-知識` 採功能導向分類，最多兩層：

```text
0-知識/
└─ 功能分類/
   └─ 原理文件.md
```

這是 Ai-knowledge 的工程成本控制規則，不是通用分類學定律。

如果同一功能需要更多原理，優先增加文件，而不是建立第三層目錄。

如果未來實際驗證證明兩層造成的成本高於收益，再重新評估。

## 八、分類維度

目前區分：

- 功能
- 資料性質
- 領域
- 物件
- 狀態
- 適用範圍

其中 `0-知識` 主要使用「功能」作為第二層目錄維度。

其他維度原則上由：

- 文件內容。
- 文件名稱。
- 引用。
- 必要的屬性。
- 必要的標籤。
- 必要的關係。

表達。

只有當某維度實際影響以下工作時，才考慮將它結構化：

- 搜尋。
- 篩選。
- 排序。
- 驗證。
- 維護。

不能因為工具支援某種欄位或標籤，就預先為所有資料建立該欄位。

## 九、可檢索性

分類完成後，還要檢查資料是否容易被搜尋系統定位。

最低限度應注意：

```text
文件名稱
↓
是否能表達核心功能／主題

內容開頭／摘要
↓
是否能快速判斷文件用途

正文術語
↓
是否包含實際使用時可能出現的核心概念

分類位置
↓
是否提供合理的搜尋範圍
```

這不是要求每份文件建立完整 metadata，而是避免「分類正確，但名稱與內容讓搜尋仍然困難」。

## 十、最小分類原則

新增分類前至少回答：

1. 是否有明確實際功能需求？
2. 是否存在一組可以獨立描述的原理或資料？
3. 現有分類是否無法合理容納？
4. 新分類是否降低未來成本？
5. 是否只是因為某個主題暫時出現很多次？
6. 是否其實只需要改善文件名稱或搜尋方式？

如果只是主題增加，而沒有獨立功能需求，不建立新功能分類。

## 十一、分類錯誤診斷

### 1. 混用分類維度

例如：

```text
0-知識/
├─ 系統/
├─ AI/
├─ 已確認/
└─ 搜尋/
```

這混合了物件、領域、狀態與功能。

### 2. 把目錄當成完整分類模型

資料可能有多個維度，但目錄只需要承擔最主要且最穩定的維度。

### 3. 為少量資料建立過深結構

目錄深度增加不代表資料更有秩序；如果探索成本反而增加，就是分類失敗。

### 4. 把搜尋問題誤判成分類問題

如果文件已經合理歸類，但使用者只是用不同詞彙尋找，應先檢查搜尋與查詢改寫，而不是立即建立新分類。

### 5. 把命名問題誤判成分類問題

如果資料位置合理，但文件名稱無法反映用途，優先改善名稱或描述，不應新增資料夾。

## 十二、與資料探索與搜尋系統的介面

本系統提供：

```text
功能分類
目錄結構
文件名稱
必要描述
必要的結構化資訊
```

供資料探索與搜尋系統利用。

資料探索與搜尋系統反過來提供：

```text
找不到資料的案例
結果過多／過少的案例
搜尋改寫次數
搜尋範圍
搜尋成本
```

這些資料用於判斷：

```text
分類問題？
命名問題？
描述不足？
搜尋問題？
資料缺口？
```

兩個系統形成回饋，但不合併。

## 十三、分類品質驗證

不要只問「分類看起來是否合理」，而應使用真實任務測試：

### A. 放置測試

新增文件時，使用者能否快速判斷應放在哪個功能分類？

### B. 瀏覽測試

不知道文件名稱時，能否從功能分類逐步找到相關資料？

### C. 搜尋測試

知道問題但不知道文件名稱時，分類是否能協助縮小搜尋範圍？

### D. 維護測試

文件增加後，分類是否仍然容易維護？

### E. 誤分類診斷

若任務失敗，是否能區分：

```text
分類錯誤
命名錯誤
描述不足
搜尋策略錯誤
資料不存在
```

## 十四、第二輪實測指標

後續實測不只記錄「找到／找不到」，至少觀察：

| 指標 | 觀察內容 |
|---|---|
| 定位成功 | 是否能找到目標資料 |
| 首次定位 | 第一次搜尋／瀏覽是否找到 |
| 重試次數 | 需要幾次改寫或返回 |
| 干擾量 | 是否出現大量無關資料 |
| 閱讀成本 | 找到前需要讀多少資料 |
| 分類判斷成本 | 新文件歸類是否困難 |
| 維護成本 | 增加資料後結構是否仍清楚 |

不預先設定固定數值門檻。先累積案例，再決定是否需要量化標準。

## 十五、可移植性

本系統不依賴：

- 特定程式語言。
- 特定資料庫。
- 特定 UI。
- 特定 AI 模型。
- 特定專案。

在檔案系統、文件庫、資料庫或其他環境中，都可以使用相同的分類決策原理；具體目錄、欄位或索引則由實作層決定。

## 十六、Ai-knowledge 目前實測結果

目前觀察到：

```text
0-知識/
├─ 分類/
├─ 知識/
└─ 管理/
```

其中 `分類` 與 `管理` 已符合功能導向；`知識/` 仍承載早期建立、尚未完成重新分組的文件。

這不是單純分類原理錯誤，而是 repository 正處於「舊結構 → 功能系統化」的過渡狀態。

因此目前最合理的優化不是新增複雜搜尋技術，而是：

1. 查找既有歷史分類與系統設計。
2. 依既有分類決策重新檢查 `0-知識/知識/`。
3. 只在有明確功能需求時建立新分類。
4. 同時檢查文件名稱與可檢索性。
5. 以實際搜尋任務驗證分類結果。

## 十七、外部方法比較後保留的設計

### Obsidian

參考其「Markdown 文件 + Properties + Search + Bases」模式，保留：

- 文件仍是主要資料本體。
- 結構化資訊只在實際需要時增加。
- 搜尋可以利用內容與屬性，而不是只靠目錄。

### Notion

參考其 workspace search 與 database/filter 的區分，保留：

- 全域內容搜尋與結構化篩選不必視為同一種操作。

### Tana

參考其 typed node、field、query 與 search node，保留：

- 結構化描述可以支援篩選與查詢。
- 不因工具能做到就預先建立完整欄位系統。

### Capacities

參考其 object type、tag、property 與 exact／semantic search 的區分，保留：

- 資料分類、資料描述與搜尋方式可以是不同層次。
- 語意相似只能作為相關性線索，不能直接當成知識正確性證明。

### Information Architecture / Faceted Navigation

參考階層分類與多面向篩選的區分，保留：

- 目錄只承擔最主要且穩定的維度。
- 其他維度不必全部轉成目錄。

## 十八、目前不採用的方向

目前沒有足夠證據支持直接加入：

- 向量資料庫。
- RAG 系統。
- 知識圖譜。
- 複雜 metadata schema。
- 完整 tag ontology。
- 自動分類平台。
- 複雜排名模型。

原因不是這些技術無效，而是目前實際瓶頸仍主要來自資料結構、歷史文件重組與搜尋任務驗證。
