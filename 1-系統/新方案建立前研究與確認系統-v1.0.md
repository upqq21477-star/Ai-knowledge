# 新方案建立前研究與確認系統 v1.0

日期：2026-09-17
狀態：【候選系統；已建立；待真實新方案案例驗證】

## 一、目的

阻止 AI 在新方案構想提出後直接進入正式建立，確保新方案先經過研究、比較、漏洞分析、討論與確認。

## 二、觸發

當使用者提出建立、設計、規劃新的「方案」或提出可能形成新方案的架構構想時觸發。

第一個動作不是建立方案，而是建立／更新「候選方案」狀態並進入建立前分析。

## 三、最小流程

```text
方案構想
→ 建立候選標記
→ 問題／目標分析
→ 既有能力盤點
→ 外部研究
→ 產品／工具／方法比較
→ 優缺點分析
→ 漏洞攻擊
→ 反方案檢查
→ 候選架構
→ 使用者討論
→ 修正
→ 必要時再次研究／比較
→ 方案確認
→ 才允許建立
```

## 四、建立前 Gate

只有以下核心條件具備，才能由候選狀態進入「已確認／允許建立」：

- 問題與目的明確。
- 既有能力已盤點。
- 外部研究已完成。
- 同類方法／產品／工具已比較。
- 優缺點與限制已分析。
- 主要漏洞已分析。
- 已檢查是否根本不需要新方案。
- 候選架構已形成。
- 必要討論已完成。
- 修正已完成。
- 邊界與責任已確認。

核心條件未完成時，不得直接建立正式方案文件、方案知識書或方案核心系統。

## 五、討論迴圈

方案不是一次研究就直接建立。

```text
候選架構
→ 使用者討論
→ 發現問題
→ 修改
→ 外部再比較（必要時）
→ 再討論
→ 待確認
```

## 六、結果

系統產生：

- 候選方案狀態。
- 研究與比較記錄。
- 優缺點與漏洞記錄。
- 反方案判斷。
- 候選架構。
- 討論修正結果。
- 最終建立 Gate 判定。

## 七、禁止事項

1. 不得因使用者使用「建立方案」字樣就直接建立。
2. 不得用 AI 自己的架構直覺取代外部研究。
3. 不得以一次搜尋取代必要的比較與漏洞分析。
4. 不得把「建立 Gate 通過」誤認為方案已被實測證明有效。
5. 不得用後續順便驗證機制取代建立前研究。
6. 不得因候選方案已有部分文件就自動宣布成立。

## 八、與其他系統接口

### 問題解決系統

研究或討論中若發現無法直接判斷的實際問題，轉入問題解決流程。

### 小系統建立與生命週期管理系統

若判斷不需要新方案，只需獨立小系統，停止方案建立流程並轉交小系統建立流程。

### 後續工作觸發式順便驗證系統

只有方案已確認、系統／能力已建立並等待實際案例時，才可使用順便驗證；不能用來跳過建立 Gate。

### 統御分支

方案確認後才登錄正式方案及其系統狀態；候選方案不得被當成正式方案能力。

## 九、目前驗證方式

下一次真實提出新方案時，本系統必須自然觸發，並記錄：

```text
是否攔截直接建立？
是否完成外部研究？
是否完成比較？
是否完成漏洞分析？
是否進行反方案檢查？
是否經過討論／修正？
是否在確認前停止正式建立？
確認後才是否進入建立？
```

至少取得一筆真實案例後，才能判斷本系統是否開始成立。
