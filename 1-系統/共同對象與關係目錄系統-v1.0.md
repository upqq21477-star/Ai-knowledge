# 共同對象與關係目錄系統 v1.0

版本：v1.0  
狀態：【建立中；候選系統已確認；待最小實作驗收】  
日期：2026-09-17

## 一、定位

本系統是四方案共同使用的薄型 Object Catalog / Relationship Registry 能力。

目的不是建立中央治理引擎，而是提供共同、可追溯的對象身份與對象關係定位能力，避免四個方案各自保存互相衝突的身份與關係資料。

本系統來源於：

- 資料身份與唯一識別原則
- 共同關係模型最小原則
- 四方案功能 → 系統能力映射
- 既有系統目錄／登錄原理的重製需求

## 二、建立理由

本次施工已確認：

1. 四方案均需要識別資料、知識、系統、方案等對象。
2. 四方案均需要查詢所屬、依賴、引用、支援、取代、驗證等關係。
3. Repository 已存在 System Catalog / System Registry 的設計原理與觸發條件管理，但尚未形成一個明確承接「共同對象身份＋共同關係」的正式系統邊界。
4. 若各方案自行保存正式身份與關係，將產生重複權威來源與同步風險。
5. 因此需要一個薄型共同系統承接這項基礎能力。

這不是因為「有功能就必須建立系統」，而是完成既有能力盤點後確認：此能力跨四方案、責任穩定、輸入輸出明確，且需要共同來源。

## 三、核心能力

### 1. 對象身份定位

輸入：

- 對象類型／Kind
- 穩定 Identity（若已存在）
- 人類可讀名稱
- 別名／歷史名稱
- 其他可協助定位的 metadata

輸出：

- 對象唯一定位
- 對象類型
- 目前名稱
- 別名／歷史名稱
- 目前承載位置
- 可追溯的版本／狀態資訊入口

本系統不負責自動判定所有資料是否為同一對象；身份判定不確定時，保留不確定狀態並交由適當工作流程處理。

### 2. 關係查詢

最小關係：

```text
Source → Relationship Type → Target
```

第一階段支援：

- belongsTo
- owns
- dependsOn
- references
- supports
- replaces
- derivedFrom
- validates
- relatedTo

支援依 Source、Target、Relationship Type 查詢。

### 3. 版本／狀態定位

本系統可以提供版本與狀態的定位資訊，但不把 Version 或 State 重新定義成 Identity。

例如：

```text
System A
├─ Identity
├─ Version
├─ State
└─ Relationships
```

## 四、最小責任邊界

本系統負責：

- 對象身份定位。
- 名稱／別名／歷史名稱定位。
- 對象關係保存與查詢。
- 關係方向與類型表達。
- 關係的版本／時間／條件定位。
- 提供其他系統查詢共同身份與關係。

本系統不負責：

- 方案決策。
- 業務流程執行。
- 問題解決。
- 自動重構。
- 自動遷移。
- 自動刪除舊資料。
- 權限授權（Authorization）。
- 觸發條件本身的執行。
- 取代其他系統的完整資料內容。

## 五、與既有系統的關係

### System Catalog / System Registry

既有原理負責「系統目錄／登錄」概念；本系統將其收斂為更大的共同對象與關係基礎能力。

### 觸發條件管理系統

Trigger Registry 可以透過本系統取得 System ID、位置、狀態與關係，但不得自行建立第二份正式 System Identity。

### 四個正式方案

四方案可以引用本系統提供的共同身份與關係，但不得各自建立互相衝突的權威身份／關係來源。

## 六、最小資料模型

目前只定義語義，不凍結完整 JSON / YAML Schema。

```text
Object
- Identity
- Kind
- Name
- Aliases
- Location
- Version reference
- State reference

Relationship
- Source Identity
- Relationship Type
- Target Identity
- Version / Time / Condition（需要時）
- Relationship State
- Evidence / Source reference（需要時）
```

## 七、最小輸入／輸出

| 類別 | 輸入 | 輸出 |
|---|---|---|
| 對象定位 | 名稱／Identity／Kind | 對象 Identity 與定位資訊 |
| 關係查詢 | Source／Target／Type | 符合條件的關係 |
| 反向查詢 | Target／Type | 指向 Target 的來源對象 |
| 歷史定位 | 舊名稱／舊位置 | 對應目前對象 |
| 版本定位 | Identity＋Version | 指定版本入口 |

## 八、最小實作驗收方法

驗收方法已定義，不代表驗收已完成。

至少完成以下案例：

1. 建立一個正式 System 對象並可由 Identity 定位。
2. 系統文件改名後仍能定位同一對象。
3. 文件搬移後仍能維持同一 Identity。
4. 建立 System → belongsTo → Solution 關係並可查詢。
5. 建立 System A → dependsOn → System B 並可進行正向與反向查詢。
6. 同名不同 Kind／不同 Identity 的對象可以區分。
7. 版本改變不會自動產生錯誤的新 Identity。
8. 關係失效或條件改變後可以標示／定位其有效性，而不是繼續視為永久有效。

最低驗收結果必須可重新執行並能指出實際輸入、實際輸出與差異。

## 九、實戰驗證驗收方法

驗證方法已定義，不代表實戰驗證已完成。

在正常四方案施工中，選擇一個自然需要跨方案查詢身份／關係的真實工作案例，觀察：

- AI 是否能找到正確對象。
- AI 是否能避免把檔名／路徑誤當身份。
- AI 是否能正確取得關係。
- 關係是否能支持後續影響分析、版本分析或方案組合。
- 是否產生新的身份／關係缺口。
- 是否產生重複權威來源。

不得為了驗證本系統而製造與正常施工無關的大型測試工作；若自然工作無法提供必要證據，再另外設計最小驗證案例。

## 十一、重要限制

本系統第一版不得：

- 建立大型中央治理引擎。
- 強制所有 Repository 文件立即新增 ID。
- 建立全球自動 Identity Resolver。
- 自動修改所有關係。
- 將 Relationship Registry 變成業務流程引擎。
- 取代四方案本身的決策與執行責任。
- 因規模尚小而預先分片／分庫。

若後續真實工作證明查詢、更新、責任或同步成本已達到需要拆分的程度，再依實際證據處理。
