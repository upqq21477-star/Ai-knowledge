# 資料層級與分類－外部比對

## 狀態
【外部稽核完成／實際驗證待進行】

## 一、稽核問題

原文件把「知識、記憶、管理、系統、軟體、應用」放在主要資料分類中，同時使用「資料層級」與「分類」兩個概念，但沒有充分區分：

- 語義內容
- 來源與證據
- 文件承載形式
- 工作結果
- 管理屬性
- 目錄分類

本次稽核的問題不是單純重新命名分類，而是確認這些概念是否真的屬於同一個層級。

## 二、外部研究

### 1. ISO／知識管理

ISO 30401 的知識管理框架區分 data、information、knowledge，並將 knowledge 視為能支持有效決策與行動的理解；這支持資料、資訊、知識之間可以區分，但不需要把所有其他概念硬塞進同一條階梯。

### 2. Notion

Notion 將資料庫項目、properties、relations、views 分開。Properties 用來提供分類、狀態、日期、連結等上下文；relations 用於連接不同資料；views 則以不同方式呈現同一批資料。

這表示「內容是什麼」「它有哪些屬性」「它和什麼相關」「怎麼看」不是同一個分類維度。

### 3. Obsidian

Obsidian 的 Markdown 文件是內容承載形式，而 properties、tags、links、search 等提供額外結構與檢索方式。這支持「文件」不應直接等同於某種語義資料類型。

### 4. Faceted Classification

知識組織與資訊架構研究長期使用 faceted classification，將主題、文件類型、對象、時間等不同維度分開，而不是要求所有內容只能落入一條單一階層。這支持 Ai-knowledge 將「功能、領域、物件、狀態、適用範圍」視為不同維度。

## 三、比較結果

| 概念 | 原本容易被視為 | 稽核後判定 |
|---|---|---|
| 資料 | 層級 | 內容／語義類型 |
| 資訊 | 層級 | 內容／語義類型 |
| 知識 | 層級 | 可重用理解／內容 |
| 來源 | 資料的一種 | 形成來源／關係 |
| 證據 | 資料的一種 | 支持主張的關係／角色 |
| 文件 | 資料類型 | 承載形式 |
| 記憶 | 資料類型 | 連續性用途／管理概念 |
| 決策 | 知識的一種 | 特定情境下的工作結果 |
| 狀態 | 分類 | 管理屬性 |
| 分類 | 資料種類 | 管理行為／結構 |

## 四、主要發現

### 發現一：原模型混合了不同維度

原文件的「第一層分類」把知識、記憶、管理放在一起，容易讓人誤以為這三者是同一分類維度。

實際上：

- 知識描述內容性質。
- 記憶描述保存與連續性用途。
- 管理描述對知識庫本身的管理內容。

它們可以同時作用於同一內容，因此不是天然互斥的分類。

### 發現二：文件不應視為資料層級

同一個 Markdown 文件可以同時包含知識、決策、來源、證據與歷史內容。文件是承載形式。

### 發現三：狀態不應成為主要分類樹

「已確認」與「待確認」可以套用到同一種內容，因此是正交屬性，而非內容類型。

### 發現四：分類應與內容語義分離

「這份文件主要支援搜尋」是分類結果，不是文件的內容本身。

### 發現五：DIKW 不應變成資料庫結構

資料→資訊→知識可以作為理解資料加工與語義提升的概念模型，但不應強迫所有資料依序通過每一層。

## 五、修正決策

將「資料層級與分類」從單一分類樹改為正交概念模型。

核心模型：

```text
內容／語義
＋來源／證據關係
＋承載形式
＋工作結果
＋管理屬性
```

而 `0-知識` 的目錄仍由功能導向分類處理。

## 六、與目前分類設計的關係

這次修正沒有推翻 `0-知識` 的功能導向目錄設計，反而把兩者邊界釐清：

```text
資料層級與分類
→ 解釋資料概念如何區分

分類原理
→ 決定什麼情況值得建立分類

分類維度
→ 決定分類是在回答哪一個問題

分類與目錄
→ 決定邏輯分類如何落到實體目錄
```

四者不應互相取代。

## 七、過度簡化檢查

原模型最大的過度簡化，是把多種不同性質的概念放進同一棵樹。

本次修正後仍刻意保持簡單：沒有建立知識圖譜、證據資料庫、型別系統或大型 metadata schema。

## 八、過度工程化檢查

本次外部研究沒有足以支持立即建立完整資料庫的證據。

因此只修正概念模型，不建立額外軟體機制。

## 九、實際驗證計畫

選取既有文件測試：

1. 基礎原理
2. 長期記憶
3. 專案決策
4. 外部來源
5. 證據內容
6. 混合內容文件
7. 已取代方案

觀察是否能更快回答：

- 這是什麼？
- 從哪裡來？
- 為什麼存在？
- 目前是否可用？
- 可以如何重用？

## 十、結論

「資料層級與分類」不應再被理解成一棵完整的資料分類樹。

本次稽核確立：

> **語義、來源、證據、承載形式、工作結果與管理屬性應分開建模；目錄只是其中一種實體組織方式。**
