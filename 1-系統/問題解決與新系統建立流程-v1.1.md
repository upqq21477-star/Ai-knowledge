# 問題解決與新系統建立流程-v1.1

## 狀態
【建立中；已整合問題解決與新系統建立流程；待後續案例驗證】

## 一、定位

本文件不是新的大型方案，也不是第四個正式方案。

它是「問題解決系統」的擴充版流程，用來處理兩種高度相似的工作：

1. 發現既有架構中的問題，尋找並驗證解法。
2. 發現問題需要一項目前不存在的系統能力，建立並驗證新系統。

兩者不應各自維護一套完全不同的研究流程，因為兩者共同使用：

- 問題定義。
- 既有搜尋研究方案。
- 外部方法／工具／案例比較。
- 候選方案。
- 最小實測。
- 結果判定。
- 回饋與後續驗證。

差異只在於「實測後的處理分支」：

```text
問題
↓
問題確認
↓
使用既有搜尋研究方案
↓
外部方法／工具／案例比較
↓
候選解法
↓
最小實測
↓
判定
├─ 現有能力足以解決
│   ↓
│  採用／條件採用既有解法
│
└─ 現有能力不足，且需要新增系統能力
    ↓
   進入新系統建立流程
    ↓
   系統需求 → 功能 → 知識 → 系統需求
    ↓
   確認既有系統是否完全重疊
    ↓
   建立／採用系統候選
    ↓
   實際驗證
    ↓
   採用／條件採用／暫緩／拒絕
↓
回饋相關知識／系統／方案
```

## 二、為什麼合併

原本的兩個流程：

### 問題解決

```text
發現問題
→ 搜尋解法
→ 外部比較
→ 候選方案
→ 實測
→ 判定
→ 回饋
```

### 建立新系統

既有方案建構紀錄已形成：

```text
方案需求
→ 功能
→ 功能需要的知識
→ 確認知識
→ 補充知識
→ 功能需要的系統
→ 確認既有系統
→ 建立／採用系統
→ 組建方案
→ 實際驗證
→ 記錄問題與差異
```

兩者前半段實際上高度重疊。

因此不再把「問題解決」與「新系統建立」視為兩套獨立的研究引擎，而採用：

> **一個問題處理入口 + 一個共同研究／比較／實測核心 + 必要時分流到新系統建立。**

## 三、核心原則

### 1. 先解問題，不先指定系統

問題描述必須與解法分離。

例如：

```text
問題：
變更後無法可靠知道哪些下游資料需要重新驗證。
```

不能直接寫成：

```text
需要建立知識圖譜。
```

後者已經提前指定解法。

### 2. 先使用既有能力

問題出現後，先檢查現有知識、搜尋、系統與方案是否已經能處理。

只有確認能力不足，才進一步提出新增系統。

### 3. 新系統不是問題解決的預設結果

問題可能透過以下方式解決：

- 使用既有知識。
- 使用既有系統。
- 調整使用方式。
- 增加小型流程。
- 補充知識。
- 建立新系統。
- 跨系統組合。

不能因為問題存在，就自動建立新系統。

### 4. 新系統建立必須繼承問題實證

若最後需要建立新系統，該系統必須能回答：

- 解決哪個已確認問題？
- 現有能力為什麼不足？
- 為什麼不能直接重用現有系統？
- 新系統最小能力是什麼？
- 如何驗證它確實補足缺口？

## 四、統一流程

### 第 0 步：問題確認

區分：

```text
觀察 ≠ 問題 ≠ 需求 ≠ 解法
```

至少形成可驗證問題。

### 第 1 步：確認處理價值

判斷：

- 是否影響核心工作。
- 是否會重複發生。
- 是否造成明顯錯誤或成本。
- 是否有可接受替代方案。
- 解決後是否能改善後續工作。

小問題不應自動啟動大型建構。

### 第 2 步：盤點現有能力

先檢查：

```text
現有知識
現有搜尋能力
現有系統
現有方案
現有流程
```

目的不是強迫重用，而是避免在已有能力存在時重建相同功能。

### 第 3 步：調用既有搜尋研究方案

依既有搜尋研究方案處理：

```text
問題
↓
研究問題
↓
資訊需求
↓
查詢策略
↓
資料探索
↓
候選資料
↓
來源／證據分析
↓
外部方法／工具／案例比較
```

問題解決流程不得另行發明一套搜尋規則。

### 第 4 步：建立候選解法

候選解法至少比較：

| 維度 | 判斷內容 |
|---|---|
| 問題匹配 | 是否直接處理原問題 |
| 解法機制 | 如何解決問題 |
| 適用條件 | 什麼條件下成立 |
| 成本 | 建立與維護成本 |
| 複雜度 | 是否引入不必要架構 |
| 相容性 | 能否與目前架構共存 |
| 可驗證性 | 是否能建立最小案例 |
| 可追溯性 | 結果是否能重建 |
| 限制 | 哪些情況仍無法解決 |

### 第 5 步：最小實測

優先建立能區分候選解法的最小案例。

至少記錄：

```text
問題
輸入資料
候選解法
操作方式
預期結果
實際結果
失敗點
成本
可追溯性
是否改善原問題
```

### 第 6 步：分流判定

實測後分成兩條路。

#### A. 現有能力可以解決

```text
實測
↓
採用／條件採用
↓
回饋既有知識／系統／方案
```

不建立新系統。

#### B. 確認現有能力不足

只有在以下條件大致成立時才進入新系統建立：

- 問題本身已被確認。
- 現有能力不足已經有證據。
- 外部研究顯示存在可行的能力方向，或問題值得建立專門能力。
- 新能力不是現有系統的完全重複。
- 可以建立最小驗證案例。

## 五、新系統建立分支

進入新系統建立後，沿用既有「方案建構」的成熟流程，但只處理必要範圍：

```text
已確認問題
↓
系統目標
↓
功能需求
↓
功能 → 知識需求
↓
確認既有知識／補充缺少知識
↓
功能 → 系統能力需求
↓
確認既有系統是否完全重疊
├─ 完全重疊 → 重用／重新驗證
├─ 部分重疊 → 不直接整併，記錄邊界後建立候選
└─ 無既有系統 → 建立候選
↓
最小系統設計
↓
實際驗證
↓
判定
```

這裡特別保留原有建構原則：

- 功能完全重疊：優先重用。
- 功能部分重疊：不能直接假設可以合併。
- 沒有既有系統：才建立新系統。
- 發現舊系統多餘、應拆分或應整併：先記錄，不在本流程中直接重構舊架構。

## 六、新系統的最小驗證

新系統至少需要證明：

1. 能處理原問題。
2. 能完成定義的核心功能。
3. 不依賴尚未存在的能力才能成立，或其依賴已明確。
4. 與既有資料與責任邊界相容。
5. 不只是文件存在，而是真的能執行／推演／驗證。
6. 已知失敗條件與限制已被記錄。

「建立文件」不等於「系統成立」。

## 七、問題解決與新系統建立的共同輸出

兩條路最後都回到同一個結果模型：

```text
問題
↓
研究證據
↓
候選解法
↓
實測結果
↓
判定
↓
適用範圍與限制
↓
回饋
```

因此可以共用同一套問題收據（Receipt）與實測記錄，而不必為「問題解決」與「新系統建立」建立兩套完全不同的追蹤格式。

## 八、與三個正式方案的關係

本流程不是第四個正式方案。

它是跨方案的問題處理能力。

```text
整體資料治理方案
→ 提供資料、責任、邊界與治理約束

AI知識管理方案
→ 提供任務理解、搜尋、上下文、執行與驗證能力

知識迭代與資料演化方案
→ 處理變更、影響、版本、相容性與演化

問題解決與新系統建立流程
→ 在三者遇到具體缺口時，研究、比較、實測並形成可驗證解法
```

若問題跨越多個方案，先進行跨方案影響分析，再決定回饋位置。

## 九、停止與失敗回退

問題解決不能因為存在未知就無限研究。

當：

- 問題已充分處理。
- 候選差異不足以改變決策。
- 新資料邊際價值降低。
- 實測足以支持目前判定。
- 繼續研究成本高於可能收益。

即可停止。

若實測失敗，依序檢查：

```text
候選失敗
↓
問題定義是否錯誤？
↓
搜尋是否不足？
↓
外部解法是否不適用？
↓
測試案例是否錯誤？
↓
現有能力是否真的不足？
↓
必要時進入新系統建立分支
```

不得因第一次候選失敗就直接建立大型新系統。

## 十、目前邊界

目前仍未正式建立：

- 固定 JSON Schema。
- 固定資料庫結構。
- 自動判定「真實解法」的引擎。
- 自動建立新系統。
- 自動整併舊系統。
- 完整 Agent Trace／Observability 平台。
- 單一數值化「最佳解」評分器。

這些都必須在後續實測證明確有必要後才能提出。

## 十一、目前驗證狀態

第一、第二輪問題解法案例已支持：

- 先問題定義，再搜尋。
- 使用既有搜尋研究方案，而非重新發明搜尋流程。
- 外部方法比較後再建立候選。
- 最小實測後才判定。
- A2／B2／C2 候選方向可通過最小案例。

本版本新增的是「問題解決 → 必要時進入新系統建立」的統一分流，尚未完成長期、多案例驗證。

## 十二、下一步

使用第三輪案例驗證以下問題：

1. 一個問題是否能從發現一路跑到新系統建立，而不產生流程重複。
2. 已有系統與部分重疊系統如何保持邊界。
3. 新系統建立後，問題解決流程能否正確回饋三方案。
4. 同一問題反覆出現時，能否避免重複建立系統。
5. 問題解決與新系統建立共用 Receipt 後，是否足以支援後續追溯。
