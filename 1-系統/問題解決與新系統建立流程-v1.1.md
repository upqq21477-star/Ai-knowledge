# 問題解決、方案與新系統建立流程

版本：v2.0
狀態：【融合後單一跨方案問題處理入口；待多案例驗證】

## 一、定位
將「問題解決」「新系統建立前研究確認」「新系統建立分支」統一為一個入口。

三者共同前半段都是：
問題／需求確認 → 研究 → 外部比較 → 候選 → 最小實測 → 判定。
差異只在最後要回饋既有能力、建立方案，或建立新系統。

## 二、核心原則
1. 觀察 ≠ 問題 ≠ 需求 ≠ 解法。
2. 先解問題，不先指定系統或方案。
3. 先盤點既有能力，再考慮新增。
4. 外部研究不能被 AI 直覺取代。
5. 最小實測先於正式成立。
6. 問題存在不等於必須建立新系統。
7. 方案／系統文件存在不等於已驗證。

## 三、統一流程
```
問題／架構構想
↓
問題確認
↓
確認處理價值
↓
盤點既有知識／能力／系統／方案
↓
研究問題與資訊需求
↓
外部研究／工具／方法／案例比較
↓
漏洞、限制、反方案檢查
↓
候選解法
↓
最小實測
↓
判定
├─ 現有能力足夠
│  → 採用／條件採用 → 回饋
├─ 需要建立／調整方案
│  → 方案候選 → 討論／修正 → 建立 Gate → 方案驗證
└─ 現有系統能力不足
   → 新系統候選 → 功能／知識／依賴／邊界
   → 最小設計 → 實際驗證 → 採用／條件採用／暫緩／拒絕
↓
回饋知識／系統／方案／CURRENT
```

## 四、方案建立前 Gate
若問題最後需要形成正式方案，至少確認：
- 問題與目的明確。
- 既有能力已盤點。
- 外部研究與同類比較完成。
- 優缺點、限制、漏洞已分析。
- 已檢查是否根本不需要新方案。
- 候選架構形成。
- 必要討論與修正完成。
- 邊界與責任確認。
只有通過後才建立正式方案；候選方案不得視為正式能力。

## 五、新系統建立 Gate
只有在：
- 問題已確認。
- 現有能力不足有證據。
- 新能力不是現有系統完全重複。
- 可定義最小功能。
- 可建立最小驗證案例。
才建立候選新系統。

部分重疊時先明確邊界，不直接整併；完全重疊優先重用。

## 六、候選解法比較
至少比較：
問題匹配、機制、適用條件、成本、複雜度、相容性、可驗證性、可追溯性、限制。

## 七、失敗回退
```
實測失敗
↓
檢查問題定義
↓
檢查研究／搜尋
↓
檢查外部解法適用性
↓
檢查測試案例
↓
重新判斷既有能力是否不足
↓
必要時再進入方案／新系統分支
```

不得因第一次候選失敗就直接建立大型系統。

## 八、共用問題收據
```
問題
→ 證據
→ 候選
→ 實測
→ 結果
→ 判定
→ 適用範圍／限制
→ 回饋
```

## 九、驗收
至少以真實案例確認：
1. 問題能從發現一路處理到判定。
2. 方案建立前研究不與問題解決重複。
3. 新系統建立不與既有系統重複。
4. 失敗能回退並重新研究。
5. 同一問題重現時不重複建構相同能力。
6. 結果能回饋三個正式方案。

## 十、禁止
不得因使用者說「建立方案」就跳過研究；不得因問題存在就自動建立系統；不得用文件存在冒充實測；不得建立第二套搜尋引擎；不得以固定分數取代可解釋比較。
