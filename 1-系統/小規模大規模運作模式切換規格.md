# 小規模／大規模運作模式切換規格 v1.1

版本：v1.2
日期：2026-09-19
狀態：【正式規格；Small Mode 啟用；Control Plane 已接入；Large Mode 介面預留】

## 1. 核心決策

本系統現在採用：

> 小規模採輕量模式；架構介面先預留，大規模時切換運作模式，而不是重新設計整套系統。

這不是兩套架構。

而是：

同一套核心架構
→ Small Mode（目前）
→ Large Mode（未來）

模式切換只改變「如何檢索、選擇、組合、載入 Skill」，不重新定義 Skill、Responsibility 或核心資料契約。

## 2. 這次創建模式的分類結果

本項經過既有 Skill 架構與創建流程判斷後，分類為：

- 類型：System Architecture / Operating Mode Specification
- 不是：新 Skill
- 不是：Provider
- 不是：Tool
- 不是：單一 Workflow
- 不是：單一 Capability
- 作用：定義 Small / Large Mode 的共同介面、切換條件與相容性

因此不建立新的 Skill。

它應由現有 Agent、Skill 架構與未來 Infrastructure 共用。

## 3. 為什麼不是重新設計

大規模化真正改變的是：

- Skill 如何被找到
- Candidate 如何產生
- Skill 如何排序
- 多 Skill 如何組合
- Context 如何檢索
- Dependency 如何處理

大規模化不應改變：

- Skill 是什麼
- Skill 負責什麼
- Trigger 是什麼
- Input / Output 是什麼
- Verification 如何完成
- Failure 如何分類
- Lifecycle 如何管理

因此：

Small Mode = 直接路由
Large Mode = 基礎設施輔助路由

不是：

Small Architecture → 廢棄 → Large Architecture 重做

## 4. 固定核心資料契約

Small / Large 必須共用：

- Skill ID
- Name
- Responsibility
- Purpose
- Trigger
- Input
- Output
- Mode
- Dependencies
- Routing Conditions
- Failure Patterns
- Verification
- Cost
- Lifecycle
- Provider / Tool References

缺少資料不得補猜，標記 UNKNOWN。

任何模式都不得擅自改變既有 Responsibility 語義。

若確實需要改變：

Skill Classification
→ Evolution
→ Execution
→ Verification

## 5. Small Mode：目前正式運作

目前系統採 Small Mode。

基本流程：

Task
→ Task Understanding
→ Problem Triage
→ Control Plane Query（必要時）
→ Context Selection
→ Agent / Semantic Router Skill Selection
→ Skill / Mode Execution
→ Verification
→ Replan（必要時）

### 5.1 Small Mode 的工作方式

Agent 根據：

- Task
- Responsibility
- Trigger
- Context
- Skill Definition
- Routing Conditions

直接選擇 Skill。

目前以 Markdown 文件、檔案索引與明確路由規則提供必要支援。

### 5.2 Small Mode 的限制

目前不建立：

- 獨立 Skill Registry Runtime
- Embedding
- Vector Database
- 自動 Skill Ranking
- 動態 Skill Composition Engine
- 複雜 Dependency Resolver
- 常駐 Agent Runtime
- 大型自動化 Pipeline

原因不是這些能力沒有價值，而是目前規模尚不足以證明其成本合理。

## 6. Large Mode：現在只預留介面

Large Mode 不提前建立完整 Runtime。

預留標準流程：

Task
→ Task Understanding
→ Problem Triage
→ Problem Decomposition
→ Capability Retrieval
→ Skill Candidate Retrieval
→ Skill Ranking
→ Skill Composition
→ Dependency Resolution
→ Context Retrieval
→ Execution
→ Verification
→ Telemetry
→ Replan

未來啟用時，這些元件讀取既有 Skill Definition。

不重新建立另一套 Skill 系統。

## 7. Small / Large 共用運作介面

### Input

兩種模式均可接受：

- Task
- Context
- Candidate Skills（若已知）
- Provider / Tool constraints
- Verification requirements

### Output

兩種模式均應輸出：

- Selected Skill / Skills
- Selected Mode
- Execution Result
- Verification Result
- Failure Classification（若失敗）
- Replan Requirement（若需要）

### 路由差異

Small：

Agent
→ Skill Selection

Large：

Problem
→ Capability
→ Candidate Skills
→ Ranking
→ Composition
→ Skill Selection

因此 Large Mode 只是增加「選擇基礎設施」。

## 8. Large Mode 預留功能介面

### G01 Skill Registry

提供 Skill Definition 的集中檢索介面。

### G02 Capability Registry

將 Capability 與可提供該 Capability 的 Skill / Provider 建立映射。

### G03 Candidate Retrieval

根據 Problem / Capability 找出候選 Skill。

### G04 Skill Ranking

根據 Responsibility、Trigger、Context、歷史結果等資訊排序候選 Skill。

### G05 Skill Composition

處理單一任務需要多個 Skill 的情況。

### G06 Dependency Resolution

處理 Skill、Context、Provider、Tool 之間的依賴。

### G07 Routing Telemetry

記錄：

- Skill Selection
- Routing Failure
- Context Cost
- Execution Cost
- Verification Result
- Replan

### G08 Automated Candidate Filtering

在候選數量過大時，先排除明顯不符合條件的候選。

目前 G01–G08 均為預留規格，不提前實作。

## 9. Large Mode 切換條件

不使用單一 Skill 數量作為硬門檻。

必須觀察實際運作資料。

### 9.1 Routing 壓力

出現：

- Skill Selection 錯誤反覆發生
- Skill Overlap 造成路由衝突
- 人工選 Skill 已成為主要成本
- Agent 無法穩定區分大量候選 Skill

### 9.2 Context 壓力

出現：

- 為了選 Skill 必須讀取大量文件
- 無關 Context 明顯增加
- Context Cost 成為主要瓶頸
- Skill Definition 檢索本身開始消耗大量資源

### 9.3 Composition 壓力

出現：

- 單一任務經常需要多個 Skill
- Skill 順序不再固定
- 固定 Workflow 無法覆蓋主要任務
- Skill 組合本身成為主要工作

### 9.4 Maintenance 壓力

出現：

- Skill Mapping 維護成本顯著上升
- Dependency 難以人工管理
- Lifecycle 管理開始失控
- 檔案索引不足以支援有效檢索

### 9.5 切換原則

任何一項壓力都只能觸發「Large Mode 評估」。

不是直接切換。

必須先：

Usage / Failure / Cost
→ Evidence / Verification
→ Research
→ 判斷瓶頸
→ 確認 Large Mode 是否真的降低成本
→ 建立必要 Infrastructure
→ 驗證
→ 正式切換

## 10. Small → Large 的實際切換方式

不是重建。

而是逐層增加：

Small Mode
→ Registry
→ Retrieval
→ Ranking
→ Composition
→ Dependency
→ Telemetry
→ Automation

每一層獨立驗證。

如果只需要 Registry，就先建立 Registry。

不因進入 Large Mode 就一次建立全部大型元件。

## 11. Large → Small 的回退能力

Large Mode 必須可回退。

如果驗證發現：

- Context Cost 增加
- Routing Cost 增加
- Execution Cost 增加
- Maintenance Cost 增加
- Failure Rate 增加
- Replanning 增加

而沒有解決主要瓶頸，則可以停止大型化，退回 Small Mode。

因此 Large Mode 是可切換運作模式，不是不可逆架構升級。

## 12. 模式切換時的相容性要求

切換時必須：

1. 讀取既有 Skill Definition。
2. 保留既有 Skill ID。
3. 保留 Responsibility。
4. 保留 Trigger。
5. 保留 Input / Output。
6. 保留 Verification。
7. 保留 Failure Pattern。
8. 保留 Lifecycle。
9. 只增加必要的 Retrieval / Ranking / Composition Infrastructure。
10. 若必須改變 Skill 語義，先走 Skill Classification → Evolution → Execution → Verification。

禁止：

以 Large Mode 為理由直接重寫既有 Skill。

## 13. 失敗處理

Small / Large 共用 Failure Classification：

- Data
- Context
- Research
- Routing
- Skill
- Provider
- Execution
- Verification

統一流程：

Failure
→ Classification
→ Diagnosis
→ Replan
→ 必要時重新選 Skill / Mode
→ Execution
→ Verification

因此模式切換不會造成兩套完全不同的錯誤處理系統。

## 14. 與 Skill 建立流程的關係

「建立新 Skill」與「進入 Large Mode」是兩件不同的事。

新 Skill：

Research D3
→ 問題拆解
→ 研究問題地圖
→ 既有 Skill 盤點
→ Capability / Responsibility
→ Boundary Analysis
→ Skill Classification
→ NEW / MERGE / UPDATE / REPLACE / DEFER
→ Evolution
→ Execution
→ Verification
→ Feedback

Small Mode 仍然可以建立正式 Skill。

Large Mode 只改變：

「如何從大量 Skill 中找到與組合 Skill」。

## 15. 與目前架構的關係

目前：

Agent
→ Task Understanding
→ Research
→ Context
→ Skill Selection
→ Execution
→ Verification
→ Evolution / Knowledge / Distillation 等治理能力

其中：

- Problem Triage：目前由 Research 內部負責
- Research Depth Selection：目前由 Research 內部負責
- Skill Boundary Analysis：目前由 Skill Classification 負責
- Skill Routing：目前由 Agent 直接負責

不因「未來大型化」提前把上述責任拆成大量 Skill。

只有實際使用證明具有：

- 獨立 Trigger
- 獨立 Input / Output
- 獨立 Responsibility
- 獨立 Verification
- 明確 Routing Value
- 合理 Maintenance Cost

才重新進行 Skill 分化判斷。

## 17. 驗證指標

每次模式升級前後至少比較：

- Context Cost
- Routing Cost
- Execution Cost
- Verification Cost
- Maintenance Cost
- Failure Rate
- Replanning Frequency

判斷目的不是追求「更大型」。

而是確認是否真正解決目前瓶頸。

## 18. 建立與演化規則

本規格本身屬於架構規格，不是 Skill。

後續若需要修改：

一般文字／欄位修正
→ 直接更新規格。

若改變核心責任邊界：
→ Research D3
→ Skill Classification
→ Evolution
→ Execution
→ Verification

若要建立新 Skill：
→ 使用《Skill 建立流程規格》。

若要啟用 Large Mode：
→ 先使用本文件的切換條件與驗證流程。

## 19. 禁止事項

- 不因預測未來會變大而提前建立大型 Runtime。
- 不因 Skill 數量增加就自動拆分 Skill。
- 不因 Provider 增加而建立 Skill。
- 不因 Tool 增加而建立 Skill。
- 不因 Mode 增加而建立 Skill。
- 不因單次 Failure 改變整體架構。
- 不把 Simulation PASS 當成 Field PASS。
- 不因 Large Mode 建立而重新定義既有 Skill。
- 不一次建立所有大型 Infrastructure。
- 不讓 Large Mode 取代 Small Mode 的低成本優勢。
