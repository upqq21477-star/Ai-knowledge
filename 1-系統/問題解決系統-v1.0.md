# 問題解決系統-v1.0

## 狀態
【建立中；已通過第一、第二輪案例驗證；待第三輪持續驗證】

## 一、系統定位

本系統是一個小型、跨方案的問題解決系統。

它不負責日常搜尋，也不負責單純發現變更；它負責處理「已經確認值得解決的問題」，把問題轉化為可研究、可比較、可實測、可回饋的候選解法。

核心流程：

```text
發現問題
↓
確認問題值得處理
↓
使用既有搜尋方案找解法
↓
外部方法／工具／案例比較
↓
建立候選解法
↓
最小實測
↓
比較實測結果
↓
採用／暫緩／拒絕
↓
回饋相關知識／系統／方案
```

本系統的存在理由不是增加一個大型治理平台，而是避免每個系統、方案各自發明一套「遇到問題後怎麼找解法」的流程。

## 二、與既有能力的關係

本系統不取代既有搜尋、研究或外部比對能力，而是負責把它們組合成問題解決流程。

### 既有搜尋研究方案

負責：

- 定義研究問題。
- 建立資訊需求。
- 設計查詢。
- 控制搜尋範圍與停止條件。
- 取得足夠資料。

本系統調用它，不重新建立另一套搜尋方法。

### 知識外部比對系統

負責：

- 比較外部成熟方法。
- 比較工具與實作。
- 找出共通原理、差異與適用條件。
- 檢查目前設計是否過度簡化或過度工程化。

本系統把它作為候選解法研究能力，而不是把外部資料直接視為答案。

### 三個正式方案

```text
整體資料治理方案
→ 提供共同資料、邊界、責任與驗證約束

AI知識管理方案
→ 提供任務理解、搜尋、上下文、執行與驗證流程

知識迭代與資料演化方案
→ 處理變更、影響、相容性、版本與演化回饋
```

本系統不是第四個大型正式方案，而是一個支援三方案及其他系統處理具體問題的共用小型系統。

## 三、與「變更與新知檢測方案」的區別

兩者不能混為一談。

```text
變更與新知檢測
→ 發現「可能值得重新研究的變化」

問題解決系統
→ 處理「已確認需要解決的問題」
```

檢測輸出可以成為本系統的輸入，但不是必要來源。

問題也可能來自：

- 實際執行失敗。
- 三方案協作失敗。
- 驗證失敗。
- 資料不足。
- 使用者需求。
- 新案例暴露的架構缺口。
- 外部研究發現現有方法不足。

## 四、核心輸入

一個問題進入本系統前，至少要能回答：

1. 問題是什麼？
2. 問題在哪個對象、系統或方案發生？
3. 為什麼值得處理？
4. 不處理的影響是什麼？
5. 已知的限制與條件是什麼？
6. 是否已有現成解法？

問題描述不完整時，可以先進入問題澄清，不應直接搜尋大量資料。

## 五、標準流程

### 第 0 步：問題確認

先區分：

```text
觀察
≠
問題
≠
解法
≠
需求
```

至少形成一個可驗證的問題描述。

例如：

```text
問題：
共同資料語義發生變更後，無法可靠知道哪些下游資料需要重新驗證。
```

而不是：

```text
我們需要知識圖譜。
```

後者已經提前指定解法。

### 第 1 步：確認處理價值

判斷：

- 是否影響核心工作。
- 是否會重複發生。
- 是否造成明顯錯誤或成本。
- 是否存在可接受的暫時替代方案。
- 解決後是否能改善後續工作。

小問題不應自動啟動大型研究。

### 第 2 步：使用既有搜尋研究方案

優先調用既有搜尋研究流程：

```text
問題
↓
研究問題
↓
資訊需求
↓
查詢策略
↓
資料探索
↓
候選資料
↓
來源／證據分析
↓
比較
```

不得因為「問題解決」而自行建立另一套搜尋規則。

### 第 3 步：外部解法比較

搜尋至少覆蓋適合問題的外部類型：

- 理論／方法。
- 成熟工具。
- 實際系統。
- 技術研究。
- 使用案例與失敗案例。

比較至少回答：

| 維度 | 問題 |
|---|---|
| 問題定義 | 外部方法到底解決什麼？ |
| 解法機制 | 它怎麼解決？ |
| 適用條件 | 在什麼情況下成立？ |
| 成本 | 導入與維護成本？ |
| 限制 | 哪些問題仍不能解決？ |
| 相容性 | 能否與目前架構共存？ |
| 可驗證性 | 能否建立最小測試？ |

### 第 4 步：建立候選解法

候選解法必須與「問題」分離。

例如：

```text
問題：
變更後無法知道影響範圍。

候選 A：
只增加版本變更說明。

候選 B：
增加直接依賴與下游影響分析。

候選 C：
建立完整知識圖譜。
```

不因外部方法看起來先進，就直接採用。

### 第 5 步：最小實測

優先測試能以最低成本區分候選解法的案例。

測試至少記錄：

```text
輸入問題
測試資料
候選解法
操作方式
預期結果
實際結果
失敗點
成本
可追溯性
是否改善問題
```

若候選解法無法在最小案例中證明有用，不進入正式架構。

### 第 6 步：判定

本系統不使用單一「最佳分數」決定答案。

至少依下列約束判斷：

1. 是否真正解決原問題。
2. 是否能重現與驗證。
3. 是否與現有資料與責任邊界相容。
4. 是否增加合理而非不必要的複雜度。
5. 是否能維護。
6. 是否有清楚的失敗與限制。
7. 是否值得進入正式系統／方案。

判定結果至少可為：

```text
採用
條件採用
暫緩
拒絕
問題仍未解決
```

「暫緩」與「問題仍未解決」不能視為失敗；它們是研究結果。

### 第 7 步：回饋

只有經過實測的結果才能回饋正式架構。

```text
實測結果
↓
確認是知識問題？
→ 回饋 0-知識

確認是共同資料／責任問題？
→ 回饋 整體資料治理方案／系統

確認是 AI 任務／搜尋／上下文問題？
→ 回饋 AI知識管理方案／系統

確認是版本／變更／相容性問題？
→ 回饋 知識迭代與資料演化方案／系統

確認涉及多者？
→ 先進行跨方案影響分析
```

## 六、問題解決與「最優解」

本系統中的「最優解」不是功能最多，也不是外部最先進工具。

它是：

> 在目前問題、條件、證據、成本與架構約束下，經過候選比較與實測後，能以合理複雜度可靠解決問題的目前可採用解法。

因此：

```text
最優解是條件性的
不是永久真理
```

外部出現新方法、條件改變或實測失敗時，可以重新進入本系統。

## 七、問題解決的停止條件

問題解決不能無限搜尋。

當：

- 問題已被充分處理。
- 候選解法差異已不足以改變決策。
- 新搜尋資料的邊際價值降低。
- 實測已足以支持目前判定。
- 繼續研究成本高於可能收益。

可以停止。

如果仍存在重要未知，必須明確標記，而不是用「已完成」掩蓋。

## 八、失敗與回退

候選解法失敗時，不立即建立更大的系統。

依序檢查：

```text
候選失敗
↓
檢查問題定義
↓
檢查搜尋是否不足
↓
檢查候選是否錯誤
↓
檢查測試案例是否不適合
↓
重新搜尋必要的資訊缺口
↓
建立下一候選
```

只有確認是現有架構能力不足，才提出正式架構變更。

## 九、與問題收據（Receipt）的關係

問題解決過程應逐步採用最小可回溯記錄。

至少能重建：

```text
問題
→ 搜尋
→ 候選
→ 測試
→ 結果
→ 判定
```

這與第一、第二輪實測發現的最小執行／搜尋 Receipt 相容。

目前不要求建立完整 Agent Trace 或 Observability 平台。

## 十、最小可用版本

第一版只需要：

1. 問題描述。
2. 問題價值判斷。
3. 調用既有搜尋研究方案。
4. 外部解法比較。
5. 候選解法。
6. 最小實測。
7. 採用判定。
8. 回饋對象。
9. 問題解決記錄。

不建立：

- 自動解題引擎。
- 自動知識圖譜。
- 自動最佳化器。
- 固定評分模型。
- 自動修改正式架構。
- 完整 ITSM 平台。
- 完整 Agent Observability 平台。

## 十一、目前已驗證案例

第一、第二輪驗證已實際形成三個代表案例：

### A：變更影響

問題：變更後不知道哪些資料需要重新驗證。

目前候選：變更對象＋依賴＋影響分析。

結果：【目前通過最小案例】。

### B：失敗重建

問題：跨方案失敗後無法知道當時使用了什麼資料與條件。

目前候選：最小搜尋／執行 Receipt。

結果：【目前通過最小案例】。

### C：安全變更入口

問題：跨方案發現共同缺口後沒有安全的變更入口。

目前候選：Change Request＋影響分析＋驗證＋決策。

結果：【目前通過最小案例】。

以上均屬目前實測結果，不等於永久正式架構。

## 十二、與三個正式方案的接口

```text
                問題解決系統
                       │
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
整體資料治理      AI知識管理      知識迭代與資料演化
        │              │              │
        └────────問題回饋／變更────────┘
```

本系統不擁有三方案的治理權，也不直接修改它們。

它只負責：

```text
問題 → 解法研究 → 實測 → 結果 → 回饋
```

正式採用仍由對應的治理、知識管理或演化流程處理。

## 十三、成立與升級條件

目前成立為小型共用系統的理由是：

1. 已經被實際問題重複使用。
2. 已經證明單靠搜尋或外部比對不足以完成問題處理。
3. 問題解決需要「候選 → 實測 → 判定 → 回饋」這個穩定中間流程。
4. 把流程抽出後可以被多個方案共用。
5. 仍然可以保持很小，不需要增加大型基礎設施。

未來只有在實際使用證明出現瓶頸時，才增加：

- 候選解法資料管理。
- 測試案例管理。
- Receipt 管理。
- 影響分析工具。
- 半自動搜尋或比較。

不得因為能力「可能有用」就預先建立大型平台。

## 十四、核心邊界

```text
搜尋系統
≠ 問題解決系統

外部比對系統
≠ 問題解決系統

變更檢測方案
≠ 問題解決系統

問題解決系統
≠ 三個正式方案

問題解決系統
= 把「發現的問題」轉化為「經過搜尋、比較、實測的可採用解法」的共用中間能力
```
