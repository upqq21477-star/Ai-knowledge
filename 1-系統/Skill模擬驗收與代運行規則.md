# Skill 模擬驗收與代運行規則 v1.0

## 目的

降低新 Skill 從設計到可運行之間的等待成本。模擬驗收通過後，即可進入正式運行流程；尚未有自然／實際運行證據時，以「（代）」標註其狀態。

## 正式規則

1. Skill 完成定義、觸發、邊界、協作與模擬驗收後，模擬驗收 PASS 即可視為正式 Skill。
2. 模擬驗收 PASS 的 Skill 可以進入正常運行，不必等待自然工作案例。
3. 尚未經實際運行驗證的正式 Skill，名稱或狀態加註「（代）」。
4. 「（代）」代表「已通過模擬驗收、可運行，但實際運行尚未驗證」，不是未完成，也不是 DEFER。
5. 當實際運行取得足夠驗證證據並確認運作正常後，取消「（代）」標註。
6. 實際運行失敗時，不因單次失敗自動撤銷 Skill；依既有驗證、診斷、演化流程處理。

## 狀態流程

企劃候選 → 模擬驗收 → PASS → 正式 Skill（代）→ 實際運行驗證 → 正式 Skill

若模擬驗收 FAIL，不能進入正式運行。

## 「（代）」語義

「（代）」是運行成熟度標記，不是 Skill 類型，也不是第二套生命週期。

它只回答一件事：
這個 Skill 是否已經有實際運行驗證？

- 有：取消「（代）」
- 沒有：保留「（代）」

## 與既有 Control Plane 的關係

- 不改 Skill Definition 為 Source of Truth 的原則。
- 不改 Registry 為 Derived View 的原則。
- 不讓 Registry 取代 Definition。
- 不把模擬驗收當成實際 Evidence。
- 模擬驗收 = 可以准入運行的門檻。
- 實際運行驗證 = 成熟度確認與「（代）」解除的依據。

## 驗收最低條件

至少確認：
1. 觸發正常。
2. Responsibility 邊界正常。
3. Input / Output 正常。
4. 與既有 Skill 委派正常。
5. 不產生路由循環或責任衝突。
6. 正常案例與主要失敗案例均能處理。

以上模擬 PASS 後，即可建立正式 Skill 並進入運行。

## 本次決策

2026-09-19 起採用本規則。原先「必須等待自然運行證據才能正式化」的門檻取消，改為「模擬驗收後正式運行、以（代）標註未經實際驗證」。
