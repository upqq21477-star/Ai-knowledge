# 問題清單 Problem Registry v1.0

版本：v1.0
日期：2026-09-19
狀態：【正式使用；隨 FIELD 持續更新】
用途：所有實際工作發現的問題之唯一追蹤入口。Problem Record 不取代 FIELD、Feedback 或施工紀錄；負責追蹤問題本身的生命週期。

## 一、問題入口規則

任何實際工作發現以下任一情況，必須先建立 Problem Record，再進入後續處理：
- Expected ≠ Actual
- 文件／索引／版本資訊不一致
- Context、資料或引用缺失
- Routing、Skill、Provider、Tool、Execution 或 Verification 異常
- 交接或追溯可靠性受到影響
- 重複出現的操作障礙
- 其他可能影響系統可靠性的異常

問題不要求一定 FAIL 才能登錄；PARTIAL、Verification 發現、非阻塞異常也可建立 Problem。

## 二、標準問題閉環

發現問題
→ 建立 Problem Record
→ Problem List
→ 分類
→ Severity / Impact / Scope
→ Diagnosis
→ Research（必要時 D0–D3）
→ Solution
→ Implementation
→ Verification
→ Re-test
→ 更新 Problem Record
→ CLOSED / DEFER / ACCEPTED RISK / ESCALATED
→ 判斷是否形成結構性 Failure Pattern
→ 必要時進 Skill Classification / Evolution / Distillation

禁止：
- 只寫在 FIELD Case 而不建立 Problem Record
- 只修正檔案而不留下 Problem Record
- 以 Re-test PASS 直接抹除問題歷史
- 把單次問題直接升格為新 Skill

## 三、Problem Record 欄位

| 欄位 | 說明 |
|---|---|
| Problem ID | 唯一 ID |
| Source Case | 發現問題的 FIELD / Real Work |
| Date | 發現日期 |
| Problem | 問題描述 |
| Layer | Data / Context / Research / Routing / Skill / Provider / Execution / Verification |
| Severity | L / M / H / UNKNOWN |
| Impact | 對可靠性、交接、成本、正確性的影響 |
| Scope | 單檔／單 Skill／跨文件／系統 |
| Expected | 預期 |
| Actual | 實際 |
| Diagnosis | 原因 |
| Solution | 解法 |
| Fix | 實際修改 |
| Verification | 修正驗證 |
| Re-test | 再測結果 |
| Preventive Rule | 防止重複規則 |
| Recurrence | 是否重複 |
| Structural Pattern | 是否形成結構性模式 |
| Related Records | 關聯案例／回饋／施工紀錄 |
| Status | OPEN / DIAGNOSING / FIXING / RE-TEST / CLOSED / DEFER / ACCEPTED RISK / ESCALATED |

- Structural Pattern：目前判定為流程缺口候選，尚無足夠重複證據升格為結構性 Failure Pattern。

## 五、問題與其他紀錄的關係

FIELD Case：
記錄「這次工作發生什麼」。

Problem Registry：
記錄「問題本身如何被發現、處理、驗證與關閉」。

Skill運作回饋：
記錄「問題／使用結果是否應影響 Skill 決策」。

施工總控：
記錄「這個問題在整體工程中處於什麼位置」。

四者可以互相引用，但不得互相取代。

## 六、驗收要求

任何新 Problem：
1. 建立 Problem Record。
2. 進入分類與 Diagnosis。
3. 有 Fix 才執行 Re-test。
4. Re-test 後更新 Status。
5. 關閉後仍保留歷史。
6. 若重複發生，更新 Recurrence 與 Structural Pattern。
7. 只有證據足夠才進 Skill Classification / Evolution / Distillation。
