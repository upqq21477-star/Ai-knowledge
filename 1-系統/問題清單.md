# 問題清單 Problem Registry v1.0

版本：v1.0
日期：2026-09-19
狀態：【正式使用；隨 FIELD 持續更新】
用途：所有實際工作發現的問題之唯一追蹤入口。Problem Record 不取代 FIELD、Feedback 或施工紀錄；負責追蹤問題本身的生命週期。

## 一、問題入口規則

任何實際工作發現以下任一情況，必須先建立 Problem Record，再進入後續處理：
- Expected ≠ Actual
- 文件／索引／版本資訊不一致
- Context、資料或引用缺失
- Routing、Skill、Provider、Tool、Execution 或 Verification 異常
- 交接或追溯可靠性受到影響
- 重複出現的操作障礙
- 其他可能影響系統可靠性的異常

問題不要求一定 FAIL 才能登錄；PARTIAL、Verification 發現、非阻塞異常也可建立 Problem。問題必須先記錄，再決定立即修正或延後批次修正。

## 二、問題處理策略：即時記錄、分層修正

發現問題
→ 建立 Problem Record
→ 分類：Structural Blocking / Non-Blocking
→ 判斷 Scope：單一系統／系統族群／跨 Skill 整合
→ 判斷是否影響後續結構

### Structural Blocking Problem
若問題會污染後續建立、破壞責任邊界、資料契約、Routing、上游／下游依賴或使後續工作建立在錯誤結構上：

立即停止受影響施工
→ Diagnosis
→ Solution
→ Fix
→ Verification
→ Re-test
→ 確認可繼續後恢復施工

### Non-Blocking Problem
若問題不影響後續結構，只影響局部品質、文件、同步、成本或非關鍵細節：

建立 Problem Record
→ 暫存
→ 繼續目前建立／整合
→ 在該建立階段或整合批次完成後統一 Diagnosis / Fix / Re-test

### 單一系統／Skill 建立
優先：
完成建立 → 記錄非阻塞問題 → 實際驗證 → 集中回修。

但只要問題會影響後續結構，立即轉 Structural Blocking。

### 多 Skill／多系統整合
若問題屬非阻塞：
先完成相關 Skill／系統的整合
→ 統一 Verification
→ 批次 Diagnosis / Fix / Re-test。

若問題會污染整合結構：
立即停止受影響部分並修正。

### 階段結束 Gate
每個建立族群／整合批次結束前：
1. 結清所有該批次 Problem。
2. OPEN 不得直接帶入下一個依賴階段，除非正式 DEFER / ACCEPTED RISK 並記錄理由、觸發條件與處理階段。
3. 所有 Fix 必須完成 Verification + Re-test。
4. 確認沒有未處理的 Structural Blocking Problem，才能進入下一階段。

### 整體工程 Closure Gate
整體工程結束前：
- 全部 Problem Record 必須有最終狀態。
- OPEN / DIAGNOSING / FIXING / RE-TEST 不得殘留。
- DEFER / ACCEPTED RISK 必須有正式理由、範圍、觸發條件、後續處理位置。
- Structural Blocking 必須全部解除。
- 最終 Verification 必須確認問題不再阻礙 CURRENT Baseline、交接與後續運作。

標準生命週期：
發現 → 建立 Record → 分類／Scope → Diagnosis → Solution → Implementation → Verification → Re-test → 更新 Record → CLOSED / DEFER / ACCEPTED RISK / ESCALATED → Failure Pattern 判斷 → 必要時 Classification / Evolution / Distillation

注意：
「記錄問題」與「立即修完問題」是兩件事。
所有問題都必須立即記錄；只有 Structural Blocking 必須立即修正。

禁止：
- 只寫在 FIELD Case 而不建立 Problem Record
- 只修正檔案而不留下 Problem Record
- 以 Re-test PASS 直接抹除問題歷史
- 把單次問題直接升格為新 Skill

## 三、Problem Record 欄位

| 欄位 | 說明 |
|---|---|
| Problem ID | 唯一 ID |
| Source Case | 發現問題的 FIELD / Real Work |
| Date | 發現日期 |
| Problem | 問題描述 |
| Layer | Data / Context / Research / Routing / Skill / Provider / Execution / Verification |
| Severity | L / M / H / UNKNOWN |
| Impact | 對可靠性、交接、成本、正確性的影響 |
| Scope | 單檔／單 Skill／跨文件／系統 |
| Expected | 預期 |
| Actual | 實際 |
| Diagnosis | 原因 |
| Solution | 解法 |
| Fix | 實際修改 |
| Verification | 修正驗證 |
| Re-test | 再測結果 |
| Preventive Rule | 防止重複規則 |
| Recurrence | 是否重複 |
| Structural Pattern | 是否形成結構性模式 |
| Related Records | 關聯案例／回饋／施工紀錄 |
| Status | OPEN / DIAGNOSING / FIXING / RE-TEST / CLOSED / DEFER / ACCEPTED RISK / ESCALATED |

## 五、問題與其他紀錄的關係

FIELD Case：
記錄「這次工作發生什麼」。

Problem Registry：
記錄「問題本身如何被發現、處理、驗證與關閉」。

Skill運作回饋：
記錄「問題／使用結果是否應影響 Skill 決策」。

施工總控：
記錄「這個問題在整體工程中處於什麼位置」。

四者可以互相引用，但不得互相取代。

## 六、驗收要求

任何新 Problem：
1. 建立 Problem Record。
2. 進入分類與 Diagnosis。
3. 有 Fix 才執行 Re-test。
4. Re-test 後更新 Status。
5. 關閉後仍保留歷史。
6. 若重複發生，更新 Recurrence 與 Structural Pattern。
7. 只有證據足夠才進 Skill Classification / Evolution / Distillation。
