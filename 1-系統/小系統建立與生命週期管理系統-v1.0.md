# 小系統建立與生命週期管理系統 v1.0

日期：2026-09-17
狀態：【新建立；候選小系統；待最小實測】

## 一、定位

本系統負責處理「功能已具備獨立運作價值，但規模尚不足以列入正式方案／核心系統」的小型系統。

它不是第四個正式方案，也不改變目前三方案架構。

小系統可以作為一個「單獨系統的最小方案（Minimum System Plan）」理解與管理：具有目的、邊界、輸入、輸出、依賴、建立程序、驗證程序與生命週期，但因規模過小，暫不升格為正式方案等級。

## 二、建立原則

不能因為想到一個功能就直接建立小系統。

建立前必須先確認：

1. 問題／需求確實存在。
2. 現有系統或方案沒有合理承擔能力。
3. 該能力具有可獨立運作的邊界。
4. 能明確說明輸入、輸出與使用時機。
5. 規模足以需要獨立管理，但不足以合理升格為正式方案。

## 三、最小建立流程

```text
發現需求／問題
↓
確認是否已有能力可處理
↓
搜尋外部方法／工具／案例
↓
比較成熟做法與本專案需求
↓
形成候選小系統
↓
建立對應知識書
↓
建立小系統最小規格
↓
確認與既有系統／方案的邊界
↓
最小實測
↓
判定
├─ 不成立 → 廢止／保留研究記錄
├─ 可用但需修正 → 修正後再測
└─ 成立 → 登錄小系統列表
```

## 四、知識建立要求

每個成立或進入實測的小系統，都應有對應的知識書，至少記錄：

- 解決的問題
- 核心概念
- 適用條件
- 不適用條件
- 最小運作方式
- 與既有能力的邊界
- 外部比較結果
- 已知限制
- 驗證狀態

知識書不是小系統規格的複製品；知識書保存可重用的知識，小系統文件保存可運作的能力契約。

## 五、外部搜尋與比對

小系統建立仍必須執行外部研究，不得因規模小而跳過。

研究至少回答：

- 外部是否已有成熟做法？
- 是否已有相近系統／工具？
- 本方案採用、修改或拒絕哪些做法？
- 為什麼不直接使用既有能力？
- 有哪些已知失敗模式？

本次建立參考 NIST AI RMF 的 Govern / Map / Measure / Manage 與生命週期持續管理觀念；NIST 明確要求 AI 風險管理持續進行，並重視文件、角色、測試與持續監測。citeturn0search3turn0search4 ISO/IEC 42001 亦採建立、實施、維護與持續改善的管理系統循環。citeturn0search1turn0search13

對能力目錄的外部比較顯示，能力目錄通常需要描述能力用途、依賴、輸出、成熟度與限制，並可作為治理與路由依據；因此本專案的小系統列表不應只是檔名清單，而應保留最小可統御資訊。citeturn1search3turn1search4

## 六、最小資料契約

每個小系統至少具有：

```text

名稱
目的

依賴

狀態
驗證狀態
知識書
系統文件
後續檢測標記
```

## 七、生命週期

```text
候選
↓
研究中
↓
建立中
↓
實測中
↓
成立
↓
運作中
↓
修正／再驗證
↓
升格／整合／廢止
```

「成立」不代表永久有效；後續系統更新、資料變更或實際使用結果可能觸發重新驗證。

## 八、統御規則

小系統由「小系統列表」統一登錄。

統御在開始其他工作時，應檢查：

1. 是否有與目前工作相關的小系統。
2. 是否有待驗證的小系統可以順便實測。
3. 是否有小系統依賴目前正在修改的系統／資料。
4. 是否有小系統因新工作而暴露缺口。
5. 是否達到升格、整合或廢止條件。

不得為了完成小系統檢測而刻意製造工作或繞過施工 Gate。

## 九、與正式方案的關係

```text
正式方案
  └─ 有明確完整責任範圍與足夠規模

小系統
  └─ 可獨立運作，但規模過小，不列入方案等級

小系統列表
  └─ 統一登錄、分類、路由、驗證與生命週期
```

當多個小系統形成穩定的共同目標、資料接口、責任邊界與足夠複雜度時，才可提出升格為方案或正式系統的問題。

## 十、成立條件

本文件目前只是候選小系統規格。

至少完成一次實際案例：

```text
需求
→ 外部研究
→ 知識書
→ 小系統規格
→ 實測
→ 結果
→ 列表登錄
→ 後續工作觸發檢測
```

全部通過後，才能將本系統狀態改為正式成立。
