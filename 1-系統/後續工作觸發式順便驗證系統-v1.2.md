# AI 知識庫後續工作觸發式順便驗證系統 v1.2

日期：2026-09-17  
狀態：【候選小系統；v1.0／v1.1 完善版；待後續真實施工驗證】

## 一、版本定位

本文件不是修改或覆蓋 v1.0，而是對 v1.0、v1.1 的後續完善版本。

v1.0 已建立基本能力：

```text
待驗證標記
→ 後續工作
→ 自然觸發
→ 順便驗證
→ 記錄結果
```

v1.1 進一步把待驗證標記與待辦／正常工作建立輕量關聯，並明確要求問題發生時優先利用自然案例，而不是另造測試工作。

本版進一步修正四個實際運作缺口：

1. `NOT TRIGGERED` 不應與 `MARKED` 混為同一層級的生命週期狀態。
2. 「工作看起來相似」不等於真正符合自然觸發條件。
3. 「已觸發」不等於「已完成驗證」；必須區分觸發、執行、證據充分與判定。
4. 待驗證標記不能只存在文件中，必須在後續工作開始時成為實際操作檢查。

因此本版的核心不是增加測試，而是把「等待自然案例」變成可重複執行的施工能力。

---

## 二、外部方法比對

本版建立前進行外部資料比對。

NIST AI RMF 的 Measure 功能要求 AI 系統在運作期間持續監測功能與行為，並記錄實際環境中的表現；同時要求追蹤既有、非預期與新出現的風險，並將實際表現、測量結果與回饋納入後續判斷。citeturn0search4turn0search9

NIST 2026 年針對部署後 AI 監測的研究也指出，部署前測試主要發生在受控環境，而部署後監測對確認真實環境中的可靠運作、發現非預期輸出與追蹤實際情境問題具有必要性。citeturn0search10

因此本專案採用的「正常施工時取得真實案例」方向與外部成熟方法一致，但本專案進一步把它縮小成自己的施工管理能力：

```text
已知待驗證能力
→ 等待正常工作自然提供案例
→ 使用真實工作資料驗證
→ 將結果回寫能力狀態
```

本系統不是 NIST 方法的複製品，也不負責完整 AI TEVV（Testing, Evaluation, Verification and Validation）。它只負責「已知待驗證項目如何在正常後續工作中被自然觸發並留下可追溯驗證資料」。

## 三、真正要解決的問題

本系統解決的是一個施工管理問題：

> 已經知道某項能力需要實際驗證，但正常工作尚未自然產生合適案例；如果為了驗證而另造工作，會增加施工成本並可能干擾主線；如果完全等待，又可能在後續工作中忘記驗證。

因此需要第三種方式：

```text
不人工製造問題
        ↓
保留待驗證標記
        ↓
每次相關正常工作開始時檢查
        ↓
自然觸發才介入驗證
        ↓
使用同一個真實案例取得資料
```

核心原則：

> 不為了驗證而製造工作；但只要正常工作自然產生有效案例，就不得無意識地錯過驗證機會。

## 四、系統邊界

### 本系統負責

```text
待驗證項目登記
↓
自然觸發條件定義
↓
後續工作開始時檢查
↓
自然觸發判定
↓
同步驗證標記
↓
驗證資料收集提醒
↓
結果回寫
↓
驗證標記狀態更新
```

### 本系統不負責

- 決定什麼問題本身值得解決
- 取代問題解決系統
- 取代搜尋研究方案
- 取代外部研究
- 取代完整測試／驗證方案
- 決定知識是否為真
- 決定方案是否成立
- 決定是否跨越施工 Gate
- 自行製造測試問題

因此：

```text
順便驗證系統
≠ 問題解決系統
≠ 測試系統
≠ 知識真實性裁決系統
```

## 五、核心資料物件：驗證標記

每一個待驗證能力建立一個輕量 `Validation Marker`。

最小格式：

```text
驗證 ID：V-XXX
待驗證能力：____
來源問題／缺口：____
自然觸發條件：____
不算觸發的情況：____
預期觀察：____
最低證據：____
結果回寫位置：____
目前狀態：MARKED
```

其中最重要的是三個欄位：

```text
自然觸發條件
不算觸發的情況
最低證據
```

沒有這三項，就容易發生「看到相似工作便宣稱已驗證」的錯誤。

---

## 六、自然觸發不是「看起來相似」

自然觸發必須至少符合：

```text
本次正常工作
＋
實際輸入／情境符合觸發條件
＋
該工作本身會產生所需觀察資料
＋
不需要為驗證額外製造特殊行為
```

### 不算自然觸發

```text
只是名稱相似
只是同一個系統
只是同一個待辦區段
只是可以想像能測
只是模擬了可能發生的情況
```

### 算自然觸發

```text
正常工作實際遇到標記中定義的情境
→ 該情境原本就需要處理
→ 處理過程會產生驗證所需資料
```

因此：

> 「能不能順便驗證」必須依觸發條件與證據需求判定，而不是依方便程度判定。

## 七、完整運作流程

```text
開始正常工作
↓
讀取目前狀態
↓
讀取本次待辦／工作
↓
取得目前 MARKED 驗證標記
↓
快速篩選可能相關標記
↓
逐項檢查自然觸發條件
        ↓
 ┌──────┴──────┐
否              是
↓               ↓
正常施工       標記 TRIGGERED
↓               ↓
保留 MARKED    正常完成主要工作
                ↓
             收集驗證資料
                ↓
             Expected / Actual
                ↓
             判定證據是否充分
                ↓
        ┌───────┴────────┐
      不充分             充分
        ↓                 ↓
    PARTIAL／OPEN     PASS／FAIL/PARTIAL
        ↓                 ↓
     回寫原因          回寫結果
        └───────┬─────────┘
                ↓
          更新標記狀態
                ↓
          判斷是否需重驗
```

## 八、狀態模型重新定義

v1.0／v1.1 最大的語義問題之一，是把 `NOT TRIGGERED` 與生命週期狀態放在同一層。

本版修正為兩個維度。

### A. 標記生命週期

```text
MARKED
→ OPEN
→ VERIFIED
→ CLOSED
```

或：

```text
MARKED
→ OPEN
→ FAILED
→ REOPENED
```

### B. 每次工作事件結果

```text
NOT TRIGGERED
TRIGGERED
```

觸發後再記錄：

```text
EVIDENCE-SUFFICIENT
EVIDENCE-INCOMPLETE
```

最後才形成：

```text
PASS
PARTIAL
FAIL
```

因此：

```text
NOT TRIGGERED
不是失敗
也不是永久狀態

它只是「本次工作事件沒有觸發」。
```

例如：

```text
V-002：MARKED

工作 A → NOT TRIGGERED → V-002 仍 MARKED
工作 B → TRIGGERED → EVIDENCE-INCOMPLETE → V-002 OPEN
工作 C → TRIGGERED → EVIDENCE-SUFFICIENT → PASS
```

這比讓 `MARKED → NOT TRIGGERED → MARKED` 反覆跳轉更適合長期追蹤。

## 九、驗證資料最低要求

一旦自然觸發，不得只記錄「已使用」。

至少記錄：

```text
驗證 ID
觸發工作
觸發條件
實際執行
預期結果
實際結果
Expected / Actual 差異
證據是否充分
判定
後續處理
```

其中：

```text
實際使用 ≠ 實際驗證
觸發 ≠ PASS
PASS ≠ 永久正確
```

如果問題解決系統介入，還必須保留其問題解決記錄的引用關係，而不是在本系統重新複製整份問題報告。

## 十、與問題解決系統的正確接口

當自然工作發現真正異常時，本系統只負責確認「這個異常同時也是某個待驗證項目的自然案例」。

若異常本身需要解決：

```text
正常工作
↓
發現異常
↓
後續工作觸發式順便驗證
↓
確認 V-001 / V-002 是否被觸發
↓
問題解決系統
↓
問題確認
↓
既有能力盤點
↓
外部研究／比較
↓
候選解法
↓
最小實測
↓
實際結果
↓
Expected / Actual Revalidation
↓
問題解決結果回寫
↓
同時更新 Validation Marker
```

因此本系統不是「問題解決路由器」本身。

真正的責任關係是：

```text
驗證標記系統：不要忘記驗證
問題解決系統：真正處理問題
統御能力：決定施工狀態與後續路由
```

---

## 十一、與待辦清單的接口

待辦清單仍是施工主線來源，不由本系統另建一套待辦。

待辦負責：

```text
做什麼
為什麼做
前置條件
依賴
Gate
施工進度
```

Validation Marker 負責：

```text
這項正常工作是否有機會順便驗證已知能力
```

操作順序：

```text
讀取待辦
↓
取得本次工作
↓
查找相關 MARKED
↓
自然觸發判定
↓
正常施工
↓
必要時同步驗證
```

因此：

```text
待辦完成 ≠ 驗證完成
驗證完成 ≠ 待辦完成
```

同一個工作可以同時完成兩者，但兩個結果必須分開記錄。

---

## 十二、與統御能力的接口

本系統最適合由統御能力在「工作開始前」進行輕量檢查。

不是每次重新分析所有驗證項目，而是：

```text
目前工作
↓
相關性快速篩選
↓
只檢查可能相關的 MARKED
↓
確認觸發條件
```

因此可以把操作成本控制在正常施工前的一個小檢查，而不是增加一套平行工作流。

未來若統御能力正式建立，可將本檢查作為其工作開始前的標準 Hook（鉤子／檢查點）。

目前不因此提前建立新的正式統御系統。

## 十三、目前應保留的驗證標記

### V-001：AI 知識庫基本運作真實問題閉環

待驗證：

```text
真實施工問題
→ 異常偵測
→ 警報
→ 問題分析
→ 嚴重程度
→ 影響分析
→ 處理建議
→ 必要時問題解決
→ 實測
→ 結果
→ 狀態重新驗證
```

目前：`MARKED`

自然觸發：

- 真實施工結果與預期狀態不一致
- Gate／依賴／工作順序發生實際異常
- 發生需要問題分析的真實施工問題

### V-002：問題解決系統自然啟動

來源問題：

```text
曾經發現明確流程異常
→ 問題解決系統當下未被自然啟動
```

待驗證閉環：

```text
自然異常
→ 問題解決系統被實際啟動
→ 問題解決
→ 候選解法
→ 最小實測
→ 實際結果
→ 狀態重新驗證
```

目前：`MARKED`

不得為 V-002 另造「第二次問題解決路由測試」，除非後續正常施工長期沒有自然觸發，或已有證據顯示需要受控重現。

## 十四、什麼情況可以建立獨立測試

正常情況優先順便驗證。

只有下列情況才考慮獨立測試：

1. 正常施工長期沒有自然觸發。
2. 該能力具有高阻斷性，不能等待自然案例。
3. 驗證需要正常工作不會提供的特殊輸入／環境。
4. 驗證本身具有破壞性。
5. 正常工作雖然觸發，但無法取得最低證據。
6. 已有自然案例顯示疑似失效，需要受控重現。
7. 若不立即驗證，可能造成後續大量錯誤施工或資料污染。

即使符合條件，也必須先經問題／施工狀態判定，不得因「想取得 PASS」就自行插入測試工作。

---

## 十五、禁止事項

- 不得人工製造問題，只為了讓標記觸發。
- 不得把表面相似工作當成自然觸發。
- 不得把觸發當成通過。
- 不得把使用當成驗證。
- 不得把模擬、推演、文件設計當成真實施工證據。
- 不得因待驗證標記擅自跨越 Gate。
- 不得建立與待辦平行的第二套施工主線。
- 不得把 `NOT TRIGGERED` 當成 FAIL。
- 不得因長期未觸發就無限期忘記該標記；必須在工作開始檢查時保留其可見性。
- 不得為了降低成本而降低最低證據標準。
- 不得以本系統取代問題解決、搜尋研究或正式驗證能力。

---

## 十六、成立條件

本小系統仍為候選，不因文件完善而自動成立。

至少需要未來真實施工產生以下資料：

### 必須出現一次自然觸發

```text
正常工作
→ 正確找到 MARKED
→ 正確判定自然觸發
→ 同步收集驗證資料
→ 完成判定
→ 回寫狀態
```

### 必須出現一次自然未觸發

```text
正常工作
→ 檢查 MARKED
→ 判定不符合條件
→ 不製造測試
→ 正常施工
→ 標記保持 OPEN/MARKED
```

### 必須證明問題路由

至少一次真實異常能完成：

```text
異常
→ 驗證標記檢查
→ 問題解決系統
→ 實測
→ 結果
→ Recovery Revalidation
```

### 必須證明沒有干擾主線

驗證不能造成：

- 不必要的獨立工作
- Gate 越級
- 待辦分叉
- 重複建立系統
- 虛構實測結果

## 十七、成立後的狀態判定

### PASS

表示本系統在實際工作中已能完成最小閉環，但不代表所有未來情況都已證明。

### PARTIAL

表示自然觸發與部分資料回寫正常，但存在漏檢、資料不足、路由錯誤等缺口。

### FAIL

表示在明確自然觸發條件成立時，系統未能執行必要檢查或造成實際施工錯誤。

### NOT TRIGGERED

只屬於單次工作事件結果，不是系統失敗。

## 十八、後續實際施工規則

從本版開始，後續正常工作採用以下順序：

```text
開始工作
↓
讀取目前狀態
↓
讀取待辦
↓
檢查相關 MARKED 驗證項目
↓
沒有自然觸發
→ 正常施工
→ 標記保留

有自然觸發
→ 正常施工
→ 同步取得驗證資料
→ 問題若需要解決則進入問題解決系統
→ 結果回寫
→ Recovery Revalidation
→ 更新 Validation Marker
```

因此下一步不是建立新的「第二輪測試」。

下一步是：

> 在下一個真正的正常施工工作開始時，實際執行這個檢查；如果自然出現 V-001 或 V-002 的觸發條件，就把該工作直接作為真實驗證案例。

若沒有觸發，只記錄必要的 `NOT TRIGGERED` 事件，不另造測試工作。

## 十九、目前結論

v1.0 解決「知道有待驗證項目」。

v1.1 解決「把待驗證項目帶入後續工作」。

v1.2 再解決：

```text
什麼才算自然觸發
什麼不算觸發
觸發與驗證的區別
事件狀態與生命週期狀態的區別
最低證據要求
問題解決系統接口
統御工作開始 Hook
獨立測試的例外條件
```

因此目前正式採用的最小模型是：

```text
MARKED
↓
後續正常工作開始
↓
相關性篩選
↓
自然觸發判定
├─ 否 → 正常施工；標記保留
└─ 是 → 同步驗證
          ↓
       實際執行
          ↓
       Expected / Actual
          ↓
       證據判定
          ↓
       PASS / PARTIAL / FAIL
          ↓
       回寫
```

本系統目前仍未通過真實施工 Gate。

文件完整 ≠ 系統成立。

下一個真實施工案例才是本系統真正的驗證來源。
