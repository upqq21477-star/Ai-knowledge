# 觸發條件管理系統 v1.0

日期：2026-09-17
狀態：正式建立；待實際運作驗證

## 一、定位

本系統是 Ai-knowledge 的 Trigger Registry（觸發索引）。

唯一核心任務：

> 將「事件／問題／需求」快速匹配到可能需要被啟動的 System ID。

本系統不是問題解決系統，不執行目標系統的工作，也不保存目標系統的完整流程。

## 二、最小資料模型

每一筆觸發記錄至少包含：

| 欄位 | 說明 |
|---|---|
| Trigger ID | 觸發條件唯一識別碼 |
| 觸發條件 | 可被觀察、描述與匹配的事件／情境 |
| 目標系統 ID | 被觸發的正式系統 |
| 系統名稱 | 方便人與 AI 直接理解 |
| 系統目錄位置 | 系統文件所在位置 |
| 狀態 | 啟用／停用／待驗證／待更新 |
| 備註 | 必要的最小說明 |

## 三、工作流程

```text
事件／問題／需求發生
↓
辨識事件特徵
↓
搜尋觸發條件
↓
找到一個或多個候選 System ID
↓
交給系統管理統御分支
↓
取得系統所屬方案、狀態與關係
↓
交由方案／系統進行精確判斷
↓
啟動實際處理
```

## 四、責任邊界

本系統負責：

- 觸發條件索引
- Trigger ID 管理
- 觸發條件與 System ID 的關係
- 基本觸發狀態
- 第一級候選匹配
- 觸發紀錄的更新與失效標記

本系統不負責：

- 判斷完整問題是否成立
- 執行問題解決
- 決定完整方案策略
- 執行系統內部流程
- 保存完整系統內容
- 取代系統或方案

## 五、觸發條件設計原則

### 1. 粗觸發，不保存完整邏輯

觸發條件的目的，是把 AI 從大量系統中導向少量候選能力。

例如：

```text
發現明確流程異常
→ 問題解決系統
```

而不是：

```text
發現異常 + 條件 A + 條件 B + 狀態 C + 知識 D
→ 執行完整問題解決流程
```

後者屬於目標系統自己的判斷邏輯。

### 2. 允許一對多候選

同一事件可能符合多個觸發條件。系統不得假定永遠只有一個候選。

候選衝突、優先順序與是否同時啟動，交由後續路由與方案層判定。

### 3. Trigger 不直接綁定方案

Trigger Registry 原則上只需要知道目標 System ID。

系統屬於哪個方案，由系統管理統御分支查詢。

這避免方案變更時必須同步修改大量觸發資料。

## 六、生命週期

```text
建立
↓
待驗證
↓
啟用
↓
更新／重新驗證
↓
停用
↓
廢棄
```

系統改名、搬移、升版、整合、廢棄時，必須檢查對應 Trigger 是否仍有效。

## 七、異常情況

至少需要能辨識：

- 找不到候選系統
- 同一事件命中過多系統
- 觸發條件互相衝突
- 目標 System ID 已不存在
- 系統已停用但仍有有效 Trigger 指向
- Trigger 與系統文件版本不一致
- Trigger 長期沒有實際命中而可能過時

## 八、目前不做的事情

本版本不建立複雜規則引擎（Rule Engine）、優先級計算器、事件總線（Event Bus）或自動化執行器。

先證明「觸發索引 → 系統目錄 → 方案 → 系統」這條路由在實際工作中有效，再決定是否需要增加能力。

## 九、驗證目標

至少取得一個自然工作案例，證明：

```text
實際事件
→ Trigger 命中
→ 找到 System ID
→ 系統管理統御分支查詢
→ 找到所屬方案
→ 正確移交
→ 目標系統實際啟動
→ 結果可回寫
```

沒有實際啟動與結果，不判定系統已完成驗證。
