# AI 知識庫後續工作觸發式順便驗證系統 v1.0

日期：2026-09-17  
狀態：【新建立；候選小系統；待後續工作實測】

## 一、目的

本系統用於處理一類不適合立即獨立施工、但後續正常工作很可能自然遇到的檢測項目。

核心原則：

> 已知需要驗證，但不必為了驗證而中斷主線時，先建立「待觸發驗證標記」；後續每次開始系統更新、方案施工或其他實際工作時，先檢查待辦與工作內容是否提供自然驗證機會。若條件成立，直接把該工作同時作為驗證案例，完成後記錄結果。

本系統不是要求所有待驗證事項都延後，而是避免兩種錯誤：

1. 為了小型驗證而頻繁中斷主施工主線。
2. 明知道某項能力需要驗證，卻在後續工作中反覆錯過自然測試機會。

## 二、目前已標記的驗證事項

### V-001：AI 知識庫基本運作系統的真實問題閉環

來源：

- `1-系統/AI知識庫基本運作系統-v1.0.md`
- `2-方案/完善/AI知識庫基本運作系統-v1.0最小實測-v1.0.md`
- `1-系統/問題解決系統-v1.0.md`

待驗證內容：

```text
真實施工問題
→ 異常偵測
→ 使用者可見警報
→ 問題分析
→ 嚴重程度判定
→ 後續施工／依賴／Gate 影響分析
→ 處理建議
→ 必要時進入問題解決流程
→ 候選解法
→ 最小實測
→ 問題解決結果
→ 回饋統御／目前狀態
→ Recovery Revalidation
```

目前狀態：

【已完成規格級最小測試；真實問題閉環尚未完成】

處理方式：

不立即另外開一條獨立施工主線。後續只要發生符合條件的真實施工問題，即優先使用該問題作為 V-001 實測案例。

完成後必須建立驗證記錄，不以「實際有用過」視為自動完成。

---

## 三、觸發條件

每次準備開始下列工作之一時，應先執行一次「順便驗證檢查」：

- 系統更新
- 方案更新
- 新功能／能力施工
- 既有系統實際操作
- 跨系統流程測試
- 問題解決工作
- 待辦項目施工
- 發現與既有標記項目高度相似的異常或工作場景

不要求每次都進行完整分析；先快速判斷是否存在可自然共用的驗證案例。

---

## 四、最小運作流程

```text
準備開始正常工作
↓
讀取目前狀態與待辦
↓
檢查「待觸發驗證標記」
↓
比較本次工作是否提供自然驗證條件
↓
否 → 正常施工

是
↓
把本次工作標記為「同時驗證」
↓
正常完成主要工作
↓
同步記錄驗證結果
↓
判定 PASS / PARTIAL / FAIL / NOT TRIGGERED
↓
更新驗證狀態
```

---

## 五、不得因此產生的錯誤行為

### 1. 不得為了湊驗證而修改正常工作

如果本次工作與標記事項只有表面相似，沒有實際驗證條件，不得硬套。

### 2. 不得把「使用到」直接視為「驗證通過」

必須有：

```text
觸發條件
→ 實際執行
→ 預期結果
→ 實際結果
→ 差異
→ 判定
```

### 3. 不得因待驗證項目而擅自跨越施工 Gate

本系統只能搭便車驗證，不得改變正式施工順序。

### 4. 不得把待驗證事項永久留在待辦清單而不檢查

每次自然觸發後都必須更新其狀態。

### 5. 不得因沒有觸發就判定失敗

`NOT TRIGGERED` 表示本次工作沒有提供有效驗證條件，不等於能力失敗。

---

## 六、驗證狀態

| 狀態 | 意義 |
|---|---|
| MARKED | 已標記，等待自然觸發 |
| TRIGGERED | 已找到符合條件的實際工作 |
| PASS | 實際驗證通過 |
| PARTIAL | 部分通過，仍有缺口 |
| FAIL | 實際驗證失敗 |
| NOT TRIGGERED | 本次工作不具備有效驗證條件 |
| CLOSED | 已完成足夠驗證，不再需要此標記 |

---

## 七、最小驗證記錄

每次觸發只需記錄：

```text
驗證 ID：
觸發工作：
原待驗證問題：
預期能力：
實際使用方式：
實際結果：
異常／差異：
判定：PASS / PARTIAL / FAIL
後續處理：
```

完整問題解決或大型驗證仍應使用既有的問題解決／驗證記錄，不在本系統重複建立完整報告。

---

## 八、與目前施工主線的關係

目前施工主線仍以 `待辦清單-v2.0.md` 為準。

本系統只提供一個輔助能力：

```text
主施工主線
    +
待觸發驗證標記
    ↓
正常工作時順便取得驗證案例
```

它不是新的核心正式系統，也不是第四個核心系統。

是否升格為正式系統，必須等實際使用後證明目前的小系統不足以支撐需求。

---

## 九、與目前 V-001 的關係

V-001 是本系統的第一個標記案例。

因此後續第一次符合以下條件的工作，應優先檢查是否可以直接完成 V-001：

- 發生真實施工問題；或
- 發現施工結果與預期狀態不一致；或
- 發現 Gate、依賴、工作順序、資料狀態存在實際異常；或
- 問題解決流程被真實觸發。

若符合，不能只把問題處理掉；應同步觀察 AI 知識庫基本運作系統是否完整執行：

```text
偵測
→ 警報
→ 問題分析
→ 嚴重程度
→ 影響分析
→ 建議
→ 問題解決
→ 結果
→ Recovery Revalidation
```

若整條閉環跑通，建立獨立驗證記錄並將 V-001 更新為 PASS 或其他實際判定。

---

## 十、成立條件

目前僅建立候選小系統。

至少完成以下實測後，才能判斷是否需要調整：

1. 至少一次正常工作成功觸發待驗證案例。
2. 至少一次沒有有效觸發條件時，能正確判定 `NOT TRIGGERED` 而不干擾主線。
3. 至少一次實際驗證結果能被獨立記錄。
4. 驗證完成後能正確更新標記狀態。
5. 不因順便驗證而破壞原本施工順序。

若實測顯示小系統已足夠，維持小系統，不升格。

---

## 十一、禁止事項

- 不得因本系統而自行建立大量待驗證項目。
- 不得把所有待辦都標成需要驗證。
- 不得為了驗證而製造人工問題。
- 不得把 `MARKED` 當成未完成主線工作。
- 不得把 `NOT TRIGGERED` 當成 FAIL。
- 不得繞過正式 Gate。
- 不得用本系統取代問題解決系統、搜尋研究方案或正式驗證方案。

---

## 十二、目前結論

本小系統解決的不是「如何驗證」，而是：

> 「已知需要驗證的能力，如何在不打斷正常施工的情況下，於後續實際工作自然發生時自動被想起、被觸發、被記錄，最後真正結案。」

目前：

```text
系統：候選小系統
V-001：MARKED
主施工：不受阻斷
下一觸發：後續系統更新／方案施工／實際問題處理時檢查
```
