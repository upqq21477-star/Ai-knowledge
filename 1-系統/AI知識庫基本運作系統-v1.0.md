# AI知識庫基本運作系統 v1.0

## 狀態
【新建立；候選系統；立即進入最小實測】

## 一、建立原因

目前專案已建立資料治理、AI知識管理、知識迭代與資料演化等多個架構能力，也建立問題解決與搜尋研究流程，但實際施工過程暴露出一個更基礎的缺口：

> 有「知識、方案、系統、待辦、驗證」的設計，卻缺少一個最小而持續運轉的基本工作循環，負責把目前狀態、問題、研究、知識、系統變更與驗證結果串成可運作流程。

因此本系統不是新增一個大型治理平台，而是提供 Ai-knowledge 本身最基本的 Operating Loop。

本次建立的直接觸發問題包括：

- 發現異常後沒有立即形成可見的問題回報。
- 統御雖能判斷狀態異常，但沒有穩定輸出問題分析、嚴重程度、後續影響與處理建議。
- 問題發現與問題解決流程之間存在路由斷點。
- 已累積大量研究與方案，但尚未形成足以持續產出「可重用知識」與「可運作能力」的最小閉環。

## 二、系統定位

本系統是 Ai-knowledge 的基本運作層。

它不取代：

- 整體資料治理系統。
- AI 知識管理系統。
- 知識迭代與資料演化系統。
- 問題解決系統。
- 搜尋研究方案。

它負責把這些能力按照目前狀態與問題需要組合起來，讓知識庫可以持續工作。

目前不直接宣告為第四個正式核心系統；先以候選系統建立並實測。只有實測證明三個正式系統無法合理承擔此責任時，才進行正式系統地位判定。

## 三、最小運作循環

```text
讀取交接與目前狀態
↓
確認目前施工階段與 Gate
↓
確認目前目標／待辦
↓
執行允許工作
↓
取得結果
↓
Expected State vs Actual State
↓
正常 → 記錄結果 → 進入下一允許工作

異常
↓
建立異常警報
↓
問題分析
↓
嚴重程度分析
↓
比較後續規劃／依賴／Gate／影響範圍
↓
處理建議
↓
必要時路由至問題解決系統
↓
取得問題解決結果
↓
重新檢查 Actual State
↓
重新判定 Gate 與施工方向
↓
形成知識／決策／狀態／驗證記錄
```

## 四、基本輸入

至少包括：

1. 目前狀態 Current State。
2. 正式規則與 Gate。
3. 待辦與目前目標。
4. 已知知識 Knowledge。
5. 工作記憶 Memory。
6. 執行結果 Observation。
7. 外部來源與證據 Source / Evidence。
8. 已確認決策 Decision。

## 五、核心能力

### 1. 狀態恢復

從交接資料、目前狀態、規則與待辦恢復：

- 現在在哪一階段。
- 哪些階段已完成。
- 哪些階段 LOCKED。
- 現在允許做什麼。
- 現在禁止做什麼。
- 下一個合法工作是什麼。

### 2. 工作守門

每次開始工作前檢查：

```text
目前階段
目標階段
前置條件
Gate 狀態
工作是否被允許
是否違反禁止事項
```

不得因使用者一句「開始做下一項」就跳過 Gate。

### 3. 結果檢查

工作完成後不能只記錄「完成」，必須比較：

```text
Expected State
vs
Actual State
```

差異即使尚未證明是故障，也必須被標記為需要判斷的異常或狀態差異。

### 4. 異常警報

異常不得靜默吞掉。

最小回報格式：

```text
【統御異常警報】
問題：____

【問題分析】
發生了什麼、與預期哪裡不同：____

【嚴重程度】
L0 / L1 / L2 / L3

【影響分析】
對目前工作、Gate、後續規劃、依賴與可能返工的影響：____

【建議】
繼續／修正後繼續／暫停受影響工作／進入問題解決流程

【處理優先級】
低／一般／高／阻斷
```

「沒有需要處理的異常」也應明確回報，而不是讓使用者無法知道系統是否檢查過。

### 5. 嚴重程度判斷

第一版不建立複雜數值風險模型，以可解釋規則為主。

```text
L0：資訊／描述差異，不影響目前合法工作。
L1：一般異常，目前不影響關鍵 Gate 或後續可信度。
L2：重要異常，可能影響後續工作、驗證或造成返工，建議先處理受影響部分。
L3：重大／阻斷異常，破壞 Gate、施工順序、資料可信度或造成大範圍錯誤，強烈建議先停止受影響工作並進入問題解決流程。
```

嚴重程度不是只看問題本身，而是同時看：

```text
問題本身
+
目前施工影響
+
後續規劃影響
+
依賴／傳播範圍
+
Gate 影響
+
返工成本
+
資料／狀態可信度
```

外部事件管理實務同樣將 triage、severity、impact、scope 與 response action 串接，而不是只產生警報。Microsoft 的事件管理文件明確將嚴重程度與影響範圍、受影響系統及適當回應連結，並要求根據嚴重程度決定處理層級。citeturn0search0turn0search2

### 6. 問題解決路由

當異常達到需要調查的程度：

```text
異常
↓
問題描述
↓
問題價值／影響確認
↓
問題解決系統
↓
搜尋研究
↓
外部方法比較
↓
候選解法
↓
最小實測
↓
判定
↓
回饋
```

L2 不應被當成普通資訊；L3 應強烈建議先處理，不應讓一般後續施工掩蓋它。

### 7. 恢復重新驗證

問題解決完成不代表施工狀態自動恢復正常。

必須重新取得：

```text
Actual State
↓
Gate
↓
依賴
↓
後續計畫
```

再判斷是否可以繼續。

## 六、知識產出循環

本系統不是只管理問題。

當一輪工作完成後，應判斷產出屬於：

```text
Observation
→ 發生了什麼

Evidence / Source
→ 依據在哪裡

Claim
→ 可以合理說什麼

Knowledge
→ 哪個可重用結論／方法已被支持

Decision
→ 本次採取什麼決定

Current State
→ 現在系統變成什麼狀態

Memory
→ 後續工作需要記住什麼上下文
```

只有可重用、條件清楚、依據可追溯的內容，才提升為正式 Knowledge。

## 七、研究與外部資料的基本規則

遇到新的技術問題時，不直接把搜尋結果當知識。

```text
問題
↓
研究問題
↓
外部方法／工具／案例
↓
比較
↓
候選解法
↓
最小實測
↓
判定
↓
形成可重用知識
```

研究資料是候選輸入；驗證後才能成為正式設計依據。

## 八、最小運作收據

每次重要工作至少應能重建：

```text
目前狀態
→ 問題／任務
→ 使用的知識／來源
→ 執行動作
→ 預期結果
→ 實際結果
→ 異常／正常判定
→ 嚴重程度
→ 處理決策
→ 驗證結果
→ 最終狀態
```

第一版不要求完整 Agent Observability 平台，也不要求資料庫。

## 九、與現有施工順序的關係

本系統不能成為跳過施工 Gate 的理由。

它反而負責執行 Gate：

```text
① 交接／工作狀態
→ ② 新系統規格
→ ③ 共同資料語義
→ ④ 狀態／版本／關係
→ ⑤ 現行格式唯一性
→ ⑥ 三方案資料／責任接口
→ ⑦ 跨系統長流程實測
→ ⑧ 統御能力驗證
```

目前應先在既有 ①～⑧範圍內實測本系統，而不是因為建立本系統就跳往⑨圖書館式知識管理。

## 十、與三個正式核心系統的責任分工

```text
基本運作系統
→ 何時做什麼、目前狀態是否正常、發生問題時怎麼回報與路由

整體資料治理系統
→ 資料的共同規則、邊界、責任、治理與驗證

AI知識管理系統
→ AI 如何理解任務、取得 Context、使用知識與完成任務

知識迭代與資料演化系統
→ 知識／資料如何變更、版本化、影響分析與演化

問題解決系統
→ 已確認問題如何研究、比較候選解法、實測與判定
```

若實測證明上述責任可以被既有三系統合理吸收，本系統可以降級為共用運作能力；若證明無法吸收，再進行正式系統化判定。

## 十一、第一輪最小實測案例

### 案例 A：正常施工

輸入：目前階段合法、前置條件完成、Actual State 符合 Expected State。

預期：

```text
無異常
繼續目前合法工作
```

### 案例 B：一般異常

輸入：工作結果與預期有小差異，但不影響 Gate 與後續關鍵工作。

預期：

```text
發出異常回報
L0/L1
說明差異
可繼續，但留下記錄
```

### 案例 C：重要異常

輸入：結果會影響後續驗證或造成返工，但尚未破壞整體施工主線。

預期：

```text
異常警報
問題分析
L2
說明後續影響
建議先處理受影響工作
必要時進入問題解決
```

### 案例 D：阻斷異常

輸入：嘗試進入尚未解鎖的階段，例如在②～⑧尚未完成時進入⑨。

預期：

```text
異常警報
問題分析
L3
明確指出 Gate 未滿足
強烈建議停止越級工作
路由問題解決
修復後重新驗證 Gate
```

### 案例 E：問題解決後恢復

輸入：L2/L3 問題已完成處理。

預期：

```text
重新讀取 Actual State
↓
重新檢查 Gate
↓
確認影響是否解除
↓
更新施工判定
↓
才允許繼續
```

## 十二、成立條件

本 v1.0 目前只是候選系統，不因文件建立即視為成立。

至少完成：

- [ ] 正常施工案例
- [ ] 一般異常案例
- [ ] 重要異常案例
- [ ] 阻斷異常案例
- [ ] 問題解決路由案例
- [ ] 問題解決後重新驗證案例
- [ ] 無歷史記憶 AI 可依交接資料恢復並執行本循環
- [ ] 與既有問題解決系統責任不重疊
- [ ] 與三個正式核心系統責任邊界清楚

只有實測完成後，才判定它是正式系統、共用能力，或應拆分／撤銷。

## 十三、目前明確禁止

- 不因建立本文件就宣告系統已驗證。
- 不因出現一次異常就自動建立更大的系統。
- 不以複雜風險分數取代可解釋的問題分析。
- 不讓警報取代問題解決。
- 不讓問題解決完成取代恢復後的狀態驗證。
- 不因本系統存在而跳過①～⑧ Gate。
- 不把搜尋結果直接提升為 Knowledge。
- 不把舊架構文件自動視為目前有效規則。
