# 整體系統健檢與架構健康度規則 v1.0

版本：v1.0
日期：2026-09-19
狀態：【正式治理規則；健檢結果回既有 Problem / Workpool】

## 1. 定位
本規則定義跨 System、Skill、Agent、Control Plane、Routing、Evidence、Lifecycle 與 Runtime 的整體健檢方法。

它不是：
- 新的 Skill。
- 第二套 Workpool。
- 第二套 Problem Registry。
- 第二套 Registry。
- 第二套 Runtime / Maturity 系統。

健檢的目的只有一個：
> 發現整體結構、責任邊界、依賴、Runtime 閉環與治理一致性是否仍健康，並把可執行結果送回既有工程控制面。

## 2. 職責
主控 Agent：
- 在適當事件發生時啟動或要求健檢。
- 提供本次任務與 CURRENT Context。
- 接收健檢結果，不自行替健檢結論升格 Skill。

Control Plane / 工程治理：
- 組織健檢範圍。
- 檢查 Authority、Dependency、State、Lifecycle、Evidence、Routing 與 Runtime 邊界。
- 對 Findings 分類並決定後續入口。

各 System / Skill：
- 提供自身 Definition、Boundary、Evidence、Verification 與實際運行資料。
- 不自行宣稱整體系統健康。

Problem Registry：
- 接收已確認問題。
- 管理問題生命週期。

Workpool（待辦清單.md）：
- 只保存可執行的後續工作。
- 健檢報告不得直接取代 Workpool。

## 3. 啟動條件
初期採事件觸發 + 定期保底，不設定僵化週期。

至少在以下情況重新健檢：
1. 重大架構或責任邊界變更。
2. Control Plane / Registry / Query / Routing 核心規則變更。
3. 連續自然異常或同類 Problem recurrence。
4. 一個主要工程階段完成。
5. CURRENT Authority、核心入口或 Source of Truth 發生變更。
6. 發現跨系統同步、依賴或 Lifecycle 邊界異常。
7. 長時間累積自然工作後，已足以重新評估原有設計假設。

若上述事件未發生，不強制為了「維持健檢」而製造案例。

## 4. 健檢範圍
每次只檢查與當前工程成熟度相關的項目，不做無差別全庫深掃。

最小檢查面：
- Authority / Source of Truth 是否唯一且可追溯。
- CURRENT / Workpool / Handoff / Blueprint 是否角色分離且沒有互相覆蓋。
- Skill Trigger → Capability → Candidate → Route → Invocation 是否閉合。
- Invocation → Context → Execution → Verification 是否閉合。
- Failure → Diagnosis → Fallback / Re-route → Recovery 是否有路徑。
- Multi-Skill 協作是否有責任邊界與實際 Evidence。
- State ≠ Acceptance ≠ Lifecycle 是否維持。
- Dependency / Impact / Change Set 是否仍一致。
- Runtime Trace / Receipt 是否能回答「為何啟動、做了什麼、如何驗證、為何停止」。
- Stop / Retry / Re-route / Chain depth / Cost 是否有基本邊界。
- Simulation 與 FIELD / Real Work 是否明確分離。
- 【代】是否仍有自然 Evidence 缺口。
- 重大變更後是否留下必要的 Handoff / Historical Trace。

## 5. Findings 分類
每個 Finding 必須同時標示 Type 與 Priority。

Type：
- BUG_CONFIRMED：已有可重現、可定位或直接檔案證據的錯誤。
- STRUCTURAL_GAP：規格／責任／契約缺口已被證據確認。
- RISK：目前尚未造成錯誤，但存在可識別風險。
- OBSERVATION：值得持續觀察，尚不足以施工。
- UNPROVEN：研究假設或尚未證明的能力，不得當 Bug。

Priority：
- P0：核心正確性、Authority、資料安全或主執行鏈受到阻塞。
- P1：已確認的跨系統／Runtime／結構性缺陷，應進主要 Workpool。
- P2：已確認但非阻塞問題，列入待處理批次。
- P3：低風險改善／觀察項，不阻塞目前主線。
- Deferred：尚未證明，留在研究／未來方向。

規則：
- 「可能有問題」不能直接寫成 BUG_CONFIRMED。
- UNPROVEN 不進 Problem Registry 的 Bug 類問題。
- BUG_CONFIRMED 必須進 Problem Registry。
- P0/P1 必須進主要 Workpool。
- P2/P3 可留在 Workpool 的低優先區、Pending／Observation 區。
- Deferred 不進施工 Workpool，除非後續證據改變分類。

## 6. 健檢報告與工程資料的關係
固定資料流：

健檢
→ Findings
→ Type / Priority
→ 已確認問題 → Problem Registry
→ 可執行工作 → 待辦清單.md
→ CURRENT / Blueprint / Handoff 必要同步
→ Verification / Re-test
→ 關閉或重新分類

健檢報告本身屬 Evidence / Historical Record。

不要建立：
- 「整體健檢待辦.md」
- 「整體 Bug 清單.md」
- 「第二 Problem Registry」

若需要查看 Bug，查既有 1-系統/問題清單.md；若需要知道下一步，查 待辦清單.md。

## 7. Problem 與待辦的分工
Problem Registry 回答：
> 發生了什麼問題？證據是什麼？原因、修正、驗證與生命週期到哪裡？

Workpool 回答：
> 現在還要做什麼？

因此：
- 健檢報告不能取代 Problem Record。
- Problem Record 不能取代施工待辦。
- 待辦完成不能抹除 Problem 歷史。
- CLOSED Problem 若產生新的預防性工作，才另外建立 Workpool 項目。

## 8. 健檢完成 Gate
一次健檢不得以「看過文件」就宣告完成。

至少完成：
1. Findings 已分類。
2. BUG_CONFIRMED 已進 Problem Registry。
3. P0/P1 已進 Workpool。
4. 必要的 Dependency / Authority / Lifecycle 影響已標記。
5. 已確認的同步修改完成後重新讀取受影響文件。
6. Simulation 與 FIELD 狀態沒有混寫。
7. 若發現重大結構缺口，已產生明確 Next Cursor。
8. 沒有把尚未證明的候選能力誤升格為施工項目。

若健檢本身產生主要待辦尚未完成，不代表健檢失敗；表示健檢完成、工程問題進入後續 Workpool。

## 9. 觸發後的最小健檢順序
CURRENT / Authority
→ Architecture / Boundary
→ Dependency / Change
→ Trigger / Routing
→ Invocation / Runtime
→ Verification / Failure Recovery
→ Lifecycle / Acceptance
→ Evidence / Trace
→ Findings 分類
→ Problem / Workpool 回流

先檢查控制閉環，再檢查個別細節。

## 10. Runtime 健康度最小要求
目前不建立大型 Observability 系統，只保留最小可追溯資料。

一次 Skill / Agent 執行至少應能逐步回答：
- Task
- Trigger
- Route
- Selected Skill
- Required Context
- Execution
- Verification
- Failure / Re-route（若有）
- Final Result
- Stop Reason

若目前自然運行尚不足以取得完整資料，標記為未證明能力，不以 Simulation 冒充 FIELD。

## 11. 停止與成本邊界
整體健檢同樣受最小成本原則限制。

不為了健檢而：
- 全庫無差別掃描。
- 重複讀取已確認的 Source。
- 建立大型新 Registry。
- 建立新的 Router / Agent。
- 人工製造 Failure。
- 把所有風險都變成施工項目。

若健檢成本開始高於能避免的實際風險，應縮小範圍並記錄原因。

## 12. 定期保養方式
不採固定「每週一定健檢」作硬 Gate。

採：
- 事件觸發：必做。
- 自然異常 recurrence：提高頻率。
- 主要階段完成：做一次完整健檢。
- 長期無重大事件：低頻抽查即可。
- 發生核心 Runtime / Authority 異常：立即局部健檢。

未來若自然工作資料顯示固定週期確有價值，再建立週期；沒有證據前不增加固定行政成本。

## 13. 與既有系統邊界
Blueprint：只保存全局地圖與導航，不保存完整健檢報告。
CURRENT：只保存現在工程狀態與游標，不保存所有健檢歷史。
Registry：只保存 Derived Metadata / Relation / Query View。
Problem Registry：保存已確認問題生命週期。
Evidence：保存健檢依據與實際驗證證據。
Handoff：只保存接手所需的最小恢復資訊。
Workpool：保存可執行工作。

以上角色不得互相取代。

## 14. 升格條件
只有當自然工作持續證明某類健檢能力本身值得獨立路由、具有穩定 Trigger、明確 Input / Output、獨立責任與可重複 Verification 時，才重新評估是否建立「健檢 Skill」。

在此之前，本規則只是治理方法，不建立新 Skill。

## 15. 核心判斷
整體健檢不是「再增加一層管理」。

它是：
> 對既有系統做定期／事件式健康檢查，將發現的問題回流到既有 Problem Registry 與唯一 Workpool，而不是再造一套管理系統。
