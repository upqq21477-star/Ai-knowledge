# AI 知識庫後續工作觸發式順便驗證系統 v1.1

日期：2026-09-17
狀態：【候選小系統；v1.0 完善版；待後續真實施工驗證】

## 一、這次修正的問題

v1.0 已建立「待驗證標記 → 後續工作自然觸發 → 同步驗證」能力，但本次實際施工發現仍有一個重要缺口：

> 待驗證能力雖然存在，施工者仍可能在正常工作中忘記檢查標記，或在發現問題後另外建立一次測試，而沒有把自然施工事件直接當成驗證案例。

因此本版把「待辦工作」與「待驗證標記」正式建立輕量關聯。

核心不是增加測試工作，而是讓待驗證項目成為後續工作開始時的檢查項。

## 二、核心原則

```text
正常施工工作
+
待驗證標記
+
自然觸發條件
↓
同一次工作順便驗證
```

只要正常工作本身已經會產生足夠的觀察資料，就不應另外建立獨立測試工作。

但如果正常工作不會自然產生所需資料，仍然必須建立專門測試；不能為了避免測試而降低驗證標準。

## 三、待辦清單中的最小驗證標記

待辦不需要增加完整驗證報告，只需要在適當工作項目附近保留：

```text
[驗證標記]
驗證 ID：V-XXX
待驗證能力：____
自然觸發條件：____
預期觀察：____
結果回寫：____
```

待辦項目仍然是施工主線；驗證標記只是附加資訊，不得變成另一套施工主線。

## 四、工作開始前的最小檢查

每次開始新的實際工作時：

```text
讀取目前施工狀態
↓
讀取本次待辦工作
↓
讀取與本工作可能相關的 MARKED 驗證項目
↓
判斷是否存在自然觸發條件
```

### A：沒有自然觸發

```text
NOT TRIGGERED
↓
正常施工
↓
保留 MARKED
```

不能因沒有觸發而判定失敗。

### B：有自然觸發

```text
TRIGGERED
↓
正常完成主要工作
↓
同步收集驗證資料
↓
實際結果
↓
Expected / Actual 比較
↓
判定
↓
更新驗證標記
```

## 五、與待辦清單的關係

待辦清單負責：

```text
做什麼
為什麼做
目前進度
前置條件
Gate
依賴
```

後續工作觸發式驗證負責：

```text
這次工作是否剛好可以順便驗證已知待驗證能力
```

兩者不能互相取代。

因此：

```text
待辦完成 ≠ 驗證完成
驗證完成 ≠ 待辦完成
```

同一工作可以同時完成兩者，但必須分別記錄。

## 六、本專案目前應採用的待驗證項目

### V-001：AI 知識庫基本運作真實問題閉環

驗證：

```text
異常偵測
→ 警報
→ 問題分析
→ 嚴重程度
→ 影響分析
→ 問題解決
→ 實測
→ 結果
→ Recovery Revalidation
```

目前：`MARKED`

### V-002：問題解決系統自然啟動

本次實際施工已發現問題：

```text
發現明確流程異常
→ AI 未啟動既有問題解決系統
```

目前已完成：

```text
問題確認
→ 既有能力盤點
→ 外部比較
→ 候選解法
→ 最小處理
```

但尚未證明下一次自然施工中會自動完成：

```text
異常
→ 問題解決系統自然啟動
→ 問題解決
→ 實測
→ 結果
→ 狀態重新驗證
```

因此 V-002 應標記為：`MARKED`

而不是建立一個「問題解決路由專用測試工作」。

## 七、這次問題的正確後續處理

今後如果正常施工再次出現以下任一情況：

- 實際施工結果與預期狀態不一致
- 發現系統／流程缺口
- Gate 或前置條件異常
- AI 明確發現需要解決的問題
- 使用既有問題解決能力的自然場景

應先檢查 V-001 / V-002。

如果符合自然觸發條件，就直接把該工作作為驗證案例。

不要另外建立：

```text
「第二次問題解決路由測試」
```

除非後續正常工作長時間都沒有自然觸發，且該能力的重要性已高到必須獨立驗證。

## 八、什麼情況才需要獨立測試

只有符合下列任一條件，才考慮脫離順便驗證：

1. 正常工作長時間沒有自然觸發。
2. 該能力具有高阻斷性，不能等待自然案例。
3. 驗證需要特殊環境或特殊輸入。
4. 驗證具有破壞性，不能混入正常施工。
5. 正常工作雖然會觸發，但無法取得判定所需資料。
6. 已有自然案例顯示能力可能失效，需要可控條件重現。

否則優先採用後續工作順便驗證。

## 九、驗證資料最低要求

即使是順便驗證，也不能降低證據要求：

```text
驗證 ID
觸發工作
觸發條件
執行內容
預期結果
實際結果
Expected / Actual 差異
判定
後續處理
```

因此：

```text
順便驗證 ≠ 隨便驗證
順便驗證 = 把驗證成本嵌入正常工作
```

## 十、狀態轉換

```text
MARKED
  ↓
NOT TRIGGERED
  ↓
MARKED

MARKED
  ↓
TRIGGERED
  ↓
PARTIAL / FAIL / PASS
```

`PASS` 不等於永久正確；若未來出現反例，可以重新開啟驗證。

## 十一、與問題解決系統的接口

如果自然施工發現的異常符合問題解決條件：

```text
後續工作觸發式驗證
        ↓
發現實際問題
        ↓
問題解決系統
        ↓
候選解法
        ↓
最小實測
        ↓
問題解決結果
        ↓
Expected / Actual Revalidation
        ↓
同時回寫 V-001 / V-002
```

這裡的關鍵是：

> 「順便驗證系統」不是問題解決系統的替代品，而是負責確保已知待驗證能力在自然工作中不被遺忘。

## 十二、目前施工策略

現在不再安排：

```text
第二次問題解決路由獨立測試
第二次實測回寫獨立測試
```

而改成：

```text
正常下一項施工
↓
開始前檢查 MARKED 驗證項目
↓
有自然觸發 → 同時驗證
無自然觸發 → 正常施工，標記保留
```

這符合既有「後續工作觸發式順便驗證原則」，並把它從一般原則提升為實際施工操作規則。

## 十三、成立條件

本版仍為候選小系統。

需要透過後續真實施工觀察：

1. 是否能在工作開始前實際檢查 MARKED 項目。
2. 是否能正確判斷自然觸發／未觸發。
3. 觸發後是否真的同步記錄結果。
4. 問題發生時是否能自然路由至問題解決系統。
5. 是否不增加不必要的獨立測試工作。
6. 是否不破壞原施工 Gate 與主線。

只有這些實際使用資料足夠後，才判斷是否需要進一步升級系統。

## 十四、結論

本次修正後，施工策略正式從：

```text
發現待驗證能力
→ 再安排一次測試
```

改為：

```text
發現待驗證能力
→ 建立 MARKED
→ 放入後續工作可檢查範圍
→ 正常施工
→ 自然觸發就順便驗證
→ 沒觸發就保留
→ 只有必要時才建立獨立測試
```

這可以降低驗證工作的額外成本，同時避免「知道需要驗證，但一直忘記驗證」的問題。
