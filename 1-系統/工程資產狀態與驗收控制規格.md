# 工程資產狀態與驗收控制規格 v1.0

版本：v1.0
日期：2026-09-19
狀態：【正式規格；新規則】
定位：統一 Skill、System、Plan、Application 等正式工程資產的狀態、生命週期與驗收階段語義。

## 1. 為什麼需要獨立控制

本庫目前存在三種不同性質的狀態資訊：

1. 工程建立／驗收階段：描述一項能力目前施工到哪裡。
2. Runtime / Availability State：描述目前是否可運行、是否停用。
3. Lifecycle：描述資產從建立、驗證、FIELD、Active 到 Historical 的演變。

這三者不能用同一個欄位混合。

尤其「【代】」不是 Active / Inactive，也不是 Lifecycle；它表示「功能已建立並可運行，但尚未取得足夠自然／實際運行證據」。

外部實踐也採用類似分離：Backstage 將 lifecycle 與 status 分開；Kubernetes 則將期望規格與實際 status 分開，並可用多個 conditions 表達不同狀態面向。citeturn1search4turn1search0turn1search6

## 2. 三個正交維度

### A. Acceptance Stage｜建立／驗收階段

統一使用：

【未】 → 【驗】 → 【代】 → 【已建立】

- 【未】：只有功能線索／規劃入口，正式建立尚未開始。
- 【驗】：已有正式規劃，功能仍在建立、整合、修正，尚未到只剩實際驗收。
- 【代】：規劃功能全部完成，可正式運行；只剩自然／實際運行證據尚未充分。模擬驗收只作准入與追蹤，不等於實際驗收。
- 【已建立】：完成該建立／驗收階段，且已有足夠 Evidence 支持正式完成。

【代】實際運行出現重大問題時，回到【驗】；證據不足則保持【代】。

### B. State｜目前可用狀態

由 Control Plane / Registry 使用既有正式語義，例如：

CURRENT / ACTIVE / INACTIVE / PENDING / DEFERRED / CLOSED / UNKNOWN / HISTORICAL

State 回答：「現在是否處於某種正式工作／可用狀態？」

不得用 State 直接代替 Acceptance Stage。

### C. Lifecycle｜生命週期

依正式 Lifecycle 規格，例如：

Created → Verified → FIELD → Active → Updated → Superseded → Historical

Lifecycle 回答：「這個資產在整體生命週期位於哪個階段？」

Lifecycle 不因一次驗收標記直接改寫。

## 3. 最小資料模型

正式工程資產至少可被描述為：

- ID
- Type
- Name
- State
- Acceptance Stage（適用時）
- Lifecycle（適用時）
- Version
- Authority
- Source
- Evidence / Verification Pointer

其中：

State ≠ Acceptance Stage ≠ Lifecycle

## 4. 例子

### Blueprint Governance Skill

State：ACTIVE
Acceptance Stage：【代】
Lifecycle：Active
Meaning：可正式運行，但自然運行 Evidence 尚未充分。

### 會議紀錄管理 Skill

State：ACTIVE
Acceptance Stage：【代】
Lifecycle：Active

其內部「OPEN → READY → CONVERTED → CLOSED」是「會議紀錄本身」的內容生命週期，不是這個 Skill 的工程生命週期，也不是 Control Plane 的 State。

### 尚未施工的新 System

State：PENDING
Acceptance Stage：【未】
Lifecycle：Created / 尚未進入後續階段

## 5. 責任分工

| 項目 | 主責 |
|---|---|
| Acceptance Stage 的建立／完成判定 | Planning + 實作者 + Verification |
| Acceptance Stage 地圖同步 | Blueprint Governance |
| State / Availability | Control Plane / Registry 正式規則 |
| Lifecycle | Skill/System 對應正式 Lifecycle Governance |
| 實際驗收 | Verification |
| Evidence | Evidence |
| 正式工程游標 | CURRENT |
| Skill 詳細 Definition | 各 Skill Source of Truth |

任何單一 Skill 不得自行宣告自己完成或自行解除【代】。

## 6. Registry 規則

Registry 可以保存：

State
Acceptance Stage
Lifecycle

但三者必須分欄，不得把：

ACTIVE（代）

當成單一 State。

正確表示：

State = ACTIVE
Acceptance Stage = 【代】

Registry 是 Derived View；正式來源仍由 Definition / CURRENT / Evidence 等對應權威來源提供。這符合成熟目錄系統將 lifecycle、status 與來源資料分開的做法。citeturn1search2turn1search4

## 7. Blueprint 規則

Blueprint 只需要顯示理解全局所需的最小資訊。

對主要功能至少顯示：

名稱｜功能｜State／Acceptance Stage｜位置｜主要關係｜詳細來源

Blueprint 不建立第二套狀態資料庫。

## 8. 會議紀錄規則

會議紀錄管理 Skill 的「OPEN / READY / CONVERTED / CLOSED」只管理「紀錄內容是否已轉移／關閉」。

它不能被解讀成：

- Skill State
- Skill Lifecycle
- Acceptance Stage

需要判斷 Skill 本身狀態時，回到本規格。

## 9. 模擬驗收規則

模擬驗收 PASS：

- 可取得正式運行准入。
- Acceptance Stage 可進入【代】。
- 不產生 FIELD / REAL_WORK 證據。
- 不可宣稱實際運行已驗證。

自然工作產生的實際 Observation / Evidence 才能解除【代】。

## 10. 一致性檢查

發現以下情況時標記 DRIFT，而不是猜測：

- State 與正式 CURRENT 不一致。
- Acceptance Stage 與實作完成度不一致。
- Lifecycle 與正式 Change / Verification 不一致。
- Registry 與 Source 不一致。
- Blueprint 與正式來源不一致。

UNKNOWN 保持 UNKNOWN。

## 11. 不做

本規格不建立：

- 第二 Registry
- 第二 CURRENT
- 第二 Lifecycle
- 第二 Problem Registry
- 自動完成判定
- 用名稱推導狀態
- 用 ACTIVE（代）這種複合字串取代結構化欄位

## 12. 核心原則

> 一個資產可以「ACTIVE，但仍是【代】」。
>
> 一個資產可以「PENDING，但不是【代】」。
>
> 「【代】」回答驗收證據是否成熟；
> 「State」回答目前正式狀態；
> 「Lifecycle」回答生命週期位置。
>
> 三者必須分開，才能讓 Skill、System、Plan、Application 共用同一套控制語義而不互相污染。
