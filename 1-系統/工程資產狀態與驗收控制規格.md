# 工程狀態與驗收最小規則 v1.0

版本：v1.0
日期：2026-09-19
狀態：【正式規則；蒸餾版】

## 1. 目的

統一工程資產最小必要的「目前狀態」與「驗收／實際運行證據」語義。

本規則不建立新的 Registry、Lifecycle 或 Evidence 系統。

## 2. State

State 表示資產目前的正式工作／可用狀態。

例如：
- ACTIVE
- INACTIVE
- PENDING
- DEFERRED
- CLOSED
- UNKNOWN
- HISTORICAL

State 回答：

> 現在處於什麼正式狀態？

State 不表示實際驗收證據是否已成立。

## 3. Acceptance

Acceptance 只表示建立／驗證目前走到哪裡：

### 【未】
只有功能線索或規劃入口，正式建立尚未開始。

### 【驗】
已有正式規劃，但功能仍在建立、整合或修正。

### 【代】
規劃功能已完成，模擬驗收 PASS，可正式運行；但尚缺足夠的自然／實際運行 Evidence。

【代】是暫時標記，不是新的 State，也不是 Lifecycle。

實際運行取得足夠 Evidence：
→ 移除【代】

實際運行發現需要修正的問題：
→ 回到【驗】

## 4. 模擬驗收

模擬驗收 PASS：
- 取得正式運行准入。
- 標記【代】。
- 不產生自然工作 Evidence。
- 不得宣稱已完成實際驗收。

模擬驗收 FAIL：
- 不准入正式運行。
- 回到建立／修正流程。

## 5. State 與 Acceptance 不得合併

正確：

State = ACTIVE
Acceptance = 【代】

禁止：

複合狀態字串
（不得把 State 與 Acceptance 合併）

因為兩者回答不同問題。

## 6. Lifecycle

Lifecycle 不在本規則重新定義。

各 Skill / System 依既有 Lifecycle 規格管理。

因此：

State ≠ Acceptance ≠ Lifecycle

本規則只要求三者不要混寫；不建立第二套 Lifecycle。

## 7. 責任邊界

- Skill Definition：功能本身的 Source of Truth。
- Control Plane / Registry：保存／查詢正式狀態資訊。
- Blueprint：顯示理解全局所需的最小狀態與驗收標記。
- Verification：判定驗證是否成立。
- Evidence：保存實際驗證依據。
- CURRENT：反映正式工程現況。
- 本規則：只定義 State 與 Acceptance 的最小共同語義。

任何單一 Skill 不得自行把自己的【代】解除；解除必須有對應實際 Evidence 與正式驗證結果。

## 8. 會議紀錄例外

會議紀錄本身的：

OPEN → READY → CONVERTED → CLOSED

只表示該筆紀錄內容的處理生命週期。

它不是：
- Skill State
- Acceptance
- 工程資產 Lifecycle

## 9. 最小流程

```
建立／修正
    ↓
模擬驗收
    ├─ FAIL → 繼續修正
    └─ PASS
          ↓
        【代】
          ↓
      正式運行
          ↓
   自然工作 Evidence
      ├─ 不足 → 保持【代】
      ├─ 正常且足夠 → 移除【代】
      └─ 發現問題 → 【驗】
```

## 10. 不做

本規則不建立：
- 第二 Registry
- 第二 CURRENT
- 第二 Lifecycle
- 第二 Problem Registry
- 自動完成判定
- 自動解除【代】
- 複合狀態字串
- 另一套 Runtime / Maturity 系統

## 11. 核心原則

> State 管「現在的正式狀態」。
>
> 【代】只管「功能已可運行，但尚缺實際運行證據」。
>
> 有足夠 Evidence 就移除【代】；發現需要修正的問題就回【驗】。

本文件是共同最小語義來源；其他文件只引用，不重複建立另一套狀態規則。
