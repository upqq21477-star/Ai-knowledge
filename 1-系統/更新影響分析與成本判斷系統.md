# 更新影響分析與成本判斷系統

## 狀態
【第一版建立；待更新方案實際驗證】

## 一、目的

處理「一項內容發生變更後，哪些資料、系統、方案可能受到影響，以及是否值得一起更新」的可重複問題。

本系統不是單純的檔案搜尋，也不是直接修改所有引用文件。

## 二、輸入

- 變更檔案。
- 舊版本與新版本差異。
- 變更原因。
- 已知依賴／引用／使用關係。
- 使用頻率與風險資訊（若有）。
- 更新時效要求。

## 三、處理流程

```text
變更確認
↓
建立變更集
↓
找直接依賴／使用者
↓
判斷直接影響
↓
逐層追蹤依賴
↓
形成影響範圍
↓
分類必須更新／條件更新／不更新／待確認
↓
估算更新成本與不更新風險
↓
判斷是否超過效率閾值
↓
形成更新計畫
```

## 四、影響分析規則

### 1. 先差異，後影響

不能因檔案被修改就假設整個檔案都受到影響。

先確定：

- 哪個定義變了。
- 哪個參數變了。
- 哪個條件變了。
- 哪個輸出或規則變了。

再尋找使用這些內容的項目。

### 2. 逐層擴散

每層只追蹤有實際關係的項目：

```text
變更項目
→ 直接使用者
→ 使用直接使用者的項目
→ 下一層使用者
→ ……
```

每加入一層，都重新判斷是否真的存在語義影響。

### 3. 防止循環

若某項目已分析過，不重新展開同一條路徑。

### 4. 停止

分支在以下情況停止：

- 沒有新依賴。
- 關係不存在。
- 變更不影響語義。
- 已經回到已分析節點。
- 新增分析只產生低可信度潛在關係。
- 分析成本已不值得降低的風險。

## 五、更新分類

| 分類 | 意義 |
|---|---|
| 必須更新 | 變更直接使內容失效或產生矛盾 |
| 條件更新 | 只有特定條件下受到影響 |
| 建議檢查 | 關係存在，但影響程度尚未確定 |
| 不需更新 | 已確認變更不影響該內容 |
| 暫不更新 | 已知可能受影響，但更新成本目前不值得 |

## 六、成本判斷

本系統只做足以支持決策的成本估算，不建立精密財務模型。

至少比較：

```text
更新成本
=
分析＋修改＋驗證＋連鎖更新

不更新成本／風險
=
錯誤使用＋未來重工＋一致性損失
```

判斷：

```text
收益明顯 > 成本 → 更新
收益接近成本 → 增加必要分析
收益明顯 < 成本 → 暫不更新
```

若增加分析本身的成本已高於可能改變決策的價值，也停止分析。

## 七、輸出

### A. 影響範圍

```text
變更
├─ 第一層
│  ├─ 第二層
│  │  └─ 第三層
│  └─ 第二層
└─ 第一層
```

### B. 更新清單

每個項目至少記錄：

- 路徑。
- 受影響內容。
- 影響關係。
- 更新必要性。
- 預估成本。
- 驗證需求。
- 狀態。

### C. 更新順序

先更新上游定義與核心規則，再更新依賴它們的系統、方案與應用。

## 八、系統邊界

本系統不負責：

- 自動修改所有檔案。
- 保證找出全部影響。
- 建立大型知識圖譜資料庫。
- 建立固定成本公式。
- 自動決定所有更新是否值得。
- 無限追蹤弱關係。

第一版只要求能用現有 Markdown、Git 歷史、檔案搜尋與已知系統關係完成分析。

## 九、與既有系統的關係

`1-系統/知識更新與狀態管理系統.md`：負責知識更新本身的狀態與更新管理。

`1-系統/知識整合系統.md`：負責知識間關係與整合。

`1-系統/方案管理系統.md`：負責方案的建立與驗證管理。

本系統增加的是「從一次變更出發，逐層找出受影響範圍並判斷更新成本」的能力。

## 十、成立性限制

這是小方案的第一版系統，不因為已建立就視為成熟。

只有實際更新任務證明：

- 能找到重要影響。
- 不會大量產生無效影響。
- 成本估算足以支援延後／更新決策。
- 能降低後續重新檢查成本。

才進一步穩定本系統。
