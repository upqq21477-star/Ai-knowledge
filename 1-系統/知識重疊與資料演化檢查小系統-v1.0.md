# 知識重疊與資料演化檢查小系統 v1.0

## 狀態

【候選小系統；已完成問題拆解與外部方法比對；首輪自然案例驗證待進行】

## 一、目的

本小系統用於處理知識庫、能力庫與系統重製過程中最常見的一組問題：

- 新增內容是否其實與既有內容重疊？
- 新資料應新增、修正、融合、取代，還是建立新版本？
- 舊資料是否仍有價值、依賴或歷史證據？
- 更新後哪些 Relationship、State、Version、Metadata 必須同步變更？
- 如何避免「新增一份就再加一份」造成資料膨脹與結構屎山？
- 如何避免同一底層能力被不同舊名稱、不同系統包裝重複保存？
- 如何讓大型重製可以逐步進行，而不是一次性刪除舊資料？

本系統不是完整的「知識迭代與資料演化方案」，也不是總體治理系統。

它只負責一件事：

> 在新增或更新資料／能力時，檢查是否存在既有可重用、可融合、可取代或應保留的內容，並形成可追溯的演化判定。

## 二、建立依據

本系統直接使用：

- `0-知識/管理/舊能力重製判定原則.md`
- `紀錄/舊模式重疊能力重製映射-v1.0.md`
- 目前正在建立的共同資料類型、Metadata、Relationship、State、Version 共同資料契約

舊能力重製判定原則要求以「能力」而不是檔名、目錄或系統名稱作為重製判斷單位；並以 Keep / Merge / Refactor / Replace / Rebuild / Retain / Retire 進行處置。其重疊判定至少比較目的、輸入、輸出、觸發、責任、狀態、資料、使用者、依賴與驗證等維度。

## 三、外部方法比對結論

本系統的設計先與軟體現代化與大型系統重製方法比較。

AWS 的大型組合分析方法要求先建立目前資產與依賴資料，再進行合理化分類，並將生命週期、相依性、複雜度與遷移方式一起考慮；AWS 的 7Rs 包含 Retire、Retain、Rehost、Relocate、Repurchase、Replatform、Refactor/Re-architect。citeturn0search1turn0search14

Microsoft 的 6Rs 也不是單純以「新舊」判斷，而是依複雜度、需求、依賴、時間、成本、效能、擴展性與整合要求決定 Rehost、Replatform、Refactor、Rebuild、Retire 或 Retain。其現代化生命週期先評估目前狀態，再規劃、執行與維護。citeturn0search0turn0search9

AWS 與 Microsoft 的大型重製指引都強調先拆分元件／能力、理解依賴，再決定處置方式，而不是看到舊系統就直接重寫或淘汰。citeturn0search3turn0search15

Strangler Fig 模式則提供另一個重要原則：新舊能力可以在遷移期間共存，逐步將功能移至新承載，最後才移除舊路徑。citeturn0search16

因此本小系統採用：

```text
先辨識 → 再比較 → 再判定 → 再遷移 → 驗證 → 最後處理舊資料
```

而不是：

```text
新增 → 疊加 → 重複 → 再新增一套管理
```

## 四、核心問題拆分

### P1：重疊偵測

判斷新內容是否與既有能力／資料具有實質重疊。

最低比較維度：

```text
目的
輸入
輸出
責任
觸發
資料
狀態
依賴
使用方式
驗證方式
```

結果：

```text
R0：無實質重疊
R1：局部重疊
R2：高度重疊
R3：完全重疊
```

### P2：處置判定

依重疊、價值、需求、證據與新架構責任判定：

```text
Keep
Merge / Consolidate
Refactor
Replace
Rebuild / Re-architect
Retain
Retire
```

本系統只產生判定結果／候選建議，不因判定而自動刪除舊資料。

### P3：資料演化

任何被採用的更新都必須區分：

```text
新增資料
修正既有資料
建立新版本
建立演化關係
部分取代
完全取代
融合
拆分
廢棄
```

不能用「新增一份 Markdown」取代所有演化操作。

### P4：舊資料處理

舊資料至少分成：

```text
目前有效
歷史有效
待遷移
被取代但需保留歷史
已驗證可淘汰
僅保留作為證據／追溯
```

「舊」本身不是淘汰理由。

### P5：防止無腦疊加

每次新增前先回答：

```text
是否已有相同能力？
是否已有可擴充能力？
是否只是現有資料的新版本？
是否只是既有能力的新名稱？
是否只是 Metadata／Relationship／State 的變化？
是否應修正原物件而不是新增物件？
```

若答案指向既有能力，優先進入融合／修正／版本演化，而不是建立新的平行能力。

### P6：防止屎山式結構累積

禁止用以下方式解決新需求：

```text
新問題
↓
新增一個系統
↓
新增一份資料
↓
新增一套狀態
↓
新增一套 Relationship
↓
新增一個特殊例外
```

必須先檢查既有共同資料能力與既有系統能力是否可以承接。

只有在既有能力無法合理承接，且新能力邊界、資料、責任與驗證條件已明確時，才進入新增系統流程。

## 五、與共同資料契約的對接

本小系統本身即作為共同資料契約的實際案例，不等待所有共同模型完全完成才開始使用。

### 1. Metadata

Metadata 用於描述物件，不應把可由其他資料安全推導的內容大量重複保存。

本系統關注：

```text
身份
類型
來源
責任
生命週期
目前有效性
驗證狀態
版本指標
```

實際欄位以共同 Metadata 最終契約為準。

### 2. Relationship

本系統需要使用演化與相依關係，尤其：

```text
修正
補充
部分取代
完全取代
融合
拆分
前身／歷史
依賴
```

若關係可以由既有資料安全推導，不重複人工保存反向關係。

### 3. State

不能使用單一 `status` 表達所有情況。

本系統至少需要區分：

```text
生命週期
有效性
驗證
啟用／工作狀態
```

例如「已被新能力取代」與「已從 Repository 刪除」不是同一狀態。

### 4. Version

版本用於表示同一能力／資料的演化，不等於檔名，也不等於 Git commit。

本系統需要能回答：

```text
目前版本是哪一版？
前一版是哪一版？
本次變更是修正、融合、取代還是拆分？
哪些舊版本仍可追溯？
新版本是否相容？
```

### 5. 共同資料類型

本系統不得自行創造與共同資料契約衝突的新核心資料類型。

如果檢查過程發現某種資訊無法合理放入既有資料類型，該問題應回寫共同資料模型分析，而不是直接增加一個新的核心類型。

## 六、最小運作流程

```text
觸發：新增／修改／重製候選
        ↓
取得物件身份與 Metadata
        ↓
搜尋既有相關能力／資料
        ↓
建立候選重疊集合
        ↓
比較目的／輸入／輸出／責任／資料／狀態／依賴／驗證
        ↓
判定 R0～R3
        ↓
檢查是否只是版本／Metadata／Relationship 變化
        ↓
形成 Keep / Merge / Refactor / Replace / Rebuild / Retain / Retire 候選
        ↓
檢查資料遷移、依賴、歷史與驗證條件
        ↓
建立演化關係與版本變更
        ↓
執行最小必要更新
        ↓
驗證新狀態
        ↓
舊資料：保留／標記歷史／轉移／淘汰
        ↓
記錄判定與證據
```

## 七、輸入

最小輸入：


```text

證據位置
```

## 九、核心防呆規則

### 規則 1：名稱不能直接判斷重疊

相同名稱可能是不同能力；不同名稱可能是同一底層能力。

### 規則 2：新增前必須查重

新增能力、系統或核心資料類型前，必須先檢查既有能力。

### 規則 3：相似不等於融合

至少需要 R1～R3 的實際責任／資料／輸出比較。

### 規則 4：重疊不等於刪除

發現重疊後先判定 Merge / Replace / Refactor / Retain / Retire 等處置，不直接刪除。

### 規則 5：新版本不應複製整份舊資料

能用 Version + Relationship 表達演化時，優先保存差異與演化關係，而不是無腦複製。

### 規則 6：淘汰必須可回溯

淘汰前要保留必要歷史、證據、依賴與替代關係。

### 規則 7：不能靠新增管理層解決管理膨脹

如果發現新的檢查功能與本系統高度重疊，先檢查是否應融合本系統，而不是直接建立第二套平行管理系統。

### 規則 8：本系統不取代問題解決系統

當檢查發現「共同資料契約不足」「多套系統責任衝突」「無法判定是否融合」等結構性問題時，轉入既有問題解決流程。

## 十、效率原則

效率不是少寫幾個檔案，而是降低整個生命週期的總成本。

主要成本：

```text
搜尋成本
AI 理解成本
重複資料成本
維護成本
狀態同步成本
Relationship 同步成本
版本管理成本
驗證成本
遷移成本
回復成本
錯誤累積成本
```

因此採用「先查重、再決定新增」而不是「先新增、之後整理」。

但也禁止為每一次小變更建立昂貴的完整分析流程；小變更應使用最小檢查，大型結構變更才提高分析深度。

## 十一、何時升級成方案

本系統維持小系統範圍，直到實際運作證明以下情況：

```text
跨多個系統與資料類型
需要完整遷移流程
需要批次影響分析
需要跨方案協調
需要大量版本／Relationship 管理
需要正式退役與回滾流程
需要多階段驗證與發布管理
```

若多項條件同時成立，則不再擴充本小系統成為巨型系統，而應依「問題拆分 → 外部研究 → 方案建立 Gate」評估是否形成正式的「資料演化／重製管理方案」能力。

## 十二、與舊能力重製映射的對接方式

`紀錄/舊模式重疊能力重製映射-v1.0.md` 不直接視為真實架構，而是本系統的第一批候選輸入。

每個映射項目後續應逐項補充：

```text
舊能力
↓
實際能力身份
↓
共同資料類型
↓
Metadata
↓
Relationship
↓
State
↓
Version
↓
實際依賴／使用
↓
R0～R3
↓
Keep / Merge / Refactor / Replace / Rebuild / Retain / Retire
↓
驗證條件
```

這一步的核心不是立刻完成整份映射，而是測試：

> 多個舊系統是否能被還原成少數幾個穩定的底層資料／能力物件。

如果大量舊能力最後只是在描述相同的 Metadata、Relationship、State、Version 與核心責任，則表示過去存在「同一底層能力的多重舊包裝」。

## 十三、目前邊界

本 v1.0 不負責：

- 自動刪除舊資料
- 自動合併全部文件
- 自動修改共同資料契約
- 自動建立新系統
- 自動決定所有架構問題
- 取代完整資料演化方案
- 取代問題解決系統
- 取代 Git 版本控制

本系統負責的是「檢查、比較、形成演化判定、建立追溯資訊、把結構性問題轉出」。

## 十四、首輪驗證案例

第一個實際驗證對象預定使用：

```text
紀錄/舊模式重疊能力重製映射-v1.0.md
```

驗證目標：

1. 能否找出同一底層能力的不同舊包裝。
2. 能否區分真正的新能力與單純版本／Metadata／Relationship 變化。
3. 能否避免因重疊而直接刪除仍有價值的舊資料。
4. 能否形成可追溯的演化關係。
5. 能否在共同資料類型尚未完全定稿時暴露契約缺口。
6. 能否降低新增平行系統的傾向。

本案例不得視為「模擬通過」。只有實際執行並產生可重現結果後，才可更新驗證狀態。

## 十五、驗證狀態

```text
文件建立：完成
問題拆分：完成
外部方法比對：完成
共同資料契約對接：進行中
實際案例執行：待進行
實測結果回寫：待進行
系統成立判定：待驗證
```

## 十六、重要原則

> 新增不是預設答案；先判斷它是不是已存在能力的另一種表示。
>
> 更新不是覆蓋；要能表示演化。
>
> 舊資料不是垃圾；先判斷它是目前資料、歷史資料、證據、前身還是可淘汰資料。
>
> 整合不是把文件貼在一起；是重新定義唯一責任、資料、關係、狀態與版本。
>
> 防止屎山不是禁止增加，而是禁止在沒有檢查既有能力與責任邊界前無限制增加平行結構。
