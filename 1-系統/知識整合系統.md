# 知識整合系統

## 狀態
【建立中／第二版】

## 一、系統目的

本系統負責把 `0-知識` 中已建立的基礎原理整合起來，確認它們彼此如何定義、依賴、約束、互補、實作，以及實際使用後如何互相影響。

核心問題不是「還缺多少知識」，而是：

> 單項知識各自成立後，組合起來是否仍然成立、是否缺少前提、是否互相重複或矛盾，以及如何共同支援 `1-系統`。

目前先用 Markdown 明確描述關係，不建立知識圖譜資料庫。

```text

↓

↓

↓
0-知識
↓

↓

↓
1-系統
↓

↓

↓

```

外部比對回答「單項知識是否值得採用」；知識整合回答「多項知識如何共同運作」。

## 四、知識關係模型

不把知識設計成單一父子樹，而採用最小的有向關係網。

目前使用六種關係：

1. **定義**：A 決定 B 所使用的概念含義。
2. **依賴**：A 成立或可使用，需要 B 作為前提。
3. **約束**：A 限制 B 可以如何使用。
4. **實作**：A 的原理被 B 落實成目錄、流程或系統方法。
5. **互補**：A、B 沒有上下級關係，但共同處理同一問題。
6. **產生／反饋**：實際使用產生新觀察，再反向修正既有知識。

因此：

```text
資料夾結構 ≠ 知識關係
```

`0-知識` 的資料夾回答「這份原理主要支援哪個功能」，不能代替邏輯關係。

## 七、知識、記憶、狀態的邊界

```text
知識
→ 目前可重用的理解、判斷或方法

記憶
→ 為了延續未來工作而保存的背景、歷史、決策或經驗

狀態
→ 內容目前處於什麼工作／採用／有效狀態
```

記憶中的經驗可以抽象成知識；知識被使用後也可能產生新的專案記憶。

```text
記憶／經驗 → 反覆使用 → 發現模式 → 抽象／驗證 → 知識
知識 → 實際使用 → 新記憶／新經驗
```

三者可以互相影響，但不能互相取代。

---

## 八、狀態對其他知識的約束

`資料狀態模型` 提供重要限制：

```text
內容 ≠ 狀態
```

所以：

```text
文件建立中 ≠ 內容全部錯誤
文件較新 ≠ 一定取代舊內容
歷史資料 ≠ 目前規則
AI 輸出 ≠ 已確認知識
```

這直接影響搜尋、比較、衝突與更新。涉及「目前」的問題，不能只依文字相似度判定，還要考慮時間、狀態、適用條件與正式決策。

目前尚無證據證明需要獨立的「知識狀態資料庫」，先沿用最小狀態模型。

## 九、知識變更的影響傳播

```text
知識 A 變更
↓
確認 A 改變了什麼
↓
找出直接依賴／受約束的內容
↓
逐項檢查是否使用到被修改部分
↓
判斷實際影響
↓
更新必要文件
↓
重新檢查相關 1-系統
↓
實際驗證
```

影響可能是：無影響、內容更新、條件補充、狀態更新、分類調整、系統流程調整、重新驗證。

「存在關係」不等於「一定受影響」。目前不做自動級聯修改。

---

## 十、整合時的衝突判定

內容不同不能直接視為衝突。

```text
主題 → 對象 → 時間 → 條件 → 適用範圍 → 狀態 → 結論
```

只有相同或重疊條件下仍不能同時成立，才判定真正衝突。

衝突後不能直接選「最新文件」或「AI 認為合理的答案」，而應回到來源、證據、正式決策、後續修改與實際使用結果。

## 十一、失敗時的錯誤定位

```text
實際結果錯誤
↓
應用使用錯誤？
↓
軟體實作錯誤？
↓
系統流程錯誤？
↓
知識使用錯誤／缺少條件？
↓
知識本身錯誤？
↓
定義／分類／狀態／證據是否有問題？
```

例如搜尋找不到資料，可能是分類錯誤、探索範圍錯誤、搜尋條件錯誤、文件表達問題，或資料確實尚未建立。因此搜尋失敗不等於搜尋技術不足。

---

## 十二、新知識加入時的整合檢查

新增或重大修改 `0-知識` 時，至少檢查：

1. 解決什麼問題？
2. 使用哪些既有概念？
3. 依賴哪些知識？
4. 哪些知識會約束它？
5. 與哪些知識互補或重疊？
6. 是否產生差異？
7. 差異是時間、條件、範圍、表述，還是真衝突？
8. 來源／證據是什麼？
9. 目前狀態是什麼？
10. 變更後哪些系統需要重新檢查？

不要求大量 metadata；必要關係直接寫在文件即可。

## 十三、目前關係成熟度

### 目前可直接採用的關係

- `知識定義與邊界` → 定義 → `資料層級與分類` 中的知識概念。
- `知識定義與邊界` → 上位概念 → `系統定義與邊界`。
- `資料層級與分類` → 提供概念邊界 → `分類維度`。
- `分類維度` → 約束 → `分類與目錄`。
- `分類原理` → 實作 → `分類與目錄`。
- `分類原理` → 屬於管理範圍 → `資料管理原理`。
- `系統定義與邊界` → 組織方式 → `系統與知識關係`。
- `資料探索` → 前置縮小範圍 → `搜尋原理`。
- `來源與證據` → 支撐 → `比較／衝突／更新`。
- `知識比較` → 前置判斷 → `知識衝突判定`。
- `比較＋衝突判定` → 決定 → `知識更新`。
- `資料狀態模型` → 約束 → `搜尋／比較／衝突／更新`。

這裡的「可直接採用」表示依現有文件內容已能合理建立關係，不代表已完成大量案例驗證。

### 待實際驗證

- `記憶定義與邊界` ↔ `知識定義與邊界` 的分類穩定性。
- `分類` → `探索` → `搜尋` 的實際成本改善程度。
- `搜尋失敗` → `分類問題` 的判定條件。
- `系統失敗` → `知識問題` 的定位流程。
- 描述性 `來源／證據` 是否足以支撐長期維護。

## 十四、與 1-系統的關係

```text
0-知識
↓
知識整合
↓
1-系統
↓
2-軟體
↓
具體應用
```

`0-知識` 提供原理；知識整合確認原理之間的關係；`1-系統` 再把它們組織成可反覆工作的結構。

系統必須增加組織能力：何時使用哪項知識、先後順序、決策條件、輸入輸出、驗證方法，以及失敗後如何回查。

因此：

```text
知識集合 ≠ 系統
```

## 十五、目前不建立的機制

暫不建立：

- 知識圖譜資料庫
- 知識 ID 系統
- 自動依賴分析
- 自動級聯更新
- 自動衝突裁決
- 統一可信度分數
- 複雜 metadata schema
- 大型關係資料庫

目前沒有足夠實際成本證明需要這些機制。

↓
