# 交接、待辦工作記憶與統御能力檢驗 v1.0

日期：2026-09-17
狀態：【第一輪檢驗完成；待實例持續驗證】

## 一、檢驗目的

確認目前 repository 是否已具備：

1. 將工作交接給下一個無歷史記憶的 AI。
2. 保存所有重要待辦及其施工脈絡，避免多輪對話後遺失。
3. 讓 AI 根據目前進度、依賴與返工風險安排施工順序。
4. 在不需要時暫緩好點子，而不是因為有價值就立即建立系統。

## 二、現有能力檢查

### A. AI 上下文與交接

現有文件：`1-系統/AI上下文與交接系統.md`

已具備：

- 分層讀取
- 最小充分上下文
- 目前狀態／歷史區分
- repository 黑箱接手測試
- 缺口發現後擴大搜尋
- 交接成功標準
- 過時資料與衝突辨識

判定：

> 交接能力已存在，而且已有實際驗證基礎；目前主要缺口不是「沒有交接系統」，而是交接內容需要更穩定地攜帶工作規劃脈絡。

### B. 根目錄待辦

現有 `待辦清單.md` 已是工作追蹤入口，保存大量共同規格、方案、系統與驗證事項。

問題：

> 它偏向「事項清單」，尚未穩定保存每個重要事項的「為什麼現在不做、依賴什麼、何時可恢復、完成條件、相關討論決策」。

因此只靠事項清單，經過十輪對話後仍可能需要重新推理。

### C. 待辦工作記憶

已新增：`待辦/待辦工作記憶與施工順序-v1.0.md`

用途不是取代根待辦，而是保存：

- 目的
- 狀態
- 優先級
- 依賴
- 延後原因
- 施工條件
- 禁止提前做的事情
- 恢復入口
- 已確認決策

判定：

> 這是目前最小必要補強，可先解決「想法存在但多年後不知道為何延後」的問題；尚不需要建立大型任務資料庫。

## 三、統御能力是否應建立

目前不直接建立獨立「統御系統」。

先驗證一項最小能力：

```text
目前狀態
→ 目標
→ 待辦
→ 依賴
→ 返工風險
→ 施工順序
→ 執行
→ 結果
→ 更新計畫
```

### 最小責任

統御／協調角色只需要回答：

- 現在在哪裡？
- 現在要達成什麼？
- 哪些事情已經完成？
- 哪些事情阻塞？
- 哪些事情有依賴？
- 哪件事現在做會返工？
- 哪件事應該先做？
- 現有能力是否足夠？
- 是否真的需要建立新系統？

不負責：

- 取代知識治理
- 自行裁決證據真實性
- 取代搜尋研究
- 取代資料演化
- 自行增加正式方案

## 四、實例驗證：圖書館式知識管理

輸入：

> 圖書館式知識管理很有必要，應建立 Catalog、Index、Collection 與大量知識定位能力。

統御判斷：

1. 需求有長期價值。
2. 但它依賴共同資料語義。
3. Catalog／Index 依賴版本與格式契約。
4. 大型知識管理還依賴跨方案接口與實際使用案例。
5. 現在直接細化會造成資料格式變動後重新設計 Catalog／Index。
6. 因此目前只保存範圍與前置條件，不進入完整實作。

結果：

> 通過第一個「先規劃、後施工」判斷案例。

## 五、目前不能宣稱的能力

尚不能宣稱統御能力已成為獨立系統，因為目前只有一個明確案例。

尚不能宣稱待辦工作記憶已完成正式 Schema，因為目前只確立最小保存內容。

尚不能宣稱交接能保證零遺失；只能說已有交接流程與驗證框架，且新增工作記憶後，對長期延期事項的恢復能力得到補強。

## 六、下一個實測

用同一套能力處理一個真正跨系統長流程：

```text
AI 任務
→ 搜尋研究
→ 外部證據
→ 知識衝突
→ 資料演化
→ 影響分析
→ 治理檢查
→ 新版本
→ Context 重新取得
→ 任務重新執行
→ 驗證
→ 失敗時問題解決流程介入
```

觀察統御能力是否能：

- 正確選擇下一步
- 不跳過前置條件
- 不重複已完成工作
- 不提前建立新系統
- 發現真正缺口時才建立能力
- 將結果寫回工作記憶

## 七、判定原則

若多個真實案例均能穩定完成以上判斷，再考慮是否把統御能力正式化為系統。

遵守：

> 先證明能力缺口，再建立系統；不是先建立系統，再尋找用途。
