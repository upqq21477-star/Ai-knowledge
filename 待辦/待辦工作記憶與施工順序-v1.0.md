# 待辦工作記憶與施工順序 v1.0

日期：2026-09-17
狀態：【建立；第一版施工記憶】

> 本文件是既有根目錄 `待辦清單.md` 的補充工作記憶，不取代、不刪除、不重寫既有待辦。
> 目的不是增加另一份互相競爭的待辦，而是保存「為什麼做、為什麼現在不做、前置條件、依賴關係、恢復時應從哪裡開始」；避免經過多輪對話後只剩下一串事項而遺失決策脈絡。

## 一、目前工作總目標

先完成新架構的共同基礎與實際對接驗證，再建立依賴這些基礎的上層能力。

核心原則：

```text
先確認規格
→ 再確認共同資料
→ 再確認版本／狀態／關係
→ 再確認接口
→ 再做跨系統實測
→ 確認穩定
→ 才建立依賴它們的上層能力
```

目的：降低返工，不因單一好點子提前建立完整系統。

## 二、目前第一優先級

### P0：新系統與交接基礎確認

狀態：【進行中】

必須確認：

- 三個正式新系統的正式規格
- 各系統責任、輸入、輸出、邊界
- 三系統與三正式方案的對接關係
- 新架構與舊架構的隔離規則
- AI 交接入口、目前狀態、決策、禁止事項、下一步
- 目前「不啟動」的正確語義
- 目前哪些能力已驗證、哪些仍只是設計

前置依賴：現有交接資料與三方案角色澄清。

完成條件：無記憶 AI 能依交接資料恢復工作狀態，且不把舊文件中的過時文字誤當成目前規則。

### P0：共同資料與版本統一

狀態：【進行中】

必須確認：

- 核心資料類型與邊界
- 共同最小描述原則
- 狀態模型
- 版本模型
- 關係語義字典
- 時間／範圍／條件表示
- 來源／證據／主張追溯
- 歷史／演化模型
- 大型整體更新（Full Migration / Full Rebuild）原則
- 現行格式唯一性：同一代現行資料不得長期並存多套正式格式

完成條件：三方案與三系統對共同資料語義、狀態、版本、關係的理解一致。

### P0：跨系統／跨方案實際驗證

狀態：【待執行】

主測試鏈：

```text
AI 任務
→ 搜尋研究
→ 外部證據
→ 發現知識衝突
→ 資料演化
→ 影響分析
→ 治理檢查
→ 建立新版本
→ AI 重新取得 Context
→ 任務再次執行
→ 驗證
→ 若失敗，問題解決流程介入
→ 再研究／候選解法／最小實測
```

重點檢查：

- 是否重複定義資料
- 是否出現版本／狀態名稱分裂
- 是否能傳遞 Change Request
- 是否能傳遞 Failure Receipt
- Search Receipt → Change Receipt → Validation Receipt 是否能形成可追溯鏈
- 是否需要正式交換格式；若需要，先由案例證明，而不是提前過度設計

## 三、第二優先級：知識書原子化規格

狀態：【方向已確認；等待共同規格穩定】

已確認方向：

> 知識書保持語義原子化、結構簡潔、低耦合、長期穩定；分類、索引、搜尋、版本、狀態、關係、遷移、驗證與 Context 組裝由上層能力承擔。

待確認：

- 知識書最小不可變核心
- 內容與治理 Metadata 的邊界
- 不應直接寫入知識書的管理資訊
- 知識內容變更與系統格式變更的邊界
- 跨系統／跨版本穩定性

禁止提前：完整 Schema、大型 Metadata、複雜索引。

## 四、第三優先級：圖書館式知識管理

狀態：【候選；已保存；暫緩製作】

這個想法不是遺失，而是已明確保存於：

`待辦/架構整合後續工作-v1.0.md`

定位：

> 以 Library 管理思想管理大量原子知識的 Catalog、Collection、Index、定位與 Context 前候選篩選；知識書本身不承擔整套管理複雜度。

暫定能力範圍：

- Knowledge Catalog
- 分類／Collection
- Knowledge Index
- 知識定位／檢索輔助
- Context 前候選篩選
- 大量知識分層管理
- 現行／歷史區分
- 大型資料重製後重建索引

正式製作前置條件：

```text
新系統規格
→ 交接資訊
→ 共同資料語義
→ 共同版本模型
→ 格式唯一性
→ 跨方案接口
→ 實際案例驗證
→ 再製作
```

禁止：現在直接做完整 Library 系統；提前決定 DB／Vector DB／Knowledge Graph；與搜尋研究方案重複。

## 五、第四優先級：統御／協調能力驗證

狀態：【候選能力；尚未升格正式系統】

目前假設的最小能力：

```text
讀取目前狀態
→ 讀取工作記憶／待辦
→ 理解目標
→ 理解依賴與前置條件
→ 判斷現在能不能做
→ 判斷先做什麼能降低返工
→ 排定順序
→ 執行或交給適當能力
→ 讀取結果
→ 更新工作計畫
```

必須具備的判斷：

- 目前進度在哪裡
- 現在的主要目標是什麼
- 哪些事項已完成／進行中／阻塞／暫緩
- 哪些事項互相依賴
- 哪些想法雖然有價值但目前不應製作
- 哪些事項應先完成以避免返工
- 現有能力是否足夠
- 是否真的存在新系統缺口

目前不建立獨立「統御系統」。先用真實案例驗證這項能力是否有穩定、不可由現有 AI 知識管理能力自然完成的缺口。

第一案例：圖書館式知識管理。

正確行為不是立即建立，而是辨識：它有必要，但依賴共同規格穩定，因此先暫緩並保存施工條件。

## 六、交接與待辦的資料保存要求

未來任何重要待辦，至少要能恢復以下資訊：

- 事項身份
- 目的
- 目前狀態
- 優先級
- 為什麼需要
- 為什麼現在做／不做
- 前置條件
- 依賴事項
- 建議施工順序
- 參考文件
- 已確認內容
- 尚未確認內容
- 相關決策
- 禁止事項
- 完成判定
- 下一步
- 若長時間未處理，重新啟動時應讀取什麼

這不是要求立即建立完整 Schema；先確立資訊保存原則。

## 七、不可遺失的目前決策

1. 三個正式方案仍只有：整體資料治理、AI 知識管理、知識迭代與資料演化。
2. 統籌目前是 AI 知識管理中的協調／能力分配角色，不是第四方案。
3. 融合蒸餾目前是跨方案分析／演化能力，不是第四方案。
4. 新三系統可以獨立執行、測試、互相驗證；禁止修改、接管、依賴舊架構。
5. 舊文件的「不啟動」文字不能凌駕目前交接澄清。
6. 大型整體格式更新採「新格式完整建立 → 全量轉換／重製 → 驗證 → 一次切換 → 舊格式退出現行體系」方向。
7. 舊格式可保留作歷史、Migration Source、Regression Test，但不作現行資料格式長期並存。
8. 知識書應保持簡潔與語義原子化，管理複雜度由上層能力承擔。
9. 圖書館式知識管理有價值，但必須等待共同規格、接口與實測穩定後再製作。
10. 目前不因候選能力名稱增加新的正式系統／方案；先證明缺口。

```text

↓
10. 圖書館式知識管理方案／系統能力正式製作
↓
11. 實際驗證
```

## 九、目前禁止返工的判斷

若後續提出新功能或新系統，先問：

```text
它依賴哪些共同規格？
是否已有現成能力？
是否真的存在能力缺口？
現在建立是否會因上層規格變動而重做？
是否能先以最小案例驗證？
```

若答案顯示上層規格尚未穩定，先保存需求、邊界、依賴與施工條件，不進入細部實作。
