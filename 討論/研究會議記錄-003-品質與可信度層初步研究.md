# 研究會議記錄 003：品質與可信度層初步研究

日期：2026-09-18

## 一、研究範圍

本輪研究項目：

10. 驗證 Verification
11. 證據 Evidence
12. Artifact

研究目標是確認 v0.1 是否需要將「驗證、證據、持久化成果」設為獨立架構能力，以及在「無 API、單人、GitHub 作為外部記憶」條件下，如何以最低有效複雜度建立可信度。

本輪特別避免一個危險假設：

「GPT 自己重新檢查一次 = 已完成可靠驗證。」

外部 Agent 工程資料顯示，隨著系統具有多步驟、工具呼叫、狀態修改與上下文取得，驗證本身需要被視為獨立工程問題。Anthropic 2026 年的 Agent evals 研究也明確指出，Agent 比單一 prompt 更難評估，應使用與系統複雜度相匹配的多種評估技術。citeturn0search1turn0search10

## 二、10. 驗證 Verification

### 1. 外部研究得到的核心結論

驗證不能只有一種形式。

OpenAI 的 Graders API 已將不同類型的評分器區分為字串檢查、文字相似度等機制，說明模型輸出可以由不同 evaluator／grader 依明確標準進行檢查，而不是只依靠模型自由判斷。citeturn1search8

Anthropic 對 Agent evals 的近期工程經驗則強調：Agent 會呼叫工具、修改狀態、根據中間結果調整，因此評估必須能覆蓋整體行為，而不能只看最後一句回答。citeturn0search1

這支持本系統把 Verification 從普通「最後再看一次」提升成正式能力。

### 2. 驗證應至少分成不同層級

可暫定為：

A. 結構驗證 Structural Validation
- 檔案是否存在
- Markdown／JSON／Schema 是否符合格式
- 必要欄位是否完整
- 連結、路徑、索引是否存在

B. 規則驗證 Rule Validation
- 是否違反系統規則
- 是否違反禁止事項
- 是否符合目前正式架構
- 是否產生重複／衝突責任

C. 內容／證據驗證 Evidence Validation
- 結論是否真的由來源支持
- 引用是否對應實際主張
- 外部資料是否被正確理解
- 是否把推論誤寫成事實

D. 行為驗證 Behavioral Validation
- 實際操作是否達成預期
- 檔案建立／修改後是否可被重新讀取
- 流程是否真的能運作

E. 回歸驗證 Regression Validation
- 新修改是否破壞既有能力
- 舊入口、索引、規則、交接流程是否仍有效
- 大型架構修改後是否留下舊格式與新格式混用

F. 架構健康驗證 Architecture Validation
- 是否產生責任重疊
- 是否出現孤兒文件
- 是否出現 CURRENT／HISTORY 混淆
- 是否出現重複知識
- 是否出現入口漂移
- 是否造成 Context 膨脹
- 是否使系統更難交接

### 3. GPT 自我驗證的正確定位

GPT 自我檢查可以保留，但只能視為一種 evaluator／review pass。

不能把：

「我重新看過了，沒有問題」

直接等價成：

「已驗證。」

更可靠的順序應該是：

產出
→ 機械／結構檢查
→ 規則檢查
→ 證據檢查
→ 必要時重新推理／反例檢查
→ 實際行為測試
→ 高風險項目人工確認

不是所有任務都需要跑完全部層級。

### 4. 無 API 條件下的最小可行驗證

目前不需要立即建立獨立評估服務。

第一階段可採：

「驗證清單 + GPT 驗證角色 + GitHub 歷史／Diff + 實際檔案重讀」

其中 GitHub 本身提供非常有價值的外部可觀察證據：Commit 具有唯一 SHA，可追蹤修改內容、時間與作者；Git 的版本歷史也允許恢復舊版本。citeturn2search0turn2search1

因此本系統可以把 GitHub history 當成驗證基礎設施的一部分，而不是只把它當儲存空間。

### 初步結論

Verification 必須保留為獨立能力。

但它不是固定的一個「AI 驗證員」，而是依風險選擇不同檢查層級的驗證機制。

暫定模型：

Task
→ Risk / Verification Requirement
→ 選擇驗證層級
→ Validation / Review / Test
→ Verification Result
→ 完成或退回修正

目前狀態：核心概念獲得強支持；具體驗證等級與門檻仍需實測。

## 三、11. 證據 Evidence

### 1. Evidence 與 Verification 必須分開

這一點非常重要。

Evidence 回答：

「為什麼我們現在相信這個結論？」

Verification 回答：

「我們如何確認這個結果符合要求？」

兩者相關，但不是同一件事。

例如：

外部官方文件是 Evidence。
確認我們的文件真的符合官方規格，是 Verification。

測試結果是 Evidence。
確認測試覆蓋了真正需要驗證的行為，是 Verification。

### 2. 外部研究：Provenance

W3C PROV 將 provenance 定義為描述某個資料／成果由哪些 Entity、Activity、Agent 產生、影響或交付的資訊；其用途包括理解來源、進行信任判斷、驗證流程是否符合要求，以及重現產生過程。citeturn0search0turn0search5

PROV 進一步將：
- Entity
- Activity
- Agent
- Derivation
- 時間
- 關聯

納入可追蹤模型。citeturn0search2turn0search6

這與本系統需要記錄「某個正式結論從哪裡來」高度相關。

### 3. 本系統不需要直接實作完整 W3C PROV

這是重要的成本控制。

我們需要的是 provenance 的核心思想，而不是建立完整 provenance database。

對本系統而言，最低有效 Evidence 可以記錄：

- 結論／主張
- 證據來源
- 來源類型
- 研究日期
- 關聯文件／章節
- 推論內容
- 驗證方式
- 最後狀態
- 若被推翻，指向新的結論

必要時再增加：
- Commit SHA
- 研究會議記錄
- 測試結果
- 相關 Artifact

### 4. Evidence 的重要性

Evidence 的真正價值不是「讓現在的 GPT 看起來比較可信」。

而是讓未來的 GPT 能回答：

「這個決策為什麼存在？」

「當初根據什麼資料？」

「這是外部事實、內部決策，還是當時的推論？」

「後來有沒有被推翻？」

因此 Evidence 是長期交接能力的一部分。

### 初步結論

Evidence 應獨立存在。

但第一階段採「輕量 provenance record」，不直接導入完整 provenance framework。

暫定 Evidence 類型：

1. External Source
2. Internal Evidence
3. Test Result
4. Decision Rationale
5. Observation
6. Historical Evidence

目前狀態：概念獲得強支持；資料欄位需要與研究／正式化流程整合。

## 四、12. Artifact

### 1. Artifact 與回答不同

Chat response 是當下溝通結果。

Artifact 是可以被後續工作重新使用、引用、修改、驗證、版本化的持久成果。

這是本系統非常重要的區分。

例如：

「我們應該建立圖書館系統。」

只是聊天結論。

「圖書館系統正式規格.md」

才是 Artifact。

### 2. GitHub 非常適合作為 Artifact 的持久層

GitHub／Git 的基本能力本身就包含：
- 檔案
- Commit
- 歷史
- Diff
- SHA
- 分支
- 標籤
- 精確版本連結

GitHub 文件指出 Commit 會記錄檔案變更、唯一 SHA、時間與作者；Git repository 同時保留檔案及其 revision history。citeturn2search0turn2search1

GitHub 也提供檔案歷史與逐行變更追蹤，以及指向特定 commit 版本的永久連結。citeturn2search2turn2search9

因此本系統沒有必要再建立一個獨立 Artifact Database。

### 3. Artifact 不只是「把答案存成 Markdown」

真正需要的是 Artifact 的生命週期。

可暫定：

Draft
→ Reviewed
→ Accepted
→ Active
→ Superseded / Deprecated
→ Historical

並且需要能知道：

- 它由什麼任務產生
- 使用了哪些 Evidence
- 經過什麼 Verification
- 目前是否為正式內容
- 是否被新 Artifact 取代
- 相關決策／研究記錄在哪裡

### 4. 與 Decision Record 的關係

外部 ADR 實務也支持將「重要決策」從普通討論中獨立保存。

ADR 的基本目的就是保存重要架構決策，以及其 Context、Decision、Consequences；成熟的 ADR 實務也強調 rationale、時間、替代方案與後續影響，並透過新 ADR 取代舊決策，而不是把歷史直接抹掉。citeturn1search0turn1search1turn1search7

這與本系統目前「研究 → 討論 → 驗證 → 正式化 → 歷史」的方向一致。

但 Artifact 不應等同於 ADR。

ADR 是一種 Artifact。

其他 Artifact 還包括：
- 系統規格
- 知識文件
- 研究結果
- 驗證報告
- 交接文件
- 方案
- 索引
- 會議記錄

### 初步結論

Artifact 應作為正式架構概念保留。

但不需要建立獨立儲存系統。

第一階段：

Artifact = Repository 中具有明確用途、狀態、來源與版本關係的持久成果。

## 五、本輪三項最重要的架構發現

### 發現 1：Verification、Evidence、Artifact 是三種不同問題

Verification：
「這個東西對不對？」

Evidence：
「為什麼我們相信它？」

Artifact：
「如何讓它在未來仍然存在、可引用、可驗證？」

三者不能合併。

### 發現 2：驗證應該是風險驅動，而不是固定流程

小任務：
結構／規則檢查可能足夠。

研究任務：
需要 Evidence Validation。

修改正式架構：
需要 Regression + Architecture Validation。

高風險或不可逆操作：
需要更強的實際測試／人工確認。

這避免驗證系統本身成為新的成本黑洞。

### 發現 3：GitHub 不只是 Storage，而是部分可信度基礎設施

Git history、Commit、Diff、SHA、permalink 讓 Repository 同時提供：
- 持久化
- 版本
- 變更追蹤
- 歷史
- 可回溯性

因此 v0.1 對 GitHub 的定位應逐漸從：

「外部記憶」

擴張理解為：

「外部記憶 + Artifact Store + Version History + 部分 Provenance / Verification Infrastructure」

但目前仍不應把 GitHub 宣稱為完整驗證系統。

## 六、暫定整體品質鏈

目前可形成：

Intent
↓
Control Core
↓
Execution
↓
Artifact
↓
Evidence
↓
Verification
↓
Decision / Adoption
↓
Current State

其中實際流程不是固定線性流程。

Evidence 可以在研究期間持續產生。

Verification 可以在中間多次發生。

Artifact 可以先產生 Draft，再經驗證後成為正式 Artifact。

因此更合理的理解是：

「Control Core 驅動的閉環品質系統」

而不是單純：

「執行 → 存檔」。

## 七、目前建議保留的最小資料模型

先不做完整資料庫。

Evidence Record：

- evidence_id
- type
- claim
- source
- date
- relation
- verification_status
- related_artifact

Verification Record：

- verification_id
- target
- verification_type
- criteria
- method
- result
- date
- related_evidence
- related_artifact

Artifact Metadata：

- artifact_id
- type
- status
- purpose
- created_from
- evidence
- verification
- supersedes
- superseded_by
- current / historical

這只是研究模型，不代表正式 schema 已確定。

## 八、目前仍未解決的問題

1. Evidence 是否需要獨立文件，還是可內嵌於 Artifact？
2. Verification Record 是否每次都持久化，還是只對重要任務保存？
3. Artifact metadata 是否需要統一格式？
4. 哪些任務達到「必須驗證」門檻？
5. GPT 自我驗證與獨立驗證的最低可靠組合是什麼？
6. 如何避免 Evidence 數量快速膨脹造成新的 Context Entropy？
7. 如何讓 Evidence、Artifact、Decision Record 互相可追蹤，但又不形成過度複雜的圖資料庫？

這些問題進入後續研究／實測，不在本輪直接定案。

## 九、對目前 v0.1 的影響

本輪研究沒有推翻原本的三層品質設計，反而使其邊界更清楚：

Evidence ≠ Verification ≠ Artifact。

同時增加一個重要限制：

不能把「GPT review」本身視為充分驗證。

因此未來品質層應該是：

Evidence
+
Risk-based Verification
+
Durable Artifact

而不是：

GPT 自我檢查
+
存檔。
