# 研究會議記錄 002：AI 決策與控制層初步研究

日期：2026-09-18
狀態：研究中
性質：討論／研究記錄，不代表正式採用

## 一、研究範圍

本輪研究項目：

4. 觸發管理
5. Intent／意圖解析
6. 回應契約
7. 藍圖規劃
8. 統御核心
9. GPT 角色切換

研究目標是確認 v0.1 所設計的「Intent → 回應契約 → 統御核心 → Blueprint → Role → Execute」是否具有外部工程與研究依據，以及各元件是否真的需要獨立存在。

## 二、4. 觸發管理 Trigger Management

外部研究顯示，Routing 通常可以採多層級決策，而不是所有請求一律交給大型模型。

OpenZiti 的 LLM Gateway Semantic Routing 採用三級 cascade：
1. 快速 heuristic rules
2. embedding similarity
3. LLM classifier
若前一層無法高信心判斷，才交給下一層；全部無法判斷則使用 default route。

這與本系統先以規則／關鍵字取得高召回候選，再由 GPT 依完整上下文進行語義判斷的想法高度接近。

### 初步結論

觸發管理應該被理解成「候選能力／流程的發現與啟動條件」，而不是單純 if/else 關鍵字表。

合理結構可能是：

使用者輸入
→ 低成本規則／索引取得候選
→ Intent 判斷
→ 能力適配度判斷
→ 啟動或不啟動

重要限制：

不能讓 Trigger 本身直接擁有完整的任務決策權，否則會與 Intent／統御核心重疊。

目前狀態：概念得到支持，但資料模型尚未定案。

## 三、5. Intent／意圖解析 Intent Parsing

外部 Agent 架構已經將「根據使用者意圖選擇 agent／能力」作為實際機制。

GitHub Copilot custom agents 的 runtime 會分析使用者 prompt 與 agent 的 name/description 之間的匹配，再決定是否 delegation；這是一個直接的 Intent → Capability 選擇案例。

因此 Intent 不應只回答「使用者在問什麼」，還應形成可供後續控制層使用的任務描述。

### 建議 Intent 結構

至少研究以下欄位：

- intent_type：查詢／研究／討論／規劃／執行／修改／驗證／交接等
- target：針對什麼對象
- objective：希望得到什麼結果
- scope：範圍
- depth：深度
- evidence_requirement：是否需要外部證據
- repository_requirement：是否需要讀取 Repository
- modification_permission：是否允許修改
- output_requirement：需要答案、Artifact、會議記錄或其他成果

### 初步結論

Intent 應該是「自然語言 → 可操作任務描述」的轉換層，而不是簡單分類器。

這與 v0.1 的設計一致。

目前狀態：概念得到強支持，欄位需要後續實測。

## 四、6. 回應契約 Response Contract

OpenAI API 的 Structured Outputs 提供一個直接的工程案例：使用 JSON Schema 限定模型輸出，strict 模式要求輸出遵守指定 schema。這說明當模型輸出需要成為可靠的下游介面時，不能只依賴自然語言格式約定。

因此本系統的「回應契約」可以理解成：

「本次任務允許 GPT 做什麼，以及完成後必須交付什麼格式與證據。」

它不只是輸出 JSON。

### 回應契約至少需要研究

- 是否允許讀 Repository
- 是否需要 Web Research
- 是否允許修改 Repository
- 是否需要建立 Artifact
- 是否需要驗證
- 是否需要引用證據
- 回答深度
- 必要輸出欄位
- 完成條件

### 初步結論

「回應契約」值得獨立存在，但名稱可能需要與「輸出格式 Schema」區分。

目前更接近：

Task Contract / Execution Contract

而非單純 Response Format。

這是本輪發現的一個可能修正點。

## 五、7. 藍圖規劃 Blueprint Planning

LLM Agent Planning 的研究已形成相對完整的研究領域。

2024 年 survey 將 LLM agent planning 主要研究方向整理為：
- Task Decomposition
- Plan Selection
- External Module
- Reflection
- Memory

2025 年的 comprehensive survey 進一步將方法整理為：
- External Module Augmented
- Fine-tuning based
- Searching based

並指出 planning 涉及環境理解、順序決策與複雜任務拆解。

這支持本系統 Blueprint 的基本概念。

### 但有一個重要修正

Blueprint 不應該等於「所有任務都先做完整計畫」。

外部 orchestration 實務將 Router、Planner、Supervisor 視為不同控制模式：

Router：決定任務去哪裡。
Planner：決定任務怎麼拆。
Supervisor：在執行過程持續決定下一步。

因此 Blueprint 應該是「需要時才建立的任務結構」，而不是所有請求的固定前置程序。

### 初步結論

保留 Blueprint，但採「任務規模／複雜度門檻」啟動。

小任務：
直接處理。

中型任務：
簡化 Blueprint。

大型／高風險任務：
完整 Blueprint + 驗證節點 + 必要時重新規劃。

## 六、8. 統御核心 Orchestration / Control Core

這一項獲得非常強的外部架構支持。

OpenAI Agents SDK 將 orchestration 定義為：
「哪些 agents 執行、以什麼順序執行、下一步如何決定」。

並區分：
- 由 LLM 決策流程
- 由程式碼固定流程
- 兩者混合

近期 Agent Engineering 的 Router / Planner-Executor / Supervisor 模式也清楚區分：

Router：
選擇路徑。

Planner：
產生 roadmap。

Executor：
執行計畫。

Supervisor：
在整個過程中持續保有控制權。

因此 v0.1 的「統御核心」並不是多餘的總控層。

### 初步結論

統御核心真正負責的是：

根據：
- 使用者目標
- Intent
- 目前狀態
- 可用能力
- 方案
- 證據
- 風險
- 約束
- 執行結果

決定：

「現在下一步應該做什麼。」

這與 Router／Planner／Supervisor 有關，但不必完全等同於任何一種模式。

目前較合理的理解是：

統御核心 = 上層控制決策。

它可以在不同任務中採用：
- 簡單 Router
- Planner → Executor
- Supervisor loop
- 直接 GPT response

因此不應固定成單一 workflow。

## 七、9. GPT 角色切換 Role Switching

GitHub Copilot 現行 Agent 架構直接提供：
- Custom Agents
- Subagents
- Skills
- Research Agent
- Explore Agent
- Task Agent
- Code Review Agent

Custom agents 可以具有不同 prompt、tool restrictions、MCP servers；subagent 可以在隔離 context 中執行子任務，再把結果回傳主 agent。

這直接支持「角色／能力上下文隔離」的工程方向。

### 但需要區分兩種模式

模式 A：同一 GPT 動態切換工作角色

例如：
研究者 → 規劃者 → 執行者 → 驗證者。

模式 B：建立真正獨立的 Subagent

例如：
主 Agent → Research Agent → 回傳研究結果。

目前無 API 單 GPT 架構更適合模式 A。

模式 B 應視為未來 API／Agent runtime 擴展，而不是目前必要條件。

### 初步結論

「角色」不應被理解為必須建立多個 AI。

更合理的是：

Role = 工作模式 + 對應上下文 + 權限 + 工具範圍 + 產出責任。

未來有 Agent runtime 時，可以自然映射成真正的 Custom Agent / Subagent。

## 八、本輪最重要的架構發現

### 發現 1：六項不是六個平行系統

更合理的控制鏈是：

Intent
↓
Contract
↓
Control Core
↓
決定是否需要 Blueprint
↓
選擇 Role / Capability
↓
Execute
↓
Observe / Verify
↓
回到 Control Core 或完成

Trigger 位於這條鏈的「候選能力發現」位置，而不是取代 Control Core。

### 發現 2：統御核心不應變成固定流程

外部研究支持多種 orchestration pattern。

因此統御核心應該是「決策者」，而不是：

if A → B → C → D

的死板 workflow。

### 發現 3：Blueprint 應該是條件式啟動

不是每個問題都需要完整計畫。

這也符合目前 AI Agent 工程中對成本、延遲與複雜度的考量。

### 發現 4：Role 與 Capability 必須分開研究

Role：
「現在以什麼工作模式思考？」

Capability：
「現在可以使用什麼能力？」

這兩者不能完全合併。

### 發現 5：Response Contract 可能需要重新命名／拆分

目前「回應契約」實際涵蓋：
- 權限
- 上下文需求
- 研究需求
- Artifact
- 驗證
- 輸出格式
- 完成條件

因此它可能更接近：

Task / Execution Contract

而「Structured Output Schema」只是其中一個子層。

這是目前尚未正式採用的研究性結論。
