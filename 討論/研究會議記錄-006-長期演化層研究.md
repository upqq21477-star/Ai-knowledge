# 研究會議記錄-006-長期演化層研究

## 研究範圍

本輪研究第 19、20、21 項：

- 19. 系統生命週期（System Lifecycle）
- 20. 知識生命週期（Knowledge Lifecycle）
- 21. 長期系統熵（Long-term System Entropy）

本輪的核心問題不是「如何再增加功能」，而是：

> 一套由 GPT 持續使用、持續寫入 GitHub 的外部記憶系統，運作半年、數年後，如何避免失效、膨脹、矛盾與架構腐化？

---

## 一、外部工程實務

### 1. 系統生命週期不是一次性建置

Microsoft 的 Application Modernization guidance 把現代化視為持續循環：

> Assessment → Planning → Execution / Launch → Maintenance

而不是「建好一次就結束」。

其中特別強調先理解 Current State，再決定現代化方向；並透過 PoC 驗證策略，再進入持續維護。這與本系統目前的：

> Current → Research → Proposal → Implementation → Verification → Current

高度相容。

來源：
Microsoft Learn — Application modernization life cycle
https://learn.microsoft.com/en-us/azure/app-modernization-guidance/get-started/application-modernization-life-cycle

Microsoft Azure Well-Architected Framework 也明確指出，架構規格不是一次性工作，架構師應持續參與實作、處理變化、POC 與 technical debt。

來源：
Microsoft Learn — Architect collaboration with workload teams
https://learn.microsoft.com/en-us/azure/well-architected/architect-role/collaboration

因此：

**系統生命週期應該是循環，而不是線性專案。**

---

## 二、知識生命週期

外部系統普遍不是把資料視為永久有效。

Microsoft Well-Architected guidance 建議持續記錄架構決策，並定期處理 technical debt、平台變化與 deprecation。

來源：
Microsoft Learn — Recommendations for standardizing tools and processes
https://learn.microsoft.com/en-us/power-platform/well-architected/operational-excellence/tools-processes

Kubernetes 的 API lifecycle 更提供了一個非常成熟的例子：

- Alpha
- Beta
- GA
- Deprecated
- Removed

而且 Deprecated 並不等於立即刪除。Kubernetes 會保留過渡窗口、提供警告、記錄使用情況，讓使用者遷移到替代方案。citeturn0search0turn0search3

這對知識庫非常重要：

**知識不應只有「存在／不存在」兩種狀態。**

## 三、系統熵：真正的長期問題

IEEE 對軟體架構演化的研究指出，架構會因演化而侵蝕（erosion），而設計決策如果只隱含在架構中，會發生「knowledge vaporization」：當初為什麼這樣設計的知識逐漸消失。

因此，將架構視為一組明確的設計決策，可以降低這種知識蒸發。citeturn1search12

另一項 IEEE 多案例研究則指出，architecture technical debt 會累積，而且其成因與後續回收存在可研究的演化過程。citeturn1search14

這直接支持本系統目前已經建立的：

- Evidence
- Decision
- Artifact
- Current / History
- Verification
- Handoff

它們並非單純增加文件，而是在保存「系統為什麼變成現在這樣」。

## 四、對本系統而言，「系統熵」是什麼？

本研究後，不建議把「系統熵」理解成單純的檔案數量。

真正需要控制的是：

### 1. 語意熵（Semantic Entropy）

不同文件對同一概念給出不同定義。

例如：

A 文件說 Library 是「知識索引」。

B 文件說 Library 是「能力註冊」。

C 文件又把 Library 當成「RAG」。

檔案仍然存在，但系統的語意已經不穩定。

### 2. 狀態熵（State Entropy）

系統無法判斷：

- 哪個是 Current？
- 哪個是舊版本？
- 哪個只是 Proposal？
- 哪個已被 Reject？
- 哪個只是研究結論？

這會直接造成 GPT 載入錯誤上下文。

### 3. 結構熵（Structural Entropy）

相同內容散落在大量不同位置：

- 同一規則多份複製
- 多個索引指向同一資訊
- 同一文件被不同目錄定義
- 文件之間產生循環依賴

### 4. 決策熵（Decision Entropy）

只知道「現在怎麼做」，卻不知道：

> 為什麼這樣做？

因此未來 GPT 很容易重新討論已經解決的問題。

### 5. 上下文熵（Context Entropy）

GPT 每次為了完成一個任務，需要讀取大量低相關內容。

結果：

> Token 增加，但有效資訊密度下降。

這與 Context Engineering 的核心問題直接相關。

### 6. 歷史熵（Historical Entropy）

歷史資料沒有消失，但大量歷史與 Current 混在一起，導致：

> 舊資訊看起來像新規則。

因此 History 必須可保留，但預設不能與 Current 等價。

## 五、系統生命週期模型

本研究不建議採用傳統「版本 1 → 版本 2 → 版本 3」作為唯一生命週期。

對本系統更合理的是：

> Build
> ↓
> Operate
> ↓
> Observe
> ↓
> Detect Problem
> ↓
> Research
> ↓
> Propose
> ↓
> Adopt
> ↓
> Implement
> ↓
> Verify
> ↓
> Operate

也就是：

**持續演化循環（Continuous Evolution Loop）。**

其中：

### Build

建立系統初始架構。

### Operate

實際使用 GPT + GitHub 執行工作。

### Observe

觀察：

- 找不到資料
- 找錯資料
- 上下文過大
- 重複研究
- 文件互相矛盾
- Handoff 失敗
- GPT 誤讀 Current
- 系統維護成本增加

### Detect Problem

把反覆出現的問題轉成：

> 可研究的工程問題。

### Research

外部研究與實際案例比較。

### Propose

提出改進方案。

### Adopt

經過 Adoption Gate 後正式採用。

### Implement

修改實際系統。

### Verify

驗證實作。

然後回到 Operate。

## 六、知識生命週期模型

建議知識採用：

> Discovered
> ↓
> Recorded
> ↓
> Classified
> ↓
> Validated
> ↓
> Current
> ↓
> Reviewed / Revalidated
> ↓
> Superseded / Deprecated
> ↓
> Historical / Archived

但這不是所有知識都必須完整走過。

例如：

### 外部事實

Research → Evidence → Knowledge

### 系統規則

Proposal → Decision → Current

### 暫時推論

Observation → Hypothesis → Pending

### 已失效知識

Current → Deprecated → Historical

## 七、重要修正：不要用單一 Status 解決所有生命週期

本輪與上一輪結果一致：

**不要建立一個巨大 Status Enum。**

建議拆成正交維度。

### Knowledge Type

- Fact
- Inference
- Decision
- Rule
- Procedure
- Observation
- Hypothesis

### Lifecycle Stage

- Discovered
- Recorded
- Validated
- Active
- Superseded
- Deprecated
- Historical

### Validity

- Confirmed
- Partially Confirmed
- Pending
- Rejected
- Unknown

### Source

- External
- Internal
- Derived
- User Decision
- Experiment

這比：

> ACTIVE_RESEARCH_VALIDATED_EXTERNAL_CURRENT

之類的巨大狀態字串更容易維護。

## 八、不要追求「所有知識定期重驗」

這是一個重要的工程取捨。

如果要求 GPT 定期重新驗證整個知識庫：

> Knowledge 數量 × 驗證成本

會持續增加。

最終系統自己就會變成負擔。

因此應採：

**Risk-driven Revalidation（風險驅動重新驗證）。**

高風險：

- 核心架構
- Current Rules
- 決策
- Context Loading Rules
- Library Routing Rules
- 外部快速變動的事實

→ 高頻或事件觸發驗證。

低風險：

- 穩定歷史
- 已封存資料
- 不影響目前行為的背景知識

→ 不主動重新驗證。

---

## 九、不要用「最後修改時間」判斷知識是否有效

這一點與第 13 項 Current / History 研究完全一致。

GitHub 的修改時間只能表示：

> 文件被修改過。

不能表示：

> 這個資訊現在仍然正確。

因此：

Current 應由：

- 正式決策
- 適用範圍
- 驗證狀態
- 是否被取代

共同決定。

而不是：

> modified_at 最大 = current。

## 十、系統熵控制：真正需要建立的機制

本研究不建議建立「Entropy Database」。

更合理的是建立一組可觀察指標。

### A. 重複率

同一概念有多少份權威性內容？

### B. 衝突率

多少文件對同一規則產生互相衝突的描述？

### C. 過時率

多少 Active 知識已經超過其合理有效期限或被外部事實改變？

### D. 找不到率

GPT 是否無法找到應該存在的資料？

### E. 誤載入率

GPT 是否經常讀入與任務無關的資料？

### F. 決策重複率

是否反覆重新討論已經正式決定的問題？

### G. Handoff 恢復失敗率

新 GPT 是否能從 Recovery Entry 恢復目前工作？

### H. Orphan Artifact

是否存在：

- 沒有索引
- 沒有引用
- 沒有用途
- 沒有 Current / History 關係

的孤立 Artifact？

這些才是「系統熵」的實際觀測對象。

## 十一、GitHub 對長期演化的啟示

GitHub 的 repository archive 是一個極端的生命週期狀態：

> Active Repository → Archived / Read-only

它不是刪除，而是明確表示「不再主動維護」。citeturn0search1

這與本系統的：

> Active → Historical / Archived

概念一致。

但本系統不能直接照搬 Repository Archive。

原因是：

- 一個知識文件可能失效
- 其他文件仍然有效
- 同一決策可能被新決策取代
- 整個 Repository 不一定需要停止維護

因此：

**生命週期應以 Artifact / Knowledge Unit 為粒度，而不是只以整個 Repository 為粒度。**

---

## 十二、外部依賴的長期維護

GitHub Dependabot 的模式值得借鑑：

它不是要求人每天重新檢查所有依賴，而是：

> Monitoring → Detect Change → Generate Update → Review → Merge

並可設定更新頻率與範圍。citeturn1search0turn1search2

本系統可抽象成：

> Observe → Detect Knowledge Risk → Create Maintenance Task → Review → Update → Verify

這仍然不代表現在要建立自動 Worker。

在 No-API 條件下，可以先人工／GPT 驅動：

> 使用時發現問題 → 記錄 → 累積 → 定期維護。

等重複性真的出現，再自動化。

## 十三、最終系統模型

                    │    現行系統      │

                    ┌─────────────────┐
                    │     Research    │
                    │      研究        │
                    └────────┬────────┘
                             ↓
                    ┌─────────────────┐
                    │     Proposal    │
                    │      提案        │
                    └────────┬────────┘

                    │     Adoption    │

## 十四、對目前架構的最終判定

### 已證明合理

1. GitHub 作為長期記憶與版本歷史。
2. Current / History 分離。
3. Evidence / Decision / Artifact 分離。
4. Verification 作為生命週期的重要節點。
5. Handoff 作為 Recovery Entry。
6. Research → Proposal → Adoption → Implementation → Verification 的治理鏈。
7. 需求驅動而非預先建立大量自動化。

### 必須補強

1. 建立知識／Artifact 的生命週期概念。
2. 建立 Deprecated / Superseded / Historical 的語義。
3. 建立風險驅動 Revalidation。
4. 建立系統熵的觀測指標。
5. 建立維護問題的累積與處理機制。
6. 明確區分「文件修改」與「知識有效性」。

### 不建議加入

1. 不建立獨立 Entropy Database。
2. 不建立全知識庫定期重驗機制。
3. 不建立大型 Knowledge Garbage Collector。
4. 不因為存在歷史資料就定期大量刪除。
5. 不建立自動 Agent / Worker 直到實際瓶頸證明需要。
6. 不用檔案數量作為系統健康度的主要指標。

## 十六、最終架構觀

21 項研究最終沒有形成 21 個獨立模組。

真正形成的是六個互相連接的能力層：

> Library
> ↓
> Control
> ↓
> Context
> ↓
> Execution
> ↓
> Verification / Evidence / Artifact
> ↓
> Governance
> ↓
> Evolution
> ↓
> 回到 Current

因此，本系統真正的核心不是「資料庫」。

而是：

> **一個可以保存知識、理解目前狀態、控制上下文、進行決策、驗證結果、保留證據，並在長期使用中自行暴露維護問題的外部記憶與工程治理系統。**

這也是「大型架構、小 Runtime」在長期尺度上的真正含義：

**把複雜度放在可閱讀、可驗證、可版本控制的外部結構中，而不是放進一個難以控制的常駐 Runtime。**
