# 研究會議記錄 004：時間與上下文層初步研究

日期：2026-09-18
狀態：研究中
性質：討論／研究記錄，不代表正式採用

## 一、研究範圍

本輪研究項目：

13. 目前狀態／歷史分離 Current vs History
14. 交接能力 Handoff
15. 上下文控制 Context Control
16. 無 API 檢索 No-API Retrieval

本輪核心問題不是「怎麼把更多資料塞給 GPT」，而是：

「當 Repository 持續成長、GPT 每次只看到有限上下文，而且可能由另一個新的 GPT 接手時，系統如何仍然知道什麼是現在、什麼是歷史、下一步要做什麼，以及哪些資料值得載入？」

外部研究對這個問題的方向相當一致：Context 是有限資源；長期 Agent 需要持久化記憶、壓縮、即時檢索與結構化筆記，而不是把所有歷史永遠放進上下文。Anthropic 將此稱為 context engineering，並明確指出 context 應被視為有限且會產生 diminishing returns 的資源。citeturn1search1

## 二、13. 目前狀態／歷史分離 Current vs History

### 1. 外部系統已經存在相似做法

GitHub Copilot 的 repository-level memory 是一個很有價值的比較案例。

目前 GitHub Copilot Memory 會保存 repository-level facts，而且每個 fact 帶有引用來源；Agent 使用前會重新檢查 citation 是否仍由 current branch 支持，只有通過驗證的 facts 才會被使用。未使用的 fact / preference 也會因 retention 機制被移除。citeturn1search9

這其實證明了一個非常重要的原則：

「長期記憶不能只保存；還必須有 validity / freshness 機制。」

### 2. 本系統應明確區分四種狀態

目前建議：

CURRENT
：現在正式有效的內容。

HISTORY
：曾經有效，但目前不是工作依據。

PENDING
：正在研究／討論，尚未正式採用。

DEPRECATED
：明確不再使用，但保留原因與歷史。

這四種狀態不能只靠檔名猜測，最好在重要 Artifact 中具有明確 status metadata。

### 3. Current 不是「最新修改時間」

這是本輪非常重要的修正。

Git commit 最新，不代表內容就是 Current。

例如：
- 新研究文件可能比正式架構文件更新，但仍是 PENDING。
- 舊正式決策可能仍然有效。
- 新文件可能只是實驗方案。
- 修改日期可能因格式調整而更新，但語義沒有變成 current。

因此：

Current = 正式狀態 + 適用範圍 + 未被取代

而不是：

Current = 最新檔案。

### 初步結論

「目前狀態／歷史分離」應保留為正式架構能力。

並且狀態應優先由語義／治理決定，而不是由時間戳決定。

目前狀態：強支持。

## 三、14. 交接能力 Handoff

### 1. Handoff 不只是「摘要上一輪對話」

OpenAI 的 Agent 架構將 handoff 視為控制權轉移，而且轉移時需要傳遞最新 conversation state。citeturn1search4turn1search43

在較新的 Agents SDK 架構中，系統進一步將 memory、compaction、filesystem、skills 與 sandbox 等視為長期 Agent 所需要的基礎能力。citeturn1search8

這支持本系統把 Handoff 視為一種「狀態恢復機制」，而不是普通摘要。

### 2. 本系統的 Handoff 應回答七個問題

新 GPT 不應需要重新猜測：

1. 這個系統是什麼？
2. 現在正式架構是什麼？
3. 哪些規則不可違反？
4. 哪些決策已經正式確立？
5. 現在正在進行什麼？
6. 哪些事情尚未完成？
7. 下一步具體要做什麼？

因此 Handoff Artifact 最少需要：

- Purpose
- Current Architecture
- Current Rules
- Confirmed Decisions
- Active Work
- Pending Items
- Known Risks
- Next Action
- Relevant Entry Points

### 3. Handoff 應該是 Current State 的「索引」

這是比單純「交接摘要」更重要的結論。

Handoff 不應複製整個知識庫。

它應該告訴新 GPT：

「先讀哪些東西。」

因此：

Handoff
→ Current State
→ Architecture / Rules
→ Active Plans
→ Relevant Knowledge
→ History only when needed

這與 Anthropic 的 just-in-time retrieval / progressive disclosure 模式高度一致：先保留輕量 reference，再依任務需要載入實際內容。citeturn1search1

### 初步結論

Handoff 應保留，而且應從「交接文件」提升為：

「新 AI 的恢復入口（Recovery Entry Point）」。

目前狀態：強支持。

## 四、15. 上下文控制 Context Control

### 1. 外部研究高度支持「不要全部載入」

Anthropic 的 context engineering 研究明確指出，模型 context 雖然越來越大，但資訊量增加仍可能造成 context pollution / context rot，因此有效 Agent 的核心不是最大化載入，而是最大化高訊號資訊密度。citeturn1search1

GitHub 也明確建議保持 context lean，並指出：
- 長對話會持續消耗 context
- 開啟的檔案與附加資料也會累積
- 可以用 compact 壓縮長 session
- 應提供 repository map，避免 Agent 每次重新探索整個 repository
- 工具集合過大也會增加 context 成本。citeturn0search6turn0search7

這與本系統原本的「Minimum Sufficient Context」原則高度一致。

### 2. Progressive Disclosure 得到進一步支持

GitHub 現在把 repository-wide instructions、path-specific instructions、AGENTS.md、skills 等分成不同作用範圍；也就是說，並不是所有規則與知識都應該永遠同時載入。citeturn0search0turn0search5

近期 2026 年的 progressive disclosure 實驗也指出，在大型 corpus 中，透過逐層暴露內容可以降低不必要的 context 使用；但更深層的多級 routing 並不一定帶來收益，甚至可能傷害準確度。citeturn0academia36

因此本系統應避免「為了管理 Context 而建立十幾層索引」。

### 3. 本系統目前較合理的 Context Loading 層級

建議維持：

Level 0：Recovery / Current Entry
→ 確認系統現在在哪裡。

Level 1：System Rules / Architecture
→ 知道怎麼工作。

Level 2：Active Plan / Task Contract
→ 知道現在要完成什麼。

Level 3：Relevant Knowledge / Capability
→ 載入完成任務所需要的知識與能力。

Level 4：Evidence / History
→ 只有需要追溯、驗證或理解決策原因時才載入。

這與「最小充分上下文」比單純「少載資料」更精確。

### 初步結論

Context Control 應保留為獨立能力。

但它不應成為一套非常複雜的中央資料庫。

第一階段以：

「入口 → 索引 → 按需載入」

為核心。

## 五、16. 無 API 檢索 No-API Retrieval

### 1. 外部 Agent 已經證明不一定需要先建立 Vector DB

Anthropic 的 context engineering 實務明確描述了一種 just-in-time context 模式：保存輕量 identifier，例如 file path、stored query、web link，再由 Agent 在需要時使用工具讀取實際內容。這與傳統「先把所有資料 embedding，再由 retrieval service 找出內容」不同。citeturn1search1

這直接支持本系統目前的無 API 方向。

### 2. Repository 本身可以成為 Retrieval Interface

GitHub repository 已經具備：

- 目錄結構
- 檔名
- 路徑
- Markdown heading
- Commit history
- Diff
- 搜尋
- 版本
- 狀態標記
- 文件間引用

這些 metadata 本身就是 retrieval signal。

Anthropic 特別指出，檔案路徑、資料夾、命名、時間戳等 metadata 都可以幫助 Agent 判斷資料用途與相關性。citeturn1search1

### 3. 不能把「無 Vector DB」誤解成「不用索引」

這是本輪的重要修正。

無 API Retrieval 不是：

「GPT 自己亂翻 GitHub。」

而應該是：

Repository
→ Discovery Index
→ Candidate Files
→ Targeted Read
→ Evidence / Context
→ Answer / Action

也就是把「檢索」拆成：

Discovery
+
Selection
+
Loading

而不是一定要：

Embedding
+
Vector Search
+
RAG Service

### 4. Progressive Disclosure 與目前圖書館系統的關係

這與第一階段研究得到的 Library System 結論直接接合。

Library 的作用不是保存所有內容。

Library 的作用是：

「告訴 GPT 哪裡可能有答案，以及下一步應該讀什麼。」

因此 Library + Context Control + No-API Retrieval 實際上是一條連續鏈：

Library
→ Discovery
→ Context Selection
→ Targeted Retrieval
→ Working Context

不是三套互相競爭的系統。

### 初步結論

No-API Retrieval 可以成立。

但必須建立最基本的 discovery/index 機制。

目前不需要因為 Repository 變大就立即導入 Vector DB。

只有當：
- repository 規模
- 搜尋時間
- 找不到率
- 誤載入率
- GPT 手動搜尋成本

持續超過人工／GPT 導航可接受門檻時，才應研究 embedding／RAG／外部 retrieval service。

## 六、本輪最重要的架構發現

### 發現 1：Current 不是最新，而是「目前有效」

這會成為未來 Knowledge Lifecycle 的核心。

### 發現 2：Handoff 應該是 Recovery Entry，而不是聊天摘要

真正目的不是保存上一輪對話，而是讓新的 GPT 能快速恢復：

Purpose
→ Current
→ Rules
→ Decisions
→ Active Work
→ Next Action

### 發現 3：Context Control 與 Library 是連續鏈

Library 解決：

「去哪裡找？」

Context Control 解決：

「這次應該載入多少？」

Retrieval 解決：

「實際把哪個內容拿進來？」

### 發現 4：無 API 不等於無 Retrieval

目前可以使用：

Repository structure
+
Index
+
Path
+
Search
+
Progressive Disclosure
+
Targeted Read

形成低基礎設施成本的 retrieval system。

### 發現 5：不要為了避免 Context 爆炸而建立過度複雜的索引層

2026 年 progressive disclosure 實驗對多級 routing 的結果並不支持「層級越多越好」。因此 Context 架構應保持少層、清晰、可人工理解。citeturn0academia36

## 七、目前形成的 Context Architecture

可暫定為：

New GPT
↓
Recovery Entry
↓
Current State
↓
System Rules / Architecture
↓
Active Task / Plan
↓
Library Discovery
↓
Relevant Knowledge / Capability
↓
Targeted Read
↓
Working Context
↓
Execution
↓
Evidence / Artifact
↓
Update Current State
↓
Next Handoff

這是一個閉環。

其中 History 不在主路徑，而是按需進入。

## 八、目前建議的狀態模型

先不建立資料庫。

重要 Artifact 可逐步具備：

status:
- CURRENT
- PENDING
- DEPRECATED
- HISTORY

以及：

effective_from
supersedes
superseded_by
related_decision
related_evidence

但這些欄位目前仍屬研究模型。

## 九、目前仍未解決的問題

1. Recovery Entry 應是一個文件，還是一組固定入口文件？
2. Current State 是否應與 Handoff 分開？
3. Library Index 應人工維護、GPT 維護，還是混合？
4. Repository 多大時，純 path/search retrieval 開始失效？
5. 如何測量 retrieval 的「找不到率」與「誤載入率」？
6. History 的自動淘汰／壓縮門檻應如何定義？
7. Context Level 是否真的需要四／五層，還是可以再簡化？
8. 未來導入 API 後，Vector/RAG 應該接在 Library 前面、後面，還是成為另一種 retrieval backend？

這些問題進入後續壓力測試與正式化，不在本輪直接定案。

## 十、對 v0.1 的影響

本輪沒有推翻原本的：

「GitHub = 長期外部記憶」

反而將其精確化為：

「GitHub = 持久記憶 + Repository Knowledge Base + Artifact Store + Version History」

而 AI 本身的 context：

「GPT Working Context = 暫時工作記憶」

兩者之間由：

Recovery / Current State
+
Library
+
Context Control
+
Targeted Retrieval

連接。

因此目前架構已經形成一個清楚的「外部記憶 → 工作上下文」轉換層。
