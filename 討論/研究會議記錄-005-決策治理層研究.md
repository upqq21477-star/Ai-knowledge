# 研究會議記錄-005-決策治理層研究

## 研究範圍

本輪研究第 17、18 項：

- 17. 研究 → 採用（Research → Adoption）
- 18. 提案 → 正式化（Proposal → Formalization）

本輪目的不是建立更多文件，而是確認「外部研究結果如何安全地進入正式系統」，以及「候選方案何時、由誰、以什麼證據成為現行規則」。

## 一、外部工程實務

### 1. AWS Architectural Decision Records（ADR）

AWS 的 ADR 流程把重大架構選擇記錄成具有生命週期的決策文件。

其流程明確區分：

1. Proposed：提出並準備審查
2. Review：檢查、討論、要求修改或拒絕
3. Accepted：正式接受
4. Rejected：正式拒絕
5. Superseded：後續新決策取代舊決策

AWS 特別強調：接受或拒絕後，原 ADR 應視為不可變；如果未來需要改變決策，應建立新的 ADR，新的 ADR 接受後再標記舊 ADR 為 Superseded。

這個設計直接支持本系統的「研究與正式決策分離」。

來源：
AWS Prescriptive Guidance — Architectural Decision Record Process
https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html

### 2. GitHub Pull Request / Branch Protection

GitHub 的工程治理不是「作者寫完就算正式」，而是可以把：

- Pull Request
- Review
- Required approvals
- Status checks
- Code Owners
- Merge

串成正式進入受保護分支的門檻。

特別重要的是 GitHub 支援「最近一次修改後重新審查」，避免舊審查被新提交的內容悄悄繞過。

對本系統而言，這代表「研究完成」與「正式寫入 Current / Architecture」之間應存在一個明確的採用門檻。

來源：
GitHub Docs — About protected branches
https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches

GitHub Docs — About code owners
https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners

### 3. Kubernetes KEP

Kubernetes Enhancement Proposal（KEP）把重大功能的設計、動機、替代方案、風險與測試寫入結構化提案，再透過 Pull Request 與社群審查形成共識。

Kubernetes 也把「設計完成」與「實際成熟」分開：功能可以經歷 Alpha → Beta → Stable 等階段，而不是一旦提案被接受就等於已證明成熟。

這對本系統有一個重要啟示：

「採用」與「實作完成」不是同一件事；
「實作完成」與「驗證成熟」也不是同一件事。

來源：
Kubernetes Blog — Enhancing Kubernetes one KEP at a Time
https://kubernetes.io/blog/2022/08/11/enhancing-kubernetes-one-kep-at-a-time/

Kubernetes Release Cycle
https://kubernetes.io/releases/release/

## 二、研究 → 採用的結論

目前系統採用的流程：

> 外部研究
> → 比對現有架構
> → 找出差異
> → 討論
> → 壓力測試／驗證
> → 得出候選方案
> → 正式採用

整體方向正確，但研究後仍缺少一個明確的「採用閘門」。

建議正式定義：

> Research → Candidate → Review/Stress Test → Adoption Decision → Formalization → Implementation → Verification → Current

其中：

### Research

回答：

- 外界怎麼做？
- 有哪些實際案例？
- 有哪些證據？
- 哪些做法成功？
- 哪些做法失敗？
- 與本系統需求有什麼差異？

研究結果本身不改變正式架構。

### Candidate

將研究結果轉成「本系統可能採用的方案」。

此時可以提出：

- 保留
- 修改
- 部分採用
- 不採用
- 暫緩

但仍不是正式規則。

### Review / Stress Test

檢查候選方案：

- 是否與現有架構衝突？
- 是否增加不必要複雜度？
- 是否解決實際問題？
- 是否只是因為外部工具流行而引入？
- 是否符合 No-API 約束？
- 是否能在手機 + GPT + GitHub 條件下運作？
- 是否有反例？
- 是否存在更簡單方案？

這一階段是目前「研究 → 採用」流程最重要的品質閘門。

### Adoption Decision

明確回答：

> 「我們是否決定把這個候選方案作為本系統正式設計？」

此時才產生正式決策。

重要規則：

**研究證據不能自動轉化為正式架構。**

GPT 可以研究、比較、提出候選方案、指出風險，也可以進行驗證；但重大架構變更的「正式採用」仍應由使用者明確確認。

這可以防止 AI 因為一次研究結果或一次對話，就自行改變整個知識庫的規則。

## 三、提案 → 正式化

本輪確認「Proposal」與「Formalization」必須分開。

### Proposal（提案）

提案回答：

> 「我們可以怎麼改？」

可以包含：

- 問題
- 背景
- 現況
- 研究證據
- 候選方案
- 替代方案
- 優缺點
- 風險
- 預期影響
- 實作方式
- 驗證方式

提案可以被：

- 修改
- 暫緩
- 拒絕
- 拆分
- 合併
- 繼續研究

因此提案不是權威來源。

### Formalization（正式化）

正式化回答：

> 「從現在開始，系統正式採用什麼？」

正式化後必須產生或更新「權威性 Artifact」。

至少要能回答：

- 正式決策是什麼？
- 為什麼這樣決定？
- 適用範圍是什麼？
- 有哪些限制？
- 哪些舊決策被取代？
- 實作狀態如何？
- 驗證狀態如何？
- 相關研究與證據在哪裡？

## 四、最重要的結構：決策與實作分離

本輪研究後，建議正式採用以下五層：

> Evidence
> ↓
> Proposal
> ↓
> Decision
> ↓
> Implementation
> ↓
> Verification

再由：

> Verification + Decision

共同決定：

> Current State

這比「研究完直接修改 Current」安全得多。

例如：

研究發現「Library 應該具有 Discovery Index」。

不能直接把「知識/管理/圖書館系統.md」改成正式規則。

應該經過：

1. Research：研究外部 Library / Progressive Disclosure
2. Candidate：提出 Discovery Index 方案
3. Stress Test：測試 No-API 條件、GPT 導航成本、維護成本
4. Adoption：確認採用
5. Formalization：建立正式決策 Artifact
6. Implementation：建立或修改 Library 文件
7. Verification：確認實作符合決策
8. Current State：更新目前有效架構

## 五、為什麼不能只靠「Proposal → Accepted」

如果只有：

> Proposed → Accepted

會產生一個嚴重問題：

「接受」究竟代表：

- 接受這個想法？
- 接受設計？
- 已經實作？
- 已經驗證？
- 已經成為 Current？

這些其實是五個不同問題。

因此不應把所有狀態塞進單一 status。

建議採用「階段 + 狀態」分離：

### Stage

- Research
- Proposal
- Decision
- Implementation
- Verification

### Status

- Draft
- Active
- Rejected
- Superseded
- Deprecated
- Blocked

### Implementation State

- Not Started
- In Progress
- Complete

### Verification State

- Not Verified
- Partially Verified
- Verified
- Failed

這樣可以避免狀態爆炸。

例如：

> Decision / Active
> Implementation / In Progress
> Verification / Not Verified

意思非常清楚：

「決策已正式採用，但實作尚未完成，也尚未驗證。」

## 六、單人 AI 系統的特殊問題

一般公司可以依靠：

> 作者 → Reviewer → Approver → Merge

形成權限隔離。

本系統只有：

> User + GPT

因此不能假裝存在真正的第二個獨立審查者。

GPT 可以扮演：

- Researcher
- Designer
- Critic
- Verifier
- Implementer

但這些都是同一個 AI 系統中的不同工作模式。

因此：

**GPT 的自我審查不是權限隔離。**

它可以提高品質，但不能等價於第二個獨立決策者。

所以本系統應採：

> GPT 提案
> → GPT 反向審查
> → GPT 驗證
> → 使用者確認正式採用
> → GPT 正式化
> → GPT 實作
> → GPT 驗證
> → GitHub 留存歷史

這比單純讓 GPT「自己決定並修改正式架構」可靠。

## 七、正式採用閘門

建議正式加入一個最小 Adoption Gate：

### A. 問題確認

是否存在需要解決的實際問題？

### B. 證據充分

是否有：

- 外部資料
- 工程案例
- 實際測試
- 現有系統觀察

至少一項以上可驗證依據？

重大架構變更應要求更高證據強度。

### C. 替代方案比較

是否確認不是單純因為「別人這樣做」就採用？

至少要有：

- 現行方案
- 候選方案
- 不採用／簡化方案

### D. 架構相容性

是否符合：

- No-API
- GPT 為主要推理核心
- GitHub 為長期記憶
- 大架構、小 Runtime
- 最小充分上下文
- 需求驅動自動化

### E. 風險

是否知道：

- 複雜度增加
- 維護成本
- 上下文成本
- 錯誤傳播
- 未來遷移成本

### F. 驗證方式

採用後如何知道它真的有效？

如果無法描述驗證方式，重大架構方案不應直接正式化。

### G. 正式採用

最後才進入：

> Accepted / Active Decision

## 八、研究 → 採用與提案 → 正式化的正式模型

~~~text
                    ┌──────────────┐
                    │   Research   │
                    │    研究      │
                    └──────┬───────┘
                           ↓
                    ┌──────────────┐
                    │  Candidate   │
                    │   候選方案    │
                    └──────┬───────┘
                           ↓
                ┌─────────────────────┐
                │ Review / Stress Test│
                │ 審查 / 壓力測試       │
                └──────────┬──────────┘
                           ↓
                    ┌──────────────┐
                    │   Adoption   │
                    │   採用決策     │
                    └──────┬───────┘
                           ↓
                    ┌──────────────┐
                    │ Formalization│
                    │   正式化      │
                    └──────┬───────┘
                           ↓
                    ┌──────────────┐
                    │Implementation│
                    │    實作       │
                    └──────┬───────┘
                           ↓
                    ┌──────────────┐
                    │ Verification │
                    │    驗證       │
                    └──────┬───────┘
                           ↓
                    ┌──────────────┐
                    │ Current State│
                    │   現行狀態    │
                    └──────────────┘
~~~

歷史與新決策則透過：

> Superseded / Deprecated / Historical

保留，而不是直接覆寫。

## 九、與目前四方案的關係

本輪不新增「第五方案」。

研究 → 採用、提案 → 正式化屬於：

> 系統治理規則（Governance Rules）

不是另一套工程方案。

目前四方案仍然是工程治理與執行方法。

這兩個流程負責的是：

> 「什麼東西可以成為正式系統規則？」

而四方案負責：

> 「正式系統如何被設計、建立、驗證、維護？」

兩者層級不同。

## 十、對現有架構的修正

### 已確認保留

1. Research 與正式 Knowledge 分離
2. Proposal 與正式 Decision 分離
3. Verification 與 Evidence 分離
4. Artifact 作為持久化成果
5. Current 與 History 分離
6. GitHub 作為正式 Artifact / Version History
7. GPT 可以執行多種角色，但角色不是權限隔離
8. 重大架構變更需要明確採用閘門

### 建議新增

1. Adoption Gate
2. Formal Decision Artifact
3. Decision → Implementation → Verification 的明確關係
4. Stage / Status / Implementation State / Verification State 分離
5. 明確記錄「誰／什麼機制」批准正式決策

### 建議避免

1. 不建立龐大的企業級審批系統
2. 不因為 GitHub 有 PR 就強制所有小修改都走 PR
3. 不把所有知識都變成 ADR
4. 不讓 Proposal 直接成為 Current
5. 不讓 GPT 的自我審查被視為真正獨立批准
6. 不增加過多狀態名稱造成狀態機本身成為負擔

## 十一、最終判定

本輪研究支持目前架構的大方向，而且發現一個值得正式補上的治理缺口：

> **研究與採用之間需要明確的 Adoption Gate。**

同時：

> **提案與正式化必須保持分離。**

最終形成：

> Evidence 是「為什麼相信」
>
> Research 是「外面怎麼做」
>
> Proposal 是「我們可以怎麼做」
>
> Adoption 是「是否決定採用」
>
> Decision 是「正式決定了什麼」
>
> Implementation 是「實際做了什麼」
>
> Verification 是「是否符合決定且有效」
>
> Current 是「現在正式有效的是什麼」
>
> History 是「過去曾經有效／曾經採用過什麼」

這使整個知識庫從「文件集合」進一步成為具有決策治理能力的工程系統。
