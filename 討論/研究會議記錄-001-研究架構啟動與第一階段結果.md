## 三、第一階段研究：知識與資料基礎層

### 1. 圖書館系統

外部研究顯示，現代 AI 知識架構已不再把「知識庫」單純理解為文件儲存。

Microsoft 的 Agent Skills 架構採用「Discovery → Instructions → Fetch」的漸進式揭露（Progressive Disclosure）：先讀取 skill 的名稱與描述判斷相關性，再載入完整指令，需要時才取得最新內容。

此結構與本系統的「圖書館」概念高度相關：索引本身不等於知識內容，而是負責告訴 AI「什麼存在、何時可能需要、去哪裡取得」。

Microsoft 也明確將 Agent、Skill、Tool 分開：Agent 負責協調與決策，Skill 是按需載入的能力／工作流程，Tool 是具有明確介面的具體功能。

初步結論：
- 圖書館不應只是資料夾。
- 應至少包含「發現／索引 → 判斷相關性 → 載入 → 使用」的概念。
- 「只載入必要內容」有現代實務支持。
- 未來可將圖書館與上下文控制、系統庫、觸發管理連接，但目前不應因此提前建立複雜 Vector DB。

來源：
- Microsoft Learn：Azure Agent Skills
- Microsoft Learn：Search and tool use architectures
- GitHub Docs：Copilot custom instructions / skills

### 2. 系統庫

GitHub Copilot 現行架構提供多個不同層級的 AI 能力描述：
- Repository-wide custom instructions
- Path-specific instructions
- Agent instructions
- Prompt files
- Custom agents
- Subagents
- Agent skills
- Hooks
- MCP servers

GitHub 官方將 Agent Skills 定義為可按相關性載入的「instructions, scripts, resources」能力模組；Skills 與 Custom Instructions 的職責不同：前者適合詳細且只在相關任務時載入的能力，後者適合幾乎所有任務都需要的通用規則。

這直接支持本系統「系統庫」的核心思想：系統庫不是保存知識，而是保存「可以使用的能力，以及何時使用」。

初步結論：
- 系統庫概念有直接外部對應。
- 能力應具有觸發／適用範圍與載入條件。
- 「能力」與「知識」分離是合理的。
- 未來可進一步研究 Capability Registry、Skill Registry、Tool Registry 三者是否應統一索引，或保持不同層級。

來源：
- GitHub Docs：Copilot customization cheat sheet
- GitHub Docs：Adding agent skills
- Microsoft Learn：Azure Agent Skills

### 3. 方案庫

目前研究結果支持「能力」與「解題流程」分離。

Microsoft 的 Agent 架構明確將 Skill 描述為可按需載入的 workflow/capability；這表示「我能做什麼」與「針對某類問題應如何完成」可以是不同層級。

因此本系統的「方案庫」不應被簡化成另一個系統庫，而應保存較高階的：
- 問題類型
- 解題流程
- 使用哪些能力
- 執行順序
- 決策條件
- 驗證方法
- 例外處理

初步結論：
- 系統庫 = 能力資源。
- 方案庫 = 能力組合成的解題方法。
- 兩者分離具有架構合理性。
- 仍需後續研究 Workflow / Playbook / Runbook / Planning Library，以確定方案庫的最佳資料模型。

## 四、目前發現的跨項目結論

### 結論 A：三庫不是重複建設

目前外部架構可以形成：

知識 Library
→ 提供「知道什麼」

系統／Skill Library
→ 提供「能做什麼」

方案／Workflow Library
→ 提供「怎麼完成一類問題」

這與 v0.1 的三庫思想一致。

### 結論 B：Discovery 與內容本體應分離

Microsoft Agent Skills 的 Progressive Disclosure 是目前非常直接的外部驗證案例。

因此圖書館的核心價值不是把所有資料塞進 GPT，而是降低「找到正確資料所需的上下文成本」。

### 結論 C：不應因為外部系統使用 RAG 就直接採用 RAG

目前找到的 Microsoft Agentic RAG 架構是成熟的 API／服務型架構，讓 Agent 動態決定何時搜尋、搜尋什麼、是否繼續搜尋。

這可以作為未來方向，但不能直接證明目前無 API 版本需要 Vector DB。

本系統仍應先研究：
- Repository 結構
- Markdown 索引
- 關鍵字搜尋
- GitHub Search
- 分層索引
- 語義判斷

是否已足夠支撐目前規模。
