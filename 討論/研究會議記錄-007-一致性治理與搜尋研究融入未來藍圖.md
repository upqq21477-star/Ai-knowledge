# 研究會議記錄-007-一致性治理與搜尋研究融入未來藍圖

## 研究範圍

本輪討論針對兩個目標進行拆解與藍圖對照：

1. 研究 `check-consistency.yml`／Consistency Validator 類機制的功能與可移植價值。
2. 研究「搜尋研究方案」如何與未來藍圖的 Verification、Observation、Research、Evolution 閉環融合。

本紀錄屬於 RESEARCH / CANDIDATE INPUT。

**本紀錄不代表正式新增系統、能力或方案；正式導入仍須經 Proposal → Adoption → Implementation → Verification。**

---

## 一、已確認的外部／既有材料

目前已確認：

`參考資料/check-consistency.yml`

其設計包含：

- GitHub `push` Trigger。
- 執行 `scripts/check_consistency.py`。
- 產生／更新 `現況-自動產生.md`。
- 即使檢查失敗，也先保存自動產生的索引。
- 最後再讓 Workflow 以失敗狀態暴露一致性問題。
- 透過 GitHub Actions 將檢查結果轉成可觀察事件。

目前尚未在 Repository 中確認 `scripts/check_consistency.py` 的實體，因此只能確認 Workflow 設計，不能宣稱完整 Validator 已實際存在或已驗證。

---

## 二、第一個目標：Consistency Validator 應如何定位

不建議把 `check-consistency` 直接升格成一個獨立大型系統。

較合理的抽象是：

> **Validator / Verification Capability 的一個具體實作。**

其功能可拆成：

1. Trigger
2. Automated Check
3. Index / Result Generation
4. Result Persistence
5. Failure Signal
6. Observation Trigger

未來可納入：

- State Validator
- Version Validator
- Reference Validator
- Path Validator
- Namespace Validator
- Mapping Validator
- Canonical Source Validator
- Consistency Validator

因此：

> `check-consistency` 是 Verification Layer 的候選能力，而不是新的最高層架構。

---

## 三、第二個目標：搜尋研究方案的定位

搜尋研究不應只被理解為：

> 「人要求 GPT 搜尋資料。」

融入未來藍圖後，應成為 Evolution Loop 中的正式 Research 能力。

建議抽象流程：

> Problem / Change Signal
> ↓
> Failure Classification
> ↓
> Research Trigger
> ↓
> Research Intent
> ↓
> External Research
> ↓
> Evidence Assessment
> ↓
> Applicability
> ↓
> Candidate Solution
> ↓
> Validation
> ↓
> Proposal / Decision
> ↓
> Implementation
> ↓
> Verification

因此搜尋研究的角色是：

> **外部方法、工具、案例與證據的輸入層。**

外部研究結果不應直接成為 Current Knowledge 或正式 System。

## 五、與未來藍圖的對照

### 目標一：自動一致性檢查

最適合放置於：

> **Verification / Validator**

並向前連接：

> Trigger

向後連接：

> Result Persistence → Observation → Change Signal

它不應直接負責：

- Research
- Decision
- Adoption
- System Evolution

因為這些屬於更高層治理責任。

---

### 目標二：搜尋研究

最適合放置於：

> **Research / External Evidence**

並由：

> Observation / Change Signal / Confirmed Problem

觸發。

向後連接：

> Evidence → Applicability → Candidate → Proposal → Adoption

因此它不是 Validator 的子功能，而是 Validator 暴露問題後可以進入的下一階段。

## 八、與 Document Graph 的關係

本輪結果也支持先前對 Graph 思路的判斷。

Validator 若只看單一文件，只能回答：

> 「這份文件是否有問題？」

若增加文件／能力關係：

- References
- Depends On
- Supersedes
- Implements
- Derived From
- Uses
- Affects

則可以進一步：

> Git Change → Changed Node → Related Nodes → Affected Scope → Validation

因此 Graph 的第一個實際價值不是建立一個大型 Graph Engine。

而是：

> **支援 Change Impact Analysis 與精準 Verification。**

但目前仍不應因此立即建立完整 Graph Engine。

---

## 九、工程化邊界

本輪不建議立即：

1. 建立完整 Registry。
2. 建立完整 Graph Engine。
3. 建立常駐 Agent。
4. 建立自動 Research Worker。
5. 建立大型 Orchestrator。
6. 將所有研究自動轉成 Knowledge。
7. 將所有 Validation 全自動化。

原因：

> 未來藍圖目前需要的是「能力位置與閉環關係被證明」，不是提前實體化所有 Runtime。

應採：

> 實際需求 → 觀察 → 重複瓶頸 → 結構問題確認 → 研究 → 最小實作 → 驗證 → 再決定是否系統化。

---

## 十、本輪兩個目標的最終定位

| 目標 | 藍圖位置 | 主要責任 | 不負責 |
|---|---|---|---|
| Consistency Validator | Verification / Validator | 檢查、產生結果、暴露異常 | Research、Decision、Adoption |
| 搜尋研究方案 | Research / External Evidence | 尋找外部方法、工具、案例、證據 | 直接決定採用 |
| Observation | Evolution / Governance | 接收驗證結果、形成 Change Signal | 自己解決問題 |
| Document Graph | 未來支援層 | 關係、影響範圍、Recall | 取代治理流程 |

## 十一、與現有藍圖的關係判定

本輪沒有發現需要新增第五方案，也沒有發現需要改變 A/B/C/D 四方案。

目前較合理的判定是：

> **這兩個目標是未來藍圖既有節點之間的「連接能力」研究，而不是新的頂層模組。**

尤其重要的是：

### Consistency Validator

位於：

> Trigger → Verification → Observation

### 搜尋研究

位於：

> Observation / Problem → Research → Evidence → Proposal

### 兩者的橋

位於：

> **Verification Result → Observation → Change Signal → Research Trigger**

因此真正值得保留的不是某個 Python 腳本，而是這條工程關係。

## 十二、目前狀態

### 已確認

- GitHub Actions 可以作為低成本 Trigger / Automation 執行環境。
- Consistency Check 可被抽象成 Validator / Verification Capability。
- 自動索引可作為 Result Persistence / Recall 輸入。
- 失敗狀態可作為 Observation / Change Signal。
- 搜尋研究可作為外部 Evidence / Method Research 層。
- Validator 與 Research 可以透過 Observation / Problem Confirmation 形成閉環。
- 這與既有 Continuous Evolution Loop 相容。

### 待研究

- `scripts/check_consistency.py` 的完整設計與實際規則。
- 現況自動索引應包含哪些欄位。
- 哪些一致性檢查適合機器確定性判斷。
- 哪些問題必須交給 GPT 做語義判斷。
- Research Trigger 的最小必要條件。
- Research Result → Evidence → Decision 的資料結構。
- Graph / Impact Analysis 是否在實際工作中形成足夠瓶頸。

### 尚未採用

- 完整 Validator Framework
- 完整 Research Orchestrator
- Document Graph Engine
- 自動 Research Worker
- 自動 Agent Runtime

---

## 十三、研究結論

本輪最重要的結論不是「建立一致性檢查工具」。

而是確認未來藍圖可以形成：

> **自動檢查問題 → 觀察問題 → 觸發研究 → 尋找外部方法 → 驗證候選解法 → 正式採用 → 實作 → 回歸驗證**

這使搜尋研究從「獨立研究活動」提升為：

> **系統演化閉環中的 Research Stage。**

而 Consistency Validator 則成為：

> **把系統變更轉化成可觀察工程訊號的 Verification Capability。**

兩者共同形成：

> **Verification → Observation → Research → Evolution**

但目前仍屬研究結論，不直接改變正式 CURRENT 架構。
