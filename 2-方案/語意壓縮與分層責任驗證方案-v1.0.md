# 語意壓縮與分層責任驗證方案

版本：v1.0
類型：實驗研究方案
狀態：【新方案；已完成初步模擬驗證】

## 一、方案目的

本方案以正式 System 與極致壓縮對照組 System 進行對照，研究在 Knowledge 不變的前提下：
1. Solution、System、Knowledge 的責任如何分層。
2. System 可以壓縮到什麼程度。
3. 哪些語意可以刪除、合併或移交。
4. 哪些語意刪除後會造成路由錯誤、功能錯誤或語意失真。
5. 如何用最少 Context 保留完整可運作能力。

核心目標不是追求文件最短，而是找出「最小充分語意（Minimum Sufficient Semantics）」。

## 二、三層責任

Knowledge 決定「依據是什麼」。
System 決定「能做什麼」。
Solution 決定「這次怎麼用、怎麼串、什麼結果算完成」。

### Knowledge
負責：原理、規則、事實、證據、判定依據。
不負責：本次任務路由、執行流程、方案驗收。

### System
負責：固定能力、功能邊界、必要輸入、固定依賴、結果產出。
不負責：特定方案目的、實驗路由、場景性驗收。

### Solution
負責：任務目的、System 路由、串接順序、使用邊界、依賴、實驗變因、驗收條件、結果判定。

## 三、對照實驗

### A 組：正式組
使用正式 Solution、正式 System、相同 Knowledge。
保留較完整的功能、輸入、輸出、依賴與驗證資訊。

### B 組：壓縮對照組
使用壓縮 Solution、壓縮 System、完全相同 Knowledge。
刪除可由其他層取得的重複語意；保留功能身份、必要依賴、不可替代的結果語意；由 Solution 承擔場景性路由與驗收。

### 實驗控制
Knowledge 不變。
主要變因限定為：
```
Solution 語意壓縮
+
System 語意壓縮
```

## 四、初步實驗結果

50 次結構化模擬：

| 指標 | 初始壓縮組 | 加入 Solution 邊界後 | 加入驗收定義後 |
|---|---:|---:|---:|
| 路由錯誤 | 3/50 | 0/50 | 0/50 |
| 語意失真 | 4/50 | 1/50 | 0/50 |
| 幻覺 | 1/50 | 0/50 | 0/50 |
| 功能完成 | 48/50 | 49/50 | 50/50 |
| 整體成功 | 46/50 | 49/50 | 50/50 |

Token 結構化估算：
- 正式組：約 28,201 tokens／50 次。
- 初始壓縮組：約 9,177 tokens／50 次。
- 加入 Solution 邊界後：約 9,500 tokens／50 次。
- 壓縮後仍約降低 66%～67%。

以上是結構化模擬與估算，不是獨立模型/API benchmark，不得直接視為真實模型錯誤率。

## 五、錯誤來源

### 路由錯誤
原因：壓縮 Solution 未明確指定正式組／對照組 System，可能造成同名 System 誤用。
修正：Solution 必須保存目的、路由身份、使用邊界、依賴身份。

結論：
> 影響「呼叫誰」的語意不能刪。

### 語意失真
主要路徑：
```
System 執行 → 得到結果 → 結果如何解讀不明確
```

例如只保留「Result: Context Profile」，可能不足以判定 Context Profile 的必要內容。

修正方式不是恢復完整 System，而是在 Solution 保存驗收結果定義。

C03 必須能判定：Context 梯度、結果、最小可靠 Context、飽和／下降點。
C04 必須能區分：合理變化、非預期漂移、Context 敏感條件。
C05 必須區分：Supported、Contradicted、Unsupported、Uncertain、Context-induced Error。

其中：
> Unsupported 不等於 Hallucination。

## 六、語意壓縮規則

### 規則 1：刪除跨層重複語意
可由另一層可靠取得的資訊，不在目前層重複保存。

### 規則 2：可推導資訊可以壓縮
固定身份、固定結構可使用名稱、代碼或短契約表示，不必重複完整敘述。

### 規則 3：不可替代的身份不能刪
以下不可僅靠猜測：
- 正式組／對照組身份
- System 身份
- 依賴身份
- 實驗組別
- 方案邊界

### 規則 4：影響結果解讀的語意不能刪
若刪除後，同一結果可能得到不同結論，該語意必須保留。

包括：判定類別、排除條件、重要區分、結果最低必要欄位、特殊例外。

### 規則 5：執行細節優先壓縮
可優先刪除重複說明、完整背景、Knowledge 已提供的原理、非必要流程與不影響判定的解釋。

### 規則 6：驗收條件放 Solution
System 提供能力與結果；Solution 判定本次任務是否達標。

## 七、壓縮後必須保留的最小語意

### Solution 最小契約
```
目的
路由
邊界
依賴
驗收
```

### System 最小契約
```
身份
功能
必要依賴
結果
```

### Knowledge 最小契約
```
原理
規則
證據
判定依據
```

## 八、禁止的壓縮方式

1. 只留下名稱，沒有功能語意。
2. 讓 Solution 猜正式組／對照組身份。
3. 讓 System 猜本次方案的驗收標準。
4. 把 Knowledge 原理複製進 System。
5. 為修復單次錯誤而恢復整份長文件。

正確修正流程：
```
發現錯誤
↓
定位缺失語意
↓
只補最小不可替代語意
↓
重新測試
```

## 九、語意刪除判定

每刪除一段語意，檢查：

Q1：是否仍知道自己是誰？否 → 不可刪。
Q2：是否仍知道要做什麼？否 → 不可刪。
Q3：是否仍知道依賴誰？否 → 不可刪。
Q4：是否仍能正確理解結果？否 → 不可刪。
Q5：是否仍能判斷任務完成？否 → 將語意移至 Solution，而非直接刪除。
Q6：若只是背景、重複或其他層可取得資訊 → 可以壓縮。

## 十、最小充分語意模型

```
Knowledge
「依據是什麼」
      ↓
System
「能做什麼」
「需要什麼」
「產出什麼」
      ↓
Solution
「這次為什麼做」
「呼叫誰」
「怎麼組合」
「什麼結果算完成」
```

核心原則：
> 壓縮不是刪字，而是刪除不會影響決策、執行與結果解讀的冗餘語意。

## 十一、驗收標準

方案通過的最低條件：

1. Knowledge 不變時，壓縮 System 不改變核心能力。
2. Solution 能正確指定 System 身份。
3. 不發生正式組／對照組混用。
4. System 能完成核心功能。
5. 結果能被正確解讀。
6. 驗收分類不因壓縮改變。
7. 不因壓縮增加無法解釋的幻覺。
8. Context 成本顯著低於完整版本。
9. 錯誤能定位到具體缺失語意。
10. 修正時只補必要語意，不恢復不必要冗餘。

## 十二、方案結論

本實驗支持以下分層原則：

> Knowledge 保存「真實依據」。
>
> System 保存「可重複能力」。
>
> Solution 保存「場景使用與驗收」。

語意壓縮的核心是：
> 每一個語意只在真正需要它的層存在一次。

因此：
```
可由 Knowledge 取得 → 不在 System 重複
可由 System 身份取得 → 不在 Solution 重複
屬於本次任務用途／路由／驗收 → 必須在 Solution
影響 System 身份／功能／結果理解 → 必須保留
```

最終目標：
> 在維持可交接、可執行、可驗收的前提下，找到整個知識庫的最小充分語意集合。
