# 工程運作與持續改進方案 v1.2

日期：2026-09-17
前版：`2-方案/工程運作與持續改進方案-v1.1.md`
狀態：【正式補強；新增「新內容 → 問題接收 → 研究結論」入口】

## 一、修正原因

v1.1 已把「建立規劃」納入工程運作，但本次發現仍可能發生：

```text
新內容／新要求
→ 直接進入規劃或規則修改
```

因此工程運作現在必須從「問題接收」開始，而不是只從「建立規劃」開始。

## 二、工程運作完整入口

```text
新內容／新要求／新發現
↓
Problem Intake
↓
問題識別／拆解
↓
既有能力檢查
↓
外部研究／比較
↓
漏洞／失效／反方案
↓
結論
↓
是否進入工程規劃
↓
建立規劃
↓
【規劃完成／未建立／未完善】
↓
待辦／順序／依賴／施工入口
↓
正式建立方案流程
```

## 三、Problem Intake 的工程責任

工程運作層負責判斷一項新內容目前處於哪個狀態：

```text
普通討論
問題候選
需求候選
研究項目
方案候選
正式工程項目
```

只要可能改變知識、規則、系統、方案、流程或架構，就不得直接視為正式工程結論。

## 四、Problem Intake 不等於建立方案

Problem Intake 只負責把新內容轉成可研究、可判斷的工程問題。

正式研究與建立仍由：

`2-方案/正確成立方案與系統方案-v2.2.md`

負責。

責任分界：

```text
工程運作
= 新內容在哪裡、是否需要處理、目前處於哪一階段

正確成立方案與系統方案
= 問題如何被研究、比較、反方案、確認，以及何時 ALLOW 建立
```

## 五、規劃建立時的同步內容

只有 Problem Intake 得到正式結論、確認值得進入工程後，才建立規劃。

建立規劃時一次同步：

```text
規劃狀態
建立狀態
完善狀態
待辦
順序
依賴
前置條件
下一個可執行工作
施工入口
```

施工入口固定標記：

```text
【規劃完成／未建立／未完善】
```

## 六、回傳與紀錄成本

不得因新增 Problem Intake 而重新陷入逐步紀錄。

```text
微步驟：不記錄／不回傳
問題研究批次：內部完成
問題成立／否決：Checkpoint
進入規劃：同步一次
Gate：Checkpoint
重大狀態／新基準：完整同步
```

待辦只在工程階段、阻塞、結論、Gate 或狀態真正改變時更新。

## 七、下一個 AI 的強制入口

看到任何新的重大內容時，先問：

```text
這是普通討論，還是可能改變工程方向？
```

若可能改變工程方向：

```text
停止直接建立
→ Problem Intake
→ 問題拆解／研究／比較
→ 結論
→ 才能進入規劃
```

若已存在規劃且標記：

```text
【未建立】／【未完善】
```

則直接進入既有的正式建立前流程，不得把規劃視為已成立方案。

## 八、正式狀態

本版與 v1.1 的「規劃生命週期」相容；新增的只是更早的 Problem Intake 入口，不建立第二套工程運作系統。
