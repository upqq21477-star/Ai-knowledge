# 工程運作與持續改進方案－企劃

版本：v1.0
狀態：【企劃完成；尚未建立正式方案；待後續方案建立 Gate】
日期：2026-09-17

## 一、企劃目的

本企劃針對 Ai-knowledge 長期、多輪對話、多人／多 AI 交接、方案並行規劃與持續修改後產生的工程連續性問題，提出一個候選上位方案。

核心問題不是管理所有知識、系統或方案內容，而是維持：

```text
目前在哪裡
↓
接下來要做什麼
↓
哪些工作已規劃但尚未施工
↓
哪些工作因依賴／優先順序而延後
↓
為什麼延後
↓
最近發生了什麼變更
↓
下一個 AI 如何可靠接手
↓
實際運作發現的問題如何形成改進訊號
↓
何時需要全面重新評估／重整
```

目標：降低長期運作中的狀態漂移、待辦遺失、順序錯亂、交接失真、變更不可追溯與重複犯錯。

## 二、問題定義

### 1. 長對話造成工程狀態遺失

對話持續增加後，原本規劃的工作可能離開目前上下文。若只有待辦清單，容易失去：

- 原始規劃目的
- 原本順序
- 延後原因
- 前置條件
- 依賴
- 重新啟動條件
- 是否仍有效

因此「待辦」不能等同於「工程狀態」。

### 2. 已規劃但尚未施工的方案容易失聯

例如圖書館式知識管理方案可能已完成研究準備，但尚未到正式施工順序。

系統必須能明確區分：

```text
未提出
已構想
已研究
已規劃
等待施工
施工中
已完成未驗收
已驗收未實戰
已驗證
暫停
延期
取消
待重新評估
```

實際合法狀態仍需後續共同資料模型確認，不在本企劃中凍結完整 Schema。

### 3. 交接文件與工程實際狀態可能脫離

交接文件回答「告訴下一個 AI 什麼」，工程運作管理回答「整個工程現在實際處於什麼狀態」。兩者需要互相引用，但不能混為同一責任。

### 4. Git 變更與工程變更意義不同

Git 記錄檔案版本與提交歷史；本候選方案若成立，只記錄工程意義上的：

```text
改了什麼
為什麼改
影響什麼
目前是否已重新驗證
是否產生待重新評估項目
```

不得取代 Git。

### 5. 改進訊號沒有穩定回流位置

實際工作可能發現知識不足、系統缺口、方案組合問題、資料模型問題或整體架構問題。需要記錄訊號並送回真正負責的層，而不是全部堆進本方案。

## 三、候選定位

暫定名稱：

**工程運作與持續改進方案（Engineering Operations & Continuous Improvement Solution）**

暫定定位：

> 管理整個 Ai-knowledge 工程的狀態、路線、順序、依賴、延期、交接、變更與改進訊號；不直接取代知識、系統、正式方案或 Git 的專業責任。

它不是：

- 中央萬能治理系統
- 專案管理軟體完整替代品
- 知識庫
- 方案內容管理器
- Git 替代品
- 所有系統的執行引擎
- 自動決策／自動刪除引擎

## 四、預定管理範圍

### A. 工程目前狀態

記錄：

- 目前主線
- 目前階段
- 目前工作
- 已完成
- 未完成
- 阻塞
- 待驗證
- 待決策
- 目前重大風險

### B. 工程路線與工作池

管理不同時間尺度的工作：

```text
現在工作
近期工作
已規劃待施工
等待前置條件
延後工作
長期候選
待重新評估
```

每項工作至少需要能回答：

```text
做什麼
為什麼做
目前狀態
前置條件
依賴
目前順序
延後原因
重新啟動條件
```

### C. 方案生命週期與施工順序

特別處理「方案已建立但尚未施工」的情況。

例如：

```text
圖書館方案
→ 已完成研究／規劃
→ 尚未進入正式施工
→ 保留在未來工作池
→ 不因長時間沒有施工而遺失
```

### D. 變更追蹤

記錄工程層面的重大變更，並與 Git commit／檔案變更建立可追溯關係。

最小概念：

```text
工程變更事件
├─ 變更對象
├─ 原狀態
├─ 新狀態
├─ 原因
├─ 影響
├─ 相關決策
├─ Git／文件證據
├─ 驗證狀態
└─ 待重新評估事項
```

### E. AI 交接狀態

提供下一個 AI 的最小充分工程背景：

```text
目前目標
目前主線
目前狀態
最近完成
未完成
禁止事項
正在等待什麼
下一步
重要未解問題
待重新評估項目
```

它不取代完整交接文件，而是提供交接所需的工程狀態入口。

### F. 改進事件

記錄實際工作產生的改進訊號：

```text
觀察
↓
問題／缺口判定
↓
判斷責任層
↓
送回知識／系統／方案／整體重整
↓
處理
↓
驗證
↓
回寫結果
```

本方案不自行吞掉所有改進工作。

### G. 待重新評估／整體重整

當問題可能影響多個方案、共同資料、系統責任、身份／版本／歷史／接口時，建立：

```text
REASSESS-PENDING
```

先記錄，不立即局部 Patch；待適當時機進行全面影響分析與整體重整。

### H. 文件與結構變更追蹤

提供：

- 最近變更
- 變更原因
- 影響對象
- 新舊狀態
- 相關 commit
- 是否需要回寫待辦／交接／方案狀態

## 五、與既有能力的責任邊界

### 方案管理系統

負責「方案本身」的目的、組成、流程、條件、驗證與歷史。

本候選方案負責「所有方案在整個工程中的位置、順序、狀態與下一步」。

### AI 上下文與交接系統

負責上下文選擇、交接內容與 AI 所需背景。

本候選方案提供工程狀態來源，不取代上下文管理。

### 整體資料治理方案

負責共同資料語義、身份、版本、關係、狀態、歷史與追溯。

本候選方案使用這些資料語義，不自行發明另一套身份／版本／關係模型。

### 知識與資料迭代演化方案

負責正常變更如何安全進行。

本候選方案負責知道「有一個變更正在進行／已完成／需要回寫」，不取代變更處理本身。

### 能力蒸餾與系統重構方案

負責長期累積後的結構性重整。

本候選方案負責記錄重整候選、順序、狀態與交接，不自行執行蒸餾。

### 問題解決系統

負責真正的問題分析與解決。

本候選方案只負責發現、記錄與路由問題，不建立第二套問題解決流程。

### Git

Git 是檔案與版本歷史的底層證據。

本方案若成立，只增加工程語義層的變更索引，不重複保存 Git 全部資料。

## 七、核心工作流程

### 正常工程流程

```text
工作／方案被提出
↓
建立工程項目狀態
↓
確認目的與依賴
↓
決定施工順序
↓
進入施工
↓
更新狀態
↓
驗收／實戰驗證
↓
完成／進入下一階段
↓
回寫工程狀態
```

### 工作延期

```text
原工作
↓
發現更高優先工作或前置條件不足
↓
記錄延期
↓
保存原順序
↓
記錄新位置
↓
記錄延期原因
↓
記錄重新啟動條件
↓
進入待施工工作池
```

禁止單純把項目從待辦清單刪掉。

### 長對話後恢復

```text
新 AI／新工作階段
↓
讀取工程狀態
↓
讀取目前主線
↓
讀取未完成與延期項目
↓
讀取最近變更
↓
讀取待重新評估項目
↓
再進入目前工作
```

### 改進回流

```text
實際工作
↓
觀察問題
↓
建立改進事件
↓
判斷責任層
↓
交給真正負責方案／系統
↓
處理與驗證
↓
回寫工程狀態
```

## 八、全面重整機制

當某個問題可能跨越多個方案或共同資料層時：

```text
發現問題
↓
確認問題成立
↓
建立 REASSESS-PENDING
↓
記錄已確認／可能影響
↓
暫不局部回改
↓
繼續目前主線
↓
到達重新評估時機
↓
全面檢查知識／系統／方案／共同資料／接口
↓
形成整體重整候選
↓
確認
↓
一次性重整
↓
整體驗證
```

但若出現以下情況，不得因等待整體重整而延後：

- 資料已被破壞
- 目前狀態已明顯錯誤
- 驗證已無法進行
- 當前工作會持續產生錯誤
- 安全／完整性邊界被破壞

此時仍可立即修正。

## 九、失效模式

需要特別防止：

1. 待辦項目因延期而消失。
2. 原始順序被新對話覆蓋。
3. 延期原因沒有保存。
4. 已規劃但未施工被誤認為不存在。
5. 文件已建立被誤認為方案已完成。
6. 方案完成被誤認為方案已驗證。
7. Git 有變更但工程不知道變更原因。
8. 工程狀態與交接文件不一致。
9. 改進事件沒有回流真正責任層。
10. 中央管理層逐步吞入其他方案的執行責任。
11. 局部 Patch 過多造成架構進一步分裂。
12. 為了管理而建立過度複雜的專案管理平台。

## 十、外部方法比對結論

本企劃參考成熟的 Portfolio Management、Portfolio Backlog、Roadmap、Dependency Management 與 AI Handoff 模式。

外部方法顯示值得採用的共同原理：

- 以 portfolio／roadmap 管理跨工作項目的順序、依賴、風險與長期方向。
- 把已規劃、進行中與未來工作保留在同一可追蹤結構中，而不是只保留當前工作。
- 使用 dependency 關係表達「誰必須先完成」。
- 將工作狀態與實際執行內容分離。
- AI／代理交接需要保存可恢復的上下文與狀態。

本專案不直接複製 Jira、Azure Boards、Planner、PMI Portfolio 或 Agent Framework 的完整產品模型，只吸收必要原理。

主要參考：

- PMI, The Standard for Portfolio Management：Portfolio Roadmap、Dependencies、Timing、Sequencing、Planned Tasks。
- Microsoft Azure Boards：Portfolio Backlog、跨團隊 Dependency、Progress。
- Microsoft Planner Portfolios：Portfolio、Roadmap、Milestone、Status。
- Atlassian Jira / Advanced Roadmaps：Backlog、Dependency、Roadmap、Scheduling、Warning。
- Microsoft Agent Framework：Handoff、Context、Checkpoint、Routing。

## 十一、建立前 Gate

本文件只是企劃，不代表正式方案成立。

正式建立前必須重新確認：

```text
□ 問題已確認
□ 現有方案／系統能力已完整盤點
□ 外部方法已研究
□ 外部工具／產品已比較
□ 與方案管理、交接、待辦、檔案追蹤能力的重疊已分析
□ 資料責任邊界已確認
□ 與共同資料治理模型的接口已確認
□ 最小資料模型已確認
□ 主要失效模式已分析
□ 真實案例已選定
□ 最小實作驗收方法已確認
□ 實戰驗證驗收方法已確認
□ 使用者已確認方案方向
□ 方案正式建立
```

其中：

```text
驗收方法已確認
≠ 已實作
≠ 已驗收
≠ 已實戰驗證
```

## 十二、第一批真實案例候選

### 案例 001：圖書館方案

驗證：

- 已規劃但未施工的方案能否長期保留。
- 延後後能否知道原始順序與延期原因。
- 前置條件完成後能否重新找到。
- 新 AI 是否能從工程狀態恢復它。

### 案例 002：長對話造成待辦漂移

驗證：

- 對話跨多個主題後，原待辦是否仍可恢復。
- 新工作是否錯誤覆蓋舊工作。
- 延後是否有理由與重新啟動條件。

### 案例 003：AI 交接

驗證：

- 新 AI 是否能知道目前主線。
- 是否能知道已完成、未完成、禁止事項。
- 是否能找到待重新評估事項。

### 案例 004：檔案變更

驗證：

- Git commit 與工程變更是否能建立關係。
- 是否能知道修改原因與影響。
- 是否能回寫目前狀態與交接資訊。

## 十三、停止條件

本企劃完成後停止方案結構擴充。

下一階段不直接建立系統，而是先完成：

```text
資料格式確認
↓
圖書館方案正式完成
↓
知識書／系統／方案／整體架構全面重評估
↓
依新的共同資料格式進行大重整
```

只有後續正式方案建立 Gate 通過，才進入方案施工。
