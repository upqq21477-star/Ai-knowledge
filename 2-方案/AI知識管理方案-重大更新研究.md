# AI 知識管理方案－重大更新研究

狀態：**【重大更新研究進行中；已完成第一輪外部方法與同類產品比對；候選架構待實際驗證】**

## 一、更新方式

本次不是修補舊方案，而是把舊版 `2-方案/AI知識管理方案.md` 視為歷史基準，重新回答：

> 在目前 AI、知識管理、搜尋、Agent Memory 與研究工具的發展下，一套以 AI 長期使用為目的的個人／專案知識管理方案，應該由哪些能力組成？這些能力應如何協作？

舊方案的八個系統不具有架構優先權；每個系統都重新接受「保留、拆分、合併、降級、取代、新增」檢查。

## 二、外部環境第一輪研究結果

### 1. 企業知識工具正在從「文件搜尋」走向「跨來源檢索＋回答＋研究＋行動」

Notion 目前的 Enterprise Search 可跨 Notion、Slack、Google Drive、Jira、GitHub 等來源搜尋，回答附來源；Research Mode 可將內部來源與網路組合成多步研究；同時支援模型選擇與權限範圍控制。

這表示成熟產品的核心不再只是「把文件放好」，而是：

```text
多來源
↓
搜尋／檢索
↓
理解問題
↓
整合
↓
帶來源回答／研究
↓
必要時進入行動
```

對本方案的影響：

- 搜尋系統不能只負責「找到檔案」。
- 研究能力與知識管理之間需要明確介面。
- 來源／引用不能被視為附加功能，而是回答可信度的重要支撐。
- 但目前仍不代表本方案需要立即改成企業級多來源平台。

### 2. Atlassian Rovo 將 Search、Chat、Agents、Knowledge Cards、Deep Research 分開但互相協作

Rovo Search 用於跨連接資料來源的搜尋與篩選；Rovo Chat 用於理解、分析與行動；Knowledge Cards 用於提供實體／主題的關聯資訊；Deep Research 用於跨來源研究並產生帶來源報告；Agents 則負責特定工作。

這支持一個重要架構原則：

```text
搜尋
≠
研究／推理
≠
行動
```

三者可以組合，但不應因為都由 AI 操作就混成一個「萬能系統」。

### 3. AI Agent Memory 已形成獨立的工程領域

2026 年的研究與產品開始明確把 memory 視為獨立架構層，而不是把完整對話歷史全部塞入 context。

Mem0 的近期架構同時使用語意相似度、BM25 關鍵字與 entity matching 進行多訊號檢索，並將 memory 依 user、agent、session/run、organization 等 scope 管理；同時開始處理 memory staleness、background consolidation、去重與過期資訊標記。

Letta 則把 persistent memory、identity、experience、skills 與 agent runtime 視為 stateful agent 的核心，並研究 memory usage 與 memory generation 的獨立評估。

ACL 2026 的 Agentic Memory 研究甚至把「儲存、檢索、更新、摘要、丟棄」作為 agent 可執行的 memory actions。

對本方案的影響非常大：

```text
記憶 ≠ 知識
但
知識管理方案不能忽略記憶的生命週期
```

目前舊方案把「AI 上下文與交接」放在橫跨流程的位置，但沒有充分處理：

- 什麼應永久保存？
- 什麼只屬於目前工作狀態？
- 什麼是歷史事件？
- 什麼是目前有效知識？
- 什麼已過期？
- 什麼應合併？
- 什麼應保留原始歷史？
- 何時應重新整理／壓縮記憶？

這應成為本次重大更新的重點檢查項目。

### 4. Markdown／本地檔案仍然是有效的知識承載方式

Obsidian 目前仍以本地 Markdown 檔案作為知識基礎，並提供全文搜尋、搜尋運算子、屬性篩選、圖譜與 local graph。其官方文件明確把純文字檔案、檔案系統與連結視為核心資料模型。

因此本方案目前採 Markdown＋Git 並沒有因為市場出現向量資料庫或知識圖譜產品就被證明錯誤。

更合理的結論是：

```text
Markdown／Git
= 知識的可攜式主要承載層

搜尋索引／語意索引／關係索引
= 可以在其上建立的檢索能力
```

不應把「使用 Markdown」與「只能全文搜尋」綁定。

## 三、第一輪外部方法帶來的新架構訊號

目前至少發現六個需要重新檢查的架構方向：

### A. 檢索需要多訊號，而非單一搜尋方式

成熟方案逐漸使用：

```text
關鍵字
+
語意相似
+
實體／關係
+
時間／狀態／權限等結構化條件
```

這與現有搜尋系統的「精確／關鍵字／語意／分類」模型相容，但需要把「多訊號組合與排序」重新納入設計。

### B. 知識管理需要處理「目前有效性」

只保存內容不夠。

需要能判斷：

```text
現在有效
歷史有效
已被取代
暫不確認
局部適用
條件改變
```

因此「狀態」不是單純文件 metadata，而是檢索、比較、更新與上下文選擇的重要條件。

### C. Memory consolidation 是新的候選能力

近期 memory 系統開始處理：

```text
新增記憶
↓
去重
↓
合併／更新
↓
標記過期／被取代
↓
保留歷史
↓
形成較高層摘要／程序性知識
```

本方案目前只有「更新」概念，沒有把「長期累積後的整理」獨立處理。

需要在本次重構中判斷：

> 這是否應成為獨立系統，還是知識更新／整合系統的一部分？

### D. Context 不是單純的「讀多少文件」

現代 agent memory 系統開始把 context、working state、long-term memory、skills、history 分開。

因此現有「AI 上下文與交接系統」需要重新檢查，是否應從：

```text
上下文成本控制
```

擴展成：

```text
任務狀態
+
工作記憶
+
長期知識
+
歷史記憶
+
程序／技能
+
目前必要上下文
```

### E. 研究能力應與一般搜尋分開

Notion Research Mode、Atlassian Deep Research 以及本庫已有的搜尋研究方案，都顯示：

```text
搜尋
→ 候選資料
```

與：

```text
研究問題
→ 搜尋策略
→ 多來源證據
→ 比較
→ 綜合
→ 結論
```

是不同工作單位。

因此現有「資料探索與搜尋系統」不能直接吞併整個研究流程。

### F. 評估／回饋需要成為閉環

近期 memory 研究開始把 memory usage、memory generation、hygiene、retrieval 等分開評估。

本方案目前雖然有「實際驗證」，但還沒有形成穩定的：

```text
任務
↓
執行
↓
結果
↓
失敗／成本／漏失
↓
原因分類
↓
回饋到知識／系統／方案
```

這需要在新版方案中正式化。

## 四、目前舊方案的主要問題

舊方案目前以八個系統組成：

1. 資料分類與組織
2. 資料探索與搜尋
3. 來源與證據分析
4. 知識比較與衝突分析
5. 知識更新與狀態管理
6. 知識整合
7. AI 上下文與交接
8. 方案管理

舊方案的問題不是這八個能力「錯」，而是它們的層級不完全一致。

其中：

- 分類、搜尋、證據、比較、更新屬於知識處理能力。
- 上下文與交接屬於 AI 執行／資訊供應能力。
- 方案管理比較接近上位管理能力，而不是知識處理核心能力。

因此直接把八項並列為「核心系統」會造成架構層級混雜。

## 五、候選新版架構

目前形成候選模型，尚未正式定案：

```text
                    AI 知識管理方案
                           │
       ┌───────────────────┼───────────────────┐
       ↓                   ↓                   ↓
   知識生命週期         AI 使用／取用          驗證與回饋
       │                   │                   │
       ↓                   ↓                   ↓
  取得／整理          搜尋／檢索／上下文       任務執行
  分類／結構化        記憶／狀態／技能         結果評估
  證據／來源          Context 組裝             失敗診斷
  比較／衝突                                   回饋更新
  更新／整合
```

再由方案層把這些能力組合成：

```text
知識取得
→ 知識整理
→ 知識驗證
→ 知識保存
→ 任務取用
→ 實際使用
→ 結果驗證
→ 回饋
→ 知識／記憶更新
```

這只是目前候選架構，不是最終架構。

## 六、需要重新判定的系統

### 原分類與組織系統

暫時保留，但需要確認是否應改名為「知識結構與組織系統」。

原因：現在需要的不只是資料夾分類，而是內容、屬性、狀態、關係、可檢索特徵的組合。

### 原資料探索與搜尋系統

保留，但需要重新設計成「檢索系統」候選，納入：

- 關鍵字
- 語意
- 結構化條件
- 實體
- 時間／狀態
- 多訊號排序

### 原來源與證據分析系統

暫時保留，但需要檢查是否應擴張為「來源、證據與主張驗證系統」。

### 原知識比較與衝突分析系統

暫時保留。

需要加入時間、條件、狀態與版本比較，並與更新系統建立明確介面。

### 原知識更新與狀態管理系統

高度可能保留，但需要吸收：

- stale detection
- superseded state
- consolidation
- history preservation
- update triggers

### 原知識整合系統

需要重新評估是否與「更新／consolidation」形成重疊。

可能結果：

```text
保留獨立
或
拆成「知識整合」＋「知識整理／consolidation」
或
部分降級為流程
```

目前不定案。

### 原 AI 上下文與交接系統

必須重新設計，是本次重大更新的主要變更候選。

可能擴張為「AI 記憶、狀態與上下文系統」，但必須先確認與知識／記憶邊界。

### 原方案管理系統

需要重新檢查是否應屬於「方案層的管理能力」，而非 AI 知識管理核心系統。

可能保留為上位管理系統，但不再與知識處理系統平行排列。

## 七、目前明確不採用的方向

### 1. 不因為市場流行就直接導入向量資料庫

目前外部產品大量使用向量搜尋，但這只證明語意檢索有價值，不證明本庫必須立即使用特定資料庫。

### 2. 不把知識圖譜視為必要核心

外部方案正在使用 entity linking、graph memory 或 graph-aware retrieval，但不同產品的實作取捨不同。應先確認本庫的關係複雜度是否真的需要圖資料結構。

### 3. 不把所有 memory 都轉成知識

記憶、歷史、工作狀態、程序性技能與穩定知識仍應維持不同用途。

### 4. 不把所有能力做成一個 Agent

目前市場已經顯示 Search、Research、Memory、Agent、Action 可以協作，但不代表全部必須合併。

### 5. 不放棄 Markdown＋Git

目前沒有證據證明它已經不足以作為主要承載層；反而其可攜性、版本控制與資料所有權仍有明顯價值。

## 八、下一輪研究問題

在正式寫新版方案前，必須回答：

1. 「知識生命週期」是否應成為新版主軸？
2. 「記憶／狀態」應與知識如何分層？
3. Search、Research、Retrieval 是否應拆成三個能力？
4. Evidence／Claim／Knowledge 是否需要更明確資料模型？
5. Knowledge consolidation 是否需要獨立系統？
6. Evaluation／Feedback 是否需要獨立系統？
7. 外部搜尋／同類產品監測是否應留在更新方案，還是成為獨立能力？
8. 哪些現有系統其實是流程，而不是系統？
9. 哪些系統可以合併？
10. 哪些能力目前缺失？
11. 新版方案如何在 Markdown＋Git＋手機操作條件下保持低維護成本？
12. 如何驗證「AI 不需要重讀全部歷史，也能正確恢復並使用知識」？

## 九、第一輪研究結論

目前證據支持的不是「增加更多系統」，而是：

> **重新整理系統的層級與生命週期，將知識內容管理、AI 記憶／狀態、檢索／上下文供應、研究、驗證／回饋分開，再用方案把它們組合。**

因此新版方案不應從「八個舊系統還剩幾個」開始，而應從「AI 知識管理需要完成哪些能力」重新開始。

目前仍不直接寫死最終系統數量。
