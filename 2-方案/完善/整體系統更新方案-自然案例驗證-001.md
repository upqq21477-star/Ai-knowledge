## 四、外部研究與比較

### 1. GitHub Migration

GitHub 的官方遷移流程要求先定義遷移範圍，區分不同遷移保真度，並對 repository 進行 dry run，再安排 migration 前後步驟。這支持本案例增加「遷移前驗證」與「遷移後驗證」，而不是只建立新版本。

來源：GitHub Docs，Planning your migration to GitHub。

### 2. GitHub API Versioning

GitHub 將 breaking changes 明確視為可能破壞整合的變更，要求升級前閱讀 breaking changes、進行必要修改並測試；舊版本也具有明確支援期限。這支持本案例將「破壞性變更、相容性、遷移、測試、退役」視為一條連續生命週期。

來源：GitHub Docs，API Versions / Breaking changes。

### 3. Microsoft Azure Well-Architected

Microsoft 建議小型增量更新、嚴格測試、漸進式暴露、向前／向後相容，以及為錯誤部署準備補救與回復方案。對重大系統變更，還可採用雙環境、逐步增加流量與驗證後切換等模式。

來源：Microsoft Azure Well-Architected Framework，Operational Excellence、Mission-critical deployment/testing。

### 4. 外部研究形成的共同原則

不同工具與平台雖然實作不同，但共同指向：

```text
重大變更
→ 新舊基線
→ 依賴／相容性檢查
→ 遷移策略
→ Dry Run／測試
→ 分階段或受控切換
→ 結果驗證
→ 回復條件
→ 穩定後退役舊狀態
```

外部研究不支持把所有更新都做成重型遷移；遷移強度應依破壞性、影響範圍、依賴數量、錯誤成本與回復難度決定。

## 六、重新盤點既有系統能力

補入上述知識後重新檢查既有系統：

### 更新監控與觸發系統

負責變更來源、觸發與頻率；不應承擔完整遷移施工。

### 知識更新與狀態管理

負責建立新版本、目前狀態、歷史與廢棄；可承載版本生命週期，但不應單獨承擔大型遷移驗證。

### 知識比較與衝突分析

負責新舊內容差異、關係與衝突判定。

### 更新影響分析與成本判斷

負責依賴、影響擴散、更新必要性與成本／不更新成本。

### 知識整合與驗證

負責更新後一致性與知識間關係。

### 方案管理

負責固定目的下的系統組合、流程、紀錄與方案狀態。

### 結論

目前不存在必須立即建立的「重大遷移獨立系統」。新增知識可以先由既有更新、影響分析、知識整合、方案管理等能力組合承載。

真正尚未證明的是：在實際大型重製時，現有系統是否能低成本執行 Dry Run、分階段切換與 Rollback。

1. 新缺口目前是知識與流程策略缺口，不是已證明的獨立責任系統缺口。
2. 既有系統已覆蓋偵測、比較、影響、更新、整合、方案管理等主要責任。
