## 一、補強目的

第四方案目前已經具備「為什麼需要蒸餾、蒸餾什麼、如何分析、候選處置」的基本骨架，但還缺少真正能承擔高風險重構的安全閉環。

本規格不是新方案，也不是獨立系統。

目的只有一個：

> 讓能力蒸餾從「分析與提出處置」提升為「可追溯、可恢復、可驗收、可建立新基準的完整工程流程」。

---

## 二、第四方案完整閉環

正式閉環應整理為：

```text
蒸餾訊號
↓
結構性問題確認
↓
判斷是否屬於正常迭代
↓
確認蒸餾範圍
↓
實際能力盤點
↓
使用／依賴／證據盤點
↓
重疊／責任／資料／關係分析
↓
提出候選處置
↓
影響分析
↓
處置前保存
↓
遷移／相容性設計
↓
恢復條件確認
↓
最小實作驗收方法確認
↓
執行重構／融合／取代／重建
↓
最小實作驗收
↓
真實工作驗證
↓
新基準建立
↓
舊能力 Retire／Archive 或保留既定狀態
↓
回寫相關知識／系統／方案／接口
```

若任何安全關鍵步驟未完成，不得直接宣布蒸餾成功。

---

## 三、第一個補強：處置前保存

任何可能造成既有能力退出、資料改寫、責任轉移、關係改變、接口改變或不可逆結構變更的處置，都必須先完成保存。

### 最小保存內容

```text
原始 Identity
原始 Version
原始 State
原始 Lifecycle
原始位置／路徑
原始內容或可恢復版本
原始關係
原始依賴
原始驗證狀態
處置前 Git Commit
```

保存的目的不是讓 Repository 永遠保留兩套正式能力，而是確保：

```text
可以知道原本是什麼
可以知道為什麼改
可以知道改成什麼
必要時可以恢復
```

Archive、Git 歷史、正式事件紀錄三者責任不同，不得混為一談。

---

## 四、第二個補強：Distillation Event 蒸餾事件

每次真正執行蒸餾處置，都應有一筆可追溯事件。

最小事件概念：

```text
Distillation Event
├─ Event Identity
├─ Trigger
├─ Scope
├─ Structural Problem
├─ Source Capabilities
├─ Source Identity / Version
├─ Candidate Disposition
├─ Reason
├─ Impact Analysis
├─ Dependencies
├─ Migration / Compatibility
├─ Preservation
├─ Recovery Condition
├─ Acceptance Method
├─ Execution Result
├─ Validation Result
├─ New Baseline
├─ Old State
├─ New State
├─ Related Commit
└─ Follow-up
```

這不是要求建立大型資料庫。

第一階段可以用可讀的正式紀錄文件實作；真正欄位是否需要擴張，應由第一個真實案例驗證。

## 五、第三個補強：安全閘門

候選處置不能直接進入執行。

### Gate D1：影響分析

確認：

```text
誰會受影響？
哪些資料會變？
哪些關係會變？
哪些依賴會變？
哪些接口會變？
哪些系統／方案會受到影響？
```

### Gate D2：保存

確認舊狀態已可追溯、可恢復。

### Gate D3：遷移／相容性

若新舊結構不能直接替換，必須明確定義：

```text
Identity Mapping
Version Mapping
Relation Mapping
Data Conversion
Usage Conversion
Compatibility Layer（若必要）
Cutover
Rollback
```

不得因「先做再說」而永久留下雙格式。

### Gate D4：驗收方法

在執行前先定義：

```text
預期狀態
預期輸出
驗收條件
失敗條件
需要保留的證據
```

這是驗收方法的定義，不是提前宣稱驗收通過。

### Gate D5：執行

完成實際重構。

### Gate D6：最小實作驗收

確認重構後的能力在預定條件下工作。

### Gate D7：真實工作驗證

讓新的結構進入正常工作，觀察實際使用、錯誤、理解成本、同步成本、依賴與維護狀態。

### Gate D8：新基準

只有驗證完成後，才建立新的正式基準。

## 六、第四個補強：蒸餾觸發器

以下可作為蒸餾訊號：

```text
累積複雜度持續上升
重複責任持續出現
依賴關係開始侵蝕邊界
資料格式出現結構漂移
相同語義開始分裂
文件與實際能力持續偏離
驗證方法與實際結構脫節
Compatibility Layer 長期存在
正常迭代反覆撞到同一結構問題
AI Context 成本開始明顯上升
維護／同步成本開始明顯上升
大型資料／架構格式變更
```

但：

> 觸發器只是蒸餾訊號，不是自動蒸餾命令。

收到訊號後必須先確認：

```text
這是正常迭代問題？
還是結構性累積問題？
```

如果正常迭代即可解決，交回方案三等日常迭代責任。

只有確認需要跨多個能力、資料、系統或方案重新整理時，才進入第四方案。

---

## 七、第五個補強：完成度分層

第四方案不得使用單一「完成／未完成」描述全部狀態。

至少分成：

```text
L0 方案建立
L1 最小驗收
L2 正常工作驗證
L3 真實蒸餾案例驗證
L4 失敗／回復流程驗證
L5 整體實戰驗證
```

### L0 方案建立

流程與邊界已形成文件。

### L1 最小驗收

能用最小案例重現完整蒸餾流程與必要證據。

### L2 正常工作驗證

蒸餾後的新結構能進入正常工作。

### L3 真實蒸餾案例驗證

至少完成一次真實舊能力／系統重疊或結構累積問題的蒸餾。

### L4 失敗／回復流程驗證

至少證明一次失敗或異常情境下，舊資料、舊狀態或回復路徑仍可使用。

### L5 整體實戰驗證

第四方案在多次正常迭代與重構循環中，證明能降低累積問題，而不是只完成一次漂亮的整理案例。

## 八、處置結果與生命週期

處置結果不應直接等同於檔案刪除。

例如：

```text
Merge
→ 新能力建立
→ 舊能力進入 Retire / Archive

Replace
→ 新能力驗證
→ 舊能力退出使用
→ 保留恢復證據

Rebuild
→ 新結構建立
→ 驗證完成
→ 舊結構 Retire / Archive

Retain
→ 暫不改變
→ 保留原因與重新評估條件

Keep
→ 維持現狀
→ 記錄為已檢查而非待處理
```

因此「處置」與「刪除檔案」不是同一概念。

## 九、與其他方案的責任邊界

### 方案三：知識與資料迭代演化

負責正常新增、修正、版本演化與日常變更。

### 方案四：能力蒸餾與系統重構

負責跨多個能力／系統／資料／方案的結構性累積問題，以及建立新的整體基準。

### 整體資料治理方案

提供 Identity、Version、State、Lifecycle、Relation、Traceability 等共同語義。

### 問題解決流程

當蒸餾執行中出現未預期問題，負責問題確認、既有能力盤點、候選解法、驗證與結果回寫。

### Git

保留版本與變更歷史；不取代蒸餾事件的語義紀錄。

## 十、第一個真實案例要求

第一個真實案例不再使用純假設模擬。

優先選擇：

```text
舊能力／系統重疊
```

原因：

1. 已有舊能力重製判定原則。
2. 已有能力重疊映射歷史資料。
3. 可以直接檢驗 Keep / Merge / Refactor / Replace / Rebuild / Retain / Retire / Archive 的責任邊界。
4. 能同時驗證保存、Identity、Relation、影響分析、驗收與回寫。

第一個案例的目標不是整理整個 Repository。

而是證明：

```text
發現結構問題
→ 做出可追溯判定
→ 安全保存舊能力
→ 建立新能力／新結構
→ 驗收
→ 實際工作驗證
→ 建立新基準
→ 能反查歷史
```

## 十一、外部實務對照

Microsoft 的現代化流程以現況盤點與評估為起點，並要求依賴、資料、技術狀態等資訊支持後續規劃；現代化執行後仍需測試、驗收與穩定化。citeturn0search1turn0search3turn0search12

AWS 的 Strangler Fig 模式則以「新舊並存 → 驗證 → 漸進替換 → 舊能力退出」降低大改造風險，並明確要求回復計畫。citeturn0search6turn0search14turn0search16

因此本補強不是單純增加文件欄位，而是把成熟現代化實務中已反覆出現的幾個工程原則轉換成 Ai-knowledge 可執行的最小閉環：

```text
現況盤點
+
依賴分析
+
保存舊狀態
+
漸進轉換
+
驗收
+
真實工作驗證
+
新基準
```

## 十二、目前結論

第四方案目前不應再增加更多抽象分類。

現在最重要的是把「分析方案」變成「安全可執行的重構流程」。

本補強規格完成後，下一階段應：

```text
補強規格確認
↓
方案四整體重整為 v1.1
↓
與方案三、共同資料、相關系統做影響分析
↓
建立最小蒸餾案例
↓
實際驗收
↓
進入第一個真實蒸餾案例
```

在上述整體重整前，不應對受影響方案／系統進行零碎局部 Patch。
