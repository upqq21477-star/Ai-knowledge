# 三方案第二輪真實案例檢驗-v1.0

## 狀態
【第二輪檢驗完成；A2／B2／C2 通過最小案例；尚未完成多案例與長期回歸】

## 一、檢驗目的

本輪不新增第四方案，也不修改既有舊檔案。

目的：把第一輪篩出的三個候選解法放入目前真實知識庫結構中，檢查它們是否真的能解決問題，而不是只在概念層面成立。

第一輪候選：

- A2：變更對象＋直接／下游依賴＋影響分析
- B2：最小執行／搜尋收據（Receipt）
- C2：變更請求（Change Request）＋影響分析＋驗證＋決策

本輪仍依既有「搜尋研究方案」的原則：問題 → 資訊需求 → 候選方法 → 最小測試 → 結果 → 限制。

## 二、案例 A：共同資料語義變更

### 測試問題

假設「核心資料類型與邊界」中，某一資料類型的定義或邊界發生變更，能否找出三方案中需要重新檢查的內容？

### 測試資料

目前已存在：

- `0-知識/分類/核心資料類型與邊界.md`
- `0-知識/管理/共同資料最小描述原則.md`
- `0-知識/管理/資料關係類型與語義字典.md`
- `2-方案/整體資料治理方案-v1.0.md`
- `2-方案/AI知識管理方案-v2.0.md`
- `2-方案/知識迭代與資料演化方案-v1.0.md`

### A1：只有版本變更紀錄

可以知道「規則改了」，但不能可靠回答：

- 哪些方案依賴這個規則？
- 哪些流程假設舊定義？
- 哪些測試需要重新執行？

判定：不足。

### A2：變更對象＋依賴＋影響分析

建立最小變更描述：

```text
變更對象
→ 被哪些資料／方案使用
→ 直接影響
→ 間接影響
→ 需要重新驗證
→ 暫不受影響
```

此模型能把「規則改變」轉換成「驗證範圍」，且不要求建立完整知識圖譜。

判定：通過最小案例。

### A 結論

A2 可保留為目前正式候選方向。

但尚不能證明完整 lineage graph 不需要。若後續真實案例出現多層、多跳、跨版本依賴無法以目前關係描述，再進行第二次外部搜尋與技術比較。

## 三、案例 B：搜尋／執行失敗後重建

### 測試問題

模擬 AI 在處理一項資料採用判斷時，搜尋到舊版本資料，最終因版本不相容而拒絕採用。

要求：事後能回答「當時查了什麼、用了什麼、為什麼拒絕」。

### B1：自由文字

```text
搜尋到舊版資料，因版本不相容而拒絕。
```

可以讀懂結果，但無法穩定重建：

- 原始任務。
- 查詢目的。
- 使用哪一筆資料。
- 使用哪個版本。
- 判斷依據。
- 驗證結果。

判定：不足。

### B2：最小 Receipt

測試最小記錄：

```text
任務：判斷資料是否可採用
搜尋目的：尋找目前適用的共同資料規則
候選資料：共同資料最小描述原則
資料版本：目前版本
使用條件：目前三方案架構
執行結果：候選資料被採用於比較
驗證結果：版本相容性檢查失敗
失敗位置：採用判斷
失敗原因：候選版本不符合目前條件
```

此記錄已能重建主要事件鏈，而且不需要記錄完整模型內部推理或所有 token。

判定：通過最小案例。

### B 結論

B2 可保留。

但「Receipt」目前只是資料／記錄概念，不應立即固定為產品、資料庫 schema 或完整 Agent Trace 平台。

## 四、案例 C：共同資料模型不足

### 測試問題

假設三方案協作時發現「現有核心資料類型無法描述某種新資料」，但尚未證明應新增資料類型。

### C1：直接修改核心資料模型

直接修改會跳過：

```text
問題是否真實
→ 是否只是既有類型描述不足
→ 是否影響其他方案
→ 是否需要新增、拆分或修改
```

判定：不採用。

### C2：變更請求

建立：

```text
問題觀察
→ 變更請求
→ 影響分析
→ 候選變更
→ 最小案例測試
→ 驗證
→ 採用／保留／拒絕
→ 歷史
```

此流程允許提出問題而不直接改變治理規則。

判定：通過最小案例。

### C 結論

C2 可保留。

但目前不建立完整 ITSM、審批平台或自動工作流。這些能力只有在真實變更量與責任管理需求證明必要時才搜尋與評估。

## 五、第二輪外部方法再檢查

本輪再次用既有搜尋流程檢查第一輪候選是否與成熟方法方向衝突。

### 1. 檢索品質不能靠直覺優化

Microsoft 的 RAG 評估文件明確區分 document retrieval、groundedness、relevance、completeness 等評估面向，並建議以有 ground truth 的測試資料評估檢索品質。citeturn0search0turn0search11

因此本專案不能把「看起來搜尋到了」當作搜尋最佳化證據。

### 2. Hybrid Search 暫不升級

Microsoft 的檢索架構文件指出 hybrid search、filter、reranking 各自解決不同問題，且應以測試比較結果決定是否需要。citeturn0search2turn0search9

因此目前維持：

```text
既有搜尋方式
→ 案例發現缺口
→ 建立可重現測試
→ 比較搜尋方式
→ 必要時才增加 hybrid／reranking
```

### 3. Receipt 的方向得到外部方法支持

W3C PROV 將 provenance 建模為實體、活動、代理者、使用、生成與衍生等關係，目的之一就是讓資料的產生與來源可以被追溯。citeturn1search0turn1search5

這支持本專案保留「最小可回溯記錄」方向，但不代表必須完整實作 W3C PROV。

## 七、第二輪暴露的新問題

本輪反而發現三個新的驗證缺口：

### D：影響分析依賴關係是否足夠完整

目前已有六種最小關係，但尚未實測它們是否足以支撐跨方案、多跳依賴追蹤。

### E：Receipt 的最小欄位是否足夠

目前能重建主要事件，但尚未測試：

- 同一任務多輪搜尋。
- 查詢改寫。
- 多來源比較。
- 中途失敗後重新搜尋。
- 同一資料不同版本。

### F：變更請求是否需要明確狀態模型

目前流程有採用／保留／拒絕，但尚未證明是否需要更細的狀態，例如草案、待影響分析、待驗證、已核准、已執行、回滾等。

## 八、下一輪條件

第三輪不應直接設計 D/E/F 的解法。

應再次使用既有搜尋方案：

```text
D/E/F 問題定義
→ 資訊需求
→ 外部成熟方法搜尋
→ 候選解法
→ 比較
→ 最小案例
→ 驗證
```

只有當第三輪也通過，才考慮把 A2/B2/C2 正式吸收進三個方案的完善版本。

## 九、限制

本輪沒有建立真正運行中的搜尋引擎、資料庫或 Agent Runtime，因此「真實案例」指以目前 GitHub 知識庫中的實際資料結構進行可重現的設計案例與人工驗證，不等同於生產環境壓力測試。

因此目前證據強度為：

```text
概念成立
＋
實際資料案例可操作
＋
外部方法方向一致
＝
候選解法通過第二輪

但尚未達到：
長期運行驗證
大規模資料驗證
自動化回歸驗證
```
