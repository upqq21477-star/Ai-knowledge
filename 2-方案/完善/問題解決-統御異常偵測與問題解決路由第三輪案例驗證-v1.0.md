# 問題解決：統御異常偵測與問題解決路由第三輪案例驗證 v1.0

日期：2026-09-17
狀態：【第三輪案例驗證；不建立新正式系統】

## 一、驗證目的

第二輪已確認最小統御能力不能只守施工階段，還必須檢查前置條件、允許動作、執行結果，並在重複或結構性異常時提出進入問題解決流程的建議。

第三輪測試五個容易造成 AI 誤判的情境：

1. 同時存在多個異常時，能否先處理真正阻斷施工的異常。
2. 異常修復後，能否重新檢查 Gate，而不是永久保持 LOCK。
3. 問題解決流程完成後，能否把結果回寫到 Expected State / Actual State。
4. 新舊工作記憶衝突時，能否辨識舊資料並拒絕使用過時狀態。
5. 同一項工作文字上同時符合多個階段時，能否依目前 Gate 與依賴關係判定真正允許的階段。

外部資料支持將 workflow 狀態、允許轉移、前置條件、持久狀態、恢復與可追溯性分開處理；狀態機 guard、恢復前重新驗證 live state，以及錯誤後停止／隔離而不是盲目繼續，均是近期實務與研究反覆出現的控制方向。citeturn0search0turn0search2turn0search3turn0search5

本輪仍採最小能力原則，不建立完整 Planner、風險評分引擎或獨立統御系統。

## 二、案例 A：多個異常同時發生

輸入：目前合法階段⑧；同時出現「Validation Receipt 缺失」、「下一步文件名稱與待辦描述不一致」、「舊版工作記憶仍標示可進入⑨」。

判斷不能按照發現順序直接處理，也不能因異常數量多而全部阻斷。應先判斷對目前施工合法性的影響：Receipt 缺失直接影響 Gate 證據；文件名稱不一致先確認是否為描述問題；舊工作記憶與現行狀態衝突，應標記為過時資料。

預期：主要阻斷異常為 Receipt 缺失；⑨ 維持 LOCKED。

結果：PASS。統御應以對合法施工狀態的阻斷影響排序，而不是以異常數量或文字嚴重程度排序。不建立完整風險評分。

## 三、案例 B：異常修復後重新解除 Lock

原狀態：⑧ Gate 未通過，原因為 Validation Receipt 缺失，因此⑨ LOCKED。

問題解決完成後：補正驗證、產生 Receipt、Receipt 可追溯。

正確流程：

```text
異常修復
↓
重新讀取 Actual State
↓
重新檢查 Gate
↓
確認所有前置條件
↓
Gate 通過
↓
解除⑨ LOCK
```

結果：PASS。LOCK 是由當前條件決定的狀態，不應變成永久標記；不能因「問題解決完成」文字本身直接推導 Gate 通過。

## 四、案例 C：問題解決結果回饋統御

Expected State：⑧ Gate 需要 Validation Receipt。
Actual State：Receipt 缺失。
問題解決結果：確認產生步驟未完成，已補做並完成驗證。

問題解決流程不能只回傳「已解決」，而應產生可供統御重新判斷的結果：

```text
問題：Receipt 缺失
原因：產生步驟未完成
修正：已補做
新 Actual State：Receipt 存在且可追溯
驗證：通過／待驗證
```

統御再比較 Expected / Actual State，然後重新檢查 Gate。

結果：PASS 條件。確認「問題解決 → 統御」需要最小結果回饋概念，但目前不固定完整 JSON Schema。

## 五、案例 D：新舊工作記憶衝突

```text
舊工作記憶：⑧ 完成後直接進入⑨
目前正式施工狀態：⑧ 尚未通過 Gate
最新待辦：⑨ LOCKED
```

不能用舊工作記憶覆蓋目前正式狀態。判斷優先依目前正式狀態、最新有效規則／待辦、Gate 結果；舊資料只能作為歷史證據，不能作為目前施工指令。

預期警報：

```text
【狀態衝突警報】
類型：新舊工作記憶衝突
處置：拒絕採用舊狀態，依現行 Gate 判斷
```

結果：PASS。這再次支持「Memory ≠ Current State」。

## 六、案例 E：工作同時符合多個階段描述

工作描述：「整理知識索引並測試搜尋效果」。文字上可能同時涉及⑨、⑩、⑪。

不能因包含「搜尋」「知識」「測試」就直接歸入已 LOCK 的階段。必須先判斷：目前 Gate、是否為前置條件、是否需要已解鎖能力、是否只是研究準備、是否會實際啟動被 LOCK 的階段。

若目前仍在⑧：

```text
正式建立⑨系統能力 → 禁止
研究⑨所需內容、整理案例、形成問題解決輸入 → 可視為準備工作
```

結果：PASS。階段歸屬不能只靠自然語言相似度，而要依 Gate、依賴、產物與實際啟動的能力判定。

## 七、三輪案例合併後的最小統御閉環

```text
讀取正式施工狀態
↓
確認目前階段
↓
確認 Gate / 前置條件
↓
確認工作是否允許
↓
執行
↓
Expected State vs Actual State
↓
正常 → 繼續
異常 → 分類
↓
判斷阻斷程度
↓
警報
↓
一般偏差 → 修正／重新驗證
阻斷異常 → 暫停依賴工作
重複／結構性異常 → 建議進入問題解決流程
↓
問題解決結果
↓
重新驗證 Actual State
↓
重新檢查 Gate
↓
解除 Lock 或維持 Lock
```

這比單純工作排程器更接近本專案所需的統御職責。

## 八、第三輪仍不能推出的內容

本輪仍不能證明需要獨立統御正式系統、大型 Planner、完整風險分數模型、獨立資料庫、大型 JSON Schema，也不能推出所有異常都應自動阻斷或全部進入問題解決流程。

目前只證明最小統御能力的責任邊界與閉環已足夠清楚，值得進行更接近實際工作的最終能力驗證。

## 九、外部比較

近期 workflow / agent orchestration 資料支持：

1. 狀態機應限制合法轉移與前置條件，而非只依賴模型記憶。citeturn0search0turn0search5
2. 長流程需要持久化目前狀態與可追溯事件，才能在中斷或錯誤後恢復。citeturn0search1turn0search2turn0academia24
3. Resume / Recovery 應重新驗證 live state，而不是直接沿用舊 checkpoint 假設。citeturn0search3turn0search8
4. 異常處理應區分停止、修復、重新驗證與恢復，而不是單純 retry。citeturn0search4turn0academia27
5. 執行記錄需要能重建狀態與決策路徑。citeturn0search0turn0search1

這些方向與本專案的「Expected / Actual State + Gate + Anomaly Routing + Problem Solving」一致；但本專案只採必要的最小子集。

> 統御不能只保存「下一步」，還必須保存「目前狀態如何被重新驗證，以及異常恢復後何時可以解除 Lock」。

```text

```
