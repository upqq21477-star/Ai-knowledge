## 一、問題確認

### 1. 實際事件

四方案逐項功能研究完成 A9～A12 後，既有研究文件曾寫出「下一批：A13～A16」。Repository 的正式功能清單實際上只定義方案一 A1～A12，並不存在 A13～A16。

之後 AI 依照先前工作指令繼續處理 A13～A16，造成批次來源錯置。

目前 Repository 的正式功能清單確認：

```text
方案一：A1～A12
方案二：B1～B16
方案三：C1～C18
方案四：目前已定義至 D18，後續需依正式清單確認
```

A13～A16 不是目前正式功能。

### 2. 問題不是「編號寫錯」

真正問題是：

> AI 在開始下一批工程工作時，沒有重新從正式功能來源計算「下一個存在且尚未完成的工作」，而是把歷史／交接文件中的「下一批」敘述當成了正式工作來源。

因此這是「工作來源權威性與執行前確認」問題，而不是單純編號問題。

---

## 二、問題拆分

本問題拆成五個子問題。

### P1：正式功能存在性未確認

執行 A13～A16 前沒有確認這四個功能是否存在於目前正式功能清單。

### P2：工作來源層級混淆

把：

```text
正式功能清單
```

與：

```text
研究文件中的下一批敘述
交接資料中的工作建議
舊工作指令
AI 對進度的推論
```

視為同等權威。

### P3：下一批不是由正式資料推導

目前的「下一批」主要以文字記錄保存，例如 A9～A12 文件末尾寫有「下一批：A13～A16」。這是一個人工敘述，而不是由正式功能清單與研究狀態重新計算出的結果。

### P4：缺少執行前阻斷

即使輸入要求與 Repository 正式內容衝突，AI 仍可以繼續建立研究成果。

### P5：錯誤可以向後傳播

一旦不存在的 A13～A16 被建立為研究對象，後續 AI 可能把它們當成已存在的正式功能，進一步產生：

```text
虛構功能
→ 虛構責任
→ 虛構知識需求
→ 虛構系統需求
→ 虛構方案結構
```

因此問題具有資料污染風險。

## 三、既有能力盤點

### 已存在且應沿用的能力

Repository 已經存在：

1. 正式四方案功能清單。
2. 問題解決系統。
3. 問題解決與新系統建立流程。
4. 搜尋研究方案。
5. 工程運作與持續改進方案。
6. 正式規則中的「真實來源與衝突處理」。
7. 既有「文件存在 ≠ 功能完成」原則。
8. 既有「問題 → 研究 → 比較 → 候選 → 實測 → 判定 → 回饋」流程。

正式規則已明確要求：實際檔案樹是內容存在性的主要真實來源；文件衝突時應停止猜測、檢查實際檔案樹與 Git 歷史，而不能因某文件較完整就視為最新。這表示本次缺口不是完全沒有「真實來源」規則，而是**該規則沒有在批次啟動時形成強制性的執行入口**。

### 既有類似問題

Repository 曾處理過「施工階段誤跳至後續階段」問題。當時研究已得到 Stage-Gate + Transition Guard 的最小守門模式：狀態、前置條件與目標工作必須在轉移前確認，前置條件未完成時禁止進入後續階段。

本次問題與該案例同構，但不是同一問題：

```text
施工階段問題：
目前階段 → 是否允許進入下一階段？

本次批次問題：
正式清單 → 目標工作是否真的存在且屬於下一批？
```

因此應重用既有守門思想，而不是重新建立大型系統。

## 四、外部研究／方法比較

本次依既有問題解決流程進行外部比較，不把外部方法直接當成答案。

### 1. Single Source of Truth

成熟工程通常會明確指定某一來源為 authoritative source，而不是讓多份文件各自成為真實來源。例如部分 Git 工作流將主要分支明確定義為特定內容的 source of truth；當其他文件或分支與其不一致時，需回到權威來源判斷。citeturn1search0turn1search7

對本問題的啟示：

```text
正式功能清單 = 功能存在性的權威來源
研究文件 = 研究證據／歷史記錄
交接文件 = 工程狀態與背景
工作指令 = 待驗證輸入
```

不能讓「下一批：A13～A16」這種敘述反過來創造功能存在性。

### 2. AI Agent 的 Repository Read-Before-Act

近期 AI 工程方法開始把 repository 本身作為 agent 的 system of record，要求 agent 在執行修改前先讀取目前目錄、規則、狀態與既有能力，再依目前真實資料執行；如果輸入與既有約束衝突，應停止並要求重新對齊。這類方法特別針對 AI 容易依賴舊上下文、重建不存在內容的問題。citeturn1search2turn1search17

對本問題最直接的對應是：

```text
READ
↓
確認 Source of Truth
↓
確認目標存在
↓
確認目前狀態
↓
才允許 ACT
```

### 3. Structured Issue Intake

GitHub 官方提供 Issue Templates／Issue Forms，目的就是把問題輸入標準化，讓工作在進入後續流程前具有固定欄位與必要資訊。citeturn0search0turn0search1

但本問題不是「問題回報資料不足」，而是「已經開始執行後，工作對象沒有再次對權威來源確認」。

因此 Issue Template 只能改善輸入，不能單獨解決本問題。

### 4. Stage-Gate / Guard

既有 Repository 類似案例已研究過 Stage-Gate + Transition Guard。其核心不是增加文件，而是在動作發生前檢查必要條件；條件不成立時阻止非法轉移。

本次可直接借用相同原理：

```text
目標批次
↓
Source Verification Guard
↓
存在？
屬於正式功能清單？
未完成？
確實是下一個批次？
全部通過
↓
允許研究
```

## 五、候選解法

### 候選 A：只修正本次錯誤

做法：把 A13～A16 改成 B1～B4，之後繼續。

問題：

- 只修事件，不修機制。
- 同類錯誤仍可能發生。
- 沒有處理「為何錯誤工作指令可以覆蓋正式來源」。

判定：不採用。

### 候選 B：加強交接文件

做法：在交接文件寫清楚目前進度與下一批。

問題：

- 仍然增加第二個可能過時的來源。
- 交接資料本身也可能錯誤。
- 不能解決「正式清單與交接文件衝突時誰優先」。

判定：不作為核心解法。

### 候選 C：每批研究前重新閱讀正式功能清單

做法：批次開始前重新讀取正式功能清單，確認目標存在，再開始研究。

優點：

- 成本極低。
- 不需要新系統。
- 直接利用 Repository 現有權威資料。
- 能阻止不存在功能被研究。

不足：

- 如果只寫成「提醒」，仍可能被 AI 忽略。
- 還沒有明確定義「下一批如何計算」。

判定：必要，但不足以成為完整解法。

### 候選 D：Batch Source Verification Gate

在每一批研究開始前，增加最小守門判斷：

```text
1. 讀取目前正式功能清單
2. 確認目標功能存在
3. 名稱／ID 與正式清單一致
4. 確認目前狀態
5. 確認尚未完成
6. 從正式清單計算下一個未完成功能／批次
7. 檢查是否已有研究文件
8. 檢查既有能力映射
9. 若任何項目無法確認 → 停止正式研究
```

優點：

- 同時處理存在性、批次順序與重複研究。
- 與既有 Stage-Gate / Guard 原則一致。
- 不需要新增大型系統。
- 可以直接嵌入既有問題解決／工程運作流程。

不足：

- 初期主要依賴 AI 執行守門步驟。
- 未來若需要機器自動化，可再演化成可執行檢查。

判定：目前最適合。

### 候選 E：建立完整工作清單資料庫／任務調度系統

做法：建立機器可執行的完整任務註冊、排程、依賴與自動阻斷系統。

問題：

- 過度工程化。
- 本次問題尚未證明需要完整調度系統。
- 增加新的資料來源與同步成本。

判定：暫不採用。

## 六、候選解法比較結論

本問題不是選擇「功能最多」的解法，而是尋找能在目前架構中，以最低新增複雜度阻止錯誤再次發生的解法。

```text
A 只修事件             → 不足
B 加強交接文件           → 不足
C 重新讀正式清單         → 必要但不足
D Source Verification Gate → 採用
E 完整任務調度系統       → 過度
```

最終採用方向：

> **D：Batch Source Verification Gate，並以 C 作為其最小實作。**

它不是新系統，也不是第五個方案。

它是一個嵌入既有工程／問題處理流程的執行前守門能力。

## 七、正式處理模型

今後「批次研究」不得直接由上一份文件的「下一批」文字決定。

正確流程：

```text
批次工作開始
↓
讀取正式功能清單
↓
取得目前正式功能全集
↓
取得已完成／已研究狀態
↓
排除不存在、已完成、已研究項目
↓
依正式清單順序尋找下一個未完成項目
↓
形成候選批次
↓
檢查既有研究文件與能力映射
↓
確認無衝突
↓
允許建立研究工作
```

其中最重要的是：

```text
「下一批」是計算結果
不是文件中的永久事實。
```

研究文件可以記錄當時的下一批，但它只能作為歷史狀態，不得凌駕目前正式功能清單。

## 八、Source Verification Gate 最小規格

每次開始新的功能研究批次，至少產生以下判斷：

| 檢查項目 | 必須回答 |
|---|---|
| Formal Source | 哪份文件定義正式功能？ |
| Target ID | 目標 ID 是否存在？ |
| Target Name | 名稱是否與正式清單一致？ |
| Current State | 目前是否已完成／研究？ |
| Batch Position | 是否確實位於下一個未完成位置？ |
| Existing Research | 是否已有對應研究文件？ |
| Existing Capability | 是否已有相關能力？ |
| Conflict | 是否存在交接／舊文件衝突？ |
| Decision | 是否允許開始研究？ |

任何一項無法確認：

```text
禁止建立正式研究結果
↓
進入問題確認／資料確認
```

### 最小阻斷規則

```text
Target 不存在
→ BLOCK

Target 存在但不是目前正式清單的一部分
→ BLOCK

Target 已完成
→ BLOCK / 尋找下一個未完成項目

Target 已研究
→ BLOCK / 檢查是否需要重新研究

交接資料與正式清單衝突
→ 正式清單優先；記錄衝突

正式清單本身無法確認
→ BLOCK
```

## 十一、為什麼不把「正式功能清單」變成新的大型資料庫

目前沒有必要。

正式功能清單本身已存在，而且目前規模很小。真正缺的是：

```text
使用規則
```

而不是：

```text
儲存系統
```

在目前階段建立資料庫、任務引擎或完整工作流平台，只會增加新的同步問題。

如果未來功能規模大到人工／AI 無法可靠從正式清單計算批次，再由真實工作問題驅動新的系統需求。

## 十二、問題根因

### 直接原因

AI 使用錯誤的「下一批」敘述。

### 流程原因

批次開始時沒有強制執行 Source Verification。

### 資料原因

「下一批」是文字敘述，而不是從正式功能清單與研究狀態推導的結果。

### 交接原因

交接資料／歷史文件與正式功能清單沒有被明確區分為不同權威層級。

### 系統性原因

Repository 已經有「真實來源優先」原則，但目前沒有把它轉換成每次批次執行前的最小 Guard。

所以真正缺口是：

> **規則已存在，執行入口不足。**

---

## 十三、最終處置

### 採用

1. 建立 Batch Source Verification Gate 概念。
2. 將「正式功能清單」定義為功能存在性的權威來源。
3. 「下一批」改為由正式清單＋目前研究狀態推導。
4. 批次開始前先驗證 Target。
5. 發現不存在／衝突／無法確認時立即阻斷。
6. 將交接資料與研究文件中的「下一批」視為歷史／工作提示，不視為功能存在性的來源。
7. 將本次錯誤保留為問題案例，供未來回溯。

### 不採用

- 新增大型任務調度系統。
- 新增第五方案。
- 建立獨立批次管理資料庫。
- 讓交接文件成為正式功能來源。
- 修改舊 A9～A12 文件以掩蓋歷史錯誤。

## 十六、核心結論

本次問題真正需要修正的不是「A13～A16 寫錯」，而是：

> **任何批次工作都不得由上一份文件告訴 AI「下一個是誰」；必須回到正式來源重新確認，再計算目前真正可執行的下一批。**

因此最小且適合目前 Ai-knowledge 的解法為：

```text
正式功能清單
      ↓
Source Verification
      ↓
Target Exists？
      ↓
Current / Unfinished？
      ↓
Next Batch Position？
      ↓
Existing Research Check
      ↓
允許研究
```

這就是本次問題處理的採用解法。
