# 問題解決：施工階段誤跳至⑨之最小守門能力驗證 v1.0

## 狀態
【問題解決流程執行中；已完成外部方法比較與最小案例實測；暫不建立新統御系統】

## 一、問題

### 1. 已觀察事件

施工主線已明確定義為：

```text
① 交接／工作狀態
↓
② 新系統規格
↓
③ 共同資料語義
↓
④ 狀態／版本／關係
↓
⑤ 現行格式唯一性
↓
⑥ 三方案資料／責任接口
↓
⑦ 跨系統長流程實測
↓
⑧ 待辦工作記憶／統御能力實例驗證
↓
⑨ 圖書館式知識管理
↓
⑩ 知識書原子化規格
↓
⑪ 實際驗證
```

先前已判定：

```text
① 完成
②～⑦ 尚未完成整體驗收
⑧ 尚未完成實例驗證
```

因此⑨尚未解鎖。

但實際執行時曾直接進入⑨相關規劃，形成「未完成前置階段卻開始後續階段」的施工順序錯誤。

### 2. 問題定義

> 在已存在明確施工主線、前置依賴與部分完成狀態的情況下，AI 未在執行前重新檢查當前階段與前置條件，導致提前進入尚未解鎖的後續階段。

這不是單純文件缺失問題，而是「施工狀態 → 前置條件 → 可執行動作」之間缺少強制守門判斷。

---

## 二、問題價值確認

本問題值得處理，原因：

1. 會直接造成施工順序錯誤。
2. 會產生返工與架構污染。
3. 未來新的無歷史記憶 AI 也可能重犯。
4. 僅依賴模型記憶「①～⑧後才能⑨」不可靠。
5. 這正是目前⑧「待辦工作記憶／統御能力實例驗證」需要驗證的真實案例。

---

## 三、現有能力盤點

### 已存在能力

- 施工主線①～⑪。
- 交接資料。
- 待辦資料。
- 問題解決與新系統建立流程。
- 搜尋研究方案 v2.0。
- 三方案及三核心系統的責任邊界。
- 「文件存在 ≠ 階段完成」的既有判斷原則。

### 現有能力缺口

目前資料能描述施工順序，但尚未形成足夠強制性的：

```text
目前階段
＋
前置條件
＋
完成 Gate
＋
Locked Stage
＋
允許動作
＋
禁止動作
```

因此目前屬於「知道順序」，但還不能可靠地「守住順序」。

## 四、既有搜尋研究與外部方法比較

本次依既有「搜尋研究方案 v2.0」與「問題解決與新系統建立流程」進行研究，不另建立搜尋規則。

外部研究顯示兩種成熟做法與本問題高度相關：

### A. Stage-Gate／Phase-Gate

成熟專案管理方法把工作切成階段，階段之間設置 Gate；下一階段必須先滿足預先定義的交付物與判定條件。Gate 可以產生繼續、暫停、重工或停止等結果。citeturn2search1turn2search2turn2search39

其中重要特徵不是「有順序表」，而是：

```text
Stage
↓
Exit Criteria
↓
Gate Review
↓
是否允許進入下一 Stage
```

### B. State Machine Guard

狀態機中的 Guard Condition 是在狀態轉移前檢查的條件；條件不成立時，轉移不得發生。IBM 與多個狀態機實作文件均將 Guard 定義為轉移發生前的條件判斷。citeturn2search7turn2search13

這與本問題的必要能力直接對應：

```text
目前狀態 = ⑧未完成
事件 = 嘗試進入⑨
Guard = ⑧完成？
結果 = False
→ 阻止轉移
```

### 外部方法結論

目前問題不需要立即建立完整「統御系統」。

最小可行能力可以先採用：

> **Stage Gate + Transition Guard 的施工守門模式。**

也就是把「施工順序」從單純資訊提升為「帶有前置條件的狀態轉移規則」。

## 五、候選解法比較

| 候選 | 方法 | 優點 | 缺點 | 本問題適用性 |
|---|---|---|---|---|
| A | 繼續依賴 AI 記憶順序 | 零建構成本 | 容易再次跳階 | 不足 |
| B | 強化待辦清單 | 可保留狀態與依賴 | 若沒有轉移守門，仍可能跳階 | 部分可用 |
| C | Stage-Gate + Guard 最小流程 | 可在執行前阻止非法階段轉移；複雜度低 | 尚需在實際案例持續驗證 | 採用候選 |
| D | 完整統御／Agent Planner | 能處理更廣泛規劃 | 過度建構，尚未證明必要 | 暫緩 |

目前採用 C 作為最小候選能力，不建立第四方案，也不建立新的大型統御系統。

## 六、最小守門能力

每次準備執行施工工作前，先執行以下判斷：

```text
1. 目前施工階段？
2. 目標工作屬於哪一階段？
3. 目標階段的前置階段有哪些？
4. 前置階段是否全部達到完成條件？
5. 目標階段是否已解鎖？
6. 該工作是否屬於目前允許範圍？
7. 若不允許，應返回哪個未完成階段？
```

最小轉移規則：

```text
若 Previous Stage 未完成
→ Next Stage = LOCKED
→ 不得執行該 Stage 的正式建構工作
→ 可以做的工作只能是：
   - 補足前置階段
   - 驗收前置階段
   - 修復阻斷問題
   - 建立不會啟動後續階段的研究準備資料
```

特別區分：

```text
研究準備資料 ≠ 正式進入階段
```

## 七、最小實測：使用本次真實錯誤

### 輸入狀態

```text
施工主線：①→②→③→④→⑤→⑥→⑦→⑧→⑨→⑩→⑪

目前：①完成；②～⑦未完整驗收；⑧未完成
目標：建立⑨圖書館式知識管理
```

### 守門判斷

```text
目標階段 = ⑨
前置階段 = ①～⑧
⑧ = 未完成

因此：
⑨ = LOCKED
```

### 實測結果

正確行為應為：

```text
拒絕正式進入⑨
↓
返回目前未完成的前置施工
↓
優先處理⑧
↓
將本次錯誤作為⑧的統御能力驗證案例
```

這個判斷不需要完整統御系統即可成立。

因此本次案例證明：

> **最小 Stage-Gate + Guard 模式足以識別本次錯誤。**

暫採用「施工階段守門」作為現有問題解決流程中的最小能力，而非建立新系統。

### 暫不採用

## 十、下一個實際動作

本問題已從「發現錯誤」進入「最小解法實測」。

下一步不是建立⑨，而是繼續⑧的實例驗證：

```text
本次錯誤案例
↓
施工狀態判斷
↓
前置條件檢查
↓
Gate 判定
↓
Lock / Unlock
↓
選擇允許的下一工作
↓
再次檢驗 AI 是否仍會跳階
```

如果第二輪、第三輪不同類型案例仍能穩定阻止非法跳階，才考慮把這項能力正式納入「待辦工作記憶／統御能力」的最小規格。

## 十一、成功條件

本能力至少需要通過：

1. 前置階段未完成時，不能進入後續正式階段。
2. 文件存在但未驗收時，不能視為階段完成。
3. 研究準備資料存在時，不能誤判為正式階段已啟動。
4. 發現錯誤後能返回正確的未完成階段。
5. 下一步必須從「目前允許工作」中選擇，而非從完整路線任意選擇。
6. 新 AI 無歷史記憶重新讀取施工狀態後，仍能得到相同的 Lock / Unlock 判斷。
