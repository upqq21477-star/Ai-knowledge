## 一、研究範圍

本批次依正式功能清單研究：

```text
C5 既有能力盤點
C6 影響分析
C7 演化必要性判定
C8 候選變更產生
```

前置責任為 C1～C4：

```text
變更訊號 → 變更確認 → 對象識別 → 目標確認
```

本批次不研究 C9～C18，也不提前決定最終版本、相容性、遷移、執行或驗證結果。

## 二、外部研究與交叉比較

### 1. NASA 系統工程／需求變更

NASA 的需求變更流程要求在批准與實施前分析變更對成本、性能、時程、技術設計及風險的影響；其變更分析也會檢查其他系統部分、介面、測試、文件、資源、錯誤風險與關鍵性。這支持 C5、C6 必須先於變更執行。citeturn0search2turn0search4turn0search10

### 2. NASA Decision Analysis

NASA 將決策分析定義為：先明確決策問題與判準，再形成多個候選替代方案，分析技術、成本、時程與不確定性；「不做變更」本身也可以是候選選項。這與 C7 的「是否需要演化」及 C8 的「產生候選變更」應分離相符。citeturn0search0turn0search48

### 3. NASA Configuration Management

NASA 將 Configuration Management 視為維持產品真實基線、控制變更、追蹤變更與避免不良後果的核心實務；配置與分析結果也需要受到版本與基線控制，否則環境或設計變更可能使既有分析失效。這支持 C5 必須盤點目前基線，C6 必須帶有版本／狀態條件。citeturn0search11turn0search6

### 4. IBM Impact Analysis

IBM 的 Impact Analysis 會沿著 configuration item 與關係識別可能受到變更影響的對象，並把影響結果提供給變更授權、排程與實施規劃。這支持本系統使用既有 Relationship，而不是只看單一檔案。citeturn0search1turn0search5turn0search13

## 三、C5 既有能力盤點

### 3.1 責任

C5 負責回答：

> 目前已經有哪些資料、知識、能力、系統、流程或方案可以處理 C4 的 Change Objective？

核心原則：

```text
需求出現 ≠ 新增系統
```

必須先確認既有能力，再決定是否需要擴充、重構、替換或新增。

### 3.2 最小盤點內容

每個候選既有能力至少記錄：

```text
Stable Identity
名稱／Alias
能力目的
輸入
輸出
責任範圍
目前 State
Version
Lifecycle
實際使用證據
驗證狀態
依賴／Relationship
與 Change Objective 的匹配程度
限制／缺口
```

### 3.3 能力判定類型

```text
SUFFICIENT       已足以完成目標
PARTIAL          部分具備，需要補強
OVERLAPPING      有重疊能力，需要界線分析
UNVERIFIED       文件存在但實際能力未確認
INACTIVE         存在但目前不在工作路徑
OBSOLETE         已被新能力取代
MISSING           未找到相關能力
```

UNVERIFIED 不得被當成 SUFFICIENT；文件宣稱不等於實際能力。

### 3.4 與既有系統的關係

C5 本身不是新的「能力搜尋系統」。它應使用現有 Repository 搜尋、資料探索、AI 知識管理、工程運作與方案一共同語義完成盤點。

若現有能力已足夠，應停止新增能力候選並回到正常使用／執行路徑；若只有部分能力，應把真正缺口交給後續 C6～C8。

## 四、C6 影響分析

### 4.1 責任

C6 負責回答：

> 如果針對 C4 的目標進行演化，哪些既有對象、關係、使用方式、驗證資料或歷史基線可能受到影響？

C6 的輸出是「潛在影響範圍」，不是實際結果預測，更不是變更批准。

### 4.2 影響範圍

至少檢查：

```text
直接目標
上游依賴
下游依賴
引用者
使用者／工作流程
介面
資料／知識
State / Version
驗證案例
文件／交接資料
跨方案接口
歷史／追溯鏈
成本／資源
風險／失效模式
```

NASA 的變更分析同樣要求檢查架構、設計、介面、需求、測試、文件、資源、品質、可靠性與錯誤風險，而不是只看變更所在位置。citeturn0search4turn0search10

### 4.3 影響不是確定結果

必須明確區分：

```text
Potential Impact  潛在影響
Actual Outcome    實際結果
```

C6 只能根據目前證據與關係產生前者。實際結果要由後續驗證取得。

### 4.4 最小影響收據

```text
Impact Analysis Receipt
- Change Case
- Baseline
- Affected Object
- Relationship Path
- Impact Type
- Direct / Indirect
- Confidence
- Evidence
- Assumption
- Potential Risk
- Potential Rework
- Verification Case Affected
- Unknown / Unchecked Area
```

## 五、C7 演化必要性判定

### 5.1 責任

C7 負責回答：

> 在目前能力、缺口、影響、成本、風險與證據條件下，是否有充分理由進入演化／變更設計？

這不是「哪個候選最好」的問題。

### 5.2 判定依據

至少考慮：

```text
Change Objective 是否仍成立
Current Gap 是否真實
Evidence 是否足夠
既有能力是否不足
影響是否可接受
不演化的成本／風險
演化的成本／風險
時程／環境條件
替代方案是否存在
不確定性是否足以改變判定
```

NASA 的 Decision Analysis 強調決策應建立在決策判準、替代方案與不確定性分析上；如果額外資訊可能改變決策，應考慮先降低不確定性。citeturn0search0turn0search48

### 5.3 輸出

```text
EVOLUTION-REQUIRED
EVOLUTION-NOT-REQUIRED
DEFER
NEED-MORE-EVIDENCE
OUT-OF-SCOPE
```

其中 `EVOLUTION-REQUIRED` 只代表值得進入 C8，不代表任何候選方案已被採用。

### 5.4 特別停止條件

若 C5 已確認現有能力足夠，通常不應因「想讓系統更漂亮」而進入演化。

若證據不足以確認問題，應停在 NEED-MORE-EVIDENCE，而不是用設計熱情代替證據。

## 六、C8 候選變更產生

### 6.1 責任

C8 將已確認的演化需求轉成一組可比較、可驗證的候選變更。

C8 產生候選，不負責最終採用。

### 6.2 候選類型

依正式功能清單，至少支援：

```text
Add
Correct
Extend
Partial Replace
Replace
Merge
Split
Migrate
```

實際案件也可包含 Keep / No Change 作為比較基準，但不得把它偽裝成「候選變更已執行」。

### 6.3 每個候選至少包含

```text
Candidate ID
Candidate Type
Target Identity
Change Description
Scope
Expected Effect
Required Existing Capability
Dependencies
Assumptions
Risks
Migration Need
Compatibility Concern
Estimated Effort / Cost
Reversibility
Success Criteria
Required Validation
Known Unknowns
```

### 6.4 C8 的邊界

```text
C8：產生候選
C9：版本分析
C10：相容性分析
C11：遷移分析
C12：最小變更執行
C13：實際驗證
C14：採用／暫緩／退回
```

因此 C8 不得直接：

- 修改 Repository
- 宣告候選已採用
- 宣告候選成功
- 自行刪除舊能力
- 繞過 C9～C14

### 方案一

```text

```

不得建立第二套語義模型。

### 方案二

B12、B15、B16 可以提供變更訊號與問題證據；但 B12 的 FAIL 不等於必然需要架構演化。仍需經 C5～C7 判斷。

### 問題解決系統

問題解決系統可以提供已確認問題、外部候選解法與最小實測結果；C5 仍需確認現有能力，C7 仍需判斷是否值得進入方案三演化。

### 方案四

C5～C8 發現單一變更已演變成長期能力整理、重疊、責任重新劃分或系統重構問題時，可產生蒸餾候選，但不得自行跳入方案四執行。

## 九、研究結論

C5～C8 是方案三中「從確認目標到形成候選變更」的核心中段。

```text
C5 防止重複造系統
C6 防止只看局部而忽略依賴
C7 防止收到訊號就修改
C8 防止直接把第一個想法當成正式方案
```

四者不需要建立四個獨立大型系統。最佳結構是共用 Change Case／Evolution Case 工作資料與方案一共同語義，由四個責任節點依序處理。
