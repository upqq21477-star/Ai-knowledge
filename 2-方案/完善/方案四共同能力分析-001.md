# 方案四共同能力分析-001

## 狀態

【第一輪共同能力分析完成；暫不抽出新系統；待影響分析與實際施工驗證】

## 一、目的

承接「方案四系統能力級真實蒸餾案例-001」，進一步判斷既有系統之間出現的相似工作是否真的屬於共同能力。

本文件只做能力層分析，不直接修改舊系統。

## 二、分析對象

本輪以四個既有系統作為第一批樣本：

1. `1-系統/更新監控與觸發系統.md`
2. `1-系統/知識更新與狀態管理系統.md`
3. `1-系統/知識整合系統.md`
4. `1-系統/方案管理系統.md`

## 三、候選共同能力

### C1 變更／影響分析

四個系統都會遇到「某項變化是否影響目前工作」的問題，但目前證據不足以證明它們應由同一個獨立系統統一負責。

目前判定：

`候選共同能力`

理由：

- 更新監控需要判斷事件是否值得進入後續分析。
- 知識更新需要判斷新資訊是否改變目前知識。
- 知識整合需要檢查變更後的依賴、約束與受影響系統。
- 方案管理需要知道重大變更對方案、組合與驗證的影響。

但四者的判斷對象與責任不同，因此不能直接 Merge。

### C2 依賴／關係分析

目前確認存在共同性，但更接近「共用分析能力」而不是獨立業務系統。

不同系統需要知道：

- 誰依賴誰。
- 哪些內容是前置條件。
- 哪些關係會受到變更影響。
- 關係存在是否真的造成實際影響。

目前判定：

`候選共用基礎能力`

暫不建立獨立系統。

### C3 驗證

四個系統都要求實際驗證，但驗證目的不同：

- 更新監控：確認事件分類與觸發是否合理。
- 知識更新：確認目前內容是否應更新。
- 知識整合：確認多項知識組合後仍成立。
- 方案管理：確認整個方案在實際使用中是否可重用。

目前判定：

`不是單一可直接抽離的驗證系統`

較適合保留共同驗證原則與驗收語義，而不是把驗證責任集中到一個新系統。

### C4 回寫

四個系統都可能產生新觀察並回饋，但回寫目的與責任層級不同。

目前判定：

`共同閉環原則，不是立即獨立系統`

## 四、第一輪結論

目前真正值得進一步施工的共同能力只有兩類：

```text
A. 變更影響／遷移分析
B. 關係／依賴分析
```

而：

```text
驗證 → 保留共同驗收原則，不集中責任
回寫 → 保留共同閉環原則，不集中責任
```

## 五、重要邊界

不能因為不同系統都出現以下詞語就判定能力重複：

- 更新
- 影響
- 依賴
- 驗證
- 回寫

必須比較：

```text
輸入
→ 判斷對象
→ 處理邏輯
→ 輸出
→ 使用者
→ 前置條件
→ 後續責任
```

只有核心處理邏輯與責任真正重疊，才進入 Merge / Refactor 候選。

## 六、目前不執行

- 修改既有系統責任。
- 宣稱共同能力已經完成重構。
