## 一、目的

驗證能力蒸餾與系統重構方案是否能處理長期累積問題，同時避免把正常迭代、單次問題或單純文件差異誤判為需要重構的問題。

本案例為條件模擬，不代表方案四已完成實戰驗證。

## 二、案例 A：正常重複但不應融合

假設兩個系統都有相似的資料驗證功能，但：

- 使用情境不同。
- 風險邊界不同。
- 責任歸屬不同。
- 驗證條件不同。

判定：

```text
表面重複
≠ 實質重複
→ Keep
```

PASS。

## 三、案例 B：真正重疊能力

假設兩個系統：

- 輸入相同。
- 輸出相同。
- 觸發相同。
- 責任相同。
- 依賴相同。
- 驗證方式相同。
- 實際用途也相同。

判定：

```text
R3 實質完全重疊
→ 建立融合候選
```

注意：R3 不是自動刪除命令。

PASS。

## 四、案例 C：舊能力已失效

某能力已無實際使用者、無有效依賴、被新能力完整取代，且已有足夠證據。

判定流程：

```text
盤點
→ 使用／依賴確認
→ 替代能力確認
→ 影響分析
→ 可逆性確認
→ Retire 候選
→ 驗證
→ Archive 歷史
```

不得因「看起來沒用」直接刪除。

PASS。

## 五、案例 D：架構侵蝕

假設多輪迭代後出現：

```text
多個系統重複責任
+
永久 Compatibility Layer
+
Hidden Coupling
+
每次變更都需要跨越大量系統
```

此時不是單次迭代問題。

判定：

```text
Architecture Erosion
→ 蒸餾候選
→ 完整影響分析
→ 重構方案
```

PASS。

## 六、案例 E：蒸餾後修正失敗

假設融合兩個能力後，原本兩個獨立使用情境中有一個開始失敗。

不能直接宣稱重構成功。

流程：

```text
重構
↓
驗證 FAIL
↓
診斷
↓
問題確認
↓
問題解決
↓
候選修正
↓
重新驗證
```

如果修正仍失敗：

```text
REDIAGNOSE
```

必要時：

```text
Rollback
或
Restore previous baseline
```

PASS。

## 七、案例 F：蒸餾本身不成立

如果實際分析後發現：

```text
重疊不足
或
證據不足
或
依賴無法確認
或
風險不可接受
```

不得為了完成蒸餾而強行融合。

判定：

```text
RETAIN / DEFER
```

PASS。

## 八、與前三方案的邊界

### 方案二

日常任務使用與驗證。

若一次任務失敗，不直接進方案四。

### 方案三

正常知識／資料演化。

若單次變更失敗，先走問題解決。

### 方案四

長期累積後的結構性問題。

必須有足夠證據證明問題不是單次局部錯誤。

因此：

```text
單次 FAIL
≠ 蒸餾

反覆結構性 FAIL
+
責任／依賴／複雜度持續惡化
→ 蒸餾候選
```

## 九、處置邊界

本方案允許：

```text
Keep
Extend
Refactor
Merge
Split
Replace
Rebuild
Retain
Retire
Archive
```

但所有處置都是候選處置，不等於立即執行。

尤其：

```text
Retire ≠ Delete
Merge ≠ Remove immediately
Rebuild ≠ 必須重建全部
```

真正執行前必須有：

```text
影響分析
↓
責任確認
↓
遷移／回復條件
↓
驗收方法
```

## 十、停止邊界

本模擬通過後，不再增加更多失效模式。

方案四達到本輪最低結構條件後：

```text
停止結構性擴充
↓
最小實作驗收模擬
↓
真實蒸餾案例
↓
實際驗證
```

只有真實案例或驗收發現阻塞性缺口，才重新打開方案四結構。
