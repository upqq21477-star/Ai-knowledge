## 一、案例來源

本案例源自一次工程執行錯誤：

在進行四方案功能逐項研究時，工作指令要求研究「A13–A16」，但重新讀取 Repository 後確認：目前方案一正式功能清單只有 A1–A12，A13–A16 並不存在。

錯誤並不是單純的編號錯誤。

真正問題是：

> AI 在沒有重新確認目前正式資料邊界的情況下，直接依工作指令繼續施工，導致不存在的工作項目被當成正式研究對象。

此類問題如果直接修正當前工作即可結束，仍可能在下一次 AI 接手時再次發生。

因此本案例必須進入「問題處理」流程，而不是只修改當前工作順序。

---

## 二、正確的工程路由

本案例應遵循：

```text
發現異常／錯誤
↓
回報問題
↓
問題確認
↓
問題拆分
↓
既有能力／既有流程盤點
↓
搜尋研究
↓
外部方法／工具／案例比較
↓
建立候選解法
↓
分析候選解法是否適合 Ai-knowledge
↓
最小模擬驗證
↓
判定
├─ 現有能力可處理
│   ↓
│  採用／完善既有流程
│
├─ 現有能力不足，但小幅流程補強即可
│   ↓
│  建立流程／守門能力
│
└─ 確認需要新系統能力
    ↓
   進入問題解決與新系統建立流程
↓
回饋真正責任層
↓
回歸工程運作與持續改進方案
↓
建立回歸測試
```

因此，「發現錯誤」與「處理錯誤」不是同一層工作。

---

## 三、為什麼不能直接修正

若只做：

```text
A13–A16 錯誤
↓
改成 B1–B4
↓
繼續研究
```

只能修復本次事件的表面結果，不能回答：

1. 為什麼 AI 沒有先讀正式功能清單？
2. 為什麼工作指令可以覆蓋 Repository 現況？
3. 為什麼不存在的功能沒有被阻擋？
4. 為什麼沒有批次啟動前的邊界確認？
5. 下一次遇到類似衝突時，如何保證進入問題處理？

因此本案例的工程目標不是「修正 A13–A16」，而是：

> 建立一個能把「發現錯誤 → 回報 → 問題化 → 研究比較 → 適用性判斷 → 驗證 → 回饋」完整閉環的流程。

---

## 四、問題拆分

### P1：輸入來源衝突

工作指令與 Repository 正式功能清單不一致。

### P2：來源優先級未在工作入口被強制確認

AI 使用了工作指令，沒有先確認 Repository 正式結構。

### P3：批次邊界缺少守門

沒有在研究批次開始前確認：

- 功能存在。
- 名稱正確。
- 尚未研究。
- 位於正式清單。
- 是目前下一個未完成批次。

### P4：錯誤發現後沒有立即轉入問題處理

如果只修正當前工作，不會形成可重複使用的工程改進。

### P5：問題處理結果需要回饋工程運作層

問題處理完成後，必須留下：

- 問題來源。
- 根因。
- 解法。
- 驗證結果。
- 回歸案例。
- 後續工作。

## 五、既有系統盤點

目前 Repository 已存在可承接此工作的能力：

### 1. 問題解決系統

已定義：

```text
發現問題
→ 確認問題值得處理
→ 使用既有搜尋方案
→ 外部方法／工具／案例比較
→ 建立候選解法
→ 最小實測
→ 比較實測結果
→ 採用／暫緩／拒絕
→ 回饋相關知識／系統／方案
```

因此本案例不需要另建一套問題研究引擎。

### 2. 問題解決與新系統建立流程

既有流程已明確要求：

```text
問題
→ 問題確認
→ 既有搜尋研究
→ 外部方法／工具／案例比較
→ 候選解法
→ 最小實測
→ 判定
→ 必要時進入新系統建立
→ 回饋
```

而且明確規定：

> 先解問題，不先指定系統。

因此本案例符合既有流程，不應直接建立大型新系統。

### 3. 工程運作與持續改進方案

該方案已定義「實際工作 → 觀察 → 問題／缺口確認 → 判斷責任層 → 送回真正負責的知識／系統／方案 → 處理 → 驗證 → 回寫工程狀態」的改進回流流程。

因此本案例應成為該流程的具體驗證案例，而不是新增第五個正式方案。

## 六、外部方法比對

本次比對不是尋找一個可以直接複製的「最佳流程」，而是確認本系統是否遺漏成熟工程實踐中的必要環節。

### 1. ITIL Problem Management

ITIL Problem Management 的核心目的包含識別事件的實際或潛在原因，以及管理 workaround 與 known error，重點不是只處理單一事件，而是降低事件再次發生的可能性與影響。citeturn0search10

對本系統的可用原則：

```text
事件／錯誤
→ 問題化
→ 原因分析
→ 處理
→ 防止重複發生
```

適合採用，但不直接照搬 ITIL 的完整 ITSM 結構，因為 Ai-knowledge 並不是傳統 IT 服務台。

### 2. Google SRE Postmortem

Google SRE 將事故記錄、影響、根因與後續防止再發生的行動放在同一個學習閉環中，並強調處理根因，而不只是恢復表面正常狀態。citeturn0search0turn0search1

對本系統最有價值的是：

```text
發現
→ 記錄
→ 根因分析
→ 修正
→ 預防再發
→ 行動項目回到工程工作池
```

本系統可採用這個閉環思想，但不需要建立完整事故管理平台。

### 3. Google SRE 的系統性問題分析

Google SRE 的 postmortem 分析會把不同事件的根因分類並進行趨勢分析，以發現個別事件背後的系統性問題。citeturn0search3

這與本系統的「單一錯誤 → 判斷是否為流程／系統性缺口 → 必要時進入更高層重新評估」高度相容。

### 4. NIST Change Control

NIST 的組態變更控制要求對變更進行提出、審查、核准／拒絕、實施、記錄、測試與後續監控。citeturn0search12

本系統不需要照搬完整變更管理制度，但應保留：

```text
變更提案
→ 理由
→ 影響
→ 實施
→ 驗證
→ 記錄
```

尤其適合用來約束「問題處理完成後到底改了什麼」。

## 七、外部方法與本系統的適用性判斷

| 外部方法 | 可吸收原則 | 不直接採用部分 | 適用判斷 |
|---|---|---|---|
| ITIL Problem Management | 問題化、根因、known error、降低再發 | 完整 ITSM 管理體系 | 適合吸收核心原則 |
| Google SRE Postmortem | 問題記錄、根因、後續行動、回饋 | 大型事故管理文化 | 高度適合 |
| SRE 趨勢分析 | 從單點事件找系統性問題 | 大型營運分析平台 | 適合保留輕量版 |
| NIST Change Control | 變更理由、影響、驗證、記錄 | 完整合規流程 | 適合吸收變更驗證原則 |

結論不是建立一個 ITIL/SRE/NIST 混合系統。

而是提取共同且與本系統直接相關的工程原則。

## 八、本系統應採用的最小閉環

經過既有架構與外部方法比對後，本系統的最小問題處理閉環應為：

```text
① 發現
↓
② 回報
↓
③ 問題確認
↓
④ 問題拆分
↓
⑤ 既有能力盤點
↓
⑥ 搜尋／研究
↓
⑦ 外部方法／工具／案例比對
↓
⑧ 候選解法
↓
⑨ 本系統適用性分析
↓
⑩ 最小模擬／實測
↓
⑪ 判定
↓
⑫ 修正／採用／暫緩／拒絕
↓
⑬ 回歸驗證
↓
⑭ 回饋知識／系統／方案
↓
⑮ 回寫工程狀態
```

這個閉環比單純的：

```text
發現問題 → 解決
```

更重要，因為它把「如何避免同一類問題再次出現」納入工程流程。

## 九、最優解的定義

本案例不採用「功能最多」或「最先進」作為最優解。

目前適合 Ai-knowledge 的解法必須同時滿足：

1. 能捕捉錯誤並形成正式問題。
2. 能阻止錯誤直接繼續污染正式知識。
3. 能利用既有問題解決流程。
4. 能搜尋與比較外部方法。
5. 能分析外部方法是否適合本系統。
6. 能用最小成本驗證。
7. 能把結果回饋真正責任層。
8. 能形成回歸測試，防止同類錯誤再次發生。
9. 不因單一案例建立不必要的大型系統。

因此目前候選最優解不是「新增一個大型問題管理系統」，而是：

> **將「錯誤發現 → 問題回報 → 問題處理 → 研究比對 → 適用性判斷 → 最小驗證 → 回歸驗證 → 回饋工程」正式接入既有工程運作與問題解決流程。**

## 十、案例的具體處理結果

對 A13–A16 案例：

### 已確認

- A13–A16 不是目前正式功能。
- 不應繼續建立 A13–A16 研究結果。
- B1–B4 才是目前已確認的下一批正式功能。
- 原先錯誤研究指令必須視為問題輸入，而不是正式知識。

### 問題層處理

建立「批次來源驗證守門」能力需求：

```text
每次開始批次工作
↓
讀取正式功能清單
↓
確認功能存在
↓
確認名稱一致
↓
確認尚未完成
↓
確認既有研究／能力映射
↓
確認沒有重複／衝突
↓
確認確實為下一個未完成批次
↓
才允許正式研究
```

### 重要限制

這裡目前只能提出「需要此守門能力」的結論。

在完成模擬案例之前，不應宣稱它已經能可靠阻止所有同類錯誤。

## 十一、回歸測試案例

### Case 1：錯誤指令要求研究不存在功能

輸入：

```text
研究 A13–A16
```

預期：

```text
阻止正式研究
→ 重新讀取正式功能清單
→ 發現不存在
→ 建立問題回報
```

### Case 2：交接文件與 Repository 衝突

輸入：

```text
交接文件說下一批是 A13–A16
Repository 顯示下一批不是 A13–A16
```

預期：

```text
Repository 正式結構優先
→ 不執行 A13–A16
→ 建立問題／來源衝突事件
```

### Case 3：功能存在但已研究完成

預期：

```text
阻止重複研究
→ 檢查既有研究文件
→ 判斷是否進入更新／重新驗證
```

### Case 4：功能存在但責任已改變

預期：

```text
不能直接沿用舊研究
→ 進入變更／影響分析
→ 判斷是否需要重新研究
```

### Case 5：問題處理本身失敗

預期：

```text
不直接擴大系統
→ 回到問題定義／搜尋／候選／測試
→ 找出失敗原因
→ 必要時提高處理層級
```

## 十二、工程定位

本案例最後應落在：

```text
工程運作與持續改進方案
        │
        ├─ 發現問題
        │
        ├─ 問題回報
        │
        └─ 問題工作項目
                ↓
        問題解決系統
                ↓
        搜尋／外部比較／候選／驗證
                ↓
        必要時進入新系統建立
                ↓
        回饋真正責任層
                ↓
        工程運作方案更新狀態
```

因此：

> 「問題處理」不是第五個方案。
>
> 「問題處理」是工程運作中遇到異常後，進入既有問題解決能力的標準路由。

## 十三、目前下一步

在不修改舊文件的前提下，下一步只做一件事：

> **對本案例進行問題處理閉環的模擬驗證。**

模擬必須驗證：

1. 能否正確從錯誤發現轉入問題回報。
2. 能否阻止不存在功能進入正式研究。
3. 能否完成問題拆分。
4. 能否調用既有問題解決流程。

6. 能否分析候選解法是否適合本系統。
7. 能否產生最小可驗證處理方案。
8. 能否建立回歸案例。
9. 能否把結果回寫工程運作狀態。

在這輪模擬通過前，不將「批次來源驗證守門」宣稱為已完成能力。
