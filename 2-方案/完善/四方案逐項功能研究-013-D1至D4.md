## 三、D1 蒸餾案件建立

### 功能目的

將一個經確認具有長期結構性問題可能性的訊號，轉換成一個可追蹤、可限定範圍的 Distillation Case（蒸餾案件）。

### 最小輸入

```text
Trigger / 蒸餾訊號
Structural Problem Candidate / 結構問題候選
來源證據
初步涉及對象
```

### 最小輸出

```text
Case Identity
開始原因
初步結構問題
初步範圍
不處理範圍
目前證據
未知事項
關聯來源／版本
```

### 邊界

D1 建立案件，不決定是否 Merge、Retire、Replace 或 Refactor。

D1 不取代方案三 C1～C4。C17 只負責把超出正常單次變更範圍的候選轉交方案四；方案四仍必須重新建立自己的案件、範圍、能力盤點與證據確認。既有接口研究已明確定義此邊界。fileciteturn166file1L15-L25

### 外部研究對照

NASA Technical Planning 強調在工程開始前先明確技術工作範圍、角色、責任、約束、工作流程與成功條件；重大變化也應重新分析其對既有基準與計畫的影響。citeturn0search0turn0search4

ADR（Architecture Decision Record）實務也把 Context、Decision、Consequences 與狀態作為可追溯決策的基本結構，並強調決策記錄應保持獨立、可追溯。citeturn1search0turn1search2

### 研究結論

D1 必要，但應保持輕量。第一階段使用 Markdown + Git 即可，不需要建立大型案件資料庫。

## 四、D2 範圍界定

### 功能目的

把蒸餾案件從「可能涉及整體 Repository」限制為明確的分析邊界。

### 最小輸入

```text
D1 Case
涉及對象
問題證據
目前未知
```

### 最小輸出

```text
In Scope
Out of Scope
Affected Object Candidates
Time / Version Boundary
Evidence Boundary
Analysis Questions
Stop Conditions
```

### 核心規則

```text
蒸餾案件成立
≠
掃描整個 Repository
```

應優先從已知能力、依賴、關係與證據向外擴張；只有存在證據支持時才擴大範圍。

NASA Technical Planning 同樣強調先理解並規劃技術工作的 scope、interfaces、resources、constraints 與 success criteria，而不是讓工作範圍無限制擴張。citeturn0search0turn0search36

### 研究結論

D2 是蒸餾安全性的第一個實質控制點。沒有範圍就不能可靠進入 D3，否則能力盤點容易變成無邊界 Repository 掃描。

## 五、D3 能力盤點

### 功能目的

在任何重構候選形成前，建立「目前有哪些實際能力」的可追溯基準。

### 盤點對象

```text
Data / 資料
Knowledge / 知識
Capability / 能力
System / 系統
Scheme / 方案
Relationship / 關係
Dependency / 依賴
```

### 最小欄位

```text
Stable Identity
Name / Alias
Purpose
Input
Output
Trigger
Owner / Responsibility
Dependencies
Consumers / Users
Evidence of Use
Validation State
Lifecycle
Version
Source
```

但這些欄位是盤點所需的最小理解集合，不代表必須立即固化成永久 Schema。

既有方案四正式文件已明確指出「檔案存在只能證明檔案存在，不能證明能力正在使用」。fileciteturn168file0L2-L2

第一個真實案例也採用四個既有系統做能力拆解，分別辨識變更入口、更新決策、知識整合與方案組合等責任，而沒有因名稱相近就直接 Merge。fileciteturn173file0L2-L2

### 外部研究對照

NASA Configuration Management 強調必須知道產品／系統的真實 configuration，控制變更並保持產品資訊與實際產品一致；這與 D3 的「實際能力基準」高度相關。citeturn0search7turn0search10

### 研究結論

D3 必要，且是 D7 重疊分析、D8 責任分析、D9 關係分析的前置資料來源。沒有 D3，後續蒸餾只能建立在文件猜測上。

## 六、D4 實際使用／依賴確認

### 功能目的

驗證 D3 所盤點的能力是否真的被使用、被依賴、被其他工作流程引用，而不是只存在於文件中。

### 最小證據類型

```text
實際工作紀錄
實際輸入／輸出
其他文件引用
上下游接口
驗證案例
Commit / Version evidence
使用者／AI 工作紀錄
實際依賴關係
```

### 必須區分

```text
文件宣稱
≠
文件存在
≠
歷史曾使用
≠
目前仍使用
≠
存在實際依賴
```

D4 的結果至少應能分類：

```text
USED
DEPENDENCY-CONFIRMED
HISTORICAL-ONLY
UNUSED-EVIDENCE
UNKNOWN
```

UNKNOWN 不得轉成 USED。

NASA 的 Configuration Management 與 Requirements Management 都強調以受控資料、狀態紀錄、變更歷史與驗證／稽核維持可追溯性，而非只依賴文件宣稱。citeturn0search7turn0search4

### 研究結論

D4 是 D3 與後續重構決策之間的證據閘門。它不要求一定找到使用證據；找不到時應保存 UNKNOWN，而不是推論「沒有人使用」。

## 七、D1～D4 的責任鏈

```text
蒸餾訊號
↓
D1 建立可追蹤案件
↓
D2 限定分析範圍
↓
D3 盤點範圍內實際能力
↓
D4 確認使用／依賴證據
↓
D5 證據／驗證狀態確認
↓
D6 能力語義分析
```

因此 D1～D4 不是四個獨立小工具，而是一條前置證據建立鏈。

## 八、與既有方案四案例的關係

既有共同能力分析已確認「變更影響／遷移分析」與「關係／依賴分析」可以作為候選共用能力，但目前證據不足以支持立即建立中央系統；應由自然工作觀察實際重複成本。fileciteturn176file0L2-L2

這個案例可以作為 D1～D4 的實際素材，但不能反過來把案例既有結論當成 D1～D4 的正式研究驗收。

## 九、失敗與阻斷規則

以下情況應 BLOCK：

1. 沒有蒸餾訊號卻直接建立案件。
2. D1 尚未建立就開始無邊界 Repository 掃描。
3. D2 沒有 In Scope / Out of Scope。
4. D3 把文件列表直接當能力列表。
5. D4 把文件存在直接當使用證據。
6. UNKNOWN 被轉成 USED。
7. 收到 C17 後跳過 D1～D4。
8. D1～D4 直接產生 Merge / Retire / Replace 決策。

既有模擬驗證已測試「每個小問題都建立蒸餾案件」「C17 直接決定 Merge」「C17 跳過 D1-D5」等錯誤路徑並要求阻止。fileciteturn167file4L55-L64

## 十、與外部成熟方法的綜合結論

外部資料沒有顯示需要建立一個龐大的「蒸餾平台」。反而支持幾個穩定原則：

```text
先定義工作範圍
→ 明確角色與責任
→ 受控地建立現況基準
→ 保存版本與變更證據
→ 保持決策可追溯
→ 再進入後續分析與處置
```

NASA 的 systems engineering / configuration management 對 scope、baseline、change control、traceability 與 verification 的要求，和 ADR 對 context、decision、consequence、status 的做法，可以作為方案四 D1～D4 的外部參考；但 Repository 的四方案責任邊界仍以本專案自身正式定義為準。citeturn0search0turn0search7turn1search0turn1search13

## 十一、研究結論

```text
D1 必要：建立蒸餾案件與追蹤身份
D2 必要：限制分析範圍
D3 必要：建立實際能力基準
D4 必要：確認實際使用／依賴證據
```

四者均屬方案四核心前置責任，沒有發現可刪除或合併成單一功能的充分理由。
