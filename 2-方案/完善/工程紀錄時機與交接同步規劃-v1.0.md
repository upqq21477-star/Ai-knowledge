# 工程紀錄時機與交接同步規劃 v1.0

> 建立日期：2026-09-17
> 狀態：方案規劃建立
> 目的：把「何時應建立工程紀錄、何時更新待辦、何時更新交接資料」從 AI 臨時判斷，提升為工程運作與持續改進方案的正式運作規則。

## 一、建立原因

近期實際工程運作發現，Repository 已能建立方案、系統、驗收案例與工程狀態，但工作容易退化成「做一個文件、驗收一個文件、再做下一個文件」。

真正需要管理的是工程階段與狀態，而不是讓每一個工作動作都產生獨立驗收案例。

本規劃因此先建立「紀錄時機」與「交接同步」規則，再決定如何修改工程運作方案。

## 二、核心原則

1. 討論不是自動等於紀錄。
2. 討論形成可執行的正式結論後，必須先形成方案規劃或明確的工程工作規劃。
3. 方案規劃形成後，必須建立對應的工程狀態。
4. 可執行工作必須進入待辦／工作池。
5. 重大工程狀態形成後，必須更新交接資料，使新 AI 不需要依賴原對話才能恢復。
6. 系統或方案完成建立、只剩整體實際驗收時，必須進行一次階段紀錄並更新交接資料。
7. 系統／方案正式實際驗收完成後，必須再次記錄結果、更新狀態、待辦與交接。
8. 日常小變更不應被迫產生新的驗收案例；只有具備獨立驗證目的的事項才建立驗收案例。
9. 工程狀態、待辦、方案、驗收紀錄、交接資料各自負責不同資訊，不建立重複的第二套資料。
10. 任何重大狀態紀錄都必須能追溯到方案、工作項目或驗證結果。

## 三、正式紀錄節點

### R0：討論形成正式工程結論

觸發條件：

- 問題已被確認；且
- 已形成下一步可執行方向；且
- 不再只是候選想法。

動作：

```text
正式結論
↓
建立／更新方案規劃
↓
建立工程狀態
↓
加入待辦／工作池
↓
必要時更新交接
```

若只是研究、比較或尚未形成決策，不強制建立正式工程狀態。

### R1：方案規劃完成，準備施工

至少記錄：

- 目的
- 問題
- 範圍
- 責任
- 主要工作
- 依賴
- 驗證方式
- 尚未完成事項
- 下一步

工程狀態至少由「已規劃」進入「等待施工」或等價狀態。

### R2：正式開始施工

當實際開始建立／修改系統、方案或正式資料時，工程狀態進入「施工中」。

不要求每次小修改都更新交接；若工作已跨越 AI、長時間中斷或重大結構變更，應更新工程狀態與交接。

### R3：建立完成，只剩整體實際驗收

這是強制紀錄節點。

判定條件：

```text
方案／系統／能力的預定建立工作已完成
↓
文件／實作已具備可驗收條件
↓
只剩整體實際工作驗收
```

動作：

```text
建立階段紀錄
↓
狀態 = 已完成未驗收／已驗收未實戰等適用狀態
↓
建立／更新實際驗收待辦
↓
更新交接資料
```

目的：即使原 AI 在此時中斷，新 AI 也能直接知道「東西已經建好，只差什麼」。

### R4：正式實際驗收完成

記錄：

- 預期
- 實際觸發
- 實際執行
- 實際結果
- 差異
- PASS／PARTIAL PASS／FAIL
- 未完成原因
- 後續工作

並同步：

```text
驗收結果
↓
工程狀態
↓
待辦
↓
交接
↓
必要時形成新基準
```

### R5：重大架構／方案狀態改變

即使尚未完成，也應觸發階段紀錄與交接更新，例如：

- 方案重製
- 責任重新分配
- 系統 Merge／Split／Replace／Rebuild
- 新增正式方案
- 核心資料格式重大變更
- 重要系統從施工中進入待驗收
- 驗收結果導致整體路線改變
- 發現必須重新評估整體架構

## 四、交接更新規則

交接資料不是工程日誌，也不是每次小修改都建立新版本。

### 一般工作

```text
小變更
→ 工程狀態／待辦／檔案索引
```

### 重大階段

```text
方案規劃完成
→ 視交接需求更新

系統建立完成、只剩整體驗收
→ 必須更新

正式驗收完成／新基準建立
→ 必須更新

重大架構變更
→ 必須更新
```

交接資料應保存「下一個 AI 接手所需的最小完整狀態」，而非複製所有工程文件。

## 五、方案、狀態、待辦、驗收、交接的責任

| 資料 | 主要回答 | 不負責 |
|---|---|---|
| 方案規劃 | 要解決什麼、怎麼做 | 即時施工日誌 |
| 工程狀態 | 現在做到哪裡 | 完整歷史 |
| 待辦／工作池 | 接下來做什麼 | 定義方案本身 |
| 驗收紀錄 | 實際結果如何 | 取代目前狀態 |
| 交接資料 | 新 AI 如何快速恢復 | 保存所有歷史細節 |
| 檔案索引 | 最近哪些檔案發生變化 | 管理工程狀態 |

## 六、驗收案例的建立條件

不得因為「做了一份文件」就建立驗收案例。

只有以下情況才建立獨立驗收紀錄：

1. 有明確的驗收目標。
2. 有可重現的驗收方法。
3. 驗收結果會改變工程狀態、責任、設計或後續工作。
4. 該驗收結果具有獨立追溯價值。

一般自然工作應優先使用工程狀態、待辦與階段紀錄，不應文件化過度。

## 七、與工程運作方案的關係

本文件目前是「規劃」，不是第五方案，也不是獨立正式系統。

後續應將已驗證的規則回寫至：

`2-方案/工程運作與持續改進方案-v1.0.md`

回寫前必須先檢查：

- 是否與現有工程狀態模型重複。
- 是否與 AI 交接責任重複。
- 是否需要新增正式紀錄事件類型。
- 是否需要調整工程工作項目欄位。
- 是否需要新增交接觸發條件。
- 是否會與方案 3／方案 4 的驗收與回寫責任衝突。

## 八、本規劃的第一輪驗證方式

不立即建立大型紀錄系統。

先用目前工程自然工作驗證以下情境：

1. 討論形成正式結論後是否能建立方案規劃。
2. 方案規劃後是否能自然形成工程狀態與待辦。
3. 系統建立完成、只剩整體驗收時是否能形成階段紀錄。
4. 重大狀態改變時是否能更新交接。
5. 新 AI 是否能從交接快速恢復，而不需要重新閱讀全部歷史。
6. 一般小工作是否能避免產生不必要的驗收文件。

## 九、目前狀態

```text
本規劃：已建立
工程運作方案回寫：待驗證後處理
狀態紀錄規則：第一版
交接觸發規則：第一版
驗收案例建立條件：第一版
自然工作驗證：待執行
正式納入工程運作方案：待驗證
```

## 十、禁止事項

- 不因每個文件建立就建立驗收案例。
- 不建立第三個「目前狀態」入口。
- 不把交接資料變成完整工程資料庫。
- 不讓待辦清單取代工程狀態。
- 不讓工程狀態取代方案規劃。
- 不讓驗收紀錄取代交接。
- 不因本規劃成立就立即修改大量舊文件。
- 不在驗證前凍結完整 JSON／YAML Schema。

## 十一、下一步

```text
本規劃建立
↓
建立狀態紀錄
↓
排入待辦
↓
更新交接資料
↓
以自然工程工作驗證
↓
回寫工程運作方案
↓
再次驗證
↓
形成新基準
```


## 十二、交接推進與退出閉環

原規劃解決「何時建立／更新交接」，本節補足「何時退出交接」。

交接建立後必須綁定一個施工游標，至少能回答：
```
這份交接負責什麼？
目前做到哪裡？
還剩什麼？
完成後下一個入口是什麼？
```

進度推進：
```
施工
→ 更新完成／未完成
→ 驗收
→ 更新交接游標
```

退出觸發：
```
主要待辦接近完成（預設約 2 項）
或
該階段已形成新基準
```

退出驗收：
```
未完成事項清零／轉移
→ 新入口確認
→ 引用／依賴掃描
→ 歷史價值判定
→ 必要資訊蒸餾
→ HANDOFF-RETIRED
→ 刪除
```

因此交接不再是「永久保存的施工文件」，而是具有建立、推進、驗收、退出的短生命週期工作資產。

本規劃仍不建立新的總控系統；直接使用現有工程狀態、待辦、驗收與 Handoff Skill。
