# A1 資料身份／識別 Identity

## 1. 原問題

回答：「這個資料／知識／能力到底是哪一個對象？」

目前候選功能要求研究 Identity、canonical identity、stable identifier、alias，以及 path 與 identity 的區別。

## 2. 外部研究

Dublin Core 將 Identifier 定義為在特定情境中對資源的「無歧義參照」，並建議使用符合正式識別系統的字串；其例子包括 ISBN、DOI、URN，並指出持久識別碼可使用 HTTP URI。

FAIR 原則進一步要求資料與中繼資料具有全球唯一且持久的識別碼，且 metadata 應明確包含其所描述資料的 identifier。

依據：Dublin Core Identifier；FAIR F1～F4。

## 3. 對本系統的結論

A1 有必要成立，但不應等同於「所有 Markdown 檔案都必須立即新增一個大型 ID 系統」。

本系統至少需要區分：

- Identity：某個邏輯對象是誰。
- Path：目前儲存位置。
- Filename：人類可讀名稱。
- Version：該對象的內容演化版本。
- Alias：曾經使用過的名稱或其他可辨識名稱。

因此「檔案路徑」不能直接充當永久 Identity。

## 4. 建議能力邊界

最小必要能力：

```text
Logical Identity
Stable Identifier
Human-readable Name
Alias
Current Path
Version Reference
State Reference
```

其中 Identity 應穩定跨越檔名或路徑變更；Path 屬於儲存位置資料。

## 5. 不應做的事

- 不建立過度複雜的企業級 Master Data Management 系統。
- 不要求所有歷史文件立即補齊完整 metadata。
- 不把 Git SHA 當成知識本體的永久 Identity。
- 不把檔名當成唯一邏輯身份。
- 不因存在 ID 就宣稱身份治理已完成。

## 6. 驗收條件

至少建立一個可實際測試的案例：

```text
文件 A
↓ 改名
文件 A'
↓ 搬移路徑
文件 B
```

若系統仍能判斷 A、A'、B 是同一邏輯對象，且能區分其版本／狀態，A1 才算通過最小實戰驗證。

## 7. 判定

【保留；正式能力候選】

優先級：高。

# A2 Metadata 描述 Metadata

## 1. 原問題

回答：「最少需要哪些描述，才能讓其他系統理解與使用？」

## 2. 外部研究

Dublin Core Metadata Terms 是一套可組合的 metadata 詞彙，除了原始 Dublin Core 元素，也包含 properties、classes、vocabulary encoding schemes 等；官方文件明確指出，這些 terms 可以與其他相容詞彙組合形成 application profiles，也可以在 JSON、XML、UML 或 relational database 等非 RDF 環境中使用。

FAIR 原則要求資料具有豐富且準確相關的 metadata，並要求 metadata 可搜尋、可理解與可重用。

依據：DCMI Metadata Terms；FAIR F2、R1、R1.1～R1.3。

## 3. 對本系統的結論

A2 有必要，但「Metadata」不能變成另一套與文件正文競爭的大型資料庫。

本系統真正需要的是「最小充分 metadata」，服務於：

```text
識別
狀態判斷
版本判斷
適用性判斷
搜尋
追溯
關係判斷
```

## 4. 建議最小欄位方向

候選欄位：

```text
identity
name
type
state
version
created
modified
source
owner/responsibility
related_to
status_note
```

實際欄位仍需在後續 A1～A12 整合研究後確定，不在本輪凍結完整 schema。

## 5. 核心設計原則

Metadata 應回答「如何找到、理解、判斷、使用這個對象」，而不是複製正文內容。

因此：

```text
Metadata ≠ Summary
Metadata ≠ 全文內容
Metadata ≠ AI 記憶
Metadata ≠ Git commit
```

## 6. 不應做的事

- 不建立幾十／上百個強制欄位作為第一版。
- 不要求每份歷史文件一次性全部補 metadata。
- 不讓 metadata 重複保存正文語義。
- 不因 schema 完整而宣稱治理完成。

## 7. 驗收條件

挑選不同類型的 Repository 對象，例如：知識、方案、工程狀態、案例、歷史資料。

確認最小 metadata 是否能讓另一個 AI：

1. 判斷它是什麼。
2. 判斷目前是否可用。
3. 找到來源與相關對象。
4. 判斷是否需要讀全文。

## 8. 判定

【保留；正式能力候選】

優先級：高，但 schema 暫不凍結。

# A3 來源管理 Source Management

## 1. 原問題

回答：「資料從哪裡來？」並明確區分 Source 與 Evidence。

## 2. 外部研究

Dublin Core 將 Source 定義為描述資源所衍生自的相關資源，並建議以 URI 或正式識別系統識別來源。

PROV-DM 則將 provenance 建模為產生資料／事物過程中的 entities、activities、agents，以及 derivation 等關係。因此「來源」不是單純的一個 URL 欄位，而可能是資料生成鏈的一部分。

依據：Dublin Core Source；W3C PROV-DM。

## 3. 對本系統的結論

A3 必須與 A4 分開。

```text
Source
= 資料／內容從哪個資源取得或衍生

Evidence
= 用來支撐某個 Claim 的具體證據
```

同一個 Source 可以提供多個 Evidence；一個 Claim 也可以由多個來源／證據共同支撐。

## 4. 建議資料關係

```text
Knowledge/Object
    ↓ derived_from
Source

Claim
    ↓ supported_by
Evidence
    ↓ located_in / derived_from
Source
```

這比單純在文件頂部放一個「來源：URL」更接近實際治理需求。

## 5. 不應做的事

- 不把 URL 本身視為完整來源治理。
- 不把 Source 與 Evidence 合併成同一概念。
- 不要求所有來源立即建立複雜 provenance graph。
- 不把「有引用」直接等同於「已驗證」。

## 6. 驗收條件

建立一個實際案例：

```text
外部文章 A
↓
研究觀察 B
↓
Claim C
↓
知識文件 D
```

系統必須能回答：

- D 的內容來源是什麼？
- C 由哪些 Evidence 支撐？
- Evidence 位於哪個 Source？
- 哪一部分是原始來源，哪一部分是本系統自己的推論？

## 7. 判定

【保留；正式能力候選】

優先級：高。

# A4 Claim／Evidence 關聯

## 1. 原問題

回答：「某項主張由哪些證據支撐？證據本身是否只是來源？」

## 2. 外部研究

W3C PROV 將 provenance 視為描述資料／事物產生過程的資訊，包含 entities、activities、agents、derivations 等關係；其用途之一是支持對品質、可靠性與可信度的評估。

FAIR 原則 R1.2 要求資料／metadata 與詳細 provenance 關聯，I3 要求 metadata 包含對其他資料的 qualified references。

Dublin Core 也將 references 定義為被描述資源所引用、指向或參照的相關資源。

依據：W3C PROV、FAIR R1.2/I3、Dublin Core References。

## 3. 對本系統的結論

A4 是目前四方案中非常重要的基礎治理能力，因為本知識庫的核心要求之一就是不能把「AI 推論」偽裝成「已確認知識」。

至少需要區分：

```text
Observation
Claim
Evidence
Source
Inference
Decision
```

其中：

```text
Source ≠ Evidence
Evidence ≠ Claim
Claim ≠ Inference
Inference ≠ Fact
```

## 4. 建議最小關係模型

```text
Source
  ↓ contains / provides
Evidence
  ↓ supports
Claim
  ↓ interpreted_as / leads_to
Inference
  ↓ may_support
Decision
```

此模型不要求一開始使用 RDF 或圖資料庫；Markdown + 明確關係欄位即可作為第一階段實作。

## 5. 關鍵治理規則

一個 Claim 至少應能標記：

```text
Claim
Evidence
Evidence strength / verification state
Source
Inference（如果存在）
```

而「沒有證據」本身也應能被保存為不確定狀態，而不是自動補成確定知識。

## 6. 不應做的事

- 不建立自動判定真假的 AI 權威機制。
- 不把引用數量當成證據強度。
- 不把 Source 存在視為 Claim 已驗證。
- 不把 AI 生成內容自動標成 Evidence。
- 不建立大型知識圖譜作為第一階段必要條件。

## 7. 驗收條件

建立三種案例：

### 案例 A：直接證據

Source → Evidence → Claim

### 案例 B：多證據

Source A → Evidence A
Source B → Evidence B
Evidence A + B → Claim

### 案例 C：推論

Evidence → Claim → Inference

驗收時 AI 必須能區分「來源」「證據」「主張」「推論」，不能因文字寫得像事實而提高其狀態。

## 8. 判定

【保留；核心正式能力候選】

優先級：非常高。

# 二、A1～A4 的共同結論

這四項不應各自建立四套資料結構。

目前研究支持一個共同方向：

```text
Identity
   ↓
Object
   ↓
Metadata
   ↓
Source / Evidence / Claim
   ↓
Provenance / Relationship
```

但目前證據不足以在本輪直接凍結完整中央資料模型。

## 共同原則

1. Identity 必須與 Path、Filename、Version 分離。
2. Metadata 應保持最小充分，而不是全文複製。
3. Source 與 Evidence 必須分離。
4. Evidence 與 Claim 必須分離。
5. Inference 必須與 Claim 分離。
6. Git 可以提供版本／變更證據，但不能自動取代邏輯 Identity、Source、Evidence 或 Claim。
7. 第一階段不需要導入大型知識圖譜或企業級 MDM。
8. 所有正式能力都必須經實際案例驗證後才能從「候選」升為「成立」。
