# 四方案逐項功能研究-017-D17至D20

版本：v1.0  
狀態：【研究完成；待模擬實作驗收】  
研究範圍：D17～D20  
前置：D1～D16 已完成逐項研究與模擬驗收；D17～D20 為正式功能清單最後一批。

## 一、正式功能來源

Repository 正式功能清單明確定義：

- D17 新基準建立
- D18 歷史／舊能力保存
- D19 蒸餾結果回寫
- D20 再次蒸餾觸發

正式清單目前最後項目為 D20，未建立 D21。

## 二、D17 新基準建立

### 2.1 功能目的

將已完成重構且通過 D16 驗證的新結構，正式形成下一個可供正常工程工作依賴的 Current Baseline。

D17 不是單純「新增一個版本號」，而是建立可被後續 Scheme 1～3、工程運作與 AI 工作引用的已確認結構狀態。

### 2.2 最小必要內容

- Baseline Identity
- Stable Identity／受控對象
- 新結構描述
- Current State
- Version
- 生效時間
- D16 驗證結果
- 採用／成立條件
- 來源 Change/Distillation Case
- 相關證據與 Traceability
- 適用範圍與限制

### 2.3 邊界

D17 只能建立已通過驗證的基準。

D16 FAIL、UNKNOWN 或尚未完成驗證的結果不得直接成為 Current Baseline。

D17 也不應重新執行 D13～D16；它承接已完成的驗證結果並建立新的正式基準。

### 2.4 外部交叉研究

NASA Configuration Management 將 baseline 定義為特定時間點、已確認的配置描述，並要求後續變更以 current baseline 為基礎；NIST 亦將 configuration baseline 定義為經正式審查同意、可作為後續 build/release/change 基礎的配置。這支持 D17 將「通過驗證的新結構」與「下一次正常變更的基準」分開處理。

## 三、D18 歷史／舊能力保存

### 3.1 功能目的

將退出目前工作結構的舊能力、舊版本與相關決策保存為可追溯歷史，而不是讓它繼續被誤認為 Current。

### 3.2 最小必要內容

- Old Stable Identity
- Old Version／State
- 退出時間
- 被何種新結構取代或影響
- 原用途與責任
- 歷史使用／依賴資訊
- 蒸餾案件與變更案件關聯
- 重構前後差異
- 保存位置／Snapshot
- 回溯限制

### 3.3 關鍵語義

Historical ≠ Current。

Archived ≠ Deleted。

Retired ≠ Never Existed。

保存歷史不是讓舊能力重新進入目前搜尋結果的理由；需要明確標示 Lifecycle／State。

### 3.4 外部交叉研究

NASA Configuration Status Accounting 要求保留 current 與 historical configuration documentation；NIST SP 800-128 明確指出新的 baseline 成為 current 後，舊 baseline 不再有效但應保留作歷史用途，並可支援 rollback、incident response 與 traceability。這與 D18 的「退出 Current、保留可追溯歷史」一致。

## 四、D19 蒸餾結果回寫

### 4.1 功能目的

保存本次蒸餾「為什麼做、看到了什麼、如何判斷、實際改了什麼、驗證如何、哪些問題仍未解決」，使下一次 AI 或工程工作可以理解這次蒸餾的決策脈絡。

### 4.2 回寫內容

- Distillation Case Identity
- Trigger／Problem
- Scope
- Evidence
- Capability Inventory
- Semantic/Overlap/Boundary/Dependency Analysis 摘要
- Candidates
- Selected Disposition
- Impact／Migration Conditions
- Actual Changes
- D16 Validation
- D17 New Baseline
- D18 Historical Preservation
- Unresolved Issues
- Uncertainty
- Follow-up Conditions
- Traceability

### 4.3 邊界

D19 是結果保存與回饋，不是重新修改所有相關知識。

「回寫結果」與「更新某項知識內容」不是同一責任；實際內容修改仍須交回相應 Scheme／系統的責任層。

D19 不得把推測、未驗證候選或 UNKNOWN 結果寫成已確認事實。

### 4.4 外部交叉研究

NASA CM 要求保存變更請求、處置理由、變更記錄、驗證／稽核結果與歷史資料；ADR 的實務則強調決策、Context、理由、替代方案、後果與狀態應形成持久紀錄，而重大決策改變時以新的決策紀錄取代舊紀錄，而非覆寫歷史。這支持 D19 將「決策脈絡與結果」作為獨立可追溯工程產物。

## 五、D20 再次蒸餾觸發

### 5.1 功能目的

當正常工程運作中再次累積到符合蒸餾條件的結構性問題時，建立新的 Distillation Case，而不是在原案件上無限追加。

### 5.2 觸發條件

觸發可以來自：

- 長期重複出現的結構性問題
- 多個能力持續重疊
- 責任邊界再次失效
- 維護／同步／理解成本持續累積
- 多次局部修正仍無法消除共同根因
- 關係／依賴複雜度持續增加
- AI Context 成本或錯誤風險持續升高
- 正常 Scheme 3 演化已無法以合理的單次變更處理

### 5.3 不應觸發的情況

- 單一低風險局部錯誤
- 一次性的資料錯誤
- 尚可由正常 Scheme 3 變更處理的問題
- 沒有證據的「感覺應該重構」
- 僅因文件數量增加
- 僅因名稱相似

### 5.4 觸發結果

D20 只負責建立下一次蒸餾候選／案件入口。

它不能跳過：

`D1 蒸餾案件建立 → D2 範圍界定 → D3 能力盤點 → D4 實際使用／依賴確認`

因此 D20 是閉環重新進入 D1，而不是直接重新開始 D5 或直接執行重構。

## 六、D17～D20 閉環

```text
D15 重構執行
↓
D16 重構後驗證
↓
D17 新基準建立
↓
D18 歷史／舊能力保存
↓
D19 蒸餾結果回寫
↓
正常工程運作
↓
新的結構性問題累積／被確認
↓
D20 再次蒸餾觸發
↓
新的 D1 蒸餾案件
```

## 七、四項責任邊界

| 功能 | 核心責任 | 不負責 |
|---|---|---|
| D17 | 建立通過驗證的新 Current Baseline | 重新執行驗證／自行決定未驗證結果有效 |
| D18 | 保存退出 Current 的歷史／舊能力 | 讓舊能力重新成為 Current |
| D19 | 保存本次蒸餾的判斷、變更、驗證與未解決事項 | 無條件修改所有相關知識 |
| D20 | 判斷是否形成下一次蒸餾入口 | 直接執行新蒸餾或跳過 D1～D4 |

## 八、與其他方案的接口

### Scheme 1

D17、D18、D19 使用既有 Identity、State、Version、Lifecycle、History、Traceability 語義，不另建第二套資料治理語義。

### Scheme 3

Scheme 3 的 C17 可把超出單次演化範圍的問題交給 Scheme 4；D20 則是 Scheme 4 完成後，未來新的結構性問題再次進入 Scheme 4 的入口。

### 問題解決系統

正常工程運作中發現問題時，先判斷問題是否值得進入蒸餾。不能把所有問題直接升級成 D20。

### 工程運作與持續改進

D20 的觸發依賴長期實際工作觀察；模擬驗收只能驗證規則是否可運作，不能宣稱已經發生真實長期蒸餾需求。

## 九、主要禁止事項

1. D17 不得把未驗證結果直接建立成 Current Baseline。
2. D18 不得把 Historical 當 Current。
3. D19 不得把 UNKNOWN 寫成已確認事實。
4. D20 不得因單一局部問題自動觸發完整蒸餾。
5. D20 不得跳過 D1～D4。
6. 不建立 D21。
7. 不以本批研究文件反向新增正式功能。

## 十、研究結論

D17～D20 形成方案四的閉環末端：

`驗證通過 → 新基準 → 舊能力歷史化 → 結果回寫 → 正常運作 → 新結構性問題 → 下一蒸餾案件`

目前未發現需要新增正式功能的結構性缺口。下一步進入模擬實作驗收。
