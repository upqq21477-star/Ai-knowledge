# 工程交接四情境失憶測試 001

日期：2026-09-17
測試對象：`2-方案/工程運作與持續改進方案-v1.3.md`、`2-方案/正確成立方案與系統方案-v2.4.md`、`交接資料-v2.5.md`、`2-方案/完善/目前工程狀態快照-002.md`
狀態：【四情境測試完成；發現一項結構性缺口；正式新基準暫緩】

## 一、測試目的

模擬一個完全失去對話記憶的新 AI，只能依 Repository 內容恢復工程位置。

必須驗證：

1. 找到正確工作。
2. 判斷正確階段。
3. 不重做已完成工作。
4. 不把未完成工作當成完成。
5. 找到下一步。
6. 只在必要時補交接。

本測試不修改既有方案與舊檔案；情境以 Repository 現有文件、狀態與 Git 可驗證資訊重建。

## 二、實際恢復順序

按照 v1.3 定義的順序執行：

```text
交接
↓
目前工程狀態快照
↓
目前工作／方案／施工檔案
↓
待辦
↓
Git 實際變更
↓
必要歷史
```

同時加入一個反向檢查：若交接狀態與工作檔案／Git 不一致，不直接採信交接。

## 三、情境 A：討論中死亡

### 模擬狀態

假設上一 AI 只完成問題討論、搜尋與分析，尚未形成正式工程結論。

### 新 AI 判定

```text
沒有正式結論
→ 不建立新工程狀態
→ 不進入施工
→ 不更新正式交接基線
→ 回到原討論階段
```

### 驗證

Repository 規則明確要求「未形成正式結論的討論不產生工程狀態」。因此新 AI 不應因看到大量討論資料就自行建立方案或施工。

結果：PASS

### 是否需要交接更新

否。

原因：這不是工程狀態轉換，只是未完成的討論。

## 四、情境 B：規劃完成後死亡

### 模擬狀態

討論已形成正式結論，規劃已建立，但施工尚未開始。

### 新 AI 判定

Repository 現行規則要求正式進入規劃時建立一次新的工程交接基線；規劃完成後若尚未施工，新 AI 應從規劃入口恢復，而不是重新做問題分析。

### 必須避免

- 重新做問題拆解。
- 重新做功能盤點。
- 把方案當成尚未成立。
- 直接跳過規劃而自行施工。

### 驗證

目前交接與快照本身可表達「規則已建立、四情境測試待執行」，因此恢復入口清楚；在真實規劃案例中，工作檔案仍必須具備目前階段、已完成、未完成與下一步欄位。

結果：PASS（規則恢復能力）；真實施工案例仍需自然案例驗證。

### 是否需要交接更新

若規劃完成時尚未同步：需要一次。
若已同步且只是接手施工：不需要重複同步。

## 五、情境 C：施工 50% 中死亡

### 模擬狀態

假設已開始施工並產生實際 Repository 變更，但工作尚未完成，交接仍停留在上一個正式基線。

### 新 AI 判定

不能因交接仍顯示上一基線，就判定施工尚未開始。

必須進一步讀取：

```text
工作檔案
＋
Git 實際變更
＋
待辦
```

再判斷實際完成比例與下一步。

### 驗證依據

目前 v1.3 已明確規定施工中斷不等於工作不存在，且工作檔案最低恢復資訊包含：目前工作、目前階段、目前子步驟、已完成、未完成、阻塞、下一步、最後有效狀態。

因此正確行為是「恢復施工」，而不是「重新開始」。

結果：PASS（恢復規則）；實際 50% 施工資料目前 Repository 中沒有一個專門的中斷案例，因此屬規則實測，不是歷史施工實測。

### 是否需要立即更新交接

否。

先恢復施工並依工作檔案／Git 繼續；只有形成重大狀態轉換時才更新交接。

## 六、情境 D：施工完成但交接尚未更新時死亡

### 模擬狀態

施工實際已完成，但交接仍停留在施工前狀態。

### 新 AI 判定

這是四情境中最重要的反向一致性測試。

不能看到交接寫「未完成」就重新施工。

必須核對：

```text
工作檔案
＋
Git 實際變更
＋
待辦
```

若三者足以證明施工已完成，則：

```text
判定實際完成
→ 不重工
→ 補交接同步
→ 更新待辦
→ 建立新基準／進入驗收
```

### 驗證依據

v1.3 已明確寫入：若交接與 Repository 實際狀態衝突，不得盲信交接；v2.5 也明確規定，若工作檔案與 Git 已顯示完成，必須先核對實際狀態，再補交接。

結果：PASS（反向恢復規則）。

### 是否需要交接更新

是。

因為此時不是普通接手，而是發現一個已經成立但尚未同步的重大工程狀態轉換。

## 七、四情境總表

| 情境 | 正確恢復 | 重工風險 | 是否補交接 | 結果 |
|---|---|---|---|---|
| A 討論中死亡 | 回到未完成討論 | 不應重工施工 | 否 | PASS |
| B 規劃完成後死亡 | 從規劃入口恢復 | 不應重新規劃 | 視是否已同步 | PASS* |
| C 施工 50% 中死亡 | 工作檔案＋Git 恢復 | 不應從零施工 | 否 | PASS* |
| D 施工完成但交接落後 | 以實際 Repository 狀態校正 | 不應重新施工 | 是 | PASS |

`*` 表示規則已通過，但缺少對應的歷史自然案例作為實際施工資料驗證。

## 八、發現的結構性缺口

四情境測試沒有推翻「交接不是活動日誌」這個核心原則；反而確認其必要性。

但測試發現一個更重要的實作前提：

> **施工工作檔案必須真的存在，而且必須是可恢復的狀態載體。**

目前 v1.3 已規定工作檔案應具備最低欄位，但 Repository 中現有多數方案／完善文件並不是按照這個最低恢復結構建立的施工工作檔案。

因此目前存在：

```text
交接規則：已建立
恢復規則：已建立
工作檔案最低格式：已定義
工作檔案普遍實際採用：尚未證明
```

這代表若現在直接宣布正式新基準，會把「規則存在」誤認成「系統具備實際恢復能力」。

## 九、測試結論

核心交接模型：PASS。

四種狀態邊界：PASS。

D 情境的「實際狀態優先於過時交接」：PASS。

但完整工程恢復能力：PARTIAL PASS。

原因不是交接規則失效，而是其依賴的「施工工作檔案狀態載體」尚未在自然施工中證明可用。

因此：

```text
交接同步新規則：基本模型 PASS
正式新基準：LOCK
```

## 十、下一步

不要再建立新的交接規則文件。

下一步應選一個真實、低風險的自然施工案例，按照 v1.3 的最低恢復欄位執行一次施工，故意在中途形成可恢復狀態，再由失去對話記憶的 AI 只讀 Repository 接手。

若該案例能通過 C／D 型恢復，才有足夠證據建立正式新基準。
