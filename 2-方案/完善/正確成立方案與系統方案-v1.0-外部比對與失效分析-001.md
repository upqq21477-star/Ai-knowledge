## 四、內部規則已存在但沒有形成真正行動 Gate

`規則.md` 已經要求：

```text
列功能
→ 分析知識需求
→ 檢查既有知識
→ 盤點既有系統
→ 判斷既有能力
→ 判斷邊界
→ 建立／完善
→ 驗收
→ 實際任務驗證
```

`新方案建立前研究與確認原則` 更明確要求：

```text
問題／目的
→ 既有能力盤點
→ 外部研究
→ 外部比較
→ 優缺點／限制
→ 漏洞攻擊
→ 反方案檢查
→ 候選架構
→ 討論／修正
→ 確認
→ 才能建立
```

因此問題不是「完全沒有流程」，而是「流程沒有成為每次 AI 行動前不可跳過的執行門檻」。

## 五、外部方法比對

### 1. Microsoft Azure Well-Architected ADR

Microsoft 目前建議對架構上重要、影響結構／品質屬性或難以逆轉的決策建立 ADR，記錄背景、選項、決策、取捨、狀態與影響；決策變更時建立新的取代紀錄，而不是覆寫歷史。citeturn1search0turn1search1

採用：

- 重大決策必須可追溯。
- 選項與不採用方向要保留。
- 決策與實作結果分離。
- 重大變更建立新紀錄。

不採用：

- 每個微小步驟都建立 ADR。
- 建立獨立龐大決策資料庫。

### 2. AWS ADR

AWS 將 ADR 視為架構決策生命週期，要求記錄重大結構、非功能需求、依賴、介面與建構方法等決策；接受後保持不可變，新決策取代舊決策。citeturn1search7

採用：

- 建立前要知道決策的範圍。
- 重大決策與實作／Code Review 有關聯。
- 決策狀態與取代關係需要保留。

### 3. GitLab 工程運作

GitLab 採非同步工程溝通，強調把重要結論寫下來，但不是每一個微步驟都廣播；其工程狀態更新採固定週期與明確模板，內容集中在進度、下一步與阻塞。citeturn0search0turn0search1

這直接支持本次修正：

```text
工程狀態 ≠ 每一步回報
```

而是：

```text
工作持續執行
↓
只在有意義的 checkpoint 更新
↓
固定摘要包含進度／下一步／阻塞
```

### 4. GitLab 非同步溝通原則

GitLab 明確將文件、Issue、Merge Request 作為非同步工作層，並要求重要結論留下可追溯紀錄；同時指出需要即時協調時才使用同步溝通。citeturn0search2turn0search6

採用：

- 狀態紀錄應非同步、可累積。
- 使用者回覆不需要與每個內部操作同步。
- 重要決策與階段結果才需要對外回報。

## 六、v1.0 的主要缺口

### 缺口 A：沒有「建立前鎖定」的強制執行器

雖然有 Gate，但 AI 可以直接進入 create_file／update_file。

因此 v2.0 必須增加：

```text
任何新方案／核心系統建立意圖
↓
Preflight
↓
檢查 Gate
├─ 未完成 → LOCK
└─ 完成 → ALLOW
```

### 缺口 B：把「流程存在」誤認為「流程已被執行」

文件寫了流程，不代表 AI 每次行動前真的檢查流程。

因此必須分開：

```text
規則存在
≠
Gate 可執行
≠
本次 Gate 已通過
≠
方案成立
```

### 缺口 C：沒有明確的批次／階段工作單位

如果每一個搜尋、比較、文件讀取、建立、更新都產生狀態紀錄，會造成記錄成本高於工程價值。

v2.0 必須以「工作批次 Batch／Gate／Checkpoint」為狀態更新單位，而不是工具呼叫或微步驟。

### 缺口 D：沒有明確區分 AI 內部進度與使用者回報

兩者必須分開：

```text
內部工程紀錄
≠
使用者可見回覆
```

### 缺口 E：沒有 Context／算力成本門檻

狀態紀錄本身會增加 AI 需要重新讀取的文字量，也會增加 Git 操作與搜尋成本。

因此 v2.0 必須以「最小充分資訊」為原則，不以完整紀錄所有操作為目標。

## 七、狀態紀錄頻率結論

不採用「每一步記錄」。

採用四級：

### S0 微步驟

搜尋一個來源、讀一份文件、比較一個細節、修正一句文字。

→ 不建立獨立狀態紀錄。
→ 不更新交接。
→ 不需要使用者回報。

### S1 工作批次

完成一組有共同目的的研究／比較／施工動作。

→ 可在批次結束時更新一次工作狀態。
→ 通常不更新交接。
→ 不要求立即對使用者回報。

### S2 Gate／Checkpoint

完成一個重要階段，例如：

- 功能盤點完成
- 外部研究完成
- 比較完成
- 方案確認
- 系統建立完成只剩整體驗收
- 驗收結果產生

→ 必須更新工程狀態。
→ 必要時更新待辦。
→ 符合交接條件時更新交接。
→ 對使用者回報一次階段摘要。

### S3 重大狀態／新基準

例如：

- 方案正式確認／重製
- 核心責任改變
- 重大架構變更
- PASS／PARTIAL／FAIL 改變主線
- 新 AI 即將接手
- 新穩定基準建立

→ 更新狀態、待辦、交接與必要索引。
→ 對使用者回報完整摘要。

## 八、回傳頻率原則

使用者可見回傳採「階段式」，不是「步驟式」。

```text
大量內部操作
→ 1 次階段摘要
```

預設：

```text
每個 Gate 最多 1 次主要回報
每個獨立工作批次最多 1 次摘要
重大阻塞立即回報
重大決策立即回報
普通微步驟不回報
```

如果一個 Gate 內包含 20 次搜尋與 30 次文件讀取，仍只需要在 Gate 完成或出現重大阻塞時回報一次。

## 九、狀態紀錄內容壓縮原則

狀態紀錄只保留：

```text
目前在哪裡
為什麼
已完成什麼
未完成什麼
阻塞什麼
下一步
需要讀哪裡
```

搜尋細節、逐條比較、完整研究內容留在專門研究文件，不複製到狀態紀錄。

因此：

```text
研究文件 = 深度內容
狀態紀錄 = 索引／摘要
交接 = 最小恢復上下文
待辦 = 行動清單
```

## 十、結論

既有流程不是沒有，而是沒有真正形成「行動前 Gate + 批次紀錄 + 階段回報」三件事。

因此 v2.0 必須重建，而不是只在 v1.0 上增加更多提醒文字。
