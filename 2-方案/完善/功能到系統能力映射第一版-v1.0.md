# 功能到系統能力映射第一版 v1.1

版本：v1.1
狀態：【創建中；第一輪能力映射；完成度與驗收分層已修正】
日期：2026-09-17

## 一、定位

本文件是四方案創建階段的「功能 → 系統能力」中間層。

它不是正式系統設計，也不是系統清單。

目的：

```text
功能需求
↓
功能所需能力
↓
既有能力盤點
↓
能力組合／邊界判定
↓
候選系統能力
↓
系統處置
↓
正式系統設計／既有系統完善
```

不得因功能數量增加而一對一建立系統。

## 二、系統能力的最低判定條件

候選「系統能力」至少必須回答：

1. 解決什麼可重複問題？
2. 接收什麼輸入？
3. 產生什麼可觀察輸出？
4. 需要哪些既有知識？
5. 需要哪些共同資料語義？
6. 與其他能力的責任邊界在哪裡？
7. 是否會被多個工作／方案重複使用？
8. 是否存在明確觸發條件？
9. 如何進行最小實作驗收？
10. 如何進行實戰驗證驗收？

以上第 9、10 項只要求先定義驗收方法，不代表已完成實作、驗收或實戰驗證。

## 三、第一批能力組合

### 3.1 共同資料識別與關係能力

來源功能：

- A1 資料身份／識別
- A7 關係管理
- A12 跨方案共同語義
- B10 記憶／目前狀態辨識
- C3 變更對象識別
- D3 能力盤點

候選能力：

```text
共同對象識別與關係查詢能力
```

最小責任：

- 將資料、知識、系統、方案等對象識別為穩定對象。
- 查詢對象之間的已知關係。
- 支援別名、版本、狀態等資訊定位。

不負責：

- 執行業務流程。
- 自動修改關係。
- 自動判定是否應重構。

判定：候選共同能力，尚未等同正式系統成立。

### 3.2 變更影響與相容性分析能力

來源功能：

- C3 變更對象識別
- C5 既有能力盤點
- C6 影響分析
- C9 版本分析
- C10 相容性分析
- C11 遷移分析
- C17 蒸餾轉交
- D9 關係／依賴分析
- D13 影響分析
- D14 遷移條件分析

候選能力：

```text
變更影響與遷移分析能力
```

最小責任：

```text
變更對象
↓
關係／依賴
↓
使用範圍
↓
版本
↓
相容性
↓
遷移需求
↓
驗證需求
```

輸出：

- 可能受影響對象
- 影響等級／不確定性
- 相容性狀態
- 是否需要遷移
- 遷移前置條件
- 需要重新驗證的案例

不負責：

- 自動執行遷移。
- 自動刪除舊資料。
- 自動決定方案是否採用。

判定：候選共同能力；方案三與方案四共用，但責任不可因此合併成同一方案。

### 3.3 驗證與實測證據能力

來源功能：

- B12 結果驗證
- B14 結果保存
- C13 實際驗證
- C18 結果回饋
- D5 證據／驗證狀態確認
- D16 重構後驗證
- D17 新基準建立

候選能力：

```text
驗證狀態與實測證據管理能力
```

最小責任：

- 區分設計、研究、模擬與實際執行。
- 保存最小可重現的實測證據。
- 將驗證結果與對象／版本／狀態建立可追溯關係。
- 支援 PASS / INCOMPLETE / NOT-A-TEST 等狀態。

不負責：

- 替所有系統執行測試。
- 自動宣稱能力成立。
- 以文件存在取代實際驗證。

判定：候選共同能力。

## 四、目前候選能力的處置規則

既有能力映射完成後，不直接跳到實戰驗證，而是進行系統施工處置：

```text
既有能力盤點
↓
完整承擔？
├─ 是 → 沿用，確認系統完成度與驗收狀態
└─ 否
   ↓
部分承擔？
├─ 是 → 完善／重新分責／重構
└─ 否
   ↓
真正缺口成立
↓
進入新系統建立 Gate
```

完成必要系統後才進入：

```text
系統完成
↓
系統最小實作驗收
↓
系統實戰驗證
↓
方案系統統整
↓
方案完成
↓
方案最小實作驗收
↓
方案整體實戰驗證
```

## 五、暫不組建為獨立系統的功能

以下功能目前維持為工作流程能力，而不是獨立系統：

- C4 變更目標確認
- C12 最小變更執行
- C14 採用／暫緩／退回
- C16 歷史保存
- C17 蒸餾轉交
- D15 重構執行
- D18 歷史／舊能力保存

原因：它們目前主要是決策／施工流程中的動作，尚未證明需要獨立、可重複、可搜尋、可驗證的系統能力。

「暫不獨立系統」不等於「相關功能已完成」。實際責任仍須在方案施工中確認。

## 六、方案與系統的邊界

外部成熟案例顯示，系統通常作為能力的抽象邊界，而不是每一個功能各自成為系統。Backstage 的 System Model 將多個 Components、Resources 與 APIs 組合為 System，以隱藏內部實作並降低消費者耦合；Relations 則另外表達 ownership、dependency 等關係。

因此本專案採：

```text
功能 ≠ 系統
能力 ≠ 必然獨立系統
多個相關能力 → 候選系統
跨方案共用能力 → 優先考慮共同能力
```

但「共同能力」不代表一定建立中央巨型系統。能力是否需要獨立系統，仍需依責任、觸發、輸入輸出、驗收與實際使用證據判定。

## 八、禁止提前做的事

目前不得因本文件存在而：

- 直接建立三個正式系統。
- 建立大型中央治理引擎。
- 建立全球 Identity Service。
- 建立自動遷移引擎。
- 建立自動重構／自動刪除引擎。
- 凍結完整 JSON／YAML Schema。
- 宣稱四方案系統已成立。
- 宣稱方案已完成或已通過整體驗證。

## 九、下一步

1. 對候選能力逐一確認輸入／輸出／觸發／責任。
2. 與 Repository 現有系統逐一比對，避免重複建立。
3. 對既有系統判斷沿用／完善／重構／整合／拆分。
4. 對真正缺口進入新系統建立 Gate。
5. 完成必要系統後，執行系統最小實作驗收。
6. 系統成立後再進入系統實戰驗證。
7. 完成必要系統後組建四方案初步實作。
8. 執行方案最小實作驗收。
9. 進入真實工作進行方案整體實戰驗證。
10. 回寫結果並建立新基準。

## 十、外部參考

- Backstage Software Catalog System Model：Systems 用於將合作的 Components、Resources 等封裝成較高層能力邊界。
- Backstage Well-known Relations：Relation 以 Source → Relation Type → Target 表達，並將 ownership 與 runtime authorization 分離。

外部方法只作為設計參考，不直接複製其模型。
