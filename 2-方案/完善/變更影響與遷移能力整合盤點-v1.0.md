## 一、目的

本文件用於完善方案二「AI知識管理」在更新、版本變更、資料遷移與結果重新驗證上的能力接口。

本輪不建立新的「變更影響分析系統」或「遷移系統」。Repository 已存在相關能力，現在確認這些能力能否形成最小責任鏈。

## 二、外部方法比對

AWS 的 Change Impact Assessment 要求比較 Current State 與 Future State、辨識影響範圍與風險；其遷移方法也強調現況分析、計畫、實施、測試與驗證的循環，而非一次性搬移。citeturn0search1turn0search14

Fowler 的 Parallel Change／Expand-Migrate-Contract 將不相容變更拆成 Expand、Migrate、Contract，降低一次性切換造成的破壞，並要求最終完成 Contract，否則雙版本本身會成為新的複雜度。citeturn0search0turn0search6

因此本方案採用「影響分析先於遷移決策、驗證先於舊能力收縮」的最小原則。

## 四、最小責任鏈

方案二遇到資料／知識發生變更時，最小鏈為：

```text
發現變更
↓
確認變更內容
↓
辨識 Identity / Version
↓
找直接使用者／依賴／關係
↓
判斷影響範圍
↓
判斷 Compatibility
↓
判斷是否需要 Migration
↓
形成遷移／並存／更新條件
↓
執行變更
↓
重新驗證
↓
確認新狀態
↓
回寫結果與歷史
```

## 五、模擬案例 C1：相容性變更

### 條件

```text
Knowledge-A
Identity = K-A
Version = v1

變更：補充一個不改變既有語義的說明欄位

目標：K-A v2
```

### 推演

1. **Change**：確認新增的是說明資訊，不改變既有規則。
2. **Identity / Version**：Identity 保持 `K-A`，Version 從 `v1` 到 `v2`。
3. **Impact**：搜尋與引用 `K-A` 的使用者可能看到新版內容，但既有核心語義不變。
4. **Compatibility**：屬於資料／語義上的條件相容；原使用方式仍可繼續。
5. **Migration**：不需要建立獨立遷移流程；只需確保新版資料可被既有使用方式讀取。
6. **Validation**：確認原使用方式與新版內容仍符合原預期。
7. **State**：新版成為目前版本，舊版保留歷史追溯。
8. **Feedback**：記錄變更與驗證結果。

### 判定

```text
C1：SIMULATION-PASSED
```

此案例證明「小型相容變更」不應被強迫套用完整 Migration Engine；現有 Change → Impact → Compatibility → Validation 能力即可承擔。

## 六、模擬案例 C2：不相容變更

### 條件

```text
Knowledge-B v1

舊規則：使用格式 A

新規則：使用格式 B

A 無法被既有消費者直接理解 B
```

### 推演

```text
Change
↓
Identity / Version
↓
Impact
↓
發現舊使用者／依賴者
↓
Compatibility = INCOMPATIBLE
↓
不能直接 Contract
↓
Expand
↓
保留 A + 建立 B
↓
Migrate 使用者／資料
↓
Validate
↓
確認 B 已成為穩定使用方式
↓
確認 A 已無必要依賴
↓
Contract
↓
移除 A
```

### 判定

```text
C2：SIMULATION-PASSED
```

這與 Fowler 的 Parallel Change 模式一致：先支援新舊版本，再逐步遷移，最後才移除舊版本。citeturn0search0turn0search6

## 七、模擬結果：真正接口是否閉合

目前可以形成以下責任分工：

```text
共同資料治理
├─ Identity
├─ Version
├─ Relationship
├─ State

├─ Change

├─ Migration

├─ 任務理解
├─ 搜尋／Context
├─ 使用變更結果
├─ 執行更新
├─ 驗證
└─ 結果回寫
```

目前沒有發現必須新增獨立系統才能完成 C1/C2 的明確缺口。

## 八、模擬驗證限制

本輪只有人工建立條件並推演責任鏈，沒有：

- 真實修改既有正式知識。
- 真實遷移既有資料。
- 真實修改既有系統介面。
- 真實讓下游使用者從舊版本切換到新版本。
- 真實 Contract 舊能力。

因此：

```text
模擬驗證：SIMULATION-PASSED
實戰驗證：FIELD-PENDING
```

不得升格為實戰驗證通過。

## 九、與方案二完成度的關係

C1/C2 通過只證明這一段責任鏈在模擬條件下具有一致性。

它不能證明：

```text
方案二已完成
方案二已驗收
方案二整體實戰已驗證
```

方案二仍須完成其他功能所需系統、接口整合與整體驗收。

## 十、下一個真正要找的缺口

現在不應再繼續無限增加 Change／Migration 類系統。

下一階段應轉向方案二其他核心接口，尤其是：

```text
B2 任務拆解
B7 適用性判斷
B10 記憶／目前狀態
B13 Context 組合
B15 知識回饋
B16 失敗診斷
```

要檢查的是：

```text
任務
↓
拆解
↓
適用性判斷
↓
取得正確 Context
↓
執行
↓
驗證
↓
失敗診斷
↓
知識／狀態回寫
```

而不是再建立另一個與上述能力重疊的管理系統。

