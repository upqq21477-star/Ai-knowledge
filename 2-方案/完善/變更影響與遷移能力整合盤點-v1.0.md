# 變更影響與遷移能力整合盤點 v1.0

版本：v1.0
狀態：【施工盤點；非新系統；待實際案例驗證】
日期：2026-09-17

## 一、目的

本文件用於完善方案二「AI知識管理」在「更新、版本變更、資料遷移與結果重新驗證」上的能力接口。

本輪不直接建立新的「變更影響分析系統」或「遷移系統」。原因是 Repository 已存在相關能力，現在首先需要確認它們能否形成完整責任鏈。

## 二、外部方法比對後的判斷

AWS 的 Change Impact Assessment 以 Current State、Future State、影響範圍與風險作為變更評估基礎；AWS 的相依性分析也要求先辨識直接依賴、外部工作與資料關係，再決定遷移策略。Microsoft 的現代化流程同樣先做現況盤點與評估，再進入規劃與實施。這些方法共同支持「先知道改了什麼與影響誰，再決定怎麼遷移」，而不是更新後再補做影響分析。citeturn0search11

Fowler 的 Parallel Change／Expand-Migrate-Contract 則提供不相容變更的分階段模式：先建立新能力、再遷移與驗證，最後移除舊能力。其優點是降低一次切換的破壞範圍；代價是暫時存在雙版本／雙路徑，因此必須追蹤遷移完成條件與舊能力移除條件。

## 四、方案二真正需要的責任鏈

方案二遇到「資料／知識發生變更」時，至少需要能走完：

```text
發現變更
↓
確認變更內容
↓
辨識 Identity / Version
↓
找直接使用者／依賴／關係
↓
判斷影響範圍
↓
判斷 Compatibility
↓
判斷是否需要 Migration
↓
形成遷移／並存／更新條件
↓
執行變更
↓
重新驗證
↓
確認新狀態
↓
回寫結果與歷史
```

這條鏈不能被簡化成「更新檔案」。

## 五、目前發現的接口問題

### 1. Change 與 Impact 已存在，但共同 Identity／Relationship 尚未完成實作

影響分析需要知道「改的是哪個對象」以及「哪些對象與它有關係」。目前共同對象與關係目錄只有模擬驗證通過，尚缺真實工作驗證。

因此這不是現在再建立一套 Dependency System 的理由；應先觀察共同目錄與既有影響分析能否自然接合。

### 2. Impact 與 Compatibility 有語義區分，但尚未證明工作接口

影響分析回答「誰可能受到影響」。

Compatibility 回答「舊使用方式是否仍可工作」。

兩者不能互相取代：

```text
Impact
→ 受影響對象

Compatibility
→ 舊使用方式是否仍成立
```

### 3. Compatibility 與 Migration 有語義區分，但缺少真實案例

Migration 需要來源 Identity／Version、目標 Identity／Version、受影響關係、轉換方式、驗證與失敗處理。目前已有原則，但尚未由實際變更案例證明完整性。

### 4. Migration 與 Validation 已有接口，但驗證狀態需要沿用新的分層模型

不能因「遷移計畫完成」就宣稱遷移驗證完成。

應區分：

```text
遷移方法已定義
≠ 遷移已執行
≠ 遷移驗收通過
≠ 真實工作已驗證
```

若先以人工推演確認流程，可以標記：

```text
SIMULATION-PASSED
FIELD-PENDING
```

後續自然工作真正使用後，才轉為 `FIELD-PASSED` 或 `FIELD-FAILED`。

## 六、方案二接口草案

本方案不直接擁有所有底層治理責任，而是提出需求並接收結果：

```text
AI知識管理方案
│
├─ 發現資料變更
│   ↓
├─ 向資料演化能力提出 Change / Impact Request
│   ↓
├─ 取得 Impact Result
│   ↓
├─ 取得 Compatibility / Migration 條件
│   ↓
├─ 選擇最小充分 Context
│   ↓
├─ 執行任務／更新
│   ↓
├─ 執行驗證
│   ↓
└─ 回寫實際結果
```

資料治理負責共同身份、關係、狀態與追溯語義；資料演化負責變更與遷移；AI知識管理負責在任務中正確使用這些結果。

## 七、暫不建立的新系統

目前不建立：

- 新的變更影響分析系統。
- 新的 Dependency Graph 系統。
- 新的 Compatibility Engine。
- 新的 Migration Engine。
- 全域自動遷移平台。

理由不是「永遠不需要」，而是目前已有相關能力，真正缺口尚未被實際案例證明。

## 八、下一個驗證案例

可以使用人工條件先做小型模擬，確認責任鏈是否閉合：

### Simulation C1：知識定義變更

條件：

```text
Knowledge-A v1
↓
某一核心條件改變
↓
Knowledge-A v2
```

推演：

```text
Change
→ Identity / Version
→ Impact
→ Compatibility
→ Migration 是否需要
→ Validation
→ 新狀態
```

驗收重點：每一段都有明確責任，不把所有工作塞進單一系統。

### Simulation C2：不相容變更

條件：舊格式無法直接被新使用方式接受。

推演：

```text
Expand
→ 保留舊方式
→ 建立新方式
→ Migrate
→ Validate
→ Contract
```

驗收重點：不得在尚未確認依賴消失前直接刪除舊方式。

```text
方案二此部分能力已存在
↓
主要問題是跨能力接口與實際施工閉環尚未證明
```


若後續真實工作自然觸發變更案例，再使用同一責任鏈進行實戰驗證。
