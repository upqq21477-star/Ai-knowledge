## 一、研究範圍

本批次只研究正式功能清單中的 C17、C18，不新增不存在的功能。

- C17 蒸餾轉交
- C18 結果回饋

正式功能清單將 C17 定義為：發現問題已超出單次變更範圍時，建立蒸餾候選並轉交方案四；C18 定義為：把使用與驗證結果回饋至知識與後續演化。fileciteturn104file0L2-L2

## 二、C17 蒸餾轉交

### 1. 核心責任

C17 不是直接啟動方案四重構，而是判斷「單次演化案件已經不足以安全處理問題」，將已經整理過的問題、證據、能力與影響資訊形成可供方案四接手的蒸餾候選。

### 2. 觸發條件

至少可能包括：

- 多個能力或系統存在高度重疊，需要重新劃分責任。
- 問題不是單一變更可以解決，而涉及架構層級的長期成本。
- 需要 Merge、Split、Replace、Rebuild 等結構性處置。
- 現有責任邊界反覆造成問題。
- 同類問題跨多個演化案件重複出現。
- 變更成本已超過單次局部修正的合理範圍。

觸發條件只是蒸餾候選訊號，不代表方案四一定應該重構。

### 3. C17 最小輸出

```text
Distillation Candidate
- Candidate ID
- Source Change Case
- Problem / Gap
- Affected Objects
- Existing Capability Summary
- Evidence / Validation State
- Repeated Failure / Pattern
- Impact Scope
- Why Local Evolution Is Insufficient
- Candidate Distillation Scope
- Constraints
- Uncertainty
- Traceability
```

### 4. 責任邊界

C17 負責「何時需要轉交、轉交什麼、轉交到哪裡」。

C17 不負責：

- 自行決定方案四的 Keep / Merge / Split / Replace。
- 自行執行重構。
- 刪除舊能力。
- 宣告蒸餾成功。

方案四收到候選後，仍須依 D1～D18 等正式責任重新分析。

## 三、C18 結果回饋

### 1. 核心責任

C18 將實際使用、驗證與變更處置產生的新資訊回送至知識、狀態、歷史及後續演化流程。

它不是「把所有結果都寫回知識」，而是先分類結果的語義與可信度。

### 2. 回饋來源

```text
C13 實際驗證
C14 採用／暫緩／退回
C15 新目前狀態
C16 歷史記錄
實際工程運作
方案二任務結果
問題解決結果
方案四重構結果
```

### 3. 回饋分類

```text
CONFIRMED-KNOWLEDGE
STATE-UPDATE
HISTORY-ONLY
CHANGE-SIGNAL
FAILURE-SIGNAL
DISTILLATION-CANDIDATE
UNRESOLVED
NO-NEW-KNOWLEDGE
```

結果不能因為「實際使用過」就自動升格為正式知識。

### 4. C18 最小輸出

```text
Feedback Receipt
- Feedback ID
- Source Result
- Object Identity
- Result Type
- Evidence
- Validation State
- Current State Impact
- Knowledge Impact
- New Change Signal
- Distillation Signal
- Uncertainty
- Traceability
```

## 四、C17 與方案四的接口

```text
C13 驗證
   ↓
C14 採用／暫緩／退回
   ↓
C15 / C16
   ↓
C17 蒸餾候選
   ↓
方案四 D1 蒸餾案件建立
```

C17 是「轉交接口」，不是方案四的前置替代品。

方案四仍需重新確認範圍、能力、實際使用、證據、重疊、責任、依賴與長期成本。

## 五、C18 與其他方案接口

```text
C13/C14/C15/C16
       ↓
      C18
 ┌─────┼─────┐
 ↓     ↓     ↓
方案一 方案二 方案三
語義    知識   新變更訊號
       
必要時 → 方案四蒸餾候選
```

C18 不建立第二套知識、狀態、版本或歷史模型，使用方案一共同語義。

## 六、關鍵防錯規則

1. C17 不能因單次小問題就自動建立方案四重構案件。
2. C17 不能把「候選蒸餾」當成「必須重構」。
3. C18 不能把所有結果自動寫成正式知識。
4. C18 不能用一次成功結果覆蓋既有衝突證據。
5. C18 不能把 UNKNOWN 升格為 PASS 或確定知識。
6. 方案四不能因收到 C17 就跳過自己的 D1～D5。
7. C18 產生的新變更訊號仍須回到 C1～C4。
8. 歷史結果不能因回饋而重新成為目前狀態，除非經正式狀態更新流程確認。

## 八、研究結論

C17、C18 都是必要的閉環能力，但不需要新增大型獨立系統。

C17 解決「局部演化何時應該轉交結構性蒸餾」；C18 解決「演化結果如何安全回流到知識、狀態與下一輪演化」。

方案三的完整閉環因此形成：

```text
變更訊號
→ 確認
→ 對象
→ 目標
→ 能力
→ 影響
→ 必要性
→ 候選
→ 版本
→ 相容
→ 遷移
→ 執行
→ 驗證
→ 處置
→ 新狀態
→ 歷史
→ 蒸餾／回饋
→ 下一輪變更
```
