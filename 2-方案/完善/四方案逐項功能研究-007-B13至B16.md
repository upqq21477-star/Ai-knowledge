# 三、B13 不確定性保存

## 3.1 功能定義

B13 的核心不是「給每件事打一個信心分數」，而是防止 AI 將未知、未確認、條件不足或互相衝突的資訊，在後續流程中被錯誤升格成確定知識。

因此 B13 必須保存：

```text
知道什麼
不知道什麼
為什麼不知道
目前證據到哪裡
適用條件
衝突內容
尚待驗證事項
目前判定狀態
```

## 3.2 與 A5 State、A4 Evidence、B6 Source/Evidence Judgment 的關係

B13 不建立另一套資料真實性模型。

它應使用方案一既有共同語義：

```text
Identity
Source
Evidence
Claim
State
Version
History
Traceability
```

B6 負責判斷來源／證據；B7 負責適用性；B12 負責實際輸出驗證；B13 負責把「尚未足以確定」這件事保存下來，使後續 AI 不會忘記限制條件。

因此：

```text
B6：這是什麼證據？
B7：這個資料能不能用在目前情境？
B12：這次輸出是否通過驗證？
B13：哪些部分仍然不能當成確定事項？
```

## 3.3 最小模型

```text
Uncertainty Record
├─ Subject / Identity
├─ Related Claim / Result
├─ Uncertainty Type
├─ Current State
├─ Supporting Evidence
├─ Missing Evidence
├─ Conflict
├─ Scope / Conditions
├─ Time / Version
├─ Impact if Wrong
├─ Next Verification Action
└─ Traceability
```

建議的不確定性類型：

- Unknown：目前不知道
- Unverified：有主張但尚未驗證
- Insufficient Evidence：證據不足
- Conflicting Evidence：證據衝突
- Conditional：只有在特定條件下成立
- Outdated / Time-sensitive：時間有效性不確定或可能過期
- Applicability Unknown：真實性可能成立，但是否適用於目前任務未知

不要求所有不確定性都轉換為數值概率。數值信心只有在具有可解釋、可校準的來源時才有意義。

NIST 對 AI 的 Confidence / Uncertainty 區分指出，高 confidence 並不等於正確；不確定性應能協助辨識輸入是否落在模型不熟悉或例外的範圍。citeturn1search36turn1search3 2025 年對 LLM 不確定性估計的研究也顯示，準確率高並不代表不確定性估計可靠，因此不能把模型自己報出的信心直接視為事實狀態。citeturn1academia37

## 3.4 外部研究結論

W3C PROV 將 provenance 定義為描述資料由哪些實體、活動與責任者產生或影響的資訊，可用於評估品質、可靠性與可信度；同時明確指出 provenance 本身不保證權威或正確，因此信任判斷仍須另外處理。citeturn1search1turn1search0

這與本系統的方向一致：

```text
有來源 ≠ 已證實
有 provenance ≠ 正確
有 confidence ≠ 真實
```

因此 B13 應保存「不確定性的原因與邊界」，而不是假裝把不確定性消滅。

## 3.5 B13 停止條件

當目前任務需要的未知項目、證據缺口、適用條件與下一步驗證方式已被清楚保存，而且沒有必要繼續搜尋才能安全交付目前結果時，可以停止 B13 的處理。

若新的證據能改變結果，則交由 B15 回饋／方案三演化處理，而不是直接覆蓋歷史不確定性。

# 四、B14 結果保存

## 4.1 功能定義

B14 不是「把最後答案存成 Markdown」。

它的責任是讓一次任務完成後，未來可以回答：

```text
做了什麼？
得到什麼結果？
使用了哪些資料？
依據是什麼？
結果是否驗證？
有哪些限制？
哪些問題尚未解決？
哪些內容值得重用？
```

## 4.2 最小結果收據

```text
Result Receipt
├─ Task / Goal
├─ Result
├─ Status
├─ Verification
├─ Sources / Evidence Used
├─ Context / Version Reference
├─ Decisions
├─ Uncertainty
├─ Unresolved Issues
├─ Reusable Knowledge Candidate
├─ Related Change / Problem
└─ Traceability
```

其中 `Result` 不等於 `Knowledge`。

一次任務的輸出可能只是：

- 一次性答案
- 部分完成結果
- 暫時性結論
- 實驗結果
- 失敗結果
- 待驗證候選

只有經過適當判定後，才可能進入長期知識或正式系統。

## 4.3 與 B12、B13、B15 的接口

```text
B11 任務執行
↓
B12 結果驗證
↓
B13 保存限制／不確定性
↓
B14 保存完整結果收據
↓
B15 判斷哪些經驗值得形成後續回饋
```

B14 不負責判斷知識是否應正式升格；它負責保存，使後續判斷有資料可用。

## 4.4 外部研究結論

W3C PROV 的用途包含記錄資料的產生、交付、影響與衍生關係，並支援理解資料如何形成、驗證過程是否符合要求以及重現產生過程。citeturn1search2turn1search4

因此結果保存至少要保留足夠 provenance / traceability，而不能只存最終文字。

NASA 的知識管理也採取「保存—搜尋—再利用」的方向，並特別把 lessons learned 視為關鍵知識；其 Lessons Learned lifecycle 明確區分 Collect、Record、Disseminate、Apply。citeturn0search0turn0search2

這支持本系統把「結果保存」與「知識回饋／正式採用」分開，而不是把每次結果直接寫成正式知識。

# 五、B15 知識回饋

## 5.1 功能定義

B15 是把實際工作中的結果、問題、成功模式、失敗模式與新證據，轉換成後續知識／演化的候選訊號。

最重要的邊界是：

```text
回饋訊號 ≠ 正式知識
```

B15 不應因一次任務成功，就直接修改知識庫；也不應因一次失敗，就直接推翻既有知識。

## 5.2 最小回饋模型

```text
Feedback Signal
├─ Origin Task / Result
├─ Observation
├─ Evidence
├─ Problem / Success Pattern
├─ Reproducibility
├─ Scope
├─ Confidence / Uncertainty
├─ Candidate Knowledge Change
├─ Affected Knowledge / System
├─ Required Validation
└─ Routing
```

## 5.3 回饋分流

B15 至少應能分成：

```text
一次性觀察
↓
保存即可

可重複現象
↓
建立問題／研究候選

已多次驗證的模式
↓
形成知識變更候選

涉及結構性能力問題
↓
轉方案三

涉及能力重疊／系統重構
↓
轉方案四候選
```

因此 B15 是「訊號轉換層」，不是自動知識寫入器。

## 5.4 外部研究結論

NASA 的 Lessons Learned lifecycle 明確把 Collect、Record、Disseminate、Apply 分開；其中 lesson 的價值在於最後進入實際流程、清單、手冊、政策等，而不是只完成記錄。citeturn0search2turn0search8

NASA 也指出 lessons learned 應透過適當審查後，回饋到政策、程序、指南、標準與訓練等既有 corrective-action 系統。citeturn0search8

這對本系統的直接啟示是：

```text
工作結果
→ 回饋訊號
→ 分析／驗證
→ 決定是否形成變更
→ 交由方案三正式演化
```

而不是：

```text
工作結果
→ 直接修改知識庫
```

## 5.5 B15 與方案三的責任邊界

B15：發現值得回饋的訊號並保存／分流。

方案三 C1～C18：判斷是否需要演化、產生候選變更、分析相容性／遷移、執行與驗證變更。

B15 不取代方案三。

# 六、B16 失敗診斷

## 6.1 功能定義

B16 不是「找一個錯誤答案」。

它負責回答：

```text
這次失敗到底是哪一層失敗？
```

因為不同失敗原因需要完全不同的處理方式。

## 6.2 最小失敗分類

```text
F1 任務理解錯誤
F2 任務拆解錯誤
F3 搜尋不到必要資料
F4 找到資料但資料不足
F5 外部研究不足
F6 來源／證據不足
F7 適用性錯誤
F8 Context 選擇錯誤
F9 Context 組裝錯誤
F10 記憶／目前狀態錯誤
F11 執行能力不足
F12 結果驗證不足
F13 保存／追溯錯誤
F14 環境／工具失敗
F15 多層責任組合錯誤
```

這些是診斷類別，不代表必須建立 15 個系統。

## 6.3 最小診斷模型

```text
Failure Case
├─ Original Task
├─ Expected Result
├─ Actual Result
├─ Failure Point
├─ Failure Type
├─ Evidence
├─ Contributing Conditions
├─ Existing Capability Checked
├─ Root Cause Candidate
├─ Confidence / Uncertainty
├─ Responsible Layer
├─ Next Action
└─ Revalidation Target
```

尤其需要區分：

```text
症狀 ≠ 原因

結果錯誤
≠
知識錯誤

搜尋不到
≠
Repository 沒有資料

驗證失敗
≠
執行能力不足
```

## 6.4 B16 與問題解決系統

B16 不重新建立問題解決系統。

正確接口為：

```text
B12 FAIL
↓
B16 失敗診斷
↓
確認問題類型與責任層
↓
問題解決系統
↓
搜尋外部／既有解法
↓
候選解法
↓
最小實測／修正
↓
回 B12 重新驗證
```

若診斷結果是結構性演化問題，則可轉方案三；若發現長期能力重疊、責任混亂或需要系統重構，則形成方案四蒸餾候選。

## 6.5 外部研究結論

NIST AI RMF 將 AI 風險管理定位為設計、開發、使用與評估 AI 系統的持續性框架，並強調依使用情境調整風險管理與評估方式。citeturn0search11turn0search13

NIST AI Resource Center 也把 Testing、Evaluation、Verification、Validation（TEVV）作為 AI 實務化的重要支援方向。citeturn1search6

這支持 B16 不應只記錄「失敗」，而應把失敗定位到具體工作階段，並把診斷結果送回正確責任層，再重新驗證。

# 七、B13～B16 整體責任鏈

四項功能不是四個獨立系統，而是一條結果生命鏈：

```text
B11 任務執行
        ↓
B12 結果驗證
        ↓
 ┌──────┴──────┐
 │             │
PASS/PARTIAL   FAIL/UNKNOWN
 │             │
 ↓             ↓
B13 保存不確定性  B16 失敗診斷
 │             │
 └──────┬──────┘
        ↓
B14 結果保存
        ↓
B15 知識回饋
        ↓
方案三／問題解決／方案四（視責任而定）
```

其中 UNKNOWN 不得自動轉成 PASS；FAIL 也不得由 B16 自行修改正式知識或系統。

# 十、重要研究結論

## 結論 1：B13～B16 都必要，但不需要四個獨立系統

四項功能屬於方案二的結果管理、學習與失敗處理責任。

現有系統已經承擔相當部分能力，本輪主要工作是補足語義、責任、接口與保存格式，而不是新增四套系統。

## 結論 2：不確定性必須是一級資料，而不是文字備註

如果「未驗證」「條件限制」「證據衝突」只寫在自然語言段落裡，後續 AI 很容易遺失這些限制。

因此 B13 至少需要可被搜尋、引用、追溯的結構化記錄。

## 結論 3：結果、知識、回饋三者必須分離

```text
Result
≠
Feedback Signal
≠
Formal Knowledge
```

這是避免知識庫污染的核心邊界。

## 結論 4：失敗診斷必須先定位責任，再進入修正

不能採用：

```text
失敗 → 直接修改最近使用的東西
```

而應採用：

```text
失敗
→ 診斷
→ 找責任層
→ 使用既有問題解決流程
→ 修正
→ B12 重新驗證
```

## 結論 5：B15 是方案二與方案三的重要接口

B15 不應把方案三的演化責任提前吞進來。

它只負責讓實際工作產生的訊號不被遺失，並以明確條件轉交方案三。
