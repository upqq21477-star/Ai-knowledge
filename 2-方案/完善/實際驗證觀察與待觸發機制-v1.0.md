# 實際驗證觀察與待觸發機制 v1.0

日期：2026-09-18  
來源問題：GitHub Issue #1  
狀態：【正式建立；待自然工程觸發】

## 一、定位

本文件不是第五方案，也不是新的生命週期模型。

它是工程運作層對既有 `FIELD-PENDING` 的操作規則，負責把「尚未有自然實際使用證據」與未來實際使用事件連接起來。

## 二、核心原則

```text
SIMULATION-PASSED
↓
可以進入正常工程
↓
若實際運作尚未發生
↓
FIELD-PENDING
↓
等待自然觸發
```

不得為了消除 FIELD-PENDING 而人工創造不存在的工程案例。

FIELD-PENDING 不阻塞後續工程。

## 三、標記建立條件

符合以下任一情況即可建立 `FIELD-PENDING`：

1. 模擬驗收只能證明流程在受控案例下成立，不能證明真實工程使用。
2. 能力依賴未來才會出現的自然任務、實際資料或真實上下文。
3. 真實運作結果具有無法由模擬完整重現的因素。
4. 工程上目前沒有合理的自然案例可以執行。

如果模擬已經足以證明能力且實際使用不是該能力的必要證據，不必為形式完整而建立 pending。

## 四、待驗證標記的最小欄位

```text
Validation Observation ID
Target Type
Target ID
Target Version
Current State
Created At
Reason = 需要自然實際使用才能取得證據
Trigger Condition
Status = FIELD-PENDING
```

Target 可以是：

- 方案
- 功能
- 系統能力
- 明確工程流程

不得只以檔名作為 Target Identity；應使用既有穩定識別語義。

## 五、自然觸發

當正常工程工作第一次真正使用該 Target 時：

```text
FIELD-PENDING
↓
FIELD-OBSERVING
↓
建立 Observation Record
```

觸發不是「測試人員決定測一下」，而是正常工作本身需要該能力。

如果一次正常工作同時觸發多個 pending，可以在同一 Observation 中關聯多個 Target，但每個 Target 仍須保留自己的驗證狀態。

## 六、觀察記錄

每次自然實際使用至少記錄：

```text
Observation ID
Target ID
Target Version
Trigger / Task
Input / Context
Operation
Expected Result
Actual Result
Evidence
Outcome
Timestamp
Related Problem / Improvement Case（若有）
```

### Outcome

只能使用：

```text
NORMAL
ABNORMAL
INCONCLUSIVE
```

`INCONCLUSIVE` 不得被當作通過。

## 七、正常結果

若實際運作正常：

```text
FIELD-OBSERVING
↓
保存 Observation Record
↓
確認沒有未解決異常
↓
移除「待實際驗證」標記
```

注意：

> 移除的是 pending 標記，不是歷史紀錄。

Observation Record 永久保留於 History / Traceability 所允許的歷史範圍。

一次正常觀察也不代表永遠不會再出問題；後續新異常可以重新建立新的 Observation / Improvement Case。

## 八、異常結果

若實際運作異常：

```text
FIELD-OBSERVING
↓
保存 Observation Record
↓
保留／重新開啟 FIELD-PENDING
↓
建立 Real-World Validation / Improvement Case
↓
進入問題解決系統
```

不得直接推論：

```text
一次 FIELD 異常
→ 整個方案失敗
→ 立即 Scheme 4
```

先確認問題責任與影響，再依既有問題解決流程處理。

## 九、無法判定

若資料不足、結果不可重現或觀察本身不能判斷正常與異常：

```text
Outcome = INCONCLUSIVE
FIELD-PENDING 保留
```

不得為了關閉 pending 而把未知轉成正常。

## 十、與既有狀態模型的關係

本機制不新增平行的正式生命週期。

既有工程狀態仍依 `工程運作與持續改進方案` 管理：

```text
SIMULATION-PASSED
FIELD-PENDING
FIELD-PASSED
FIELD-PARTIAL
FIELD-FAILED
FIELD-UNKNOWN
```

本文件中的 `FIELD-OBSERVING` 是「事件處理中的操作標記」，不是新的長期生命週期狀態；事件完成後回到既有 FIELD 狀態語義。

因此：

```text
FIELD-PENDING
  ↓ 自然觸發
Observation Event = OBSERVING
  ↓
NORMAL / ABNORMAL / INCONCLUSIVE
  ↓
回寫既有 FIELD 狀態
```

## 十一、跨方案追溯

每個 Observation 必須能沿既有資料治理語義追溯：

```text
Observation
↓
Target Identity
↓
Version / State
↓
Trigger / Operation
↓
Evidence
↓
Outcome
↓
Problem / Improvement Case（若有）
```

這使未來出問題時可以回答：

- 哪個能力？
- 哪個版本？
- 當時什麼狀態？
- 在什麼自然任務中被使用？
- 實際輸入是什麼？
- 發生什麼結果？
- 有什麼證據？
- 是否已知曾經正常？
- 哪次觀察開始出現異常？

## 十二、禁止事項

1. 不得因 FIELD-PENDING 阻塞正常工程。
2. 不得把 SIMULATION-PASSED 當作 FIELD-PASSED。
3. 不得人工製造不存在的自然工程案例，只為關閉 pending。
4. 不得刪除成功 Observation 以達到「清除」效果。
5. 不得把 INCONCLUSIVE 當 NORMAL。
6. 不得因單一 FIELD 異常直接啟動 Scheme 4。
7. 不得建立與既有狀態模型衝突的新生命週期。
8. 不得修改歷史驗收紀錄來偽造 FIELD 證據。

## 十三、正式流程

```text
方案／能力
↓
SIMULATION-PASSED
↓
正常工程運作
↓
FIELD-PENDING
↓
等待自然觸發
├─ 尚未觸發 → 繼續正常工程，不阻塞
│
└─ 已觸發
    ↓
  FIELD-OBSERVING（事件標記）
    ↓
  保存 Observation
    ├─ NORMAL
    │   ↓
    │  清除 pending，保留歷史
    │
    ├─ ABNORMAL
    │   ↓
    │  保留／重新開啟 pending
    │   ↓
    │  問題解決流程
    │
    └─ INCONCLUSIVE
        ↓
       保留 pending
```

## 十四、工程意義

這個機制把「驗收」與「真實證據累積」分開：

```text
驗收回答：現在是否足以進入工程？
實際觀察回答：在自然工程中是否真的按預期運作？
```

兩者不是同一件事，也不應互相取代。

## 十五、完成條件

本機制建立後，工程不再等待 FIELD 測試活動。

接下來只需：

1. 對目前明確需要自然實際使用才能驗證的項目建立 pending 標記。
2. 正常工程繼續。
3. 自然觸發時記錄 Observation。
4. 正常則清除 pending 標記。
5. 異常則進入問題解決流程。

因此本機制的下一狀態不是「等待測試」，而是：

> 【待自然工程觸發】
