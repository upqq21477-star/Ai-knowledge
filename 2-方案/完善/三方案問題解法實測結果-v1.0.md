# 三方案問題解法實測結果-v1.0

## 狀態
【第一輪實測完成；候選解法已篩選；待後續真實案例持續驗證】

## 一、實測目的

本文件承接「三方案問題發現與舊搜尋方案解法驗證-v1.0」，實際套用既有「搜尋研究方案」與「搜尋原理」，對三方案協作中已發現的問題尋找外部成熟方法，再比較候選解法，避免直接新增系統或直接修改既有架構。

本輪只建立新的驗證結果，不修改任何舊檔案。

## 二、實際套用的舊搜尋流程

依既有「搜尋研究方案」：

```text
問題
→ 研究問題／資訊需求
→ 查詢策略
→ 資料探索與搜尋
→ 候選資料
→ 來源與證據分析
→ 比較與採用判斷
→ 測試／驗證
→ 結論與限制
```

依「搜尋原理」控制搜尋：

- 先縮小問題與搜尋目的。
- 不把搜尋結果直接當成答案。
- 同時考慮關鍵字、語意、分類與範圍。
- 結果不足才改寫查詢或擴大範圍。
- 結果足夠或邊際收益下降即停止。
- 外部方法只能作為候選，必須回到本專案條件測試。

## 三、問題 A：變更後不知道哪些資料受影響

### 研究問題

如果共同資料語義、主張、條件或關係發生變更，目前系統是否能可靠找出需要重新檢查的下游資料？

### 資訊需求

需要找到：

1. 變更對象。
2. 直接依賴。
3. 間接下游影響。
4. 需要重新驗證的對象。
5. 變更前後的可追溯關係。

### 外部搜尋結果

成熟資料治理與資料工程系統普遍使用 data lineage 與 impact analysis 追蹤資料依賴與下游影響。Microsoft Fabric 的 impact analysis 可從 lineage 觀察直接子項、下游一層與全部下游受影響項目；Google Cloud 也將 lineage 用於變更影響分析與錯誤追溯。citeturn0search5turn0search11

軟體工程的 Change Impact Analysis 研究則將 change request 與受影響構件的分析視為降低變更風險與維護成本的方法。citeturn1search1

### 候選方案比較

| 候選 | 方法 | 解決能力 | 複雜度 | 與目前架構相容 |
|---|---|---|---|---|
| A1 | 只記錄「此版本修正了什麼」 | 只能說明變更本身 | 低 | 高 |
| A2 | 變更對象＋直接／下游依賴＋影響分析 | 能找出重新驗證範圍 | 中 | 高 |
| A3 | 立即建立完整知識圖譜 | 理論上可做廣泛關係追蹤 | 高 | 未證明必要 |

### 最小測試

以目前三個新系統及共同資料規則作測試對象，假設「核心資料類型邊界」中的一條語義規則發生變更。

A1 可以記錄：

```text
某規則由舊版變成新版。
```

但無法直接回答：

```text
哪些系統使用這條規則？
哪些方案中的主張受影響？
哪些既有測試必須重跑？
```

A2 可以要求變更記錄至少指出：

```text
變更對象
→ 直接依賴
→ 間接下游
→ 需重新驗證項目
→ 影響判斷
```

因此在目前問題範圍內，A2 已經解決核心缺口；A3 尚沒有實測證明其額外成本有必要。

### 實測判定

【目前採用候選：A2】

不是建立完整知識圖譜，而是在既有關係與版本模型上增加「影響對象／影響分析」能力。

## 四、問題 B：跨方案失敗事件無法重建

### 研究問題

當 AI 搜尋、判斷、執行或驗證失敗時，能否在之後重建「當時使用了什麼資料、得到什麼結果、在哪裡失敗」？

### 資訊需求

至少需要：

- 任務。
- 搜尋目的／查詢。
- 使用的資料或證據。
- 資料版本或時間。
- 執行結果。
- 驗證結果。
- 失敗位置。

### 外部搜尋結果

近期 LLM agent provenance 研究將 retrieval evidence、tool output、memory、intermediate claims、actions 與 final answer 放進可追蹤的 execution provenance，目的就是讓失敗原因、證據來源與執行路徑可以重建。citeturn1academia24

RAG 實務也逐漸把 provenance 與 citations 分開：citation 是使用者可見的來源指向，而 provenance 是能追蹤來源版本、轉換、檢索與上下文的內部鏈路。citeturn0search2turn0search8

### 候選方案比較

| 候選 | 方法 | 解決能力 | 複雜度 | 與目前架構相容 |
|---|---|---|---|---|
| B1 | 自由文字記錄失敗原因 | 可閱讀，但難重建 | 低 | 高 |
| B2 | 最小執行／搜尋收據（receipt） | 可重建關鍵輸入、結果、驗證與失敗 | 中 | 高 |
| B3 | 完整 agent observability／trace 平台 | 可記錄大量執行細節 | 高 | 未證明必要 |

### 最小測試

假設 AI 嘗試判斷某資料是否可採用，但因版本不相容而失敗。

B1：

```text
因版本問題，資料不可採用。
```

這句話無法保證下次能知道：使用了哪個版本、哪個搜尋結果、哪個判斷條件。

B2 最小記錄：

```text
任務
搜尋／取得資料
資料識別與版本
使用條件
執行結果
驗證結果
失敗原因
```

這已足以支援後續問題定位與重新驗證，不需要先建立完整 observability 平台。

### 實測判定

【目前採用候選：B2】

正式名稱暫不固定為特定產品或平台；先確立「最小可回溯執行／搜尋收據」概念。

## 五、問題 C：跨方案發現共同問題後沒有安全的變更入口

### 研究問題

當三方案協作發現共同資料語義不足時，如何提出變更，而不是直接修改治理規則或某一方案？

### 外部搜尋結果

資料治理實務使用 Change Request 與 Impact Assessment 將變更描述、影響分析、風險與批准流程分開。官方資料治理框架的 Change Request & Impact Assessment 範本包含變更識別、描述與影響評估；相關治理流程要求評估資料模型、治理政策、技術與流程的影響後再決策。citeturn1search25

SAP 等成熟治理系統也將 change request 設計成具狀態、處理步驟與角色的流程，而不是直接修改資料模型。citeturn1search0turn1search4

### 候選方案比較

| 候選 | 方法 | 解決能力 | 複雜度 | 與目前架構相容 |
|---|---|---|---|---|
| C1 | 發現問題後直接修改治理資料 | 快，但破壞責任邊界 | 低 | 低 |
| C2 | 建立變更請求＋影響分析＋驗證＋決策 | 可追蹤、可回退、保留責任邊界 | 中 | 高 |
| C3 | 導入完整 ITSM／工作流平台 | 可高度流程化 | 高 | 未證明必要 |

### 最小測試

假設三方案發現「目前共同資料類型不足以描述某一類資料」。

C1 直接修改核心資料類型會造成治理層在沒有完成影響分析前就被改動。

C2 則形成：

```text
問題觀察
→ 變更請求
→ 影響分析
→ 候選修改
→ 測試
→ 採用／保留／拒絕
→ 歷史記錄
```

這與目前三方案的責任邊界相容，而且不要求導入外部工作流產品。

### 實測判定

【目前採用候選：C2】

先建立「變更請求」作為跨方案問題進入治理／演化流程的資料物件，不直接確定具體工作流軟體。

## 六、混合搜尋是否為最優解

外部資料顯示，生產 RAG 常將 hybrid search、metadata filtering、reranking 等作為逐步增加成本的檢索優化手段，而不是預設所有問題都使用最高複雜度方法。citeturn0search0

因此本輪沒有把「混合搜尋」直接判為最佳方案。

目前舊搜尋原理已經允許：

```text
分類／範圍
＋關鍵字
＋語意
＋必要時擴展
```

這實際上已經是「可組合搜尋方式」的設計。若未來真實案例顯示單一方式漏失重要資料，再以具體案例測試 hybrid retrieval，而不是先建立固定技術架構。

## 七、第一輪最優解判定

本輪不使用單一分數選出「最高分方案」，而採工程約束判定：

1. 是否直接解決已確認問題。
2. 是否能被回溯與驗證。
3. 是否維持三方案責任邊界。
4. 是否能與現有資料關係、狀態、版本模型相容。
5. 是否避免不必要的新系統或大型技術依賴。
6. 是否能進入後續真實案例驗證。

依以上條件，本輪得到：

```text
問題 A → A2：變更對象＋依賴＋影響分析
問題 B → B2：最小執行／搜尋收據
問題 C → C2：變更請求＋影響分析＋驗證＋決策
```

這是「目前可採用的最小充分解」，不是宣稱在所有知識庫架構中的絕對最佳解。

## 八、仍未證明的部分

本輪仍不足以證明：

- 影響分析是否需要完整圖結構。
- receipt 的最小欄位是否已經穩定。
- 變更請求是否需要獨立資料類型，或可先作為觀察／決策的專門結構。
- 三方案連續處理真實多輪變更時是否會產生新的責任重疊。
- 混合搜尋在本專案真實資料量下是否值得增加技術複雜度。

因此本輪只確認候選方向，不修改三個正式方案，也不建立第四方案。
