# 問題解決：統御異常偵測與問題解決路由第二輪案例驗證 v1.0

日期：2026-09-17
狀態：【第二輪案例驗證；不建立新正式系統】

## 一、驗證目的

第一輪已證明「施工階段越級」可以用最小 Stage-Gate + Transition Guard 阻止；但這只證明統御能力的一個面向：守住階段轉移。

本輪進一步驗證統御是否能處理三種不同情況：

1. 前置條件未完成，但工作看似合理。
2. 執行結果與預期狀態不一致。
3. 發生異常後，能否提出「進入問題解決流程」而不是自行發明大型解法。

外部比較顯示，近期 AgentOps 與 agent workflow 實務普遍將監控、異常偵測、根因分析與處置視為連續閉環；workflow orchestration 也常以狀態、guardrail、gate 與可追溯執行作為控制點。citeturn0search0turn0search3turn0search8

因此本輪不把「異常偵測」理解成單純監控，而是驗證：

```text
預期狀態
↓
實際狀態
↓
差異判定
↓
異常分類
↓
處置建議
↓
必要時進入問題解決流程
```

## 二、案例 A：前置條件未完成

### 輸入

```text
目前階段：⑥
目標工作：建立⑦跨系統長流程實測
⑥尚未完成正式 Gate
但已有部分接口文件與測試資料
```

### 潛在錯誤

「已有大量資料」容易被誤判為「⑥已完成」。

### 統御檢查

```text
文件存在 ≠ 階段完成
案例資料存在 ≠ Gate 通過
部分工作完成 ≠ 前置條件全部完成
```

### 判定

```text
⑥ Gate = 未通過
⑦ = LOCKED
```

### 預期警報

```text
【施工警報】
類型：前置條件未完成
目標：⑦
阻斷：⑥ Gate 尚未通過
建議：停止⑦正式施工，回到⑥完成驗收
```

### 結果

PASS：能阻止「資料很多」被誤判成「階段完成」。

## 三、案例 B：執行結果偏離預期

### 輸入

假設目前已合法進入某一階段，工作本身沒有越級問題。

```text
Expected State：
完成指定接口驗證 → 產生 Validation Receipt → 狀態更新為「已驗證」

Actual State：
接口驗證完成，但沒有產生 Validation Receipt
```

### 判定

這不是「下一階段越級」，而是「預期產物缺失／狀態未閉合」。

因此不能只使用 Stage-Gate 判斷。

需要第二層檢查：

```text
Expected Output / State
        vs
Actual Output / State
```

### 預期警報

```text
【施工警報】
類型：執行結果與預期狀態不一致
預期：Validation Receipt + 已驗證狀態
實際：驗證完成但缺少 Receipt
風險：後續無法可靠追溯驗證結果
建議：暫停依賴該結果的後續工作，進入問題解決流程確認缺失原因
```

### 結果

PASS：證明統御的責任不能只看「現在在哪一階段」，還必須檢查「執行後是否得到應有狀態與產物」。

## 四、案例 C：異常後的問題解決路由

### 輸入

發現：同一類異常已連續出現兩次。

```text
第一次：Receipt 缺失
第二次：同類 Receipt 再次缺失
```

### 判斷

單次異常可以先局部修復；重複異常則開始具有「能力缺口」訊號。

此時統御不應直接宣布「建立統御系統 v1.0」或其他大型系統，而應：

```text
異常
↓
判斷是否重複／結構性
↓
是
↓
提出問題解決流程建議
```

問題解決流程已有正式入口：問題確認 → 盤點現有能力 → 搜尋研究 → 外部方法／工具／案例比較 → 候選解法 → 最小實測 → 判定 → 回饋。citeturn174file0L2-L2

### 預期警報

```text
【結構性異常警報】
類型：同類異常重複發生
問題：Validation Receipt 連續缺失
風險：現有流程可能存在系統性缺口
建議：進入問題解決方案調查，不直接建立新系統
```

### 結果

PASS：統御可以把「監控結果」轉成「問題解決入口」，而不是把異常偵測與解法建立混成同一職責。

## 五、案例 D：正常變化不得誤報

統御若只會報警，也會造成另一種問題：把正常施工變化全部視為異常。

例如：

```text
原預估：本案例需要 3 個步驟
實際：因發現額外證據，需要 5 個步驟
```

只要：

- 仍在目前合法階段；
- 沒有違反禁止事項；
- 新增步驟有合理依據；
- 不影響前置條件；
- 最終仍能達成該階段 Exit Criteria；

就不能只因「步驟數增加」判定為結構性異常。

### 結果

PASS 條件：統御必須比較「規則與預期狀態」，而不是單純比較「原計畫文字」。

## 六、第二輪得到的最小統御模型

目前不需要完整 Planner；最小能力已可整理為五個連續檢查：

```text
① Stage Check
目前是否在合法階段？

② Gate Check
前置條件是否全部滿足？

③ Action Check
目前準備執行的工作是否屬於允許範圍？

④ Result Check
執行後的實際狀態／產物是否符合預期？

⑤ Anomaly Routing
若不符合：
一般偏差 → 局部修正／重新驗證
阻斷異常 → 停止後續依賴工作
重複／結構性異常 → 建議進入問題解決流程
```

這形成：

```text
施工
↓
Stage Check
↓
Gate Check
↓
Action Check
↓
執行
↓
Result Check
↓
正常 → 繼續
異常 → 分類 → 警報
             ↓
       結構性／重複？
          ↓是
       問題解決流程
             ↓
       候選解法／實測
             ↓
       結果回饋統御
```

## 七、目前尚未正式建立的內容

本輪不能推出以下結論：

- 不代表已經建立完整統御系統。
- 不代表需要獨立資料庫。
- 不代表需要完整 JSON Schema。
- 不代表需要自主 Agent Planner。
- 不代表所有異常都應自動阻斷。
- 不代表所有問題都要進入問題解決流程。

目前只證明最小「守門 + 結果檢查 + 異常路由」值得繼續驗證。

## 八、與外部方法的比對結論

外部方法支持以下共同方向：

1. 工作流應具有明確狀態與允許轉移，而不是完全依賴 Agent 自己記憶順序。
2. 關鍵階段可以使用 Guard / Gate 在執行前攔截非法轉移。
3. Runtime monitoring 應能發現異常，並連接後續 investigation / resolution，而非只產生儀表板。
4. 高風險或不可逆操作通常需要明確的 escalation / approval / pause 機制。
5. 執行記錄、決策原因與狀態變更需要可追溯。

近期研究與實務資料亦指出，AgentOps 的監控、異常偵測、根因分析與處置應形成連續生命週期，而不是彼此孤立的功能。citeturn0search3turn0search5

因此本專案的「統御」方向與外部成熟做法一致，但目前只採用其中必要的最小能力，不提前複製完整企業級架構。

## 十、第三輪驗證條件

下一輪不再只測施工順序。

需要測試：

1. 同時存在兩個異常時，能否判斷主要阻斷異常。
2. 異常恢復後，能否重新判斷是否解除 Lock。
3. 問題解決流程回傳結果後，統御能否更新 Expected / Actual State。
4. 新舊版本工作記憶衝突時，能否識別舊資料而不採用。
5. 一項工作同時符合多個階段描述時，能否依目前 Gate 判定其真正歸屬。

第三輪通過前，⑧仍保持「驗證中」，⑨維持 LOCKED。

## 十二、結論

第二輪已把統御能力從「守住施工階段」擴展到：

```text
守階段
→ 守前置條件
→ 守允許動作
→ 檢查執行結果
→ 發現異常
→ 發出警報
→ 判斷是否阻斷
→ 必要時建議進入問題解決流程
→ 接收結果後重新評估
```

但仍屬案例驗證，不升格為正式統御系統。
