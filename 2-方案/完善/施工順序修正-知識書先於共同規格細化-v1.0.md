# 施工順序修正：知識書先於共同規格細化 v1.0

日期：2026-09-17
狀態：【本輪修正；取代前一輪施工順序判斷】

## 一、修正原因

前一輪將「知識書原子化規格」排在「圖書館式知識管理」之後，順序不正確。

原因是：

> 在沒有先研究成熟的知識庫／圖書館／Catalog／Index／Retrieval／Knowledge Atomization 實作方式前，不能直接假定我們的知識書應該採用什麼原子粒度、文件形式、Metadata 邊界與檢索單位。

如果先定義知識書格式，再研究圖書館管理，很可能因研究結果改變知識單位而重新設計一次。

因此本輪正式修正施工順序。

## 二、正確順序

```text
共同規格與目前新系統基線
↓
搜尋／研究成熟外部方法
↓
研究知識庫、圖書館 Catalog、Metadata、Index、Retrieval、Knowledge Atomization
↓
比較不同知識組織方式
↓
形成「知識書應如何存在」的候選模型
↓
用現有知識與實際 AI 任務驗證
↓
確認知識書最小單位、文件形式、Metadata 邊界與歷史／版本處理
↓
再建立圖書館式知識管理方案／系統能力
↓
用圖書館管理需求反向驗證知識書規格
↓
共同資料契約與跨系統接口最終化
↓
正式實作
```

這裡的「共同規格」指目前已經存在的共同語義與施工基線，不代表必須先把所有細節規格全部封死。

## 三、重要區分

### 目前可以先確定

- 知識是內容資產，不等於管理系統。
- 知識書應保持語義清楚、低耦合、可獨立理解。
- AI 不應每次載入全部知識。
- 大量知識需要 Catalog、Index、Retrieval、Context Assembly 等管理能力。
- 圖書館式管理是為了管理大量知識，不應反過來改變知識本身的基本語義。

### 目前不能提前確定

- 一個知識書究竟應該多大。
- 是否一個主張就是一個知識單位。
- 是否採用「原子知識」作為正式單位。
- 一個 Markdown 是否應包含一個或多個語義單位。
- Metadata 應放在知識書內還是由 Catalog 管理。
- Index 應以文件、段落、語義單位或其他粒度建立。
- 是否需要知識圖譜、向量資料庫或其他索引技術。

這些都必須先研究與實測。

## 四、外部研究初步結果

本輪網路研究得到幾個重要訊號：

1. Library of Congress 的目錄與資源發現模型明確區分「被描述的資源」與「描述／Metadata／檢索系統」，並強調檢索單位與描述粒度需要依資源與發現任務決定，而不是固定只有一種粒度。citeturn0search2turn0search12

2. Library of Congress 的數位典藏實務也沒有要求所有資料使用單一 Metadata 標準；不同內容類型可以使用不同描述標準，再由共同的管理與發現機制協調。citeturn0search12

3. Microsoft 的 RAG 架構將原始內容、chunk、metadata、index、retrieval 與 context 組裝分開處理，並指出 Metadata 應依實際查詢與品質需求決定。這支持「不要先把所有管理資訊硬塞進知識書」。citeturn0search15turn0search16

4. Microsoft Research 的 PIKE-RAG 明確採用不同知識粒度，並包含 knowledge atomization；這說明「原子化」可以是檢索與推理層的能力，不代表原始知識文件必須全部拆成最小原子。citeturn0search8turn0search18

因此目前較合理的研究方向不是直接宣布「知識書 = 原子知識」，而是研究：

```text
原始知識書
＋
語義單位
＋
Catalog Metadata
＋
Retrieval Index
＋
Context Assembly
```

是否應該分層，以及每層的最小責任。

## 五、對原施工計畫的修正

原本：

```text
⑨ 知識書原子化規格
⑩ 圖書館式知識管理
```

修正為：

```text
⑨ 圖書館／知識管理外部研究
↓
⑩ 知識書形式與粒度設計
↓
⑪ 知識書＋圖書館管理聯合驗證
↓
⑫ 再確認共同資料契約與接口
↓
⑬ 正式實作
```

注意：這不是立即建立完整圖書館系統，而是先使用「圖書館方案」作為研究框架，研究它需要什麼樣的知識資源結構。

## 六、統御能力的實際意義

這個案例正好證明統御能力需要具備：

```text
需求很重要
≠
現在立刻製作
```

正確判斷應該是：

```text
圖書館需求成立
↓
但知識資源的實際形式尚未確定
↓
先研究成熟方案與實作
↓
由研究結果反推知識書設計
↓
再設計管理系統
```

這可以避免兩次返工：

第一次錯誤：先定義知識書，再發現圖書館需求不適合。

第二次錯誤：先做圖書館，再發現底層知識書格式不適合。

## 七、下一步

下一階段正式任務不是製作圖書館系統，也不是製作知識書 Schema。

而是：

> 使用搜尋研究方案，系統性比較成熟的知識庫、數位圖書館、Catalog、Metadata、Index、RAG、Knowledge Atomization 做法，建立候選模型，再用我們現有知識庫案例進行驗證。

研究完成前：

- 不固定知識書粒度。
- 不固定原子化形式。
- 不固定 Metadata Schema。
- 不固定 Index 技術。
- 不固定資料庫／向量資料庫／知識圖譜。

研究完成後，再決定下一層設計。
