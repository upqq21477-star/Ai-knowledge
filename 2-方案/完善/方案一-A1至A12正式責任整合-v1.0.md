## 一、文件目的

本文件將 A1～A12 的逐項研究結果整合為一套單一責任模型，供後續整體模擬驗收與回歸驗證使用。

本文件不是新增 A13 以後的功能，也不凍結最終實作 Schema。正式功能清單以 Repository 現行正式功能拆解為準；方案一正式範圍為 A1～A12。

## 二、整合後責任鏈

```text
A1 Identity
  ↓
A2 Metadata
  ↓
A3 Source
  ↓
A4 Claim / Evidence
  ↓
A5 State
  ↓
A6 Version
  ↓

  ↓
A9 History
  ↓

  ↓

  ↓

```

實際運作不是單向流水線，而是由 Identity 作為穩定對象基礎，由 Metadata 描述對象，由 Source/Evidence/Claim 保存依據，由 State/Version/Lifecycle 表達時間與有效性，由 Relationship 建立對象間語義連接，再由 History/Traceability/Impact 支撐追溯、變更與影響判斷，最後由 A12 維持四方案之間必要且穩定的共同語義。

## 三、各功能正式責任

### A1 Identity

負責回答「這是哪一個邏輯對象」。

必須區分 Logical Identity、Stable Identifier、Name、Alias、Current Path、Version Reference、State Reference。

禁止把檔名、路徑或單一 Git SHA 直接視為永久邏輯身份。

### A2 Metadata

負責提供最小充分描述，使其他系統能判斷對象是什麼、目前狀態、版本、來源、關係與是否需要讀取全文。

Metadata 不等於 Summary、全文、AI Memory 或 Git Commit。

### A3 Source

負責保存內容的來源與衍生來源。

Source 與 Evidence 必須分開；來源可以提供多個 Evidence。

### A4 Claim / Evidence

負責表達主張與證據之間的支撐關係，並維持 Observation、Claim、Evidence、Source、Inference、Decision 的區分。

禁止因內容寫法像事實，就將 AI 推論自動提升為已確認知識。

### A5 State

負責描述對象在特定狀態維度下目前的有效狀態。

State 不得與 Version、Lifecycle、History、Evidence 混為單一 status 欄位。

必要時應能區分 validation_state、usage_state、lifecycle_state 等不同維度。

### A6 Version

負責表達同一 Logical Identity 的內容／結構／規格演化。

必須能表示版本間的 revision 關係，並區分 Logical Identity、Version、Git Commit、Path、Filename。

### A7 Relationship

負責以具語義、具方向的關係連接已識別對象。

最低模型應能表達 subject、relation_type、object，並可附加 evidence、source、time、note。

禁止以單一 related_to 取代所有關係語義。

### A8 Lifecycle

負責表達對象從建立、使用、修正、取代、退役到歷史保存的生命週期。

Lifecycle 描述完整生命歷程；不能直接取代某一時間點的 State。

### A9 History

負責保存已離開目前工作狀態或已發生的歷史事件、狀態、版本與變更原因。

歷史資料必須可追溯，但不得因仍存在 Repository 就被自動視為目前有效資料。

### A10 Traceability

負責讓結果、Claim、Evidence、Source、Version/Snapshot 形成可回溯鏈。

最小追溯鏈：

```text
Result
  → derived_from
Claim
  → supported_by
Evidence
  → located_in / derived_from
Source
  → represented_as
Version / Snapshot
```

### A11 Impact

負責識別某項變更可能影響的關係、依賴、使用者、系統、驗證案例或下游對象。

Impact 是影響範圍分析，不等於保證實際結果。

### A12 Cross-Scheme Semantics

負責維持四方案真正需要共享的共同語義，例如 Identity、State、Version、Relationship、Evidence、Traceability 等。

共同語義層必須小而穩定；不得把所有方案內部流程強行集中成單一結構。

## 四、核心責任邊界

```text
Identity  → 對象是誰
Metadata  → 如何描述與辨識
Source    → 從哪裡來
Evidence  → 哪些內容支撐主張
Claim     → 主張是什麼
State     → 現在處於什麼狀態
Version   → 如何演化
Relationship → 與其他對象有什麼語義關係
Lifecycle → 從建立到退出如何經歷
History   → 過去發生過什麼
Traceability → 如何一路追溯
Impact    → 改變可能影響什麼
Cross-Scheme Semantics → 四方案需要共同理解什麼
```

## 五、整合規則

1. 不因兩項功能都有「關係」字樣就合併責任。
2. 不因同一文件同時具有 Source、Evidence、Claim 就取消三者語義區分。
3. 不以單一 status 欄位承擔 State、Lifecycle、Validation、Usage 等不同維度。
4. 不以 Git Commit 取代 Logical Identity 或 Version。
5. 不因存在歷史文件就將其視為目前有效資料。
6. 不因存在引用就判定 Claim 已驗證。
7. 不因 Impact 分析指出可能受影響，就宣稱實際結果已發生。
8. A12 只共享必要語義，不集中所有方案內部流程。
9. 不在本階段直接建立大型 Knowledge Graph / RDF Store 作為必要條件。
10. 不在正式責任整合階段直接宣稱實際運作驗收完成。

## 六、與其他方案的介面

### 方案一 → 方案二

方案一提供可識別、可描述、可追溯、具狀態與版本資訊的治理對象；方案二負責搜尋、探索、上下文組裝與任務使用。

### 方案二 → 方案一

方案二在使用知識、來源、證據與結果後，將必要的結果、來源、驗證與不確定性回寫至治理語義。

### 方案一 → 方案三

方案一提供 Identity、State、Version、Relationship、History、Traceability、Impact 等治理基礎，使方案三能辨識變更對象、版本與影響範圍。

### 方案三 → 方案一

方案三完成變更後，將新的目前狀態、版本、歷史與追溯資訊形成新的治理基準。

### 方案一 → 方案四

方案一提供能力、資料、關係、版本、歷史與影響資訊，供方案四進行長期能力蒸餾與重構分析。

### 方案四 → 方案一

方案四完成重構後，透過新基準、歷史保存與關係更新，使新的結構重新成為可治理對象。

## 七、整體驗收入口

下一階段不是重新研究 A1～A12，而是以本整合結果建立整體模擬案例。

最低驗收面向：

```text
1. Identity / Path / Filename 分離
2. Metadata 最小充分性
3. Source / Evidence / Claim 分離
4. State / Version 分離
5. Lifecycle / History 分離
6. Typed Relationship 正確性
7. Traceability 完整性
8. Impact 範圍與實際結果區分
9. Cross-Scheme Semantics 邊界
10. 歷史資料不得污染目前狀態
11. 版本與狀態變更後仍可追溯
12. 錯誤輸入、衝突資料與不確定性不得被提升為確定事實
```
