## 一、研究範圍

本批次由工程運作的 Batch Source Verification Gate 重新從正式功能清單推導，正式下一批為方案三 C1～C4。正式功能定義如下：

- C1 變更訊號接收：接收新需求、新證據、失敗、過期、條件變更、外部方法更新等訊號。
- C2 變更確認：判斷訊號是否真的代表需要改變。
- C3 變更對象識別：找出資料、知識、能力、系統或方案中的真正變更對象。
- C4 變更目標確認：回答這次到底要改善什麼。

本研究不修改舊功能清單，也不把研究結論直接升格為正式功能定義。

---

# 二、核心判斷

C1～C4 不是「收到任何新資訊就修改 Repository」的自動修改鏈，而是方案三的 Change Intake / Change Qualification 前段。

正確責任鏈為：

```text
C1 變更訊號接收
↓
C2 變更確認
↓
C3 變更對象識別
↓
C4 變更目標確認
↓
C5 既有能力盤點
↓
C6 影響分析
...
```

四者必須分離，原因如下：

```text
有訊號 ≠ 有變更
有變更 ≠ 已知道變更對象
知道對象 ≠ 已知道應改善什麼
```

因此不能讓 C1 直接跳到 C8 候選變更，也不能讓 AI 看到新資料後直接修改正式知識。

# 三、C1 變更訊號接收

## 3.1 定義

C1 負責把可能代表「需要重新評估目前結構」的事件轉成可追蹤的 Change Signal，而不是判定變更成立。

可接受來源包括：

- 新需求
- 新證據
- 實際任務失敗
- 驗證結果改變
- 資料過期
- 條件／環境改變
- 外部方法、工具、標準更新
- 使用者回饋
- 發現現有內容與實際狀況不一致

## 3.2 最小輸出

```text
Signal ID
Signal Type
Observed At
Source / Origin
Affected Candidate
Observation
Evidence / Reference
Current Baseline Reference
Uncertainty
```

其中 Observation 與「已確認需要變更」必須分離。

## 3.3 停止條件

若只有模糊意見、沒有可追溯來源、沒有任何可定位對象，C1 可以保存為低可信訊號，但不得直接進入變更執行。

---

# 四、C2 變更確認

## 4.1 定義

C2 判斷收到的訊號是否足以代表需要進入變更評估。

至少檢查：

- 是否為真實的新資訊或事件
- 是否與目前基準存在差異
- 差異是否具有實際意義
- 是否可能影響目前使用方式、正確性、適用性或責任
- 是否只是重複訊息、個人偏好或未證實猜測

## 4.2 輸出

```text
CONFIRMED-CHANGE-SIGNAL
NO-CHANGE
NEEDS-MORE-EVIDENCE
DUPLICATE
OUT-OF-SCOPE
```

C2 不負責決定怎麼改。

## 4.3 關鍵原則

「最新」不等於「應採用」。

新資料只有在與目前基準存在可證實且有意義的差異時，才可能形成變更案件。

---

# 五、C3 變更對象識別

## 5.1 定義

C3 將已確認的變更訊號定位到真正受影響的對象。

可能對象：

```text
資料
知識
Claim
Evidence
能力
系統
流程
方案
關係／依賴
狀態／版本
```

## 5.2 身份要求

不能只依靠檔名或路徑定位。

應優先使用方案一的 Identity / Stable Identifier / Relationship 語義，並保留目前路徑作為輔助定位資訊。

## 5.3 多對象情況

一個訊號可能涉及多個對象。例如一項規則改變可能同時影響：

```text
知識 → 系統 → 方案 → 驗證案例
```

C3 應建立對象集合與關係，而不是強迫選出唯一對象。

---

# 六、C4 變更目標確認

## 6.1 定義

C4 把「這裡有問題／新資料」轉成可驗證的變更目標。

例如：

錯誤：
> 這份知識需要更新。

較完整：
> 修正目前規則，使其能反映新條件 X，並保持既有使用案例 Y 正常運作。

## 6.2 最小輸出

```text
Change Objective
Current Problem / Gap
Desired Future State
Constraints
Success Criteria
Non-Goals
Affected Objects
Evidence Basis
Uncertainty
```

## 6.3 Non-Goals 必須保存

C4 不只定義「要做什麼」，還應明確定義「這次不處理什麼」，避免小變更無限制擴張成整體重構。

---

# 七、四者責任邊界

| 功能 | 負責 | 不負責 |
|---|---|---|
| C1 | 接收、標準化、保存變更訊號 | 判定變更成立、設計解法 |
| C2 | 判斷訊號是否值得進入變更流程 | 決定如何修改 |
| C3 | 定位真正變更對象及其關係 | 決定修改方案 |
| C4 | 定義改善目標、限制、成功條件 | 執行變更、判定最終成功 |

# 八、與既有方案／系統的關係

## 8.1 方案一

直接使用 Identity、Stable Identifier、Source、Evidence、State、Version、Relationship、Impact 等共同語義。

不建立第二套身份、版本或證據模型。

## 8.2 方案二

方案二的 B12 結果驗證、B15 知識回饋、B16 失敗診斷都可能產生 C1 Change Signal。

但「使用結果產生訊號」不等於「方案三直接接受該結論為正式變更」。仍需經過 C2。

## 8.3 問題解決系統

問題解決系統可以提供已確認問題或候選修正作為 C1/C2 的輸入，但方案三仍負責判斷它是否屬於資料／知識／能力／系統／方案演化問題。

## 8.4 工程運作與持續改進方案

工程運作中的實際問題可形成 C1 訊號，但工程運作方案負責工作調度與責任路由，方案三負責正式演化判斷。

# 九、外部研究比較

## 9.1 NIST Engineering Change Management

NIST 的 Engineering Change Management 研究指出，系統交付後仍可能因原始規格錯誤、客戶回饋、競爭或改善想法而需要重新檢視已完成的決策與工作。這支持把「變更訊號」與後續工程變更管理分離，而不是假設完成即永久固定。citeturn0search1turn0search4

## 9.2 IBM Configuration Management

IBM 的 Configuration Management 將 configuration identification、change control、status accounting、audit 分開；change control 包含提出變更、評估、批准、實施與記錄，status accounting 則保存位置、版本、狀態與變更歷史。這與本批次將 C1～C4 定位為「變更前段」而非完整變更執行流程一致。citeturn0search0turn0search7

## 9.3 NIST / IBM Change Control

變更控制通常要求先提出、說明、評估、決策，再實施與驗證。IBM 的 CM-3 指引也將 proposed change 的審查、決策紀錄、實施、保存紀錄與後續監控分開。這支持 C2 不應直接等同於「批准修改」，C3/C4 則應提供後續影響與變更決策所需的結構化資訊。citeturn0search3turn0search5

# 十、研究後正式判斷

C1～C4 均有必要，但不應各自建立大型獨立系統。

最佳結構為：

```text
C1 Change Signal Intake
        ↓
C2 Change Qualification
        ↓
C3 Change Target Identification
        ↓
C4 Change Objective Definition
        ↓
C5 Existing Capability Assessment
```

可由同一個方案三 Change Case / Evolution Case 工作流承載，但每項功能保持獨立責任。

本批次沒有發現需要建立新的大型基礎系統。

真正需要補強的是：

1. Change Signal 的最小收據格式。
2. Change Signal 與正式 Change Case 的邊界。
3. C2 的「無變更／證據不足」退出路徑。
4. C3 對多對象與關係的表達。
5. C4 必須保存 Success Criteria 與 Non-Goals。
6. C1～C4 不得直接修改正式知識或系統。
