## 一、目的

驗證方案三在正常演化完成後，如果重新驗證失敗，能否正確進入問題診斷與修正，而不是把失敗直接視為更新完成，或無限重做整個方案。

本案例為條件模擬，不代表方案三已完成實戰驗證。

## 二、案例

假設知識項目由 A 更新為 A'。

更新前完成：

```text
Change
→ Impact
→ Compatibility
→ Migration
→ Validation
```

但在實際驗證條件中，某個下游任務仍得到不符合預期的結果。

因此：

```text
Validation = FAIL
```

## 三、第一階段：失敗診斷

不能直接回到「重新更新」。

先判斷：

```text
資料／知識內容錯誤？
版本／狀態錯誤？
相容性判斷錯誤？
遷移錯誤？
Context／使用方式錯誤？
下游系統能力不足？
驗證條件本身錯誤？
```

本案例假定診斷結果為：

`Compatibility 判斷遺漏一個仍使用舊格式的下游依賴。`

## 四、第二階段：問題解決

因問題已超出單純內容修正，轉入既有問題解決流程：

```text
問題確認
↓
既有能力盤點
↓
外部研究／比較（必要時）
↓
候選解法
↓
最小實測
↓
判定
```

不建立第二套問題解決系統。

## 五、第三階段：修正

候選修正：

```text
補充下游相容性依賴
→ 建立明確遷移條件
→ 更新候選變更
```

狀態：

`FIX-IMPLEMENTED`

注意：此狀態不能直接等於 RESOLVED。

## 六、第四階段：重新驗證

必須重新使用原本失敗的條件驗證：

```text
原任務
+
原資料條件
+
原下游依賴
+
修正後版本
```

結果：PASS。

再檢查是否有新的相容性副作用。

模擬結果：未發現阻塞性副作用。

判定：

```text
RESOLVED
```

## 七、失敗注入：修正再次失敗

第二次模擬：假設修正後仍 FAIL。

正確行為：

```text
REVALIDATING
↓
FAIL
↓
REDIAGNOSE
```

禁止：

```text
FAIL
→ 重複相同修正
→ FAIL
→ 重複相同修正
→ ……
```

應檢查：

- 原問題定義是否錯誤。
- 責任層是否判錯。
- 是否存在另一個依賴。
- 是否應轉入第四方案。
- 是否需要暫緩採用。

## 八、失敗注入：結構性問題

假設分析後發現：

```text
同一類相容性問題已在多個系統反覆發生
+
多個永久兼容層持續存在
+
每次新增能力都需要額外繞路
```

此時不應繼續當成一次普通變更處理。

應建立蒸餾候選，交給：

`能力蒸餾與系統重構方案`

第三方案停止處理這個結構性問題，但保留目前變更的安全狀態與歷史。

## 九、邊界驗證

### 1. 不跨責任

資料／知識內容問題 → 方案三。

一般能力不足 → 問題解決流程。

長期結構性腐化 → 第四方案。

### 2. 不跨層升格

```text
修正完成
≠ 問題解決
≠ 系統驗收
≠ 方案驗收
≠ 實戰驗證
```

### 3. 不無限重試

相同修正連續失敗後，必須重新診斷。

### 4. 不無限擴充方案

單一案例不能證明需要新增整套治理能力。

### 5. 允許暫緩

如果修正風險過高或證據不足，可以：

```text
暫緩採用
↓
保存目前狀態
↓
等待更多證據
```
