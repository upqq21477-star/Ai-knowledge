# 施工主線-①至⑪-v1.0

## 1. 文件定位

本文件固定目前 Ai-knowledge 工程的主要施工順序，避免不同工作項目互相提前、造成規格反覆修改與返工。

本文件為新的施工基線，不修改既有舊文件。

## 2. 正式施工順序

```text
① 交接／工作狀態
        ↓
② 新系統規格
        ↓
③ 共同資料語義
        ↓
④ 狀態／版本／關係
        ↓
⑤ 現行格式唯一性
        ↓
⑥ 三方案資料／責任接口
        ↓
⑦ 跨系統長流程實測
        ↓
⑧ 待辦工作記憶／統御能力實例驗證
        ↓
⑨ 圖書館式知識管理
        ↓
⑩ 知識書原子化規格
        ↓
⑪ 實際驗證
```

## 3. 各階段完成條件

### ① 交接／工作狀態

確認沒有歷史對話時，AI 仍能從 Repository 恢復：

- 專案目的
- 目前架構
- 已確立決策
- 禁止事項
- 目前施工位置
- 待辦事項
- 下一步

交接不只是恢復「知道什麼」，還要能恢復「現在正在做什麼以及為什麼先做這件事」。

### ② 新系統規格

確認新系統的：

- 目的
- 職責
- 輸入
- 輸出
- 邊界
- 與其他系統的關係
- 使用條件
- 驗證條件

不得因舊系統文件中的舊狀態文字而誤判新系統不可測試；現行交接規則已將「不啟動」與「不可使用／測試」區分。

### ③ 共同資料語義

固定跨系統共同理解的核心資料類型及其邊界，例如：

- 知識 Knowledge
- 記憶 Memory
- 目前狀態 Current State
- 來源 Source
- 證據 Evidence
- 主張 Claim
- 決策 Decision
- 觀察 Observation

此階段只固定語義與邊界，不提前固定最終資料庫、JSON Schema 或實作技術。

### ④ 狀態／版本／關係

建立共同理解的：

- 狀態模型
- 版本模型
- 關係模型
- 歷史與演化關係
- 時間、條件、範圍
- 來源與證據追溯

需要區分內容版本、來源版本、方案版本、系統版本、軟體版本、Git 版本與檔案版本。

### ⑤ 現行格式唯一性

確認一個正式資料世代中，現行系統只存在一套正式格式。

大型格式更新採：

```text
新格式設計
→ 完整轉換／重建
→ 語義與完整性驗證
→ 切換
→ 舊格式退出現行層
→ 舊格式只保留於歷史／遷移／回歸驗證用途
```

不得長期維護多套並行的「現行正式格式」，以避免 AI 在不同資料世代之間產生判斷混亂。

### ⑥ 三方案資料／責任接口

確認三個正式方案之間：

- 誰產生資料
- 誰使用資料
- 誰驗證資料
- 誰負責變更
- 誰保存歷史
- 誰提供 Context
- 發生錯誤時交給誰

三個正式方案目前為：

1. 整體資料治理方案
2. AI 知識管理方案
3. 知識迭代與資料演化方案

問題解決系統為跨方案能力，不增加第四個正式方案。

### ⑦ 跨系統長流程實測

不能只做文件對照，必須實際模擬完整資料流：

```text
AI 任務
→ 搜尋研究
→ 外部證據
→ 發現知識衝突
→ 資料演化
→ 影響分析
→ 治理檢查
→ 建立新版本
→ AI 重新取得 Context
→ 任務重新執行
→ 驗證
→ 必要時問題解決流程介入
```

確認三方案與新系統在長流程中不發生責任斷裂、資料遺失或版本歧義。

### ⑧ 待辦工作記憶／統御能力實例驗證

先驗證能力，不先建立大型「統御系統」。

需要證明 AI 能夠根據：

- 目前工作狀態
- 待辦
- 依賴關係
- 先後順序
- 延後原因
- 已完成與未完成事項
- 返工風險

判斷下一步該做什麼、什麼不能現在做，以及何時應重新規劃。

只有證明現有能力不足，才建立新的正式系統能力。

### ⑨ 圖書館式知識管理

此階段必須先建立「圖書館式知識管理方案」的研究與功能框架，但不是直接完成最終軟體實作。

研究範圍至少包含：

- Knowledge Catalog
- Collection / 分類與集合
- Metadata
- Index
- Retrieval
- Navigation
- Source / Provenance
- Current / Historical separation
- Version與再索引
- 不同知識粒度的管理
- 知識與檢索單位是否需要分離

外部成熟做法顯示，圖書館的 Catalog / Metadata 與實際資源內容不是同一層；Library of Congress 同時使用多種資源描述標準，並明確處理不同描述層級與關係。citeturn0search3turn0search7turn0search14

現代 RAG / Knowledge Base 也將原始文件、Metadata、Chunk、Index、Retrieval、Grounding Context 分成不同處理階段。Microsoft 的目前文件特別指出，chunk 粒度需要依資料內容與使用方式測試，而不是直接固定一個通用大小。citeturn0search2turn0search8turn0search11

因此⑨的目的，是取得足夠的管理與檢索需求，讓⑩有真實設計依據。

### ⑩ 知識書原子化規格

只有完成⑨的研究與需求確認後，才正式決定知識書的形式。

要回答：

- 一個知識書究竟代表什麼？
- 最小語義單位是什麼？
- 是否需要原子化？
- 原子化到什麼程度？
- 一個檔案是否可以包含多個知識單位？
- 知識保存單位與 Retrieval Unit 是否相同？
- Metadata 放在哪一層？
- 關係放在哪一層？
- 來源與證據如何追溯？
- 更新時是修改、拆分、融合還是建立新版本？

「原子化」目前只是候選設計方向，不是既定結論。

禁止直接假設：

```text
一個知識 = 一個 Markdown
```

也禁止直接假設：

```text
一個知識書 = 一個 Retrieval Chunk
```

真正需要固定的是能同時支援保存、理解、分類、檢索、引用、版本、更新與 Context 組裝的適當粒度。

### ⑪ 實際驗證

最後使用 Repository 中的真實知識與實際 AI 任務驗證：

- 建立
- 查找
- 分類
- 關聯
- 引用
- 版本更新
- 衝突處理
- Retrieval
- Context 組裝
- AI 使用
- 更新後重新檢索
- 歷史資料處理

若⑩的規格在⑪中造成圖書館管理、搜尋或 AI 使用問題，必須回到⑩修正，而不是直接修改上層共同資料規格。

## 4. 為什麼⑨必須在⑩之前

如果先固定知識書形式，再研究圖書館管理，可能發生：

```text
先定知識書
→ 發現 Catalog 需要另一種粒度
→ 發現 Retrieval 需要上下文層級
→ 發現 Metadata 應與內容分離
→ 發現一個文件需要多層描述
→ 原知識書規格不適用
→ 重新設計
```

正確方式為：

```text
先建立圖書館管理問題空間
→ 搜尋成熟做法
→ 明確管理／檢索需求
→ 比較知識粒度
→ 推導知識書形式
→ 實驗
→ 固定規格
```

因此⑨不是「知識書規格完成後的附屬系統」，而是⑩的設計輸入來源。

## 5. ⑨的外部研究重點

目前外部研究已確認幾個重要方向：

1. 圖書館描述具有不同層級與粒度；Library of Congress 的目錄規範本身就區分不同 cataloging level，並處理 Work、Expression、Manifestation、Item、Series 等不同層級與關係。citeturn0search17turn0search6

2. Metadata 並非只有「檔名／標籤」。成熟標準會描述類型、識別碼、主題、關係、來源、時間、內容形式等不同屬性。citeturn0search16turn0search10

3. 現代 Knowledge Base / RAG 系統通常將原始資料與 Retrieval 結構分層；大型文件可以經過語義切分並保留標題、頁碼、Chunk ID 等 Metadata。citeturn0search11turn0search8

4. Chunk 不等於知識本體。Microsoft 的檢索架構允許階層式 Index、不同類型 Index，以及依資料型態選擇不同檢索結構。citeturn0search2

5. Knowledge Base 本身也可以是上層管理物件，下面再掛多個 Knowledge Source，而來源可以由索引、Metadata、權限與 Retrieval 機制共同支撐。citeturn0search13

6. NISO 在 2026 年發布新版 KBART，仍把 Knowledge Base 與 metadata exchange 作為獨立的管理與交換問題，說明大型知識／資源管理的核心之一不是單純「把內容切小」，而是可靠地描述、交換與發現資源。citeturn0search1turn0search18

## 6. 禁止事項

目前禁止：

- 在⑨完成前固定知識書最終格式。
- 直接宣布「一知識一檔案」為正式規則。
- 直接宣布所有知識都必須 Atomic Knowledge。
- 把 Knowledge Book、Catalog、Index、Chunk、Retrieval Unit、Context Unit 當成同一物件。
- 在尚未驗證需求前選定資料庫、Vector DB、Knowledge Graph 等實作技術。
- 因為研究到外部新方法就直接替換現有架構。
- 把外部工具的實作形式直接複製成 Ai-knowledge 的正式規格。

## 7. 當前位置

目前施工位置：⑨圖書館式知識管理。

⑨完成後才進入⑩知識書原子化規格。

⑪為⑩完成後的真實資料與 AI 任務驗證。

## 8. 判定原則

```text
外部方法是證據來源
不是本專案的規格。

圖書館需求是設計輸入
不是知識書格式本身。

知識書規格是經研究、推導、實測後形成的結果
不是預先假設。
```
