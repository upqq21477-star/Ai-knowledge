# AI知識管理方案 v2.1－完善草案

版本：v2.1 草案  
狀態：【完善草案；待三方案協作驗證】

## 一、文件定位

本文件不是修改舊版 `AI知識管理方案-v2.0.md`，而是建立下一版候選設計。

v2.0 已完成 84 項功能盤點與基本工作流。本版不增加大量新功能，而是把 84 項功能重新組織成「任務入口、資料取得、Context、執行、驗證、回饋」六個可協作階段，避免把功能清單直接膨脹成系統數量。

## 二、外部比對後的核心判斷

Anthropic 對 context engineering 的近期實務將 Context 視為有限資源，強調根據任務動態挑選最小且高訊號的資訊，並支持 just-in-time retrieval、結構化記憶、compaction 與專門化子代理等方法。citeturn1search0turn1search8

Anthropic 的 Contextual Retrieval 也指出，檢索品質會受到 chunk 邊界、上下文資訊與候選數量影響，且加入更多資料並不必然更好，因此需要實際 eval。citeturn1search3

Microsoft 的 RAG 文件同樣把 Retrieve → Augment → Generate 與 grounding、來源引用及檢索評估分開。citeturn1search4turn1search12

因此本方案保留「最小充分 Context」作為核心，但把它正式化為一個可驗證的決策流程，而不是一句原則。

## 三、方案總流程

```text
任務進入
↓
任務識別
↓
任務分型
↓
需求／條件抽取
↓
資料與能力需求判定
↓
直接取用／搜尋／研究判定
↓
候選資料取得
↓
來源／狀態／版本／適用性檢查
↓
Context 組裝
↓
任務執行
↓
結果驗證
↓
結果分類
↓
保存／回饋
↓
必要時觸發治理或演化
```

## 四、任務分型

最小任務類型：

- 直接取用：已有資料足以回答。
- 搜尋：已知目標但位置未知。
- 研究：需要比較多個來源或形成新結論。
- 更新：已有內容需要確認是否變更。
- 驗證：確認資料、系統或方案是否成立。
- 交接：恢復另一工作階段的必要狀態。
- 建構：建立新的知識、系統或方案。
- 執行：使用既有能力完成具體工作。

任務可以同時包含多種子類型，但主流程需要先判斷目前的主要工作。

## 五、資料需求模型

AI 不直接問「需要多少資料」，而先判斷：

```text
需要解決的問題
＋
必要條件
＋
需要判斷的未知量
＋
需要使用的能力
＋
結果驗證方式
```

再反推出資料需求。

資料需求至少分：

- 必要資料。
- 條件資料。
- 驗證資料。
- 背景資料。
- 可選補充資料。

## 六、搜尋／研究分界

### 直接取用

已存在且狀態、版本、適用範圍均足夠，不必重新研究。

### 搜尋

目標資料存在的可能性高，主要問題是定位。

### 研究

現有資料不足，或需要比較、外部確認、衝突判定、形成新結論。

研究不是「搜尋更多」，而是有明確研究問題、資訊需求、證據判斷與停止條件的流程。

## 七、Context 組裝模型

Context 分成六層：

1. 任務與輸出要求。
2. 必要規則與限制。
3. 目前狀態。
4. 必要知識／證據。
5. 必要歷史與記憶。
6. 工作過程中的新觀察。

載入順序不是固定永遠不變，而依任務調整。

## 八、最小充分 Context 判定

加入資料前問：

1. 不加入它是否會影響正確完成任務？
2. 它是否提供必要條件、證據或約束？
3. 它是否只是背景但不影響判斷？
4. 是否已有其他資料可以替代？
5. 它是否與目前版本或狀態一致？

若資料只增加篇幅而沒有增加必要判斷能力，預設不加入工作 Context。

這與外部 context engineering 對有限注意力資源及 just-in-time retrieval 的方向一致。citeturn1search0

## 九、Context 動態管理

Context 不是一次組裝後永遠不變。

```text
初始 Context
↓
執行
↓
發現未知
↓
追加必要資料
↓
移除已失去作用的內容
↓
重新執行／驗證
```

長任務可使用：

- 壓縮 Compaction。
- 結構化工作筆記 Structured Notes。
- 即時檢索 Just-in-time Retrieval。
- 專門化子任務 Sub-agent。

但這些是能力模式，不代表目前必須建立對應軟體。

## 十、資料使用前檢查

重要資料進入 Context 前至少檢查：

```text
身份
↓
資料類型
↓
目前狀態
↓
版本
↓
適用範圍／條件
↓
來源／證據
↓
與任務的關聯
```

發現資料已取代、待確認或條件不符時，不得因為搜尋命中就直接採用。

## 十一、結果驗證

結果驗證分五層：

1. 任務要求是否完成。
2. 使用資料是否適用。
3. 重要主張是否有足夠依據。
4. 是否混淆事實、推論、決策、觀察與記憶。
5. 是否產生需要回饋治理／演化的問題。

## 十二、結果分類與保存

AI 完成工作後，不是所有輸出都保存為知識。

```text
一次性回答 → 通常不保存
重要觀察 → Observation
使用者／專案背景 → Memory
目前採用情況 → Current State
明確選擇 → Decision
可重用且經確認 → Knowledge
待判斷命題 → Claim
來源材料 → Source
支持／限制／反駁材料 → Evidence
```

這與目前共同資料語義模型一致。

## 十三、失敗處理

失敗首先分類，不直接重做全部流程：

| 失敗 | 優先回饋 |
|---|---|
| 找不到資料 | 搜尋／資料探索 |
| 資料不存在 | 研究／外部研究 |
| 資料狀態不明 | 資料治理 |
| 版本不適用 | 資料演化 |
| 來源不足 | 證據／研究 |
| Context 太少 | Context 管理 |
| Context 太多 | Context 管理 |
| 資料互相衝突 | 比較／研究／治理 |
| 系統能力不足 | 系統層 |
| 方案責任衝突 | 三方案協作層 |

## 十四、三方案介面

### 向資料治理提出

- 資料需求。
- 狀態／版本疑問。
- 來源／證據問題。
- 共同語義衝突。

### 向資料演化提出

- 過期訊號。
- 重複／衝突。
- 使用失敗。
- Context 組裝困難。
- 新證據導致內容需要變更。

### 接收治理結果

- 可引用資料。
- 共同語義。
- 適用條件。
- 版本與狀態。
- 追溯資訊。

### 接收演化結果

- 新版本。
- 取代／補充通知。
- 適用範圍變更。
- 重新驗證要求。

## 十五、協調角色邊界

統籌角色屬於本方案的任務理解與能力分配能力，不是第四個方案。

統籌可以：

- 拆解複合任務。
- 判斷需要哪些資料／系統／方案。
- 分配工作。
- 收集結果。
- 發現能力缺口。

統籌不能：

- 取得其他方案的內部治理權。
- 直接修改其他方案。
- 把一次性協調工作自動升格為新系統。

## 十六、驗證矩陣

至少驗證：

1. 直接取用已存在資料。
2. 精確搜尋。
3. 語意搜尋。
4. 搜尋失敗診斷。
5. 外部研究。
6. 新證據修正。
7. 無歷史交接。
8. Context 過長。
9. Context 不足。
10. 版本變更後重新使用。
11. 資料治理衝突。
12. 演化結果回流。

## 十七、評估指標

目前不建立單一總分，而觀察：

- 是否取得必要資料。
- 是否引用錯誤版本。
- 是否帶入不必要 Context。
- 是否遺漏必要 Context。
- 搜尋是否找到真正相關資料。
- 研究是否在證據不足時停止。
- 結果是否能追溯依據。
- 失敗是否能定位到正確層級。

外部 RAG 評估也將檢索品質與生成結果分開評估，這支持本方案不要用「最後答案看起來合理」代替檢索與 Context 品質驗證。citeturn1search12

## 十八、禁止過度工程化

目前不要求：

- 單一萬能 Agent。
- 強制向量資料庫。
- 所有任務固定 Context 模板。
- 全自動長期記憶。
- 自動真偽裁決。
- 所有問題都啟動多代理。

## 十九、成立條件

本方案只有在實際任務中證明以下流程可以穩定運作，才可宣布成立：

```text
任務理解
→ 資料取得
→ Context 組裝
→ 執行
→ 驗證
→ 保存／回饋
```

## 二十、目前結論

v2.1 的主要工作不是再增加功能，而是將 84 項功能變成有責任邊界、輸入／輸出與驗證點的執行流程。

下一步應與治理及演化方案共同跑同一組真實案例，而不是各自獨立宣稱完成。
