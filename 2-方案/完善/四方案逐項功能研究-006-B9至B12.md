## 一、批次來源

本批先經「批次來源驗證（Batch Source Verification）」重新由 Repository 正式功能清單推導。

目前正式研究進度為 B8，因此下一個連續批次為 B9～B12。

本文件不新增不存在的功能，也不因既有能力存在而宣稱功能已完成。

## 二、既有能力處置

| 功能 | 既有能力 | 本批處置 |
|---|---|---|
| B9 上下文組裝 | AI上下文與交接系統＋AI知識管理系統 | 整合責任與接口，不建立第二套 Context 系統 |
| B10 記憶／目前狀態辨識 | AI上下文與交接系統＋整體資料治理相關知識 | 明確區分 Memory、Current State、Knowledge、History |
| B11 任務執行 | AI知識管理系統＋AI知識庫基本運作系統 | 沿用既有執行能力，確認輸入、執行、結果、失敗回路 |
| B12 結果驗證 | AI知識管理系統＋既有結果檢查／觸發式驗證能力 | 統一驗證責任、證據與成功條件，不另建萬能 Judge |

既有能力只是施工處置依據，不是驗證證據。

## 三、外部研究結論

本批重點對照 Anthropic 的 Effective Context Engineering、Anthropic 的長期 Agent Harness 研究，以及 NIST 2026 Agentic AI evaluation / TEVV 工作。

Anthropic 將 Context 視為有限資源，強調應根據當前任務動態整理 system instructions、tools、external data、message history、memory 與 state，而不是單純增加 Context 長度。對長期任務，還需要 compaction、structured note-taking 與跨 context window 的工作銜接。citehttps://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

NIST 的 Agentic AI evaluation 工作則強調：Agent 的結果不能只看「最後文字像不像正確答案」，還需要能追蹤工具使用、 gathered evidence、決策與輸出，並透過 structured audit trail、evaluation probes 檢查 faithfulness、completeness、sufficiency。citehttps://www.nist.gov/programs-projects/building-evaluation-probes-agentic-ai

NIST 2026 TEVV-Athlon 也將 Test、Evaluation、Verification、Validation 視為需要針對不同 AI 應用調整的方法，而不是單一固定評分方式。citehttps://www.nist.gov/artificial-intelligence/ai-research/tevv-athlon-framework-evaluating-ai-systems

因此本批的核心不是建立四個大型系統，而是把「Context → State/Memory → Execution → Verification」形成一條可追溯責任鏈。

# 四、B9 上下文組裝 Context Assembly

## 4.1 功能問題

B8 負責「選哪些資料足夠」，B9 負責把這些資料依任務組合成可工作的 Context。

最小語義模型：

```text
Task
↓
Selected Knowledge
Selected Evidence
Current State
Relevant Memory
Relevant History
Tool / Capability Information
Output Requirements
↓
Context Assembly
↓
Working Context
```

## 4.2 為什麼需要獨立功能

如果只有 B8，系統知道哪些資料值得使用，但沒有明確定義如何把不同來源、不同語義層級與不同時間狀態組合在一起。

這會產生另一種錯誤：每一份資料本身都正確，但組合後彼此衝突、順序錯誤或缺少必要背景。

因此 B9 必要，但不代表需要建立獨立大型 Context 平台。

## 4.3 與 B8 的邊界

```text
B8：選擇哪些資料進入 Context
B9：把選定資料組成工作 Context
```

B9 不重新決定所有資料是否適用；它使用 B6、B7、B8 的結果。

## 4.4 組裝原則

至少保留：

1. 任務目標與限制。
2. 目前有效狀態。
3. 必要知識與證據。
4. 必要歷史背景。
5. 與當前任務相關的工具／能力。
6. 輸出與驗證要求。
7. 各資料的身份、版本、狀態與來源線索。

順序不是固定模板；應由任務類型決定。

## 4.5 重要防錯

### 錯誤一：把所有搜尋結果直接串接

B8 已經負責最小充分選擇，B9 不得繞過 B8。

### 錯誤二：不同版本資料同時進入 Context 卻沒有標示

可能造成 AI 把舊規則與新規則混合。

### 錯誤三：Memory 與 Knowledge 沒有區分

「過去曾經發生」與「目前正式知識」不能用同一語義處理。

### 錯誤四：歷史資料被誤當成目前狀態

歷史可以解釋原因，但不能無標記地覆蓋 current state。

## 4.6 最小輸出

```text
Context Packet
├─ Task
├─ Constraints
├─ Current State
├─ Selected Knowledge
├─ Evidence
├─ Memory / History（若必要）
├─ Tools / Capabilities（若必要）
├─ Output Requirements
└─ Traceability
```

這是語義模型，不凍結成永久 JSON Schema。

## 4.7 模擬案例

任務要求修改一項現行規則。

B8 選出：目前正式規則、上一版本變更原因、相關驗證案例、目前工程狀態。

B9 組裝後必須清楚標示：

```text
目前規則 = Current
上一版本 = Historical
驗證案例 = Evidence
工程狀態 = Current State
```

不能將四者直接拼成一段無來源文字。

【研究判定：必要】

# 五、B10 記憶／目前狀態辨識 Memory / Current State Recognition

## 5.1 功能問題

判斷目前取得的資訊究竟屬於：

```text
Knowledge
Memory
Current State
History
```

這四者不能因為都是「以前看過的資料」就混成同一類。

## 5.2 為什麼必要

長期 AI 工作最危險的問題之一，是把舊資訊誤當成現在有效狀態。

例如：

```text
2026-09-10 的工程狀態
≠
2026-09-17 的工程狀態
```

又例如：

```text
「曾經決定採用 X」
≠
「目前仍採用 X」
```

因此 B10 是 B9 Context 組裝前後的重要狀態辨識層。

## 5.3 與方案一共同語義的關係

B10 不建立第二套 State、Version、Lifecycle、History 定義。

方案一提供共同資料語義；B10 負責在 AI 任務中辨識並正確使用這些語義。

## 5.4 最小判斷維度

```text
Identity
Type
Version
Lifecycle
Validity / State
Timestamp
Authority
Relationship to current task
```

## 5.5 四類資料邊界

### Knowledge

相對穩定、可重用的知識內容。

### Memory

AI 或工程過程保留的過去資訊，例如偏好、過往工作脈絡、曾經完成的事情。

Memory 不自動等於正式知識。

### Current State

目前工程、系統或任務正在有效使用的狀態。

### History

已退出目前工作狀態、但保留追溯價值的資料。

History 不應因為重新被讀取就自動變成 Current State。

## 5.6 失敗案例

Context 中同時存在：

```text
舊方案：B1～B4 後接 A13～A16
目前正式清單：A1～A12，接著 B1～B16
```

B10 必須把前者辨識為歷史錯誤資訊，而不能因為它仍存在於 Repository 就當成目前狀態。

【研究判定：必要】

# 六、B11 任務執行 Task Execution

## 6.1 功能問題

利用已完成的任務理解、拆解、資料取得、Context 與必要系統能力，實際完成任務。

B11 是「做事」，不是「決定怎麼找資料」或「判斷結果是否正確」。

## 6.2 為什麼不建立新的執行系統

既有映射已指出 B11 的工作能力存在於 AI 知識管理系統與 AI 知識庫基本運作系統。

因此本功能目前的主要問題不是缺少一個 Agent，而是需要把執行能力與前後責任接起來：

```text
B1/B2
↓
B3/B4/B5
↓
B6/B7/B8
↓
B9/B10
↓
B11 執行
↓
B12 驗證
```

不應建立「方案二自己的萬能 Agent」來取代這條責任鏈。

## 6.3 最小執行模型

```text
Executable Task
↓
Required Capability
↓
Action / Tool / Work
↓
Intermediate Result
↓
Final Result
↓
Execution Record
```

執行記錄至少應能回答：

```text
做了什麼？
使用了什麼？
得到什麼？
是否發生失敗？
是否需要重新執行？
```

## 6.4 失敗處理

B11 發現失敗時，不直接自行改規則：

```text
Execution Failure
↓
B16 Failure Diagnosis
↓
Problem Solving
↓
Fix
↓
Revalidation
```

這與目前方案二既有 FAIL 閉環一致。

## 6.5 模擬案例

任務：「建立 B9～B12 研究文件」。

B11 使用已確認的研究規則、外部研究結果與 Repository 狀態完成文件。

若發現正式功能清單與交接文字衝突，不應自行選擇較方便的版本，而應觸發既有來源驗證／問題處理責任。

【研究判定：必要；沿用既有執行能力】

# 七、B12 結果驗證 Result Validation

## 7.1 功能問題

判斷任務執行結果是否真的符合：

```text
任務目標
需求／限制
證據要求
適用條件
輸出格式
成功條件
```

B12 是「結果是否合格」，不是「資料看起來可信」。

## 7.2 外部研究

NIST 2026 Agentic AI evaluation 工作把 Agent 的結果驗證拆成可追溯的評估探針，至少關注 faithfulness、completeness、sufficiency，並把 verdict 與 supporting evidence 保存進 structured audit trail。citehttps://www.nist.gov/programs-projects/building-evaluation-probes-agentic-ai

NIST TEVV-Athlon 也指出，AI 系統的 Test、Evaluation、Verification、Validation 必須依應用調整，不能把單一 benchmark 分數視為所有使用情境的完整證明。citehttps://www.nist.gov/artificial-intelligence/ai-research/tevv-athlon-framework-evaluating-ai-systems

因此 B12 應採「任務成功條件＋證據＋追溯」模式，而不是單純一個 `PASS/FAIL` 欄位。

## 7.3 最小驗證模型

```text
Result
↓
Validation Criteria
├─ Goal Met?
├─ Requirement Met?
├─ Evidence Supported?
├─ Conditions Satisfied?
├─ Output Complete?
├─ Contradictions?
└─ Side Effects?
↓
Validation Verdict
├─ PASS
├─ PARTIAL
├─ FAIL
└─ UNKNOWN
```

## 7.4 B12 與 B6/B7 的關係

```text
B6：證據支持什麼？
B7：證據／方法是否適用？
B12：這次實際產生的結果是否符合任務？
```

即使 B6、B7 都 PASS，B12 仍可能 FAIL。

例如一個外部方法確實有效，也適用本系統，但實際執行時配置錯誤，結果仍可能不合格。

## 7.5 驗證不能只看最後文字

對長流程 Agent，驗證還需要檢查：

- 使用的來源是否與宣稱一致。
- 工具／資料是否真的被正確使用。
- 是否跳過必要步驟。
- 是否利用評估漏洞得到表面 PASS。
- 是否存在未被輸出文字反映的副作用。

NIST 近期對 Agent 評估也特別關注 evaluation validity，以及模型利用評估漏洞「得到高分但沒有完成原本要測的能力」的問題。citehttps://www.nist.gov/caisi/cheating-ai-agent-evaluations

因此本系統的驗證紀錄不應只有最後答案。

## 7.6 模擬案例

任務要求「找出目前正式功能清單中的下一批」。

AI 找到一份舊文件寫著 A13～A16，最後回答 A13～A16。

B12 必須判定 FAIL，因為：

```text
任務成功條件包含：使用目前正式功能來源
```

即使回答文字本身看起來合理，也不能 PASS。

## 7.7 驗證結果與方案二 FAIL 閉環

```text
B11 任務執行
↓
B12 結果驗證
├─ PASS → B14 結果保存／B15 回饋
├─ PARTIAL → 保留缺口，決定是否補做
├─ UNKNOWN → 補證據／補研究／重新判斷
└─ FAIL → B16 失敗診斷
             ↓
          問題解決流程
             ↓
          修正
             ↓
          重新驗證
```

這使 B12 成為方案二正常路徑與失敗路徑的共同出口。

【研究判定：必要；核心驗證能力】

# 八、B9～B12 整體責任鏈

```text
B8 最小充分上下文選擇
↓
B9 上下文組裝
↓
B10 記憶／目前狀態辨識
↓
B11 任務執行
↓
B12 結果驗證
├─ PASS
│   ↓
│  B14/B15 後續責任
│
└─ FAIL / PARTIAL / UNKNOWN
    ↓
   B16 失敗診斷
    ↓
   問題解決
    ↓
   修正
    ↓
   回 B12
```

其中 B10 與 B9 可能在實際 Context 組裝前後反覆互動，不應硬性理解為一次性線性步驟。

## 九、共同錯誤邊界

| 錯誤 | 應由誰處理 |
|---|---|
| 搜不到資料 | B3/B4 |
| Repository 不足，需要外部資料 | B5 |
| 不知道來源支持什麼 | B6 |
| 不知道是否能用 | B7 |
| 資料太多，不知道選什麼 | B8 |
| 選對了資料但組合混亂 | B9 |
| 舊資料被當成目前狀態 | B10 |
| 已有正確 Context 卻沒有完成工作 | B11 |
| 工作完成但結果不符合要求 | B12 |
| 驗證失敗但不知道原因 | B16 → 問題解決 |

## 十、必要性結論

### B9 上下文組裝
【必要】。但主要是既有 Context 系統與方案二的責任整合，不需要第二套大型系統。

### B10 記憶／目前狀態辨識
【必要】。是長期工程中避免舊資料污染目前工作的重要責任層，並應依賴方案一共同語義，而非另造 State/Memory Schema。

### B11 任務執行
【必要】。已有工作能力，不應因功能清單而建立新的萬能 Agent；重點是把執行接到前後責任鏈。

### B12 結果驗證
【必要；核心】。必須驗證實際結果，不得由 B6/B7 或「執行完成」直接推論成功。

## 十一、本批研究結論

B9～B12 不應形成四個互相獨立的大系統。

正確結構為：

```text
B8：選擇
↓
B9：組裝
↓
B10：辨識狀態與記憶
↓
B11：執行
↓
B12：驗證
↓
成功 → 保存／回饋
失敗 → 診斷／問題解決／修正／重新驗證
```

本批研究完成後，下一步為：

```text
B9～B12 模擬實作驗收
↓
若通過 → 正式責任整合
↓
重新執行批次來源驗證
↓
推導下一批 B13～B16
```

目前不得宣稱 FIELD-PASSED。
