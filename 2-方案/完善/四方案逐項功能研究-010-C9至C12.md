## 一、研究範圍

本批正式功能為：

- C9 版本分析
- C10 相容性分析
- C11 遷移分析
- C12 最小變更執行

正式順序：

```text
C1～C4 變更訊號／目標確認
↓
C5 既有能力盤點
↓
C6 影響分析
↓
C7 演化必要性判定
↓
C8 候選變更產生
↓
C9 版本分析
↓
C10 相容性分析
↓
C11 遷移分析
↓
C12 最小變更執行
↓
C13 實際驗證
```

本研究不把 C9～C12 建立成四個大型獨立系統，而是定義為方案三演化工作流中的四個責任節點。

## 二、C9 版本分析

### 1. 核心問題

確認候選變更涉及哪些版本、基準、語義差異與歷史演化，避免把「目前檔案」誤認為唯一版本真相。

### 2. 必要責任

C9 至少分析：

- 來源版本／目前基準
- 候選目標版本
- Identity 是否相同
- 語義是否改變
- State／Lifecycle 是否改變
- 依賴與關係是否改變
- 舊版本是否仍被使用
- 歷史與驗證結果是否仍適用
- 是否存在需要重新驗證的分析或證據

版本不等於 Git commit，也不等於檔名；Git 可提供實體變更追蹤，但邏輯版本必須由知識治理模型表達。

### 3. 外部交叉研究

NASA Configuration Management 要求受控項目具有可識別的 baseline、版本與變更歷史，並追蹤 successive baselines 的差異。citeturn0search0turn0search16

NIST 將 configuration management 定義為識別 components、versions、baselines 並控制與追蹤變更的正式方法。citeturn0search4

因此本系統的 C9 應保留「邏輯版本」與「實體變更紀錄」兩層，不應互相取代。

### 4. C9 輸出

```text
Version Analysis
- Baseline Identity
- Source Version
- Candidate Version
- Semantic Difference
- State/Lifecycle Difference
- Relationship Difference
- Dependency Difference
- Validation Relevance
- Historical Relevance
- Revalidation Required
- Uncertainty
```

## 三、C10 相容性分析

### 1. 核心問題

判斷新舊能力、資料、介面、知識或工作方式能否共存、繼續使用，或必須進行遷移。

### 2. 相容性不是「版本較新所以可以用」

至少區分：

- Backward Compatible：新版本不破壞既有使用方式
- Conditional Compatible：在特定條件下可共存
- Incompatible：既有依賴會失效
- Unknown：證據不足

NIST FIPS 201-3 明確區分 backward-compatible 與 backward-incompatible change。citeturn0search1

NASA 也指出影響外部介面的變更需要與受影響的利益相關者協調；重大變更可涉及相容性與介面影響。citeturn0search0turn0search36

### 3. 分析維度

```text
資料格式／結構
語義
輸入／輸出
介面
依賴
狀態
使用流程
驗證案例
外部引用
歷史資料
```

### 4. C10 輸出

```text
Compatibility Result
- Compatible / Conditional / Incompatible / Unknown
- Affected Interface
- Affected Dependency
- Broken Assumption
- Coexistence Requirement
- Revalidation Requirement
- Evidence
```

## 四、C11 遷移分析

### 1. 核心問題

當舊結構不能直接繼續使用時，定義如何從 Source State 安全轉移到 Target State。

C11 不執行遷移，只定義遷移條件、順序、資料對應、共存與回復條件。

### 2. 最小遷移模型

```text
Source Baseline
↓
Migration Preconditions
↓
Mapping / Transformation
↓
Target Baseline
↓
Verification
↓
Cutover / Coexistence
↓
Rollback Condition
```

IBM 的實際 migration 文件反覆採用 source snapshot、target preparation、mapping/import、驗證等概念，並明確限制可支援的 migration path。citeturn0search2turn0search7

因此本系統不能假設「任何舊版本都能直接遷移到任何新版本」。

### 3. C11 必須保存

- Source Identity／Version
- Target Identity／Version
- Mapping Rules
- Transformation Rules
- Preconditions
- Ordering
- Coexistence Strategy
- Cutover Condition
- Rollback Condition
- Validation Criteria
- Unsupported Paths

## 五、C12 最小變更執行

### 1. 核心問題

只執行已確認且必要的最小變更，不因候選方案存在就擴大重構範圍。

NASA Configuration Management 將變更流程描述為 proposal、justification、evaluation、approval、incorporation、verification；變更執行不是分析階段自行決定的副作用。citeturn0search0turn0search16

### 2. C12 前置條件

至少必須存在：

```text
C4 Change Objective
C5 Existing Capability
C6 Impact Analysis
C7 Evolution Necessity
C8 Candidate Change
C9 Version Analysis
C10 Compatibility Analysis
C11 Migration Analysis（若需要）
Execution Scope
Success Criteria
Rollback / Recovery Condition
```

任何必要項目未知時，不得把「執行」偽裝成完成。

### 3. 最小變更原則

```text
能沿用 → 不新增
能局部修正 → 不整體重建
能擴充 → 不直接替換
能相容共存 → 不強制遷移
需要遷移 → 先建立遷移條件
無法證明安全 → 不執行
```

### 4. C12 輸出

```text
Change Execution Record
- Change Case
- Approved Candidate
- Scope
- Objects Changed
- Objects Explicitly Not Changed
- Preconditions
- Actions
- Result
- Unexpected Effects
- Rollback Status
- Verification Pending
- Traceability
```

## 六、四項責任邊界

| 功能 | 負責 | 不負責 |
|---|---|---|
| C9 版本分析 | 判斷版本、基準與語義演化 | 不決定採用哪個候選 |
| C10 相容性分析 | 判斷新舊是否可共存 | 不自行遷移 |
| C11 遷移分析 | 定義遷移路徑與條件 | 不執行遷移 |
| C12 最小變更執行 | 執行已確認的最小變更 | 不跳過 C13 驗證、不自行擴大範圍 |

## 八、研究結論

C9～C12 均有必要，且形成清楚的工程鏈：

```text
C8 候選變更
↓
C9 確認版本與語義差異
↓
C10 確認相容性
↓
C11 必要時定義遷移
↓
C12 執行最小必要變更
↓
C13 驗證
```

核心防錯點是：

1. 新版本不等於自動可用。
2. 不相容不等於立即重建。
3. 需要遷移不等於立即執行遷移。
4. 候選變更不等於已批准變更。
5. 已執行不等於已成功，最終結果仍由 C13 判定。
