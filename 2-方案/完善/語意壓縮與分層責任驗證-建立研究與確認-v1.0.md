# 語意壓縮與分層責任驗證｜建立研究與確認

版本：v1.0
狀態：【研究階段；未形成最終方案】

## 一、研究問題

目標不是直接設計壓縮規則，而是回答：

1. AI 知識庫中的 Knowledge、System、Solution 各自應保存哪些不可替代語意？
2. 哪些語意可以跨層移動？
3. 哪些語意刪除後會造成路由錯誤、功能錯誤、結果誤解或語意失真？
4. 如何以最少語意維持可交接、可執行、可驗收？
5. 如何建立可重複的壓縮與驗收方法？

## 二、問題拆分

### P01｜分層責任
確認 Knowledge、System、Solution 的職責邊界與重疊區。

### P02｜功能識別
找出壓縮系統真正需要保存的功能元素：
- 身份
- 目的／功能
- 輸入
- 依賴
- 輸出
- 邊界
- 驗收

### P03｜語意重要性
區分：
- 不可刪語意
- 可移交語意
- 可合併語意
- 純冗餘語意

### P04｜壓縮方法
研究自然語言 Prompt／Context 壓縮的資訊保存與效能代價。

### P05｜錯誤機制
研究壓縮後可能出現：
- 路由錯誤
- 功能遺失
- 結果誤解
- Unsupported 與 Hallucination 混淆
- Context-induced Error 無法識別

### P06｜驗收
建立壓縮前後可比較的測量項目。

## 四、既有實驗資料

既有 50 次結構化模擬：

| 階段 | 路由錯誤 | 語意失真 | 幻覺 | 功能完成 | 整體成功 |
|---|---:|---:|---:|---:|---:|
| 初始壓縮 | 3/50 | 4/50 | 1/50 | 48/50 | 46/50 |
| 加入 Solution 邊界 | 0/50 | 1/50 | 0/50 | 49/50 | 49/50 |
| 加入 Solution 驗收定義 | 0/50 | 0/50 | 0/50 | 50/50 | 50/50 |

Token 結構化估算：
- 正式組：約 28,201 / 50 次。
- 初始壓縮組：約 9,177 / 50 次。
- 加入 Solution 邊界：約 9,500 / 50 次。

此資料是本專案內部的結構化模擬，不是獨立 API benchmark。

## 五、外部研究

### R01｜Prompt Compression Survey
Li et al., NAACL 2025。
研究指出 Prompt Compression 的核心問題是降低長 Prompt 帶來的記憶與推理成本，同時維持下游任務效能；研究方法包含 hard prompt 與 soft prompt compression。 
來源：ACL Anthology，https://aclanthology.org/2025.naacl-long.368/

### R02｜Information Preservation
Łajewska et al., Findings of EMNLP 2025。
研究以 compression ratio、下游任務效能、grounding、information preservation 共同評估壓縮，並指出高壓縮可能遺失關鍵細節；因此單純追求壓縮率不足，必須測量資訊保存。 
來源：ACL Anthology，https://aclanthology.org/2025.findings-emnlp.949/

### R03｜Context Engineering
現代 Context Engineering 將 System Prompt、使用者問題、檢索資料、工具輸出與歷史等都視為模型推理時可見的 Context；Context 的品質與結構會影響推理、工具使用與輸出。 
來源：IBM，https://www.ibm.com/think/topics/context-engineering

## 六、研究初步結論

外部研究支持「壓縮不能只看字數／Token」，而必須同時驗證：
- 任務表現
- Grounding
- 關鍵資訊保存
- 成本

本專案內部實驗進一步顯示，對分層知識庫而言，錯誤不只來自資訊遺失，也來自「語意被放錯層」。

目前形成的研究假設：

> 語意是否可刪，不能只看它是否重複；必須看刪除後是否改變決策、路由、執行、結果解讀或驗收。

## 七、待建立 Knowledge

下一階段必須將上述研究結果整理成可重複使用的 Knowledge：
1. 分層責任原理
2. 最小充分語意原理
3. 語意可刪除／可移交判定
4. 結果語意保存原理
5. 壓縮驗收原理

## 八、研究停止條件

在 Knowledge 建立前，不直接定稿 Solution。
Knowledge 完成後，建立對應 System；
System 完成後，再由 Solution 組裝完整流程。
