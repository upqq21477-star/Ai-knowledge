## 一、驗收規則修正

自本文件起，四方案所有「實戰驗收」在系統尚未進入長期真實運作前，統一先採用「模擬測試運行（Simulation Validation）」。

模擬驗收的目的不是宣稱能力已被真實環境證明，而是確認：

1. 功能定義是否可操作。
2. 邊界是否能與相鄰能力分離。
3. 資料模型是否能承受典型案例。
4. AI 是否可能誤解或繞過規則。
5. 失敗案例是否能被識別。

正式進入長期運作後，再把真實發生的問題納入「真實案例驗證（Real-world Validation）」。

因此本批所有驗收結論均標記為：

【模擬驗收通過；未等同真實環境驗證】

# 二、A9 歷史保存 History

## 2.1 要回答的問題

退出目前工作結構的資料如何保存，而不重新成為目前資料？

## 2.2 外部研究

記錄管理領域把保存、保留期限與 disposition（處置）視為正式管理問題。ISO/TS 7538:2024 明確涵蓋 records disposition 的責任、評估、實施與整合；ISO 的相關說明也指出 disposition 可以包含保留、銷毀或移轉等處置。

這支持一項重要區分：歷史保存不是單純「不要刪除」，而是要讓舊資料保留其歷史價值，同時避免被誤當成目前有效資料。

## 2.3 系統必要性

【必要】

原因：本知識庫會持續發生方案更新、格式重製、知識淘汰與能力重構。如果只有目前版本而沒有歷史層，AI 無法判斷某項舊知識究竟是歷史決策、已退役能力，還是目前規則。

## 2.4 邊界

History ≠ Lifecycle

Lifecycle 描述對象目前所處及曾經經歷的生命階段；History 保存具體過去事件、舊版本、舊狀態與決策記錄。

History ≠ Version

Version 描述內容演化序列；History 可保存比版本更廣泛的事件。

History ≠ Archive only

Archive 是保存方式或保存區域；History 是可追溯的歷史資訊。

## 2.5 最小模型

```text
Object ID
Historical Event
Event Time
Previous State
New State
Related Version
Reason / Decision
Related Actor
``` 

舊資料進入歷史後，必須仍可被辨識，但不能因為存在於 Repository 就自動成為目前可用知識。

## 2.6 模擬測試

案例：方案 A v1 被方案 A v2 取代。

要求：
- AI 能找到 v1。
- AI 能知道 v1 已不屬於目前基準。
- AI 能指出 v1 為何被取代。
- AI 不得因 v1 內容完整而直接把它當目前規則。

結果：【通過】

# 三、A10 引用／追溯 Traceability

## 3.1 要回答的問題

AI 或系統使用某資料後，能否追溯使用來源、版本與依據？

## 3.2 外部研究

W3C PROV 將 provenance 建模為實體（Entity）、活動（Activity）、代理者（Agent）以及衍生、使用、產生等關係。這說明追溯不能只依賴「檔名」，而應能回答某結果如何由先前資訊產生。

## 3.3 系統必要性

【必要；核心共同能力】

A3 Source、A4 Claim/Evidence、A6 Version 都會產生追溯需求。A10 不應重新建立來源或版本資料，而應把這些資料串起來。

## 3.4 邊界

```text
Source      = 資料從哪裡來
Evidence    = 哪一段內容支撐某主張
Claim       = 提出的主張
Version     = 使用的是哪一版
Traceability= 如何把上述資訊串成可追蹤路徑
```

因此 Traceability 是「關聯能力」，不是另一套資料來源系統。

## 3.5 最小追溯鏈

```text
Result
  ↓ derived_from
Claim
  ↓ supported_by
Evidence
  ↓ located_in
Source
  ↓ represented_as
Version / Snapshot
```

## 3.6 模擬測試

案例：AI 產生一項方案判斷。

要求：可以反向回答：
- 判斷用了哪些 Claim？
- Claim 由哪些 Evidence 支撐？
- Evidence 來自哪個 Source？
- 使用哪一版本？

結果：【通過】

失敗模式：只有「參考資料：某文件.md」，但無法指出使用內容、版本與依據。

結論：僅有引用檔名不算 Traceability 通過。

# 四、A11 變更影響 Impact Analysis

## 4.1 要回答的問題

某項資料變更後，哪些關係、使用者、系統或方案可能受影響？

## 4.2 外部研究

RDF 使用 subject-predicate-object 的有向關係表達資源間關係，適合形成可遍歷的依賴結構。W3C RDF 的核心模型即以帶標籤的有向關係連接節點。這支持影響分析建立在 Relationship 之上，而不是重新建立另一套關係模型。

## 4.3 系統必要性

【必要；方案三與方案四的重要共同能力】

變更管理如果沒有 Impact Analysis，很容易變成「修改一份文件後再猜哪些東西需要同步」。

## 4.4 邊界

Relationship：A 與 B 是什麼關係？

Impact：如果 A 發生某種變更，哪些關係／對象可能受到影響？

Impact 不等於預測實際結果。第一階段只要求辨識「可能受影響範圍」，不能把依賴關係直接宣稱為確定破壞。

## 4.5 最小模型

```text
Changed Object
→ Relationship
→ Related Object
→ Usage / Dependency
→ Potential Impact
→ Validation Required
```

## 4.6 模擬測試

案例：共同 Metadata 規則修改。

要求系統至少找出：
- 使用該規則的方案文件。
- 依賴該欄位的工作流程。
- 可能需要重新驗證的案例。

結果：【通過】

限制：不能只因為「同目錄」或「名稱相似」就判定為受影響。

# 五、A12 跨方案共同語義 Cross-Scheme Semantics

## 5.1 要回答的問題

四方案究竟共用哪些概念？哪些應保持方案內部自由？

## 5.2 外部研究

RDF 的模型將資源與關係抽象成可跨資料集使用的基本結構，並允許不同 schema 之間進行資料合併；這支持「共同語義層」存在，但不要求所有領域資料都被塞進同一套細節模型。

## 5.3 系統必要性

【必要；但最容易過度設計】

四方案目前已明確共享：

```text
Identity
Metadata
Source
Evidence
Claim
State
Version
Relationship
Lifecycle
History
Traceability
Impact
```

但這不代表四方案內部流程、判斷規則、操作步驟必須完全統一。

## 5.4 核心原則

只統一「跨方案必須互通的語義」，不統一「方案內部如何工作」。

例如：

```text
共同：Object ID / Version / State
方案一：資料治理流程
方案二：AI 搜尋與任務執行
方案三：演化與遷移流程
方案四：蒸餾與重構流程
```

## 5.5 模擬測試

建立一個 Object：

```text
ID = OBJ-001
Type = Knowledge
State = Active
Version = 3
```

四方案分別使用它：

- 方案一：把它視為治理對象。
- 方案二：把它視為 AI 可檢索知識。
- 方案三：把它視為演化對象。
- 方案四：把它視為可被蒸餾／重構的能力或知識來源。

要求：四方案仍能指向同一 Identity，而不要求四方案使用完全相同的工作語言。

結果：【通過】

失敗模式：為了統一而把四方案所有流程硬塞進共同 Schema。

結論：共同語義層應保持小而穩定。

# 六、A9～A12 綜合邊界

```text
Lifecycle = 對象生命階段
History   = 已發生的歷史記錄
Version   = 內容演化單位
State     = 當前／特定時間點狀態

Relationship = 對象之間存在什麼關係
Traceability = 沿關係與來源回溯資訊如何產生
Impact       = 某變更沿關係可能影響什麼

Cross-Scheme Semantics = 四方案共同理解哪些核心語義
```

這八個概念不可互相取代。
