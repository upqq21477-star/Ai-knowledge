# 三方案問題發現與舊搜尋方案解法驗證 v1.0

日期：2026-09-17
狀態：【驗證中】

## 一、目的

本文件不是第四個方案，也不修改舊方案。

用途是：當三方案協作驗證發現問題時，不立即新增能力，而先使用既有的搜尋方案／搜尋系統尋找外部成熟方法，再比較、實驗與判定是否真的需要修改目前設計。

基本流程：

```text
三方案協作驗證
↓
發現問題
↓
精確定義問題
↓
使用既有搜尋能力尋找外部方法
↓
取得來源與證據
↓
比較候選解法
↓
建立最小測試案例
↓
測試候選解法
↓
比較結果
↓
選擇目前可採用解法／保留未決
↓
回饋三方案
```

## 二、本輪已發現的問題

### 問題 A：局部影響描述不足

目前演化方案可以描述「部分取代」，但還不能穩定表示：

- 哪一個資料物件受到影響。
- 哪一個主張／條件受到影響。
- 影響是直接還是間接。
- 哪些下游內容需要重新驗證。

### 問題 B：跨方案失敗事件沒有共同最小描述

AI 知識管理可以辨識「資料不足、資料衝突、Context 不足、驗證不足」等失敗，但治理與演化目前沒有共同的最小事件描述，使失敗回饋容易停留在自然語言。

### 問題 C：共同變更請求沒有最小資料契約

當 AI 或演化系統發現共同語義可能需要改變時，目前有責任回到治理，但缺少一個最小且可追溯的變更請求描述。

## 三、舊搜尋方案的使用規則

本輪不重新建立搜尋系統。

既有搜尋能力只負責：

1. 找問題相關資料。
2. 找成熟方法、標準、工具與實作案例。
3. 比較不同方法的適用條件。
4. 將來源與證據交回分析流程。

搜尋結果不直接等於採用方案。

## 四、外部搜尋結果的初步候選

### 1. Change Impact Analysis / Data Lineage

成熟資料治理實務通常先精確定義變更，再沿 lineage／dependency 找出受影響物件，再做影響分類與驗證。Microsoft Fabric 的 impact analysis 支援查看直接與下游受影響項目；近期資料治理實務也將 impact analysis 視為建立在 lineage 與 metadata 上的變更決策流程。citeturn0search15turn0search1

對問題 A 的啟示：不要只增加「部分取代」一個關係，而應保留「變更對象 → 受影響範圍 → 下游依賴 → 驗證要求」這條鏈。

### 2. Provenance / Retrieval Receipt

W3C PROV 的方向是保存 entity、activity、agent、generation、usage、derivation 等 provenance 關係。近期開源 knowledge-base 實作也出現 retrieval receipt：記錄是哪個 retriever、哪次搜尋、哪些結果實際被使用。citeturn0search7

對問題 B 的啟示：失敗事件不必立即建立大型事件平台，可以先要求一次 AI 任務至少能追溯「使用了什麼資料、哪次搜尋、哪個版本、結果如何」。

### 3. Governed Retrieval / Context Governance

近期研究指出，retrieval relevance 本身不足以保證版本、來源、完整性與 point-in-time reconstruction；因此 retrieval 前仍需要治理層判斷哪些資料目前可被使用。citeturn0academia35

對問題 B、C 的啟示：變更請求與失敗回饋應至少攜帶資料身份、版本、來源／證據、使用情境與發生時間，否則後續無法可靠重現問題。

### 4. Hybrid Retrieval

近期 AI 知識檢索實務普遍把 keyword／sparse retrieval、semantic retrieval、metadata filter、reranking 與 bounded context 視為可以組合的檢索層，而不是假定單一向量搜尋永遠足夠。citeturn0search13turn0search11

對本專案的啟示：搜尋問題應先判斷是「找精確物件」、「找語義相似內容」還是「找關係／依賴」，再選檢索方式；不應直接把所有問題改成向量搜尋或知識圖譜。

## 五、候選解法比較

| 問題 | 候選 | 優點 | 成本／風險 | 目前判定 |
|---|---|---|---|---|
| 局部影響 | lineage + impact analysis | 可追蹤直接／下游影響 | 需要關係資料 | 候選 A |
| 局部影響 | 純文字搜尋 | 建立成本低 | 無法穩定推導依賴鏈 | 不足 |
| 失敗回饋 | retrieval／execution receipt | 可重現使用資料 | 需要最小紀錄格式 | 候選 B |
| 失敗回饋 | 自由文字紀錄 | 最簡單 | 難以機器判讀與回放 | 不足 |
| 共同變更 | Change Request | 可追蹤提出者、目標、原因與影響 | 需要最小契約 | 候選 C |
| 共同變更 | 直接修改治理規則 | 快 | 破壞責任邊界與歷史 | 禁止 |
| 多類搜尋 | Hybrid Retrieval | 同時處理精確、語義、關係需求 | 複雜度較高 | 僅在測試證明需要時採用 |

## 六、最優解不是「功能最多」

本專案目前不以單一總分選擇「最佳解」。

採用判定至少看：

```text
問題是否真的解決
↓
是否能重現
↓
是否保留來源／證據
↓
是否破壞三方案責任邊界
↓
新增複雜度是否必要
↓
是否能在現有架構運作
↓
是否通過實際案例
```

因此「最優解」在本專案中定義為：

> 在相同問題與測試條件下，能達成必要結果、可追溯、可驗證、符合責任邊界，且沒有不必要架構複雜度的可採用方案。

這不是政治或主觀排名，而是工程採用標準。

## 七、第一輪測試設計

### 測試 A：局部影響

輸入：一份知識中的某項主張被新證據修正。

比較：

- A1：只標記「部分取代」。
- A2：記錄受影響主張，再追蹤直接／下游依賴。

必要輸出：

```text
變更對象
→ 受影響主張
→ 直接依賴
→ 間接依賴
→ 需要重新驗證的項目
```

### 測試 B：失敗回饋

輸入：AI 使用某版本知識回答任務，但結果驗證失敗。

比較：

- B1：只保存失敗文字。
- B2：保存任務、搜尋、使用資料、版本、結果、驗證結果的最小 receipt。

必要輸出：可以重新定位「AI 當時看到了什麼」。

### 測試 C：共同變更

輸入：某方案提出「目前核心資料類型不足以描述新案例」。

比較：

- C1：直接修改共同規則。
- C2：建立變更請求，經治理檢查與案例驗證後再決定。

必要輸出：保留提出原因、受影響範圍、候選變更與驗證結果。

## 八、目前測試結論

目前外部資料支持「影響分析、provenance／receipt、變更請求、受治理的 retrieval」這幾個方向，但外部方法只能作為候選，不直接證明本專案必須採用完整產品或完整框架。

目前最小採用方向是：

1. 局部影響 → 增加「受影響對象」的描述能力，而不是立刻建立完整 Knowledge Graph。
2. 失敗回饋 → 增加最小 retrieval／execution receipt 概念，而不是建立大型事件平台。
3. 共同變更 → 增加最小 Change Request 概念，而不是直接修改治理規則。
4. 搜尋 → 保留既有搜尋方案，必要時以 hybrid retrieval 作為候選，必須用本庫案例測試後再決定。

## 九、下一步

下一輪必須實際建立 A／B／C 三個測試案例，分別比較候選解法，記錄：

- 輸入。
- 檢索方法。
- 使用資料。
- 候選解法。
- 執行結果。
- 失敗模式。
- 追溯能力。
- 複雜度。
- 最終採用／保留待驗證。

在測試完成前，不把任何候選解法升格為正式共同規格。
