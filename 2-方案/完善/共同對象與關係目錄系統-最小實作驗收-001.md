# 共同對象與關係目錄系統：最小實作驗收 001

日期：2026-09-17
系統：共同對象與關係目錄系統 v1.0
驗收類型：系統最小實作驗收＋模擬驗證

## 一、驗收目的

確認新建立的共同對象與關係目錄系統，是否至少能以 Repository 現有實際對象驗證其核心語義與查詢邏輯。

本次不是方案驗收，也不是方案整體實戰驗證。

## 二、整體狀態

```text
系統建立：已建立
最小實作驗收：INCOMPLETE
模擬驗證：SIMULATION-PASSED
實戰驗證：FIELD-PENDING
```

`SIMULATION-PASSED` 僅表示在人工建立的驗證條件／推演情境下，核心語義與預期行為符合目前驗收條件；不得視為真實工作驗證通過。

## 三、原本已檢查的案例

### Case 1：系統對象定位

結果：PASS（語義層）

已存在正式系統文件，例如：

`1-系統/共同對象與關係目錄系統-v1.0.md`

其系統身份不應等同於目前 Markdown 路徑；系統文件本身已明確區分 Identity、Name、Location、Version、State。

### Case 2：System → Solution 關係

結果：PASS（模型層＋Repository 結構證據）

既有 Repository 已反覆使用「系統屬於方案」關係，並已在共同 Relationship 原則中定義 `belongsTo`。

### Case 3：System A → dependsOn → System B

結果：PASS（模型層）

共同 Relationship 原則明確定義有方向的 `dependsOn`，並要求可從 Source、Type、Target 表達與查詢。

### Case 4：正向／反向關係查詢

結果：PASS（模型層）

系統規格已要求依 Source、Target、Relationship Type 查詢；反向查詢由方向關係推導，不建立第二份獨立權威資料。

### Case 5：同名不同對象區分

結果：PASS（原則層）／待實作資料案例

Repository 已明確規定 Kind／Identity 與人類名稱分離；目前尚未建立正式 Identity Registry 資料集，因此還不能宣稱已完成實際資料層驗證。

### Case 6：版本變更不自動建立新 Identity

結果：PASS（原則層）／待實際變更案例

Identity 知識已明確區分 Identity 與 Version，但尚未以實際 Identity 資料執行版本變更案例。

### Case 7：文件改名後保持 Identity

結果：NOT-A-TEST

本次沒有直接改動既有正式文件，因此沒有產生真實「改名前／改名後」的 Identity 連續性證據。

不得把設計文件的規則當作實測通過。

### Case 8：文件搬移後保持 Identity

結果：NOT-A-TEST

同理，目前沒有實際搬移案例，因此不能宣稱通過。

## 四、補充模擬驗證

為了在不修改既有正式資料的前提下確認施工方向，本次另外建立人工條件進行推演。

### Simulation S1：改名

條件：

```text
Object Identity = OBJ-SIM-001
Name = 舊名稱
Location = 舊位置
Version = v1.0
```

模擬變更：

```text
Name → 新名稱
Location 不變
Identity 不變
Version 依變更語義另行判定
```

預期：查詢新名稱仍能定位 `OBJ-SIM-001`，且不得因名稱變更自動產生新的 Object Identity。

結果：符合預期。

判定：PASS。

### Simulation S2：搬移

條件：同一 `OBJ-SIM-001`。

模擬變更：

```text
Location → 新位置
Name 不變
Identity 不變
```

預期：以 Identity 查詢仍能定位同一對象；Location 只表示目前承載位置，不作為 Identity。

結果：符合預期。

判定：PASS。

### Simulation S3：關係保存

條件：

```text
System-A
  --dependsOn-->
System-B
```

模擬查詢：

```text
Source = System-A
Type = dependsOn
Target = System-B
```

再進行反向查詢：

```text
Target = System-B
Type = dependsOn
```

預期：能找到 System-A，且不需要建立第二份獨立權威關係資料。

結果：符合目前共同關係模型。

判定：PASS。

### Simulation S4：同名不同對象

條件：

```text
OBJ-SIM-001 / Name = 系統A
OBJ-SIM-002 / Name = 系統A
```

預期：名稱相同不能導致兩個對象被視為同一對象；Identity 必須能區分。

結果：符合預期。

判定：PASS。

## 五、模擬驗證結論

```text
模擬驗證：SIMULATION-PASSED
```

本次模擬證明目前提出的 Identity／Relationship 最小語義，在人工條件下可以形成一致的預期行為。

但尚不能證明：

- 真實文件改名後資料仍能保持 Identity。
- 真實文件搬移後資料仍能保持 Identity。
- 真實工作中查詢關係時不會產生遺漏或錯誤。
- 實際施工流程會正確觸發本系統。

因此 `SIMULATION-PASSED` 必須保留，直到後續真實工作產生足夠證據後再被 `FIELD-PASSED` 或 `FIELD-FAILED` 取代。

## 六、主要實作缺口

本次驗收暴露的核心缺口仍然是：

```text
Identity 原則
↓
Relationship 原則
↓
System 規格
↓
模擬驗證
```

已形成，但尚未形成真正可持續保存的「正式對象記錄＋穩定 Identity＋關係記錄」實作資料。

因此：

```text
系統已建立
≠ 系統已完成
≠ 系統已驗收
≠ 系統實戰已驗證
```

## 七、是否建立第二個新系統

目前：不因本次結果建立新的 Identity 系統或 Relationship 系統。

原因：目前缺口仍屬於本系統最小資料實作／驗收缺口，尚未證明需要另一個系統。

## 八、自然實戰驗證條件

後續正常施工若自然產生：

```text
跨方案對象查詢
或
系統改名／搬移
或
需要查詢系統依賴／歸屬關係
```

則應在不額外製造測試工作的情況下，觀察本系統實際運作。

若有足夠結果證據：

```text
SIMULATION-PASSED
↓
FIELD-PASSED
```

若發現問題：

```text
SIMULATION-PASSED 保留為歷史證據
↓
FIELD-FAILED
↓
記錄實際缺口
↓
進入系統完善／問題解決流程
```
