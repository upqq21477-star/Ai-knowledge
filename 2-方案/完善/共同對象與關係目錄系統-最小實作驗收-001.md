# 共同對象與關係目錄系統：最小實作驗收 001

日期：2026-09-17
系統：共同對象與關係目錄系統 v1.0
驗收類型：系統最小實作驗收

## 一、驗收目的

確認新建立的共同對象與關係目錄系統，是否至少能以 Repository 現有實際對象驗證其核心語義與查詢邏輯。

本次不是方案驗收，也不是方案整體實戰驗證。

## 二、驗收結果

總判定：INCOMPLETE（部分成立，尚未通過完整最小實作驗收）

原因：Repository 可以直接提供目前對象、方案歸屬、文件位置與多個歷史／現行名稱作為實際資料；但「文件改名／搬移後仍維持同一 Identity」需要實際身份資料與變更操作才能完成，不能只靠設計文件推論。

## 三、已實際檢查

### Case 1：系統對象定位

結果：PASS（語義層）

已存在正式系統文件，例如：

`1-系統/共同對象與關係目錄系統-v1.0.md`

其系統身份不應等同於目前 Markdown 路徑；系統文件本身已明確區分 Identity、Name、Location、Version、State。

### Case 2：System → Solution 關係

結果：PASS（模型層＋Repository 結構證據）

既有 Repository 已反覆使用「系統屬於方案」關係，並已在共同 Relationship 原則中定義 `belongsTo`。

### Case 3：System A → dependsOn → System B

結果：PASS（模型層）

共同 Relationship 原則明確定義有方向的 `dependsOn`，並要求可從 Source、Type、Target 表達與查詢。

### Case 4：正向／反向關係查詢

結果：PASS（模型層）

系統規格已要求依 Source、Target、Relationship Type 查詢；反向查詢由方向關係推導，不建立第二份獨立權威資料。

這與外部成熟 Catalog 的方向性 Relation 模型一致。Backstage 將 relation 定義為 source、target、type，並提供反向關係查詢語義。citeturn3search0turn4search6

### Case 5：同名不同對象區分

結果：PASS（原則層）／待實作資料案例

Repository 已明確規定 Kind／Identity 與人類名稱分離；目前尚未建立正式 Identity Registry 資料集，因此還不能宣稱已完成實際資料層驗證。

### Case 6：版本變更不自動建立新 Identity

結果：PASS（原則層）／待實際變更案例

Identity 知識已明確區分 Identity 與 Version，但尚未以實際 Identity 資料執行版本變更案例。

### Case 7：文件改名後保持 Identity

結果：NOT-A-TEST

本次沒有直接改動既有正式文件，因此沒有產生真實「改名前／改名後」的 Identity 連續性證據。

不得把設計文件的規則當作實測通過。

### Case 8：文件搬移後保持 Identity

結果：NOT-A-TEST

同理，目前沒有實際搬移案例，因此不能宣稱通過。

## 四、主要缺口

本次驗收暴露的不是「Relationship 語義不足」，而是：

```text
Identity 原則
↓
Relationship 原則
↓
System 規格
```

已形成，但尚未形成真正可持續保存的「正式對象記錄＋穩定 Identity＋關係記錄」實作資料。

因此目前狀態應保持：

```text
系統已建立
≠
系統已驗收
≠
系統實戰已驗證
```

## 五、是否建立第二個新系統

目前：不因本次結果建立新的 Identity 系統或 Relationship 系統。

原因：目前缺口仍屬於本系統最小資料實作／驗收缺口，尚未證明需要另一個系統。

下一步應先補足本系統的最小資料實作與可重現驗收方式，再進行正常工作中的自然實戰驗證。

## 六、外部方法對照

Backstage 的 Catalog 將 Entity、Identity、Relations 與狀態分開，並把 Catalog 定位為組織與發現的中心，而不是所有動態業務邏輯的最終來源。citeturn3search0turn4search8

這支持本系統目前採用「薄型共同目錄／關係層」而非中央業務引擎的方向。

## 七、下一步

1. 補足最小正式對象記錄方式。
2. 補足 Identity 與文件承載位置的可追溯關聯。
3. 在不破壞既有資料的前提下，選擇一個可自然發生的改名／搬移案例。
4. 再執行 Identity 連續性驗收。
5. 若自然施工觸發跨方案身份／關係查詢，順便完成實戰驗證。
6. 只有實際缺口成立，才回到系統完善流程。
