# 二、驗收規則

本專案目前所有「實戰驗收」先統一採用「模擬測試運行（Simulation Validation）」。

模擬驗收只確認：

1. 功能定義可操作。
2. 邊界可與相鄰功能區分。
3. 最小資料與流程模型能承受典型案例。
4. AI 容易犯的錯誤可被識別。
5. 失敗案例有明確診斷方向。

不得把模擬結果寫成真實長期運作證據。

未來系統進入長期真實運作後，若真的發生問題，再建立「真實案例驗證（Real-world Validation）」並回歸模擬。

# 四、B1 任務理解 Task Understanding

## 4.1 功能問題

把自然語言需求轉成可工作的任務表示：

```text
原始需求
↓
問題／目標
↓
條件
↓
限制
↓
輸出要求
↓
驗證要求
```

不能把「理解」等同於產生一段看似合理的回答。

## 4.2 外部研究

複雜任務研究顯示，LLM 任務理解的重要問題不是單純語言解析，而是把複雜目標轉為具有步驟與依賴關係的結構。Google Research 的 TaskLAMA 將 Structured Complex Task Decomposition 定義為把複雜真實任務拆成個別步驟並以依賴關係連接；其結果也指出 LLM 在步驟分解上有能力，但在預測步驟間的成對時間依賴上仍存在困難。citeturn1search5

這支持本專案把「任務理解」與「任務拆解」分開：B1 先確認任務到底要解決什麼，B2 才負責如何拆成可執行子任務。

## 4.3 必要性

【必要；系統化能力候選】

理由：若任務本身沒有被正確表示，後續搜尋、研究、Context 組裝與驗證都可能在錯誤目標上進行。

## 4.4 邊界

```text
B1 任務理解
= 我要解決什麼？條件與成功標準是什麼？

B2 任務拆解
= 要分成哪些可研究／可執行／可驗證工作？

B3 知識搜尋
= 到哪裡找相關資料？

B5 外部研究
= Repository 不足時，如何向外取得資料？
```

B1 不應直接執行搜尋，也不應直接決定最終答案。

## 4.5 最小模型

```text
Task ID
Goal
Question
Constraints
Scope
Output Requirements
Success Criteria
Uncertainties
```

欄位不是要求立即固定成 JSON Schema；目前只定義語義需求。

## 4.6 模擬案例

案例：

「我要知道這個知識庫目前的搜尋系統是否需要新增語意搜尋。」

正確理解應至少得到：

- 目標：判斷是否需要新增能力。
- 問題：目前搜尋能力能否滿足需求？
- 條件：先檢查既有能力，再研究外部方法。
- 範圍：目前搜尋系統與相關工作流程。
- 輸出：是否需要新增、完善、重構或維持。
- 成功標準：有既有能力盤點、外部證據、差距與驗證結果。

### 模擬結果

【通過】

## 4.7 失敗案例

輸入同一需求後，AI 直接回答「應該加入向量搜尋」。

判定：B1 失敗。

原因：尚未完成任務理解與既有能力檢查，就跳到方案選擇。

# 五、B2 任務拆解 Task Decomposition

## 5.1 功能問題

將複合任務轉為具有順序、依賴、輸入、輸出與驗證條件的子任務。

## 5.2 外部研究

Google Research 的 TaskLAMA 將複雜任務分解建模為有向無環圖（DAG），節點是個別步驟，邊表示時間依賴；研究同時指出 LLM 對步驟本身可以有良好表現，但步驟間依賴仍是困難點。citeturn1search5

因此不能把「列出很多步驟」當成拆解成功。拆解還必須保留依賴與可驗證性。

## 5.3 必要性

【必要；系統化能力候選】

B1 只得到任務目標仍不足以支撐大型研究、變更與驗收工作；B2 是把複合任務轉成工作單元的橋樑。

## 5.4 邊界

B2 不負責：

- 決定知識真偽。
- 執行所有子任務。
- 直接建立新系統。
- 取代結果驗證。

B2 負責的是「任務結構」。

## 5.5 最小模型

```text
Parent Task
↓
Subtask
├─ Objective
├─ Input
├─ Output
├─ Dependency
├─ Verification Condition
└─ Completion Condition
```

若兩個子任務可以平行，不能被錯誤強制串成線性流程；若存在依賴，則不能遺漏依賴。

## 5.6 模擬案例

任務：「研究一個新搜尋方法是否值得加入知識庫。」

最小拆解：

```text
1. 定義問題與成功標準
2. 盤點現有搜尋能力
3. 找到目前失敗／不足案例
4. 外部研究候選方法
5. 比較候選方法與現有能力
6. 設計模擬驗證
7. 得出採用／不採用／暫緩所需證據
```

其中 2、3 是判斷 4 的重要前置資料；5 必須同時取得現有能力與外部研究結果。

### 模擬結果

【通過】

## 5.7 失敗案例

AI 直接拆成「搜尋 → 向量化 → 上線」，完全跳過既有能力盤點、失敗案例與驗證。

判定：B2 失敗。

這不是拆解太短，而是任務結構錯誤。

# 六、B3 知識搜尋 Knowledge Search

## 6.1 功能問題

從 Repository 中找出與目前任務相關、可用且需要進一步閱讀的知識候選。

## 6.2 外部研究

現代 Retrieval-Augmented Generation（RAG）研究已證明單一檢索方法並不一定足夠。Anthropic 的 Contextual Retrieval 實驗結合語意 embeddings 與 BM25，並以 reranking 再排序；其實驗顯示，加入上下文、混合檢索與 reranking 可以逐步降低 top-k 檢索失敗率。Anthropic 同時明確指出 chunk 邊界、上下文數量與 reranking 都需要實際 eval，資料越多也不必然越好。citeturn1search0turn1search2

因此 B3 不應被定義成「使用某一種搜尋技術」，而應定義成「找到與任務相關的候選知識」。技術實作可由精確搜尋、語意搜尋、混合檢索、關係搜尋等共同支撐。

## 6.3 必要性

【必要；核心系統化能力】

沒有 B3，B9 上下文組裝只能依賴人工指定文件或整庫載入，無法規模化。

## 6.4 邊界

```text
B3 搜尋
= 找到候選資料

B4 探索
= 當不知道確切答案／名稱時，沿著相關概念擴展搜尋範圍

B6 來源／證據判斷
= 判斷找到的內容到底是什麼證據角色

B7 適用性判斷
= 判斷找到的資料能不能用在目前任務
```

B3 不應自行把「搜尋排名第一」升格為「正確答案」。

## 6.5 最小模型

```text
Query
↓
Candidate Set
↓
Relevance / Match Basis
↓
Result Metadata
↓
Next Action
```

候選結果至少應保留可追溯身份，而不是只回傳一段文字。

## 6.6 模擬案例

查詢：「目前方案四重構後驗證需要驗證什麼？」

要求搜尋系統找到：

- 方案四正式文件。
- 重構後驗證相關文件。
- 既有驗收案例。
- 相關責任邊界／歷史規則。

### 模擬結果

【通過】

## 6.7 失敗案例

搜尋只因某文件標題含「重構」就回傳它，卻沒有確認版本、狀態與內容相關性。

判定：B3 只完成字面命中，不代表知識搜尋成功。

# 七、B4 資料探索 Data Exploration

## 7.1 功能問題

當使用者不知道精確資料名稱、術語或位置，或第一次搜尋不足以建立問題全貌時，探索相關內容、鄰近概念、關係與候選路徑。

## 7.2 外部研究

資訊檢索研究長期使用 query expansion（查詢擴展）處理初始查詢不足問題。NIST 收錄的研究顯示，查詢擴展會影響檢索效能，且應分析不同主題與檢索方法的差異，而不能假定一次擴展永遠有效。citeturn1search8

較新的研究也把 query reformulation、embedding 與文件集合擴展結合，用於在初始候選之外找出相關文件，反映探索本質上不同於單次精確檢索。citeturn1search1

## 7.3 必要性

【必要；系統化能力候選】

知識庫內很多任務不是「已知檔名 → 找檔案」，而是「知道問題 → 不知道知識放在哪」。因此需要探索能力。

## 7.4 邊界

```text
搜尋 Search
= 已有較明確目標，找符合條件的候選

探索 Exploration
= 目標或路徑仍不完整，透過概念、關係、鄰近資料逐步縮小問題空間
```

探索不能無限制擴張；每次擴張都需要保留「為何探索到這裡」的路徑，並在證據不足或收益降低時停止。

## 7.5 最小模型

```text
Initial Question
↓
Known Concepts
↓
Expansion Rule
↓
New Candidates
↓
Relationship / Reason
↓
Narrowed Question
↓
Stop / Continue
```

## 7.6 模擬案例

初始問題：「這個 Repository 有沒有處理 AI 交接遺失資訊的方法？」

探索可能經過：

```text
交接
→ Context
→ 長期記憶
→ 目前狀態
→ 交接文件
→ 知識庫交接
→ 相關驗證案例
```

最後收斂到真正相關的資料，而不是把所有含「AI」的文件都納入。

### 模擬結果

【通過】

## 7.7 失敗案例

探索從「交接」一路擴展到所有「AI」「系統」「知識」文件，沒有停止條件。

判定：探索失控。

B4 必須存在停止判斷，不是「找到越多越好」。

# 八、B1～B4 的共同邊界

```text
B1 任務理解
      ↓
B2 任務拆解
      ↓
B3 知識搜尋 ←→ B4 資料探索
      ↓
候選資料
```

其中：

- B1 決定「要解決什麼」。
- B2 決定「工作怎麼分」。
- B3 決定「已知目標下找什麼」。
- B4 處理「不知道資料在哪／不知道完整概念」的探索問題。

四者不能互相吞併。

# 十、對方案二後續設計的直接結論

1. B1～B4 均有必要性，不應刪除。
2. 不應因此建立四套獨立系統；Repository 已有相關能力，應先做責任與接口整理。
3. B1、B2 是任務結構層；B3、B4 是知識取得層。
4. B3 不應被固定成單一搜尋技術；搜尋能力應可容納精確、語意、混合與關係式檢索。
5. B4 必須有探索停止條件，否則會把 Context 與搜尋成本無限放大。
6. B1～B4 的成功都不能用「AI 回答看起來合理」判定，而應以任務結構、候選相關性、依賴完整性、可追溯性與失敗案例判定。
7. 目前尚不能宣布方案二完成；本批只是 B1～B4 的逐項研究與模擬驗收。
