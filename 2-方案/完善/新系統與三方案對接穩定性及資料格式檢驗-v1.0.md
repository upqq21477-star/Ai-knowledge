# 新系統與三方案對接穩定性及資料格式檢驗 v1.0

日期：2026-09-17
狀態：【第一輪檢驗完成；語義對齊通過；流程對接可成立；共同資料格式仍屬最小描述層，尚未形成機器可執行 Schema】

## 一、檢驗目的

本文件只檢驗新架構，不修改或依賴舊方案、舊系統的運行資料。

檢驗三件事：

1. 目前有哪些新系統，以及各自負責什麼。
2. 新系統與三個正式方案能否正常對接。
3. 三方案與新系統是否使用一致的資料語義、描述維度、版本與關係概念。

「格式統一」在本輪不等於要求所有文件使用相同欄位或 JSON Schema，而是先檢查語義與最小描述維度是否一致。

## 二、目前新架構中的能力物件

### 正式三個新系統

1. 整體資料治理系統 v1.0
2. AI知識管理系統 v2.0
3. 知識迭代與資料演化系統 v1.0

三者分工為：

```text
整體資料治理
→ 共同資料語義、邊界、狀態、版本、關係與追溯規則

AI知識管理
→ 任務理解、資料取得、搜尋研究、Context、執行、驗證與回饋

知識迭代與資料演化
→ 變更確認、影響分析、版本演化、相容性、歷史與回饋
```

三個系統的定位互補，沒有發現核心責任直接重疊。

### 問題解決系統

目前另有：

`1-系統/問題解決系統-v1.0.md`

它是跨方案的小型問題處理能力，不是第四個正式方案。其工作是把已確認問題交給搜尋研究、外部比較、候選解法與最小實測，必要時進入新系統建立分支。

目前另有新版整合流程：

`1-系統/問題解決與新系統建立流程-v1.1.md`

它是問題解決系統的流程擴充，不應再視為一個獨立正式系統物件。

### 搜尋研究

`搜尋研究方案-v2.0` 是研究型工作方案，不是第四個核心系統。

它被 AI知識管理與問題解決流程調用，負責研究問題、資訊需求、搜尋、來源／證據分析、比較、停止與回退。

因此目前沒有因為加入搜尋研究新版而產生第四個核心系統。

## 三、三個正式方案與系統對接矩陣

| 方案 | 主要使用系統 | 主要輸入 | 主要輸出 | 對接結果 |
|---|---|---|---|---|
| 整體資料治理方案 | 整體資料治理系統 | 新資料、變更、衝突、版本、驗證結果 | 共同規則、狀態、版本、關係、影響判定 | 通過 |
| AI知識管理方案 | AI知識管理系統 | 任務、資料需求、知識、記憶、狀態 | 任務結果、引用資料、驗證結果、回饋 | 通過 |
| 知識迭代與資料演化方案 | 知識迭代與資料演化系統 | 變更訊號、新證據、使用失敗、演化需求 | 新版本候選、影響分析、相容性、歷史 | 通過 |

三方案不是各自建立獨立資料語言，而是共同使用治理層定義的資料語義。

## 四、共同資料語義檢查

目前共同資料類型為八類：

```text
知識 Knowledge
記憶 Memory
目前狀態 Current State
來源 Source
證據 Evidence
主張 Claim
決策 Decision
觀察 Observation
```

三方案目前可以用同一組概念描述主要資料。

特別檢查以下邊界：

```text
知識 ≠ 記憶
知識 ≠ 目前狀態
來源 ≠ 證據
證據 ≠ 主張
主張 ≠ 知識
觀察 ≠ 知識
決策 ≠ 永久規則
```

本輪未發現三方案需要自行重新定義上述概念的情況。

判定：**語義一致。**

## 五、共同描述格式檢查

目前共同描述不是固定欄位，而是七個描述維度：

```text
Identity
Content
Scope
Conditions
Time
State
Basis / Provenance
```

三方案均能對應：

- Identity：知道目前處理的是哪一項資料／能力。
- Content：知道實際內容。
- Scope：知道適用範圍。
- Conditions：知道成立條件。
- Time：知道時間有效性。
- State：知道目前採用／待確認／歷史等狀態。
- Basis / Provenance：知道形成依據與追溯來源。

因此目前可以判定：

**共同描述語義已對齊，但尚未形成固定機器 Schema。**

這不是缺陷本身，因為目前共同描述原則明確禁止在實際案例不足前強制建立固定 JSON Schema 或資料庫欄位。

## 六、版本資料對接檢查

目前三方案都需要區分：

```text
內容版本
來源版本
方案版本
系統版本
Git／檔案變更版本
```

檢查結果：

- 治理：負責共同版本語義與相容性約束。
- AI知識管理：使用版本與狀態判斷是否適用。
- 資料演化：產生與管理版本演化候選。

因此責任方向正確。

目前缺口是：尚未建立可直接機器執行的統一 Version Object。

判定：**語義對齊，執行格式未統一。**

## 七、關係資料對接檢查

目前六個最小共同關係為：

```text
定義 Defines
依賴 Depends On
約束 Constrains
實作 Implements
互補 Complements
產生／回饋 Produces / Feeds Back
```

三方案均可使用這六種關係描述主要協作：

```text
治理規則
→ 約束 → AI知識管理

AI任務結果
→ 產生／回饋 → 資料演化

資料演化結果
→ 回饋 → 治理
```

演化專用的補充、修正、部分取代、完全取代、融合、拆分、廢棄等關係目前仍是候選語義，不應假裝已經是完整共同 Schema。

判定：**基本關係對齊；演化關係仍需案例驗證。**

## 八、實際跨系統流程檢驗

### 案例 A：AI 使用資料

```text

↓

↓
治理提供資料語義／狀態／版本／來源
↓
AI取得 Context
↓
執行
↓
驗證
```

結果：通過。

### 案例 B：AI 發現新證據

```text
AI知識管理
↓
新來源／證據
↓
資料演化
↓
影響分析
↓
版本候選
↓
治理檢查共同語義
↓
AI重新取得資料
↓
再次驗證
```

結果：通過設計級對接。

### 案例 C：共同資料語義變更

```text
任一系統發現共同語義不足
↓
提出變更需求
↓
治理判斷是否屬共同規則
↓
分析受影響方案／系統
↓
建立候選變更
↓
三方案重新驗證
```

結果：流程可以閉合，但 Change Request 最小資料格式尚未正式固定。

判定：部分通過。

### 案例 D：任務失敗

```text
AI任務失敗
↓
分類原因
├─ 資料不足 → 搜尋／研究
├─ 資料狀態／版本問題 → 治理
├─ 資料過期／錯誤 → 資料演化
└─ 系統能力不足 → 問題解決／新系統建立流程
```

結果：責任分流一致。

但跨系統 Failure Receipt 尚未正式固定，因此實際長流程仍可能出現重複描述。

## 九、資料格式統一程度

本輪將「統一」分成四級：

| 層級 | 定義 | 目前結果 |
|---|---|---|
| L1 語義統一 | 同一概念有同一基本含義 | 通過 |
| L2 描述維度統一 | 能用共同 Identity／Content／Scope／Conditions／Time／State／Provenance 描述 | 通過 |
| L3 交換格式統一 | 不同系統可直接交換同一結構化資料物件 | 尚未完成 |
| L4 機器介面統一 | 可由程式直接驗證、傳輸、版本化與執行 | 尚未完成 |

因此目前不能宣稱「資料格式完全統一」。

準確說法是：

> **三方案與三核心系統已完成共同語義與最小描述層對齊；尚未建立正式交換格式與機器介面契約。**

## 十、對接穩定性判定

目前可確認：

### 已穩定

1. 三方案的責任方向一致。
2. 三核心系統的責任方向一致。
3. 八種核心資料語義可以共用。
4. 七個最小描述維度可以共用。
5. 版本責任可以分工。
6. 六個基本關係可以跨方案使用。
7. 搜尋研究可以被 AI知識管理與問題解決流程調用。
8. 問題解決可以在能力不足時進入新系統建立分支。
9. 資料演化可以把變更回饋治理，再由 AI重新使用。

### 尚未穩定／需要第三輪案例

1. 局部影響如何描述。
2. Failure Receipt 的共同最小格式。
3. Change Request 的共同最小格式。
4. 多輪搜尋的 Receipt 是否足以重建完整研究過程。
5. 多系統同時失敗時的責任歸屬。
6. 多版本並存時 AI 是否一定取得正確適用版本。
7. 演化關係在真實案例中是否需要正式化。

## 十一、重要發現

目前最大的問題不是「方案互相衝突」，而是：

> **語義已經開始統一，但交換資料的具體契約還沒有形成。**

這是合理的階段性結果。

如果現在直接建立大型 JSON Schema、資料庫或 API，反而可能在案例不足時把尚未驗證的假設硬化。

目前應先用真實跨方案案例找出反覆出現的資料，再決定哪些資料值得升格為正式交換物件。

## 十二、第一輪結論

本輪結論：

```text
三方案
  ↓
共同資料語義
  ↓
三核心系統
  ↓
問題解決／搜尋研究等跨方案能力
  ↓
可以形成閉環
```

目前沒有發現必須增加第四個正式方案的證據。

目前沒有發現必須把「問題解決與新系統建立流程」升格為第四個正式方案的證據。

目前也沒有發現搜尋研究新版與三核心系統產生不可調和的責任衝突。

但「對接可以成立」與「機器可以直接交換資料」仍是兩個不同成立條件。

本輪只證明前者。

## 十三、下一輪檢驗

下一輪不應再做抽象討論，直接建立一個跨方案長流程案例：

```text
AI任務
↓
搜尋研究
↓
取得外部證據
↓
發現與現有知識衝突
↓
資料演化
↓
影響分析
↓
治理檢查
↓
建立新版本
↓
AI重新取得 Context
↓
任務重新執行
↓
驗證失敗或成功
↓
問題解決流程介入
↓
判斷是否需要新增系統能力
```

這個案例應特別測試：

- 同一資料在不同系統間是否需要重複描述。
- 同一版本是否會出現不同名稱／不同狀態。
- Failure Receipt 能否一次傳遞而不重寫。
- Change Request 能否跨三方案追蹤。
- Search Receipt、Change Receipt、Validation Receipt 是否能形成一條可回溯鏈。

在這些案例完成前，不升格為固定 Schema 或 API 契約。
