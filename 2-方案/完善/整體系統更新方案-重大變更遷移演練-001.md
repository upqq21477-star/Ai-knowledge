# 整體系統更新方案－重大變更遷移演練 001

日期：2026-09-17
狀態：【Preflight 完成；低風險遷移演練完成；未修改舊檔案；待正式方案實戰】

案例來源：`2-方案/整體系統更新方案-自然案例驗證-001.md`
演練目的：驗證新增的「重大變更與遷移安全原理」能否實際約束一次結構性更新，而不是只存在於知識書。

## 一、演練邊界

本次不直接修改既有方案、既有知識、目錄或系統檔案。

因此本次演練驗證的是：

```text
變更辨識
→ 新舊基線
→ 依賴分析
→ Breaking Change 判定
→ 遷移策略
→ Dry Run
→ 驗證
→ Rollback 條件
→ 退役判定
```

不是實際生產資料切換。

## 二、Preflight

### 變更案例

假設將目前知識庫的「狀態標記」從舊格式：

`狀態：【第一版成立；待完整實際驗證】`

改為新的結構化狀態欄位：

```text
建立狀態
完善狀態
驗收狀態
實戰狀態
```

此變更會影響 AI 讀取方式、文件解析方式、搜尋條件與交接判讀，因此不能視為單純文字修改。

### 風險判定

| 項目 | 判定 |
|---|---|
| 結構變更 | 是 |
| 行為變更 | 是，可能改變 AI 判讀 |
| Breaking Change | 潛在是 |
| 依賴數量 | 中 |
| 回復難度 | 中 |
| 是否需要遷移 | 是 |
| 是否允許直接覆蓋 | 否 |

Preflight：PASS

## 三、新舊基線

### 舊基線

目前 Repository 的既有狀態標記格式與現有交接／方案文件。

### 新基線

新的分離式狀態欄位模型。

### 保護原則

舊基線在新基線完成驗證前保持不動。

本次實際演練中因此沒有修改舊檔案。

## 四、依賴分析

需要檢查的依賴類型：

1. 方案狀態讀取。
2. 工程狀態快照。
3. AI 交接資料。
4. 待辦清單中的狀態判斷。
5. 搜尋時依賴狀態文字的流程。
6. 未來可能建立的自動解析工具。

結論：不能只修改文件格式而不檢查下游讀取者。

## 五、遷移策略

本案例採用：

`新模型先建立 → Dry Run → 讀取驗證 → 相容性檢查 → 小範圍切換 → 穩定後才退役舊格式`

不採用直接覆蓋。

原因：目前 AI 知識庫的主要使用者是不同 AI 工作階段；若直接改格式，可能造成舊 AI 無法正確恢復工程狀態。

## 六、Dry Run

Dry Run 不寫入舊檔案，只模擬：

```text
舊狀態
↓
解析
↓
轉換成新狀態模型
↓
檢查是否遺失資訊
↓
檢查是否產生歧義
↓
模擬 AI 恢復工程位置
```

### Dry Run 結果

原有單一狀態句包含多個語義：

- 是否建立。
- 是否完善。
- 是否驗收。
- 是否實戰。

直接拆分時可以保留主要資訊，但歷史狀態與「目前採用」語義不能只靠字串轉換可靠推導。

因此：

`Dry Run：PARTIAL PASS`

發現必須另外保存「目前採用狀態」與「歷史狀態」的語義來源，不能單純 regex／文字替換。

## 七、Rollback 演練

假設新狀態模型上線後發生：

- AI 無法恢復目前工程位置。
- 舊引用仍依賴舊狀態字串。
- 新舊狀態產生矛盾。

Rollback 條件：任一核心工程恢復資訊遺失或產生不可判定狀態。

Rollback 目標：恢復到「舊基線未修改」狀態。

本次因沒有真正修改舊檔案，所以 Rollback 實際結果為：

`PASS：無需回復寫入；舊基線仍完整存在。`

## 八、驗證層級

### 1. 結構驗證

PASS：新模型可以明確表示建立／完善／驗收／實戰等狀態。

### 2. 功能驗證

PASS：可表達目前工程階段。

### 3. 相容性驗證

PARTIAL：舊格式中的複合語義不能完全安全自動拆分。

### 4. 一致性驗證

PASS（演練層級）：因未實際切換，所以不存在新舊實體資料不一致。

### 5. 實際使用驗證

尚未完成。需要真正由新 AI 使用新模型恢復工程狀態後才能判定。

## 九、退役判定

本次禁止退役舊格式。

理由：

1. 相容性仍只有 PARTIAL PASS。
2. 尚未完成真實 AI 讀取驗證。
3. 尚未完成下游引用完整盤點。
4. 尚未證明新模型在實際工作中不增加 Context 成本。

因此：

`舊格式：保留`
`新格式：候選`
`正式切換：LOCK`

## 十、演練結論

本次演練成功證明新增知識不是裝飾性文件：它實際阻止了一次「直接改格式、舊檔案立即退役」的錯誤施工。

同時也發現新的實務缺口：

> **狀態格式大型重製需要「語義遷移」能力，而不能只做檔案格式轉換。**

這是新的知識／能力觀察點，但目前不足以建立獨立系統。

## 十二、對方案的實際回饋

本次演練支持以下原則：

`重大變更不能等同於建立新版本。`

至少還需要：

`語義遷移 → 相容性 → Dry Run → 實際使用 → Rollback → 穩定後退役`

同時證明目前仍不需要建立新的「遷移系統」。既有更新、比較、影響分析、知識整合、方案管理能力可以承擔這次演練；目前缺的是流程與知識的組合，而不是獨立執行器。

## 十三、下一步

1. 不修改舊格式。
2. 不宣布新格式正式採用。
3. 對「語義遷移」建立正式知識缺口觀察。
4. 下一輪使用真實 AI 交接情境驗證新舊狀態是否可安全恢復。
5. 實際使用驗證通過後，才重新判斷是否允許正式切換。
