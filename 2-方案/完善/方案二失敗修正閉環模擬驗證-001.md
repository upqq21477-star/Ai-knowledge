## 一、目的

確認方案二在任務執行失敗後，能否形成完整且有邊界的：

```text
失敗 → 診斷 → 問題確認 → 問題解決 → 修正 → 重新驗證 → 恢復／再次診斷
```

本案例為人工模擬，不代表實戰驗證。

## 二、模擬案例 A：第一次修正成功

### 初始任務

AI 需要使用某知識項目完成任務。

預期：使用目前有效版本。

實際：錯誤使用已失效版本。

結果：驗證 FAIL。

### 處理

```text
FAILURE-DETECTED
↓
DIAGNOSING
↓
確認原因：版本／狀態判斷錯誤
↓
問題解決流程
↓
候選修正：強化目前狀態與版本適用性判斷
↓
FIX-IMPLEMENTED
↓
REVALIDATING
```

### 重新驗證

以原本失敗條件重新執行。

結果：使用有效版本，符合預期。

追加檢查：沒有發現新的阻塞性副作用。

判定：

```text
RESOLVED
```

## 三、模擬案例 B：第一次修正無效

### 初始失敗

與案例 A 相同：錯誤版本被採用。

### 第一次修正

加入額外版本判斷條件。

重新驗證仍 FAIL。

此時禁止：

```text
FIX-IMPLEMENTED → 直接 RESOLVED
```

正確流程：

```text
REVALIDATING
↓
FAIL
↓
REDIAGNOSE
```

### 第二次診斷

重新檢查問題責任層，發現真正問題不是單一版本判斷，而是 Context 組裝時同時帶入歷史版本，造成選擇歧義。

因此第二候選修正轉向 Context 組裝責任，而不是繼續增加版本判斷條件。

### 第二次修正

```text
Context 組裝
→ 排除不適用歷史版本
→ 保留必要歷史作為追溯資料
```

再次驗證：PASS。

判定：

```text
RESOLVED
```

## 四、模擬案例 C：修正產生副作用

假設修正版本判斷後，原問題消失，但導致需要比較歷史版本的任務無法取得必要資料。

此時不能宣稱完全解決。

判定：

```text
PARTIAL
```

應重新進入問題分析，尋找兼顧「目前版本使用」與「歷史版本追溯」的方案。

## 五、邊界測試

### B1：不能無限重試相同修正

若相同修正連續失敗，不得無限執行：

```text
修正 → 失敗 → 同一修正 → 失敗 → 同一修正……
```

應回到診斷階段，確認問題定義是否錯誤。

### B2：不能因一次失敗就重建整個方案

若問題只屬於版本適用性，不得因局部失敗重建整個 AI 知識管理方案。

### B3：不能因一次修正成功就宣稱整體實戰驗證

本案例即使模擬 PASS，也只能得到：

```text
SIMULATION-PASSED
FIELD-PENDING
```

### B4：不能為理論例外無限增加流程

只有真實工作或最低驗收條件證明存在的問題，才重新打開方案結構。
