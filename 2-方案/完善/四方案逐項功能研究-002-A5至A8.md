# 一、研究目的

本批次不是直接設計最終 Schema，而是逐項確認四件事：

1. 這個能力是否真的必要。
2. 它與其他能力的責任邊界在哪裡。
3. 外部成熟方法如何處理相同問題。
4. 在本知識庫中，最低需要做到什麼程度才能算成立。

目前原始功能拆解對四項能力的定義為：

- A5 狀態管理：回答「目前這筆資料處於什麼有效狀態？」並要求與版本分離。
- A6 版本管理：回答「這個內容如何由前一版本演化到目前版本？」並要求與 Git commit、檔名分離。
- A7 關係管理：回答「資料、知識、系統、方案之間如何表達關係？」並研究 relation model、dependency graph、ownership。
- A8 生命週期管理：回答「新增、使用、修正、取代、退役、歷史保存如何表達？」

以上定義來自既有功能拆解，並非本研究新創設。既有文件也明確把 State、Version、Relationship、Lifecycle 列為方案一共同核心輸出。

# 二、A5 狀態管理 State

## 2.1 問題定義

State 要回答的是：

「某一個具有固定 Identity 的對象，在某一時間與某一判定維度下，現在處於什麼狀態？」

這與「它是哪一版」不同。

同一版本可以處於不同狀態，例如：

- draft / 草稿
- under-review / 審查中
- validated / 已驗證
- active / 使用中
- superseded / 已被取代
- deprecated / 已棄用
- archived / 已封存

因此 State 不能被 Version 取代。

## 2.2 外部研究

ISO 15489-1:2016 將 records management 定義為跨時間對 records 的建立、捕捉與管理，並明確涉及 metadata、records systems、責任、控制與管理流程。這支持「資料在其存在期間需要可管理狀態」這一基本需求，但 ISO 並沒有要求本系統直接採用某一套固定狀態枚舉。 citeturn0search3

W3C PROV 也區分 Entity 的生成與失效（invalidation），並提供 wasInvalidatedBy / invalidatedAtTime 等語義；這表示「是否仍然有效／是否已失效」可以是獨立於版本身份的資訊。 citeturn1search0turn1search1

## 2.3 對本系統的結論

結論：必要，正式能力候選；優先級高。

但不應建立一個萬用的單一 `status` 欄位，把以下概念全部塞進去：

- 工作狀態
- 驗證狀態
- 使用狀態
- 生命周期狀態
- 版本狀態
- 可信度

這正是舊模式容易產生的問題。

本系統至少需要把「狀態維度」與「狀態值」概念分開。

例如：

```text
validation_state = verified
usage_state = active
lifecycle_state = current
```

這只是研究結果中的示意，不是最終 Schema。

## 2.4 與其他能力的邊界

State ≠ Version

Version 描述內容如何演化；State 描述該對象目前處於什麼狀態。

State ≠ Lifecycle

Lifecycle 描述對象從產生到退出的整體生命歷程；State 是某一時間點／階段的狀態。

State ≠ Evidence

Evidence 可以支持「已驗證」這個狀態，但 Evidence 本身不是 State。

State ≠ History

History 保存曾經發生的事件或狀態變化；State 是目前可直接使用的判定。

## 2.5 最低驗收條件

建立一個資料對象，至少模擬：

```text
draft → review → verified → active → superseded
```

驗收時必須能回答：

1. 目前狀態是什麼？
2. 這個狀態是哪一個維度？
3. 狀態依據或驗證證據在哪裡？
4. 版本改變時，狀態是否可以獨立變化？
5. 歷史狀態是否仍可追溯？

如果只能回答「status=xxx」，則不能視為完成。

# 三、A6 版本管理 Version

## 3.1 問題定義

Version 要回答的是：

「同一個邏輯對象，在內容、結構、規格或定義發生演化後，如何識別不同版本，以及版本之間如何建立演化關係？」

核心關係是：

```text
Identity
  ↓
Version 1 → Version 2 → Version 3
```

Identity 保持對「同一邏輯對象」的辨識；Version 用來區分該對象的不同演化結果。

## 3.2 外部研究

Semantic Versioning 2.0.0 明確要求版本號表達變更意義，並以 MAJOR、MINOR、PATCH 區分不相容變更、相容功能新增與相容修正；已發布版本的內容不得直接修改，修改應產生新版本。 citeturn0search0turn0search1

但 SemVer 的前提是存在可定義的 public API，因此不能直接把 `X.Y.Z` 當成本知識庫所有文件的通用版本規則。它可以作為「語義版本」的一種方法，而不是整個 Repository 的唯一版本模型。 citeturn0search0

Git 的 revision model 則以 commit、tree、blob 等物件組成歷史，commit 代表專案歷史中的一次變更步驟；revision 可以透過 SHA、ref、tag 等方式指向歷史中的特定對象。 citeturn0search7turn0search10

W3C PROV 更直接區分「版本」與「版本產生關係」：`wasRevisionOf` 表示新 Entity 是舊 Entity 的修訂版，revision 是 derivation 的特殊形式。PROV 也提供 specialization / alternate 來描述同一事物不同時間、上下文或抽象層級的表示。 citeturn1search0turn1search1

## 3.3 對本系統的結論

結論：必要，正式能力候選；優先級高。

本系統需要的是「版本模型」，而不是單純增加一個 `version: v1.2.3` 欄位。

至少必須能表達：

```text
同一 Identity
    ↓
版本 A
    ↓ revision / supersedes
版本 B
```

並能知道：

- 哪一版是目前版本
- 前一版是哪一版
- 新版由哪一版演化而來
- 變更發生的時間
- 變更原因／變更說明
- Git commit 是否存在，以及它只是實作層面的變更證據

## 3.4 Git 與 Version 的邊界

必須維持：

```text
Logical Identity ≠ Version ≠ Git Commit ≠ Path ≠ Filename
```

Git commit 可以作為版本變更的實際歷史證據，但不能直接取代知識庫的邏輯版本。

原因包括：

1. 一個邏輯版本可能涉及多個 commit。
2. 一個 commit 可能同時修改多個不同邏輯對象。
3. 文件搬移或重命名不應自動被理解成邏輯版本的新對象。
4. Repository 之外的資料也可能有版本演化，但不存在 Git commit。

因此 Git 是底層變更歷史工具，不是本系統完整的 Version 語義層。

## 3.5 最低驗收條件

至少建立：

```text
Object A
  v1
  ↓ 修改
  v2
  ↓ 修改
  v3
```

並測試：

- A1 Identity 在版本間保持一致。
- 可以找出目前版本。
- 可以從 v3 回溯 v2、v1。
- 可以說明 v2 是由 v1 修訂而來。
- Git commit 可作為附加追溯資訊，但拿掉 Git 仍能理解版本關係。

若系統只能依賴 Git SHA 判斷版本，則 A6 尚未成立。

# 四、A7 關係管理 Relationship

## 4.1 問題定義

Relationship 要回答的是：

「兩個已具 Identity 的對象之間，存在什麼有語義的關係？」

核心不是建立一個「related_files」清單，而是讓關係具有類型與方向。

例如：

```text
Knowledge A --derived_from--> Source B
Scheme A --uses--> Knowledge B
System A --depends_on--> Capability B
Document A --supersedes--> Document B
Claim A --supported_by--> Evidence B
```

## 4.2 外部研究

W3C PROV-DM 將關係視為模型的一級概念，提供 wasDerivedFrom、wasGeneratedBy、wasAttributedTo、wasRevisionOf、specializationOf、alternateOf 等不同語義關係，而不是只使用單一 generic relation。 citeturn1search0turn1search1

PROV 的設計尤其重要的一點是：不同關係代表不同語義，而且部分關係還具有可推導的結構。例如 specializationOf 具有特定的偏序性質，並可推導 alternateOf。 citeturn1search2

因此本系統若只保存：

```text
related_to: [A, B, C]
```

長期會失去可判斷性。

## 4.3 對本系統的結論

結論：必要，正式能力候選；優先級非常高。

Relationship 是 A1 Identity、A2 Metadata、A3 Source、A4 Claim/Evidence、A6 Version 等能力真正形成可運作結構的核心連接層。

但目前不應直接跳到大型 Knowledge Graph / RDF Store。

第一階段只需要：

```text
subject_id
relation_type
object_id
optional: evidence / source / time / note
```

並對 relation_type 建立受控語義。

## 4.4 關係類型至少要區分

研究階段建議至少區分以下語義類別：

```text
derivation / 衍生
revision / 修訂
supports / 支持
depends_on / 依賴
uses / 使用
contains / 包含
part_of / 屬於
supersedes / 取代
implements / 實作
owned_by / 負責
related_to / 一般關聯
```

以上是候選集合，不是最終 frozen vocabulary。

特別注意：`related_to` 應是最後的低語義強度關係，而不能成為所有關係的垃圾桶。

## 4.5 Ownership 邊界

Owner 是一種 Relationship，但不能與一般「相關」混合。

例如：

```text
Capability A --owned_by--> Scheme 1
```

和：

```text
Capability A --related_to--> Scheme 2
```

語義完全不同。

Ownership 影響責任歸屬、變更決策與衝突處理，因此需要較高強度的受控語義。

## 4.6 最低驗收條件

至少建立五種不同關係：

```text
A --derived_from--> B
A --depends_on--> C
A --supports--> D
A --supersedes--> E
A --owned_by--> F
```

驗收必須能：

1. 從 A 查詢相關對象。
2. 知道關係類型。
3. 知道關係方向。
4. 不把不同語義關係混為一談。
5. 關係兩端都能透過 Identity 找到穩定對象。

# 五、A8 生命週期管理 Lifecycle

## 5.1 問題定義

Lifecycle 與 State 最大不同是：

State 問「現在在哪裡？」

Lifecycle 問「這個對象從產生到退出，整個生命過程如何被管理？」

因此 Lifecycle 是時間序列／階段模型；State 是該模型在某一時間點的目前狀態。

一個最小示意：

```text
Created
  ↓
Review
  ↓
Active
  ↓
Superseded
  ↓
Archived
```

但不能直接假定所有資料都必須走同一條線。

## 5.2 外部研究

ISO 15489-1:2016 強調 records 的 creation、capture、management，以及相關 metadata、責任與 controls，並明確指出這些管理活動跨越時間。這支持本系統必須考慮對象在時間中的管理，而不能只保存目前內容。 citeturn0search3

W3C PROV 則從 provenance 角度提供 generation、usage、invalidation、revision 等事件／關係，因此可以用來描述「某個 Entity 如何進入、被使用、被修訂或失效」。 citeturn1search0turn1search1

這些方法共同支持一個結論：Lifecycle 不應只是單一 `status` 值，而應能表示生命過程中的階段與轉移。

## 5.3 對本系統的結論

結論：必要，正式能力候選；但目前不宜建立複雜 BPM／Workflow Engine。

第一階段的 Lifecycle 應是「資料治理生命週期」，不是整個 Repository 的工作流引擎。

至少要能表達：

```text
created
→ reviewed
→ validated
→ active
→ superseded / deprecated
→ archived
```

並允許不同資料類型採用不同 lifecycle profile。

例如：

- 知識：draft → validated → active → superseded
- 方案：draft → reviewed → approved → active → retired
- 研究紀錄：created → processed → referenced → archived

這些只是示意，不應在本研究階段直接凍結成全域固定流程。

## 5.4 Lifecycle 與 State、Version、History 的邊界

```text
Identity
  = 我是誰

Version
  = 我是哪一版

State
  = 我現在處於什麼狀態

Lifecycle
  = 我從產生到退出經歷了什麼生命階段

History
  = 過去發生過哪些事件／變化
```

四者不能互相取代。

例如：

```text
Knowledge K
Identity = K
Version = 3
State = active
Lifecycle = created → review → validated → active
History = v1建立、v2修訂、v3驗證、目前啟用
```

## 5.5 最低驗收條件

至少實際演示一個對象完整經歷：

```text
Created
→ Review
→ Validated
→ Active
→ Superseded
→ Archived
```

並確認：

1. 當前 State 可直接查詢。
2. Lifecycle 可回顧。
3. Version 可獨立追蹤。
4. History 可保留事件。
5. Archived 對象不會因為仍存在 Repository 而被誤判成 Current / Active。

# 六、A5至A8 的責任邊界正式整理

目前研究得到最重要的結構不是四個獨立欄位，而是四個不同問題：

| 能力 | 核心問題 | 不應負責 |
|---|---|---|
| Identity | 這是不是同一個對象？ | 版本、目前狀態 |
| Version | 這個對象如何演化？ | 是否目前有效 |
| State | 現在處於什麼狀態？ | 完整歷史 |
| Lifecycle | 從建立到退出如何管理？ | 單一當前狀態 |
| Relationship | 與其他對象如何連接？ | 把所有語義塞成 related_to |

並與 A1至A4 合併後形成：

```text
Identity
   ↓
Metadata
   ↓
Source / Evidence / Claim
   ↓
State / Version / Lifecycle
   ↓
Relationship
   ↓
History / Traceability / Impact
```

此圖目前只是語義依賴示意，不代表最終資料架構。

# 七、研究後的重要否定結論

## 7.1 不建立「萬用 Status」

不能用一個 status 欄位同時表示驗證、啟用、生命週期與版本狀態。

## 7.2 不用 Git 取代 Version

Git 是底層版本／變更歷史工具；本系統仍需要自己的邏輯 Version 語義。

## 7.3 不用 Version 取代 Identity

v1、v2、v3 是同一邏輯對象的不同版本，不應被當成三個完全無關的 Identity。

## 7.4 不用 Lifecycle 取代 State

Lifecycle 描述歷程；State 描述目前判定。

## 7.5 不把 Relationship 降級為 related_to 清單

關係需要方向與語義，否則無法支撐依賴分析、責任歸屬、版本演化與影響分析。

## 7.6 不立即建立大型知識圖譜系統

W3C PROV 證明複雜關係可以形式化，但本系統第一階段不需要 RDF / OWL / Graph Database 才能成立。

先使用 Markdown + 明確 Identity + Typed Relationship 驗證語義，再決定是否需要更強的資料層。
