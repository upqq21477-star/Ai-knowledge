# AI知識庫基本運作系統 v1.0 最小實測

日期：2026-09-17

## 一、測試目的

驗證新建立的「AI知識庫基本運作系統 v1.0」是否真的能完成最小運作循環，而不是只有文件描述。

本輪只測最核心能力：

```text
狀態恢復
→ 工作守門
→ Expected / Actual 比較
→ 異常警報
→ 問題分析
→ 嚴重程度
→ 後續規劃／Gate／影響分析
→ 處理建議
→ 問題解決路由
→ 恢復後重新驗證
```

本測試採「狀態注入」方式，不修改施工狀態、不偽造 GitHub 實際完成結果。

## 二、測試基準

目前正式施工主線為：

```text
① 交接／工作狀態
② 新系統規格
③ 共同資料語義
④ 狀態／版本／關係
⑤ 現行格式唯一性
⑥ 三方案資料／責任接口
⑦ 跨系統長流程實測
⑧ 待辦工作記憶／統御能力實例驗證
⑨ 圖書館式知識管理 LOCKED
⑩ 知識書原子化規格 LOCKED
⑪ 實際驗證 LOCKED
```

目前測試假定：

- 實際施工位置：⑧。
- ⑨ 尚未解鎖。
- 目前主要工作是統御／問題解決能力驗證。

## 三、案例 A：正常工作

### 注入狀態

Expected State：目前仍在⑧，執行允許的統御能力驗證。

Actual State：⑧，測試結果符合預期。

### 預期

```text
無異常
繼續目前工作
```

### 實測判定

PASS。

系統不應為正常狀態製造問題。

## 四、案例 B：L1 一般異常

### 注入狀態

某項測試紀錄描述與預期格式略有差異，但不影響⑧的 Gate、不影響資料可信度，也不會造成後續返工。

### 系統應輸出

```text
【統御異常警報】
問題：測試紀錄格式與預期描述略有差異。

【問題分析】
目前差異屬描述層，不影響施工狀態與驗證結論。

【嚴重程度】
L1

【影響分析】
目前無關鍵 Gate、依賴或後續施工阻斷。

【建議】
記錄差異，可繼續目前工作。
```

### 實測判定

PASS。

重點：異常被看見，但沒有過度阻斷施工。

## 五、案例 C：L2 重要異常

### 注入狀態

⑧的驗證發現：統御輸出的異常警報缺少「後續施工影響」判斷。若直接進行下一項測試，後續驗證結果可能被污染，需要返工。

### 系統應判斷

```text
問題：異常回報缺少後續影響分析。

問題分析：
目前異常不一定破壞⑧本身，但會使後續驗證無法可靠判讀。

嚴重程度：
L2

後續影響：
後續案例可能建立在不完整的異常資訊上，造成驗證返工。

建議：
先修正受影響的驗證流程，再繼續後續案例。
必要時進入問題解決流程。
```

### 實測判定

PASS。

系統有能力將「問題本身不阻斷」與「問題會污染後續工作」區分開來。

## 六、案例 D：L3 阻斷異常

### 注入狀態

使用者要求直接開始⑨圖書館式知識管理，但目前②～⑧尚未全部通過 Gate。

### 系統應判斷

```text
【統御異常警報】
問題：嘗試進入尚未解鎖的⑨。

【問題分析】
⑨的前置條件尚未全部完成；目前工作與正式施工 Gate 衝突。

【嚴重程度】
L3

【影響分析】
若直接進入⑨，會破壞施工順序，並可能造成後續架構建立依賴未驗證能力，產生返工與狀態不可信。

【建議】
強烈建議先停止⑨相關工作。
回到⑧完成未通過的驗證；若缺口無法直接修正，進入問題解決流程。
```

### 實測判定

PASS。

這正是本次建立基本運作系統的核心需求：不能讓「使用者要求開始下一項」覆蓋正式施工 Gate。

## 七、案例 E：問題解決後恢復

### 注入狀態

假定案例 D 的問題已經完成處理，但不能直接假定施工已恢復正常。

### 系統應執行

```text
重新取得 Actual State
↓
重新檢查②～⑧完成條件
↓
重新檢查⑨ Gate
↓
重新檢查相關依賴
↓
判斷⑨是否真的解鎖
```

### 實測判定

PASS。

系統規格有明確要求「問題解決完成 ≠ 狀態自動恢復」，因此恢復後必須重新驗證。

## 八、案例 F：異常但不值得升級

### 注入狀態

工作紀錄中出現一個不影響結果的小型描述問題。

### 系統應判斷

```text
L0/L1
↓
留下記錄
↓
不進入完整問題解決
↓
繼續
```

### 實測判定

PASS。

目前 v1.0 沒有把所有異常強制送入問題解決流程，符合「小問題不應自動啟動大型研究」原則。

## 九、案例 G：問題需要調查，但使用者沒有主動要求

### 注入狀態

系統發現某結果與 Expected State 不一致，而且可能影響後續施工，但使用者沒有說「請處理問題」。

### 系統應判斷

不得靜默繼續。

至少應輸出：

```text
異常警報
問題分析
嚴重程度
後續影響
建議
是否建議進入問題解決流程
```

若 L2/L3，應明確告知使用者「建議先處理」，而不是等使用者自己發現。

### 實測判定

PASS（依系統規格推演驗證）。

此案例也是本輪最重要的行為要求。

## 十一、發現的系統缺口

本輪測試沒有證明「系統已成立」，反而確認三個下一輪必須實測的缺口：

### 缺口 1：目前只有規格級路由

目前可以描述「異常 → 問題解決」，但還沒有用真實問題完成完整閉環。

### 缺口 2：嚴重程度目前是規則模型，不是經實例校準的判定能力

L0～L3 已足以做第一輪，但需要真實案例確認不同問題不會被過度升級或降級。

### 缺口 3：尚未測試無歷史記憶 AI

下一輪應清空歷史對話，只給交接入口與正式資料，測試 AI 是否仍能：

```text
恢復狀態
→ 發現異常
→ 發出警報
→ 分析嚴重程度
→ 判斷後續影響
→ 路由問題解決
→ 恢復後重新驗證
```

## 十二、本輪結論

目前可以確認：

> 「AI知識庫基本運作系統 v1.0」已經具備可執行的最小運作模型，且能覆蓋本次提出的「異常不能無聲、必須分析嚴重程度與後續影響」需求。

但目前只能標記：

```text
【候選系統】
【最小案例規格測試 PASS】
【實際閉環尚未完成】
```

不得標記為「正式成立」。

## 十三、下一個最小實測

不擴張系統功能。

直接使用一個真實施工問題跑完整流程：

```text
真實問題
↓
異常警報
↓
問題分析
↓
嚴重程度
↓
後續影響
↓
處理建議
↓
問題解決系統
↓
候選解法
↓
最小實測
↓
結果
↓
恢復後重新檢查
```

如果此流程再次失敗，優先修正現有基本運作系統與問題解決系統的接口，不立即增加新的大型系統。
