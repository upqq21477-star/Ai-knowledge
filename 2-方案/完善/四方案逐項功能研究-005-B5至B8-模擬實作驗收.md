## 一、驗收方式

本輪「實作驗收」依目前工程規則，以模擬取代真實實作。

原因不是降低驗收標準，而是目前仍處於方案建立與研究階段；尚未進入長期真實工程運作。因此本文件只能證明：

> B5～B8 的責任、接口、判斷條件與既有能力處置，在代表性工程情境下可以形成可執行閉環。

不得將本文件解讀為 FIELD-PASSED 或長期實戰證明。

## 二、驗收目標

確認四項功能研究結果能否落到工程操作層：

1. B5 能否在存在資訊缺口時啟動外部研究，而不取代問題解決。
2. B6 能否把 Source、Claim、Evidence、Inference、Decision 分開處理。
3. B7 能否判斷「能不能用」，而不是把可信度直接等同適用性。
4. B8 能否選出任務所需的最小充分 Context，而不是無差別載入資料。
5. 四項能力能否與既有 B3、B4、B9 形成清楚接口。
6. 發現能力不足時，能否正確回到既有問題解決流程，而不是自行建立重複系統。

## 四、模擬案例

### M1：Repository 內資料不足，需要外部研究

任務：判斷是否存在成熟的方法可以改善目前的知識檢索問題。

預期：

```text
B3/B4
→ 發現內部資訊缺口
→ B5 外部研究
→ B6 判斷來源與證據
→ B7 判斷是否適用目前 Repository
→ B8 選擇必要 Context
→ B9 組裝
```

結果：PASS。

B5 沒有直接把外部方法宣布為採用方案；採用判斷仍回到問題解決流程。

### M2：找到權威來源，但來源沒有證明目前主張

情境：找到官方文件，但文件只描述某方法的存在，沒有證明它能解決本 Repository 的特定問題。

預期：B6 將 Source 與 Claim Support 分離。

結果：PASS。

不得產生：

```text
官方來源 → 所有內容皆為本系統已證明事實
```

### M3：外部研究結果可靠，但條件不同

情境：外部研究使用不同資料集、不同環境與不同任務。

預期：B7 判定為「可作研究參考，但不能直接視為本系統已驗證」，必要時進入最小實測。

結果：PASS。

### M4：資料很新，但與目前任務無關

情境：2026 年最新研究與目前任務條件不匹配。

預期：B7 不因新鮮度直接判定 Applicable。

結果：PASS。

### M5：小型任務只需要一份正式功能清單

任務：判斷某功能 ID 是否存在。

預期 Context：

- 當前正式功能清單。
- 必要的批次來源驗證規則。
- 若發生衝突，再取得相關研究／交接資料。

不得直接載入整個 Repository。

結果：PASS。

### M6：執行中發現 Context 缺口

情境：初始 Context 不足以判斷某個版本差異。

預期：B8 追加最必要資料，而不是重新載入全部歷史資料。

結果：PASS。

### M7：B5 發現「現有能力可能不足」

預期：

```text
B5 研究結果
→ 回傳證據與候選方法
→ 問題解決流程比較候選方案
→ 最小實測
→ 判斷既有能力是否足夠
```

B5 不自行建立新系統。

結果：PASS。

### M8：B6 與 B7 發生責任混淆

錯誤行為：看到高品質來源後直接輸出「適用」。

預期：阻斷，要求進入 B7。

結果：PASS。

### M9：B8 把全部搜尋結果塞進 Context

預期：判定不符合最小充分 Context；重新依任務必要性、證據作用、版本一致性、限制與訊號密度篩選。

結果：PASS。

### M10：B7 判定資料不適用，但任務仍需要外部資訊

預期：不是直接結束整個任務，而是保留不適用原因，回到 B5 尋找符合條件的新資料。

結果：PASS。
