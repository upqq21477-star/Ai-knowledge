# 候選系統能力既有能力重疊比對 v1.0

版本：v1.0  
狀態：【創建中；第一輪既有能力比對完成；尚未建立新正式系統】  
日期：2026-09-17

## 一、目的

本文件承接「功能 → 系統能力」階段，專門回答：

> 候選能力是否已經由 Repository 現有系統、知識或流程承擔？

原則：先吸收、擴充、融合既有能力；只有證明既有能力無法合理承擔，才建立新系統。

## 二、第一批候選能力判定

### 1. 共同對象識別與關係查詢

候選來源：方案一、二、三、四。

Repository 已存在相關能力：

- `0-知識/管理/資料身份與唯一識別原則.md`
- `0-知識/管理/共同關係模型最小原則.md`
- 舊 `系統管理統御分支` 已包含 System Registry、System ID、方案關係等能力。
- `紀錄/舊模式重疊能力重製映射-v1.0.md` 已將舊 System Registry 對應至「薄型 System Catalog / System Identity」。

外部比較：Backstage 將 System 作為多個 Components、Resources 等合作實體的較高層抽象，並以 directed Relations 表達 ownership、dependency、part-of 等關係。它也將 catalog 作為可搜尋／可發現的目錄，而不是讓目錄承擔所有業務邏輯。citeturn0search0turn0search1turn1search9

判定：

```text
不建立新的「共同身份系統」
↓
保留共同 Identity / Relationship 知識
↓
後續由既有 System Catalog／資料治理能力吸收
↓
以實際案例驗證是否真的需要獨立系統能力
```

目前狀態：`既有能力可承接；不新增正式系統`。

### 2. 變更影響與遷移分析

候選來源：方案三、方案四。

Repository 已存在相關能力：

- `0-知識/管理/變更影響分析最小原則.md`
- `0-知識/管理/相容性與遷移最小原則.md`
- 方案三已有 Change / Impact / Version / Compatibility / Migration / Validation 功能拆解。
- 方案四已有影響分析與遷移條件分析。
- 舊模式映射已將「更新監控 → 影響分析」與相關變更能力重新定位。

因此目前尚未證明需要一個獨立「影響分析系統」。

判定：

```text
共同知識語義：保留
方案三：負責正常變更案件
方案四：負責長期蒸餾／重構案件
共同分析能力：可共享
執行責任：保持方案分離
```

目前狀態：`既有知識＋方案責任足以繼續研究；不新增正式系統`。

### 3. 驗證狀態與實測證據管理

候選來源：四方案。

Repository 已存在：

- `1-系統/後續工作觸發式順便驗證系統-v2.0.md`
- `1-系統/實測結果回寫檢查小系統-v1.0.md`
- `0-知識/運作/後續工作觸發式順便驗證原則.md`
- `0-知識/運作/實測結果回寫最小原則.md`
- 既有 AI 知識管理系統已有結果驗證與失敗回饋責任。

舊模式映射已將上述能力指向共同 Validation Model / Empirical Evidence，而不是維持多個彼此孤立的驗證系統。

判定：

```text
保留既有驗證能力
↓

↓
避免新增第三個「驗證系統」
```

目前狀態：`既有能力可承接；不新增正式系統`。

## 四、外部搜尋研究對方案二的補充

外部成熟搜尋系統通常不是只有單一「搜尋」能力。

OpenSearch 官方文件區分 lexical / keyword search、semantic search 與 hybrid search；Hybrid Search 可將關鍵字與語義搜尋結果組合，並透過 ranking / normalization 等方式改善相關性。citeturn1search0turn1search1turn1search16

Backstage Search 則採 plugin / collator / search engine 分層，搜尋來源可以由不同內容提供者組合，而不是把所有資料直接塞入單一搜尋邏輯。citeturn1search2turn1search14

因此方案二後續真正需要研究的是：

```text
任務理解
↓
搜尋需求形成
↓
Repository 精確搜尋
↓
語義／探索搜尋
↓
外部研究
↓
結果排序／篩選
↓
相關性判斷
↓
最小充分 Context
```

而不是簡單建立一個「搜尋系統」。

## 六、重要結論

目前 Repository 的主要問題不是「系統太少」，而是「已有能力尚未完成責任整合與實際驗證」。

因此四方案創建階段目前不應快速增加 `1-系統/` 文件數量。

下一階段應優先：

1. 將方案二功能逐項映射到 `AI知識管理系統 v2.0` 與 `AI上下文與交接系統`。
2. 將方案三／四的變更、影響、相容性、遷移能力組成一個真實案例。
3. 將共同 Identity / Relationship 能力放入真實跨方案案例驗證。
4. 由實際案例判斷是否存在「既有能力無法承擔」的真正缺口。
5. 只有真正出現缺口，才進入新系統建立 Gate。

這符合既有施工原則：功能先形成能力需求，再與既有系統比對，而不是功能一增加就建立新系統。fileciteturn565file0L6-L10
