# 四方案功能拆解第一版 v1.0

版本：v1.0  
狀態：【創建中；第一輪功能盤點完成；待逐項知識研究】  
日期：2026-09-17

## 一、使用方式

本文件不是四方案的最終系統設計，而是創建階段的「功能候選清單」。

功能只有在完成：

```text
必要性確認
↓
責任歸屬確認
↓
既有能力盤點
↓
知識需求分析
↓
外部研究／比較
```

後，才可以進入正式系統設計。

## 二、功能分類標記

```text
[K] 主要需要知識即可支撐
[S] 可能需要系統化能力
[C] 跨方案共同能力，優先避免重複建立
[W] 工作流程能力，未必需要獨立系統
[V] 驗收／驗證能力
```

標記只是第一輪假設，不是最終分類。

# 方案一：整體資料治理

## A1 資料身份／識別 [C][S]

回答：這個資料／知識／能力到底是哪一個對象？

需要研究：Identity、canonical identity、stable identifier、alias、path 與 identity 的區別。

## A2 Metadata 描述 [C][S]

回答：最少需要哪些描述才能讓其他系統理解與使用？

需要研究：metadata schema、catalog model、required vs optional metadata。

## A3 來源管理 [C][S]

回答：資料從哪裡來？

區分 Source 與 Evidence。

## A4 Claim／Evidence 關聯 [C][S]

回答：某項主張由哪些證據支撐？證據本身是否只是來源？

需要研究 provenance、traceability、evidence lineage。

## A5 狀態管理 [C][S]

回答：目前這筆資料處於什麼有效狀態？

必須與版本分離。

## A6 版本管理 [C][S]

回答：這個內容如何由前一版本演化到目前版本？

必須與 Git commit、檔名分離。

## A7 關係管理 [C][S]

回答：資料、知識、系統、方案之間如何表達關係？

需要研究 relation model、dependency graph、ownership。

## A8 生命週期管理 [C][S]

回答：新增、使用、修正、取代、退役、歷史保存如何表達？

## A9 歷史保存 [C][W]

回答：退出目前工作結構的資料如何保存而不重新成為目前資料？

## A10 引用／追溯 [C][S]

回答：AI 或系統使用某資料後，能否追溯使用來源與版本？

## A11 變更影響 [C][S]

回答：某項資料變更後，哪些關係／使用者／系統可能受影響？

## A12 跨方案共同語義 [C][S]

回答：四方案共用哪些概念？哪些應保持方案內部自由？

### 方案一核心輸出

# 方案二：AI知識管理

## B1 任務理解 [S][W]

把自然語言需求轉成問題、條件、目標、限制與輸出要求。

## B2 任務拆解 [S][W]

將複合任務拆成可研究、可執行、可驗證的子問題。

## B3 知識搜尋 [S]

從 Repository 找到可能相關的知識。

## B4 資料探索 [S]

當精確搜尋不足時，探索相關內容與鄰近概念。

## B5 外部研究 [S]

在 Repository 不足時，搜尋外部方法、工具、案例與證據。

## B6 來源／證據判斷 [K][S]

區分來源、證據、主張、觀察與推論。

## B7 適用性判斷 [K][S]

確認資料的時間、條件、範圍、版本與使用情境是否符合目前任務。

## B8 最小充分上下文選擇 [S]

避免把整個 Repository 無差別塞進 AI Context。

## B9 上下文組裝 [S]

依任務將多份知識、目前狀態、必要歷史與外部證據組合成可工作的上下文。

## B10 記憶／目前狀態辨識 [C][S]

區分長期記憶、目前狀態、知識、歷史資料。

## B11 任務執行 [W]

利用取得的知識與系統能力完成工作。

## B12 結果驗證 [V][S]

確認輸出是否符合需求、證據與條件。

## B13 不確定性保存 [C][K]

不能把未確認內容偽裝成確定知識。

## B14 結果保存 [C][S]

保存結果、依據、使用資料、未解決問題與可重用成果。

## B15 知識回饋 [C][W]

將實際使用中發現的問題轉為後續演化訊號，而非直接改成知識。

## B16 失敗診斷 [S]

區分資料不足、搜尋失敗、上下文錯誤、證據不足、系統不足等不同原因。

### 方案二核心輸出

```text
任務理解結果
搜尋／研究結果
使用資料與證據
最小充分上下文
任務結果
驗證結果
不確定性
記憶／目前狀態
演化訊號
```

# 方案三：知識與資料迭代演化

## C1 變更訊號接收 [S][W]

接收新需求、新證據、失敗、過期、條件變更、外部方法更新等訊號。

## C2 變更確認 [S]

判斷訊號是否真的代表需要改變。

## C3 變更對象識別 [C][S]

找出資料、知識、能力、系統或方案中的真正變更對象。

## C4 變更目標確認 [W]

回答這次到底要改善什麼。

## C5 既有能力盤點 [C][S]

先確認是否已有能力可處理，不因需求出現就新增系統。

## C6 影響分析 [C][S]

分析直接使用者、依賴、下游、引用、版本、歷史與驗證案例。

## C7 演化必要性判定 [K][S]

判斷應不應該改，而不是收到訊號就改。

## C8 候選變更產生 [S]

產生 Add、Correct、Extend、Partial Replace、Replace、Merge、Split、Migrate 等候選方案。

## C9 版本分析 [C][S]

分析前後版本與語義演化。

## C10 相容性分析 [S]

確認舊使用方式與新版本能否共存或需要遷移。

## C11 遷移分析 [S]

需要由舊結構轉向新結構時，定義遷移條件與風險。

## C12 最小變更執行 [W]

以最小必要變更解決問題。

## C13 實際驗證 [V][C]

區分設計、模擬與實際執行結果。

## C14 採用／暫緩／退回 [W]

依驗收結果決定變更狀態。

## C15 目前狀態更新 [C][S]

將成功變更形成新的目前狀態。

## C16 歷史保存 [C][W]

保存變更原因、依據、舊版本與結果。

## C17 蒸餾轉交 [W]

發現問題已超出單次變更範圍時，建立蒸餾候選並轉交方案四。

## C18 結果回饋 [W]

把使用與驗證結果回饋至知識與後續演化。

### 方案三核心輸出

```text
變更案件
影響範圍
候選變更
版本／相容性／遷移條件
實際驗證結果
新目前狀態
歷史記錄
蒸餾候選
```

# 方案四：能力蒸餾與系統重構

## D1 蒸餾案件建立 [S][W]

建立一次長期整理工作的明確範圍與目標。

## D2 範圍界定 [S]

限制蒸餾對象，避免每次蒸餾都掃描整個 Repository。

## D3 能力盤點 [S]

確認實際存在的資料、知識、能力、系統、方案與關係。

## D4 實際使用／依賴確認 [S]

區分文件宣稱與實際使用。

## D5 證據／驗證狀態確認 [C][S]

判斷哪些能力有實際證據、哪些只有設計文件。

## D6 能力語義分析 [K][S]

理解每個能力真正解決什麼問題。

## D7 重疊分析 [S]

比較目的、輸入、輸出、觸發、責任、資料、狀態、依賴、使用與驗證。

## D8 責任邊界分析 [C][S]

確認能力到底應由誰負責。

## D9 關係／依賴分析 [C][S]

找出隱藏耦合與下游影響。

## D10 長期成本／風險分析 [S]

分析理解成本、維護成本、同步成本、錯誤風險、AI Context 成本與依賴成本。

## D11 候選處置產生 [S]

產生 Keep、Extend、Refactor、Merge、Split、Replace、Rebuild、Retain、Retire、Archive 等候選。

## D12 處置比較 [S]

比較候選處置的收益、成本、風險與可逆性。

## D13 影響分析 [C][S]

確認重構會影響哪些系統、資料、方案與實際工作。

## D14 遷移條件分析 [S]

定義新舊能力如何安全共存、替換或退出。

## D15 重構執行 [W][S]

執行已確認的最小重構，不由蒸餾分析器自行無條件刪除內容。

## D16 重構後驗證 [V][C]

確認重構後功能、資料、依賴與工作結果是否仍正確。

## D17 新基準建立 [C][W]

將驗證通過的新結構交回正常演化基準。

## D18 歷史／舊能力保存 [C][W]

退出目前工作結構但保留歷史追溯資料。

## D19 蒸餾結果回寫 [C][W]

保存本次蒸餾的判斷、實際變更、驗證與未解決問題。

## D20 再次蒸餾觸發 [W]

當累積問題再次達到蒸餾條件時建立下一案件。

### 方案四核心輸出

```text
蒸餾案件
能力盤點
重疊／責任／依賴分析
候選處置
影響與遷移條件
重構結果
驗證結果
新基準
歷史保存
蒸餾回寫
```

# 三、第一輪跨方案重疊觀察

目前已可確認幾個不能各自重建的共同能力候選：

| 共同能力 | 主要責任 | 主要方案 | 初步處理 |
|---|---|---|---|
| Identity | 對象身份 | 方案一 | 共同資料治理 |
| Metadata | 最小描述 | 方案一 | 共同資料治理 |
| Source / Evidence / Claim | 來源與證據關係 | 方案一＋二 | 方案一定義共同語義，方案二使用 |
| State | 目前狀態 | 方案一 | 共同資料治理 |
| Version | 演化版本 | 方案一＋三 | 方案一共同語義，方案三使用 |
| Relationship | 關係／依賴 | 方案一＋三＋四 | 共同語義，實際分析分責任 |
| Validation | 驗證 | 四方案都需要 | 共同驗證語義，方案內執行 |
| History | 歷史保存 | 方案一＋三＋四 | 共同資料語義，方案內產生 |
| Impact | 影響分析 | 方案一＋三＋四 | 共享資料基礎，不共享全部決策邏輯 |
| Search | 搜尋 | 方案二為主 | 不在其他方案各建搜尋系統 |

## 四、目前暫不建立的能力

以下概念目前不直接升格為系統：

```text
大型知識圖譜
大型向量資料庫
全 Repository 自動掃描器
自動真偽裁決器
自動融合器
自動刪除器
全自動架構重構器
萬能 Agent
```

原因不是它們永遠沒有價值，而是目前尚未證明其必要性、成本合理性與最小實作方式。

## 五、下一輪工作

下一步不是建立系統，而是對以上功能逐項建立：

```text
功能
↓
知識需求
↓
外部方法／工具／產品／案例
↓
比較結果
↓
採用／拒絕／待驗證
↓
正式知識
```

優先順序：

1. 方案一：Identity / Metadata / State / Version / Relationship / Source / Evidence。
2. 方案二：Search / Research / Context / Evidence / Validation。
3. 方案三：Change / Impact / Version / Compatibility / Migration / Validation。
4. 方案四：Capability Inventory / Overlap / Responsibility / Refactoring / Migration / Validation。

完成上述知識後，才進入系統能力組建。
