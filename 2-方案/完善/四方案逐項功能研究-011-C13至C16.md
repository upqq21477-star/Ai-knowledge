## 二、C13 實際驗證

C13 負責確認「已執行的變更，在實際目標環境與實際工作條件下，是否達成 C4 定義的目標」。

核心區分：

```text
C9-C11 = 分析
C12 = 執行
C13 = 驗證實際結果
```

不能因 C12 執行成功、文件看起來正確或模擬通過，就直接宣告變更成功。

最小驗證輸入：

- Change Objective
- Success Criteria
- Affected Objects
- Applied Change / Version
- 實際環境與條件
- 實際結果
- 驗證證據
- 已知偏差與限制
- Regression / 既有能力檢查結果

輸出至少：

```text
PASS
PARTIAL
FAIL
UNKNOWN
```

其中 UNKNOWN 不得被自動轉成 PASS。

NASA 的配置管理流程將變更控制與 configuration verification 分開，要求對實施後結果與配置一致性進行確認；NIST 的軟體驗證資料也將 testing、verification、validation 視為需要明確管理的活動。citeturn0search0turn0search3

## 三、C14 採用／暫緩／退回

C14 負責根據 C13 結果與既定決策條件，決定這次變更在工程流程中的處置狀態。

不是「哪個方案最好」的評分器，而是狀態決策節點。

基本輸出：

```text
ADOPT
DEFER
RETURN
```

可附帶：

- 決策依據
- 驗證結果
- 未解決問題
- 需要補充的證據
- 下一步條件
- 責任者／責任層

典型規則：

```text
PASS + 條件滿足 → ADOPT
PARTIAL + 尚有可接受未完成項 → DEFER 或條件式 ADOPT
FAIL → RETURN
UNKNOWN → DEFER / RETURN，不得直接 ADOPT
```

C14 不應自行修改資料或系統，也不應取代 C13 的驗證職責。

NASA 的變更管理同樣將「提出、評估、批准、實施、驗證」視為不同責任階段。citeturn0search0turn0search10

## 四、C15 目前狀態更新

C15 負責在 C14 形成可採用結果後，將正式工作結構中的目前狀態更新為新的有效狀態。

核心原則：

```text
驗證結果 ≠ 目前狀態
目前狀態更新必須有決策依據
```

C15 必須保留：

- Stable Identity
- New State
- Version
- Effective Time
- Previous State / Version
- Change Case
- C13 Evidence
- C14 Decision
- Traceability

不能只改檔案內容而沒有狀態轉移紀錄。

也不能把 DEFER、FAIL、UNKNOWN 的結果偽裝成新的 Current State。

這與 NIST／NASA 配置管理對 configuration status accounting、版本、基線與歷史狀態追蹤的要求一致。citeturn0search1turn0search0

## 五、C16 歷史保存

C16 負責保存本次演化的完整歷史，使未來能回答：

```text
為什麼改？
改了什麼？
原本是什麼？
依據是什麼？
誰／什麼流程決定？
實際結果如何？
為什麼採用／暫緩／退回？
```

至少保存：

- Change Case
- 原始狀態與版本
- 變更候選
- 實際執行內容
- 驗證結果
- 決策結果
- 新狀態與版本
- 證據與限制
- 時間
- 關係與影響

歷史資料退出 Current 工作結構後，仍須能透過 Identity、Version、Relationship、Traceability 找回，但不能因此重新被當成目前資料。

NASA 將 configuration status accounting 與 historical configuration documentation、change disposition、traceability 視為配置管理的重要輸出。citeturn0search0turn0search10

## 六、四項責任邊界

| 功能 | 負責 | 不負責 |
|---|---|---|
| C13 | 驗證實際結果 | 決定是否採用 |
| C14 | 決定採用／暫緩／退回 | 執行修改、重新驗證 |
| C15 | 更新目前有效狀態 | 保存全部歷史細節本身 |
| C16 | 保存演化歷史與追溯 | 把歷史重新變成目前狀態 |

## 七、跨方案接口

```text
C12
 ↓
C13 實際驗證
 ↓
C14 採用／暫緩／退回
 ├─ ADOPT → C15 → C16
 ├─ DEFER → C16 → 後續條件追蹤
 └─ RETURN → C16 → 問題解決／重新進入候選流程
```

C13 的實際驗證結果也可回饋方案二 B12；但兩者責任不同：B12 驗證單次任務結果，C13 驗證演化變更的實際效果。

C14 若發現問題超出單次變更能力，不自行擴張範圍，而應回到問題解決或方案四蒸餾流程。

## 八、研究結論

C13～C16 是方案三後段的必要責任，且與前段 C9～C12 形成完整閉環：

```text
候選
→ 版本／相容性／遷移分析
→ 最小執行
→ 實際驗證
→ 採用／暫緩／退回
→ 更新目前狀態
→ 保存歷史
```

不需要新增大型獨立系統。應沿用方案一的 Identity、Version、State、Relationship、History、Traceability，以及既有驗證／問題解決能力。
