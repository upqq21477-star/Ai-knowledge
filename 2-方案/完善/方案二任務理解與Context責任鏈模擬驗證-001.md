## 四、模擬執行

### Step 1：任務理解

識別主要任務不是「建立新系統」，而是「繼續完善既有方案」。

條件：

- 需要讀取 Repository 現況。
- 需要確認既有能力。
- 需要避免重複建立。
- 若發現缺口，才判斷是否需要新能力。
- 正式修改必須符合目前施工階段。

判定：PASS。

### Step 2：任務拆解

拆為：

1. 讀取方案二目前狀態。
2. 找出目前施工位置。
3. 盤點 B2、B7、B8、B9、B10、B11、B12、B15、B16 相關能力。
4. 比對外部成熟方法。
5. 找責任鏈缺口。
6. 不因候選功能存在就直接建立系統。
7. 對缺口做模擬驗證。
8. 記錄結果與下一步。

判定：PASS。

### Step 3：資料取得

使用 Repository 既有：

- AI知識管理系統 v2.0。
- AI知識管理方案 v2.1 完善草案。
- 四方案功能拆解第一版。
- 目前完成度分層原則。
- 既有 Identity / Relationship / Change / Migration 等共同能力。

判定：PASS。

### Step 4：適用性判斷

每份資料分別確認：

```text
身份：方案／系統／知識／施工草案
狀態：目前／歷史／候選／建立中
版本：目前可用版本
適用範圍：本次方案二施工
```

例如：

`AI知識管理系統-v2.0.md` 是建立中、不啟動的系統文件，因此可以作為架構參考，但不能被當成「已運作系統」。

`AI知識管理方案-v2.1完善草案.md` 是完善草案，因此可以作為候選設計依據，但不能直接當成正式方案已完成。

判定：PASS。

### Step 5：最小充分 Context

模擬比較兩種 Context：

#### A：整個 Repository 全部載入

問題：

- 包含大量歷史資料。
- 混入已推翻／舊版本／事故文件。
- 增加判斷成本。
- 容易把歷史狀態誤認目前狀態。

判定：不採用。

#### B：任務相關最小集合

```text
目前方案二狀態
+
方案二功能拆解
+
目前完成度規則
+
目前正在施工的變更／Context 能力文件
+
必要的相關治理／演化接口
```

判定：採用。

### Step 6：記憶／目前狀態辨識

模擬明確區分：

```text
長期記憶
→ 過去已確認的穩定原則

目前狀態
→ 現在方案二施工到哪裡

歷史資料
→ 舊方案／舊版本／事故記錄

本次 Context
→ 為目前任務臨時組裝的工作資料
```

因此「過去曾建立某系統」不能直接推論「目前該系統已驗證」。

判定：PASS。

### Step 7：任務執行

執行順序：

```text
既有能力盤點
→ 外部比較
→ 接口分析
→ 模擬案例
→ 判斷是否有真正缺口
```

本次沒有因 B2/B7/B8/B9/B10/B15/B16 的功能名稱而建立新系統。

判定：PASS。

### Step 8：結果驗證

- 是否把模擬當實戰？否。
- 是否錯誤建立新系統？否。
- 是否保留未驗證狀態？是。
- 是否留下可追溯案例？是。

判定：PASS。

## 五、失敗注入測試

### Failure F1：把舊文件當目前狀態

若 AI 直接看到「已有系統」就判定完成，應被 B7／B10／B12 阻止。

結果：目前模型可辨識此錯誤。

### Failure F2：Context 過量

若直接載入全部歷史文件，可能混淆舊版與現版。

結果：最小充分 Context 原則可識別風險；尚未有實際長 Context 運行數據。

### Failure F3：搜尋命中就直接採用

若搜尋找到相似名稱但文件狀態為歷史／候選，不能直接採用。

結果：B7 適用性判斷可提供阻斷點。

### Failure F4：執行失敗後全部重做

若實際失敗只是「狀態辨識錯誤」，不應重新執行完整搜尋。

應進入：

```text
失敗診斷
→ 判斷責任層
→ 只修正失敗層
```

結果：責任鏈成立，但尚缺實際失敗軌跡驗證。
