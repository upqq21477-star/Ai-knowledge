# 後續工作觸發式順便驗證－外部方法比對記錄 v1.0

狀態：**【研究完成；候選小系統已建立；待實際案例驗證】**

## 1. 研究目的

確認「先做標記，未來正常工作自然遇到時順便完成驗證」是否有成熟方法可對照，以及哪些原則值得納入本專案的小系統。

## 2. 研究問題

1. 成熟系統如何處理持續監控與後續驗證？
2. 驗證是否需要留下可追溯結果？
3. 能否把驗證放入正常生命週期，而不是每次獨立建立測試任務？
4. 本專案哪些部分需要保留為自己的特殊限制？

## 3. 外部資料

### NIST AI Risk Management Framework

NIST AI RMF 將 Govern、Map、Measure、Manage 作為 AI 風險管理核心，要求風險管理持續、及時並貫穿 AI 系統生命週期；Measure 包含測試、評估、驗證與確認（TEVV），Manage 則包含回應、恢復、溝通與持續改善。citeturn0search4

### NIST Risk Management Framework

NIST RMF 的 Monitor step 要求持續監測系統與環境、分析監控輸出並採取回應，讓監控結果成為後續管理決策的依據。citeturn0search7turn0search5

### ISO/IEC 42001

ISO/IEC 42001 是 AI 管理系統標準，要求 AI 管理系統被建立、實施、維護並持續改進；ISO 對該標準的說明亦將其描述為持續改善的管理循環。citeturn0search0turn0search3

## 4. 比較

| 外部做法 | 可採用內容 | 本專案是否直接採用 |
|---|---|---|
| NIST AI RMF 持續風險管理 | 驗證／監控不應只做一次 | 採用原則 |
| NIST TEVV | 測試結果需要可追溯記錄 | 採用 |
| NIST Monitor | 監控輸出需要分析並回應 | 採用 |
| ISO/IEC 42001 持續改善 | 驗證結果應回饋後續運作 | 採用原則 |
| 大型管理框架的完整治理結構 | 角色、政策、控制等完整制度 | 不採用，超出小系統必要規模 |
| 專門排程測試 | 預先安排固定測試週期 | 不作為本小系統核心 |

## 5. 本專案新增的最小化限制

外部框架提供的是生命週期管理與持續驗證思想，但沒有直接回答本專案的「順便驗證」場景。因此增加以下專案規則：

1. 待驗證項目先建立標記。
2. 後續正常工作開始時分析待辦與標記。
3. 只有自然符合條件才觸發。
4. 不為了驗證而製造工作。
5. 使用不等於 PASS。
6. 必須比較 Expected / Actual。
7. 驗證失敗轉入既有問題解決流程。
8. 驗證完成後更新標記，而不是永久保留為待辦。

## 6. 結論

「順便驗證」不是隨意的便利功能，而是把持續驗證嵌入正常施工生命週期的最小化實作。

其必要能力可壓縮為：

```text
標記
→ 後續工作讀取
→ 自然觸發判斷
→ 同步驗證
→ Expected / Actual
→ 記錄
→ 判定
→ 後續處理
```

目前證據足以支持建立候選小系統，但不能直接證明系統已經成立。仍需透過一次真實後續工作完成閉環實測。
