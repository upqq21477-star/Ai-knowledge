# 知識迭代與能力蒸餾方案重製規劃 v1.0

版本：v1.0
狀態：【建立中；本文件作為本輪兩方案重製的共同規劃與交接入口；尚未完成實際驗證】
建立日期：2026-09-17

## 一、文件目的

本文件是本輪「知識迭代與資料演化」重製，以及新增「能力蒸餾與系統重構」方案的共同規劃文件。

本輪不是單純替舊文件改名或增加功能，而是重新整理長期演化、資料變更、能力累積、重疊、重構與淘汰之間的責任邊界。

本文件的任務是讓後續 AI 在沒有歷史對話的情況下，也能理解：

1. 為什麼原本一個方案需要拆成兩個互相配合的方案。
2. 兩個方案各自解決什麼問題。
3. 哪些能力應共享、哪些能力不能重複建立。
4. 舊文件如何保留歷史，而新方案如何成為後續工作基準。
5. 方案建立後如何與整體資料治理、AI 知識管理、問題解決、實測回寫及統御相關能力協作。
6. 為什麼本輪先建立方案架構，不立即建立大量新系統。
7. 後續如何以實際案例驗證方案，再決定是否需要新增或重製系統。

---

## 二、本輪重製背景

原有 `知識迭代與資料演化方案-v1.0` 已經建立正常演化流程，包含變更訊號、影響分析、演化判定、版本、融合、拆分、驗證與歷史保存等內容。

但長期討論後確認，正常演化與長期蒸餾／重構雖然互相關聯，卻不是同一種工作。

正常迭代主要回答：

> 現在出現新需求、新證據或使用回饋，要如何安全地改變目前能力？

蒸餾與重構主要回答：

> 長期累積後，現在這一整套資料、知識、能力、系統與方案是否已經出現重複、責任膨脹、結構侵蝕或無效遺留？哪些應保留、融合、拆分、重構、取代、重建或淘汰？

若兩者全部塞進同一方案，容易形成新的巨型方案，並把「正常變更」與「週期性整理」混成同一責任。

因此本輪採用兩方案配套架構：

```text
知識與資料迭代演化方案
= 正常向前演化

能力蒸餾與系統重構方案
= 長期累積後重新整理
```

兩者不是平行孤立系統，而是循環關係：

```text
正常迭代
↓
長期累積
↓
複雜度／重複／技術債／結構侵蝕
↓
蒸餾與重構
↓
重新建立穩定基準
↓
回到正常迭代
```

## 三、外部方法比對結論

本輪已重新參考成熟的軟體現代化與系統治理方法。

### 1. Microsoft 6R

Microsoft 將現代化選項區分為 Rehost、Replatform、Refactor、Rebuild、Retire、Retain，並指出選擇應依複雜度、時間、成本、效能、擴展性、整合需求、依賴與風險等因素判斷，而不是把所有舊系統都直接重建。此分類可作為本方案「候選處置類型」的外部參考，但不直接複製成 Ai-knowledge 的規則。

### 2. AWS 7R 與 Portfolio Rationalization

AWS 的 portfolio discovery 先盤點目前環境、依賴、生命週期與複雜度，再以 Rehost、Replatform、Refactor/Re-architect、Repurchase、Relocate、Retire、Retain 等類型進行 rationalization，並以迭代方式逐步成熟，而不是一次完成全部判定。

本專案可採用的核心思想是：

```text
先理解目前狀態
→ 確認依賴與影響
→ 判斷處置
→ 執行
→ 驗證
→ 再評估
```

而不是先建立一張固定的大型分類表。

### 3. Backstage 類 Software Catalog

成熟的軟體目錄模式通常將「身份、類型、Owner、Lifecycle、依賴、關係」集中成可搜尋的目錄資料，而不把所有執行邏輯都塞進中央目錄。

本專案因此維持：

```text
共同身份／目錄／關係
≠
所有業務執行邏輯
```

### 4. 外部方法的採用限制

外部方法只提供候選模式，不直接成為本專案規則。

採用順序：

```text
外部方法
↓
理解原本解決的問題
↓
與 Repository 現有能力比較
↓
確認重疊／缺口
↓
形成候選能力
↓
實際案例驗證
↓
才可正式納入
```

## 四、正式方案架構

本輪之後，正式方案架構規劃為四個方案：

```text
1. 整體資料治理方案
2. AI 知識管理方案
3. 知識與資料迭代演化方案
4. 能力蒸餾與系統重構方案
```

其中第 3、4 方案形成長期循環。

### 方案 1：整體資料治理方案

負責共同資料語義、共同規則、狀態、版本、關係、生命週期與追溯等橫向能力。

### 方案 2：AI 知識管理方案

負責 AI 工作過程中的資料取得、理解、搜尋、上下文、使用、驗證與結果保存。

### 方案 3：知識與資料迭代演化方案

負責正常變更、版本演化、影響分析、相容性、遷移、驗證與歷史保存。

### 方案 4：能力蒸餾與系統重構方案

負責長期累積後的能力盤點、重疊分析、責任整理、融合、拆分、重構、取代、重建、保留與淘汰，以及必要時的規模重組。

---

## 五、方案 3：知識與資料迭代演化方案

### 5.1 核心目的

讓知識、資料、能力與相關系統可以在新證據、新需求與實際使用回饋下持續演化，同時保持可追溯、可驗證、可回復與可理解。

### 5.2 主要問題

```text
新需求出現
新證據出現
使用失敗
資料過期
版本不適用
條件改變
外部方法更新
↓
是否真的需要改變？
↓
影響什麼？
↓
怎麼改？
↓
如何驗證？
```

### 5.3 核心流程

```text
變更訊號
↓
確認訊號真實性
↓
確認變更目標
↓
盤點受影響資料／能力／系統／方案
↓
影響分析
↓
判斷演化必要性
↓
選擇演化方式
↓
建立候選變更
↓
相容性／遷移分析
↓
最小實際驗證
↓
採用／暫緩／退回
↓
更新目前狀態
↓
保存歷史與變更依據
```

### 5.4 演化處置類型

暫定保留：

- 新增 Add
- 修正 Correct
- 補充 Extend
- 部分取代 Partial Replace
- 完全取代 Replace
- 融合 Merge
- 拆分 Split
- 遷移 Migrate

其中 Merge、Split 不等於蒸餾專屬。正常演化也可能需要它們。

### 5.5 方案 3 的邊界

方案 3 不負責：

- 自己判斷整個 Repository 是否需要大規模重構。
- 自己刪除長期無效能力。
- 自己決定所有系統的生命週期。
- 自己成為中央治理平台。
- 未驗證就建立大型自動演化引擎。

當問題從「這次怎麼改」變成「整體累積是否已經需要重新整理」，轉交方案 4。

## 六、方案 4：能力蒸餾與系統重構方案

### 6.1 核心目的

防止長期迭代形成：

```text
Feature Stacking
Duplicate Logic
Dead / Legacy Capability
Architecture Erosion
Dependency Explosion
Hidden Coupling
Schema Drift
Semantic Drift
Documentation Drift
Test Drift
Compatibility Layer 累積
AI-generated Technical Debt
```

方案 4 的目標不是讓文件「看起來漂亮」，而是降低長期使用成本、理解成本、錯誤率、維護成本、同步成本與重複工作。

### 6.2 核心問題

```text
現在到底有什麼？
↓
哪些真的在用？
↓
哪些有價值？
↓
哪些其實重複？
↓
哪些責任重疊？
↓
哪些依賴造成風險？
↓
哪些已經失效？
↓
應該怎麼處置？
↓
處置後是否真的改善？
```

### 6.3 四個內部能力模組

#### A. 能力盤點與理解

確認實際存在的資料、知識、能力、系統、方案、依賴、使用情況、驗證情況與生命週期。

不以檔名、目錄名稱或 AI 猜測作為能力存在的唯一證據。

#### B. 重疊與演化判定

至少區分：

- 完全重複
- 高度重疊
- 部分重疊
- 互補
- 同名不同責任
- 不同名稱但相同能力
- 有意重複
- 真正獨立

重疊判定應比較目的、輸入、輸出、觸發、責任、狀態、資料、依賴、使用方式與驗證，而不是只比較文字相似度。

#### C. 重構與遷移

候選處置至少包含：

```text
Keep 保留
Extend 擴展
Refactor 重構
Merge 融合
Split 拆分
Replace 取代
Rebuild 重建
Retain 暫留
Retire 淘汰
Archive 歷史保存
```

處置不能只依名稱或單一分數決定。

#### D. 蒸餾後驗證

```text
處置
↓
實際變更
↓
重新驗證功能
↓
重新驗證關係／依賴
↓
確認成本是否下降
↓
確認是否產生新問題
↓
建立新基準
```

## 七、蒸餾與迭代的責任分界

| 問題 | 主要責任 |
|---|---|
| 新證據需要修正一份知識 | 方案 3 |
| 新需求需要新增能力 | 方案 3，必要時進入問題解決／新系統流程 |
| 版本相容性 | 方案 3 + 共同資料治理 |
| 新舊資料遷移 | 方案 3 |
| 多份資料長期重複 | 方案 4 |
| 多個系統責任重疊 | 方案 4 |
| 系統長期沒有使用但仍保留 | 方案 4 |
| 架構逐步膨脹 | 方案 4 |
| 需要拆分大型能力 | 方案 4 |
| 需要因規模而分流 | 方案 4 |
| 蒸餾後產生的新版本 | 回到方案 3 管理演化 |

重要原則：

> 方案 4 可以提出與執行經確認的重構，但不取得其他方案的永久所有權。

## 八、共同能力，不重複建立

兩方案共同依賴但不各自重建：

```text
Identity
Metadata
Relationship
State
Version
History
Source
Evidence
Claim
Observation
Impact
Dependency
Validation
```

其中共同資料治理方案負責正式語義與共通規則。

方案 3、方案 4 負責在自身工作流程中使用這些共同資料。

禁止：

```text
方案 3 自己定義 Version v2
方案 4 又定義另一套 Version v2
```

應改為：

```text
共同 Version 語義
↓
方案 3 使用
方案 4 使用
```

## 九、尺度與語義必須分開

本輪特別禁止把「規模問題」與「內容問題」混為一談。

### 語義拆分

例如一份內容同時混有：

```text
Metadata
State
Version
Relationship
```

這是語義／責任問題。

### 規模拆分

例如同一套 System Catalog 在資料量大幅增加後造成：

```text
搜尋成本上升
更新成本上升
AI Context 過大
責任分化
同步錯誤增加
```

這是規模問題。

規模問題不應在小規模階段預先分片。

原則：

> 先以最簡單可運作的結構承載；只有實際成本、錯誤率、責任或同步問題證明需要拆分時，才進行規模重構。

## 十、蒸餾不是單純 Merge

蒸餾可能產生：

```text
保留
融合
拆分
重構
取代
重建
暫留
淘汰
歷史保存
```

其中「融合」只是其中一種結果。

蒸餾真正的目標是：

> 用較少的必要結構，維持或提升原本需要的能力，同時降低長期成本與錯誤風險。

允許有意重複：

```text
每一個重複都必須能說明：
為什麼需要重複？
重複的邊界是什麼？
誰負責？
如何避免同步錯誤？
```

---

## 十一、不要預先建立大型蒸餾矩陣

本輪不先固定 18 個、20 個或更多分析維度。

第一階段採用：

```text
選一個真實、有限、低風險案例
↓
手動完整走一次蒸餾流程
↓
記錄實際需要哪些資訊
↓
判斷哪些分析維度真的必要
↓
再形成最小資料契約
```

原因：

> 未經案例驗證的大型矩陣，很容易把「可能需要」誤認成「正式需求」，最後產生新的治理負擔。

---

## 十二、第一階段實測策略

第一階段不建立自動蒸餾引擎。

先選擇 Repository 內一個真實、有限、可回復的重疊／版本案例。

候選案例包括：

1. 舊 `0-knowledge/` 與正式 `0-知識/` 並存問題。
2. `交接資料.md` 與不同版本交接文件並存問題。
3. 已知功能重疊但尚未完成正式整合的系統。

案例選擇條件：

```text
範圍有限
可追溯
可回復
不影響核心運作
可以觀察重疊／版本／責任問題
```

第一個案例完成後才決定是否需要建立新的蒸餾小系統或正式系統。

## 十四、與問題解決系統的關係

方案 3、方案 4 不取代問題解決系統。

當演化或蒸餾過程發現：

```text
不明確原因
重大異常
能力缺口
既有系統無法處理
```

應進入既有問題解決流程：

```text
問題確認
↓
盤點既有能力
↓
外部研究
↓
候選解法
↓
最小實測
↓
判定
```

禁止因為進入蒸餾方案就直接建立新系統。

---

## 十五、與實測結果回寫的關係

兩方案都必須使用共同的實測結果回寫能力。

最低閉環：

```text
預期狀態
↓
實際觸發
↓
實際執行
↓
實際結果
↓
與預期比較
↓
判定
↓
回寫
```

文件建立、外部研究、模擬推演不等於本 Repository 的實測證據。

---

## 十六、治理與自動化邊界

蒸餾方案可以分析與提出候選處置，但不能因為「看起來重複」就自動刪除。

處置權應依：

```text
影響範圍
依賴數量
證據強度
可逆性
是否涉及正式規則
是否涉及目前有效資料
是否涉及跨方案責任
是否存在替代能力
```

再決定：

```text
可自動
AI 建議、人確認
必須人工確認
禁止自動處理
```

這一部分目前只建立原則，不先建立固定風險分數。

---

## 十七、舊資料與舊文件處理原則

舊資料不等於無效資料。

蒸餾判定前必須區分：

```text
目前有效
歷史有效
待確認
已失效
已被取代
僅作追溯
已廢棄
```

舊文件可以保留作為歷史證據，但不得因「檔案還存在」就被視為目前採用內容。

同理：

```text
舊方案存在
≠
新方案必須依賴舊方案
```

本輪採取「歷史保留、現行重新建立」方式。

## 十八、版本與舊方案處理

原有：

`2-方案/知識迭代與資料演化方案-v1.0.md`

保留為歷史文件，不直接覆寫。

本輪建立新的正式重製文件，以新的責任邊界重新描述方案。

舊版本與新版本的關係應由後續版本／歷史模型記錄，而不是透過刪除舊檔案製造「沒有歷史」的假象。

---

## 十九、建立順序

本輪建立順序固定為：

```text
共同重製規劃
↓
知識與資料迭代演化方案重製
↓
能力蒸餾與系統重構方案建立
↓
兩方案責任／資料／流程交叉檢查
↓
檢查與整體資料治理方案接口
↓
檢查與 AI 知識管理方案接口
↓
檢查與問題解決／實測回寫／統御能力接口
↓
選擇第一個真實案例
↓
實際驗證
↓
回寫
```

因此兩方案必須一起重製，不能先把其中一個做完整，再事後硬接另一個。

## 二十、目前禁止事項

1. 不覆寫舊方案文件。
2. 不因新方案名稱直接建立大量新系統。
3. 不先建立大型蒸餾矩陣。
4. 不把外部 6R／7R 直接當成本專案規則。
