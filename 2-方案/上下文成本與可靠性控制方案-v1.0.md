# 上下文成本與可靠性控制方案

版本：v1.0
狀態：【候選方案；核心已建立；待最小實測】
類型：方案候選

## 一、方案核心
本方案以三個核心能力建立：

| 核心 | 名稱 | 目的 |
|---|---|---|
| C03 | Context Budget | 控制／測定不同任務需要多少 Context |
| C04 | Context Reliability Test | 測試 Context 大小改變後，AI 的理解、記憶與規則一致性 |
| C05 | Hallucination Detection | 偵測 Context 不足或過量造成的失真、幻覺與 unsupported claims |

## 二、方案不是單純「上下文管理」
既有上下文管理已回答「讀什麼、讀多少、何時停止」。

本方案新增的是可驗證閉環：
~~~text

↓

↓

↓
Evidence Grounding
↓
錯誤分類
↓

↓
調整 Context
↓
重新驗證
~~~

## 三、三核心系統
### C03｜Context Budget
系統：1-系統/上下文預算與充分性測量系統.md

輸出：
- 最小可靠 Context。
- Context 飽和點。
- 可能性能下降點。
- 任務 Context Profile。

### C04｜Context Reliability Test
系統：1-系統/上下文可靠性測試系統.md

輸出：
- 理解可靠性。
- 關鍵資訊 Recall。
- 規則一致性。
- 輸出穩定性。
- Context 敏感條件。

### C05｜Hallucination Detection
系統：1-系統/上下文證據一致性與幻覺檢測系統.md

輸出：
- Atomic Claims。
- Evidence Mapping。
- Supported／Contradicted／Unsupported／Uncertain。
- Context-induced Error 識別。

## 六、驗證目標
至少需要三組測試：

### Test A：Context Budget
同一任務使用多級 Context，找出最小可靠 Context 與過量區間。

### Test B：Reliability
在不同 Context 大小與組成下重複執行，檢查理解、Recall、規則一致性與結論漂移。

### Test C：Hallucination
用已知證據建立 supported／unsupported／contradicted claims，測試 C05 是否能正確分類；再做 Context 梯度，確認錯誤是否隨 Context 改變。

## 七、成功條件
方案不能以「文件完成」作為成功。

至少要證明：
1. 能測出任務級 Context 差異。
2. 能辨識可靠性隨 Context 變化的實際行為。
3. 能追溯重要主張到證據。
4. 能區分 Context-induced Error 與一般模型錯誤。
5. 三核心能互相提供輸入／輸出，而非三份孤立文件。
6. 測試結果可以回寫既有知識、系統或方案。

## 八、目前停止條件
先停止擴張系統數量。

下一步不是再設計第四、第五個系統，而是執行最小實測。

若測試失敗：
問題定義／研究／Knowledge／System 逐層回退。

若測試通過：
進行方案整合驗證，再決定是否升格為正式方案。
