# 正確成立方案與系統方案 v2.2

日期：2026-09-17
前版：`2-方案/正確成立方案與系統方案-v2.1.md`
狀態：【正式流程補強；新增 Problem Intake Gate】

## 一、本版修正的根本問題

v2.1 已處理：

```text
建立規劃 → 明確標記未建立／未完善 → 施工時重新執行建立方案流程
```

但本次又發現更早的入口缺口：

```text
新內容 → 直接進入規劃／規則補強
```

AI 甚至可能沒有先判斷「這是不是一個需要研究的工程問題」。

因此 v2.2 增加正式的：

```text
Problem Intake Gate（問題接收 Gate）
```

## 二、完整生命週期

```text
新內容／新要求／新發現
↓

↓

↓

↓

↓

↓

↓

↓

↓

↓

```

## 三、Problem Intake Gate 的判斷內容

任何可能改變知識、規則、系統、方案、流程、架構或工程方向的新內容，先回答：

```text
1. 這是什麼？
   問題／需求／限制／假設／證據／新資訊／候選方案？

2. 它改變了什麼？

3. 能拆成哪些子問題？

4. 既有知識、規則、系統是否已能處理？

5. 缺什麼知識或能力？

6. 外部世界如何處理同類問題？

7. 有哪些工具／產品／方法／案例可以比較？

8. 有哪些限制、漏洞、成本與失效模式？

9. 反方案是否成立？

10. 最後是否真的需要建立／修改方案？
```

未完成前，不得直接把新內容寫成正式方案結論。

## 四、與既有流程的關係

Problem Intake Gate 不是第二套方案建立流程，也不取代 v2.1 的建立前 Gate。

它處理的是更早的問題：

```text
「我們到底是不是正在面對一個需要建立方案的問題？」
```

v2.1 的流程處理：

```text
「既然確定要建立方案，正式建立前是否已完成必要研究與 Gate？」
```

因此兩者順序固定為：

```text
Problem Intake
→ 結論
→ 建立規劃
→ 正確成立方案與系統方案
→ LOCK / ALLOW
→ 建立
```

## 五、外部方法比對結論

AWS 的 Architectural Decision Record（ADR）要求重大架構決策保存 context、decision、consequences，並經 Proposed／Accepted／Rejected 等狀態審查；其目的之一是避免沒有理由的決策與重複討論。Microsoft Azure Well-Architected Framework 的 ADR 亦要求記錄問題與背景、選項、決策、取捨、狀態與被排除的替代方案。citeturn0search0turn0search1turn0search5

本系統採用其中的可追溯決策精神，但增加更早的入口：

```text
外部共通：重大決策必須可追溯
本系統補強：重大決策形成以前，先完成問題化、拆解、研究、比較與反方案
```

因此這不是增加「紀錄數量」，而是增加「決策形成前的必要判斷」。

## 六、規劃仍不等於建立

規劃完成後固定標記：

```text
【規劃完成／未建立／未完善】
```

下一次施工仍必須：

```text
讀取規劃
→ 讀取待辦／依賴
→ Preflight
→ 完整建立前流程
→ Gate
```

不得從規劃文件直接跳到核心方案／系統建立。

## 七、狀態與回傳成本

Problem Intake 不要求逐步回傳。

```text
微步驟：不記錄／不回傳
研究批次：必要時內部摘要
問題成立：Checkpoint
正式結論：Checkpoint
規劃成立：同步狀態／待辦／依賴／施工入口
Gate：Checkpoint
重大狀態／新基準：完整同步
```

增加的是必要的內部處理，不是逐步訊息傳輸。

## 八、正式控制規則

- 新內容不得直接等同方案。
- 新內容不得直接等同正確答案。
- 新內容若可能影響工程方向，必須進入 Problem Intake Gate。
- 未完成問題拆解、既有能力檢查、外部研究比較、漏洞／失效分析與反方案檢查，不得直接方案化。
- 結論確認值得進入工程後，才建立規劃。
- 規劃完成仍必須標記【未建立／未完善】。
- 正式施工仍必須重新執行完整建立方案流程。
- 不因 Problem Intake 增加微步驟回傳或微步驟紀錄。
