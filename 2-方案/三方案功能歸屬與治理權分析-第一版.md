# 三方案功能歸屬與治理權分析－第一版

狀態：**【設計中，不啟動】**

> 本文件用於對齊「AI 知識管理方案 v2.0」與「知識迭代與資料治理方案」，並判斷是否需要建立一個具有全局治理權的上位方案。
> 本文件不是正式啟動方案，也不修改現行 GitHub 架構。

## 一、目前判定

目前確認需要增加一個「上位治理層」的架構候選：

**整體資料治理方案（Overall Data Governance Solution）**

它不是負責包辦所有資料工作的方案，而是負責定義跨資料、系統、方案共同遵守的規則、格式、狀態、版本、關係、生命週期與責任邊界。

目前三方案關係候選：

```text
                    整體資料治理方案
                 Overall Data Governance
                           │
                    全局規則／約束
                           │
             ┌─────────────┴─────────────┐
             ↓                           ↓
      AI 知識管理方案              知識迭代與資料演化方案
   AI Knowledge Management      Knowledge Iteration &
          Solution              Data Evolution Solution
```

第二個方案目前暫定改稱「知識迭代與資料演化方案」，原因是「資料治理」若同時出現在上位方案與下位方案名稱中，會造成治理權責重疊。

此名稱尚未正式定案。

## 二、為什麼需要上位治理層

兩個方案各自處理不同問題：

- AI 知識管理：AI 如何取得、理解、使用、保存與驗證知識、記憶、狀態與 Context。
- 知識迭代與資料演化：既有資料與知識發生重大變化後，如何融合、拆分、取代、遷移、壓縮與恢復一致性。
- 整體資料治理：整個資料體系的共同規則由誰定義，以及不同方案之間如何保持共同語義與相容性。

若缺少第三層，可能產生：

```text
AI方案自行定義狀態
        ↓
迭代方案自行定義狀態
        ↓
兩套狀態模型逐漸分裂
```

因此必須區分「治理權」與「執行權」。

## 三、四種責任

每項功能至少分析四種責任：

| 責任 | 定義 |
|---|---|
| 治理權 | 決定共同規則、標準與邊界 |
| 執行權 | 實際完成該功能 |
| 使用權 | 使用其他方案提供的能力或資料 |
| 回饋權 | 根據實際結果提出規則、系統或方案修正需求 |

原則：

```text
共同規則 → 整體資料治理方案
局部執行 → 對應專責方案
跨方案能力 → 協作，不重複定義
```

治理方案不得因具有治理權而包辦所有執行工作。

## 四、174 項功能的第一輪歸屬模型

目前兩個方案共有 84 + 90 = 174 項功能。

174 項不能直接等同 174 個系統；必須經過：

```text
功能
↓
所需知識
↓
既有系統
↓
系統是否足夠
↓
主責方案
↓
治理方案
↓
協作方案
↓
驗證方式
```

最終矩陣欄位：

| 功能ID | 功能 | 原方案 | 最終主責方案 | 治理方案 | 協作方案 | 所需知識 | 既有系統 | 新系統候選 | 輸入 | 輸出 | 驗證 |
|---|---|---|---|---|---|---|---|---|---|---|---|

正式建構前必須逐項完成，不得只用功能群推測。

## 五、目前功能群的初步責任分配

### A. 整體資料治理方案主要責任

主要包含跨方案共同規則：

- 資料定義與語義邊界
- 資料類型與分類規則
- Metadata 規格
- 資料格式規則
- 狀態模型
- 版本模型
- 關係模型
- 來源／溯源模型
- 生命週期模型
- 引用與依賴規則
- 歷史與廢棄規則
- 跨方案一致性規則
- 方案責任邊界
- 架構級治理與審查規則

治理方案負責「規定怎麼管理」，不是「親自執行所有管理工作」。

### B. AI 知識管理方案主要責任

主要包含 AI 使用資料體系的能力：

- 問題／任務理解
- 知識形成與組織的 AI 使用流程
- 檢索與探索
- 來源與證據處理
- 研究流程
- 記憶使用
- 目前狀態使用
- Context 組裝與控制
- AI 交接
- AI 任務執行
- AI 結果保存
- AI 任務結果驗證

它使用整體資料治理提供的共同規則，但不自行創造另一套全局資料規則。

### C. 知識迭代與資料演化方案主要責任

主要包含資料與知識發生變化後的執行流程：

- 演化需求識別
- 一般更新與結構演化區分
- 知識新增、修正、取代、融合、拆分
- 資料結構演化
- 欄位與檔案遷移
- 版本演化
- 相容性判定
- Context 壓縮與演化
- 一致性修復
- 殘留識別
- 遷移
- 交接資料演化
- 複雜度治理
- 演化結果驗證

它執行演化，但必須遵守整體資料治理定義的共同資料規則。

## 六、最重要的權責區分

例如：

### 版本

```text
整體資料治理
→ 定義「版本」的共同語義、格式與關係規則

知識迭代與資料演化
→ 執行這一次版本變更與遷移

AI 知識管理
→ 使用正確版本的資料完成任務
```

### 狀態

```text
整體資料治理
→ 定義狀態模型與合法狀態轉移

迭代方案
→ 執行狀態變更

AI 知識管理
→ 根據狀態判斷能否使用資料
```

### 關係

```text
整體資料治理
→ 定義「依賴、取代、互補、融合、拆分、歷史」等關係語義

迭代方案
→ 建立實際演化關係

AI 知識管理
→ 使用關係協助搜尋、理解與 Context 組裝
```

## 七、治理優先順序

跨方案規則的優先級候選：

```text
整體共同治理規則
        >
方案邊界規則
        >
方案內部流程規則
        >
單一實作細節
```

但治理方案只有在「共同資料規則」範圍內具有最高優先權。

不得變成可以任意否決所有方案設計的超級方案。

## 八、治理模型不能直接採用「完全中央集權」

外部資料治理實務存在中央、分散、聯邦與混合治理模型。

本知識庫規模目前不大，不需要直接複製大型企業的 Data Mesh。

但架構原則值得採用：

```text
中央定義共同規則
        ↓
各專責方案保留局部執行自主性
        ↓
跨方案遵守共同介面與資料標準
        ↓
實際問題回饋治理層
```

因此目前候選模型為：

**「中央規則＋局部執行＋回饋治理」的輕量聯邦式治理。**

這不是現階段正式導入 Data Mesh，而是借用其「全局標準與局部自治並存」的治理思想。

## 九、共同資料模型候選

需要進一步確認的共同資料類型：

- 知識
- 記憶
- 目前狀態
- 來源
- 證據
- 主張
- 決策
- 觀察
- 經驗／教訓
- 系統
- 方案
- 版本
- 歷史
- 待確認
- 廢棄資料

不得預設所有類型共用完全相同 Metadata。

應分為：

```text
共同核心欄位
＋
資料類型專屬欄位
＋
可推導欄位
＋
不應保存的冗餘欄位
```

## 十、共同關係模型候選

至少需要分析：

```text
來源 → 資料
來源 → 主張
證據 → 主張
主張 → 知識
知識 → 系統
系統 → 方案
方案 → 應用

知識 → 依賴 → 知識
知識 → 互補 → 知識
知識 → 取代 → 知識
知識 → 融合 → 知識
知識 → 拆分 → 知識
知識 → 歷史 → 知識

方案 → 使用 → 系統
方案 → 產生 → 知識
方案 → 回饋 → 知識／系統／方案
```

這些關係是否全部需要保存，仍須透過功能矩陣與實際案例確認。

## 十一、外部方法比對後的架構判定

本輪外部研究確認：

1. DAMA-DMBOK 將 Data Management 視為完整專業範圍，並把 Data Governance、Metadata、Data Quality、Data Integration 等放在共同框架中。這支持「需要上位共同管理框架」的方向，但不表示本知識庫必須照搬 DAMA 的完整組織。 
2. DCAM v3 將資料管理拆成 34 個 capabilities 與 101 個 sub-capabilities，並以 operating model、business data knowledge、architecture 等共同能力支撐資料管理。這支持我們「功能 → 能力 → 系統 → 方案」而不是「一個功能一個系統」的做法。
3. Data Mesh 的實務模型不是完全中央集權，而是 domain ownership、data as a product、self-serve infrastructure 與 federated governance。其核心是「全局標準＋局部自治」。這可作為我們避免治理方案吞掉所有執行工作的參考。
4. Databricks 的治理模型實務上提供 centralized、distributed、federated、hybrid 四種模型，並指出 hybrid 對許多企業較合適。這支持本知識庫採用輕量的「中央規則＋局部執行」而不是完全中央集權。
5. AI Agent 架構的現代實務已明確把 knowledge grounding、working context、long-term memory、tools、orchestration 與治理／可觀測性區分開。這與目前把 AI 知識管理從整體資料治理中分離的方向一致。
6. AWS 的近期 AgentCore memory 實務已把 memory lifecycle、分類、保留、合併、淘汰與審計視為獨立生命週期管理問題，進一步支持「記憶不是單純文件，也不能等同知識」。

## 十二、目前採用的架構結論

目前不採用：

- 完全中央集權資料管理。
- 每個方案自行定義一套資料格式。
- 每個方案自行定義狀態與版本。
- 一個功能直接對應一個系統。
- 直接導入 Data Mesh。
- 直接建立 Vector DB / Graph DB 作為架構核心。

目前採用的設計方向：

```text
中央共同規則
        ↓
整體資料治理方案
        ↓
共同資料模型／關係／狀態／版本／生命週期
        ↓
┌───────────────────────┐
│                       │
↓                       ↓
AI知識管理           知識迭代與資料演化
│                       │
└───────────┬───────────┘
            ↓
       系統／工具／應用
            ↓
       實際結果與驗證
            ↓
          回饋治理
```

## 十四、重要限制

本文件的外部比對只能證明：

- 類似治理思想在現實資料管理與 AI 系統中確實存在。
- 中央共同規則與局部自治的混合方式具有實務先例。
- AI 知識、Context、Memory、Data Governance 的分層並非孤立設計。

不能因此直接證明本知識庫的三方案架構已經成立。

正式成立仍必須依照本知識庫自己的功能需求、資料格式、實際操作與驗證結果確認。
