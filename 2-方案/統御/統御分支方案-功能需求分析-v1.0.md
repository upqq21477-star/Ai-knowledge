# 統御分支方案：功能需求分析 v1.0

日期：2026-09-17
狀態：【建立中；功能候選已列出；待既有能力逐項比對】

## 一、功能分析原則

本文件先列出「可能需要的功能」，不代表每一項都必須建立新系統。

每項功能都必須先回答：

```text
是否已存在？
→ 哪個知識／系統已提供？
→ 是否完全覆蓋？
→ 是否只需引用？
→ 是否需要新增能力？
```

## 二、候選功能清單

### F01 系統身份管理

目的：為每個系統建立穩定、可引用的 System ID。

最低資料：

- System ID
- 系統名稱
- 系統文件位置

### F02 系統目錄

目的：快速列出目前有哪些系統，以及基本定位資訊。

最低資料：

- System ID
- 名稱
- 位置
- 狀態
- 類別

### F03 系統狀態管理

目的：區分候選、建立中、待驗證、運作中、暫停、廢棄等狀態。

### F04 方案歸屬管理

目的：知道系統屬於哪個正式方案，或目前為跨方案／尚未歸屬。

### F05 知識關係管理

目的：知道系統依賴哪些知識書，以及知識書與系統的關係。

不把知識全文複製進目錄，只保存引用／位置／ID。

### F06 功能摘要管理

目的：讓 AI 不必先打開所有系統文件，就能快速知道系統負責什麼。

### F07 觸發條件登錄

目的：建立「事件／情境 → 目標 System ID」的可搜尋關係。

### F08 觸發條件搜尋／匹配

目的：輸入目前事件或工作情境，找到可能被觸發的系統。

### F09 觸發結果轉交

目的：觸發條件管理完成匹配後，只輸出目標 System ID，不直接執行專責邏輯。

### F10 方案路由

目的：取得 System ID 後，查詢方案歸屬並交給對應方案。

### F11 多重匹配處理

目的：避免一個事件同時命中多個系統時偷偷選錯。

第一版最低規則：

```text
0 個 → 無已知觸發能力
1 個 → 正常轉交
多個 → 標記歧義，交由統御／問題解決進一步判斷
```

第一版不自行建立複雜優先級演算法。

### F12 失效／停用系統檢查

目的：觸發命中後，確認目標系統目前是否仍可使用。

### F13 系統位置追蹤

目的：系統文件移動後仍能更新目錄位置。

正式關聯仍以 System ID 為準，不以路徑作為身份。

### F14 系統生命週期管理

目的：處理建立、驗證、運作、暫停、整合、廢棄等狀態變化。

### F15 觸發條件生命週期管理

目的：防止已失效、已移除或已不適用的觸發條件持續命中。

### F16 觸發衝突／重複檢查

目的：發現多個觸發條件描述同一情境、或不同系統競爭同一事件。

### F17 狀態與實際文件一致性檢查

目的：檢查目錄資料是否仍與實際系統文件一致。

### F18 變更後索引更新

目的：新系統、系統移動、狀態變更、方案歸屬變更時，保持目錄可用。

## 五、現有能力初步比對

repository 已存在：

- 系統定義與邊界知識。
- 系統與知識關係知識。
- 系統依賴知識。
- 方案管理原理。
- 方案管理系統。
- 統御系統狀態總表候選資料。
- 統御小系統協調管理系統候選文件。
- AI 知識庫基本運作系統中的異常、狀態與路由能力。
- 問題解決系統與問題解決路由能力。

因此本方案不能直接把上述能力全部重做。

目前最明顯的新能力候選是：

```text
「獨立的觸發條件登錄／搜尋／匹配」
+
「統一的系統身份／目錄索引」
```

其餘功能需要繼續比對後才能決定是否新增。

## 六、需要建立／補充的知識候選

### K01 系統目錄（System Catalog）原理

研究：系統目錄應保存哪些 metadata、如何搜尋、如何與真實系統文件分工。

### K02 穩定識別與引用（Stable Identifier / Reference）原理

研究：為什麼名稱與路徑不適合作為長期關聯鍵，以及 ID 如何處理移動／改名。

### K03 觸發條件管理（Trigger Registry）原理

研究：觸發條件登錄、匹配、失效、版本與責任邊界。

### K04 事件／條件到能力路由（Event-to-Capability Routing）原理

研究：事件如何找到候選能力，以及如何避免把路由器變成巨大執行引擎。

### K05 多重匹配與歧義處理原理

研究：一個事件命中多個候選能力時的處理方式。

### K06 目錄與真實來源邊界原理

研究：目錄是索引／metadata layer 還是真實狀態來源；如何避免目錄與實際文件脫節。
