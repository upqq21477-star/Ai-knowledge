# 統御分支方案 v1.1

日期：2026-09-17
狀態：【建立中；架構已調整；待功能收斂與實際驗證】

## 一、方案定位

統御分支是 Ai-knowledge 的橫向管理能力，維持：

```text
系統可被找到
→ 身份可被確認
→ 正常流程漏啟動時可被發現
→ 必要時安全補啟動
→ 正確路由到方案／專責系統
```

它不是中央執行引擎，也不是所有事件的第一啟動入口。

## 二、核心架構

```text
正常工作流程
      ↓
專責系統正常啟動
      │
      │ 若可能漏啟動
      ↓
觸發條件管理系統
（第二層啟動保險）
      ↓
Trigger → System ID
      ↓
檢查目前啟動／處理狀態
   ┌──┴──────────┐
   ↓             ↓
已處理／執行中    未處理
   ↓             ↓
不重啟           補充啟動
                 ↓
              方案／系統
```

System Catalog 仍負責 System ID、位置、狀態、方案、知識與功能摘要；Trigger Registry 不重複保存這些正式資料。

## 三、兩個核心能力

### 1. 系統目錄／身份管理

回答：有哪些系統、系統在哪裡、目前狀態、屬於哪個方案、關聯哪些知識。

### 2. 啟動保險／觸發管理

回答：正常流程是否可能漏掉某個系統？若找到候選，該系統是否已經在處理？只有未處理且條件仍成立時才補啟動。

## 四、觸發安全規則

- Trigger 命中不等於立即啟動。
- 同一 Event ID + System ID 不得重複建立相同處理。
- 已啟動／執行中／已處理 → 不二次啟動。
- 多重匹配 → 標記歧義，不預設全部啟動。
- 狀態不明 → 不擴大啟動，轉交判定。
- 系統執行造成的狀態變更不得形成無限 Trigger Loop。
- Trigger 只負責第一級候選，不負責完整方案決策。

## 五、最小功能

### 系統目錄
- System ID
- 系統名稱與位置
- 系統狀態
- 方案歸屬
- 功能摘要
- 關聯知識
- 基本生命週期

### 啟動保險
- Trigger 登錄
- Trigger 匹配
- System ID 對應
- 啟動／處理狀態確認
- 防二次啟動
- 基本循環防護
- 多重匹配歧義標記
- 失效 Trigger／失效目標檢查
- 事件與啟動關係記錄

## 六、不做

不建立中央事件總線、複雜規則引擎、完整工作流引擎、自動最佳方案選擇器、中央問題解決器或目標系統內部執行邏輯。

## 七、資料規模策略

初期仍採單一薄型 System Catalog + 薄型 Trigger Registry + 搜尋／篩選，不預先按資料量切割。只有實際出現不同責任、生命週期、同步成本或維護成本時才分流。

## 八、主要風險

1. 保險層變成第一啟動源。
2. Trigger 命中造成二次啟動。
3. 事件重複造成重入。
4. 系統狀態變更造成循環觸發。
5. 多重匹配造成大量系統同時啟動。
6. Trigger 與 Catalog 狀態脫節。
7. 統御分支逐漸接管專責系統決策。

## 九、驗證順序

```text
正常啟動 → Trigger 不重啟
漏啟動 → Trigger 補啟動
重複事件 → 不重複執行
多重匹配 → 不自動全部啟動
執行後狀態變更 → 不形成循環
```

所有驗證優先利用正常工作自然觸發，不另造不必要的測試工作。

## 十、狀態

本版完成架構修正與安全邊界調整；尚未完成實際案例驗證，因此仍為【建立中】。
