# 統御分支方案：架構與施工規劃 v1.0

日期：2026-09-17
狀態：【建立中；架構已確認；功能與知識需求分析中】

## 一、方案目的

建立一個輕量的「統御分支」，負責讓 Ai-knowledge 能快速回答三個問題：

1. 目前有哪些系統？
2. 某個系統在哪裡、屬於哪個方案、目前是什麼狀態？
3. 某個事件／情境出現時，應該先找到哪個系統處理？

本方案不負責取代各專責系統的執行邏輯，也不建立大型中央控制器。

## 二、候選核心架構

```text
                         ┌─ 系統目錄／管理統御分支
                         │
事件／情境
    │                    │  系統 ID
    ↓                    │  系統名稱
觸發條件管理系統 ───────→│  文件位置
    │                    │  狀態
    │                    │  方案歸屬
    │                    │  知識關係
    │                    │  功能摘要
    │                    │
    ↓                    ↓
找到目標系統 ID      判定所屬方案
                         ↓
                    交給方案路由
                         ↓
                    啟動專責系統
```

## 三、兩個核心能力

### A. 觸發條件管理

只負責「什麼情況可能需要叫醒哪個系統」。

核心資料：

- Trigger ID
- 觸發條件／事件描述
- 目標 System ID
- 觸發狀態
- 必要的粗略分類

不在此保存完整執行流程，不判定方案，不取代目標系統。

### B. 系統管理統御分支

只負責「這個系統是誰、在哪裡、屬於哪裡、目前狀態如何」。

核心資料：

- System ID
- 系統名稱
- 文件位置
- 系統狀態
- 方案歸屬
- 知識書關係
- 功能摘要
- 版本／生命週期資訊

## 四、責任邊界

```text
觸發條件管理
= 誰可能需要被叫醒？

系統管理統御
= 這個系統是誰、在哪裡、屬於誰？

方案
= 多個能力如何為特定目的協作？

專責系統
= 實際怎麼處理？
```

不得將完整系統執行規則塞入觸發條件管理系統，也不得讓系統管理統御分支重新實作專責方案的處理邏輯。

## 五、資料流

```text
事件／問題／工作情境
↓
觸發條件管理系統
↓
符合條件？
├─ 否 → 無已知觸發能力／進入其他搜尋或問題解決流程
└─ 是
    ↓
取得 System ID
    ↓
系統管理統御分支
    ↓
確認系統狀態與方案歸屬
    ↓
方案路由
    ↓
專責系統執行
    ↓
結果回饋
```

## 六、觸發與系統 ID 的原則

系統名稱與文件位置可以變更，因此正式關聯不應只依賴名稱或路徑。

採用穩定的 System ID 作為關聯鍵：

```text
Trigger ID → System ID
System ID → 系統名稱／位置／狀態／方案／知識
```

名稱與位置是人類閱讀與定位資訊；System ID 是跨文件關聯的穩定識別。

## 七、粗略分層

初期不建立深層目錄樹，只建立少量功能類別，例如：

- 運作／交接
- 搜尋／研究
- 更新／變更
- 驗證／實測
- 問題／異常
- 建立／生命週期
- 管理／治理

實際分類以後續使用案例調整，不預先建立大量層級。

## 八、規模控制

初期採單一總目錄與分類檢索，不因資料筆數增加就立即拆分資料。

只有當實際出現以下問題才考慮分流：

- 搜尋成本明顯增加。
- 更新責任分裂。
- 不同類型資料需要不同生命週期。
- 狀態同步成本增加。
- 不同分支產生不同管理規則。

分流後仍維持唯一 System ID，不複製同一系統的正式身份。

## 九、目前不納入

第一版不納入：

- 大型事件匯流排。
- 複雜規則引擎。
- 自動優先級最佳化。
- 全自動方案選擇。
- 即時分散式狀態控制。
- 完整企業級 CMDB。
- 大型知識圖譜。

先驗證最小可用架構。

Backstage 也使用穩定 entity reference 來連接實體，而不是依賴顯示名稱；這支持本方案使用 System ID 作為觸發條件與系統目錄之間的正式關聯鍵。citeturn0search1turn0search3
