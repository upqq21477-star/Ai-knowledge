# 統御分支候選方案：既有能力比對與功能裁減 v1.0

日期：2026-09-17  
狀態：【已完成第一輪比對；候選方案仍施工中；未進入正式方案確認】

## 一、目的

本文件不是建立新系統，而是依照方案建立流程，檢查統御分支候選方案目前提出的功能，是否已由既有系統／方案承擔，避免重複建立能力。

本輪只處理「既有能力比對與功能裁減」，不直接修改舊系統文件。

## 二、目前候選核心

統御分支目前只保留兩個能力群：

```text
A. System Catalog / 系統目錄
B. Activation Safety / 啟動保險層（Trigger Registry）
```

其核心目的不是執行業務，而是回答兩個問題：

```text
這個系統是誰、現在在哪裡、屬於哪個方案？
這個事件可能需要叫醒哪個系統，以及是否已經被處理？
```

## 三、既有能力比對

### 1. 方案管理系統

既有 `1-系統/方案管理系統.md` 負責方案本身的建立、組成系統、組合方式、驗證與方案歷史。

判定：

- 方案組合管理：已有，不納入統御分支。
- 系統所屬方案的「查詢索引」：仍需要統御分支保留最小關聯，因為 Trigger 取得 System ID 後必須知道往哪個方案移交。
- 方案內部如何協作：仍由方案負責，不由統御分支接管。

結論：統御分支不能變成第二套方案管理系統。

### 2. 小系統建立與生命週期管理系統

既有 `1-系統/小系統建立與生命週期管理系統-v1.0.md` 管理候選小系統的建立、實測、成立、升格、整合與廢止。

判定：

- 小系統生命週期：已有，不納入統御分支。
- 統御分支可以索引其「目前狀態」與 System ID，但不重新管理其生命週期。
- 「狀態」在統御目錄中是索引欄位，不是第二套生命週期規則。

結論：Catalog 的狀態欄位只保存可供路由與查詢的最小狀態，不複製生命週期管理邏輯。

### 3. 觸發條件管理系統 v1.0

既有 `1-系統/觸發條件管理系統-v1.0.md` 已定義 Trigger Registry：事件／問題／需求 → 觸發條件搜尋 → 候選 System ID → 系統管理統御分支 → 方案／系統。

這與目前候選統御分支的 Trigger Registry 高度重疊。

判定：

**不應再建立第二套 Trigger Registry。**

目前正確方向不是「再增加一個觸發系統」，而是將已存在的觸發條件管理能力重新定位為「啟動保險層」的一部分，並補上：

- Event ID / System ID 關聯
- 已啟動／處理中的狀態檢查
- 同一事件＋同一 System ID 的重複啟動阻止
- 多重命中歧義
- 基本迴圈保護
- 無效目標阻止

若上述能力尚未實際存在於 v1.0 實作，應視為既有系統的能力缺口／修正需求，而不是建立另一個同功能系統。

### 4. 系統管理統御分支 v1.0

既有 `1-系統/系統管理統御分支-v1.0.md` 已包含：

- 系統身份
- 系統目錄
- 系統位置
- 系統狀態
- System ID 接收觸發轉交
- 將系統路由至所屬方案

因此目前候選方案的 Catalog 核心並非完全的新能力，而是對既有候選系統進行收斂與資料契約化。

判定：

**不新增另一個「系統目錄系統」。**

後續應優先明確化既有 `系統管理統御分支` 的最小資料契約與責任邊界。

### 5. 既有方案／知識管理能力

目前既有知識與方案管理能力已處理知識內容、方案內容、方案組成與驗證等問題。

判定：

統御分支只保存「可供索引與路由的關係」，不保存完整知識內容、完整方案內容或系統內部流程。

## 四、第一輪功能裁減結果

### 保留

```text
C01 System ID / 穩定系統身份
C02 Catalog Location / 系統目錄位置
C03 Current Status / 最小目前狀態
C04 Solution Reference / 所屬方案引用
C05 Knowledge Reference / 相關知識書引用
C06 Function Summary / 一句話功能摘要
C07 Lifecycle Pointer / 必要時的生命週期狀態引用

T01 Trigger Registration / 觸發條件登錄
T02 Trigger Matching / 第一級匹配
T03 Trigger → System ID / 目標系統引用
T04 Activation State Check / 啟動狀態檢查
T05 Duplicate Activation Guard / 重複啟動阻止
T06 Event ID Relation / 事件與處理關聯
T07 Loop Protection / 基本迴圈保護
T08 Ambiguity Handling / 多重命中歧義
T09 Invalid Target Guard / 無效目標阻止
```

### 明確排除

以下能力不應進入統御分支第一版：

- 完整方案策略
- 系統內部業務邏輯
- 問題解決流程
- 自動選出「最佳」系統
- 複雜優先級計算
- 完整 Rule Engine
- Event Bus
- Workflow Engine
- 中央執行器
- 跨系統業務流程編排
- 完整事件歷史資料庫
- 第二套小系統生命週期管理
- 第二套方案管理

## 五、最重要的重疊發現

本輪最大問題不是「缺少更多功能」，而是**目前已存在的 `觸發條件管理系統 v1.0` 與 `系統管理統御分支 v1.0` 已經承擔了候選方案的主要能力**。

因此下一步不能再按照「功能 → 建立新系統」處理。

正確順序應改為：

```text
既有系統
↓
確認真正能力缺口
↓
確認缺口屬於既有系統修正、整合，還是真正的新能力
↓
若只是修正／整合 → 不建立新系統
↓
若確有新能力 → 才進入知識／系統建立流程
```

## 六、目前最可能的真正缺口

目前證據支持的缺口集中在「啟動安全」而非「觸發索引本身」：

```text
Trigger 命中
↓
System ID
↓
確認目前是否已啟動／處理中／已完成
↓
若已處理 → 不重啟
若未處理 → 補充啟動
若多重命中 → 標記歧義，不批量啟動
若目標無效 → 阻止
若狀態不明 → 不擴張啟動，交由後續判定
```

這是本輪應驗證的最小能力，而不是建立更多管理功能。

## 七、對方案架構的影響

候選架構暫時收斂為：

```text
                ┌─ System Catalog
統御分支 ───────┤
                └─ Activation Safety
                       │
                       └─ 既有 Trigger Registry
                              ↓
                           System ID
                              ↓
                         系統目錄查詢
                              ↓
                           所屬方案
                              ↓
                         目標系統處理
```

其中 Trigger Registry 是既有能力的收斂與強化方向，不應另造第二套。

## 八、尚未完成的比對

本輪完成的是第一層「功能名稱與責任邊界」比對，仍需要實際確認：

1. `系統管理統御分支 v1.0` 是否已具備可穩定引用的 System ID 資料契約。
2. `觸發條件管理系統 v1.0` 是否已具備 Event ID / System ID 的處理關聯。
3. 是否已有其他文件保存「系統目前啟動狀態」，避免再造狀態來源。
4. 方案歸屬是否已有唯一可信來源。
5. 知識關係是否需要 Catalog 保存，或只需引用既有索引。
6. 系統改名、搬移、升版、整合、廢止時，System ID 是否保持穩定。

上述六項確認完成後，才能形成真正的最小資料契約。

## 九、本輪判定

```text
統御分支候選方案：保留施工
新增 Catalog 系統：暫不建立
新增 Trigger 系統：暫不建立
既有 Trigger Registry：保留，改以啟動保險層角度補強
既有系統管理統御分支：保留，轉向最小資料契約
正式方案確認：未達 Gate
實測：尚未開始
```

下一步不是繼續增加文件，而是完成上述六項資料來源／責任邊界確認，然後設計最小資料契約，再進入自然工作驗證。
