# 統御分支方案 v1.0

日期：2026-09-17
狀態：【建立中；核心架構已形成；待實際驗證】

## 一、方案定位

統御分支是 Ai-knowledge 的橫向管理能力，用於維持「系統可被找到、身份可被確認、觸發可被匹配、方案可被路由」的最小閉環。

它不是第四個大型正式方案的替代品，也不是所有系統的中央執行引擎。

## 二、核心目標

```text
知道有哪些系統
→ 找得到系統
→ 知道系統屬於哪裡
→ 事件發生時找到可能需要啟動的系統
→ 正確交給系統管理統御分支
→ 路由到方案
→ 啟動專責系統
```

## 三、方案架構

```text
                     統御分支
                         │
             ┌───────────┴───────────┐
             ↓                       ↓
      觸發條件管理系統          系統管理統御分支系統
      Trigger Registry          System Catalog / Registry
             │                       │
             │ System ID             │
             └──────────→────────────┘
                                     │
                               方案歸屬
                                     ↓
                                    方案
                                     ↓
                                  系統
```

## 四、兩個核心系統

### 1. 觸發條件管理系統

負責：

- Trigger ID。
- 觸發條件。
- 目標 System ID。
- 第一級匹配。
- 觸發狀態。
- 基本失效檢查。

不負責方案判定與專責執行。

### 2. 系統管理統御分支系統

負責：

- System ID。
- 系統名稱。
- 文件位置。
- 系統狀態。
- 方案歸屬。
- 功能摘要。
- 關聯知識。
- 基本生命週期。
- System ID → 方案的路由。

不負責觸發條件匹配與專責系統內部執行。

## 五、核心資料關係

```text
Trigger ID
    ↓
System ID
    ↓
系統 metadata
    ↓
方案 ID／方案
    ↓
專責系統
```

其中 System ID 是核心穩定關聯鍵。

## 六、事件處理流程

```text
事件／問題／需求
↓
觸發條件管理
↓
0 個匹配 → 無已知觸發能力
1 個匹配 → 取得 System ID
多個匹配 → 保留候選並標記歧義
↓
系統管理統御
↓
確認系統身份／狀態／方案
↓
方案
↓
專責系統
↓
結果
↓
狀態重新確認／必要時回寫
```

## 七、功能範圍

第一版正式核心：

- 系統身份管理。
- 系統目錄。
- 系統狀態。
- 方案歸屬。
- 知識關係。
- 功能摘要。
- 觸發條件登錄。
- 觸發條件搜尋／匹配。
- Trigger → System ID 轉交。
- System ID → 方案路由。
- 基本失效系統檢查。
- 基本位置追蹤。

後續候選能力：

- 多重匹配進階判斷。
- 系統生命週期自動管理。
- 觸發條件衝突分析。
- 目錄／文件一致性檢查。
- 自動索引更新。

後續能力不因列入候選就視為必須建立。

## 八、資料分層

初期採粗略分層：

```text
運作／交接
搜尋／研究
更新／變更
驗證／實測
問題／異常
建立／生命週期
管理／治理
```

不預先建立深層分類。

資料量增加時優先採搜尋／篩選；只有實際出現不同生命週期、責任、同步或維護成本時才分流。

## 九、方案與既有能力的關係

本方案不取代：

- 問題解決系統。
- AI 上下文與交接系統。
- 知識管理系統。
- 更新／演化系統。
- 各正式方案的專責系統。

它只提供橫向的身份、索引與第一級路由能力。

## 十一、外部方法比較結論

Backstage Software Catalog 顯示，集中式 catalog 適合保存 ownership、inventory、search、lifecycle 與關係 metadata，但不應被視為所有即時動態關係的唯一真實來源。citeturn0search0turn0search11

Kubernetes Controller 顯示，控制責任適合依不同狀態面向拆分，而不是集中成單一巨大控制器。citeturn0search7

AWS EventBridge 與 Azure Event Grid 顯示，事件可以依條件／pattern 篩選後交給 target；同時存在多重匹配、精確條件與循環觸發等問題。citeturn1search2turn1search11turn1search9

因此本方案採取最小化版本：

```text
薄型 System Catalog
+
薄型 Trigger Registry
+
明確 System ID
+
方案路由
```

而不是複製企業級 CMDB、Event Bus 或 Rule Engine。

## 十二、主要風險

1. Trigger Registry 膨脹成第二個執行引擎。
2. System Catalog 與實際文件狀態脫節。
3. 同一事件匹配多個系統而沒有歧義處理。
4. 觸發條件過度模糊造成誤啟動。
5. 系統身份被名稱／路徑取代而造成引用斷裂。
6. 統御分支逐漸接管各方案的專責決策。
7. 資料量增加後維護成本超過搜尋帶來的收益。
