# 搜尋研究方案－圖書館式知識管理外部研究 v1.0

日期：2026-09-17
狀態：【第一輪外部研究完成；待以本知識庫實際案例驗證】

## 一、研究目的

不是直接建立圖書館系統，而是先回答：

> 大量 AI 知識應該以什麼粒度、文件形式、Metadata、索引與檢索單位存在？

研究結果將反過來決定「知識書」的規格，因此本研究先於知識書正式規格與圖書館系統正式設計。

## 二、研究問題

1. 外部大型知識庫如何區分原始內容、描述 Metadata、Catalog、Index、Retrieval Context？
2. 文件是否應直接等於最小知識單位？
3. 什麼情況需要 Chunk / Knowledge Atom？
4. 原始知識與檢索用資料是否應保持分離？
5. Metadata 應放在知識內容內，還是由管理／索引層提供？
6. 大型資料更新時，哪些資料需要重建？
7. 如何避免為了搜尋效率破壞知識本體的穩定性？

## 三、外部研究結果

### 1. Azure AI Search：文件、Chunk、Index、Retrieval 是不同層

Microsoft 的 2026 文件指出，大文件可以在索引階段切成較小 chunks，以符合模型輸入限制與改善檢索；chunking 是索引／查詢流程中的處理步驟，而不是要求原始文件本身必須被永久拆成相同形式的知識單位。

來源：Microsoft Learn, Chunk Documents for RAG and vector search。

### 2. Azure AI Search：Index 不等於原始知識

Microsoft 的 Agentic Retrieval index 設計中，index 可以包含人類／LLM 可讀的 chunk、Metadata、semantic ranking 與 optional vector representation。向量主要服務查詢執行，不必成為最終知識內容。

這支持一個重要分層：

```text
原始知識
↓
索引／檢索表示
↓
Context
```

而不是：

```text
原始知識 = Index = Vector = Context
```

來源：Microsoft Learn, Create an Index for Agentic Retrieval。

### 3. 結構化資料不一定需要 Chunk

Microsoft 明確指出，如果來源本身是結構化資料，例如產品資料庫，index 可以直接保留欄位，而不是套用文件 chunking。

因此「所有知識都必須原子化成固定 chunk」不能成為本系統預設規則。

來源：Microsoft Learn, Create an Index for Agentic Retrieval。

### 4. Metadata 是檢索層的重要輔助，但不等於知識正文

Microsoft 的 RAG chunk enrichment 方法會在 chunk 上增加 title、summary、keywords、questions 等 metadata，以改善檢索。

這顯示 Metadata 可以服務 Retrieval，而不代表這些欄位必須成為知識正文的一部分。

來源：Microsoft Learn, RAG Chunk Enrichment。

### 5. Knowledge Source 與 Knowledge Base 也是不同層

Microsoft 2026 Agentic Retrieval 將 knowledge source 與 knowledge base 分開：knowledge source 指向可搜尋內容；knowledge base 負責統一多個來源並進行檢索規劃與結果整合。

這與本專案目前提出的「知識內容／Catalog／Index／Context」分層方向相容。

來源：Microsoft Learn, What is a Knowledge Source?；Query Knowledge Base via API or MCP。

## 四、目前可採納的外部共識

目前可以較有把握地建立以下暫時結論：

### A. 知識正文與檢索表示應分離

知識書不應被迫等於 chunk、vector 或 search index。

### B. 原子化是檢索／使用需求，不必直接等於文件格式

可以存在：

```text
知識書
↓
語義單位
↓
檢索 Chunk
↓
Context
```

也可能某些結構化知識直接以欄位／記錄形式進入索引。

### C. Metadata 應考慮管理層與檢索層需求

不能現在就把所有可能的 Metadata 塞進知識書正文。

### D. Index 是衍生物

Index 可以因搜尋方法、模型、Metadata、版本或資料規模變化而重建，因此不應與知識本體綁死。

### E. Context 是最後使用表示

AI 真正讀取的是經過 Retrieval 篩選後的資料，不是整個知識庫。

## 五、對本專案「知識書」的暫時推導

目前不正式固定欄位與 Schema，但可以先建立設計邊界：

### 知識書應保留

- 穩定的知識內容
- 知識自身必要的語義上下文
- 適用範圍與條件
- 必要來源／證據指向
- 足以辨識該知識的 Identity

### 暫時不要直接固定進正文

- embedding vector
- 搜尋排名
- 特定搜尋引擎欄位
- chunk 序號
- 暫時性的 query keywords
- 特定 AI 模型專用欄位
- 只為某一檢索演算法存在的資料

這些更適合由管理／索引層產生。

## 六、與目前共同資料模型的關係

現有共同資料最小描述原則中的：

Identity、Content、Scope、Conditions、Time、State、Basis / Provenance

仍可作為上層語義基礎。

但本研究顯示：這些語義欄位不代表全部都必須以同一種 Markdown 正文形式保存。

因此下一步要區分：

```text
語義上必須存在
≠
必須寫在知識正文
≠
必須進入索引
≠
必須送入 Context
```

這是目前非常重要的設計邊界。

## 七、目前不能下的結論

目前仍不能直接決定：

- 每份知識書固定幾百字／幾千字。
- 一份知識書只能有一個 Claim。
- 所有知識都拆成 Atom。
- Markdown 是否永遠是唯一保存格式。
- 是否使用 JSON。
- 是否使用向量資料庫。
- 是否使用 Knowledge Graph。
- Catalog 的完整欄位。
- Index 的完整欄位。

這些必須用本專案真實知識資料測試後才能決定。

## 八、下一步實測

選取目前 repository 中至少三種不同類型知識：

1. 定義型知識。
2. 方法／流程型知識。
3. 複合型／具有多條件與關係的知識。

分別嘗試：

```text
完整知識書
vs
語義單位拆分
vs
檢索 Chunk 拆分
```

觀察：

- AI 是否更容易正確理解。
- 是否失去必要上下文。
- 是否容易重複。
- 是否容易產生錯誤關係。
- 搜尋是否更容易定位。
- Context 是否能保持最小充分。
- 知識更新時是否容易維護。

只有完成這輪實測後，才決定「知識書」正式規格。

## 九、施工順序修正

正式順序改為：

```text
問題／需求

↓
比較成熟方案
↓

↓

↓

↓

```

其中「共同語義」等基礎治理規則仍然存在；此處修正的是「知識書具體形式」不能在沒有研究圖書館與檢索需求前提前固定。

## 十、結論

第一輪外部研究支持使用「內容、Metadata、Catalog、Index、Retrieval、Context」分層，而不支持把它們全部壓縮成同一種知識文件。

因此目前最合理的做法不是立即建立圖書館系統，也不是立即把知識全部原子化。

而是：

> 先研究圖書館與知識檢索方法 → 再用真實知識決定知識書的最適粒度與形式 → 再讓圖書館方案承接這個已驗證的知識結構。
