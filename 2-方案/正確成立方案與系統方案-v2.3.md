# 正確成立方案與系統方案 v2.3

日期：2026-09-17
狀態：【流程重建完成；已加入「問題→功能→知識」前置依賴；待下一自然案例驗證】

## 一、v2.3 修正原因

v2.2 已加入 Problem Intake Gate，但實際執行再次發現：即使先辨識問題，仍可能直接從「問題」跳到「方案／系統」，再次跳過「完整功能 → 功能所需知識 → 既有知識書檢查」。

因此 v2.3 把知識層提升為正式建立前的強制依賴，而不是 F10 之後才可能發生的選配工作。


## 三、建立前強制 Gate

### Gate A：問題成立

必須能回答：

- 真正問題是什麼？
- 問題與需求、假設、候選解法有何不同？
- 為什麼需要處理？

### Gate B：功能完整

必須列出問題完整處理所需的功能，而不是只列使用者想到的解法功能。

### Gate C：知識覆蓋

每項功能必須有：

```text
功能
→ 需要的知識
→ 既有知識書
→ 知識狀態
```

知識狀態至少為：

`已有／不完整／缺失／過時／矛盾`

### Gate D：研究與比較

所有實質缺口必須依需求進行：

- 外部方法研究
- 工具／產品／開源專案比較
- 標準／案例比較
- 優缺點與限制
- 失效模式／成本／適用條件

### Gate E：知識形成

可重複研究結果必須形成或更新正式知識書，不能只留在一次性討論或方案文件中。

### Gate F：既有能力判定

知識補齊後重新盤點：

- 既有知識
- 既有系統
- 既有方案
- 既有流程
- 既有工具

先判斷重用或修改，再判斷新系統。

### Gate G：建立必要性

只有證明既有能力不足，且新增能力具有獨立責任邊界與可驗證必要性，才能進入新系統建立。

### Gate H：方案必要性

只有多個系統需要形成固定目的組合，才進入正式方案建立。

## 四、LOCK / ALLOW

任一 Gate 缺少必要證據：

`LOCK`

不得進入下一級建立。

所有必要 Gate 完成：

`ALLOW`

才可進入建立規劃或正式施工。

## 五、建立規劃的定位

建立規劃不是正式方案。

規劃完成時必須明確標記：

```text
規劃狀態：【規劃完成】
方案建立狀態：【未建立】
方案完善狀態：【未完善】
```

並同步形成：

- 待辦
- 順序
- 依賴
- 前置條件
- 下一個可執行工作
- 正式施工入口

## 六、正式建立前固定警示

所有進入正式建立的 AI 必須看到：

> **施工入口警示：本文件的規劃完成不代表方案或系統已建立。進入施工時必須重新執行本流程，不能直接把規劃內容當成已確認架構。**

若標記仍為：

`【未建立】` 或 `【未完善】`

不得宣稱已建立或已完善。

## 八、回傳與狀態成本

本流程禁止把每個工具呼叫、檔案讀取、搜尋查詢都變成使用者可見狀態回傳。

採用四級：

- S0：微步驟，不回傳。
- S1：工作批次，只在完成有意義的批次時摘要。
- S2：Gate／階段 checkpoint，回傳必要狀態、阻塞與下一步。
- S3：重大狀態／新基準，完整同步。

狀態紀錄應記錄「決策、階段、阻塞、下一步」，而不是完整活動日誌。

## 十、下一次施工的強制起點

下一個新方案或系統需求出現時，不得從「建立規劃」直接開始。

必須先執行：

```text
新內容
→ 問題
→ 完整功能
→ 功能→知識
→ 知識書實查
→ 缺口
→ 外部研究／比較
→ 知識形成
→ 系統能力盤點
→ 系統／方案必要性
```

完成後才可建立規劃。

## 十一、不可宣稱事項

- 文件存在 ≠ 能力成立。
- 知識書存在 ≠ 本次功能已被知識覆蓋。
- 規則存在 ≠ AI 已經遵守規則。
- 系統存在 ≠ 系統被正確觸發。
- 規劃完成 ≠ 方案建立。
- 建立完成 ≠ 完善完成。
- 完善完成 ≠ 驗收完成。
- 驗收完成 ≠ 實戰驗證完成。
