## 一、文件目的

本文件是四個正式方案進入「創建階段」後的共同施工入口。

四個方案：

1. 整體資料治理方案
2. AI知識管理方案
3. 知識與資料迭代演化方案
4. 能力蒸餾與系統重構方案

本文件不取代四個方案本身，而是規定四個方案如何從「方案規劃」進入「功能 → 知識 → 系統 → 初步方案 → 實戰」的實際建立流程。

## 二、方案確認與創建的分界

方案確認 Gate 只要求驗收條件已經被定義，不要求實作或實戰已經完成。

### Gate 用語

```text
最小實作驗收方法已確認
實戰驗證驗收方法已確認
```

兩者分別表示：

- 已經知道最小實作完成後用什麼條件驗收。
- 已經知道進入真實工作後用什麼條件驗證與驗收。

不表示方案在 Gate 前已完成實作或實戰。

## 四、創建階段的硬性順序

不得直接由「方案概念」跳到建立系統。

必須先完成：

```text
功能
→ 知識需求
→ 外部研究／比較
→ 知識
→ 系統能力
→ 系統
```

其中「功能」只是需求單位，不等於系統數量。

一個系統可以承擔多個功能；一個功能也可能由多個既有系統共同完成。

## 五、外部研究要求

涉及實質設計的功能，應先搜尋成熟方法、產品、工具與案例。

比較至少回答：

```text
解決什麼問題？
核心方法？
輸入／輸出？
優點？
限制？
成本？
適用規模？
失效模式？
與本 Repository 既有能力是否重疊？
哪些可以採用？
哪些不能採用？
```

外部方法不是直接複製的規則，而是候選解法來源。

## 六、目前第一輪外部研究基準

### Software Catalog / System Catalog

Backstage 的 Software Catalog 將 ownership、metadata、lifecycle、dependency 與 relations 建模為可搜尋目錄，並把 System 作為較高層的抽象，用來隱藏內部實作細節。其文件也明確指出 Catalog 不應被視為所有即時資訊的唯一真實來源，而可作為組織與探索的集中入口。citeturn0search0turn0search2turn0search7

可作為「整體資料治理」與「系統身份／關係」功能的外部參考，但不直接複製其資料模型。

### Knowledge Base / Search

Atlassian Confluence 的 Knowledge Base 以標籤、搜尋與內容導覽支援知識發現，並提供進階搜尋與篩選；其文件強調使用者通常透過搜尋與主題導航找到內容，而不是只依賴樹狀目錄。citeturn1search5turn1search9

可作為「AI 知識管理」中的搜尋、定位、分類與知識入口設計參考。

### AI Management / Continuous Improvement

NIST AI RMF 將 AI 風險工作拆成 Govern、Map、Measure、Manage，並強調持續監測、測量、文件化與生命週期中的持續管理；ISO/IEC 42001 則以管理系統與持續改善為核心。這些可作為 AI 知識管理、驗證、回饋與治理功能的外部參考，而非直接照搬成四方案流程。citeturn1search0turn1search2turn1search3turn1search16

## 八、第一輪功能分析原則

上述功能全部屬「候選功能」。正式建立前逐項檢查：

```text
是否真的必要？
是否已有知識可以支撐？
是否已有系統能力？
是否與其他功能重複？
是否應由其他方案負責？
是否只是流程步驟而非獨立能力？
是否值得系統化？
```

因此不預設「一功能一知識」或「一功能一系統」。

## 九、四方案共同依賴關係

```text

        ↓

        ↓

        ↓                         ↓
知識與資料迭代演化 ←────────────┘
        ↓

        ↓

        ↓
新穩定基準
        ↓
回到正常迭代
```

方案之間共享資料與接口，但不得互相吞併全部責任。

## 十、目前施工階段

目前正式進入：

> **第一施工階段：四方案功能分析。**

本階段不進行大型系統建立。

完成全部功能分析後，才進入：

```text
功能 → 知識需求 → 外部研究與比較 → 知識建立
```

再進入系統組建。

## 十一、最小實作驗收與實戰驗收

兩者目前只建立「驗收方法」，不宣稱已完成。

### 最小實作驗收

至少需要能以一個真實但有界限的工作案例，完整走通方案所宣稱的核心流程，並能留下可重現的輸入、處理、輸出與判定證據。

### 實戰驗證驗收

至少需要在正常工作中自然觸發方案，產生實際執行與結果，並能比較預期與實際結果，確認方案是否真的改善工作，而不是只有文件流程能走通。

具體驗收條件將在各方案完成功能分析與知識建立後再細化，不在本階段預先虛構過度詳細的測試矩陣。

## 十二、禁止事項

1. 不因方案確認就直接建立完整系統。
2. 不把候選功能直接當正式需求。
3. 不把外部產品功能表直接複製成自己的架構。
4. 不因功能名稱相似就重複建立系統。
5. 不以文件完成代替實作驗收。
6. 不以模擬或設計代替實戰驗證。
7. 不因四個方案同時施工就把共同能力各自複製四份。
8. 不預先建立大型資料庫、知識圖譜或向量平台作為必要前提。

## 十三、下一步

按照以下順序施工：

1. 完成四方案功能逐項拆解。
2. 對每項功能判斷必要性與責任歸屬。
3. 建立功能 → 知識需求映射。
4. 對關鍵功能進行第二輪外部方法／產品／工具／案例比較。
5. 建立第一批正式知識。
6. 再進行功能 → 系統能力分析。
7. 建立最小系統。
8. 組建四方案初步實作。
9. 執行最小實作驗收。
10. 進入真實工作實戰。
11. 回寫結果並建立新基準。
