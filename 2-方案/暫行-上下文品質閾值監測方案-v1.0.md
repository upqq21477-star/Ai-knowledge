# 暫行方案：上下文品質閾值監測

版本：v1.0
類型：暫行方案（Temporary / Experimental）
狀態：【暫時使用；可隨時停用／刪除】
建立日期：2026-09-19

## 1. 目的

在不讓每次對話都付出完整品質審計成本的前提下，於 Context 風險開始升高時，逐步啟動：

- 語意失真檢查
- 幻覺／Unsupported Claim 檢查
- 路由錯誤檢查
- 執行／驗證異常檢查

本方案是實驗性成本控制方案，不是正式 Skill，不修改正式 Skill 邊界。

## 2. 核心原則

前幾輪完全不檢測。

之後以 Context 負載為主要閾值，以高風險任務事件提前觸發。

正常情況只做輕量檢查；只有發現異常才升級深度診斷。

不在單輪直接宣稱「幻覺率／失真率」等統計率；單輪只記錄 PASS / SUSPECT / FAIL。累積樣本後才計算比例。

## 3. 初始閾值（待實測校正）

| 階段 | 初始條件 | 動作 |
|---|---|---|
| S0 | 前 5 輪 | 完全不檢測 |
| S1 | 5 輪後且 Context < 25% | 維持不檢測 |
| S2 | Context 25–40% | 輕量品質檢查 |
| S3 | Context 40–60% | 標準品質檢查 |
| S4 | Context 60–75% | 深度品質檢查 |
| S5 | Context > 75% | 完整診斷；必要時 Context 重整／壓縮 |

百分比是目前的初始假設，不是正式結論。

## 4. 提前觸發條件

即使尚未達 Context 閾值，出現以下任一情況可提前進入 S2 以上：

- Context 快速增長
- 大量文件／資料同時處理
- 跨 Skill 任務
- 跨多個正式文件同步修改
- 方案比較／對照實驗
- 需要精確數據或版本狀態
- 新流程第一次實際執行
- 使用者指出可能存在錯誤
- 發生 Failure
- 發生 Context、Routing、Skill、Provider、Execution、Verification 任一異常

## 5. 單輪檢查輸出

最低輸出：

```
Quality Check
Distortion: PASS / SUSPECT / FAIL
Hallucination: PASS / SUSPECT / FAIL
Routing: PASS / SUSPECT / FAIL
Execution: PASS / SUSPECT / FAIL
Verification: PASS / SUSPECT / FAIL
```

只有 SUSPECT / FAIL 才進一步 Diagnosis。

## 6. 累積統計

單輪不計「率」。

累積到足夠樣本後，再統計：

- Semantic Distortion Rate
- Hallucination / Unsupported Claim Rate
- Routing Error Rate
- Execution Failure Rate
- Verification Failure Rate
- Context-related Failure Rate

建議以 20 次作為第一次觀察窗口，50 次作為正式比較窗口；實際窗口可由 FIELD 證據調整。

## 7. 成本控制目標

本方案的目的不是追求「檢測越多越好」，而是：

```
風險低 → 不花品質審計成本
風險升高 → 增加檢測
發現異常 → 深度診斷
問題解決 → 降回低成本模式
```

初始成本目標：

- S0/S1：接近 0 額外品質檢查成本
- S2：低成本
- S3：中低成本
- S4：中成本
- S5：高成本，但只在高風險 Context 使用

實際 Token / 時間成本必須由 FIELD 測量，不以估算值作正式證據。

## 8. 與方案對照組的關係

本方案可使用既有：

`2-方案/上下文成本與可靠性控制方案-系統調用對照組-v1.0.md`

進行 Context 預算、可靠性與輸出失真／幻覺檢查。

本方案本身不改變正式組／對照組身份。

若進行方案比較，必須明確標示正式組與對照組，避免路由身份混淆。

## 9. 與現有 Skill 的關係

暫不建立新 Skill。

目前只視為方案層的實驗機制，並觀察：

- Context管理 Skill 是否已能承擔
- 證據驗證診斷 Skill 是否已能承擔
- Agent 是否只需在事件觸發時調用
- 是否存在足以證明獨立 Skill 責任邊界的實際證據

只有 FIELD 證據證明現有 Skill 無法合理承擔，才進入 Skill Classification 的 NEW 判斷。

## 10. 停用／刪除條件

本方案可隨時停用或刪除。

停用後：

- 不再依 Context 閾值觸發品質檢查
- 不影響正式 Skill
- 不影響正式 Solution
- 不影響既有 Problem Registry
- 歷史 FIELD 數據仍可保留作為驗證證據

若實測證明成本過高、效果不足、與既有機制重複，直接標記 RETIRED 或刪除，不建立替代 Skill。

## 11. 驗證方式

邊使用邊驗證，不先宣稱有效。

至少觀察：

1. 閾值前是否真的可以維持低成本。
2. Context 接近閾值後是否能捕捉異常。
3. 是否過早觸發造成不必要成本。
4. 是否過晚觸發造成失真／幻覺漏檢。
5. S2→S3→S4→S5 是否真的具有成本／風險差異。
6. 品質檢查是否反而造成新的語意失真或路由錯誤。
7. 停用後正式系統是否能正常運作。
