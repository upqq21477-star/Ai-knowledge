# 正確成立方案與系統方案 v2.0

日期：2026-09-17
前版：`2-方案/正確成立方案與系統方案-v1.0.md`
狀態：【重建中；建立前研究與執行 Gate 已重新設計】

## 一、重建原因

v1.0 已經列出完整施工方向，但實際工程再次發生同類錯誤：

```text
已有規則
＋
已有建立前系統
＋
已有建立前原則
↓
AI 仍直接進入文件／系統建立
```

因此問題不是「缺少更多文字」，而是：

```text
規則存在
≠
行動前一定檢查
```

本版重建的核心不是增加更多文件，而是把方案建立流程變成「行動前 Gate + 工作批次 + 階段 Checkpoint + 最小回報」的實際施工機制。

## 二、完整功能模型

原 v1.0 已明確定義 F01～F19，本版完整保留並重新分組。

### A. 方案成立與研究

F01 方案成立：確認問題／需求值得建立方案，定義目的與邊界。

F02 方案功能分析：完整列出方案需要的功能，不從預想系統反推方案。

F03 現有能力盤點：盤點既有知識、系統、方案、軟體／工具與流程。

F04 搜尋研究方案調用：調用既有搜尋研究能力，不重新發明搜尋流程。

F05 搜尋研究方案健康檢查：重要研究時確認搜尋能力本身仍能取得需要的資料。

F06 外部方法研究：研究成熟方法、流程、架構與實務。

F07 外部產品／工具／開源專案比較：比較真實能力，不只比較概念。

F08 外部研究／標準／案例比較：必要時納入研究、標準、規範與實際案例。

F09 採用判斷：根據問題、證據、限制、成本與既有架構決定採用／修改／不採用。

### B. 知識與系統設計

F10 知識書建立：把可重用研究結果形成知識，建立與功能的對應。

F11 系統需求判定：判斷哪些功能需要系統，以及既有系統是否已能承擔。

F12 系統建立入口 Gate：在任何正式系統建立前檢查必要條件。

F13 系統建立：只有通過 Gate 才建立候選系統。

### C. 實際驗證

F14 系統觸發驗證：確認真實工作情境出現時能被正確觸發。

F15 系統執行驗證：確認觸發後真的執行定義流程。

F16 系統結果驗證：確認輸出／決策／狀態變更符合預期。

F17 方案功能覆蓋檢查：檢查功能是否都有責任歸屬，是否有缺口／重複。

F18 方案整體驗證：以完整案例驗證方案能否完成原始目的。

F19 方案回饋與迭代：把結果回饋到方案、知識、系統或研究能力。

### D. v2.0 新增的流程控制功能

F20 建立前 Preflight：任何新方案／核心系統建立意圖出現時，先檢查目前 Gate。

F21 Gate 鎖定：核心條件未完成時禁止進入正式建立動作。

F22 工作批次管理：把多個微步驟組成一個可管理的 Batch，避免每一步都產生狀態紀錄。

F23 Checkpoint 管理：只在有工程意義的階段點更新狀態。

F24 狀態壓縮：狀態只保存最小充分資訊，不複製研究全文。

F25 回傳分層：區分 AI 內部工程紀錄與使用者可見回報。

F26 Context／成本控制：限制狀態、交接與研究摘要的重複載入，控制 AI 上下文成本。

F27 決策／證據追溯：重大決策可追溯到研究、比較、討論、結果與版本。

F28 失敗回流：FAIL／PARTIAL 必須回到診斷與修正，而不是直接宣稱完成。

F29 停止邊界：達到結構完整條件後停止無限擴充，進入實測。

F30 新基準建立：實測完成後形成新的穩定基準。

## 三、正式施工主流程

### Phase 0：候選，不建立

```text
新構想／新需求
↓
候選方案標記
↓
建立工程狀態
↓
進入建立前研究
```

此階段不得建立正式方案核心系統。

### Phase 1：問題與功能

```text
問題確認
↓
目標確認
↓
範圍／邊界
↓
完整功能清單
↓
驗收目標
```

Checkpoint：功能模型完成。

### Phase 2：既有能力盤點

```text
功能
↓
需要哪些知識
↓
需要哪些系統
↓
現有能力盤點
↓
重複／缺口／責任衝突
```

結果必須回答：

```text
沿用？
完善？
重構？
整合？
拆分？
新增？
```

Checkpoint：既有能力盤點完成。

### Phase 3：外部研究與比較

```text
研究問題
↓
外部方法
↓
外部產品／工具／開源專案
↓
研究／標準／案例
↓
比較
↓
限制／成本／適用條件
↓
漏洞與失效模式
```

不是搜尋一次就結束；若候選架構改變且會影響研究結論，回到必要研究。

Checkpoint：外部研究／比較完成。

### Phase 4：反方案檢查

正式建立前必須回答：

1. 現有方案能否處理？
2. 現有系統能否處理？
3. 是否只需完善既有系統？
4. 是否只需增加小系統？
5. 是否只是共同能力缺口？
6. 是否只是狀態／索引／流程問題？
7. 新方案是否會產生新的重複管理？
8. 是否增加協調成本大於價值？

若不需要新方案：停止方案建立，轉交適當責任層。

Checkpoint：反方案判定完成。

### Phase 5：候選架構與討論

```text
候選架構
↓
責任分配
↓
系統／小系統邊界
↓
觸發條件
↓
輸入／輸出
↓
依賴／接口
↓
使用者討論
↓
修正
```

若重大修正改變核心假設，重新進入必要的研究／比較。

Checkpoint：候選架構確認。

### Phase 6：方案確認 Gate

只有全部核心條件通過，才進入正式建立：

```text
問題確認                 PASS
目標確認                 PASS
功能清單                 PASS
既有能力盤點             PASS
外部研究                 PASS
外部比較                 PASS
優缺點／限制             PASS
漏洞攻擊                 PASS
反方案檢查               PASS
候選架構                 PASS
討論／修正               PASS
方案邊界                 PASS
系統／小系統邊界         PASS
責任／觸發歸屬           PASS
最小驗證方法             PASS
```

任一核心項目未完成：

```text
LOCK
禁止正式建立
```

### Phase 7：正式方案建立

通過 Phase 6 後才：

```text
建立正式方案
↓
建立／完善必要知識
↓
建立／完善必要系統
↓
統整系統責任與接口
↓
方案最小實作驗收
```

「建立完成」不等於「實戰完成」。

### Phase 8：實際驗證

```text
真實工作情境
↓
觸發
↓
執行
↓
Expected / Actual
↓
結果驗證
↓
PASS / PARTIAL / FAIL
```

FAIL：進入診斷／問題解決／修正。

PARTIAL：確認缺口後決定繼續驗證或回到結構修正。

### Phase 9：方案回饋與新基準

```text
結果
↓
功能覆蓋重新檢查
↓
缺口責任判定
↓
方案／知識／系統／研究能力更新
↓
再次驗證
↓
新基準
```

## 四、建立前行動鎖定機制

任何 AI 準備執行下列動作：

- 建立新方案
- 建立方案核心系統
- 建立方案核心知識書
- 大型重製／重構

都必須先執行一次 Preflight：

```text
讀取目前候選狀態
↓
讀取方案建立 Gate
↓
檢查功能是否完成
↓
檢查既有能力是否完成
↓
檢查外部研究／比較是否完成
↓
檢查反方案與漏洞分析
↓
檢查討論／修正
↓
檢查最小驗證方式
```

結果只有兩種：

```text
LOCK
或
ALLOW
```

不能由「AI 覺得已經差不多」自行跳過。

## 五、研究資料與方案文件的分離

不得把所有研究結果塞進方案主文件。

```text
研究文件
= 深度證據、比較、來源、詳細分析

知識書
= 可重用知識

方案文件
= 決策、架構、責任、流程、適用條件、驗證方式

工程狀態
= 現在做到哪裡

待辦
= 下一步做什麼

交接
= 新 AI 必要背景
```

## 六、狀態紀錄：不採用逐步記錄

### S0 微步驟

例如搜尋一個網站、讀一個文件、改一句文字。

```text
狀態：不記錄
交接：不更新
使用者回報：不回報
```

### S1 工作批次

例如「完成一輪外部方法研究」或「完成一輪既有系統盤點」。

```text
批次完成時：更新一次狀態
通常不更新交接
不要求立即使用者回報
```

### S2 Gate Checkpoint

例如功能盤點完成、研究完成、方案確認、系統建立完成只剩整體驗收。

```text
更新工程狀態
同步必要待辦
符合交接條件則更新交接
使用者回報一次摘要
```

### S3 重大狀態／新基準

例如重大架構變更、方案確認、PASS／FAIL 改變主線、新 AI 接手、新基準。

```text
狀態
＋待辦
＋交接
＋必要索引
＋使用者完整摘要
```

## 七、使用者回傳頻率

預設採「階段式回傳」，不是「步驟式回傳」。

```text
工具操作 × N
↓
內部完成一個工作批次
↓
1 次摘要
```

預設規則：

- 每個 Gate 最多一次主要回報。
- 一個工作批次最多一次摘要。
- 重大阻塞立即回報。
- 重大決策立即回報。
- 微步驟不回報。
- 純工具呼叫不回報。

因此即使一個 Gate 內執行數十次搜尋、讀取與比較，也不應產生數十次使用者訊息。

## 八、Context／算力控制

狀態紀錄的目的不是保存每一步，而是讓下一次 AI 能快速恢復。

因此採：

```text
深度研究保留在研究文件
↓
狀態只保存摘要
↓
交接只保存最小充分恢復上下文
↓
待辦只保存可執行工作
```

禁止：

- 把完整研究全文複製到狀態。
- 每個工具呼叫寫一次紀錄。
- 每個搜尋結果都寫入交接。
- 每個小修改都產生新驗收案例。
- 每個狀態更新都重新讀取全部歷史。

## 九、記錄觸發條件

### 必記

1. 新正式決策。
2. 新方案確認。
3. 責任／接口重大變更。
4. 系統／方案進入「建立完成，只剩整體驗收」。
5. PASS／PARTIAL／FAIL 改變工程主線。
6. 重大阻塞。
7. 新 AI 即將接手。
8. 新基準建立。
9. 重大資料格式／架構重製。

### 通常不記

1. 單次搜尋。
2. 單一文件閱讀。
3. 微小文字修正。
4. 同一 Gate 內的重複分析。
5. 不改變工程狀態的普通討論。

## 十、失敗與回復

任何 Gate FAIL 不直接進入下一 Gate。

```text
FAIL
↓
記錄原因
↓
判斷責任層
↓
回到對應 Phase
↓
修正
↓
重新檢查 Gate
```

已完成的研究、比較與文件不因 FAIL 消失；它們作為歷史證據保留。

## 十一、完成層級

```text
L0 構想
L1 候選
L2 建立前研究完成
L3 方案確認／允許建立
L4 正式方案建立
L5 系統最小實作驗收
L6 真實工作觸發／執行驗證
L7 方案整體實測
L8 新基準
```

不得把較低層級結果宣稱為較高層級完成。

## 十二、停止邊界

當以下成立：

```text
主要功能完成責任分配
必要知識完成／缺口已明確
必要系統完成／缺口已明確
責任與接口統整
正常成功路徑形成
FAIL 回流閉環形成
最小實測方法確認
阻塞性架構缺口已處理
```

就停止本輪結構性擴充，進入實際驗證。

不能因為「還可以增加功能」而無限施工。

## 十三、外部研究持續性

方案成立後仍可能因外部重大變化重新開啟研究：

```text
重大模型更新
重大新技術
同類方案重大突破
核心假設被新證據推翻
實際工作出現重大架構缺口
```

一般外部新資訊不自動觸發方案重建。

## 十四、與既有系統的關係

本方案使用而不取代：

- 新方案建立前研究與確認系統
- 方案管理系統
- 小系統建立與生命週期管理系統
- 搜尋／研究能力
- 知識管理能力
- 問題解決能力
- 工程運作與持續改進方案

本方案負責把它們串成「正確建立方案」的完整施工流程。

## 十五、第一個真實驗證案例

不製造額外測試案例。

下一次自然出現新方案構想時，直接用本流程執行。

若出現「AI 想直接建立」的情況，Preflight 必須先攔截。

第一個驗證重點不是文件是否漂亮，而是：

```text
沒有完成 Gate
→ AI 是否真的不能直接建立
```

## 十六、完成條件

本方案至少需要證明：

1. 真實新方案構想能被候選化。
2. 建立前研究真的發生。
3. 外部比較真的發生。
4. 漏洞與反方案檢查真的發生。
5. 未確認前正式建立真的被阻止。
6. 確認後才允許建立。
7. 狀態不是每一步都記錄，而是在批次／Gate／重大事件更新。
8. 使用者不需要接收每一個內部操作。
9. 新 AI 可以從最小狀態／交接恢復。
10. 方案最終能以真實工作完成端到端驗證。

## 十七、目前狀態

```text
v1.0：歷史版本，保留
v2.0：重建中
外部研究與比對：完成第一輪
功能模型：F01～F30
建立前 Gate：重新設計
狀態頻率模型：S0～S3
使用者回傳模型：階段式
Context／算力控制：納入
真實案例驗證：待執行
```

下一步不是建立新的系統文件，而是依 v2.0 的 Phase 0～6 重新處理下一個真正的方案構想，驗證 Preflight 是否能阻止流程再次被跳過。
