# P0.5-03-6 方案二 B1–B16 × 既有系統責任逐項稽核 v1.0

日期：2026-09-18
狀態：【第一輪完成；發現既有矩陣需修正；待第二輪系統狀態與責任驗證】

## 一、稽核目的

本文件承接 P0.5-03-5，專門對方案二 B1–B16 重新做 System Responsibility 稽核。

本輪特別修正一個前輪風險：

> 不能只拿「三個核心系統」與 B1–B16 比較，然後忽略 Repository 中已存在的專責小系統。

Repository 已存在至少：

- AI上下文與交接系統
- 資料探索與搜尋系統
- 來源與證據分析系統
- 研究證據與採用判斷系統
- AI知識庫基本運作系統
- 問題解決系統
- 實測結果回寫檢查小系統
- 以及搜尋研究方案所記錄的其他既有能力

因此本輪不能把「三核心系統」當成唯一 System Universe。

## 二、核心修正

前一輪矩陣把部分 B 功能過早概括為：

「AI知識管理系統承擔」

這個表述需要降級為：

「方案二由 AI知識管理系統負責方案級組合／接口，但實際可重用能力可能由多個專責 System 承擔。」

這是重要修正。

正確模型：

```
方案二 B1–B16
        │
        ├─ AI知識管理系統：方案級任務流程／組合
        │
        ├─ 資料探索與搜尋系統：B3/B4
        ├─ 來源與證據分析系統：B6
        ├─ 研究證據與採用判斷系統：部分 B7／B13 等候選能力
        ├─ AI上下文與交接系統：B8/B9/B10
        ├─ AI知識庫基本運作系統：B11/B14/B15 等基礎運作
        ├─ 問題解決系統：B16 後續解法流程
        └─ 驗證／回寫小系統：B12 的部分檢查責任
```

因此「System Responsibility」與「Plan Responsibility」必須同時存在。

## 四、最重要的責任分層

### B1–B2

AI知識管理系統可以承擔任務理解與任務拆解的可重用能力，但 B2 發現能力缺口時，必須進入問題解決流程。

因此：

```
B2
≠ 問題解決系統

B2
→ 發現問題
→ 問題解決系統
```

### B3–B5

這三項不能被稱為「AI知識管理系統自己的搜尋系統」。

正確關係：

```
B3/B4
→ 資料探索與搜尋系統

B5
→ 搜尋研究／外部研究能力

AI知識管理
→ 決定何時需要這些能力並組合結果
```

因此這裡已經證明「方案二功能」與「單一 System」不是一對一。

### B6–B7

B6 有非常清楚的專責 System：

```
來源與證據分析系統
→ Source / Claim / Evidence 關係
```

B7 則不能直接吞進 B6。

因為 Repository 同時存在「研究證據與採用判斷系統」，其定位明確包含情境適用性與本次研究採用方式判斷。

所以 B7 是重要的 Capability Boundary，而不是簡單的 B6 擴充。

### B8–B10

這是另一個明確的專責 System 群：

```
B8 → Context Selection
B9 → Context Assembly
B10 → Memory / Current State Recognition
```

AI上下文與交接系統已直接承擔這些能力。

但 B10 使用的是方案一共同 State / Version / History 語義。

因此：

> Context System 負責辨識與組裝；治理系統負責共同語義。

不能建立第二套 State System。

### B11–B12

B11 同時涉及：

- AI知識管理
- AI知識庫基本運作

B12 又涉及：

- AI知識管理
- 實測結果回寫檢查
- 後續工作觸發式驗證等既有驗證能力

因此 B11/B12 是典型的「方案功能由多個 System 組合完成」。

### B13–B15

這三項是目前責任邊界較容易混亂的區域。

B13 不是單純「保存一個 confidence」。

它依正式整合文件需要保存 Unknown、Unverified、Conflicting Evidence、Conditional、Time-sensitive 等狀態及原因。

這需要：

- Evidence 語義
- State 語義
- 保存能力
- AI 任務流程

共同配合。

B14 則明確與 AI知識庫基本運作系統重疊。

B15 更是跨方案接口：

```
工作結果
↓
Feedback
↓
Knowledge / Problem / Change / Distillation Candidate
```

因此 B15 不應被某一 System 獨占。

### B16

B16 是目前最清楚的「介面型責任」。

```
B12 FAIL
↓
B16 Failure Diagnosis
↓
問題解決系統
↓
候選解法
↓
修正
↓
B12 Revalidation
```

問題解決系統不是 B16 本身。

B16 是診斷與路由；問題解決系統負責後續候選解法與實測。

## 五、對前一輪矩陣的正式修正

P0.5-03-5 的以下概括需要視為「第一輪高階矩陣」，不能作為最終逐項責任證據：

> B1–B16 = AI知識管理 System 承擔主要工作能力。

更精確的 Canonical 解讀是：

> B1–B16 是方案二的正式 Plan Responsibility；AI知識管理系統負責方案級任務管理與能力組合，但其中大量具體能力由 Repository 中不同專責 System、Capability 與 Process 提供。

因此 P0.5-03-5 不撤銷，保留其高階責任分層；本文件作為 B1–B16 的細化修正。

## 七、重要架構結論

本輪可以確認一個非常重要的原則：

> **正式方案功能不應被直接轉換成 System 清單。**

方案二真正的結構比較接近：

```
                 方案二：AI知識管理
                         │
                  Plan Responsibility
                         │
        ┌────────────────┼────────────────┐
        ↓                ↓                ↓
   任務／組合        資料取得／判斷       執行／驗證／回饋
        │                │                │
        ↓                ↓                ↓
 AI知識管理      搜尋／證據／Context     基本運作／問題解決
   System          專責 Systems          專責 Systems
```

這比「B1–B16 → AI知識管理系統」更符合 Repository 實際證據。

## 八、仍未證明的事項

以下仍不能宣布：

1. 上述每個 System 已完整實作 B 功能。
2. 所有 System 都應永久保留。
3. 研究證據與採用判斷系統必須永久獨立。
4. 基本運作系統必須成為第四核心 System。
5. B13 是否值得形成獨立 Capability/System。
6. B12 的多個驗證能力是否最終應收斂。
7. 某個 System 名稱存在就等於它已承擔完整 B 功能。

原因是多數 System 文件仍處於建立中／待實際任務驗證。

## 九、對後續 Blueprint Mapping 的限制

目前不得把：

```
B功能 → System 文件存在
```

直接寫成：

```
B功能 → System 已完成
```

Blueprint 應至少能區分：

- Referenced
- Partial
- Candidate
- Canonical Responsibility
- Implemented
- Verified
- FIELD-PASSED
- Derived Mapping Only

在本輪之前，部分 Mapping 使用「已有相關能力」描述，容易被後續 AI 誤讀成「已完成」。

因此後續 Mapping 更新必須增加責任證據與狀態語義。

## 十、結論

本輪 B1–B16 稽核得到的核心結果：

**第一，方案二不是單一 System 的同義詞。**

**第二，三核心 System 不是 B 功能唯一承擔者；Repository 中已存在多個專責 System。**

**第三，AI知識管理系統的正確定位應是方案級 AI 工作能力與多個專責能力的組合／接口，而不是吞掉所有 B 功能。**

**第四，B3/B4、B6、B8/B9/B10、B16 已有明確專責邊界。**

**第五，B7、B12、B13、B15 是目前最值得繼續做 Capability-level Boundary Audit 的區域。**

**第六，不能因 Mapping 存在就宣告 System Responsibility 已成立，更不能宣告實作完成。**

本文件不修改 B1–B16 正式功能，不新增正式方案，不新增 System ID。
