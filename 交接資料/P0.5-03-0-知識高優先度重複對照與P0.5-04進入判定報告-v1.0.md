## 二、判定規則

依 P0.5 基線重建規範：

- 檔案較新不等於內容較正確。
- 版本不同不等於衝突。
- 內容高度重疊不等於可以直接刪除。
- 只有在語義、責任與後續採用關係足夠明確時，才可進入蒸餾／合併／歷史化。
- 不確定時保留並標記 REVIEW。
- P0.5-03 負責盤點與判定；P0.5-04 才負責實際蒸餾、重製、合併或歷史化。

## 三、第一組：資料狀態與生命週期原理 vs 資料狀態模型

### A. 資料狀態與生命週期原理

目前文件狀態：

【初版建立；待三方案實際建立後驗證】

主要責任：

- 定義「內容、版本、時間、狀態」的區分。
- 提出最小狀態集合：
  草稿、待確認、已採用、歷史、廢棄。
- 明確區分狀態與可信度。
- 描述一般生命週期。
- 要求狀態變更必須有依據。
- 定義「目前」不能只由 Active 判定，而要考慮狀態、版本、有效時間、適用範圍、適用條件。
- 定義治理、知識管理、資料演化、驗證的責任邊界。
- 明確反對過早建立複雜狀態機、狀態引擎與自動判斷。

### B. 資料狀態模型

目前文件狀態：

【建立中】

主要責任：

- 建立最小資料狀態模型。
- 狀態集合為：
  待確認、已確認、建立中、歷史、已失效、已否決。
- 特別區分文件狀態、內容狀態、採用狀態。
- 描述不同類型資料的狀態轉換。
- 加入 AI 輸出的特殊狀態流程。
- 加入搜尋時辨識目前／歷史／待確認／否決的要求。
- 說明狀態判定應同時考慮時間、內容、決策與適用條件。
- 同樣反對複雜狀態資料庫與全自動狀態推理。

### C. 共同語義

兩份文件都明確支持：

內容 ≠ 狀態

資料存在 ≠ 目前有效

資料較新 ≠ 一定正確

狀態變更需要依據

歷史資料不應直接視為目前規則

目前不建立複雜自動狀態機

因此，這不是兩個完全獨立的知識主題，而是高度重疊的狀態治理／模型知識。

### D. 實質差異

兩份文件的狀態集合並不相同：

第一份：
草稿、待確認、已採用、歷史、廢棄

第二份：
待確認、已確認、建立中、歷史、已失效、已否決

這些差異不能直接當作錯誤，因為它們可能反映不同抽象層：

- 「建立中」偏文件／工作進度。
- 「已確認」偏內容驗證狀態。
- 「已採用」偏採用／治理狀態。
- 「已否決」偏決策結果。
- 「已失效」偏適用性結果。
- 「歷史」偏時間與目前採用邊界。

因此目前最大的問題不是「哪一份正確」，而是兩份文件尚未把「單一狀態欄位」與「多維狀態」的關係完全統一。

### E. 判定

這兩份文件：

- Duplicate：HIGH
- Semantic overlap：HIGH
- Direct contradiction：未證明
- Evolution relationship：HIGH
- Canonical relationship：尚未完全確定
- Distillation candidate：HIGH

暫不刪除任何一份。

### F. P0.5-04 必須保留的內容

若後續進行蒸餾，至少必須保留：

1. 狀態不是內容、版本或可信度。
2. 「目前」不是單一狀態名稱，而是結合狀態、版本、時間、適用範圍與條件的工作判定。
3. AI 輸出預設為候選內容，不直接成為確認知識。
4. 文件狀態、內容狀態、採用狀態可以不同。
5. 已否決資料具有防止重複研究的價值。
6. 歷史與已失效需要有清楚語義。
7. 狀態變更必須有證據、比較、驗證或決策依據。
8. 不因檔案修改或時間較新而自動改變知識真實性。
9. 暫不建立複雜狀態機或全自動狀態推理。

### G. 進入 P0.5-04 的前置問題

在真正改寫前，仍需確認：

- 最終狀態模型是否採「多維狀態」而非把所有概念塞入單一枚舉。
- 「已採用」與「已確認」是否需要分層。
- 「歷史」與「已失效」的關係。
- 「草稿／建立中」屬文件工作狀態還是知識狀態。
- 「已否決」是否作為決策結果維度。
- 三方案實際案例是否會支持這個模型。

結論：已足以列為 P0.5-04 HIGH 蒸餾候選，但不宜在沒有統一狀態語義前直接刪除或合併。

## 四、第二組：觸發條件管理與啟動保險原理 v1.0 vs 無版本文件

### A. v1.0 文件

主要內容：

- Trigger 是第二層啟動保險，而不是主要啟動源。
- 命中不等於啟動。
- 確認狀態後才補啟動。
- 不確定不擴大。
- Event ID → Trigger ID → System ID → 處理狀態的最小安全模型。
- 分析二次啟動、重入、循環觸發、多重匹配、狀態不明。
- 明確列出自然案例驗證要求。

### B. 無版本文件

主要內容與 v1.0 高度重疊，但增加：

- 啟動保險產生背景。
- 冪等性（Idempotency）說明。
- 最小處理狀態集合。
- 外部方法比較。
- Backstage Software Catalog、Kubernetes Controller 等參考。
- 更完整的禁止事項。
- 明確要求五種自然工作案例驗證。

### C. 判定

兩份文件核心定義幾乎相同。

無版本文件並非單純複製，而是後續內容擴充：

v1.0：
較早的核心原理草稿

無版本：
在相同核心上加入實際架構邊界、冪等性、外部方法參考、禁止事項與更完整驗證要求

因此：

- Duplicate：HIGH
- Semantic overlap：VERY HIGH
- Direct contradiction：未發現
- Evolution relationship：HIGH
- v1.0 是否為前版：高度可能
- 無版本文件是否較完整：就目前內容觀察，是
- Distillation candidate：HIGH

這是推論：依文件內容的完整度、相同核心定義與新增段落判斷，無版本文件很可能是 v1.0 的後續修訂／擴充版本；但僅憑兩份文件本身，尚不能把「版本演化」當成已被正式紀錄的事實。

### D. P0.5-04 建議保留內容

應保留：

1. Trigger 是第二層保險，不是第一啟動源。
2. Trigger 命中 ≠ 立即啟動。
3. 必須檢查目標系統目前處理狀態。
4. 防止二次啟動、重入、循環觸發、多重匹配。
5. 不確定時不擴大啟動。
6. Event ID / Trigger ID / System ID 與最小必要處理狀態。
7. 不把 Trigger Registry 變成中央執行引擎。
8. 不建立大型事件總線作為前提。
9. 必須用自然工作案例驗證，而不是只靠文件內推導。
10. 外部方法只能作為參考，不代表本專案採用完整外部架構。

### E. 判定

目前不應把 v1.0 與無版本文件當成兩套獨立原理。

較合理的 P0.5-04 候選處置是：

「建立一份蒸餾後的現行原理文件；保留 v1.0 作為歷史演化證據；無版本文件作為主要內容來源之一。」

但這只是 P0.5-04 候選處置，不是本輪已執行的遷移決策。

## 五、兩組資料的共同問題

兩組文件都出現相同系統性現象：

1. 知識文件在建立過程中先形成多份候選稿。
2. 後續文件吸收前稿並增加細節。
3. 檔名版本標記沒有完全反映實際演化。
4. 文件內部狀態仍保留「候選／建立中／待驗證」。
5. 因此不能單純用檔名排序決定 Canonical Source。

這也是 P0.5-03 必須先於 P0.5-04 的直接原因。
