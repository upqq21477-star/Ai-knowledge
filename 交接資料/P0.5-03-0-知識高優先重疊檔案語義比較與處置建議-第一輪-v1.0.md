## 三、第一組：資料狀態與生命週期原理 ↔ 資料狀態模型

### 3.1 語義比較
資料狀態與生命週期原理的責任偏向共同狀態語義與治理邊界：內容、版本、時間、狀態分離；狀態不是可信度；文件修改不等於知識更新；目前判定需考慮有效時間、適用範圍與條件；並限制過早建立複雜狀態機。

資料狀態模型則把狀態放入更新與採用場景，增加文件狀態、內容狀態、採用狀態的區分，以及已否決、已失效、AI 輸出候選狀態、搜尋後狀態辨識與狀態判定依據。

因此目前最合理的關係是：前者提供共同狀態語義與治理原理，後者提供更新／資料演化情境下的具體模型。這是語義比較結果，不是依目錄位置推定。

### 3.2 必須保留
前者必須保留：內容／版本／時間／狀態分離、狀態不等於可信度、文件修改不等於知識更新、目前狀態的適用條件、四方責任邊界、避免過早建立複雜狀態引擎。

後者必須保留：文件／內容／採用三種狀態維度、已否決的獨立語義、歷史與已失效的區分、AI 輸出預設為候選、六項狀態判定依據、搜尋結果的狀態辨識、最新文件不等於最新有效內容。

### 3.3 衝突判定
兩份文件的狀態集合不同，但目前不足以判定直接衝突。前者使用草稿／待確認／已採用／歷史／廢棄；後者使用待確認／已確認／建立中／歷史／已失效／已否決。部分名稱可能位於不同層級，例如建立中主要描述工作進度，不能直接視為草稿；已否決也不能直接等同廢棄。

結論：存在模型不一致風險，但沒有足夠證據判定其中一份錯誤或取代另一份。

### 3.4 P0.5-04 建議
列為 HIGH 蒸餾候選，但暫不合併。後續需要正式決定共同狀態語義、文件／內容／採用的層級、歷史／已失效／已否決／廢棄的邊界，以及目前狀態與狀態名稱的關係。兩份原始文件目前均保留。

## 四、第二組：觸發條件管理與啟動保險原理 v1.0 ↔ 無版本

### 4.1 語義比較
兩份文件均把 Trigger 定義為第二層啟動保險，而不是第一啟動源；均要求命中後先確認目標系統狀態；均處理二次啟動、重入、循環觸發、多重匹配與不確定狀態；均提出 Event ID、Trigger ID、System ID 與處理狀態的最小安全閉環；均禁止把 Trigger Registry 變成中央執行引擎；均要求自然工作案例驗證。

無版本文件在此核心上增加了冪等性、至少一次事件傳遞背景、最小處理狀態集合、Kubernetes Controller 與 Backstage Software Catalog 的外部方法比較，以及更完整的禁止事項。

因此兩者目前不是不同責任的兩個主題，而是高度重疊的同一知識演化鏈。

### 4.2 必須保留
共同核心全部保留：第二層保險、命中不等於啟動、狀態確認、不確定不擴大、重複／重入／循環／多重匹配防護、最小識別資料、窄責任邊界、自然案例驗證。

無版本文件的新增價值也必須保留：冪等性、最小處理狀態、外部方法依據、明確禁止事項。

v1.0 文件的短版核心安全閉環與五種驗證情況同樣應保留；若後續蒸餾，應吸收而不是丟失。

### 4.3 衝突判定
目前沒有發現核心規則互相矛盾。差異主要是完整度與表述深度。

但是不能只因無版本檔內容較完整，就直接宣告它是正式最新版。需要版本／決策紀錄或後續採用證據確認演化關係。

### 4.4 P0.5-04 建議
列為 HIGH 蒸餾／歷史化候選。若後續確認無版本檔確為 v1.0 的後續修訂，則可將共同核心與新增有效內容蒸餾至單一正式知識文件，舊版作為歷史演化證據保留。

在確認前，兩份文件均維持 REVIEW / KEEP。
