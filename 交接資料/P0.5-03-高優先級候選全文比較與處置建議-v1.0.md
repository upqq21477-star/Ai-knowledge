# P0.5-03 高優先級候選全文比較與處置建議

## 一、資料狀態：全文比較

比較：
- 0-知識/管理/資料狀態與生命週期原理.md
- 0-知識/更新/資料狀態模型.md

### 共同核心

兩者均確認：
- 內容與狀態分離
- 狀態不是可信度
- 歷史不等於錯誤
- 文件修改不等於知識更新
- 最新文件不等於最新有效內容
- 狀態判定需結合時間、版本、適用條件、證據或決策
- 不應提前建立複雜自動狀態引擎

### 實質差異

管理版主要回答「狀態語義與生命週期應如何定義」：
Draft、Pending、Active、Historical、Deprecated。

更新版主要回答「實際更新工作中如何辨識資料狀態」：
待確認、已確認、建立中、歷史、已失效、已否決。

兩套狀態不是同一維度：
- Draft / 建立中：偏文件／工作進度
- Pending / 待確認：偏確認程度
- Active / 已確認：並非完全同義，前者偏可採用，後者偏證據確認
- Historical / 歷史：高度一致
- Deprecated / 已失效：高度接近，但 Deprecated 可表示治理上不再採用，已失效則明確表示內容已不再適用
- 更新版「已否決」是決策結果，管理版沒有等價項

### 判定

這不是單純 duplicate，而是「兩套狀態語義尚未統一」。

目前不能直接 Merge。

真正需要處理的問題是：
「文件狀態、內容狀態、採用狀態、決策狀態是否應拆成不同維度？」

這屬於 P0.5-04 的語義蒸餾問題。

### 建議處置

兩份原文目前均 KEEP / REVIEW。

P0.5-04 建議：
1. 抽取兩份文件共同不變原則。
2. 抽取狀態名稱與其實際語義。
3. 將「工作進度」「內容確認」「採用狀態」「歷史／失效」「否決」拆成明確維度。
4. 不在沒有實際案例前建立複雜狀態機。
5. 蒸餾完成後，再決定是否由一份總原理 + 一份應用模型構成。

因此目前 disposition 不是 DELETE/MERGE，而是 DISTILL-CANDIDATE。

## 二、觸發保險：全文比較

比較：
- 0-知識/管理/觸發條件管理與啟動保險原理-v1.0.md
- 0-知識/管理/觸發條件管理與啟動保險原理.md

### 共同核心

兩者均具有：
- Trigger 是第二層啟動保險，不是主要啟動源
- 命中不等於立即啟動
- 必須確認 System ID 與處理狀態
- 防止二次啟動
- 防止 Re-entrancy
- 防止 Trigger Loop
- 多重匹配不可無條件全部啟動
- 狀態不明時不擴大
- 不建立中央事件總線作為前提
- 必須透過自然工作案例驗證

### v1.0 → 無版本的實質演化

v1.0 已提出最小安全模型：
Event ID → Trigger ID → System ID → 處理狀態。

無版本版進一步：
- 明確提出 Duplicate Activation
- 增加 Idempotency
- 將啟動狀態細化為未啟動、啟動中、執行中、已處理／完成、暫停／失效、狀態不明
- 增加外部方法比較
- 增加禁止事項
- 將驗證案例具體化

因此兩者不是兩個獨立知識，而是明顯的版本演化。

### 判定

暫定：
v1.0 = HISTORICAL-CANDIDATE / 保留作演化證據
無版本 = CURRENT-CANDIDATE / 仍待自然工作案例驗證

注意：這裡的 CURRENT-CANDIDATE 不是正式 P0.5 CURRENT。

### 建議處置

P0.5-04 不需要重新設計此原理。

應做的是：
1. 確認無版本版已完整吸收 v1.0 有效內容。
2. 保存 v1.0 作為歷史證據。
3. 將無版本版作為後續驗證對象。
4. 若實際驗證成立，再正式完成歷史化／Canonical Mapping。

因此此組是「版本演化＋歷史化候選」，而不是兩份文件 Merge。
