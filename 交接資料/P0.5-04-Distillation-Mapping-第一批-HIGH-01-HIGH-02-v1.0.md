### 3.2 語義 Mapping

| 原文語義 | 蒸餾處理 | 候選承載位置 | 原因 |
|---|---|---|---|
| 內容 ≠ 狀態 | 保留 | 資料狀態語義基準 | 兩份共同核心 |
| State ≠ Version ≠ Time | 保留 | 資料狀態語義基準 | 防止治理混淆 |
| 最新 ≠ 有效 | 保留 | 資料狀態語義基準 | 基本判定原則 |
| 歷史 ≠ CURRENT | 保留 | 資料狀態／Context 邊界 | 直接影響 Recall |
| 狀態變更需要依據 | 保留 | 狀態治理原則 | 證據要求 |
| 文件狀態 | 分離維度 | 狀態模型 | 不與內容真偽混合 |
| 內容確認狀態 | 分離維度 | 狀態模型 | 與採用狀態不同 |
| 採用狀態 | 分離維度 | 狀態模型 | Active 不等於 Confirmed |
| 已否決 | 保留 | 決策／歷史語義 | 具有追溯與防重複研究價值 |
| 已失效 | 保留但不與 Historical 等同 | 適用性／有效性語義 | 兩者語義不同 |
| 草稿／建立中 | 不直接固化為 Knowledge State | 文件／工作狀態候選 | 目前證據不足 |
| 已確認／已採用 | 不直接合併 | 內容確認／採用語義 | 已證明不可直接視為同義 |
| 「目前」綜合判定 | 保留 | CURRENT 判定原則 | 不是單一 State 名稱 |
| 不建立複雜狀態機 | 保留 | 治理原則 | 已被兩來源共同支持 |

### 3.3 第一版重製結構候選

暫定不是建立單一 Enum，而是拆成語義層：

```
資料狀態語義基準
├─ Asset / Governance State
├─ Document / Work State
├─ Content Confirmation State
├─ Adoption State
├─ Decision State
├─ Applicability / Validity
└─ Historical Relation
```

重要：

這個結構目前是「重製候選 Mapping」，不是已正式凍結的狀態架構。

### 3.4 不應被蒸餾掉的內容

不能因追求簡潔而刪除：

- 已否決的追溯價值
- 歷史與失效的差異
- AI 輸出預設為候選內容
- 時間／適用條件
- 狀態變更證據
- 不同狀態維度可能同時存在

### 3.5 暫不處置

目前不執行：

- 合併兩份原始文件
- 選一份覆蓋另一份
- 建立正式 State Engine
- 建立 State Database
- 將所有狀態轉成單一 Enum
- 宣布新的資料狀態文件 CURRENT

### 3.6 驗證要求

正式重製前後至少需要自然案例確認：

1. 文件建立中，但內容已部分確認。
2. 內容已確認，但尚未採用。
3. 已採用內容被新內容取代。
4. 歷史資料仍有追溯價值。
5. 已否決資料需要被搜尋時能正確辨識。
6. 已失效資料不被誤判為歷史有效資料。
7. AI 新輸出不會直接成為 CURRENT。

| 原文語義 | 蒸餾處理 | 候選承載位置 | 原因 |
|---|---|---|---|

| Trigger 命中 ≠ 啟動 | 保留 | Trigger 原理基準 | 核心安全邊界 |
| 先檢查目標狀態 | 保留 | Trigger 安全流程 | 防止重複啟動 |

| Re-entrancy | 保留 | Safety Rules | 核心失效模式 |

| Unknown State 不擴大 | 保留 | Safety Rules | 最小安全原則 |
| Event ID | 保留 | 最小識別模型 | 冪等性基礎 |
| Trigger ID | 保留 | 最小識別模型 | 觸發身份 |
| System ID | 保留 | 最小識別模型 | 系統身份不可由名稱／路徑取代 |

| Idempotency | 保留 | 安全原理／驗證 | 無版本文件新增且具操作價值 |
| Trigger Registry 不可成中央執行引擎 | 保留 | Architecture Boundary | 防止能力膨脹 |
| 不建立 Event Bus 作為前提 | 保留 | Architecture Boundary | 與現行工程策略一致 |
| 不建立複雜 Rules Engine | 保留 | Architecture Boundary | 最小化原則 |
| 自然工作案例驗證 | 保留 | Validation | 文件存在不等於能力成立 |
| Kubernetes / Backstage 等外部參考 | 依需要保留來源，但不轉成專案規則 | Evidence / Reference | 外部方法不是本專案採用規格 |
| v1.0 原始表述 | 不全部搬入 CURRENT 候選 | Historical / Evolution Evidence | 核心已由後續文件吸收的部分不必重複 |

```
Trigger 啟動保險原理

├─ 最小識別模型

```

這是蒸餾目標結構，不代表 Trigger Registry 已建立。

### 4.4 v1.0 歷史保留

v1.0 應保留，至少保存：

- 初版核心原理
- 當時問題定義
- 當時安全邊界
- 與後續版本的演化關係
- 原始外部參考

目前不直接移動或改名。

若後續逐項確認全部有效語義已被重製文件吸收，才可提出 ARCHIVE / HISTORICAL 實施。

### 4.5 驗證要求

正式採用前至少驗證：

1. 正常 Trigger 命中。
2. 已處理事件再次命中。
3. 系統正在執行時再次命中。
4. 多個 Trigger 同時匹配。
5. 狀態不明。
6. Event ID 重複。
7. Trigger 本身失效／暫停。
8. Trigger 不會直接取代主要啟動來源。
9. 無需 Event Bus / 大型 Rules Engine 即可完成最小安全流程。
