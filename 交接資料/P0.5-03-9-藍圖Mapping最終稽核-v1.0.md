## 二、稽核結論

### 2.1 A/B/C/D Mapping

A1–A12：12/12 有正式功能來源，現行 Mapping 與功能語義一致。

B1–B16：16/16 有正式功能來源，現行 Capability 編號可維持。P0.5-03-6 已證明 B 功能不是單一 System 的同義詞；因此 Mapping 保留 Capability 層，不把 B 功能直接改寫成 System。

C1–C18：18/18 有正式功能來源。C5 使用 CAP-33、C6 使用 CAP-11、C9 使用 CAP-06、C15 使用 CAP-05、C16 使用 CAP-09，均符合 Shared Capability 原則。

D1–D20：20/20 有正式功能來源。D3 與 C5 共用 CAP-33；D9、D13、D14、D16、D18 分別重用共同 Relationship、Impact、Migration、Validation、History 能力。D20 使用 CAP-61，僅表示 Capability/Process/Derived Mapping，不表示已建立獨立 Trigger System。

因此：A/B/C/D 的「功能→Capability」主 Mapping 第一輪可維持，不需因責任邊界稽核而任意改號。

## 三、最重要的責任邊界修正

Mapping 必須被讀成：

Function → Capability → Plan Context → Provider/System

而不能讀成：

Function → Capability → System 已完成。

尤其 B1–B16 已有多個專責 System 分工；D1–D20 尚無足夠證據證明存在完整蒸餾 System。

因此 Mapping 文件應視為 Derived View；Canonical Source 仍是正式方案功能文件、系統正式定義、決策與驗證紀錄。

## 五、CAP ID 稽核

目前 Mapping 已形成 CAP-01–CAP-61 的連續編號，其中已知重要修正為：

- K03 Trigger Registry → CAP-60。
- D20 Distillation Trigger → CAP-61。

本輪未發現足以支持新增 CAP-62 或重排既有 CAP 編號的證據。

## 六、Namespace 稽核

正式 Namespace：

- Kxx = Knowledge
- CAP-xxx = Capability
- SYS-xxx = System
- PLN-xxx = Plan
- SCN-xxx = Scenario
- EVD-xxx = Evidence
- DEC-xxx = Decision

S01–S10 已確認為 Scenario，因此 Mapping 中以 SCN-01–SCN-10 表示其正式語義；原 S01–S10 僅作歷史來源識別。

S11–S37 未找到足以安全恢復的現行正式定義，維持 UNKNOWN。

K07–K61 同樣維持 UNKNOWN。不能用檔名、編號連續性或相鄰文件推測。

## 七、Provider／System 解讀規則

Provider 可以是 GPT／Model、System、Tool、Human。

因此：

- GPT 提供 Capability，不代表 System 消失。
- System 提供 Capability，不代表 Plan Responsibility 被 System 吞併。
- Tool 可提供局部能力，不代表它成為正式 System。
- Human 可以提供尚未系統化的判斷或施工能力。
- Provider 改變不等於 Capability 消失。
- Model 更新不應直接刪除舊 System；應先做 Capability Delta、受影響 Scenario 測試、Evidence 與 Regression。

## 八、本輪不應修改的內容

在目前證據下，不應：

1. 把 B1–B16 改成一個 AI知識管理 System 清單。
2. 把 D1–D20 建成一個蒸餾 System。
3. 把 Shared Capability 各自拆成獨立 System。
4. 把 D20 升格成獨立 Trigger System。
5. 把 S11–S37 猜成 System。
6. 把 K07–K61 補成假定 Knowledge。
7. 因「Mapping 不完整」而新增正式 A/B/C/D 功能。
8. 因 CAP 編號連續性而創造不存在的系統。
