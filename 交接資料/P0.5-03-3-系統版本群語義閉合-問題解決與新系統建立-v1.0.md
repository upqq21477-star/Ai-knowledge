## 二、直接證據

### 2.1 問題解決系統-v1.0

文件自身狀態：

【建立中；已通過第一、第二輪案例驗證；待第三輪持續驗證】

文件直接定義其定位為「小型、跨方案的問題解決系統」，核心工作是：

問題 → 確認值得處理 → 搜尋研究 → 外部比較 → 候選解法 → 最小實測 → 比較 → 採用／暫緩／拒絕 → 回饋。

它明確表示：

- 不取代既有搜尋、研究、外部比對能力。
- 不是第四個正式方案。
- 是支援三方案及其他系統處理具體問題的共用小型系統。
- 目前已經有三個代表性案例通過最小案例。
- 仍未要求建立完整 Agent Trace、Observability 平台、自動解題引擎、知識圖譜或自動架構修改。

因此 v1.0 已經不是單純概念草案，而是具有初步案例驗證的系統候選；但文件自己仍標記「建立中」且待第三輪驗證。

### 2.2 問題解決與新系統建立流程-v1.1

文件自身狀態：

【建立中；已整合問題解決與新系統建立流程；待後續案例驗證】

文件直接稱自己為「問題解決系統的擴充版流程」。

其核心變更不是推翻 v1.0，而是在原問題處理流程後增加一個分流：

- 現有能力足以解決 → 採用／條件採用既有解法。
- 現有能力不足且確實需要新增能力 → 進入新系統建立流程。

新系統建立分支再處理：

已確認問題 → 系統目標 → 功能需求 → 知識需求 → 系統能力需求 → 檢查既有系統重疊 → 建立最小系統候選 → 實際驗證 → 判定。

文件也明確要求：

- 先使用既有能力。
- 新系統不是問題解決的預設結果。
- 功能完全重疊時優先重用。
- 部分重疊不能直接假設可以合併。
- 發現舊系統多餘、應拆分或整併時，本流程只記錄，不直接重構舊架構。
- 建立文件不等於系統成立。
- 尚未正式建立自動建立新系統、自動整併舊系統、固定 JSON Schema、固定資料庫結構等大型自動化能力。

## 四、核心判定

### 4.1 不是兩個完全獨立的系統

直接證據顯示 v1.1 自己把自己定義為「問題解決系統的擴充版流程」。

因此不能把：

- 問題解決系統-v1.0
- 問題解決與新系統建立流程-v1.1

當成兩個互不相關、各自獨立的正式系統。

若目前將兩者都視為獨立 System，會造成責任重疊與重複入口。

### 4.2 也不能簡化成「v1.1 完全取代 v1.0」

v1.1 雖然擴充了新系統建立分支，但 v1.0 仍包含第一、第二輪實際案例驗證資料，且 v1.1 的新增部分尚未完成長期、多案例驗證。

因此：

- v1.0 = 已有驗證證據的問題解決核心。
- v1.1 = 在該核心上增加「必要時建立新系統」分支的擴充候選。

不能因為 v1.1 編號較新，就直接將 v1.0 的全部語義判定為失效。

### 4.3 最準確的關係是「同一系統血統 + 流程能力擴充」

本輪判定：

> 問題解決與新系統建立流程-v1.1，是問題解決系統-v1.0 的同一語義血統之擴充版流程；其新增部分同時具有「流程（Process）」性質，因此目前應視為「System Core + Process Extension」，而不是第二個獨立 System。

可表示為：

問題解決系統核心
↓
問題確認／搜尋／比較／候選／實測／判定／回饋
↓
新增分流
├─ 既有能力足夠 → 採用既有解法
└─ 能力不足且需要新增能力 → 新系統建立流程
    ↓
    系統需求／功能／知識／能力／重疊檢查／最小系統／驗證

這個關係目前比「兩個獨立系統」或「v1.1 完全取代 v1.0」更符合文件直接證據。

## 六、是否需要刪除、合併、重命名

### 6.1 不刪除

目前沒有證據支持刪除 v1.0。

v1.0 包含：

- 初始系統定位。
- 第一、第二輪案例驗證。
- 問題解決核心流程。
- 與搜尋、外部比對、三方案的責任邊界。
- 失敗回退與停止條件。

這些內容是 v1.1 演化的重要證據。

### 6.2 不直接合併檔案

目前不應把 v1.0 與 v1.1 直接壓成一份文件。

原因：

1. v1.0 是歷史演化證據。
2. v1.1 新增了新系統建立分支。
3. 新增分支尚未完成充分驗證。
4. 直接覆寫會降低演化追溯能力。

P0.5-04 的任務應該是語義遷移與收斂，而不是單純檔案合併。

### 6.3 不直接重命名

目前沒有必要在 P0.5-03 直接改名。

應先完成後續案例驗證，再決定是否需要形成：

- 一個正式問題解決系統規格；
- 一個問題解決／新系統建立流程文件；
- 或其他更清楚的 System + Process 分層。

目前證據不足以提前決定最終文件結構。

## 七、與三個正式方案的責任邊界

本輪沒有發現 v1.1 變成第四個正式方案的證據。

兩份文件都明確寫出：

- 不是第四個正式方案。
- 跨三方案使用。
- 正式採用仍由對應治理、知識管理或演化流程處理。

因此目前維持：

整體資料治理方案
→ 提供資料、責任、邊界、治理約束

AI知識管理方案
→ 提供任務理解、搜尋、上下文、執行、驗證

知識迭代與資料演化方案
→ 處理變更、影響、版本、相容性、演化

問題解決系統／問題解決與新系統建立流程
→ 處理具體問題，研究、比較、實測，必要時提出新系統候選

其中「提出新系統候選」不等於「直接建立正式系統」。

## 八、與既有 Trigger / Validation 系統的邊界

本輪可先確認一個重要邊界：

### 問題解決系統

回答：

> 已確認有問題後，如何研究並驗證解法？

### 後續工作觸發式順便驗證系統

回答：

> 已經有待驗證事項時，如何在自然工作中不要忘記驗證？

### Trigger Registry

回答：

> 發生事件／問題／狀態變化時，哪些系統可能需要被啟動，以及如何避免重複啟動？

三者不能因為都使用「問題／觸發／驗證」等詞彙就合併。

目前應維持三個不同責任：

問題處理
≠
驗證提醒
≠
啟動候選發現

## 九、與 Blueprint 的關係

本輪結果只能作為 Mapping 的 Evidence，不應直接創造新的 Blueprint ID。

目前可支持：

- 問題解決是一項跨方案共用能力。
- 「問題 → 搜尋 → 候選 → 實測 → 判定 → 回饋」符合既有 Capability 導向架構。
- 「必要時建立新系統」可作為能力擴充／系統建立流程的一部分。
- Receipt、最小實測、失敗回退與新系統建立前的重疊檢查，都是可供後續 Capability Mapping 使用的證據。

但本輪沒有證據支持：

- 新增 CAP ID。
- 新增 SYS ID。
- 宣告既有 Blueprint Capability 已實作。
- 宣告新系統已正式成立。
- 把 v1.1 的「新系統建立流程」直接視為一個獨立 System。

因此 Mapping 應等待 Canonical Source 與後續驗證閉合後再更新。

## 十、最重要的未閉合問題

本輪仍有五個需要第三輪或後續真實工作驗證的問題：

### 1. 新系統建立分支是否真的能被同一問題入口順利驅動

需要實際案例證明：

問題 → 既有能力盤點 → 研究 → 候選 → 實測 → 能力不足判定 → 新系統候選

整條流程不會重複研究。

### 2. 部分重疊系統如何保持邊界

文件已經規定：

「部分重疊 → 不直接整併，記錄邊界後建立候選」

但目前仍缺少足夠案例證明這個規則在真實架構衝突中有效。

### 3. 新系統建立後如何回饋三方案

文件已定義方向，但仍需要實例驗證：

新系統候選
→ 驗證
→ 判定
→ 正確回到資料治理／知識管理／資料演化對應責任。

### 4. 重複問題是否會避免重複建系統

這是新分支最重要的長期風險之一。

需要驗證：

同一問題再次出現
→ 能否找到既有問題 Receipt／既有解法／既有系統
→ 而不是重新建立另一個同功能系統。

### 5. 共用 Receipt 是否真的足夠

v1.1 提議問題解決與新系統建立共用 Receipt。

需要真實案例證明它可以同時重建：

問題 → 研究 → 候選 → 實測 → 判定 → 系統建立 → 驗證 → 回饋

若缺欄位，再由實際缺口驅動補充，而不是預先設計大型 Schema。

## 十一、本輪結論

本輪語義閉合結果：

> 「問題解決系統-v1.0」與「問題解決與新系統建立流程-v1.1」不是兩個獨立系統，而是同一問題處理系統血統的前後演化；v1.1 在 v1.0 的問題解決核心上增加「現有能力不足時進入新系統建立」的流程分支。

因此目前最合理的工程處置是：

1. v1.0 保留為 Evolution Evidence。
2. v1.1 保留為 Current Candidate Specification。
3. 兩者均維持 REVIEW。
4. 不刪除。
5. 不直接合併。
6. 不直接宣告 v1.1 為正式 CURRENT。
7. 不新增 Blueprint ID。
8. 透過第三輪真實案例驗證新系統建立分支。
9. 驗證完成後，再進入 P0.5-04 的語義遷移與 Canonical 收斂。

這一輪解決的是「版本群是否其實是同一條系統演化線」；尚未解決「最終 Canonical 文件應如何拆分」。
