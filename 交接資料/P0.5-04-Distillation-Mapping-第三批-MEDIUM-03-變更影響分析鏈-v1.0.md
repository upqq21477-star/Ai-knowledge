## 2. 語義責任 Mapping

| 文件 | 抽象層／責任 | 核心內容 |
|---|---|---|
| 變更影響分析最小原則 | 共同能力原理層 | 定義 Impact Analysis 的最小共同語義、最小影響鏈、必要檢查維度、Direct/Indirect、Candidate/Confirmed/No Impact/Unknown、與 Change Decision 的邊界 |
| 變更影響分析與影響範圍 | 更新操作／流程層 | 將變更集放入既有關係中逐層追蹤，定義關係類型、擴散流程、停止條件、影響範圍表示與輸出格式 |
| 關係 | Layered Complement | 前者回答「影響分析最少需要知道什麼」；後者回答「實際變更案件如何沿關係執行分析」 |

## 3. 共同語義

兩文件均確認：

1. 影響分析從變更對象開始，而非從所有相關資料開始。
2. 影響判定必須依實際關係／依賴／使用，而非僅依主題相似。
3. 影響可沿直接與間接關係傳播。
4. 存在關係不等於必然需要更新。
5. 分析必須有停止條件，避免無限擴散。
6. Impact Analysis 不等於 Change Decision。
7. 影響結果具有不確定性，不應宣稱能保證找全所有影響。
8. 第一版可用人工、Markdown、表格或文字圖驗證，不需要先建立大型 Impact Engine／Graph DB。

## 4. 分層後保留內容

### A. 共同原理候選應保留

- Impact Analysis 的目的與邊界
- 變更對象 → 關係／依賴 → 使用／下游 → 版本／相容性 → 驗證／實際工作的基本影響鏈
- Direct Impact / Indirect Impact
- Candidate Impact / Confirmed Impact / No Impact / Unknown 等結果語義
- 影響分析與 Change Decision 分離
- 影響分析深度應依風險與影響範圍調整
- 不因關係存在就宣稱必然受影響
- 不以引用數量直接代表依賴強度
- 真實案例先行、人工驗證優先於大型自動化

### B. 更新流程／應用候選應保留

- 建立 Change Set
- 記錄檔案、段落、規則、參數、結論、原因及定義／邊界／條件／輸出／行為是否改變
- 第一層影響建立
- 逐層擴散與每層重新判斷
- 停止條件
- 影響範圍文字圖／表格表示
- 輸出：變更集、直接影響、間接影響、不受影響、待確認、影響邊界、更新建議
- false positive / false negative 與分析成本邊界

## 5. 不應直接蒸餾成共同規則的內容

- 第二文件的具體流程欄位與輸出表格：屬操作模板候選，不應宣稱是所有影響分析唯一格式。
- 第一文件列出的十個檢查維度：應保留為最小共同語義候選，但「每次都檢查十項」不是規則。
- 第一文件引用的 Backstage、Microsoft、AWS 方法：屬外部佐證，不是本專案自身規範。
- 第二文件與特定既有文件的差異說明：屬本專案關係定位，不應變成普遍原理。

## 7. 驗證要求

至少需要一個真實變更案件，驗證：

1. 是否能建立清楚的 Change Set。
2. 是否能找到合理的第一層直接影響。
3. 是否能沿實際關係逐層追蹤。
4. 是否能在適當位置停止，而非無限擴散。
5. 是否能區分 Candidate／Confirmed／No Impact／Unknown 或等價語義。
6. 預測影響與實際影響是否有可比較結果。
7. 流程成本是否低於其降低錯誤風險的價值。
8. 是否真的需要額外工具／自動化；在此之前不得建立大型 Impact Engine。
