## 四、第一輪高優先閉合群

### H1：後續工作觸發式順便驗證

四版本不能直接以版本號選 CURRENT。

目前可確認的演化方向：

v1.0：基本「標記→後續工作→自然觸發→驗證」。

v1.1：增加與待辦／正常工作輕量關聯。

v1.2：明確區分生命週期狀態與單次事件結果，並強化自然觸發判定。

v2.0：重新收斂為候選小系統，並加入最小閉環實測要求。

目前判定：

**文件演化已確認；System 正式成立尚未確認。**

因此四份全部保留，暫不刪除或合併。下一步應建立「版本語義差異＋有效內容＋目前 Canonical Candidate」矩陣。

### H2：Trigger Registry

v1.0 與 v1.1 有明確語義演化。

v1.0 偏向「事件→System ID→路由」。

v1.1 增加：

- 防二次啟動
- Idempotency
- 防循環
- 多重匹配不自動全部啟動
- 不確定時不擴大啟動

因此 v1.1 不能簡單視為「另一份重複文件」，但也不能因內容較完整就直接宣布它取代 v1.0。

目前暫定：

- v1.0：HISTORICAL/CANDIDATE-EVIDENCE
- v1.1：CURRENT CANDIDATE / REVIEW
- CAP-60 Trigger Registry：保留為目前 Blueprint Derived Mapping；其成立仍需回到 Canonical Source + 實際證據確認。

### H3：統御分支

目前存在四份不同責任文件：

- 系統管理統御分支
- 系統管理統御分支系統
- 統御小系統協調管理系統
- 統御方案系統

它們不是簡單四版本；其中包含不同層級與不同候選責任。

目前不應合併。

已知正式邊界仍是：

**統御不是第五方案。**

因此本輪只做責任追蹤，不升格任何一份為正式統御架構。

以下三份文件名稱與正式方案高度相似：

- 整體資料治理系統
