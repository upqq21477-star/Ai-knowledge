# P0.5-03-2｜系統版本群語義閉合：後續驗證與 Trigger

日期：2026-09-18
狀態：【CURRENT｜P0.5-03 工作證據】

## 一、結論

本輪不以「版本號越大越新，因此直接取最新」判定。

兩組文件是不同演化線：

1. 後續工作觸發式順便驗證：從待驗證標記逐步收斂成低成本、自然觸發的候選小系統。
2. Trigger Registry：從事件到 System ID 的索引，進一步加入防重複、冪等、防循環、多重匹配與不確定時不擴大啟動。

兩者不能合併。

## 二、後續工作觸發式順便驗證 v1.0～v2.0

| 版本 | 主要內容 | 判定 |
|---|---|---|
| v1.0 | MARKED → 自然工作觸發 → 順便驗證 → 結果回寫 | 基礎語義 |
| v1.1 | MARKED 與待辦／正常工作建立輕量關聯；加入 V-002；明確獨立測試例外 | 完善語義 |
| v1.2 | 區分自然觸發、觸發≠驗證、生命週期與事件狀態、最低證據、問題解決接口 | 最完整規格候選 |
| v2.0 | 收斂為小系統：最小資料、流程、邊界、實測 Gate | 最適合實測 |

判定：

v2.0 可作為目前 Canonical Candidate（規格候選），但不能直接標成 CURRENT System。

原因是 v2.0 自身仍標示「候選小系統；待最小實測」，而 v1.0～v1.2 保留了需求與語義演化證據。

目前關係：

- v1.0～v1.2：Evolution Evidence
- v2.0：Current Candidate Specification
- System Established：待真實施工驗證

## 三、Trigger Registry v1.0 → v1.1

v1.0 核心：

事件／問題／需求 → Trigger 匹配 → System ID → 統御／方案 → 目標系統。

v1.1 增加：

Trigger 匹配 → 狀態確認 → 防二次啟動 → 冪等 → 防循環 → 多重匹配不自動全部啟動 → 補充啟動。

判定：

- v1.0：歷史基礎規格／Evolution Evidence
- v1.1：Current Candidate Specification
- 正式成立：待實際運作驗證

不能因 v1.1 較完整，就宣稱 Trigger Registry 已完成。

## 四、兩組系統的邊界

正確關係：

正常工作開始
→ 後續驗證小系統：檢查這次工作是否自然提供驗證案例。

事件／問題／需求
→ Trigger Registry：檢查可能需要哪個 System，以及是否需要補充啟動。

因此：

Validation Marker System ≠ Trigger Registry

前者解決「不要忘記驗證」；後者解決「不要漏掉應啟動的 System，且不要重複啟動」。

## 五、與 Blueprint 的關係

目前 Blueprint 已存在 CAP-60：Trigger Registry、CAP-61：Distillation Trigger。

本輪只確認 CAP-60 的文件演化證據，不把文件狀態等同 Capability 已實作。

應維持：

Blueprint Mapping = Derived View
Canonical Source = 1-系統文件＋實際驗證證據

若實測證明 v1.1 無法成立，先修 Canonical Source，再更新 CAP-60 Mapping。

## 六、目前不得做的判定

不得：

- 宣布 v2.0 已正式成立。
- 宣布 Trigger Registry v1.1 已完成驗證。
- 刪除 v1.0～v1.2。
- 將兩個系統合併。
- 建立新的 Trigger Engine / Event Bus。
- 建立新的 Capability ID。
- 把自然觸發驗證系統變成第五方案。
- 因文件完整而跳過真實工作驗證。

## 七、目前驗證 Gate

後續驗證小系統至少需要：

正常工作 → MARKED 檢查 → 自然觸發／不觸發判定 → 真實驗證 → Expected/Actual → 回寫。

並證明不會製造額外工作。

Trigger Registry 至少需要：

1. 正常工作已啟動 → 不二次啟動。
2. 正常流程漏啟動 → Trigger 能補充啟動。
3. 同一 Event ID 重複觀察 → 不重複執行。
4. 多重匹配 → 不自動全部啟動。
5. 執行後不形成無限循環。
