## 一、目的

本輪不是重新定義 A1–A12、B1–B16、C1–C18、D1–D20，而是檢查：
1. 正式方案功能是否已被既有核心 System 重複承擔。
2. 核心 System 是否只是提供共用語義／能力，而不是吞入整個 Plan Responsibility。
3. 某些功能是否其實只是 Process，而沒有獨立 System Canonical Source。
4. Blueprint Mapping 是否把「涉及／使用」錯誤寫成「負責」。
5. 哪些結論目前只有 Derived Mapping，尚缺 Canonical Source。

## 二、判定原則

- Plan Responsibility：正式方案對該功能的工程責任、組合責任與驗收責任。
- System Responsibility：某個 System 對持續性、可重用系統能力的責任。
- Process：完成某項工作的流程，不因流程存在就自動成為 System。
- Capability：可由不同 Provider 提供、比較與驗證的能力。
- Derived Mapping：由 Mapping 推導出的關係，不能反向取代 Canonical Source。
- 「使用」≠「負責」。
- 「部分承擔」≠「方案功能已被吞入」。
- 名稱相似≠責任相同。

## 三、三核心系統 Canonical 邊界

### 整體資料治理系統
Canonical 文件明定：提供三個方案共用的資料治理能力；負責共同資料類型、共同語義、描述原則、State、Version、Relationship、Source／Traceability 與跨方案規則檢查。同時明定不負責一般知識搜尋、AI 任務執行、自動演化所有資料或取代驗證流程。
第一輪定位：共同資料語義與治理責任，不是四方案功能的總承擔者。

### AI知識管理系統
Canonical 文件明定：負責 AI 在知識庫中理解問題、取得資料、使用 Context、保存結果與交接；核心流程包含任務理解、知識需求、搜尋／探索／研究、Context、執行、驗證、保存、回饋。
第一輪定位：B1–B16 的主要 System-level 工作能力承擔者，但 Plan-level 責任仍屬方案二。

### 知識迭代與資料演化系統
Canonical 文件明定：負責新證據、新需求、新狀態或驗證造成的知識／資料變更；包含變更確認、影響分析、候選演化、版本、歷史、相容性與遷移需求。
第一輪定位：C1–C18 的主要 System-level 演化能力承擔者；不因此吞入 D1–D20。

## 五、重大發現

### 5.1 A1–A12
目前沒有證據支持「治理 System 吞掉方案一」。A1–A12 與治理系統高度重疊是預期結構：方案一是 Plan-level Governance Responsibility，治理系統是 System-level Shared Governance Capability。後續仍需驗證方案一是否具有額外的組合、審查與驗收責任。

### 5.2 B1–B16
這組是目前表面重疊最高的一組。方案二幾乎完整落在 AI知識管理系統 v2.0 的核心流程，但這不等於方案二失去存在必要。必須保持 Plan 與 System 層分離。
B5 外部研究目前有明確證據屬能力／工作方案，不應升格第四核心 System。B16 應保持失敗診斷接口，問題解法仍由問題解決流程承擔。

### 5.3 C1–C18
方案三與演化 System 高度對應，但仍要區分 Plan responsibility 與 System responsibility。C13、C15、C16 等同時使用跨方案共用語義，不能被誤標成方案三獨占。

### 5.4 D1–D20
目前沒有足夠 Canonical 證據證明三核心 System 已實際承擔 D1–D20 的大部分專責責任。方案四具有蒸餾、重疊、責任邊界、處置、重構與新基準等獨立責任，因此不能全部併入演化 System。

### 5.5 真正需要邊界驗證的重疊
- C5 與 D3：都做 Capability Inventory，但目的不同。C5 為變更決策；D3 為蒸餾／重構。
- A11、C6、D13：都是 Impact，但應是一個共用 Capability 加上不同責任情境，而不是三套 Impact System。
- A5、C15、D18：共同使用 State／History 語義，不應各自建立一套狀態或歷史系統。

## 七、尚不能下的結論

1. 不能宣布 A1–A12 全部就是治理 System。
2. 不能宣布 B1–B16 已完全被 AI知識管理系統實作；System 文件本身仍標示建立中。
3. 不能宣布 C1–C18 已完全由演化 System 實際承擔。
4. 不能宣布 D1–D20 已形成獨立完整 System。
5. CAP Mapping 本身不能證明 System Responsibility。
6. 文件存在不能證明 Real-Work Validation。
