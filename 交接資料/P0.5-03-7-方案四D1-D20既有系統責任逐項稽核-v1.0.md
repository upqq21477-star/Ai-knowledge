## 四、關鍵責任邊界

### 4.1 D3 與 C5：同名能力，不同責任情境

C5「既有能力盤點」服務於正常變更決策：

`變更訊號 → 目標確認 → C5 → 判斷既有能力是否足夠`

D3「能力盤點」服務於蒸餾／重構：

`蒸餾案件 → 範圍 → D3 → 盤點範圍內實際存在的能力／系統／關係`

因此兩者不是應直接 Merge 的兩個 System。

目前更合理的模型是：

`Capability Inventory = 共用 Capability`

再由 C5、D3 使用不同的 Context、Scope、Decision Purpose。

### 4.2 A11、C6、D13：Impact 不應複製

三者都涉及影響，但：

- A11：資料治理層的變更影響語義。
- C6：正常演化案件的影響分析。
- D13：蒸餾／重構候選的影響分析。

因此不應建立三個 Impact System。

合理模型：

`Shared Impact Analysis Capability + Plan-specific Context`

### 4.3 A5、C15、D18：State／History 不應重建

A5 提供共同 State 語義；C15 產生演化後的新 Current State；D18 保存退出目前結構的歷史／舊能力。

三者使用同一套共同語義，但責任不同：

`Governance Semantics → Evolution / Distillation Uses`

不能因 D18 出現「保存」就再建立一套 History System。

### 4.4 D14 與方案三 Migration

D14 不應重新發明 Migration。

方案三負責正常演化中的 Migration 分析；方案四在蒸餾案件中使用並檢查 Migration 條件，尤其處理結構重組造成的舊／新能力共存與退出。

因此：

`Migration Capability 可重用；Decision Context 不同`

### 4.5 D16 與既有驗證系統

Repository 已存在：

- 實測結果回寫檢查小系統
- 後續工作觸發式驗證系統
- 其他驗證／Evidence 能力

但目前沒有證據支持「方案四應建立另一套獨立 Validation System」。

D16 的責任是：

`重構後 → 驗證功能、資料、依賴、工作結果 → PASS / FAIL / UNKNOWN`

實際驗證能力可以重用；方案四負責蒸餾重構後的驗證決策與閉環。

## 五、D20 特別稽核

D20 是目前最容易被錯誤升格的項目。

正式定義：

「當累積問題再次達到蒸餾條件時建立下一案件。」

既有 Mapping 將 D20 映射為：

`CAP-61 Distillation Trigger／再次蒸餾觸發`

但這只是 Derived Capability Mapping。

目前沒有足夠 Canonical 證據證明 Repository 已經建立一個獨立的：

`Distillation Trigger System`

同時，既有文件明確要求：

- D20 不直接執行下一次蒸餾。
- D20 建立新的蒸餾入口。
- 下一案件必須重新經過 D1→D2→D3→D4。
- 問題解決系統不能取代 D20。
- 正常工程運作提供長期觀察來源，但不能直接把任一局部問題判定為蒸餾。

因此 D20 目前應維持：

`Capability / Process + Derived Mapping`

而非獨立 System。

## 六、目前真正存在的 System Gap

第一輪沒有發現「D1–D20 功能缺失」；方案四的功能閉環已有正式文件與模擬／回歸證據。

但是「功能閉環存在」與「通用蒸餾 System 已建立」是兩件不同的事。

目前 System 層可明確描述為：

```
方案四 Plan
  ↓
D1–D20 Process / Capability
  ↓
使用既有：
Identity / State / Evidence / Relationship
Impact / Migration / Validation / History
  ↓
必要時呼叫既有專責 System
  ↓
實際執行重構
```

因此目前不存在足以支持以下動作的證據：

- 建立大型蒸餾 System
- 建立通用自動重構 System
- 建立獨立 D20 Trigger System
- 建立獨立 History System
- 建立第二套 Validation System
- 建立第二套 Impact System

## 七、對 P0.5-03-5 的修正關係

P0.5-03-5 將 D1–D20 高階概括為：

「Plan Responsibility + 多數仍屬 Process / Capability / 重構責任」

本輪逐項稽核後，該高階結論仍成立，但可進一步精確化：

1. D1–D4：以蒸餾案件 Process 為主。
2. D5、D9、D13、D14、D16–D18：大量使用共同 Capability／既有能力。
3. D6–D12：以方案四專責分析／決策 Process 為主。
4. D15：重構施工 Process，不等於存在通用重構 System。
5. D19：蒸餾結果的 Plan-level 回寫責任與既有保存能力的接口。
6. D20：Capability／Process；目前沒有獨立 Trigger System Canonical 證據。

因此不需要撤銷 P0.5-03-5；本文件是其逐項細化。

## 九、結論

本輪最重要的結論不是「方案四沒有 System」，而是：

> 方案四目前是一套已形成完整閉環的 Plan／Process／Capability 責任結構，但 Repository 尚沒有證據支持把 D1–D20 一對一轉換成一個「蒸餾系統」。

進一步確認：

- D3 不等於 C5；可共享 Capability，但 Context／目的不同。
- D13 不應與 A11、C6 各建一套 Impact System。
- D16 應重用共同 Validation 能力。
- D18 應重用共同 History／Archive 語義。
- D14 應重用 Migration 能力，而不是吞掉方案三。
- D20 目前仍是 Capability／Process／Derived Mapping，不是獨立 Trigger System。
- 方案四不能因存在 D1–D20 就自行建立大型自動化系統。
- 真正 System 是否成立，仍必須由實際工作、重複瓶頸、可重用需求與驗證證據決定。

因此，本輪不新增 System、不新增 System ID、不修改 D1–D20、不修改 Blueprint Mapping。
