## 4. 上下文批
5 個文件全部判定 REVIEW / KEEP。
上下文成本偏資源與成本邊界；上下文管理原理形成管理流程；上下文與資料載入介面原理處理資料與工作上下文的介面邊界；人工智慧交接文件分工處理文件責任；模型能力補償處理模型特定能力缺口。它們有關聯，但目前沒有充分證據要求合併。

## 5. 證據批
6 個文件全部判定 REVIEW / KEEP。
來源與證據是較完整的共同邊界原理；來源主張證據追溯進一步明確化追溯鏈；區分來源與知識、區分人工智慧輸出與知識真實性屬基礎邊界；證據充分性與不確定性處理採用門檻與不確定性；資訊可信度與主張驗證處理主張層級的可信度與適用性。

目前未發現需要立即合併的重複。後續需要做的是入口 Mapping，避免未來 AI 面對來源、證據、充分性、可信度等多個入口時不知道先讀哪一份。

## 6. 運作批
以下 9 個文件判定 REVIEW / KEEP：AI知識庫基本運作循環、實測結果回寫最小原則、小系統建立原則、新內容問題化與功能-知識缺口分析原則、新方案建立前研究與確認原則、系統建立流程失效原因與防止提前建系統、系統目錄與觸發條件分離原則、統御分支與系統歸屬管理原則，以及 v2.0 版後續工作觸發式順便驗證原則。

「後續工作觸發式順便驗證原則.md」與「後續工作觸發式順便驗證原則-v2.0.md」是明確版本演化。v2.0 增加 MARKED、NOT TRIGGERED、TRIGGERED、PASS/PARTIAL/FAIL、最小驗證記錄、觸發條件與 Gate 邊界，因此舊版不應再作 CURRENT 入口。
舊版處置：HISTORICAL / SUPERSEDED / ARCHIVE-RETAIN。保留它是為了保存設計演化證據，不是刪除。

「系統建立流程失效原因與防止提前建系統」記錄了真實施工失效與候選修正方向，但候選解法仍需後續實測，因此不能僅因內容完整而標成已驗證 CURRENT。
「AI知識庫基本運作循環」同樣明確要求用正常施工、異常、阻斷、恢復及無歷史記憶 AI 等案例驗證，故本次仍維持 REVIEW。
「系統目錄與觸發條件分離原則」雖文件內標示正式建立，但仍寫明待實際運作驗證；本次 P0.5 State 仍採 REVIEW，因文件內部知識狀態與資料治理 State 不是同一欄位。

## 7. 跨批初步觀察
目前看到的是概念鏈而非單純重複：上下文成本 → 上下文管理 → 資料載入介面；來源 → 主張 → 證據 → 充分性 → 可信度 → 適用性；問題／需求 → 功能 → 知識缺口 → 研究 → 候選系統／方案 → 實測 → 回寫。
因此目前沒有足夠證據要求刪除或合併。
