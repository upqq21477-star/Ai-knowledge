# P0.5-03-4 系統版本群語義閉合－統御與系統目錄-v1.0

## 一、盤點目的
本報告承接 P0.5-03-3，處理目前 1-系統 中兩組高風險責任重疊：
第一組：系統管理統御分支-v1.0、系統管理統御分支系統-v1.0。
第二組：統御方案系統-v1.0、統御小系統協調管理系統-v1.0。
另以「整體資料治理系統-v1.0」作為上層責任邊界參照，避免將 System Registry、統御索引、資料治理混成同一系統。
本輪不修改原始文件、不刪除任何文件、不新增 System ID。

## 二、第一組：系統管理統御分支 vs 系統管理統御分支系統
### 2.1 直接證據
「系統管理統御分支-v1.0」明確定位為 System Registry / System Catalog（系統目錄與系統關係索引）。核心目的為以最少資訊掌握正式系統的身分、位置、狀態、所屬方案與主要關係；不是所有系統的總控制器，也不執行各系統業務邏輯。
「系統管理統御分支系統-v1.0」同樣直接定義系統身份、目錄、位置、狀態、方案歸屬、關聯知識、功能摘要、基本生命週期、接收 Trigger Registry 的 System ID、將系統路由至所屬方案。
兩者均明確排除專責系統執行、Trigger 條件匹配、問題解決、方案內部協作、全庫即時狀態控制。

### 2.2 語義比較
| 維度 | 分支-v1.0 | 分支系統-v1.0 | 判定 |
|---|---|---|---|
| 核心目的 | System Registry / Catalog | 系統身份、目錄、路由 | 相同 |
| System ID | 核心 | 核心 | 相同 |
| 系統位置 | 核心 | 核心 | 相同 |
| 狀態 | 核心 | 核心 | 相同 |
| 方案歸屬 | 核心 | 核心 | 相同 |
| 知識關係 | 核心 | 關聯知識書 | 相同 |
| Trigger 關係 | 接收 Trigger Registry 找到的 System ID | 同樣接收 System ID | 相同 |
| 路由 | System ID → 方案 | System ID → 方案 | 相同 |
| 驗證 | 三階段目錄／路由驗證 | 六項最小驗證 | 同一責任，後者更具體 |
| 文件成熟度 | 正式建立；待實際運作驗證 | 建立中；規則已建立；待最小實測 | 後者狀態較保守 |

### 2.3 判定
本輪沒有找到足以支持「兩個獨立系統」的核心功能差異。
兩份文件描述的是同一個 System Registry / System Catalog 責任。
因此：「系統管理統御分支系統-v1.0」不是另一個獨立系統，而是對「系統管理統御分支-v1.0」同一責任的規格化／具體化版本。
更準確地說：分支-v1.0 偏定位、架構責任與運作邊界；分支系統-v1.0 偏最小資料、操作、異常與驗證。
因此目前應視為：同一 System + Specification Refinement（規格具體化）。不能同時登記成兩個 System ID。

### 2.4 State / Disposition
| 文件 | State | Disposition |
|---|---|---|
| 系統管理統御分支-v1.0 | REVIEW | KEEP / Architecture Evidence |
| 系統管理統御分支系統-v1.0 | REVIEW | KEEP / Current Candidate Specification |
原因：前者提供較完整的架構定位，後者提供較具體的最小操作與驗證要求；兩者尚未完成真實運作驗證，尚未進入 P0.5-04，因此本輪不直接合併。

## 三、第二組：統御方案系統 vs 統御小系統協調管理系統
### 3.1 直接證據
「統御方案系統-v1.0」定位為統御的系統索引與觸發歸屬分支：知道有哪些系統、各系統屬於哪個方案、尚未歸屬方案的小系統由誰負責觸發；已歸屬方案的系統，其觸發管理應移交方案。
其核心是：系統／方案索引 + 未歸屬小系統的暫時觸發管理權。
「統御小系統協調管理系統-v1.0」則定位為讓統御層辨識、檢查並操作目前已建立的小系統，現階段主要管理 SS-001、SS-002，包括查看狀態、待驗證標記、自然觸發機會、允許的最小驗證、結果記錄與異常標記。

### 3.2 語義比較
| 維度 | 統御方案系統 | 統御小系統協調管理系統 | 判定 |
|---|---|---|---|
| 對象 | 全部系統＋未歸屬小系統 | 已建立的小系統，現階段 SS-001/SS-002 | 範圍不同 |
| 系統索引 | 核心 | 非主要責任 | 前者主責 |
| 方案歸屬 | 核心 | 不負責完整方案治理 | 前者主責 |
| 未歸屬小系統觸發 | 核心 | 有自然觸發操作 | 高度重疊 |
| 小系統狀態檢查 | 有 | 核心 | 重疊 |
| 小系統驗證 | 觸發後交給小系統 | 核心 | 有介面關係 |
| 小系統生命週期 | 只索引狀態 | 不直接管理生命週期，只檢查 | 邊界可分 |
| 統御方案本身 | 索引／觸發歸屬 | 明確不是正式統御方案 | 不同層級 |

### 3.3 判定
這一組不能直接判定為同一系統的版本演化。
較合理的是：「統御方案系統」是較高層的統御索引／觸發歸屬候選；「統御小系統協調管理系統」是其中一項針對小系統的最小協調能力候選。
但兩者仍存在明顯責任交疊，尤其是小系統狀態檢查、自然觸發、未歸屬小系統管理。
因此目前最安全的判定是：System Candidate + Sub-capability Candidate / Responsibility Overlap。
目前不能判定為兩個已成立獨立 System，也不能判定為完全相同。

### 3.4 State / Disposition
| 文件 | State | Disposition |
|---|---|---|
| 統御方案系統-v1.0 | REVIEW | KEEP / System Candidate |
| 統御小系統協調管理系統-v1.0 | REVIEW | KEEP / Sub-capability Candidate |
兩者均待實際施工驗證，目前不建立第二個正式 System ID。

## 四、與整體資料治理系統的上層邊界
「整體資料治理系統-v1.0」負責共同資料類型與邊界、共同資料語義、狀態版本關係共同語義、來源追溯原則、跨方案資料規則一致性、共同資料契約變更審查。
它不是 System Registry、系統路由器、小系統觸發管理器或問題解決系統。
因此目前形成三層不同責任：
資料治理 → 定義跨方案共同資料規則。
System Registry / Catalog → 說明有哪些系統、系統是誰、在哪裡、狀態如何、屬於哪個方案。
統御／小系統協調候選 → 在目前架構中處理尚未歸屬方案的小系統之索引、觸發與最小協調。
三者不能因為都具有「管理」或「治理」文字而合併。

## 五、目前發現的真正架構風險
### 風險 1：同一 System Registry 有兩份文件
這是已確認的高風險重疊。應在 P0.5-04 做語義收斂時形成一個 Canonical System Registry 規格，而不是保留兩個平行正式系統。歷史版本仍保留可追溯。
### 風險 2：統御方案與小系統協調有責任交叉
目前文件有意保留這個分層，但實際執行責任尚未被案例證明。需要驗證誰負責判斷小系統是否應被觸發，避免 Double Trigger 或 Missed Trigger。
### 風險 3：統御層可能逐步膨脹
兩份文件都禁止把統御變成大型中央控制器。因此後續不能因發現更多小系統，就自然增加統御子系統、監控器、協調器、引擎或中央事件匯流排；都必須由真實瓶頸證明。

## 六、與 Trigger Registry 的邊界
Trigger Registry → 找可能需要被啟動的系統／能力。
System Registry → 認識系統是誰、在哪裡、狀態如何、屬於哪個方案。
目前統御文件中的觸發管理屬於特殊情況：僅針對尚未歸屬方案的小系統，暫時承擔觸發入口。
這不能被擴張解讀為統御系統本身就是 Trigger Engine。

## 七、目前不做的事情
1. 不刪除任一原文件。
2. 不把兩組文件直接合併。
3. 不建立新的 System ID。
4. 不建立新的 Capability ID。
5. 不建立大型統御系統。
6. 不建立中央事件引擎。
7. 不提前建立完整 System Graph。
8. 不因文件內容完整就宣布系統已成立。
9. 不提前進行 P0.5-04 的實際遷移。

## 八、本輪結論
第一組：「系統管理統御分支-v1.0」與「系統管理統御分支系統-v1.0」是同一 System Registry / System Catalog 責任的兩層文件，不應視為兩個獨立系統。
目前：v1.0 = Architecture Evidence；v1.0「系統」版本 = Current Candidate Specification；均 REVIEW；未建立第二個 System ID。
第二組：「統御方案系統-v1.0」與「統御小系統協調管理系統-v1.0」不是目前可以直接判定為同一系統，也不能證明為兩個完全獨立正式系統。
較合理的暫定模型：統御方案系統 → 全域系統／方案／未歸屬小系統索引與觸發歸屬；統御小系統協調管理 → 對小系統進行最小狀態檢查與自然工作協調的候選能力。
目前保留為 System Candidate + Sub-capability Candidate，待實際施工驗證後再決定最終拆分／整合。

## 九、對 P0.5-04 的預備要求
### A. System Registry Canonical 收斂
將兩份 System Registry 文件的定位、最小資料、操作、異常、驗證整理成單一 Canonical 語義來源；歷史版本仍保留可追溯。
### B. 統御責任分界
需要實際驗證：System Registry 認識系統；Trigger Registry 找候選系統；統御候選只處理未歸屬小系統的暫時協調。不得讓三者形成重複 Trigger。
### C. 小系統升格／移交
需要驗證：未歸屬小系統 → 統御暫時管理 → 納入正式方案 → 觸發責任移交 → 統御停止重複管理。
