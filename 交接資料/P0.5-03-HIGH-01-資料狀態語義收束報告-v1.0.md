# P0.5-03 HIGH-01 語義收束報告：資料狀態與生命週期原理 vs 資料狀態模型-v1.0

日期：2026-09-18
階段：P0.5-03
類型：HIGH-01／全文語義比較與 State Vocabulary 判定
狀態：本輪完成；原始知識文件未修改

## 一、審查對象

1. `0-知識/管理/資料狀態與生命週期原理.md`
2. `0-知識/更新/資料狀態模型.md`

本輪目的：

- 確認兩份文件是否為同一模型的不同層級。
- 確認 State Set 是否真正衝突。
- 確認是否存在直接 Conflict。
- 判定 Canonical / Evolution / Complementary 關係。
- 判定是否需要統一 State Vocabulary。

## 二、全文比較結果

### 1. 共同不變原則

兩份文件的核心語義高度一致：

- 資料內容與資料狀態必須分離。
- 資料存在不代表目前有效或可直接採用。
- 最新文件不等於最新有效內容。
- 歷史資料不能直接當作目前規則。
- 狀態不是可信度。
- 文件被修改不等於知識已更新。
- 狀態變更需要內容、證據、決策、版本、時間或適用條件等依據。
- 不應在沒有實際案例前建立複雜自動狀態機或自動狀態推理引擎。

因此兩份文件不是互不相關的兩套模型，而是共享同一核心治理思想。

## 三、真正差異

### A. 資料狀態與生命週期原理

主要回答：

> 「資料狀態這個概念應如何理解，以及它在治理上如何使用？」

其狀態集合：

- 草稿 Draft
- 待確認 Pending
- 已採用 Active
- 歷史 Historical
- 廢棄 Deprecated

並明確強調：

- 狀態 ≠ 版本
- 狀態 ≠ 可信度
- 「目前」不是單純狀態名稱，而是結合狀態、版本、有效時間、適用範圍與條件的工作判定。
- 三方案具有不同責任邊界。

因此它偏向「治理／原理層」。

### B. 資料狀態模型

主要回答：

> 「在實際更新、搜尋與知識工作中，如何辨識不同種類的資料狀態？」

其集合：

- 待確認
- 已確認
- 建立中
- 歷史
- 已失效
- 已否決

並新增幾個重要語義：

- 文件狀態、內容狀態、採用狀態可以不同。
- 「已確認」不等於「已採用」。
- 「建立中」主要描述工作進度。
- 「已否決」是決策結果，不等於單純失效。
- AI 輸出預設為候選內容。
- 搜尋結果必須辨識目前、歷史、待確認、否決等狀態。

因此它偏向「操作／應用模型層」。

## 四、State Set 是否不一致？

結論：

**表面 State Set 不一致，但不是直接 Conflict。**

原因是兩份文件把不同語義維度壓在「狀態」這個詞下。

目前可辨識：

| 語義 | 管理／生命週期原理 | 更新／資料狀態模型 | 判定 |
|---|---|---|---|
| 工作／文件進度 | 草稿 | 建立中 | 不同語義，不能直接合併 |
| 確認程度 | 待確認 | 待確認／已確認 | 更新版更細 |
| 採用狀態 | 已採用 | 尚未獨立命名 | 管理版明確 |
| 歷史位置 | 歷史 | 歷史 | 高度一致 |
| 目前不再適用 | 廢棄 | 已失效 | 高度相關，但語義仍不完全相同 |
| 決策否決 | 無對應 | 已否決 | 更新版新增維度 |

因此：

**不能把兩份清單直接 union 成一個 State Set。**

如果直接形成：

`草稿／建立中／待確認／已確認／已採用／歷史／廢棄／已失效／已否決`

反而會製造一個混合狀態機，把「文件工作進度」「內容確認」「採用」「歷史／有效性」「決策結果」錯誤地視為同一條互斥生命週期。

## 五、是否存在真正 Conflict？

目前判定：

**沒有足夠證據形成 Direct Conflict。**

目前看到的是：

**Semantic Divergence / Model Granularity Difference**

而不是：

**Core Knowledge Conflict**

例如：

- 「已確認」與「已採用」可以同時成立，因此不是互斥值。
- 「建立中」與「草稿」也可能同時成立，因此不是同一維度。
- 「已否決」表示決策結果，不必然表示內容不存在歷史價值。
- 「歷史」與「已失效」可以描述不同語義，不應直接視為同義。

## 六、是否為同一模型不同層級？

判定：

**部分是，同時存在不同維度；不能簡化為單純上下層。**

更精確地說：

`資料狀態與生命週期原理`
→ 提供治理語義與生命週期的共同原則。

`資料狀態模型`
→ 將其中一部分原則延伸到實際更新、搜尋與工作判定，並引入文件／內容／採用／決策等不同狀態語義。

因此兩者關係應標記為：

**Shared Core + Complementary Operational Model**

而不是：

- Duplicate
- Direct Conflict
- 單純新版取代舊版

## 七、Canonical 判定

本輪不指定單一文件吞併另一份。

暫定角色：

### Canonical Candidate：資料狀態與生命週期原理

理由：

- 提供較高層、跨方案的治理原則。
- 定義狀態與版本、時間、適用條件的關係。
- 定義「目前」的工作判定。
- 定義三方案責任邊界。

但注意：

**目前仍是 Canonical Candidate，不是正式 CURRENT Canonical 宣告。**

### Complementary / Operational Candidate：資料狀態模型

理由：

- 提供更新工作中的細化語義。
- 補足文件狀態、內容確認、採用狀態與否決等實務差異。
- 對搜尋與更新流程提供操作判定。

因此不是單純 Evolution。

## 八、是否需要統一 State Vocabulary？

結論分成兩層：

### 1. P0.5 資產治理 State Vocabulary

**需要統一，而且已經存在。**

目前 Repository 的資產治理 State：

`CURRENT / REVIEW / DEPRECATED / RETIRED / HISTORICAL`

這是：

> 「這個 Repository 資產目前在工程治理中的位置」

不能拿來取代兩份知識文件中的內容狀態。

### 2. 知識內容生命週期 Vocabulary

**目前不應強行統一成單一 State Set。**

應統一的是「語義維度」，不是把所有詞塞進同一個狀態機。

目前較合理的候選維度為：

- 文件／工作進度
- 內容確認程度
- 採用狀態
- 歷史／有效性
- 決策結果

注意：

這只是本輪語義分析所得的 Derived Model。

**尚未經自然工作案例驗證，不應現在固化成正式資料模型或狀態資料庫。**
