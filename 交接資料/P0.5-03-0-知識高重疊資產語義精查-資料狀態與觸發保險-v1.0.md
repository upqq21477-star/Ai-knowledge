## 二、資料狀態兩文件

### 1. 相同語義

兩份文件均明確主張：

- 內容與狀態必須分離。
- 最新文件不等於最新有效內容。
- 歷史內容不能直接當目前規則。
- 狀態不是可信度。
- 狀態變更需要依據。
- 不應提前建立複雜狀態機或自動判斷引擎。
- 狀態判定需要考慮時間、版本、適用條件等因素。

因此不是單純相關，而是存在實質語義重疊。

### 2. 主要差異

「資料狀態與生命週期原理」偏治理原理，狀態集合為：草稿、待確認、已採用、歷史、廢棄；並強調三方案責任邊界與「目前」是一種工作判定。

「資料狀態模型」偏操作模型，增加建立中、已確認、已失效、已否決，並明確區分文件狀態、內容狀態、採用狀態。

最重要的差異是：

已確認 ≠ 已採用。

這表示兩文件不能直接拼接成一個單一狀態欄位；若強行合併，可能把內容確認與目前採用混成同一維度。

「歷史」與「已失效」也不能直接視為同義。

## 三、觸發條件管理兩文件

### 1. 演化關係

v1.0 與無版本檔的核心定義高度一致：

- Trigger 是第二層啟動保險，而非主要啟動源。
- Trigger 命中不等於立即啟動。
- 已啟動、執行中或已處理時不得二次啟動。
- 多重匹配與狀態不明時不應無條件擴大啟動。
- Event ID → Trigger ID → System ID → 處理狀態形成最小安全閉環。
- 必須透過自然工作案例驗證。

無版本檔在此基礎上進一步增加：

- Duplicate Activation
- Re-entrancy
- Trigger Loop
- Multiple Match
- Idempotency
- 最小必要執行狀態
- 禁止事項
- 更完整的自然案例驗證要求

因此，依內容證據可將無版本檔判為「後續擴充／演化候選」。這不是依檔名新舊判定，而是依核心內容包含關係判定。

### 2. 尚不能直接歷史化 v1.0

目前仍沒有在本輪取得「無版本檔正式取代 v1.0」的明確決策證據；兩份文件也都仍屬候選知識、尚待自然案例驗證。

因此：

v1.0：REVIEW / 候選歷史演化證據 / KEEP。

無版本檔：REVIEW / 較完整候選 / KEEP。

是否立即刪除 v1.0：否。

是否立即合併：否。
