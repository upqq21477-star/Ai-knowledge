## 四、差異與保留內容

### 應保留自「資料層級與分類」

1. 不採用硬性 DIKW 階梯。
2. Source ≠ Evidence ≠ Knowledge。
3. Document 是承載形式，不是資料層級。
4. Memory ≠ Knowledge。
5. Decision ≠ Knowledge。
6. State ≠ Data Type。
7. Classification ≠ Data Property。
8. 以「內容＋適用條件＋依據＋來源／證據＋重用目的＋狀態＋分類」作為最小關係。
9. 第一輪實際驗證結果與驗證限制。

### 應保留自「核心資料類型與邊界」

1. Claim 作為獨立語義物件。
2. 八種核心語義集合的共同方案用途。
3. Knowledge / Memory / Current State / Source / Evidence / Claim / Decision / Observation 的最小定義。
4. Capability / System / Plan 等能力物件與資料語義的層次分離。
5. Current State 的時間、範圍、條件與歷史脈絡要求。
6. 最小轉換關係。
7. 不建立 Metadata Schema、Database、Knowledge Graph、Vector DB、自動分類或複雜 ID 系統的工程邊界。
8. 以實際案例決定是否增加或修改資料類型。

## 五、初步蒸餾方向

目前不應把兩份原文直接合併成單一全文。

較合理的候選結構：

`資料語義基準`

1. 定位：資料語義模型，不是 Database Schema
2. 核心語義集合
3. 各語義邊界
4. Source / Evidence / Claim 關係
5. Knowledge / Memory / Current State / Decision / Observation 關係
6. Document / File / Note = 承載形式
7. Classification / State = 管理維度，不等於資料類型
8. Capability / System / Plan = 能力層，不與資料語義混合
9. 最小關係模型
10. 已驗證案例
11. 已知限制與待驗證案例
12. 工程禁止事項

## 六、需要特別避免的語義錯誤

### 1. 不把「八種核心類型」當固定宇宙

八種是目前共同使用的最小集合候選，不宣稱所有未來資料都必須落入其中。

### 2. 不把 Current State 與 P0.5 Asset State 混合

P0.5 Asset State：

`CURRENT / REVIEW / DEPRECATED / RETIRED / HISTORICAL / UNKNOWN`

與「目前狀態」的內容語義不同。

### 3. 不把 Claim 強制視為獨立檔案

Claim 可以存在於文件中，不需要一個 Claim Database。

### 4. 不把關係圖直接實作成 Knowledge Graph

目前只是語義關係，不代表需要圖資料庫。

## 七、驗證要求

候選文件至少需要實際檢查：

1. 既有 Repository 文件能否用同一組語義描述。
2. 混合內容文件能否同時表達多種語義。
3. Claim、Evidence、Source 是否能實際區分。
4. Decision、Current State、Knowledge 是否能避免互相誤判。
5. Memory 是否能保留背景而不被誤當通用 Knowledge。
6. 目前八種集合是否出現無法合理歸類的真實案例。
7. 三方案是否能使用相同語義而不產生衝突。
