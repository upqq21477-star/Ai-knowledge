# 二、第一組：資料狀態與生命週期原理 vs 資料狀態模型

## 2.1 原始文件

---

## 2.2 共同核心

兩份文件都建立同一個基本命題：

> 資料的「內容」與「目前狀態」必須分開理解。

共同否定：

- 資料存在 ≠ 目前有效
- 文件較新 ≠ 內容一定較正確
- 歷史資料 ≠ 目前規則
- 狀態 ≠ 內容本身
- 狀態 ≠ 單純檔案修改時間

因此兩者存在高度語義重疊。

---

## 2.3 實際差異

### A.「資料狀態與生命週期原理」偏治理語義

核心問題是：

> 資料現在處於什麼工作／採用狀態？

其最小集合：

- 草稿 Draft
- 待確認 Pending
- 已採用 Active
- 歷史 Historical
- 廢棄 Deprecated

並明確區分：

- 狀態
- 版本
- 時間
- 有效範圍
- 適用條件
- 可信度／證據充分性

此外，它明確建立「生命週期」概念：

建立 → 待確認 → 已採用 → 修正／替換 → 歷史或廢棄。

### B.「資料狀態模型」偏實際更新與多維狀態

其集合為：

- 待確認
- 已確認
- 建立中
- 歷史
- 已失效
- 已否決

更重要的是，它增加了「狀態不是單一維度」：

- 文件狀態
- 內容狀態
- 採用狀態

可能同時不同。

例如：

> 文件建立中；內容部分已確認；方案尚未採用。

此外新增：

- 已否決的保存價值
- AI 輸出預設為候選內容
- 搜尋後必須再判定目前狀態
- 時間＋內容＋決策＋適用條件共同判定
- 不建立複雜狀態資料庫或自動推理引擎

---

## 2.4 是否衝突

結論：**沒有發現直接邏輯衝突，但存在術語／層級重疊。**

最需要避免的是把兩套集合直接視為同一個 Enum。

例如：

- Active 與 已確認 不必然完全相同。
- Deprecated 與 已失效 高度相關，但一個偏採用狀態／生命週期，一個偏目前適用性。
- 草稿／建立中可能描述文件工作狀態，而非知識真偽。
- 已否決是決策結果，不應簡化成「錯誤」。
- Historical 是時間／採用歷史語義，不等於失效。

因此不能直接「選一份刪另一份」。

---

## 2.5 P0.5-04 建議

**判定：可進入 P0.5-04 語義蒸餾，但不是直接合併。**

建議採「分層蒸餾」：

### 保留第一份的內容

- 狀態與內容／版本／時間的基本分離
- 最小生命週期概念
- 狀態不是可信度
- 「目前」不是單一狀態名稱，而是綜合判定
- 三方案責任邊界
- 不建立大型自動狀態機

### 保留第二份的內容

- 文件狀態／內容狀態／採用狀態多維區分
- 已否決的歷史價值
- AI 輸出 → 待確認 → 查證／比較／實驗 → 確認
- 搜尋結果必須附帶狀態判讀
- 時間、內容、決策、適用條件共同判定
- 更細的「已失效」與「已否決」語義

### 蒸餾目標

建立一份未來可作為「資料狀態語義基準」的文件，同時避免把：

- Asset State
- Document State
- Content State
- Adoption State
- Decision State

混成一個欄位。

注意：P0.5 規範中的 CURRENT / REVIEW / DEPRECATED / RETIRED / HISTORICAL / UNKNOWN 是「資產盤點／治理狀態」，不能直接拿來取代這兩份文件討論的內容狀態。

---

## 3.2 重疊程度

兩份文件的核心定義、用途與安全邊界高度一致：

- Trigger 不是第一啟動源
- 是第二層啟動保險
- 命中不等於立即啟動
- 必須確認目標系統目前處理狀態
- 防止二次啟動
- 防止 Re-entrancy
- 防止 Trigger Loop
- 防止 Multiple Match 擴大啟動
- 不確定時不擴大
- 不建立中央事件總線
- 不建立複雜規則引擎作為第一版前提
- 必須用自然工作案例驗證

因此這不是兩個獨立概念，而是同一原理的版本演化候選。

---

## 3.3 無版本文件新增內容

無版本文件在 v1.0 基礎上增加：

1. 明確說明為何需要啟動保險。
2. Duplicate Activation 的更完整描述。
3. Re-entrancy、Trigger Loop、Multiple Match 的操作化描述。
4. 冪等性 Idempotency。
5. Event ID / Trigger ID / System ID / 處理狀態的最小模型。
6. 最小執行狀態集合：
   - 未啟動
   - 啟動中
   - 執行中
   - 已處理／已完成
   - 暫停／失效
   - 狀態不明
7. 明確限制：啟動保險不能接管完整執行狀態。
8. 外部方法比較：
   - Kubernetes Controller
   - Backstage Software Catalog
   - Microsoft 事件架構
9. 更完整的禁止事項。
10. 五項自然工作驗證條件。

因此無版本文件不是單純複製 v1.0，而是擴充版／後續版的強烈證據。

---

## 3.4 是否衝突

結論：**未發現核心邏輯衝突。**

差異主要是：

> v1.0 = 初版最小原理  
> 無版本 = 擴充後的候選正式內容

而且無版本文件仍明確寫「待自然工作案例驗證」，所以不能把它視為已經 FIELD 驗證成立。
