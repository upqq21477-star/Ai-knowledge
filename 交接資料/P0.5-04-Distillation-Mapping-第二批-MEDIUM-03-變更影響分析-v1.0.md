## 三、責任分層

### A. 共同最小原理

`變更影響分析最小原則.md` 的主要責任是建立跨方案可共用的最小語義：

- Impact Analysis 的目的與邊界。
- Identity / Relationship / Dependency / Usage。
- Version / Compatibility。
- Validation / Lifecycle / Data / History。
- Direct Impact 與 Indirect Impact 的區分。
- Candidate / Confirmed / No Impact / Unknown。
- Impact Analysis 不等於 Change Decision。
- 分析深度應依風險與影響範圍調整。
- 第一次驗證應以真實變更案件人工執行，而不是先建大型 Engine。

判定：**共同原理 Canonical Candidate。**

### B. 更新場景應用

`變更影響分析與影響範圍.md` 的主要責任是把共同原理落成更新工作流程：

- 建立變更集。
- 找第一層直接影響。
- 逐層追蹤。
- 每層重新判斷是否真正進入使用範圍。
- 設定停止條件。
- 使用簡單文字圖／表格表示影響範圍。
- 輸出變更集、直接／間接影響、不受影響、待確認、邊界與更新建議。
- 明確說明 false positive / false negative 限制。

判定：**更新場景應用／流程 Candidate。**

## 四、共同語義應保留

蒸餾候選至少必須保留：

1. 影響分析的目的，是找出「需要注意／重新檢查／驗證／遷移／停止使用」的可能範圍，不是預測所有問題。
2. 影響分析從變更對象出發，沿實際 Identity / Relationship / Dependency / Usage 追蹤。
3. 關係存在不代表一定受影響。
4. Direct Impact 與 Indirect Impact 必須區分。
5. 必須允許 Unknown / 待確認。
6. 必須有停止條件，避免無限擴散。
7. Impact Analysis 不直接做 Change Decision。
8. 影響集合是目前證據下的分析結果，不是絕對完整真實集合。
9. 第一次驗證優先人工處理真實案件。
10. 沒有真實案例前，不建立大型全域 Impact Graph Engine。

## 五、不得直接抽成共同規則的內容

以下屬更新場景或目前專案應用，不直接寫入通用候選的核心規則：

- 「知識、系統、方案、應用」四類第一層對象清單。
- 特定的 Markdown 影響範圍圖格式。
- 特定輸出表格欄位。
- 「變更集」的具體欄位格式。
- 與 `知識更新原理.md` 的目前專案文件關係。
- 與 `系統依賴.md` 的目前文件關係。
- 任何尚未經自然工作驗證的自動化流程。

這些可作為應用／流程層範例，而不是宣告為全庫唯一格式。

## 七、Validation Requirements

候選蒸餾後至少需要以下實際驗證：

1. 選擇一個真實 Repository 變更案件，人工執行完整影響分析。
2. 比較「預測／候選影響」與「實際發生的影響」。
3. 檢查 Direct / Indirect / Unknown 是否能穩定區分。
4. 檢查停止條件是否能阻止無意義擴散。
5. 檢查是否能發現需要同步更新的下游文件／系統／方案。
6. 檢查是否產生過量 false positive。
7. 檢查不同變更風險下是否能合理調整分析深度。
8. 驗證 Impact Analysis 與 Change Decision 是否仍保持責任分離。
9. 驗證人工流程是否已產生足夠穩定價值，再決定是否值得系統化。
