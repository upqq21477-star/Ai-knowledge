## 一、稽核目的

本輪承接 P0.5-03-5、P0.5-03-6、P0.5-03-7，專門檢查三組高風險共用功能：

1. C5 ↔ D3：Capability Inventory
2. A11 ↔ C6 ↔ D13：Impact
3. A5 ↔ C15 ↔ D18：State／History

目的不是把同名功能合併，而是確認：

- 是否真的存在可共享的 Capability。
- 哪些只是同名但 Context／Decision Purpose 不同。
- 哪些責任屬於方案、哪些屬於共同 Capability。
- 是否已經有足夠證據建立獨立 System。
- 既有 Blueprint Mapping 是否有語義衝突。

## 二、核心判定規則

本輪採用：

`Same Capability ≠ Same Process ≠ Same System ≠ Same Plan Responsibility`

判斷共用 Capability 必須至少觀察：

1. 目的是否相同或可抽象為同一能力。
2. 輸入／輸出是否具有可重用的核心結構。
3. 成功條件是否相容。
4. 不同方案是否只是 Context 不同。
5. 是否需要不同的決策權限。
6. 是否存在不同的資料狀態／生命週期語義。
7. 是否已有 Canonical Source 支持。

## 三、C5 ↔ D3：Capability Inventory

### C5 Canonical Responsibility

方案三 C5「既有能力盤點」的直接證據：

- C4 變更目標確認後進入 C5。
- 目的為先確認既有能力是否足以處理變更。
- 原則是「不因需求出現就新增系統」。
- C5 結果會影響後續 C7 演化必要性判定與 C8 候選變更。

因此 C5 的核心決策問題是：

`這次變更是否已有可用能力？`

### D3 Canonical Responsibility

方案四 D3「能力盤點」位於：

`D1 Case → D2 Scope → D3 Inventory → D4 Usage/Dependency Evidence`

D3 必須在蒸餾案件範圍內盤點實際存在的能力、System、依賴與相關結構，並為後續 D6 語義分析、D7 重疊分析、D8 責任邊界分析提供材料。

核心問題是：

`這個蒸餾案件範圍內，實際有哪些能力與結構？`

### 邊界結論

C5 與 D3 **應共享 Capability：CAP-33 Capability Inventory**。

但不能合併為同一個 Process。

| 面向 | C5 | D3 |
|---|---|---|
| 方案 | 方案三 | 方案四 |
| 目的 | 判斷變更是否已有能力可用 | 建立蒸餾案件的能力盤點基礎 |
| 前置 | C1–C4 | D1–D2 |
| 後續 | C6/C7/C8 | D4–D10 |
| Context | 正常演化案件 | 蒸餾／重構案件 |
| 決策角色 | 支援「是否演化」 | 支援「如何蒸餾／重構」 |
| Capability | CAP-33 | CAP-33 |
| System | 尚無證據需獨立 Inventory System | 尚無證據需獨立 Inventory System |

因此：

`CAP-33 = Shared Capability`

但：

`C5 Process ≠ D3 Process`

### 重要修正

目前 Blueprint 將 C5、D3 都 Mapping 至 CAP-33 是合理的，不應因重複而拆成 CAP-33A / CAP-33B，也不應建立兩套 Inventory System。

未來若真正出現大量重複盤點、手工成本或一致性問題，再以實際工程證據判斷是否需要 Inventory System。

## 四、A11 ↔ C6 ↔ D13：Impact

### A11 Canonical Responsibility

方案一 A11「Impact」負責：

- 識別變更可能影響的關係、依賴、使用者、System、驗證案例、下游對象。
- 表達的是影響範圍分析。
- 不把 Potential Impact 當成 Actual Outcome。

A11 是共同治理語義的重要基礎。

### C6 Canonical Responsibility

方案三 C6 位於：

`C5 → C6 → C7`

用途是分析正常演化案件中，變更可能造成的影響，供演化必要性與候選變更判斷使用。

### D13 Canonical Responsibility

方案四 D13 位於：

`D11 → D12 → D13 → D14`

用途是比較候選蒸餾／重構處置後的潛在影響，作為遷移條件與實施判斷的輸入。

### 邊界結論

三者應共享：

`CAP-11 Impact / 影響分析`

但三者的 Process Context 不同：

| 面向 | A11 | C6 | D13 |
|---|---|---|---|
| 層級 | 治理 | 正常演化 | 蒸餾／重構 |
| 問題 | 變更可能影響什麼 | 這次演化會影響什麼 | 候選重構會影響什麼 |
| 目的 | 建立共同 Impact 語義 | 支援演化決策 | 支援處置／遷移決策 |
| 結果 | Impact Relation / Scope | Evolution Impact | Refactoring Impact |
| Capability | CAP-11 | CAP-11 | CAP-11 |
| 獨立 System | 無充分證據 | 無充分證據 | 無充分證據 |

因此不能：

- 建立三個 Impact System。
- 讓 A11 吞掉 C6/D13 的方案決策責任。
- 讓 C6/D13 改寫共同 Impact 語義。
- 把 Potential Impact 當成實際發生結果。

合理模型：

`CAP-11 Shared Impact Capability + A/C/D-specific Process Context`

## 五、A5 ↔ C15 ↔ D18：State／History

這一組必須拆成兩層，不能簡化為「三個都是狀態」。

### A5 State

方案一 A5 負責 State 語義：

- 描述對象目前處於什麼狀態。
- State 不等於 Version。
- State 不等於 Lifecycle。
- State 不等於 History。
- 必要時可區分 validation_state、usage_state、lifecycle_state 等不同維度。

Mapping：

`A5 → CAP-05 State`

### C15 Current State Update

方案三 C15 是一個「使用 State Capability 的方案流程」。

其責任是：

`C13 Validation → C14 Adoption Gate → C15 Current State Update`

只有被採用的成功變更才能形成新的 Current State。

因此：

`C15 ≠ 第二套 State System`

而是：

`C15 Process → CAP-05 State`

### D18 Historical／Old Capability Preservation

D18 的正式責任是保存退出 Current 的舊能力與歷史追溯。

Mapping：

`D18 → CAP-09 History`

因此 D18 **不是 State Capability 的另一種版本**。

其核心是：

`Currentightarrow Historical`

但轉換本身必須保留：

- Identity
- Version
- Lifecycle
- History
- Traceability
- 原始 Evidence

### 邊界結論

這一組的正確結構：

```
CAP-05 State
   ↑
A5 Governance Semantics
   ↑
C15 Current State Update

CAP-09 History
   ↑
A9 History Semantics
   ↑
C16 / D18 使用
```

其中 D18 與 C16 可以共享 CAP-09，但不是同一個 Process。

| 功能 | 主要責任 | Capability |
|---|---|---|
| A5 | State 語義 | CAP-05 |
| C15 | 演化後 Current 更新 | CAP-05 |
| A9 | History 語義 | CAP-09 |
| C16 | 正常演化歷史保存 | CAP-09 |
| D18 | 蒸餾／重構後舊能力保存 | CAP-09 |

因此：

`A5 ≠ C15 ≠ D18`

同時：

`C15 ≠ D18`

但：

`C15 使用 CAP-05；D18 使用 CAP-09`

## 六、三組共用 Capability 最終判定

| 組別 | 是否共享 Capability | 是否共享 Process | 是否建立獨立 System | 最終 |
|---|---|---|---|---|
| C5 ↔ D3 | 是，CAP-33 | 否 | 否 | 保持 |
| A11 ↔ C6 ↔ D13 | 是，CAP-11 | 否 | 否 | 保持 |
| A5 ↔ C15 | 是，CAP-05 | 否 | 否 | 保持 |
| A9 ↔ C16 ↔ D18 | 是，CAP-09 | 否 | 否 | 保持 |

## 七、對現有 Blueprint Mapping 的影響

本輪沒有發現需要立即修改的 Mapping。

目前下列 Mapping 均與 Canonical Responsibility 相容：

```
C5  → CAP-33
D3  → CAP-33

A11 → CAP-11
C6  → CAP-11
D13 → CAP-11

A5  → CAP-05
C15 → CAP-05

A9  → CAP-09
C16 → CAP-09
D18 → CAP-09
```

但有一個重要的治理要求：

> Mapping 中「Capability 相同」不得被讀成「Plan Responsibility 相同」或「System 相同」。

因此未來 Capability Matrix 必須至少能區分：

`Function → Capability → Plan Context → Provider/System`

而不能只有：

`Function → Capability`

## 八、System 建立判定

三組稽核均沒有足夠證據支持新增：

- Capability Inventory System
- Impact Analysis System
- State System 2
- History System 2
- C/D 專用 State／History System

原因不是這些工作不存在，而是目前它們都能合理作為 Capability + Process 使用。

只有在實際工程中出現：

```
反覆人工執行
↓
固定輸入／輸出
↓
跨案件大量重複
↓
明確品質／成本瓶頸
↓
現有 Capability + Process 不足
↓
需要穩定邊界與可重用介面
```

才進入新 System 候選。

## 九、對前面 P0.5 稽核的修正確認

P0.5-03-5、P0.5-03-6、P0.5-03-7 的高階結論均可保留。

本文件提供的是三組高風險交叉點的細化證據，而不是改寫正式方案。

尤其確認：

1. Plan Function 不應因共享 Capability 而刪除。
2. Capability 不應因跨方案使用而被複製。
3. Process 不應因 Capability 相同而被強行合併。
4. System 不應因 Process 存在而自動建立。
5. Mapping 不應反過來成為 Canonical Source。

```
                 ┌───────────────┐

                 │ Capabilities  │
                 └───────┬───────┘
                         │
          ┌──────────────┼──────────────┐

       Scheme 1       Scheme 3       Scheme 4

          │              │              │
```
