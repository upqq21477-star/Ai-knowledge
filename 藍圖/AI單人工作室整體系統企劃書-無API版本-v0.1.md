# AI 單人工作室整體系統企劃書
## 無 API 版本 v0.1

> 文件性質：未來整體規畫／企劃書  
> 文件狀態：討論稿  
> 適用環境：單人工作室、GPT + GitHub、無 API  
> 重要界線：本文件不是現行四大方案之一，不取代現行工程架構，不代表已完成實作。

---

## 1. 文件定位

本企劃書描述一套適合單人工作室的 AI 工作環境。

目前環境假設：

- 使用者一人。
- GPT／ChatGPT 是主要智慧與推理核心。
- GitHub 是主要長期資料保存與版本控制中心。
- 沒有 API。
- 沒有常駐 Agent。
- 沒有背景 Worker。
- 沒有 Webhook、Event Bus、Scheduler。
- 沒有 Vector Database、Embedding Pipeline 或獨立 RAG 服務。
- GPT 可以在需要時讀取 Repository。
- 重要成果可以保存回 Repository。
- 未來可能取得電腦、API、付費模型或其他執行環境，因此現在的資料語義必須保留升級空間。

本企劃書的目的不是現在建立一個大型 AI 平台，而是建立：

> 「今天就能工作的完整無 API 基礎架構，未來取得 API 後可以逐步自動化，而不需要推翻已累積的知識、系統、方案、證據與歷史。」

本文件本身屬於「未來規畫」，不是第五方案，也不是現行工程狀態文件。

# 2. 核心目標

## 2.1 讓一個人能長期管理大型 AI 工作環境

Repository 可以持續增長，包含：

- 知識。
- 系統。
- 方案。
- 專案。
- 規則。
- 研究。
- 測試。
- 證據。
- 歷史。
- 交接資料。

但是單次任務不應因此被迫讀完整 Repository。

核心原則：

> 全域資料可以很大，單次運行上下文必須保持最小充分。

理想流程：

```
大型 Repository
↓
目前任務
↓
判斷任務類型
↓
定位相關系統／方案
↓
檢索必要知識
↓
組裝最小充分上下文
↓
GPT 工作
↓
驗證
↓
保存必要成果
```

---

## 2.2 降低 GPT 每次重新理解專案的成本

新 GPT 必須能快速恢復：

1. 專案目的。
2. 當前狀態。
3. 正式架構。
4. 現行規則。
5. 現行方案。
6. 系統有哪些能力。
7. 知識在哪裡。
8. 哪些資料是歷史。
9. 哪些資料正在等待確認。
10. 目前下一步是什麼。

因此 Repository 不只是「檔案儲存區」，而是：

> AI 的長期外部記憶與交接環境。

# 3. 無 API 環境模型

目前最實際的架構：

```
使用者
  ↓
GPT / ChatGPT
  ↓
GitHub Repository
```

三者責任：

### 使用者

負責：

- 最終方向。
- 需求。
- 重大決策。
- 高風險判斷。
- 是否正式採用重大架構。
- 是否進入正式修改。

### GPT

負責：

- 自然語言理解。
- Intent／意圖解析。
- 檢索決策。
- 知識理解。
- 研究。
- 推理。
- 規劃。
- 執行。
- 驗證。
- 交接。
- 必要時進行 Repository 操作。

### GitHub

負責：

- 長期保存。
- 版本控制。
- 歷史。
- 知識。
- 系統定義。
- 方案。
- 狀態。
- 規則。
- 證據。
- 交接。

# 4. 不應假設目前存在的能力

無 API 版本不得把以下能力視為已存在：

- 背景常駐 Agent。
- 自動監控對話。
- 自動監控 Repository。
- Webhook。
- Event Bus。
- Message Queue。
- Cron。
- Scheduler。
- Background Worker。
- 自動 Embedding。
- Vector Database。
- 獨立 RAG Pipeline。
- 自動 Agent Spawn。
- 自動通知。
- 長時間背景任務。

這些屬於未來 API／電腦環境的升級能力。

目前的實際模式是：

```
使用者提出任務
↓
GPT 判斷任務
↓
GPT 主動讀取必要資料
↓
GPT 執行
↓
GPT 驗證
↓
必要時保存結果
```

# 5. 核心設計原則

## 5.1 大架構，小運行

這是整套系統最重要的原則。

Repository 可以很大，但每一次任務只載入必要內容。

因此：

> 「系統很大」不等於「每次使用都很重」。

---

## 5.2 最小充分上下文

目標不是最少資訊，而是：

> 對目前任務足夠、正確、可驗證的最小資訊集合。

例如只問：

「方案四現在完成了嗎？」

不應讀：

- 全部知識庫。
- 所有歷史。
- 所有方案。
- 所有研究。

只需要：

- 方案四目前狀態。
- 必要的驗收／回歸資訊。

---

## 5.3 不追求最少文件，而追求最低有效複雜度

文件少不一定好。

如果一個索引能降低搜尋成本，就應保留。

如果一個管理機制只是重複另一份資料，就應合併。

如果一個系統沒有實際責任，也沒有實際使用價值，就不應只為了架構完整而建立。

---

## 5.4 需求驅動自動化

不要因為未來可能有 API，就現在先建立：

- Vector DB。
- Agent Framework。
- Event Bus。
- 自動 RAG。
- 複雜資料庫。

正確順序：

```
人工流程
↓
實際使用
↓
發現瓶頸
↓
確認瓶頸可重複
↓
自動化
```

# 7. 知識層

## 7.1 知識回答什麼

知識回答：

> 「什麼是什麼？什麼可以被重複使用？什麼有證據支持？」

知識不負責：

- 任務。
- TODO。
- 工作流程。
- 使用者指令。
- 當前工程游標。
- 執行狀態。
- 大型規劃。

---

## 7.2 原子化知識

理想知識單元應接近：

- 一個概念。
- 一個定義。
- 一個事實。
- 一個規則。
- 一個可獨立引用的判斷。

例如：

```
BM25 是基於詞項匹配的資訊檢索排序方法。
```

而不是把完整教學、案例、歷史、實作全部塞成一個不可拆解的大知識單元。

---

## 7.3 原子化不是越短越好

判斷標準不是字數，而是：

> 脫離原文章節後，這個知識是否仍能被正確理解？

「它速度很快」很短，但不是好的原子知識。

因為缺少主體、條件、比較對象。

---

## 7.4 知識不是全部永久有效

可以區分：

```
ACTIVE        有效
DEPRECATED    不建議使用
OBSOLETE      已過時
HISTORICAL    歷史
UNCERTAIN     尚未充分確認
CONTESTED     存在爭議
SUPERSEDED    已由新資料取代
```

過時資料不等於刪除。

歷史資料仍可能用於：

- 研究。
- 交接。
- 決策追蹤。
- 錯誤分析。
- 回溯。

---

## 7.5 知識建議資料結構

未來可以逐步形成：

```yaml
id:
名稱:
內容:
類型:
分類:
關鍵詞:
別名:
適用範圍:
來源:
證據:
狀態:
有效時間:
版本:
取代:
關聯:
備註:
```

無 API 階段不需要一次強制所有欄位全部制度化。

# 8. 圖書館系統

## 8.1 定義

圖書館負責：

> 「知道有哪些知識，以及如何找到知識。」

圖書館不是知識本身。

結構：

```
知識本體
↓
圖書館目錄
↓
索引
↓
搜尋
↓
選擇
```

---

## 8.2 第一階段

可以非常簡單：

```
知識/
├── 類別A/
├── 類別B/
├── 類別C/
└── ...
```

再搭配：

```
知識索引.md
```

索引至少回答：

- ID。
- 名稱。
- 分類。
- 關鍵詞。
- 用途。
- 狀態。
- 檔案位置。
- 關聯。

---

## 8.3 圖書館真正的核心

不是「有一份目錄」。

而是：

> GPT 能不能從一個任務快速找到正確知識。

理想查詢：

```
目前問題
↓
候選知識
↓
相關性
↓
狀態
↓
衝突檢查
↓
最小充分知識集合
```

# 9. 系統層

系統回答：

> 「我們能做什麼？」

例如：

- 交接系統。
- 知識搜尋系統。
- 研究系統。
- 問題解決系統。
- 文件生成系統。
- 驗證系統。
- GitHub 維護系統。
- 寫作系統。

---

## 9.1 系統與知識的區別

```
知識
= 知道什麼

系統
= 能做什麼

方案
= 如何解決問題
```

例如：

```
知識：
什麼是 BM25。

系統：
研究資訊檢索技術。

方案：
如何判斷某種檢索架構是否適合目前知識庫。
```

---

# 10. 系統管理

系統管理負責：

> 「有哪些系統？每個系統負責什麼？需要什麼資料？什麼情況下使用？」

建議系統目錄包含：

```
系統 ID
系統名稱
目的
能力
輸入
輸出
適用情境
依賴知識
依賴系統
所屬方案
觸發條件
限制
驗證方式
狀態
版本
```

---

## 10.1 系統不要複製知識

不建議：

```
系統 A
└── BM25 知識

系統 B
└── BM25 知識

系統 C
└── BM25 知識
```

應該：

```
              BM25 知識
                   ↑
          ┌────────┼────────┐
          │        │        │
       系統 A    系統 B    系統 C
```

系統引用／依賴知識。

---

# 11. 方案層

方案回答：

> 「面對問題，我們如何解決？」

因此：

```
知識 = 知道什麼
系統 = 能做什麼
方案 = 如何解決
```

---

## 11.1 現有四大方案的位置

本企劃書不取代現有四方案。

目前四方案仍是：

1. 整體資料治理方案。
2. AI 知識管理方案。
3. 知識與資料迭代演化方案。
4. 能力蒸餾與系統重構方案。

其定位是：

> 工程治理方法。

而圖書館、系統庫、意圖解析、統御等是：

> 未來日常運行架構。

兩者不應混成第五方案。

---

# 12. 觸發管理

無 API 時，「觸發管理」不是常駐監聽器，而是：

> 觸發索引與候選規則。

例如：

```
建立
├── 建立知識
├── 建立系統
├── 建立方案
├── 建立文件
└── 建立專案
```

關鍵詞的功能是：

> 高召回地找到候選。

不是直接決定執行哪一個系統。

---

## 12.1 關鍵詞不能直接觸發

例如：

「我想建立人脈。」

不能因為出現「建立」就啟動「建立系統」。

因此：

```
關鍵詞
= 候選召回

上下文 + 語義
= 最終判斷
```

---

# 13. 對話／意圖解析

這是無 API 版本非常重要的一層。

目標：

> 將自然語言轉換成可操作的任務描述。

例如：

```
「方案四做到哪？」

↓
intent = STATUS_QUERY
target = 方案四
action = READ_STATUS
execution = false
detail = short
```

另一例：

```
「重新研究方案四是不是還有問題。」

↓
intent = RESEARCH
target = 方案四
depth = deep
repository = read
web_research = true
execution = false
```

---

# 14. 建議初期 Intent

不要一開始建立數百種。

可以先：

```
STATUS       查狀態
LOOKUP       查資料
EXPLAIN      解釋
DISCUSS      討論
RESEARCH     研究
COMPARE      比較
PLAN         規劃
CREATE       建立
EDIT         修改
VERIFY       驗證
DEBUG        排查
EXECUTE      執行
REVIEW       審查
HANDOFF      交接
SUMMARIZE    彙整
```

未來由實際誤判案例再增加。

---

# 15. 回應契約

意圖解析不只判斷「要做什麼」，還應判斷：

- 詳細程度。
- 是否需要外部搜尋。
- 是否需要 Repository。
- 是否允許修改。
- 是否需要建立文件。
- 是否只是回答。
- 是否需要驗證。
- 是否需要交接。

例如：

「目前狀態？」

```
STATUS
短
只讀
不研究
不修改
```

「重新研究架構。」

```
RESEARCH
深入
讀 Repository
外部研究
比較
反例
不直接修改
```

# 16. 藍圖規劃

藍圖不是每次任務都要啟動。

它負責：

> 把中大型問題轉成可執行結構。

基本流程：

```
目標
↓
問題拆解
↓
影響範圍
↓
依賴
↓
風險
↓
優先順序
↓
執行順序
↓
驗證
```

---

## 16.1 任務分級

### 小型任務

例如：

- 查狀態。
- 找文件。
- 修一個文字。
- 回答一個問題。

直接處理。

### 中型任務

例如：

- 整理一組文件。
- 小型系統修改。
- 局部研究。

使用簡易規劃。

### 大型任務

例如：

- 改變資料格式。
- 重新設計知識分類。
- 新建核心系統。
- 大型架構重構。

使用完整藍圖、外部研究、壓力測試與驗證。

---

# 17. 統御核心

統御核心回答：

> 「目前這個任務，下一步應該做什麼？」

可能選擇：

```
查知識
查系統
查方案
研究
規劃
執行
驗證
交接
保存
```

它不應是固定死流程。

而應根據：

```
使用者目標
+
目前狀態
+
可用能力
+
限制
+
證據
+
風險
```

決定下一步。

---

# 18. GPT 的角色

目前不需要把每個角色拆成獨立 Agent。

GPT 可以根據任務切換：

- 理解者。
- 研究者。
- 規劃者。
- 執行者。
- 驗證者。
- 審查者。
- 交接者。

「角色」可以存在於方法與規則中，不必全部變成常駐軟體。

這符合單人工作室的低維護原則。

---

# 19. 驗證

「做完」不等於「做對」。

至少區分：

### 結果正確性

輸出是否正確？

### 行為正確性

系統是否按照預期工作？

### 架構健康性

修改是否造成：

- 重複。
- 衝突。
- 依賴錯誤。
- 入口漂移。
- 上下文膨脹。
- 責任重疊。
- 版本漂移。

---

# 20. 證據

重要判斷不應只有：

> GPT 說它正確。

應盡量留下：

- 來源。
- 研究結果。
- 測試結果。
- 回歸結果。
- Observation。
- 決策理由。
- 修改內容。
- 驗證結果。

目的：

> 讓未來 GPT 能理解「為什麼這個結論存在」。

---

# 21. GitHub 的定位

GitHub 同時承擔：

- 長期記憶。
- 文件系統。
- 版本控制。
- 歷史。
- 證據。
- 交接。
- 工程狀態。

可以抽象：

```
GPT
=
短期工作記憶 + 推理

GitHub
=
長期外部記憶
```

因此重要長期資訊不能只存在聊天。

---

# 22. Artifact 原則

以下內容適合進 Repository：

- 知識。
- 系統定義。
- 方案。
- 架構決策。
- 規則。
- 測試結果。
- 研究結果。
- 交接資料。
- 當前狀態。
- 重要歷史。

聊天適合：

- 探索。
- 討論。
- 暫時假設。
- 即時推理。

---

# 23. 現行狀態與歷史分離

必須清楚區分：

```
CURRENT       目前有效
HISTORY       歷史
PENDING       待確認／待處理
DEPRECATED    已棄用
```

不能因為歷史文件仍然存在，就讓 GPT 誤認為它是現況。

---

# 24. 交接能力

理想狀態：

```
新 GPT
↓
入口
↓
專案目的
↓
目前狀態
↓
```

# 25. 上下文控制

Repository 可以比單次 GPT 上下文大很多。

前提是存在：

- 入口。
- 索引。
- 分類。
- 摘要。
- 狀態。
- 引用關係。

理想載入層次：

```
第一層：目前狀態
第二層：任務相關系統
第三層：任務相關方案
第四層：必要知識
第五層：歷史／證據
```

而不是：

```
全部文件
↓
全部讀取
↓
開始工作
```

# 26. 無 API 檢索策略

目前可使用：

```
Repository 結構
+
檔案索引
+
關鍵詞
+
GitHub 搜尋
+
GPT 語義判斷
```

搜尋不足時：

1. 擴大關鍵詞。
2. 使用同義詞。
3. 搜尋系統名稱。
4. 搜尋方案名稱。
5. 搜尋相關概念。
6. 回頭檢查索引。

只有證明上述方法已成為瓶頸後，才考慮 Vector Search。

---

# 27. 為什麼不急著 Vector Database

目前最大的問題未必是「搜尋速度」。

更可能是：

> GPT 不知道該找什麼。

如果 Intent 錯了，Vector Search 找得再快也可能找到錯誤資料。

因此目前優先順序：

```
意圖
>
分類
>
索引
>
檢索
>
Context Assembly
>
Vector Search
```

未來 API 再把這些人工步驟自動化。

---

# 28. 成本控制

無 API 時的主要成本包括：

- GPT 閱讀時間。
- 上下文長度。
- 閱讀無關資料。
- 重複研究。
- 重複交接。
- 錯誤理解造成的返工。
- 使用者等待。

所以最佳化目標不是單純「少寫文件」。

而是：

```
減少重複理解
減少重複搜尋
減少無關上下文
減少不必要深度推理
減少錯誤執行
減少返工
```

---

# 29. 回應深度控制

建議：

```
L0  極簡
L1  簡短
L2  一般
L3  深入
L4  完整研究
```

例：

「目前狀態？」

→ L0～L1。

「分析這個架構。」

→ L2～L3。

「搜尋業界方案並完整比較。」

→ L4。

真正目標不是少回答，而是：

> 在正確的深度回答。

# 44. 升級前判斷

每次想增加自動化時，先問：

1. 人工流程是否真的造成瓶頸？
2. 瓶頸是否會反覆發生？
3. 自動化後是否真的節省成本？
4. 新系統的維護成本是多少？
5. 新系統是否增加錯誤來源？
6. 是否可以保留人工 fallback？
7. 是否可以回滾？
8. 是否破壞既有資料語義？

如果只是「未來可能有用」，不應急著建立。

# 47. 失敗判準

如果出現以下情況，應重新檢討架構：

- GPT 經常找不到已有資料。
- GPT 經常讀取大量無關資料。
- GPT 經常混淆現在與歷史。
- GPT 經常混淆知識、系統、方案。
- GPT 經常把討論當執行。
- GPT 經常因索引錯誤使用錯誤系統。
- GPT 經常重複研究已有知識。
- 文件越多反而越難交接。
- 新增管理機制的成本高於收益。
- 架構本身比實際工作更需要維護。

# 48. 最終目標

本系統不是要取代使用者，也不是現在就建立完全自治 AI。

真正要解決的是：

> 一個人如何在 AI 時代長期管理一個會持續膨脹的知識、系統、方案與專案環境。

理想狀態：

```
人
=
方向、價值、重大決策

GPT
=
理解、研究、推理、規劃、執行、驗證

GitHub
=
長期記憶、歷史、證據、狀態

知識
=
可重用理解

系統
=
可重用能力

方案
=
解題方法

圖書館
=
找到知識

統御
=
決定下一步

驗證
=
確認是否真的正確

演化
=
讓整體長期不腐化
```

最終希望形成：

```
一個人
+
一個 GPT 核心
+
一個 GitHub 外部記憶
+
一套可以持續演化的工程結構
```

而不是：

```
一個人
+
一大堆必須維護的 AI 基礎設施
```
