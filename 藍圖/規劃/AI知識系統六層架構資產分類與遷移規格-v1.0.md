# AI 知識系統六層架構資產分類與遷移規格 v1.2

版本：v1.2
日期：2026-09-19
狀態：【規劃建立中（代）】

## 一、目的

把既有資產從「目前放在哪裡」改以「實際責任」分類。

本規格同時作為全庫資料重整大更新的分類判定標準。

## 二、分類原則

判定順序固定：

一、它管理的是什麼。
二、它現在處於什麼狀態。
三、它是否屬於規劃或工作過程。
四、是否需要歷史。
五、最後才決定實體路徑。

不得因檔名、資料夾名稱或既有編號直接判定責任。

## 三、功能責任分類

知識：單一可重用事實、概念或原理。
系統：單一可重用功能。
專案：特定情境、範圍與邊界。
方案能力：大方向的工作組合與規則。
協助能力：意圖理解與結構化。
代理能力：任務規劃、調度、驗證與回報。

這六類是功能責任，不是六種資料夾的強制對應。

## 四、控制資料分類

以下不是新的功能層，而是橫向資料責任：

實體、目前狀態、範圍、依賴、變更、歷史、證據、來源、追蹤。

它們由既有控制平面與受控程序管理。

## 五、專案判定

若資料描述「在哪個情境使用」，才屬專案責任。

若資料只是因為目前放在某專案資料夾，不得因此判定為專案所有。

共享資料應以：

實體 → 使用範圍 → 專案

表示，而不是：

專案 → 擁有全部資料。

## 六、狀態判定

先判斷實體類型，再決定狀態。

知識、系統通常需要生命週期；能力、專案通常增加開發與證據；任務、工作流程、代理執行才需要運作狀態。

版本是資料屬性，不是狀態。

不得建立包辦全部概念的單一「狀態」欄位。

## 七、追蹤分級

零級：目前資料與最低修訂資訊。
一級：輕量變更紀錄。
二級：核心治理與高重要性資料的完整追溯。

追蹤等級依重要性決定，不依資料量決定。

## 八、遷移處理方式

保留：原責任已符合新契約。
修整：保留原位置但修正責任邊界。
拆分：一份資料承擔多個責任。
合併：多份資料承擔同一責任。
包裝：舊資料保留，建立新的受控介面。
轉歷史：不再是目前資料但仍有追溯價值。
暫緩：證據不足，現在不處理。
待判定：無法可靠判斷。
刪除：確認無長期價值且無必要追溯需求。

## 九、與全庫大更新的協同規則

大更新總控負責作業順序；本規格負責責任判定。

資料重整執行清冊負責逐項記錄：

原路徑 → 原責任 → 目標責任 → 資料類型 → 權威 → 狀態 → 依賴 → 引用 → 處理方式 → 驗證 → 最終去向。

若分類結果不確定，不得自行猜測；填入「待判定」並進入問題或研究流程。

同一責任鏈應以批次處理，不得只搬其中一份文件而宣告完成。

## 十、控制平面接入

遷移不是單純搬檔。

每個正式責任鏈需要檢查：

實體
→ 類型
→ 權威
→ 目前狀態
→ 版本
→ 來源
→ 依賴
→ 變更
→ 影響
→ 證據

不得把原始文件全文複製成控制平面內容。

## 十一、遷移順序

第一優先：功能責任切割。
第二優先：專案範圍。
第三優先：協助能力與代理能力介面。
第四優先：控制平面映射。
第五優先：實體、狀態與追蹤模型。
第六優先：舊文件實體搬遷。
最後才刪除或封存已完全替代的舊文件。

## 十二、批次完成條件

每一批至少確認：

- 新責任可找到。
- 正式來源明確。
- 舊入口不再被誤當目前入口。
- 主要引用可解析。
- 控制平面資料一致。
- 目前狀態一致。
- 歷史不污染一般查詢。
- 模擬回歸通過（代）。
- 暫存資料具有唯一退場去向。

## 十三、不得採用的捷徑

不得看到文件就判斷是知識。
不得看到「能力」字樣就判定為正式能力。
不得為整齊而大量搬檔。
不得沒有引用掃描就刪除舊文件。
不得把歷史規劃當目前狀態。
不得把模擬結果寫成實際運作證據。
不得要求所有實體都有完整歷史。
不得要求所有實體都有全部狀態欄位。

## 十四、最終判定

只有同時滿足：

責任明確
引用完整
新介面可讀
範圍邊界通過
模擬驗收通過
實際運作證據足夠

才可以將舊資產標記為可封存或可移除。

「實際運作證據足夠」是全庫遷移的後置條件，不得因大更新工作本身正在進行而視為已滿足。
