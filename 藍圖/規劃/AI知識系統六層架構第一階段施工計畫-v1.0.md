# AI 知識系統六層架構第一階段施工計畫 v1.1

版本：v1.1
日期：2026-09-19
狀態：【施工規劃】

## 一、第一階段目標

不是一次完成全庫重構。

第一階段只建立「新架構可運作的骨架」，加入實體、狀態、範圍、變更與證據的最小模型，並用一個專案做端到端模擬。

## 二、階段零｜凍結邊界

規則：
- 不改目前基線的工程游標。
- 不取代現有能力控制平面。
- 不大規模移動舊檔案。
- 不宣告既有資產已完成新分類。
- 新架構文件本身屬規劃資產。
- 不建立第二套狀態真相來源。

完成條件：新舊架構可以同時存在，且沒有兩個目前基線。

## 三、階段一｜建立六層契約

建立：
1. 知識契約
2. 系統契約
3. 專案契約
4. 方案能力契約
5. 協助能力契約
6. 代理能力契約

同時補充：
7. 實體契約
8. 狀態配置規則
9. 追蹤等級規則
10. 範圍狀態規則

驗收：
- 每層能回答負責什麼與不負責什麼。
- 每層有最小輸入與輸出。
- 層與層之間不存在循環責任。
- 實體、狀態、歷史、證據責任可以分開。
- 專案不承擔大量資料容器責任。

## 四、階段二｜既有資產分類

對目前主要資產進行映射：

知識
系統
方案
專案
能力
藍圖
治理

並另外標出：

實體
目前狀態
變更
歷史
證據

輸出：

資產 → 責任 → 目標層 → 處理方式 → 證據 → 狀態

第一輪允許未知，不允許猜測。

## 五、階段三｜建立最小運作鏈

選擇一個低風險、非遊戲內容的工作情境：

使用者
→ 協助能力
→ 代理能力
→ 專案範圍
→ 方案能力
→ 系統
→ 知識
→ 驗證
→ 證據
→ 狀態更新
→ 變更紀錄
→ 代理回報

此階段以模擬驗收為主，標記「（代）」。

## 六、階段四｜接入控制平面

將運作鏈映射到既有：

語意路由
→ 控制平面查詢
→ 實體索引
→ 候選能力
→ 範圍檢查
→ 情境組裝
→ 執行
→ 驗證
→ 證據
→ 追蹤

不新增第二套索引，不新增第二套控制平面。

## 七、階段五｜專案甲範圍實驗

至少測試：

一、正常任務。
二、缺少條件。
三、跨專案資料污染。
四、能力找不到。
五、系統找不到。
六、知識不足。
七、驗證失敗。
八、重新規劃。
九、狀態變更。
十、不同專案對同一共享系統具有不同範圍狀態。

通過條件：錯誤情況不能靠模型自行補資料繼續假裝完成。

## 八、階段六｜決定是否遷移

只有前五階段穩定後，才開始：

分類 → 拆分／合併／包裝／修整 → 引用掃描 → 小批次實體搬遷 → 重新讀取 → 驗證 → 證據 → 下一批。

如果新架構在實驗中沒有明顯改善舊架構，停止大規模遷移並重新研究。

## 九、第一階段成功指標

不以建立多少文件衡量。

主要觀察：
- 情境所需資料是否下降。
- 能力選擇是否更準。
- 專案範圍是否更乾淨。
- 缺失資訊是否能被正確暴露。
- 驗證是否更容易。
- 舊文件互相衝突是否減少。
- 狀態是否能與內容分離。
- 歷史是否只在需要時產生。
- 新代理是否能從最小入口恢復正確結構。

## 十、驗收

設計驗收：可立即進行。

模擬驗收：目前可作為通過依據，標記「（代）」。

實際運作：等待自然工作產生證據。

實體大搬遷：等待前述證據。

模擬驗收不得標記為實際運作通過。

## 十一、停止條件

出現以下任一情況，停止擴張並回到研究或問題流程：

- 新舊責任無法清楚區分。
- 專案範圍仍會大量污染。
- 能力數量快速膨脹但責任沒有獨立性。
- 系統重新變成大型說明書。
- 知識開始承擔完整工作流程。
- 代理開始直接承擔領域知識。
- 控制平面出現第二套狀態真相。
- 所有實體被迫套用相同狀態欄位。
- 所有實體被迫保存完整歷史。
- 情境成本沒有下降且管理複雜度上升。

## 十二、第一階段終點

第一階段不是全庫完成。

終點是：

一條可理解、可路由、可按需載入、可區分範圍、可管理目前狀態、可在需要時追蹤變更、可驗證、可回報的六層工作鏈，在專案範圍內成功模擬運作。

完成後才決定是否進入全庫遷移。
