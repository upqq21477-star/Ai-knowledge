# AI 知識系統六層架構第一階段施工計畫 v1.2

版本：v1.2
日期：2026-09-19
狀態：【施工規劃（代）】

## 一、第一階段定位

第一階段建立新架構可運作的骨架，不等於全庫遷移。

本施工計畫與「全庫資料重整大更新」協同，但兩者責任不同：

本計畫負責驗證架構是否可運作。
大更新負責盤點、分類、遷移、同步、驗證與退場。

兩者共享同一控制平面、同一目前權威、同一問題流程與同一模擬驗收規則。

## 二、階段零｜凍結邊界

- 不改目前基線工程游標。
- 不取代既有控制平面。
- 不建立第二套狀態真相。
- 不建立第二個工作池。
- 不大規模移動舊檔案。
- 不宣告既有資產已完成新分類。
- 本施工文件本身屬規劃資料。
- 所有尚未有實際工作證據的驗收標記「（代）」。

## 三、階段一｜建立六層與資料治理契約

建立六層功能責任：

知識、系統、專案、方案能力、協助能力、代理能力。

同步建立橫向資料治理：

實體、狀態、範圍、變更、歷史、證據。

驗收重點：

- 每層能說明負責與不負責。
- 六層不被誤解成資料夾層級。
- 實體、狀態、變更、歷史、證據可分離。
- 專案不承擔大量資料容器責任。
- 狀態依實體類型決定。
- 追蹤深度依重要性決定。

## 四、階段二｜建立最小運作鏈

建立：

使用者
→ 協助能力
→ 代理能力
→ 專案範圍
→ 方案能力
→ 系統
→ 知識
→ 驗證
→ 證據
→ 狀態更新
→ 變更紀錄
→ 代理回報

以低風險、非遊戲內容情境進行。

此階段以模擬驗收為主，全部標記「（代）」。

## 五、階段三｜接入既有控制平面

把運作鏈映射到：

語意路由
→ 控制平面查詢
→ 實體索引
→ 候選能力
→ 範圍檢查
→ 情境組裝
→ 執行
→ 驗證
→ 證據
→ 追蹤
→ 回報

不新增第二套索引、不新增第二套控制平面。

## 六、階段四｜專案甲範圍實驗

至少模擬：

一、正常任務。
二、缺少條件。
三、跨專案資料污染。
四、能力找不到。
五、系統找不到。
六、知識不足。
七、驗證失敗。
八、重新規劃。
九、狀態變更。
十、同一共享系統在不同專案具有不同範圍狀態。

錯誤情況不得靠模型自行補資料繼續假裝完成。

## 七、階段五｜與全庫大更新協同

大更新先進行全庫盤點，不因施工開始就大量搬檔。

本施工計畫向大更新提供：

- 六層責任判定標準。
- 實體與狀態模型。
- 專案範圍規則。
- 追蹤分級。
- 模擬驗收案例。

大更新向本施工計畫回傳：

- 實際資產責任衝突。
- 舊入口與新入口衝突。
- 引用斷裂案例。
- 控制平面映射問題。
- 無法分類的問題。

雙方不得各自建立另一份真相。

## 八、階段六｜決定是否進入遷移

只有最小運作鏈與專案範圍實驗穩定後，才允許進入正式遷移。

進入條件：

- 模擬回歸通過（代）。
- 沒有第二套控制平面。
- 沒有第二個工作池。
- 主要責任邊界已可判定。
- 重大停止條件未出現。

即使達成以上條件，也不等於實際運作完成。

## 九、第一階段成功指標

- 情境所需資料下降。
- 能力選擇更容易驗證。
- 專案範圍更乾淨。
- 缺失資訊能正確暴露。
- 驗證更容易。
- 新舊責任衝突減少。
- 狀態與內容分離。
- 歷史只在需要時載入。
- 新代理可由最小入口恢復正確結構。

## 十、驗收

設計驗收：可進行。
模擬驗收：可作為目前施工判定，標記「（代）」。
實際運作：等待自然工作產生證據。
全庫遷移：等待架構與運作證據。

模擬驗收不得標記為實際運作通過。

## 十一、停止條件

任一條件成立即停止擴張：

- 新舊責任無法區分。
- 專案範圍仍大量污染。
- 能力數量增加但責任沒有獨立性。
- 系統重新變成大型說明書。
- 知識承擔完整工作流程。
- 代理直接承擔大量領域知識。
- 控制平面出現第二套狀態真相。
- 所有實體被迫使用相同狀態。
- 所有實體被迫保存完整歷史。
- 管理複雜度上升而情境成本沒有下降。
- 大更新工作區開始取代唯一工作池。

## 十二、第一階段終點

第一階段終點不是全庫完成。

終點是：

一條可理解、可路由、可按需載入、可區分範圍、可管理目前狀態、可在需要時追蹤變更、可驗證、可回報的六層工作鏈，在專案範圍內成功模擬運作。

達到此終點後，才正式評估全庫遷移是否進入下一階段。
