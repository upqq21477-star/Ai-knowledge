# AI 知識系統六層架構重構藍圖 v1.2

版本：v1.2
日期：2026-09-19
狀態：【規劃建立中（代）】
定位：本文件定義目標功能架構；不取代目前基線，不直接宣告既有文件已完成遷移。

## 一、重構定位

六層是「功能責任架構」，不是強制資料夾架構。

六層回答「誰負責什麼」；資料治理回答「資料目前怎樣、如何變化、為何可信」；控制平面負責把兩者接起來。

本架構因此維持三個互相垂直的面向：

一、功能責任：
使用者 → 協助能力 → 代理能力 → 專案情境 → 方案能力 → 系統 → 知識

二、資料治理：
實體 → 目前狀態 → 變更 → 證據 → 歷史 → 來源與範圍

三、運作控制：
查詢 → 判斷 → 變更 → 驗證 → 重新協調 → 關閉

不得把資料治理面向再擴充成新的「第七層、第八層」。

## 二、目標架構

使用者
→ 協助能力
→ 代理能力
→ 專案情境
→ 方案能力
→ 系統
→ 知識

橫向控制：
控制平面
├─ 實體索引與查詢
├─ 狀態與權限
├─ 範圍與依賴
├─ 變更與歷史
├─ 證據與追蹤
└─ 情境組裝

專案是使用範圍與工作邊界，不是資料庫。

實體是工作中被管理的對象。
狀態描述實體現在的情況。
歷史描述實體如何變成現在的情況。
證據描述為什麼可以相信目前狀態。

## 三、六個核心責任

### 3.1 知識
回答：「這是什麼？」
保存小單位、可重用的事實、概念或原理。
不承擔完整工作流程、專案決策或任務調度。

### 3.2 系統
回答：「如何完成一項功能？」
保存功能目的、輸入、需要的知識、最小處理邏輯、輸出與邊界。
不直接決定所有使用情境。

### 3.3 專案
回答：「在哪個情境使用？」
保存目標、範圍、邊界、可用能力與系統、專案規則及專案工作狀態。
不得成為大量實體、歷史與證據的容器。

### 3.4 方案能力
回答：「一個大方向的工作應如何組合？」
定義觸發、輸入、情境、系統組合、必要規則、輸出、驗證、停止與失敗回退。

### 3.5 協助能力
回答：「使用者真正想做什麼？」
負責語意拆解、目標與約束辨識、缺失條件辨識及不確定處確認。

### 3.6 代理能力
回答：「現在做什麼、下一步是什麼？」
負責任務規劃、範圍判斷、能力選擇、分派、回收、重新規劃、驗證與回報。
不得把未知內容補成事實。

## 四、實體、狀態、歷史、證據

四者不得合併成單一資料容器。

實體：是什麼對象。
狀態：現在怎樣。
變更：發生過什麼改動。
歷史：需要追溯時，如何理解演變。
證據：為什麼相信目前狀態。

基本關係：

實體
├─ 目前狀態
├─ 變更紀錄
├─ 歷史（依追蹤需要保存）
└─ 證據（依可信度需求保存）

專案只是實體的使用範圍之一，不是實體所有權容器。

## 五、狀態模型

不得要求所有實體使用同一組狀態。

由實體類型決定狀態配置：

| 實體類型 | 生命週期 | 開發 | 證據 | 運作 |
|---|---|---|---|---|
| 知識 | ✓ | — | 可選 | — |
| 系統 | ✓ | — | 可選 | — |
| 能力 | ✓ | ✓ | ✓ | — |
| 專案 | ✓ | ✓ | ✓ | — |
| 任務 | ✓ | 可選 | 可選 | ✓ |
| 工作流程 | ✓ | 可選 | 可選 | ✓ |
| 代理執行 | — | — | 可選 | ✓ |

版本是資料屬性，不是狀態維度。

同一共享系統可以有不同範圍狀態：
系統本身啟用；專案甲測試中；專案乙正常使用。

因此不得把專案識別直接當成資料所有權。

## 六、追蹤分級

零級：只維護目前資料與最低修訂資訊。
一級：增加輕量變更紀錄。
二級：對核心治理、高風險自動修改及需要責任追溯的資料保存完整變更、證據、驗證與追蹤。

不得因資料量大就全部升為二級。

## 七、控制平面定位

既有控制平面是橫向治理核心，不另建第二套。

內容層回答「它是什麼」。
控制平面回答「它現在怎樣」。

控制平面負責實體、索引、查詢、狀態、範圍、依賴、變更、證據、追蹤與影響管理。

不得讓內容文件與控制平面同時保存互相衝突的目前狀態。

## 八、與全庫大更新的關係

本藍圖只定義「應成為什麼」。

全庫資料重整大更新負責「目前資料如何安全地走到那裡」。

兩者關係固定為：

架構藍圖
→ 提供責任與資料治理判定標準
→ 大更新進行全庫盤點與責任映射
→ 小批次遷移
→ 控制平面同步
→ 驗證
→ 退場

大更新不得自行創造另一套架構。
架構藍圖也不得假設大更新已完成遷移。

本次大型更新中的工作資料只屬於更新工作區，完成後必須轉正、轉歷史、轉問題、轉路徑證據或刪除。

## 九、與第一階段施工的關係

第一階段施工不是全庫搬遷。

先建立六層責任、實體契約、狀態配置、追蹤分級、範圍規則與最小運作鏈，再決定哪些責任適合遷移。

全庫大更新可以同步盤點，但不得因盤點開始就大量搬遷。

兩條工作線必須共享同一控制平面、同一權威與同一驗收規則。

## 十、防止虛構

控制鏈：

範圍
→ 正確能力
→ 最小必要情境
→ 來源與權限
→ 證據
→ 驗證
→ 資訊不足即停止或要求補充

禁止：
- 把歷史當目前。
- 把規劃當正式。
- 把模擬當實際證據。
- 把缺失資料自行補成事實。
- 把專案資料當共享資料。
- 把所有實體建立完整歷史。

## 十一、第一階段成功條件

- 六層責任明確。
- 六層不被誤解為資料夾層級。
- 狀態由實體類型決定。
- 追蹤深度由重要性決定。
- 專案不再承擔大量資料容器責任。
- 目前狀態、變更、歷史、證據可以分離。
- 共享系統可以在不同專案中維持不同範圍狀態。
- 控制平面可以管理狀態真相。
- 至少一條完整工作鏈可以模擬通過。

## 十二、非目標

本階段不建立第二套控制平面、不建立第二個工作池、不把六層擴張成更多功能層、不把所有文件改成能力、不要求所有實體都有完整歷史、不要求一次完成全庫搬遷，也不以概念完整度宣告實際運作通過。
