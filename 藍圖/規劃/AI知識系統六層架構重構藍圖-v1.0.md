# AI 知識系統六層架構重構藍圖 v1.1

版本：v1.1
日期：2026-09-19
狀態：【規劃建立中】
定位：本文件定義下一階段目標架構；不取代目前基線，不直接宣告既有文件已完成遷移。

## 一、重構目的

將目前以大量文件承擔多種責任的結構，重新整理成可由代理按需調用的分層架構。

核心目標：
1. 知識只保存小單位、可重用的事實或原理。
2. 系統只描述一項可重用功能，以及完成該功能需要組合哪些知識。
3. 專案只保存特定情境、啟動條件、可用範圍與邊界，不作大量資料容器。
4. 方案能力負責大方向的系統組合與工作規則。
5. 協助能力負責自然語言的語意拆解、確認與意圖結構化。
6. 代理能力負責任務規劃、分派、回收結果、重新規劃與結束。
7. 控制平面作為橫向後台，管理實體、索引、查詢、狀態、範圍、權限、依賴、變更、證據與追蹤。

## 二、目標架構

使用者
→ 協助能力
→ 代理能力
→ 專案情境
→ 方案能力
→ 系統
→ 知識

橫向控制：
控制平面
├─ 實體索引與查詢
├─ 狀態與權限
├─ 範圍與依賴
├─ 變更與歷史
├─ 證據與追蹤
└─ 情境組裝

專案是使用範圍與工作邊界，不是資料庫。
實體是工作中被管理的對象。
狀態描述實體現在的情況。
歷史描述實體如何變成現在的情況。
證據描述為什麼可以相信目前狀態。

## 三、六個核心責任

### 3.1 知識

回答：「這是什麼？」

允許：單一概念、單一事實、單一原理、小範圍可重用資訊、明確適用條件。

不允許：完整工作流程、專案專屬決策、任務調度、大型方案編排。

### 3.2 系統

回答：「如何完成一項功能？」

只保留：功能名稱、功能目的、輸入、需要的知識、最小處理邏輯、輸出、邊界。

系統不決定何時一定要啟動；啟動條件由專案或方案能力決定。

### 3.3 專案

回答：「在哪個情境使用？」

保存：專案目標、啟動條件、可使用的能力與系統、專案專屬規則、禁止跨入的邊界、資料範圍。

專案可以本身具有狀態，但不得把專案內所有實體的資料、歷史與證據塞入專案文件。

### 3.4 方案能力

回答：「一個大方向的工作應如何組合？」

定義觸發條件、輸入、需要的情境、使用哪些系統、調用順序或條件、必要規則、輸出、驗證目標、停止條件與失敗回退。

### 3.5 協助能力

回答：「使用者真正想做什麼？」

負責語意拆解、目標辨識、約束辨識、缺失條件辨識、不確定處確認，並把自然語言轉成可處理的意圖契約。

### 3.6 代理能力

回答：「現在做什麼、下一步是什麼？」

負責接收意圖、建立任務、判斷專案範圍、選擇方案能力、分派子任務、接收結果、補充情境、重新規劃、驗證完成條件與回報。

代理不得把未知內容補成事實。

## 四、實體、狀態、歷史、證據

這四者不得合併成單一資料容器。

實體回答「是什麼對象」。
狀態回答「現在怎樣」。
歷史回答「怎麼變成現在這樣」。
證據回答「為什麼相信現在這樣」。

關係：

實體
├─ 目前狀態
├─ 變更歷史（依追蹤等級決定）
└─ 證據（依需求決定）

專案只是實體的使用範圍之一，不是實體的所有權容器。

## 五、狀態不是統一四欄格式

不得要求所有實體同時具有生命週期、開發、證據、運作四種狀態。

由實體類型決定狀態配置：

| 實體類型 | 生命週期 | 開發 | 證據 | 運作 |
|---|---|---|---|---|
| 知識 | ✓ | — | 可選 | — |
| 系統 | ✓ | — | 可選 | — |
| 能力 | ✓ | ✓ | ✓ | — |
| 專案 | ✓ | ✓ | ✓ | — |
| 專案實體 | 視需要 | 視需要 | 視需要 | — |
| 任務 | ✓ | 可選 | 可選 | ✓ |
| 工作流程 | ✓ | 可選 | 可選 | ✓ |
| 代理執行 | — | — | 可選 | ✓ |

版本不是狀態，而是資料屬性。

因此不得建立一個包辦所有概念的單一「狀態」欄位。

## 六、可變資料追蹤分級

不要求所有實體永久保存完整歷史。

### 零級：只維護目前資料

適用於大量普通實體。

至少保留目前值、更新時間、更新者、修訂號等最低追蹤資訊，不建立永久敘事歷史。

### 一級：輕量變更紀錄

適用於變動本身具有管理價值的實體。

只記錄時間、實體、原值、變更後值、原因，不寫長篇敘事。

### 二級：完整可追溯紀錄

只適用於核心系統、控制平面規則、重要能力、高風險自動修改與需要責任追溯的資料。

保存變更、證據、驗證與追蹤關係。

## 七、實體索引與內容分離

大量實體不得依賴大量文件才能查詢。

實體索引應是可查詢的結構化資料層，至少能表示：

實體識別、實體類型、範圍、目前狀態、版本、更新時間、追蹤等級。

細部定義只有在真正需要時才展開成獨立文件。

實作形式目前不鎖定，先定義資料契約，再依實際查詢需求選擇合適的儲存方式。

## 八、控制平面是狀態真相來源

內容層負責回答：「它是什麼。」
控制平面負責回答：「它現在怎樣。」

知識、系統、能力定義文件原則上保持穩定，不直接承擔大量狀態更新。

狀態、範圍、權限、變更、證據與索引由控制平面或受控程序管理。

不得讓內容文件與控制平面各自保存互相衝突的目前狀態。

## 九、範圍狀態

同一個共享系統可能被不同專案以不同狀態使用。

因此必須區分：

實體本身狀態
與
特定使用範圍中的狀態。

例如同一個系統本身可以是「啟用」，但在專案甲中仍是「測試中」，在專案乙中已進入正常使用。

因此不得把專案識別欄位直接當成資料所有權。

## 十、運作與防止虛構

控制鏈：

範圍 → 正確能力 → 最小必要情境 → 來源與權限 → 證據 → 驗證 → 資訊不足即停止或要求補充。

禁止：
- 把歷史資料當成目前狀態。
- 把模擬結果當成實際運作證據。
- 把候選方案當成正式方案。
- 把缺失資料自行補成事實。
- 把專案資料當成共享資料。
- 把所有實體都建立完整歷史。

## 十一、與既有控制平面的關係

既有控制平面、索引、查詢、路由、執行、驗證、證據與追蹤能力不推倒。

本次修正是補充其資料治理模型：

任務 → 代理 → 語意解析 → 控制平面查詢 → 候選能力 → 專案範圍檢查 → 情境組裝 → 執行 → 驗證 → 證據與追蹤 → 重新規劃。

索引是由內容與控制資料形成的查詢視圖，不取代原始內容來源。

## 十二、重構原則

不是全部重新寫。

採：
分類 → 定責 → 建立契約 → 建立實體與狀態模型 → 小批次遷移 → 重新讀取 → 驗證 → 才移除舊責任。

既有文件在未完成遷移前仍保留。

## 十三、成功條件

第一階段不要求全部文件搬完。

只要求：
- 六層責任明確。
- 狀態由實體類型決定。
- 追蹤深度由重要性決定。
- 專案不再承擔大量資料容器責任。
- 目前狀態與歷史可以區分。
- 狀態與證據可以區分。
- 共享系統可以在不同專案中維持不同範圍狀態。
- 控制平面可以管理狀態真相。
- 至少一條完整運作鏈可以模擬通過。

## 十四、非目標

本階段不建立第二套控制平面，不建立第二個工作池，不把所有文件改成能力，不要求所有實體都有完整狀態，不要求所有實體都有歷史，不進行全庫一次性搬遷，不以概念完整度宣告實際運作通過。
