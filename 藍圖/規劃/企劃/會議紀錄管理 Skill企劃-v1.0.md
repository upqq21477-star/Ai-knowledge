# 會議紀錄管理 Skill 企劃 v1.0

日期：2026-09-19
狀態：【企劃中；尚未升格為正式 Skill】
定位：討論 → 會議紀錄 → 企劃 → 正式 Skill／方案 → 清理 的過渡生命週期管理。

## 1. 目的

在長對話或深度研究過程中，當使用者需要暫停目前討論、切換主題、保留決策脈絡，或準備把討論成果轉成方案／Skill 時，提供一個輕量的「會議紀錄」入口。

核心不是保存聊天全文，而是：
- 判斷是否值得留下紀錄。
- 將需要保留的討論結果交給正確的既有 Skill 處理。
- 將暫時性會議紀錄與企劃資料放在 `藍圖/規劃/`。
- 在成果正式落地後清理不再需要的過渡資料。
- 僅留下必要的來源 → 產物路徑關係，避免規劃垃圾長期污染 Context。

## 2. 核心指令

使用者可直接輸入：

`會議紀錄`

此指令不是單純要求「把上一段話摘要」。

它表示：
> 分析目前討論是否形成值得保留的決策、設計、問題定義、方案方向或交接資訊；若值得，建立適合下一階段使用的會議紀錄。

若語意不明，不能自行判定。

### 2.1 短句／簡短紀錄語意判斷

例如：
- 「簡短記一下」
- 「先記錄」
- 「記一下」
- 「這個先留著」
- 「等等再做」

先判斷上下文是否明確指向「建立會議紀錄」。

若可以合理確定 → 直接執行。
若存在兩種以上合理解讀 → 用最短問題確認：

> 「要進行會議紀錄嗎？」

不得因一句「記一下」自動建立大量文件。

## 3. Trigger

主要觸發：
1. 使用者明確輸入「會議紀錄」。
2. 使用者要求暫停目前討論並保留成果。
3. 使用者準備切換到另一項工作，但目前討論已形成可恢復的決策／設計。
4. 使用者要求把目前討論整理成下一階段可使用的紀錄。
5. 深度研究或方案討論形成明確轉折點，需要留下設計脈絡。

輔助觸發：
- Context 即將重置且目前討論產生重要未完成狀態。
- Handoff 需要一份「討論階段」的來源材料。

禁止自動觸發：
- 普通聊天。
- 單純問答。
- 單次失敗。
- 沒有形成決策／設計／問題定義的長文。
- 可以直接由現有正式文件回答的內容。

## 4. 判斷輸出

先判斷：

### A. NO_RECORD
沒有足夠的可保存成果。
→ 不建立文件。

### B. MEETING_RECORD
形成暫時性討論成果，但尚未進入正式設計。
→ 寫入 `藍圖/規劃/會議紀錄/`。

### C. PLANNING
已從討論進入具體方案／Skill 設計。
→ 轉入 `藍圖/規劃/企劃/`。

### D. HANDOFF
主要目的只是讓下一個 AI 接續施工。
→ 交給 Handoff Skill，不把 Handoff Skill 重做成會議紀錄。

### E. EXISTING_UPDATE
內容其實是在修改既有正式 Skill／System。
→ 交 Evolution / Execution，不另外建立平行企劃。

## 5. 會議紀錄最小內容

只保存下一階段需要的資訊：

- 日期
- 主題
- 目的／問題
- 已確認事項
- 尚未確認事項
- 重要理由／依據
- 排除或暫緩方向
- 下一步
- 相關正式文件／候選產物
- 狀態：OPEN / READY / CONVERTED / CLOSED / DEFER
- 清理條件

不得把完整聊天內容複製進去。

## 6. 企劃最小內容

當討論已進入「準備建立方案／Skill」階段時，企劃至少記錄：

- 目的
- 要解決的問題
- 預期能力
- Trigger
- Input
- Output
- Responsibility
- Boundary
- 與既有 Skill 的重疊
- 可委派的子工作
- 驗證目標
- Unknown
- 暫緩條件
- 建立／不建立 Skill 的判斷依據
- 下一施工動作

企劃不是正式 Skill Definition，也不是正式 Knowledge。

## 7. 委派設計

此 Skill 不吞掉其他 Skill 的責任。

### 蒸餾 Skill
負責：
- 長討論壓縮。
- 重複內容去除。
- 保留結構性成果。
- 形成可保存的最小充分內容。

本 Skill 負責：
- 判斷「現在是否要留下紀錄」。
- 決定應進會議紀錄還是企劃。
- 管理過渡資料生命週期。

### 交接 Skill
負責：
- 下一個 AI 能否恢復工作。
- Handoff Package。
- 狀態凍結與恢復條件。

本 Skill 不重做 Handoff。

### Skill 分類判斷 Skill
負責：
- 判斷是否真的需要新 Skill。
- KEEP / MERGE / UPDATE / REPLACE / REFERENCE / DEFER / ARCHIVE。

本 Skill 不自行宣布「一定要建立新 Skill」。

### 演化管理 Skill
負責：
- 已確認的結構變更。
- Change Set / Impact / Migration。

本 Skill 只產生進入演化流程所需的企劃／來源資訊。

### 執行 Skill
負責：
- 實際建立、修改、移動、刪除檔案。

本 Skill 不直接承擔 Repository 修改責任。

### 驗證 Skill
負責：
- 判斷會議紀錄／企劃是否符合預期。
- 判斷成果是否真的完成。

## 8. Responsibility Boundary

本 Skill 的唯一獨立責任：

> 管理「討論成果是否需要被保存，以及應以哪一種過渡記錄形式進入下一工程階段」的生命週期。

不負責：
- 知識蒐集。
- 深度研究本身。
- 一般摘要。
- Skill 分類本身。
- Skill 建立本身。
- 正式架構設計本身。
- Repository 實際修改。
- Handoff 本身。
- 最終驗證本身。

## 9. 生命週期

`討論`
→ `語意判斷`
→ `蒸餾`
→ `會議紀錄`
→ `企劃`
→ `分類判斷`
→ `方案／Skill 建立`
→ `驗證`
→ `正式來源成立`
→ `清理過渡資料`
→ `路徑紀錄`

不是每一輪都必須經過全部階段。

## 10. 清理規則

### 10.1 會議紀錄
當內容已完全轉換成正式企劃／正式 Skill，且不存在未完成資訊：
→ 可刪除。

### 10.2 企劃
正式 Skill／方案已建立、驗證完成，且企劃沒有獨立長期價值：
→ 可刪除。

### 10.3 不應刪除
以下情況不得直接刪：
- 尚有未完成決策。
- 尚有 Unknown。
- 正式成果尚未驗證。
- 企劃仍是唯一來源。
- 其內容包含尚未轉移的必要依據。

## 11. 路徑紀錄

清理後只留下極簡來源關係：

`討論 → 會議紀錄 → 企劃 → 正式產物 → 清理`

路徑紀錄只保存：
- 日期
- 原始主題
- 來源檔
- 產物檔
- 最終狀態
- 清理狀態

它不是知識庫，也不是第二個 Workpool。

## 12. 與 ADR / Decision Log 的外部方法比較

外部工程實務對 ADR 的共通原則可作為參考：重要決策應保存 Context、Decision、Consequences／Trade-offs；應有明確狀態；已接受的決策通常不直接改寫，而以新決策取代；集中保存可降低重複討論。AWS 明確將 ADR 視為具生命週期的決策記錄，Microsoft 也要求記錄問題背景、選項、決策、取捨與狀態。這支持本方案「保存決策脈絡、但不保存完整聊天」的方向。

參考：
- AWS ADR Process：https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html
- AWS ADR Best Practices：https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/best-practices.html
- Microsoft Azure ADR：https://learn.microsoft.com/en-us/azure/well-architected/architect-role/architecture-decision-record

本專案不直接照搬 ADR，原因是目前需求更廣：
- 這裡不只記「已接受的架構決策」。
- 還要處理討論中途暫停、切換主題、AI 交接、Skill 企劃與過渡資料清理。
- 因此「會議紀錄」屬於暫時性 Context Artifact；真正具有長期工程權威性的內容仍應進入正式 Skill / System / Knowledge / Plan。

## 13. 深度研究後的結構修正

研究後確認，本系統不能把「會議紀錄」設計成永久 Decision Log。原因是 ADR 的核心對象是已形成、具架構影響的決策；本系統的會議紀錄還包含討論中途的暫停、上下文切換、未決事項與進入企劃前的過渡狀態。因此兩者應分層：

- 會議紀錄：短生命週期 Context Artifact。
- 企劃：方案／Skill 建立前的 Design Artifact。
- ADR 類決策：若未來確認需要永久保存，應進入適當正式工程文件，而不是永久堆在會議紀錄區。

另外，外部方法強調「所有重大決策都記錄」；本系統不採完全自動保存，而採 Trigger + Semantic Confirmation。原因是 AI 工作流的 Context 成本更敏感，過度記錄本身會形成噪音與維護成本。

## 14. 目前判定

本方案目前應視為：
`企劃候選 Skill`

不是立即建立正式 Skill。

升格條件：
1. 自然工作中反覆出現「會議紀錄 → 企劃 → 清理」流程。
2. 既有蒸餾／交接／分類／演化 Skill 無法合理承接「過渡資料生命週期管理」。
3. 觸發與邊界在多次實際使用中保持穩定。
4. 實際成本低於人工管理成本。
5. Verification 能證明沒有造成重複文件或 Context 污染。

若證據不足 → DEFER，不建立正式 Skill。

先建立：
- `藍圖/規劃/會議紀錄/`
- `藍圖/規劃/企劃/`

## 16. 邊界案例初步驗證

| 情境 | 預期判斷 | 後續責任 |
|---|---|---|
| 「會議紀錄」且前文有明確討論成果 | MEETING_RECORD | 蒸餾 → 建立會議紀錄 |
| 「會議紀錄」但前文沒有可保存內容 | NO_RECORD | 不建檔，回報無可保存成果 |
| 「簡短記一下」且語意明確 | MEETING_RECORD | 蒸餾 → 會議紀錄 |
| 「簡短記一下」可能是聊天中的一般備忘 | CONFIRM | 問「要進行會議紀錄嗎？」 |
| 「先記錄這個 Skill 怎麼做」 | PLANNING | 企劃 |
| 「幫我交接給下一個 AI」 | HANDOFF | 交接 Skill |
| 「把剛才內容整理成摘要」 | NO_RECORD / 일반摘要 | 不自動進會議紀錄 |
| 已確認要修改既有 Skill | EXISTING_UPDATE | Evolution → Execution |
| 發現新 Skill 候選但尚未確認 | PLANNING → Classification | Skill 分類判斷 |
| 單次失敗想分析原因 | NO_RECORD | 證據／診斷流程 |
| 長討論沒有任何決策、設計或下一步 | NO_RECORD | 不建立過渡文件 |
| 正式 Skill 已完成且企劃沒有獨立價值 | CLEANUP | Execution 清理並留下必要路徑 |

### 16.1 關鍵防錯

1. 「摘要」不等於「會議紀錄」。
2. 「交接」不等於「會議紀錄」。
3. 「建立 Skill」不等於本 Skill 自己建立 Skill。
4. 「討論很長」不等於一定要保存。
5. 「使用者說記錄」若存在真正歧義，必須確認。
6. 清理不能早於正式成果成立與必要資訊轉移。
7. 不因一次使用就判定此管理能力值得升格成正式 Skill。

## 18. 升格前最小自然 Evidence

正式建立 Skill 前，不設定人工案例數硬門檻。

只觀察自然工作是否出現：
- 同類語意觸發反覆發生。
- 短句歧義真的需要確認。
- 會議紀錄與企劃的分流穩定。
- 與蒸餾／交接／分類／演化的責任邊界沒有反覆衝突。
- 清理後仍能透過正式來源繼續工作。
- 產生的 Context 成本低於不記錄造成的恢復／重複討論成本。

若自然工作沒有證明獨立責任，維持 DEFER。

### 模擬結論

第一輪模擬未發現 Trigger、Output、Delegation、Cleanup 的立即架構矛盾。

但發現一個正式化前必須觀察的成本問題：如果每次「會議紀錄」都建立獨立檔案，短期討論可能產生大量小檔案。因此自然運作期間需觀察：

1. 是否需要每次一檔。
2. 是否需要同主題合併。
3. 何時應直接進企劃而不產生會議紀錄。
4. 清理後 Path Record 是否足以恢復來源關係。
5. 文件數量增加是否造成 Context／索引成本。

目前不預先增加自動合併、資料庫或 Registry；先以自然工作證據判斷。
