# 會議紀錄管理 Skill 企劃 v1.0

日期：2026-09-19
狀態：【企劃中；尚未升格為正式 Skill】
定位：討論 → 會議紀錄 → 企劃 → 正式 Skill／方案 → 清理 的過渡生命週期管理。

## 1. 目的

在長對話或深度研究過程中，當使用者需要暫停目前討論、切換主題、保留決策脈絡，或準備把討論成果轉成方案／Skill 時，提供一個輕量的「會議紀錄」入口。

核心不是保存聊天全文，而是：
- 判斷是否值得留下紀錄。
- 將需要保留的討論結果交給正確的既有 Skill 處理。
- 將暫時性會議紀錄與企劃資料放在 `藍圖/規劃/`。
- 在成果正式落地後清理不再需要的過渡資料。
- 僅留下必要的來源 → 產物路徑關係，避免規劃垃圾長期污染 Context。

## 2. 核心指令

使用者可直接輸入：

`會議紀錄`

此指令不是單純要求「把上一段話摘要」。

它表示：
> 分析目前討論是否形成值得保留的決策、設計、問題定義、方案方向或交接資訊；若值得，建立適合下一階段使用的會議紀錄。

若語意不明，不能自行判定。

### 2.1 短句／簡短紀錄語意判斷

例如：
- 「簡短記一下」
- 「先記錄」
- 「記一下」
- 「這個先留著」
- 「等等再做」

先判斷上下文是否明確指向「建立會議紀錄」。

若可以合理確定 → 直接執行。
若存在兩種以上合理解讀 → 用最短問題確認：

> 「要進行會議紀錄嗎？」

不得因一句「記一下」自動建立大量文件。

## 3. Trigger

主要觸發：
1. 使用者明確輸入「會議紀錄」。
2. 使用者要求暫停目前討論並保留成果。
3. 使用者準備切換到另一項工作，但目前討論已形成可恢復的決策／設計。
4. 使用者要求把目前討論整理成下一階段可使用的紀錄。
5. 深度研究或方案討論形成明確轉折點，需要留下設計脈絡。

輔助觸發：
- Context 即將重置且目前討論產生重要未完成狀態。
- Handoff 需要一份「討論階段」的來源材料。

禁止自動觸發：
- 普通聊天。
- 單純問答。
- 單次失敗。
- 沒有形成決策／設計／問題定義的長文。
- 可以直接由現有正式文件回答的內容。

## 4. 判斷輸出

先判斷：

### A. NO_RECORD
沒有足夠的可保存成果。
→ 不建立文件。

### B. MEETING_RECORD
形成暫時性討論成果，但尚未進入正式設計。
→ 寫入 `藍圖/規劃/會議紀錄/`。

### C. PLANNING
已從討論進入具體方案／Skill 設計。
→ 轉入 `藍圖/規劃/企劃/`。

### D. HANDOFF
主要目的只是讓下一個 AI 接續施工。
→ 交給 Handoff Skill，不把 Handoff Skill 重做成會議紀錄。

### E. EXISTING_UPDATE
內容其實是在修改既有正式 Skill／System。
→ 交 Evolution / Execution，不另外建立平行企劃。

## 5. 會議紀錄最小內容

只保存下一階段需要的資訊：

- 日期
- 主題
- 目的／問題
- 已確認事項
- 尚未確認事項
- 重要理由／依據
- 排除或暫緩方向
- 下一步
- 相關正式文件／候選產物
- 狀態：OPEN / READY / CONVERTED / CLOSED / DEFER
- 清理條件

不得把完整聊天內容複製進去。

## 6. 企劃最小內容

當討論已進入「準備建立方案／Skill」階段時，企劃至少記錄：

- 目的
- 要解決的問題
- 預期能力
- Trigger
- Input
- Output
- Responsibility
- Boundary
- 與既有 Skill 的重疊
- 可委派的子工作
- 驗證目標
- Unknown
- 暫緩條件
- 建立／不建立 Skill 的判斷依據
- 下一施工動作

企劃不是正式 Skill Definition，也不是正式 Knowledge。

## 7. 委派設計

此 Skill 不吞掉其他 Skill 的責任。

### 蒸餾 Skill
負責：
- 長討論壓縮。
- 重複內容去除。
- 保留結構性成果。
- 形成可保存的最小充分內容。

本 Skill 負責：
- 判斷「現在是否要留下紀錄」。
- 決定應進會議紀錄還是企劃。
- 管理過渡資料生命週期。

### 交接 Skill
負責：
- 下一個 AI 能否恢復工作。
- Handoff Package。
- 狀態凍結與恢復條件。

本 Skill 不重做 Handoff。

### Skill 分類判斷 Skill
負責：
- 判斷是否真的需要新 Skill。
- KEEP / MERGE / UPDATE / REPLACE / REFERENCE / DEFER / ARCHIVE。

本 Skill 不自行宣布「一定要建立新 Skill」。

### 演化管理 Skill
負責：
- 已確認的結構變更。
- Change Set / Impact / Migration。

本 Skill 只產生進入演化流程所需的企劃／來源資訊。

### 執行 Skill
負責：
- 實際建立、修改、移動、刪除檔案。

本 Skill 不直接承擔 Repository 修改責任。

### 驗證 Skill
負責：
- 判斷會議紀錄／企劃是否符合預期。
- 判斷成果是否真的完成。

## 8. Responsibility Boundary

本 Skill 的唯一獨立責任：

> 管理「討論成果是否需要被保存，以及應以哪一種過渡記錄形式進入下一工程階段」的生命週期。

不負責：
- 知識蒐集。
- 深度研究本身。
- 一般摘要。
- Skill 分類本身。
- Skill 建立本身。
- 正式架構設計本身。
- Repository 實際修改。
- Handoff 本身。
- 最終驗證本身。

## 9. 生命週期

`討論`
→ `語意判斷`
→ `蒸餾`
→ `會議紀錄`
→ `企劃`
→ `分類判斷`
→ `方案／Skill 建立`
→ `驗證`
→ `正式來源成立`
→ `清理過渡資料`
→ `路徑紀錄`

不是每一輪都必須經過全部階段。

## 10. 清理規則

### 10.1 會議紀錄
當內容已完全轉換成正式企劃／正式 Skill，且不存在未完成資訊：
→ 可刪除。

### 10.2 企劃
正式 Skill／方案已建立、驗證完成，且企劃沒有獨立長期價值：
→ 可刪除。

### 10.3 不應刪除
以下情況不得直接刪：
- 尚有未完成決策。
- 尚有 Unknown。
- 正式成果尚未驗證。
- 企劃仍是唯一來源。
- 其內容包含尚未轉移的必要依據。

## 11. 路徑紀錄

清理後只留下極簡來源關係：

`討論 → 會議紀錄 → 企劃 → 正式產物 → 清理`

路徑紀錄只保存：
- 日期
- 原始主題
- 來源檔
- 產物檔
- 最終狀態
- 清理狀態

它不是知識庫，也不是第二個 Workpool。

## 12. 與 ADR / Decision Log 的外部方法比較

外部工程實務對 ADR 的共通原則可作為參考：重要決策應保存 Context、Decision、Consequences／Trade-offs；應有明確狀態；已接受的決策通常不直接改寫，而以新決策取代；集中保存可降低重複討論。AWS 明確將 ADR 視為具生命週期的決策記錄，Microsoft 也要求記錄問題背景、選項、決策、取捨與狀態。這支持本方案「保存決策脈絡、但不保存完整聊天」的方向。

參考：
- AWS ADR Process：https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html
- AWS ADR Best Practices：https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/best-practices.html
- Microsoft Azure ADR：https://learn.microsoft.com/en-us/azure/well-architected/architect-role/architecture-decision-record

本專案不直接照搬 ADR，原因是目前需求更廣：
- 這裡不只記「已接受的架構決策」。
- 還要處理討論中途暫停、切換主題、AI 交接、Skill 企劃與過渡資料清理。
- 因此「會議紀錄」屬於暫時性 Context Artifact；真正具有長期工程權威性的內容仍應進入正式 Skill / System / Knowledge / Plan。

## 13. 深度研究後的結構修正

研究後確認，本系統不能把「會議紀錄」設計成永久 Decision Log。原因是 ADR 的核心對象是已形成、具架構影響的決策；本系統的會議紀錄還包含討論中途的暫停、上下文切換、未決事項與進入企劃前的過渡狀態。因此兩者應分層：

- 會議紀錄：短生命週期 Context Artifact。
- 企劃：方案／Skill 建立前的 Design Artifact。
- ADR 類決策：若未來確認需要永久保存，應進入適當正式工程文件，而不是永久堆在會議紀錄區。

另外，外部方法強調「所有重大決策都記錄」；本系統不採完全自動保存，而採 Trigger + Semantic Confirmation。原因是 AI 工作流的 Context 成本更敏感，過度記錄本身會形成噪音與維護成本。

## 14. 目前判定

本方案目前應視為：
`企劃候選 Skill`

不是立即建立正式 Skill。

升格條件：
1. 自然工作中反覆出現「會議紀錄 → 企劃 → 清理」流程。
2. 既有蒸餾／交接／分類／演化 Skill 無法合理承接「過渡資料生命週期管理」。
3. 觸發與邊界在多次實際使用中保持穩定。
4. 實際成本低於人工管理成本。
5. Verification 能證明沒有造成重複文件或 Context 污染。

若證據不足 → DEFER，不建立正式 Skill。

## 16. 邊界案例初步驗證

| 情境 | 預期判斷 | 後續責任 |
|---|---|---|
| 「會議紀錄」且前文有明確討論成果 | MEETING_RECORD | 蒸餾 → 建立會議紀錄 |
| 「會議紀錄」但前文沒有可保存內容 | NO_RECORD | 不建檔，回報無可保存成果 |
| 「簡短記一下」且語意明確 | MEETING_RECORD | 蒸餾 → 會議紀錄 |
| 「簡短記一下」可能是聊天中的一般備忘 | CONFIRM | 問「要進行會議紀錄嗎？」 |
| 「先記錄這個 Skill 怎麼做」 | PLANNING | 企劃 |
| 「幫我交接給下一個 AI」 | HANDOFF | 交接 Skill |
| 「把剛才內容整理成摘要」 | NO_RECORD / 일반摘要 | 不自動進會議紀錄 |
| 已確認要修改既有 Skill | EXISTING_UPDATE | Evolution → Execution |
| 發現新 Skill 候選但尚未確認 | PLANNING → Classification | Skill 分類判斷 |
| 單次失敗想分析原因 | NO_RECORD | 證據／診斷流程 |
| 長討論沒有任何決策、設計或下一步 | NO_RECORD | 不建立過渡文件 |
| 正式 Skill 已完成且企劃沒有獨立價值 | CLEANUP | Execution 清理並留下必要路徑 |

### 16.1 關鍵防錯

1. 「摘要」不等於「會議紀錄」。
2. 「交接」不等於「會議紀錄」。
3. 「建立 Skill」不等於本 Skill 自己建立 Skill。
4. 「討論很長」不等於一定要保存。
5. 「使用者說記錄」若存在真正歧義，必須確認。
6. 清理不能早於正式成果成立與必要資訊轉移。
7. 不因一次使用就判定此管理能力值得升格成正式 Skill。

## 18. 升格前最小自然 Evidence

正式建立 Skill 前，不設定人工案例數硬門檻。

只觀察自然工作是否出現：
- 同類語意觸發反覆發生。
- 短句歧義真的需要確認。
- 會議紀錄與企劃的分流穩定。
- 與蒸餾／交接／分類／演化的責任邊界沒有反覆衝突。
- 清理後仍能透過正式來源繼續工作。
- 產生的 Context 成本低於不記錄造成的恢復／重複討論成本。

若自然工作沒有證明獨立責任，維持 DEFER。

## 19. 第一輪模擬運行驗證

在正式升格前，先以目前真實對話型態做邊界模擬，不建立正式 Skill。

| Case | 輸入／條件 | 預期 | 結果 |
|---|---|---|---|
| 01 | 明確「會議紀錄」＋已有決策 | MEETING_RECORD | PASS |
| 02 | 明確「會議紀錄」＋無可保存成果 | NO_RECORD | PASS |
| 03 | 「簡短記一下」＋上下文明確 | MEETING_RECORD | PASS |
| 04 | 「先記錄」＋存在真正歧義 | CONFIRM | PASS |
| 05 | 已進入 Skill 企劃階段 | PLANNING，避免重複會議紀錄 | PASS |
| 06 | 實際目的為 AI 交接 | HANDOFF | PASS |
| 07 | 修改既有正式 Skill | EXISTING_UPDATE | PASS |
| 08 | 新 Skill 候選尚未確認 | PLANNING → Classification | PASS |
| 09 | 單次失敗要求分析 | NO_RECORD → 診斷流程 | PASS |
| 10 | 正式成果完成且過渡資料無獨立價值 | CLEANUP | PASS |

### 模擬結論

第一輪模擬未發現 Trigger、Output、Delegation、Cleanup 的立即架構矛盾。

但發現一個正式化前必須觀察的成本問題：如果每次「會議紀錄」都建立獨立檔案，短期討論可能產生大量小檔案。因此自然運作期間需觀察：

1. 是否需要每次一檔。
2. 是否需要同主題合併。
3. 何時應直接進企劃而不產生會議紀錄。
4. 清理後 Path Record 是否足以恢復來源關係。
5. 文件數量增加是否造成 Context／索引成本。

目前不預先增加自動合併、資料庫或 Registry；先以自然工作證據判斷。

### 模擬驗收狀態

`SIMULATION-1 = PASS`

狀態仍為：`企劃候選 Skill / DEFER`。

模擬 PASS 不等於正式 Skill 驗收 PASS；正式升格仍需自然工作 Evidence。
## 20. 第二輪模擬：完整生命週期與故障注入

依使用者要求，後續「實際測試」先以模擬運行取代，不等待自然案例。第二輪不再只測單點 Trigger，而是測完整流程是否能在中途失敗時保持邊界。

### 20.1 正常完整流程

`討論 → 語意判斷 → 蒸餾 → 會議紀錄 → 企劃 → 分類 → 正式產物 → 驗證 → 清理 → 路徑紀錄`

預期：每一階段只有一個主責，資料在階段間轉移，不重複建立平行來源。
結果：PASS。

### 20.2 在會議紀錄後中斷

條件：已建立會議紀錄，但尚未形成企劃。
預期：保留會議紀錄；不得清理；下一次工作可由該紀錄恢復。
結果：PASS。

### 20.3 在企劃後中斷

條件：企劃已完成，但正式 Skill／方案尚未建立。
預期：保留企劃；可不再保留已完全轉移且無獨立價值的會議紀錄；不得刪除企劃。
結果：PASS。

### 20.4 正式產物建立但 Verification 失敗

條件：正式產物存在，但驗證未通過。
預期：不得 CLEANUP；企劃保留作為修正來源；進入診斷／演化／執行流程。
結果：PASS。

### 20.5 Verification PASS 但仍有 Unknown

條件：主要功能驗證通過，但仍存在未決 Unknown。
預期：不得無條件清理；依 Unknown 是否影響後續工作判斷，必要時保留企劃。
結果：PASS。

### 20.6 已清理後發現需要追溯

條件：過渡文件已刪除，但仍需確認來源關係。
預期：由 Path Record 找到來源 → 正式產物；不得要求會議紀錄永久保存。
結果：PASS。

### 20.7 同一討論同時涉及既有 Skill 與新 Skill 候選

條件：部分內容是既有 Skill 修改，部分內容可能形成新能力。
預期：先分流：既有修改 → Evolution；新能力 → Planning → Classification；不得把兩者混成一份正式來源。
結果：PASS。

### 20.8 使用者直接要求刪除

條件：使用者要求刪除會議紀錄／企劃。
預期：仍先檢查是否為唯一來源、是否存在未轉移資訊、Verification 是否完成；符合清理條件才執行，否則保留並指出阻塞條件。
結果：PASS。

### 20.9 會議紀錄與正式文件內容衝突

條件：舊會議紀錄與目前正式 Skill／System 不一致。
預期：正式來源優先；舊紀錄不得覆蓋正式來源。若舊紀錄仍有歷史價值則保留或進 Path Record，否則清理。
結果：PASS。

### 20.10 模擬重複建立

條件：相同討論被連續觸發兩次「會議紀錄」。
預期：不得無條件建立兩份相同文件；先判斷是否已有同一未完成記錄，可更新／延續，而非複製。
結果：PASS。

## 21. 第二輪模擬結論

第二輪確認本方案真正需要控制的是「生命週期狀態」，而不是單純的文件建立。

目前至少需要維持以下狀態機概念：

`OPEN → READY → CONVERTED → CLOSED`

另有：
- `DEFER`：暫緩，不代表完成。
- `BLOCKED`：存在阻塞條件，不得清理。
- `SUPERSEDED`：後續正式來源已取代，但可依追溯需求保留最小來源關係。

目前不把這些狀態做成第二套 Registry；僅作為生命週期語意。

第二輪結果：

`SIMULATION-2 = PASS`

仍維持：

`企劃候選 Skill / DEFER`

下一輪模擬重點應轉向「與現有 Skill 實際委派時是否產生責任重疊」，尤其是蒸餾、交接、演化、執行、驗證之間的邊界。
## 22. 第三輪模擬：Control Plane 委派與責任邊界

### 22.2 路由衝突注入

#### Case A：使用者說「整理一下」
可能是一般摘要，也可能是會議紀錄。
預期：Task Understanding 先判定意圖；若不足則確認，不直接路由到會議紀錄管理。
結果：PASS。

#### Case B：使用者說「幫我留下剛才的重點」
若上下文明確涉及切換工作／保留決策，路由至會議紀錄管理；若只是要求一般摘要，路由至蒸餾。
結果：PASS。

#### Case C：使用者說「把這個做成 Skill」
預期：先進企劃／分類判斷；不是直接把內容寫成會議紀錄管理 Skill。
結果：PASS。

#### Case D：使用者說「把這個交接給下一個 AI」
預期：Handoff Skill 主責；會議紀錄管理只能提供討論來源材料。
結果：PASS。

#### Case E：使用者說「這個方案要不要改架構」
預期：Evolution／研究相關流程主責；本能力不取代架構演化判斷。
結果：PASS。

#### Case F：使用者說「剛才那段存起來」
預期：若語意真正歧義，最短確認；不得因單一「存」字自動建立過渡文件。
結果：PASS。

### 22.3 與 Control Plane 原則一致性

檢查以下既有原則：

- Skill Definition 是 Source of Truth：不違反。
- Registry 是 Derived View：不新增第二 Registry。
- Router 不是 Runtime：不修改 Router／Runtime 邊界。
- Dependency ≠ Impact：委派與影響分析分開。
- Evidence ≠ Trace：Path Record 不冒充 Verification Evidence。
- Verification ≠ Evidence：本能力不自行宣布驗證成立。
- Unknown 不猜測：歧義與不足資訊走確認／DEFER。
- Failure 不自動產生 Skill：符合。
- No Candidate 不自動建立 Skill：符合。
- Registry 從 Source 重建：本方案不改此規則。

結果：PASS。

## 23. 第三輪模擬結論

> 管理討論成果是否需要保存，以及應以何種過渡形式進入下一工程階段。
