# 會議紀錄管理 Skill 企劃 v1.0

日期：2026-09-19
狀態：【企劃中；尚未升格為正式 Skill】
定位：討論 → 會議紀錄 → 企劃 → 正式 Skill／方案 → 清理 的過渡生命週期管理。

## 1. 目的

在長對話或深度研究過程中，當使用者需要暫停目前討論、切換主題、保留決策脈絡，或準備把討論成果轉成方案／Skill 時，提供一個輕量的「會議紀錄」入口。

核心不是保存聊天全文，而是：
- 判斷是否值得留下紀錄。
- 將需要保留的討論結果交給正確的既有 Skill 處理。
- 將暫時性會議紀錄與企劃資料放在 `藍圖/規劃/`。
- 在成果正式落地後清理不再需要的過渡資料。
- 僅留下必要的來源 → 產物路徑關係，避免規劃垃圾長期污染 Context。

## 2. 核心指令

使用者可直接輸入：

`會議紀錄`

此指令不是單純要求「把上一段話摘要」。

它表示：
> 分析目前討論是否形成值得保留的決策、設計、問題定義、方案方向或交接資訊；若值得，建立適合下一階段使用的會議紀錄。

若語意不明，不能自行判定。

### 2.1 短句／簡短紀錄語意判斷

例如：
- 「簡短記一下」
- 「先記錄」
- 「記一下」
- 「這個先留著」
- 「等等再做」

先判斷上下文是否明確指向「建立會議紀錄」。

若可以合理確定 → 直接執行。
若存在兩種以上合理解讀 → 用最短問題確認：

> 「要進行會議紀錄嗎？」

不得因一句「記一下」自動建立大量文件。

## 3. Trigger

主要觸發：
1. 使用者明確輸入「會議紀錄」。
2. 使用者要求暫停目前討論並保留成果。
3. 使用者準備切換到另一項工作，但目前討論已形成可恢復的決策／設計。
4. 使用者要求把目前討論整理成下一階段可使用的紀錄。
5. 深度研究或方案討論形成明確轉折點，需要留下設計脈絡。

輔助觸發：
- Context 即將重置且目前討論產生重要未完成狀態。
- Handoff 需要一份「討論階段」的來源材料。

禁止自動觸發：
- 普通聊天。
- 單純問答。
- 單次失敗。
- 沒有形成決策／設計／問題定義的長文。
- 可以直接由現有正式文件回答的內容。

## 4. 判斷輸出

先判斷：

### A. NO_RECORD
沒有足夠的可保存成果。
→ 不建立文件。

### B. MEETING_RECORD
形成暫時性討論成果，但尚未進入正式設計。
→ 寫入 `藍圖/規劃/會議紀錄/`。

### C. PLANNING
已從討論進入具體方案／Skill 設計。
→ 轉入 `藍圖/規劃/企劃/`。

### D. HANDOFF
主要目的只是讓下一個 AI 接續施工。
→ 交給 Handoff Skill，不把 Handoff Skill 重做成會議紀錄。

### E. EXISTING_UPDATE
內容其實是在修改既有正式 Skill／System。
→ 交 Evolution / Execution，不另外建立平行企劃。

## 5. 會議紀錄最小內容

只保存下一階段需要的資訊：

- 日期
- 主題
- 目的／問題
- 已確認事項
- 尚未確認事項
- 重要理由／依據
- 排除或暫緩方向
- 下一步
- 相關正式文件／候選產物
- 狀態：OPEN / READY / CONVERTED / CLOSED / DEFER
- 清理條件

不得把完整聊天內容複製進去。

## 6. 企劃最小內容

當討論已進入「準備建立方案／Skill」階段時，企劃至少記錄：

- 目的
- 要解決的問題
- 預期能力
- Trigger
- Input
- Output
- Responsibility
- Boundary
- 與既有 Skill 的重疊
- 可委派的子工作
- 驗證目標
- Unknown
- 暫緩條件
- 建立／不建立 Skill 的判斷依據
- 下一施工動作

企劃不是正式 Skill Definition，也不是正式 Knowledge。

## 7. 委派設計

此 Skill 不吞掉其他 Skill 的責任。

### 蒸餾 Skill
負責：
- 長討論壓縮。
- 重複內容去除。
- 保留結構性成果。
- 形成可保存的最小充分內容。

本 Skill 負責：
- 判斷「現在是否要留下紀錄」。
- 決定應進會議紀錄還是企劃。
- 管理過渡資料生命週期。

### 交接 Skill
負責：
- 下一個 AI 能否恢復工作。
- Handoff Package。
- 狀態凍結與恢復條件。

本 Skill 不重做 Handoff。

### Skill 分類判斷 Skill
負責：
- 判斷是否真的需要新 Skill。
- KEEP / MERGE / UPDATE / REPLACE / REFERENCE / DEFER / ARCHIVE。

本 Skill 不自行宣布「一定要建立新 Skill」。

### 演化管理 Skill
負責：
- 已確認的結構變更。
- Change Set / Impact / Migration。

本 Skill 只產生進入演化流程所需的企劃／來源資訊。

### 執行 Skill
負責：
- 實際建立、修改、移動、刪除檔案。

本 Skill 不直接承擔 Repository 修改責任。

### 驗證 Skill
負責：
- 判斷會議紀錄／企劃是否符合預期。
- 判斷成果是否真的完成。

## 8. Responsibility Boundary

本 Skill 的唯一獨立責任：

> 管理「討論成果是否需要被保存，以及應以哪一種過渡記錄形式進入下一工程階段」的生命週期。

不負責：
- 知識蒐集。
- 深度研究本身。
- 一般摘要。
- Skill 分類本身。
- Skill 建立本身。
- 正式架構設計本身。
- Repository 實際修改。
- Handoff 本身。
- 最終驗證本身。

## 9. 生命週期

`討論`
→ `語意判斷`
→ `蒸餾`
→ `會議紀錄`
→ `企劃`
→ `分類判斷`
→ `方案／Skill 建立`
→ `驗證`
→ `正式來源成立`
→ `清理過渡資料`
→ `路徑紀錄`

不是每一輪都必須經過全部階段。

## 10. 清理規則

### 10.1 會議紀錄
當內容已完全轉換成正式企劃／正式 Skill，且不存在未完成資訊：
→ 可刪除。

### 10.2 企劃
正式 Skill／方案已建立、驗證完成，且企劃沒有獨立長期價值：
→ 可刪除。

### 10.3 不應刪除
以下情況不得直接刪：
- 尚有未完成決策。
- 尚有 Unknown。
- 正式成果尚未驗證。
- 企劃仍是唯一來源。
- 其內容包含尚未轉移的必要依據。

## 11. 路徑紀錄

清理後只留下極簡來源關係：

`討論 → 會議紀錄 → 企劃 → 正式產物 → 清理`

路徑紀錄只保存：
- 日期
- 原始主題
- 來源檔
- 產物檔
- 最終狀態
- 清理狀態

它不是知識庫，也不是第二個 Workpool。

## 12. 與 ADR / Decision Log 的外部方法比較

外部工程實務普遍將「討論背景、決策、理由、後果」與「實作文件」分開；AWS、Microsoft、Google 等 ADR 指南也強調決策應可追溯，重要決策變更應透過新的記錄取代舊決策，而不是讓歷史脈絡消失。citeturn0search1turn0search2turn0search3turn0search11

本專案不直接照搬 ADR，原因是目前需求更廣：
- 這裡不只記「已接受的架構決策」。
- 還要處理討論中途暫停、切換主題、AI 交接、Skill 企劃與過渡資料清理。
- 因此「會議紀錄」屬於暫時性 Context Artifact；真正具有長期工程權威性的內容仍應進入正式 Skill / System / Knowledge / Plan。

## 13. 目前判定

本方案目前應視為：
`企劃候選 Skill`

不是立即建立正式 Skill。

升格條件：
1. 自然工作中反覆出現「會議紀錄 → 企劃 → 清理」流程。
2. 既有蒸餾／交接／分類／演化 Skill 無法合理承接「過渡資料生命週期管理」。
3. 觸發與邊界在多次實際使用中保持穩定。
4. 實際成本低於人工管理成本。
5. Verification 能證明沒有造成重複文件或 Context 污染。

若證據不足 → DEFER，不建立正式 Skill。
