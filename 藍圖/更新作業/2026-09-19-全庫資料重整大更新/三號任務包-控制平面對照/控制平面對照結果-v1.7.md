## 1. 本輪工作

承接 v1.6，不再以「是否存在獨立 Registry 資料檔」作為唯一判定。改查 Repository 中是否已明確定義 Source → Derive → Registry View → Query 的實際來源與適用範圍。

## 2. 找到的明確資料流

目前可以直接證明一條「Skill 專用」資料流：

Skill Definition（Source of Truth）
→ Registry View（Derived View）
→ Control Plane Query
→ Runtime 取得必要 metadata / relationship / state / evidence pointer
→ Runtime 回讀正式 Skill Definition

相關文件一致描述：
- Registry 不是真實來源。
- Registry 可由 Source 重建。
- Definition Change 後應同步更新 Derived View。
- Registry 遺失時由 Source 重建，再重新 Query。
- 已有 11 個核心 Skill 完成 Control Plane Definition 接入。

因此，先前「Skill Registry 是否存在」的疑問不成立；此部分已有明確 Source / Derived View / Query 關係。

## 3. 關鍵限制

上述證據明確集中在 Skill Control Plane。

本輪仍沒有找到一份同等明確的「General Entity」資料流規格，能逐項回答：

General Entity Source
→ General Registry View
→ Entity Type 判定
→ State Configuration 選擇
→ General Query Result

也沒有找到一份可直接逐筆讀取的 General Entity Registry 資料集。

因此不能把 Skill 的完整資料流自動外推成所有 Entity Type 已完成相同落地。

P3-001｜Cross-Entity State Mapping / Registry Implementation Coverage

## 5. P3-002 更新

P3-002｜Entity Type → State Configuration Mapping Coverage

狀態：UNKNOWN（代）

## 6. 新的最小結論

目前證據可把問題分成兩層：

Layer A：Skill Control Plane
→ Source / Derived Registry / Query 的資料流已有明確規格與既有接入證據。（代）

Layer B：Cross-Entity Control Plane
→ Entity / State 的共通架構已有正式規格，但跨 Entity Type 的 Registry materialization 與 State Configuration mapping 尚未被 Repository 中的直接資料證據完整證明。（代）

這是目前真正剩餘的施工範圍。
