## 1. 本輪目的

針對 v1.1 唯一保留問題：

P3-001（代）｜Cross-Entity State Mapping

重新搜尋實際規格、Entity Type 定義、State configuration 與 Registry 落地證據，確認該問題究竟是：

## 2. 新確認的規格證據

### 2.1 六層架構藍圖已明確定義 Entity Type → State Configuration

《AI 知識系統六層架構重構藍圖》明確規定：

「不得要求所有實體使用同一組狀態。」

並提供 Entity Type 與狀態維度對照：

| Entity Type | Lifecycle | Development | Evidence | Operation |
|---|---:|---:|---:|---:|
| Knowledge | ✓ | — | 可選 | — |
| System | ✓ | — | 可選 | — |
| Capability | ✓ | ✓ | ✓ | — |
| Project | ✓ | ✓ | ✓ | — |
| Task | ✓ | 可選 | 可選 | ✓ |
| Workflow | ✓ | 可選 | 可選 | ✓ |
| Agent Execution | — | — | 可選 | ✓ |

因此「跨 Entity Type State mapping」本身已有正式的規範來源。

### 2.2 資產分類與遷移規格再次確認相同原則

《AI 知識系統六層架構資產分類與遷移規格》明確規定：

先判斷 Entity Type，再決定 State。

並明確指出：
- Knowledge / System 通常需要 Lifecycle；
- Capability / Project 通常增加 Development / Evidence；
- Task / Workflow / Agent Execution 才需要 Operation；
- Version 是資料屬性，不是 State；
- 不得建立包辦全部概念的單一 State 欄位。

因此 State Governance 的語義來源不是 UNKNOWN。

## 3. 對 Registry 落地面的回查

《Control Plane Registry 規格》明確定義一般 Entity 欄位：

ID / Type / Name / Path / State / Acceptance / Authority / Version / Lifecycle / Source / Updated / Confidence

也明確定義 Skill Registry 的 State / Acceptance / Lifecycle / Version 分離，以及 Skill Entity 的最小 View。

但是，本輪在目前可檢索的 Repository 內容中，仍未找到一份足以證明「一般 Entity Registry 已對 Knowledge / System / Capability / Project / Task / Workflow / Agent Execution 等所有類型逐項套用上述 State Configuration，並可由 Registry / Query 正式取回」的完整落地資料表或等價實作證據。

已找到的是：
- State Configuration 的正式規格；
- 一般 Entity 的通用 State 欄位；
- Skill Registry 的具體 State mapping；
- Query / Registry Contract。

尚未找到的是：
- 全 Entity Type → State Dimension 的正式 Registry implementation coverage；
- 或可逐項驗證的 Registry sample / Query result，足以證明全部類型均已落地。

因此本輪不能把「規格存在」升格為「全部已實作」。

## 4. P3-001 判定更新

原問題名稱保留：

P3-001（代）｜Cross-Entity State Mapping

但問題性質收窄為：

Control Plane Registry implementation coverage 未被目前證據完整證明。

不是：
- State Governance 規格缺失；
- Skill Registry 缺失；
- Control Plane 缺失；
- 第二套 State System。

目前正確狀態：

UNKNOWN（代）

停止條件：

在沒有逐類型落地證據前，不判定「已完整落地」；
也不判定「未實作」。

不得自行建立缺失 mapping。
