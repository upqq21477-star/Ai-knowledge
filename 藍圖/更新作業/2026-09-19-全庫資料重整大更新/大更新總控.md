# 全庫資料重整大更新總控

版本：v1.0
日期：2026-09-19
狀態：【規劃建立中（代）】
性質：一次性大型更新工作區
權威：本文件只負責本次資料重整的作業邊界與順序，不取代目前工程基線、控制平面或唯一工作池。

## 一、更新目的

本次更新處理目前資料重整所產生的結構問題：

- 新舊資料責任混雜。
- 正式內容、規劃、工作紀錄、目前狀態、歷史資料、證據彼此混放。
- 同一責任可能存在多個入口。
- 舊資料可能被誤讀為目前資料。
- 更新後的新資料與舊資料缺少明確退場路徑。
- 控制平面已有能力，但尚未完整接上本次全庫資料重整流程。

本次不是重新建立另一套系統，而是利用既有控制平面，完成一次受控的資料整理、映射、遷移、驗證與退場。

## 二、既有權威不得改變

本次更新期間仍維持：

- 唯一目前工程狀態：2-方案/完善/CURRENT Baseline-v1.0.md
- 唯一工作池：待辦清單.md
- 控制平面：1-系統/AI Control Plane.md
- 控制平面索引規格：1-系統/03-Spec/Control Plane Registry 規格.md
- 控制平面查詢規格：1-系統/03-Spec/Control Plane Query 規格.md
- 問題生命週期：1-系統/問題清單.md
- 原始文件仍是內容真相；索引與衍生資料不得覆寫原始文件。

不得因本次更新建立第二個目前狀態、第二個工作池、第二套控制平面或第二套索引真相。

## 三、本次工作區的定位

本工作區只是大型更新期間的暫時作業區。

它可以保存：

- 本次更新範圍。
- 全庫盤點結果。
- 分類映射。
- 遷移批次。
- 衝突清單。
- 驗證結果。
- 退場判定。
- 必要的更新證據。

它不得變成：

- 長期正式資料層。
- 第二個工作池。
- 第二個控制平面。
- 第二個目前狀態來源。
- 永久備份資料庫。

## 四、核心資料分類

所有被處理的資料先區分責任，不先依目前資料夾名稱判定。

### 一、正式內容

回答「它是什麼」。

包含：

- 知識。
- 系統。
- 能力。
- 方案。
- 專案定義。
- 正式規格。

處理結果：保留、修整、拆分、合併或轉為歷史。

### 二、規劃資料

回答「未來可能怎麼做」。

包含：

- 藍圖。
- 研究中的設計。
- 尚未定案的架構。
- 候選方案。
- 尚未具備實際證據的規劃。

規劃不得直接冒充正式目前資料。

### 三、工作資料

回答「現在正在做什麼」。

包含：

- 本次遷移工作。
- 分類過程。
- 暫時映射。
- 尚未完成的整理。
- 本次更新中的衝突處理。

更新結束後必須逐項退場。

### 四、目前狀態資料

回答「現在怎樣」。

包含：

- 目前狀態。
- 目前版本。
- 目前權威。
- 範圍。
- 目前依賴。
- 目前可用能力。
- 目前驗收狀態。

優先由控制平面或受控程序管理。

### 五、歷史資料

回答「以前怎麼樣，以及為什麼變成現在」。

只保存具有追溯價值的：

- 舊版本。
- 重大架構變更。
- 重要決策。
- 重要驗證。
- 重大問題處理。
- 必要來源與路徑證據。

歷史不是所有舊文件的垃圾場。

### 六、證據資料

回答「為什麼相信」。

包含：

- 模擬驗收。
- 實際工作證據。
- 驗證結果。
- 外部研究來源。
- 人工決策依據。

模擬證據不得標示為實際運作證據。

## 五、資料遷移總流程

建立
→ 全庫盤點
→ 更新範圍凍結
→ 責任分類
→ 權威辨識
→ 新舊對照
→ 重複與衝突辨識
→ 依賴與引用掃描
→ 遷移批次建立
→ 小批次遷移
→ 控制平面同步
→ 索引重建
→ 目前狀態重建
→ 驗證
→ 切換
→ 觀察
→ 歷史封存
→ 暫存資料退場
→ 工作區關閉

不得直接從「盤點」跳到「大量刪除」。

## 六、第一階段：全庫盤點

先取得實際資料，不修改內容。

盤點至少包括：

- 根目錄。
- 各主要資料夾。
- 文件名稱。
- 文件責任。
- 文件內目前狀態。
- 版本。
- 權威標示。
- 引用關係。
- 相互依賴。
- 新舊版本關係。
- 規劃／正式／歷史判定。
- 是否具有證據。
- 是否存在重複。
- 是否存在互相矛盾。
- 是否存在孤兒文件。
- 是否存在舊入口仍被引用。

第一輪允許「未知」，禁止靠猜測分類。

## 七、第二階段：建立責任映射

每一份重要資料建立：

原資料
→ 原路徑
→ 原責任
→ 目前權威
→ 目標責任
→ 目標位置
→ 處理方式
→ 依賴
→ 驗證需求
→ 最終去向

處理方式只使用：

- 保留。
- 修整。
- 拆分。
- 合併。
- 包裝。
- 轉歷史。
- 暫緩。
- 待判定。
- 刪除。

刪除必須最後才決定。

## 八、第三階段：控制平面接入

本次更新使用既有控制平面，不建立新後台。

控制鏈：

觀察
→ 辨識實體
→ 查詢目前狀態
→ 辨識權威
→ 建立變更集合
→ 評估影響
→ 執行遷移
→ 驗證
→ 更新索引
→ 重新對照
→ 關閉變更

重要變更以變更集合為單位處理，避免跨文件修改互相脫節。

## 九、第四階段：新舊資料隔離

更新期間允許舊資料與新資料同時存在，但必須區分：

目前視圖：
只讀取目前正式資料。

更新視圖：
可讀取目前資料、待遷移資料與更新工作資料。

歷史視圖：
只在需要追溯時讀取。

正常工作不得因舊文件仍存在，就把舊內容當成目前內容。

## 十、第五階段：批次遷移

優先處理「整個責任群組」，而不是任意逐檔搬移。

同一功能鏈如果彼此依賴，應視為同一批：

- 入口。
- 正式定義。
- 規格。
- 索引。
- 證據。
- 相關引用。

每一批完成後：

重新讀取
→ 引用檢查
→ 權威檢查
→ 狀態檢查
→ 模擬回歸
→ 再進下一批。

## 十一、第六階段：驗證

本次更新前期全部採模擬驗收，標記「（代）」。

至少驗證：

一、新入口可以找到。
二、舊入口不再被誤當目前入口。
三、目前資料與歷史資料可區分。
四、正式內容與規劃資料可區分。
五、工作資料不會永久滲入正式層。
六、狀態不與內容混成同一真相。
七、控制平面可找到必要實體。
八、索引可以由正式來源重建。
九、重要引用沒有斷裂。
十、跨專案範圍不互相污染。
十一、模擬結果沒有被標示為實際運作證據。
十二、新 AI 從最小入口可以恢復正確結構。

## 十二、第七階段：退場

每一個本次工作產生的暫時資料，必須有唯一終點：

### 轉正

內容具有長期價值，成為正式資料。

### 轉歷史

內容不再是目前資料，但具有追溯價值。

### 轉問題

內容揭露尚未解決的問題，進入唯一問題清單。

### 轉路徑證據

只需要保存來源、結果、時間與關係，不需要保留完整工作文件。

### 刪除

確認沒有長期價值，且沒有必要追溯需求。

沒有終點的暫時資料不得關閉更新。

## 十三、規劃資料的退場

規劃完成後，不得一直留在「規劃中」。

必須判定：

- 已正式採用 → 轉正式內容。
- 已被新規劃取代 → 轉歷史。
- 證據不足 → 保留為待定研究，明確標記。
- 已證明沒有價值 → 刪除。
- 尚有未完成問題 → 轉問題清單。

因此「規劃」是生命週期中的責任，不是永久垃圾桶。

## 十四、更新版本的退場規則

更新採：

舊版
→ 建立新版
→ 引用掃描
→ 驗證新版
→ 切換目前
→ 觀察
→ 舊版判定

舊版可能：

- 保留為歷史。
- 保留為必要回退來源。
- 僅保留變更與證據。
- 確認無價值後刪除。

不得因新版存在就立即刪除舊版。

## 十五、本次更新的停止條件

任一條件成立，停止擴張：

- 新舊權威無法判定。
- 同一資料存在兩個目前真相。
- 引用關係無法追溯。
- 控制平面與內容資料互相衝突。
- 遷移後無法恢復原責任。
- 大量資料需要人工猜測。
- 暫存資料開始形成第二個正式架構。
- 工作區開始取代唯一工作池。
- 驗證證據不足卻準備切換目前狀態。

遇到停止條件，回到問題流程或研究流程，不繼續搬遷。

## 十六、本次更新完成條件

不是「所有文件都搬完」。

真正完成條件：

- 全庫主要資料已完成責任盤點。
- 正式、規劃、工作、狀態、歷史、證據已能分離。
- 主要目前權威已明確。
- 新舊資料沒有雙重目前真相。
- 重要引用與依賴已驗證。
- 控制平面已能支援更新後的管理方式。
- 目前視圖不會載入不必要歷史。
- 暫時工作資料已全部完成退場判定。
- 必要歷史與證據已保存。
- 唯一工作池恢復正常。
- 本次更新工作區可以關閉。
