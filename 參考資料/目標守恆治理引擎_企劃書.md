# 目標守恆治理引擎 企劃書
### Goal-Preserving Change Governance Engine

版本：v0.1（規劃階段）｜ 更新：2026年9月 ｜ 命名為暫定工作名稱，可自行更換

> 一句話定義：允許系統的架構、資料、實作與規格自由改變，但所有非目標層級的變更都必須能追溯到明確問題、證據與可驗證的改善；無法證明必要性或價值時，預設不變更。保護的不是舊系統，是核心目標與可驗證的結果。

本企劃書基於前三輪概念設計收斂而成的最終模型撰寫，目標是把「Goal-Preserving Evolution」這套治理哲學轉譯成一個可以實際動手做的工具。全文所引用的外部方法論、工具、學術文獻皆為 2026 年 9 月查證過的真實資料，來源列在文末，不做任何虛構或改編。

---

## 一、專案定位

### 1.1 這是什麼

一個**治理引擎**，不是重構工具本身。它不取代 OpenRewrite、ArchUnit、Knip 這類做實際程式碼分析與轉換的工具，而是坐在它們上面一層，負責：

1. 儲存、版本化「這個系統存在的核心理由」（Goal Charter）
2. 把散落各處的分析工具（依賴圖、死碼偵測、測試結果、git 歷史）統一收斂成「證據」
3. 用一套固定的推理流程判斷「這次變更是否成立」，並把判斷過程留下不可竄改的紀錄
4. 讓 AI agent（例如 Claude Code）可以直接透過工具呼叫這套流程，而不是每次都憑當下對話的印象自由發揮

### 1.2 與 CIS 的關係

這套引擎最初是 CIS 四大支柱之一「軟體工程治理」的延伸構想（CIS Next），但設計上刻意讓它**不綁定 CIS**——換系統、換專案時，思路與工具都能沿用。CIS 是它的第一個實驗場，不是唯一的服務對象。

### 1.3 這不是什麼

- 不是 Clean Code 檢查器（它不問「這段程式碼漂不漂亮」，只問「這是否仍服務核心目標」）
- 不是自動重構機器人（它決定「該不該做、做完怎麼驗」，實際的程式碼轉換交給 OpenRewrite 這類確定性工具）
- 不是能自動判斷 Goal Charter 本身對不對的工具（見第五節「已知限制」）

## 二、核心原則（三輪收斂後的最終版）

以下是這套引擎所有設計決策的最終依歸，任何後續功能增修都不能違反這幾條：

1. **架構可以死，唯一不能失去的是系統存在的核心理由**。V1 → V2 如果是「更簡單、更可靠、更符合核心需求，且舊方案確實被更好的方案取代」，這是 Evolution；如果只是「在舊的上面一直加」，這是 Erosion。兩者外觀相似，區分點在於有沒有清楚的問題定義、證據與淘汰動作。
2. **STOP 是合法的預設結果**，不是流程失敗。系統不該鼓勵「看到不一致就想改」；「這不是問題」「這是問題但現在不值得改」都必須是正式、可被接受的輸出。
3. **改動幅度不等於風險，缺乏證據的改動才是風險**。修改一個核心資料模型可能比刪除兩百個 legacy 檔案風險更高；反過來，只要有清楚目標、完整證據、可比較的驗收標準與完整遷移計畫，重寫整個子系統也可以是最佳方案。
4. **證據門檻不對稱**：REMOVE（不可逆）> REPLACE > MODIFY > ADD（通常可逆）。新增功能的門檻不該和刪除功能一樣高。
5. **驗收標準必須在看到提案之前就先鎖定**，不能讓提案內容反過來定義自己的驗收標準——這條是本企劃書在三輪討論後新增的修正，理由見第四節 4.4。
6. **Goal Charter 穩定但可被挑戰（Stable but Challengeable）**，修改它本身是治理系統裡等級最高的事件，且不能由治理引擎自己裁決（見第五節）。
7. **允許刻意的重複（Intentional Duplication）**。「有重複」不等於「有問題」；過早抽象化本身也是一種需要證據支撐的架構決策。

## 四、完整流程設計

### 4.1 主流程圖

```
GOAL CHARTER（版本化）
        │
        ▼
CORE OBJECTIVE（用 GQM 拆解，見 4.2）
        │
        ▼
「這是不是真問題？」──── 沒證據 ────▶ STOP（合法結果，寫入 Decision Log）
        │ 有初步證據
        ▼
EVIDENCE COLLECTION（呼叫 Evidence Provider，每筆證據標記來源與信心度）
        │
        ▼
IMPACT / VALUE ANALYSIS（值不值得改：Impact vs Fix Cost）
        │
        ▼
CHANGE PROPOSAL（必須引用「4.2 已預先鎖定」的驗收標準，不能自訂新標準）
        │
        ▼
「比現有方案更好嗎？」四值判定（見 4.3）
   ├── PROVEN WORSE / NO MATERIAL DIFFERENCE ──▶ STOP
   ├── INSUFFICIENT EVIDENCE ──▶ STOP*（不等於「問題不存在」，只是證據不足）
   └── PROVEN BETTER
              │
              ▼
      INDEPENDENT VERIFY（獨立驗證，見 4.4）
              │
              ▼
      IMPLEMENT / MIGRATE（大改動借用 Strangler Fig 分階段遷移，見 4.5）
              │
              ▼
      VERIFY NEW STATE（重跑 Evidence Provider，前後 diff 當證據）
              │
              ▼
      OLD SOLUTION DISPOSAL（Removal Gate，見 4.6）
              │
              ▼
      DECISION LOG 寫入（MADR 格式，不可修改）
              │
              ▼
      NEW BASELINE（更新 Goal Charter 底下「目前方案」的指標，Goal Charter 本身不動）
```

### 4.2 CORE OBJECTIVE 的拆解方法：採用 GQM

Goal Charter 裡的目標通常是抽象的（例如「產出高品質影片」），這種抽象目標無法直接拿來做決策依據，必須先拆解成可驗證的問題。這裡採用軟體工程界行之有年的 **Goal Question Metric（GQM）方法論**——由 Victor Basili、Gianluigi Caldiera、H. Dieter Rombach 於 1994 年提出，是目前最廣泛採用的目標導向軟體量測方法，核心結構是三層：Goal（目的）→ Question（把目的拆成可回答的問題）→ Metric（用具體量測回答問題）。

本引擎在標準 GQM 之外多加一欄「Evidence Source」與「Acceptance Criteria」，形成五層鏈：

```
GOAL → QUESTION → EVIDENCE SOURCE → METRIC → ACCEPTANCE CRITERIA
```

**這五層必須在任何 Change Proposal 出現之前就先寫好並鎖定版本**——這是本企劃書對前三輪討論的一個關鍵補強：如果驗收標準是跟著提案一起生成的，驗證階段本質上仍是自己出題自己改。

**CIS 應用範例：**

| Goal | Question | Evidence Source | Metric | Acceptance Criteria |
|---|---|---|---|---|
| G0：產出高品質 AI 影片 | Q1：人物是否保持一致？ | 前後 Keyframe 比對、臉部特徵比對 | 臉部關鍵特徵偏差值 | 偏差 < 既定閾值視為 PASS |
| | Q2：場景是否連續？ | 場景間 Prompt/Schema 比對 | 場景特徵匹配度 | 匹配度 > 既定閾值 |
| | Q3：生成流程是否穩定？ | Pipeline 執行紀錄 | 失敗率 / 重試次數 | 失敗率 < 既定閾值 |

（此表僅為結構示範，實際閾值需依 CIS 現有驗證資料另行制定，本文不虛構具體數值。）

### 4.3 四值決策模型

不用簡單的 YES/NO，採用四值：

| 結果 | 意義 | 後續動作 |
|---|---|---|
| PROVEN BETTER | 有證據證明改善 | 進入 Independent Verify |
| PROVEN WORSE | 有證據證明退化 | STOP，記錄原因 |
| NO MATERIAL DIFFERENCE | 沒有實質改善 | STOP |
| INSUFFICIENT EVIDENCE | 證據不足以判斷 | STOP*（標記為「待補證據」，非「問題不存在」） |

`UNKNOWN ≠ BETTER` 是這裡最重要的一條規則：證據不足時系統的預設反應必須是暫停，而不是把「不知道」當成「可以」。

### 4.4 Independent Verify：為什麼 Context Isolation 還不夠

單純把驗證放到「另一個 session」讀 proposal，能消除的只是「因為我剛才推理過，所以會傾向找支持自己方案的證據」這種路徑依賴偏誤。但這解決不了更深層的問題：**LLM-as-judge 研究已經證實一種穩定存在的「自我偏好偏誤（self-preference bias / self-enhancement bias）」**——2024 年發表於 NeurIPS 的研究證實，LLM 評審會系統性地偏好自己模型家族產生的內容，且這種偏好強度與模型的自我辨識能力呈線性相關；MT-Bench 與 Chatbot Arena 的研究也記錄了同一類系統性偏誤，並指出換一個獨立、能力更強的評審模型能改善與人類判斷的一致性。

因此本企劃書建議的實作方式是雙重保險，而不是只靠「換 session」：

1. **驗收標準在 4.2 階段就先鎖定版本**，Change Proposal 只能引用、不能重新定義。
2. **驗證階段只能看到**：Proposal 內容 + репository 目前狀態 + Evidence Provider 產出的客觀證據 + 已鎖定的 Acceptance Criteria——**看不到提案者的推理過程**。
3. 若條件允許（例如接上多個模型供應商），驗證模型與提案模型應為不同模型，而非只是同模型的不同 session,以降低自我偏好偏誤;若條件不允許,至少要確保驗證的 prompt 是嚴格規則導向、可重複的評分規則,而不是開放式「你覺得這個方案好嗎」。

### 4.5 大型變更的執行策略：借用 Strangler Fig Pattern

REPLACE / REMOVE 類的大型變更，不建議一次性切換（big-bang cutover）。業界對這類遷移最成熟的模式是 Martin Fowler 於 2004 年提出的 **Strangler Fig Pattern**：在新舊系統之間放一層 façade/路由層，讓新舊系統並存，流量逐步從舊系統導向新系統，等新系統完全覆蓋後才正式除役舊系統。這個模式的核心價值是把一次高風險的「大爆炸」遷移拆成一連串小型、可回滾、每一步都能獨立驗證的動作。Fowler 自己也坦承這個模式的代價是要多維護一段時間的過渡架構（façade、雙寫邏輯），但换來的風險降低通常是值得的。

本引擎在 IMPLEMENT / MIGRATE 這一步，對 REPLACE 類事件預設套用 Strangler Fig 的三階段循環（攔截 → 導流 → 除役），並要求每個循環都留下 Decision Log 紀錄，而不是允許過渡層無限期存在（這正是原始討論裡「Compatibility Layer 永久化」想避免的問題）。

### 4.6 Removal Gate：刪除前的強制步驟

REMOVE 事件必須先走一遍以下步驟，其中「為什麼存在」是最容易被忽略、卻是治理系統存在的意義所在——**這正是 G. K. Chesterton 在 1929 年著作《The Thing》裡提出的「Chesterton's Fence」原則**：不要在還不知道一個東西為什麼被立起來之前就把它拆掉；「現在沒人用了」不代表「當初沒有理由」，很可能只是某個很久沒發生的邊界情境。

```
REMOVE REQUEST
   ↓
Why does this exist?（歷史調查：查 commit history / Decision Log / 原始 ADR）
   ↓
Current consumers?（現在還有誰依賴它——用 Evidence Provider 的依賴圖查）
   ↓
Runtime usage?（有沒有執行期使用紀錄）
   ↓
Known edge cases?（有沒有已知但罕見的使用情境）
   ↓
Replacement coverage?（新方案是否覆蓋了舊方案處理過的已知範圍）
   ↓
Observation Window（依風險分級，見第六節）
   ↓
REMOVE + Decision Log 紀錄
```

**重要限制**：REMOVE 不需要證明「世界上任何情況都不需要它」，只需要證明「在已知需求範圍、已知使用範圍、已知依賴範圍內，它已經沒有存在必要」。這是可達成的證明標準，而不是不可能的標準。

## 五、治理事件分類

| 類型 | 觸發條件 | 證據門檻 | 典型輸出 |
|---|---|---|---|
| NO-CHANGE | 問題不成立 / 證據不足 / 不值得改 | 最低 | Decision Log：STOP + 原因 |
| ADD | 現有系統無法滿足新需求 | 低（可逆） | 新 Change Proposal |
| MODIFY | 現有方案仍正確，但實作不足 | 中 | Change Proposal + 局部驗證 |
| REPLACE | 現有方案有根本問題，新方案明確更好 | 高 | Strangler Fig 式分階段遷移 |
| REMOVE | 舊方案已失去存在理由 | 最高（不可逆） | Removal Gate 全流程 |
| GOAL-CHANGE | 核心目標本身需要修正 | 特殊（見下） | 人工裁決，不可自動化 |

**關於 GOAL-CHANGE 的補充**：三輪討論的最終流程圖把 GOAL-CHANGE 放進與其他五類相同的 Evidence → Decision 管線裡，但這在邏輯上站不住腳——整套引擎能運作的前提是「有沒有更好」可以拿 Goal Charter 當裁判，而 GOAL-CHANGE 正是在改裁判本身，系統內部沒有任何東西可以拿來判斷「新 Goal 比舊 Goal 好」。本企劃書因此把 GOAL-CHANGE 明確標記為**永遠需要人工（開發者本人）裁決的節點，治理引擎只負責記錄，不負責自動判定**。

**建議補充第七類（可選，視實作優先度）**：MERGE / SPLIT——兩個原本各自演化的子系統發現大量重疊而合併，或一個模組職責過重而拆分。這種操作是「多個舊解一次性重組成新解」，可以拆成多個並行的 Change Proposal 處理，也可以在後續版本定義成獨立類型，MVP 階段不必須實作。

## 六、風險評分：把公式變成可執行的評分表

前三輪討論提出的公式（Risk ≈ 缺乏證據 + 目標不清 + 影響不明 + 未驗證改善 + 不可逆變更）是正確的哲學，但目前是比喻，不是可以拿來自動分級的算式。本企劃書建議借用工業界成熟的 **FMEA（Failure Mode and Effects Analysis，失效模式與效應分析）** 的評分結構做改造。

FMEA 的原始公式是：**RPN（風險優先數）= Severity（嚴重度）× Occurrence（發生機率）× Detection（偵測難度）**，三項各以 1–10 分計，乘積範圍 1–1000，分數越高代表越該優先處理；此方法廣泛用於工程與品質管理領域，是業界最成熟、最簡單可執行的多因子風險評分模型之一。

改造成治理引擎可用的版本：

```
Change Risk Score = Impact（1-10） × Irreversibility（1-10） × EvidenceUncertainty（1-10）
```

- **Impact**：如果這次判斷錯了，對核心目標的傷害有多大？（對照 FMEA 的 Severity）
- **Irreversibility**：一旦執行，回滾的難度有多高？（對照 FMEA 的 Detection——偵測/挽回問題的難度）
- **Evidence Uncertainty**：目前收集到的證據有多不完整、多不確定？（對照 FMEA 的 Occurrence——但這裡代表的是「誤判機率」而非「失效機率」）

分數範圍同樣落在 1–1000，並對應到第三輪討論已經提出的四級 Observation Policy：

| Risk Score 區間 | 對應等級 | Observation Policy |
|---|---|---|
| 低 | LOW | 立即執行，不需觀察期 |
| 中 | MEDIUM | 標記 deprecated + 監控 |
| 高 | HIGH | deprecated + 觀察窗 + 保留 rollback 方案 |
| 極高 | CRITICAL | 走完整 Strangler Fig 分階段遷移 |

具體的分數區間切點需要在實際使用一段時間、累積足夠案例後再校準，本文不預先給出未經驗證的具體數字。

## 七、功能清單

### 7.1 近期（MVP，套用 CIS 既有的 Development Gate 精神：先驗證核心迴圈能不能跑）

- Goal Charter 文件格式（版本化 Markdown + frontmatter，人工維護，不自動生成）
- Change Proposal 範本，採用 OpenSpec 式三態（proposal → apply → archive），先用純檔案結構實作，不需要伺服器
- Decision Log：採用 MADR（Markdown Architectural Decision Records）格式的 ADR，每筆不可修改，只能新增「superseded by」關聯
- 手動觸發的 Evidence 收集：先串接 1–2 個既有工具（例如 git log 的 co-change 分析、一個依賴圖工具）產出結構化證據
- 「真問題判斷」checklist：先做成一份必須逐項回答的 Markdown 模板或簡單 CLI，不必是完整系統
- Removal Gate 的六步驟 checklist（4.6 節）

### 7.2 中期

- 把上述能力包裝成 MCP Server，讓 Claude Code 可以直接呼叫（`propose_change`、`collect_evidence`、`verify_proposal`、`request_removal` 等工具）
- 串接更多 Evidence Provider（死碼、hotspot、規格漂移偵測）
- Change Risk Score 自動計算（第六節公式）
- Independent Verify 的 context isolation 機制：獨立 prompt session，驗證階段的輸入嚴格限制為「Proposal + repo 狀態 + 客觀證據 + 已鎖定驗收標準」

### 7.3 遠期

- 完整 Observation Window 自動追蹤（到期提醒、依風險等級自動排程）
- 跨專案共用：同一套引擎服務 CIS 之外的其他專案（例如 Legion3K、DEADFLOOR）
- 視覺化 Dashboard（Goal Charter 樹狀圖、Decision Log 時間軸、Risk Score 分佈）

## 八、技術架構建議

以下列出選項與取捨，不預設特定語言，實際選型應由你決定：

### 8.1 對外介面：MCP Server

由於你的主要工作介面是 Claude Code，把治理引擎包裝成 **MCP（Model Context Protocol）Server** 是最直接的整合方式。MCP 是 Anthropic 於 2024 年 11 月推出的開放標準，採用 client-server 架構，讓 AI 應用程式可以用一致的方式呼叫外部工具、讀取資源；官方提供 TypeScript 與 Python 的 SDK，本地伺服器走 stdio、遠端伺服器走 Streamable HTTP，協定本身建構在 JSON-RPC 2.0 之上。用 MCP 包裝的好處是治理引擎變成 Claude Code 可以直接呼叫的工具，而不是另一套要手動切換的獨立軟體。

### 8.2 資料儲存：docs-as-code 優先

Goal Charter 與 Decision Log 建議走「docs-as-code」路線——用版本化的 Markdown 檔案存在 git repository 裡,與程式碼放在一起,而不是額外的資料庫。這是 ADR 社群（Michael Nygard 提出 ADR 概念,MADR 模板由 Oliver Kopp 與 Olaf Zimmermann 制定）行之有年的實務做法,好處是天然可以用 git diff 追蹤變更、可以走 PR review 流程、不需要額外的伺服器維運。Evidence（例如 Risk Score 計算的中間結果）如果量大、結構複雜,可以另外用輕量資料庫（如 SQLite）存放,但決策紀錄本身建議保持 Markdown。

### 8.3 Evidence Provider 整合方式

不重新造輪子：直接呼叫既有工具的 CLI，解析其結構化輸出（JSON 優先）。多數第八節列出的工具都支援 CLI 呼叫與 CI 整合，可以用 shell out 的方式串接，不需要重新實作依賴圖或死碼偵測邏輯。

### 8.4 核心引擎語言

這層取決於你想要的部署形態：
- 若要單一二進位檔、快速啟動、與現有 CLI 工具風格一致 → Rust 或 Go
- 若要最快與 MCP 官方 SDK、既有 Node 生態（如 OpenSpec）整合 → TypeScript
- 若要最快原型驗證、與大多數 Evidence Provider（Python 生態的 Vulture 等）互通 → Python

三者都有官方 MCP SDK 支援，沒有技術障礙，純粹是你熟悉度與其他專案生態一致性的選擇。

## 十、開發階段規劃（套用 CIS Development Gate 精神）

沿用你已經在 CIS 驗證過的三層過濾邏輯——任何功能開發前先問：這是不是近期驗證必須的？如果不是，是不是中期自動化的必要基礎？如果都不是，就不進 Roadmap。

**近期（Reality Test）**：只用 Markdown 檔案 + 一份 checklist，手動跑一次完整流程（Goal Charter → 真問題判斷 → Evidence 手動收集 → Change Proposal → 四值判定 → Decision Log），驗證流程本身「能不能用」，先不做任何自動化或 MCP 化。

**中期**：MCP Server 化 + 串接 2–3 個 Evidence Provider + Risk Score 自動計算。

**遠期**：跨專案共用、Observation Window 自動追蹤、視覺化。

## 十一、已知限制與誠實的風險（不迴避）

1. **GOAL-CHANGE 無法自動化**。這是結構性的，不是工程實作不足——治理引擎的裁決邏輯建立在 Goal Charter 之上，Goal Charter 本身改變時，系統內沒有更高層的裁判可用，必須是人工決策。
2. **CIS 這類主觀品質目標（「好的影片」）無法完全化約成 Evidence**。GQM 拆解能降低主觀判斷的隨意性，但無法消除主觀性本身——「故事是否打動人」這類問題目前沒有可信的量化 Evidence Source。
3. **量化驗收標準有被博弈的風險（Goodhart's Law）**。一旦「有沒有達標」變成決策開關,系統會有隱性動機去挑容易量化、而非真正重要的問題。建議 Question 清單要定期由人工重新檢視,而不是只看 Metric 分數。
4. **獨立驗證無法完全消除 LLM 的系統性偏誤**，只能降低路徑依賴偏誤；同模型家族仍可能有結構性偏好，理想狀況需要跨模型驗證。
5. **治理成本本身可能變成新的技術債**。這套引擎設計給獨立開發者、同時維護多個專案的場景，MVP 階段刻意保持輕量（純檔案 + checklist），避免一開始就上重型基礎設施。
