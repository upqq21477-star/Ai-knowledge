# 重構治理系統（Refactoring Governance System）研究與設計建議

更新時間：2026年9月 ｜ 基於原始研究整理 + 獨立網路查證

## 一、對原研究的評估

原文的核心判斷是對的：這不是單純的 Code Refactoring，而是「Architecture-preserving evolution」（架構保存式演化）——每次疊代都要先理解全局，再動手，而不是「改幾個檔案、能跑就好」。這個方向在業界最新的實務文章中被反覆強調：面對不熟悉的舊系統，第一步應該是「定位（orientation），不是修改（modification）」，先讓 AI 產出架構的高層說明、資料流、隱藏耦合的模型，且明確要求分析階段「先不要提重構方案」。這跟你想要的「先分析現有系統所有功能任務、逐層拆解分類、整理主軸核心，最後才規劃重改方向」完全是同一套方法論，且有紮實的實務背書。

Carola Lilienthal 對架構侵蝕（Architecture Erosion）的學術界定，把成因歸納為四種現象：資淺開發者只顧局部不顧全局做設計決策；架構侵蝕已經發生但因時間或成本壓力沒人修正；系統複雜度隨應用問題複雜度增長；開發者對複雜問題採用過度簡化的解法但往往不成功。這與原文十二類問題的精神一致，可以作為你的系統的理論基礎。

但原文有兩個問題需要修正：

1. **工具部分部分過時或規模過小**：原文標註的 architecture-consistency-guardian 專案本身也承認只有 2 stars、0 watchers，概念可借鑑但不能當底層依賴；其餘工具中也有幾個屬於中小型專案，需要持續追蹤是否還在維護。
2. **完全沒抓到 2026 上半年最大的變化：Spec-Driven Development（SDD）生態**——這個領域幾乎是直接針對原文「Specification Drift / Business-Logic Drift」問題發展出來的一整套方法論與工具鏈，詳見第四節。

還有一點需要誠實提出：原文設計的「CIS Next 十六條規則」（10個必答問題才能合併、6階段 Feature Lifecycle、6階段 Data Lifecycle、9類治理層）本質上是**企業級規模**的治理成本。你是獨立開發者，同時維護十幾個專案，如果每次重構都要跑完整流程，治理本身很可能變成新的技術債——這正是你自己在 CIS 裡已經設下「CIS Development Gate」（新功能先問近期/中期/遠期用途，三者皆否則不進 Roadmap）想避免的事。第五節會把同一套「分級過濾」精神套用在治理系統本身上。

## 二、疊代退化的十四類問題（原文十二類 + 補充兩類，附佐證）

以下保留原文全部十二類分類，逐一補上學術或業界佐證；並新增兩類原文沒有涵蓋、但對你目前大量使用 AI 協作開發特別relevant 的問題。

1. **功能堆疊（Feature Stacking）**：新功能一律往舊架構上加，而不整理整體模型，最終形成 Manager 疊 Manager 的結構。這是技術債文獻中最常被引用的成因——時間壓力下的捷徑選擇。

2. **Duplicate Logic**：同一功能出現多個版本（`_v2`、`_new`），沒人確定哪個是正式版。屬於程式碼層級技術債的典型症狀。

3. **Dead Code / Legacy Code**：新系統取代舊系統後，舊系統沒被刪除，長期演變成沒人敢刪的相容層堆疊。2026年的死碼偵測指南指出，含有大量死碼的專案，新工程師 onboarding 時間會拉長 20-30%。

4. **Architecture Drift**：文件寫的依賴方向與實際程式碼不符。這正是 Lilienthal 四現象論中「侵蝕已發生卻沒人調整」的直接體現，也是敏捷式開發（不重視事前架構設計）特別容易誘發的問題——研究指出敏捷流程反而可能讓架構侵蝕更早出現。

5. **Dependency Explosion**：單一模組依賴過多其他模組，改一處全面震盪。這是所有依賴圖工具（見第三節）存在的核心理由。

6. **Hidden Coupling**：表面沒有依賴關係，實際透過共享狀態、環境變數、快取產生隱性耦合。現代程式碼智慧工具已把這類問題獨立出來處理，透過分析 git 歷史中「總是一起變更的檔案」來找出靜態依賴圖看不到的隱藏耦合。

7. **Data Schema Drift**：資料格式升級，但舊功能仍預期舊格式欄位，導致新資料存在但舊功能悄悄失效。**Riot Games 清理《英雄聯盟》資料債的技術部落格**是這個問題在遊戲業最紮實的實例：資料債產生於在已有技術債的系統上持續疊加內容，導致更動舊系統風險越來越高，團隊因此傾向用「更好的新格式」開新內容，而不是修舊系統——結果就是新舊格式長期並存，直到團隊專案投入清理（bundling VFX、更新腳本指向新資產路徑、清除多年累積的無用檔案）。

8. **Semantic Drift**：同一個名稱（例如 `PASSED`）在不同版本代表不同語義，程式碼還能跑但意義已經變了。這類問題目前沒有通用工具能自動偵測，屬於需要人／AI 語意判斷的治理範疇（見第五節）。

9. **Documentation Drift**：文件寫的是舊架構，AI agent 讀了舊文件後按舊規則改新系統。2026年的 AI coding context engineering 文章特別強調：如果沒有明確告知「舊模式已棄用但仍存在」，agent 會挑出現頻率較高的模式（通常是舊的）沿用，而不是正確的新模式。

10. **Test Drift**：CI 綠燈，但測試驗證的其實是舊行為。屬於技術債文獻中「測試覆蓋率下降」的子類。

11. **Compatibility Layer 永久化**：過渡期用的 Adapter 沒有退場機制，變成永久架構的一部分。Riot 案例中同樣出現：「暫時性」的向後相容層長期存在，直到專案主動決定關閉舊系統。

12. **Feature Zombie**：功能被取代但沒正式標記 deprecated，AI 搜尋 repository 時會誤判為現行系統。這與原文引用的死碼偵測工具邏輯一致：純靜態分析找不到「業務邏輯層面的淘汰」，需要結合覆蓋率監控、log 監控、feature flag 流量追蹤等多重訊號。

13.（新增）**AI 生成代碼的技術債複合速度更快**：2026年的研究指出，AI 生成程式碼量遠大於人工，導致 schema drift、格式不一致等問題複合速度比人工技術債快得多，因為「不同環境跑在稍微不同的 patched 分支上，各自對回應格式有微妙不同的假設」，沒人能追溯哪個假設才是對的，因為從沒有一個canonical contract存在過。這對你大量使用 AI 協作的工作模式直接相關。

14.（新增）**Comprehension Debt（理解債）**：一篇 2026 年針對小型獨立遊戲團隊（三人團隊，含程式設計師）的研究提出，AI 輔助開發會產生「技術債之外」的理解債——團隊對系統整體的理解速度跟不上 AI 產出程式碼的速度。這對獨立開發者/小團隊特別relevant，比企業級技術債研究更貼近你的實際工作規模。

## 三、GitHub / 工具地圖：原文八個工具現況 + 2026年更新

### 原文工具現況（逐一保留，不遺漏）

| 工具 | 原文評價 | 現況備註 |
|---|---|---|
| OpenRewrite | AST-based 確定性自動重構，最成熟 | 仍是業界標竿，多語言 migration 工具鏈成熟 |
| ArchiCore | 依賴圖/死碼/複雜度/架構規則全能型 | 概念正確，建議查證近期維護活躍度 |
| Rev-dep | 把架構規則變 CI enforcement（Architecture Contract） | 概念與下方 ArchUnit 家族工具同源，後者更成熟 |
| Fallow | 死碼+baseline audit（只擋新增的屎山，不強制清完舊的） | 這個「只審查變更檔案、不要求一次清完」的思路非常適合你，值得保留 |
| noslop | TS/JS/Python 死碼+循環依賴，強調 deterministic | 同類工具中，Knip（見下）目前是 JS/TS 死碼偵測的公認首選 |
| TrueCourse | 把 PRD/ADR/README 建成 specification corpus，驗證實作是否符合規格 | 這個方向現在已經演變成一整個「Spec-Driven Development」生態，見第四節 |
| Codespaces | Architecture-aware 程式碼智慧，回答「誰依賴這個」「改這個影響誰」 | 這類「AI agent 用的程式碼智慧層」現在是 2026 年成長最快的類別，見下 |
| architecture-consistency-guardian | 概念最接近你要的完整 workflow | 原文自己也承認規模小（2 stars），僅供借鑑思路 |

### 2026年新出現的類別：MCP 原生程式碼智慧工具

這是原文完全沒有涵蓋、但對你（大量用 Claude Code 工作）最直接相關的一批新工具，共同特徵是：把依賴圖、死碼、架構邊界檢查、git 歷史耦合分析包裝成 MCP server，直接讓 AI agent 查詢，而不是產出人看的報告。

- **repowise**：開源（AGPL-3.0）、可自架，把依賴圖、死碼偵測、git 智慧（誰改得多、誰真正擁有這段程式碼）、自動生成文件、程式碼健康分數整合成一套系統，提供 9 個 MCP 工具（overview、context、risk、decision history、semantic search、dead code、health...）。是目前開源陣營裡功能最完整的同類工具。
- **ops-codegraph-tool（optave）**：34 種語言的 function-level 依賴圖 CLI，34 個 MCP 工具，明確包含「架構邊界強制執行」「CI 品質關卡」「git diff 影響範圍分析（含 co-change 歷史耦合）」。完全本地執行、零 API key。
- **pharaoh.so**：專門針對 AI 輔助開發設計的依賴圖，強調 call graph 不足以代表完整架構（漏掉繼承、型別邊界、測試關係、套件邊界、config 耦合），走的是語意圖（semantic graph）路線。

### 死碼偵測（成熟、單一語言專精）

- **Knip**：JS/TS 死碼偵測公認首選，找未使用的檔案、匯出、依賴，把專案建模成依賴圖。
- **Vulture**：Python 死碼偵測的標準起點，容易整合進 CI。

### 架構邊界強制執行（測試驅動的架構規則）

原文沒有明確提到這一類，但這其實是「Architecture Contract」概念最成熟、最穩定的實作方式——把架構規則寫成單元測試，違反規則就是測試失敗，直接嵌進既有 CI 流程，不需要額外平台：

- **ArchUnit**（Java）、**NetArchTest**（.NET）、**import-linter**（Python）、**dependency-cruiser**（JS/TS）——概念一致：「Domain A 不能 import Domain B」寫成可執行斷言。

### 商用 Hotspot / 行為式程式碼分析

- **CodeScene**：業界公認的 hotspot-driven（用 churn × complexity 找出最該優先處理的區塊）技術債視覺化標竿，非開源但成熟度最高。

## 四、2026年最大的變化：Spec-Driven Development（SDD）生態

這是原文完全沒抓到、但直接對應原文「Specification Drift」「TrueCourse」構想的最新發展。核心概念：把規格當成可執行契約（executable contract），程式碼是從規格衍生、驗證出來的產物，用自動化強制執行來防止飄移，而不是被動的文件。

其中 **OpenSpec**（開源，2026年6月時已有約5萬顆星，是目前維護最活躍的開源 SDD 框架）用嚴格的三階段狀態機管理規格變更：`specs/`（當前狀態，單一事實來源）與 `changes/`（進行中的提案，含 proposal.md、tasks.md、delta specs）分開存放，任何程式碼變更前必須先明確寫出哪些流程被「修改」、哪些是「新增」。**這幾乎就是原文提議的「Feature Lifecycle」的現成實作**，不需要你自己重新發明狀態機。

一篇 2026 年 6 月的學術論文《The Spec Growth Engine》直接把這個問題點名為「silent spec-code drift」——程式碼演進了但規格沒有跟著動，直到問題被發現時修復成本已經很高——並提出「drift-enforced architecture」的研究方向，這正是原文「Specification / Documentation Drift」小節想解決的問題，只是用了不同的名詞。

**但這個領域也有誠實的警訊，需要一併納入你的設計考量**：業界田野調查指出規格漂移（spec drift）仍是目前最大的實務難題——規格會不斷腐化、產生重複與矛盾，過度儀式化（over-ceremony）會讓 markdown 規格量爆炸、反而稀釋 AI agent 的注意力，甚至出現「agent 不遵守規格」的問題,代表控制力某種程度上是幻覺。也有實務工作者測試後認為，對小改動套用完整 SDD 流程明顯得不償失（有位獨立開發者回報規格撰寫一度吃掉專案 50% 時間才決定縮減流程）。這與你目前的獨立開發規模高度相關：**完整 SDD 流程不該無差別套用在每一次修改上**。

## 五、我的設計建議：把「分級過濾」精神套用在治理系統本身

原文的十六條規則、十個必答問題、六階段生命週期，理論上都對，但如果每次重構都要求跑完整流程，治理成本本身會變成新的技術債——尤其你是獨立開發者，同時維護十幾個專案。我建議把你自己已經在 CIS 裡驗證過的「CIS Development Gate」三層過濾邏輯（先問近期/中期/遠期用途，三者皆否則不做），原封不動地套用在這個治理系統本身上，形成一個四階段、但**依變更規模分級**的輕量 pipeline：

**Phase 0：系統快照（工具自動產出，不靠 AI 逐行讀）**
用第三節列出的確定性工具（依賴圖 + 死碼報告 + hotspot 報告）打底，產出結構化資料，而不是把整個 repo 丟給 AI 讀——這正是《Spec Growth Engine》論文點名的「context explosion」問題：AI agent 被迫一次性推理整個 repository,輸出品質會隨 context window 被填滿而下降。用工具產出的結構化摘要當 context，AI 只需要做語意層的判斷。

**Phase 1：AI 語意分類與歸納**
把 Phase 0 的結構化輸出交給 AI，做原文列出的十類原本沒有工具能解的部分：辨識 Zombie Feature、判斷 Semantic Drift、抽取主軸核心、對照舊架構文件找出 Documentation Drift。這一步才是你原文說的「逐層拆解、分類、歸納、整理出主軸核心」。

**Phase 2：規格狀態機**
不需要自己重新設計 Feature Lifecycle 的六階段模型，直接借用 OpenSpec 的 `specs/` + `changes/` 三階段狀態機（proposal → apply → archive）,現成、有社群維護、且與原文的 Feature Lifecycle 精神一致。

**Phase 3：分級治理閘門（借用你自己的 CIS Development Gate 邏輯）**
- 小改動（單一模組內、無 API/Schema 變更）→ 輕量 checklist（跑 Phase 0 工具即可，不需要十問）
- 中改動（跨模組、有 API 變更）→ 原文十問中挑出真正相關的幾條
- 大改動（架構層級、涉及 Legacy Disposal）→ 才跑原文完整流程

**Phase 4：重構後稽核**
重新跑一次 Phase 0 的工具,把前後結果做 diff,作為「舊功能是否真的清乾淨」「有沒有製造新的 duplicate/adapter」的客觀證據,而不是靠人工檢查清單。

這個設計的核心原則，跟原文結論一致但更明確：**確定性工具（依賴圖、死碼、架構邊界、規格狀態機）已經是成熟賽道，不需要你自己重做；你真正該投入心力的，是這些工具目前都解不了的語意層判斷——Production Object、Identity、Schema、Semantic Drift 與 Architecture Contract 的治理決策，以及把治理成本本身分級，避免治理流程自己變成新的屎山。**
