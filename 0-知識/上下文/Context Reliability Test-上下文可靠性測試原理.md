# Context Reliability Test｜上下文可靠性測試原理

版本：v1.0
狀態：【候選知識；由 C04 建立；待最小實測】

## 一、定位
Context Reliability Test 用來測試：

> 當 Context 的大小、組成、順序與相關性改變時，AI 是否仍能保持任務理解、記憶、規則與結論的一致性。

它測的不是模型「記得多少」，而是 Context 變化是否使可接受的行為失穩。

## 二、核心維度
至少測四類：
1. 任務理解：是否仍正確理解任務。
2. Context Recall：關鍵資訊是否仍被正確使用。
3. Rule Consistency：固定規則是否被遵守。
4. Output Stability：在等價 Context 變化下，結果是否出現不合理漂移。

必要時增加：
- 跨段落關係。
- 長距離依賴。
- 歷史／目前狀態區分。
- 衝突資料處理。
- 不確定性表達。

## 三、測試矩陣
同一任務建立：
~~~text
短 Context / 基準 Context / 長 Context / 過量 Context
~~~

並可進一步改變：
- 關鍵資訊位置。
- 無關資料比例。
- 歷史資料比例。
- 重複資料。
- 規則位置。
- 衝突資料。
- 證據位置。

## 四、判定原則
不能只用「答案正確／錯誤」。

至少記錄：
~~~text
理解 → 關鍵證據使用 → 規則遵守 → 結論 → 變化原因
~~~

若答案改變，必須判斷：
- 是因為新 Context 提供了更正證據？
- 是因為真正的資訊衝突？
- 是因為 Context 過長造成性能下降？
- 是因為任務本身具有多解？
- 還是模型產生不受證據支持的漂移？

## 五、可靠性基準
可靠性測試的目的不是要求所有 Context 大小得到完全相同的文字答案。

應要求的是：
- 關鍵事實不應無理由漂移。
- 明確規則不應因 Context 增加而被任意忽略。
- 新證據造成的改變必須可解釋。
- 無關資料不應大幅改變核心判定。
- Context 不足時應暴露不確定性，而不是靠猜測補足。

## 六、外部研究依據
RULER 將長 Context 測試從單純 Needle-in-a-Haystack 擴展到多 needle、multi-hop tracing、aggregation 等任務，並發現模型在長度增加與任務複雜度提升時可能出現明顯性能下降。另有研究指出，即使相關證據已經被正確取得，輸入長度本身仍可能降低任務表現。

因此 C04 必須測「任務行為」，不能只測「能不能找到某個字串」。

## 七、限制
可靠性結果必須綁定：
- 模型版本。
- 任務類型。
- Context 組成。
- 測試資料。
- 評估規則。

不能宣稱一次測試證明所有 Context 大小均可靠。
