# Context Budget｜任務上下文預算與最小充分上下文

版本：v1.0
狀態：【候選知識；由 C03 建立；待最小實測】

## 一、定位
Context Budget 不是單純計算 token 上限，而是測定「完成特定任務所需的有效 Context」。

核心命題：
> Context 越多不代表越好；真正要找的是在特定任務、模型與資料條件下，足以可靠完成任務的最小充分 Context，以及增加 Context 後開始產生邊際收益下降或性能下降的位置。

## 二、由現有知識直接推導
現有「上下文成本」與「上下文管理原理」已確立：
- 任務導向載入。
- 最小充分上下文，而非最少資料。
- 資訊不足時擴大。
- 資訊足夠時停止。
- 完整稽核不能為節省 Context 而省略必要資料。

C03 將上述原理進一步變成可測量的工程能力。

## 三、測量對象
每個 Context Budget 測試至少固定：

| 對象 | 說明 |
|---|---|
| Task | 任務定義 |
| Model | 模型與版本／可辨識資訊 |
| Context Set | 提供的資料集合 |
| Context Size | token、字數或其他可重現尺度 |
| Evidence Coverage | 任務所需關鍵證據覆蓋程度 |
| Output | 模型結果 |
| Correctness | 正確性 |
| Rule Consistency | 規則一致性 |
| Unsupported Claims | 無證據主張 |
| Cost | Context 讀取／處理成本 |

## 四、核心測試
同一任務建立多個 Context 梯度：

~~~text
C0 → C1 → C2 → C3 → ... → Cn
~~~

其中可以是：
- 只提供必要證據。
- 加入定義資料。
- 加入目前狀態。
- 加入相關歷史。
- 加入大量低相關資料。

每一級都使用相同任務與判定規則。

## 五、輸出
至少得到：
1. 最小可完成 Context。
2. 最小可靠 Context。
3. 性能開始飽和的位置。
4. 增加 Context 後性能下降的位置（若存在）。
5. 哪些資料真正改變結果。
6. 哪些資料只是增加成本。
7. 任務對 Context 的敏感度。

因此 Context Budget 是「任務條件下的有效預算」，不是全專案固定 token 數。

## 六、限制
不可直接把某一任務測得的預算套用到所有任務。

Context Budget 必須與模型、任務、資料類型、評估標準、Context 組成一起解讀。

外部研究顯示，模型宣稱的 Context Window 不等於實際有效 Context；RULER 等工作也發現長度增加時，多數模型在更複雜任務上的表現會下降。2025 年研究更指出，即使相關證據已被正確取出，單純增加輸入長度仍可能造成性能下降。這支持「測有效 Context，而不是只看宣稱容量」的方向。

## 七、停止條件
當新增 Context 不再改善可靠性，或成本增加而結果沒有實質改善，即可停止擴張。

完整稽核、安全檢查等明確要求全量資料的任務，不適用一般節省 Context 的停止規則。
