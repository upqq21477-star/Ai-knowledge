# 系統目錄與觸發管理原理

日期：2026-09-17
狀態：【候選知識；已完成外部初步比對；待實際案例驗證】

## 一、核心定義

系統目錄（System Catalog）是用來保存「系統身份與關係 metadata」的薄型索引層。

觸發條件管理（Trigger Registry）是用來保存「事件／情境可能對應哪個系統」的薄型匹配層。

兩者都不是專責系統執行邏輯的替代品。

## 二、系統目錄的核心資料

最低可用資料：

- System ID
- 系統名稱
- 系統文件位置
- 狀態
- 方案歸屬
- 功能摘要
- 關聯知識書

目錄保存引用，不複製完整系統內容。

## 三、為什麼需要穩定 System ID

系統名稱可能改變，文件位置也可能移動。

因此：

```text
名稱 = 人類可讀識別
位置 = 目前定位資訊
System ID = 穩定關聯鍵
```

Trigger Registry 不應以「系統名稱＋路徑」作為唯一關聯，而應保存 System ID。

## 四、觸發條件管理的核心資料

最低資料：

- Trigger ID
- 觸發事件／條件
- 目標 System ID
- 觸發狀態
- 粗略類別

可依實際需要增加版本、來源、衝突群組等 metadata，但第一版不預先建立複雜欄位。

## 五、兩層責任

```text
Trigger Registry
= 哪個系統可能需要被叫醒？

System Catalog
= 這個系統是誰、在哪裡、屬於哪個方案？

Solution
= 多個能力如何協作？

Target System
= 實際如何執行？
```

這個分層可以避免 Trigger Registry 逐漸變成巨大中央執行引擎。

## 六、基本路由

```text
事件／情境
↓
Trigger Registry
↓
取得 System ID
↓
System Catalog
↓
取得狀態／方案歸屬
↓
方案
↓
專責系統
```

## 七、多重匹配

第一版不建立複雜自動優先級。

```text
0 個匹配
→ 沒有已知觸發能力

1 個匹配
→ 正常轉交

多個匹配
→ 保留候選
→ 標記歧義
→ 不得靜默選擇
→ 交由統御／問題解決能力處理
```

這可以降低錯誤路由比「強行選一個」更重要的風險。

## 八、目錄不是唯一真實來源

系統目錄應是 metadata／索引層，而不是所有系統執行狀態的唯一真實來源。

Backstage Software Catalog 的成熟做法也是將 catalog 用於 ownership、inventory、search、lifecycle 與 dependency mapping 等高層 metadata，同時明確指出 catalog 不適合作為所有即時動態關係的 ultimate source of truth。citeturn0search0turn0search11

因此本知識採用：

```text
系統文件／實際狀態
= 專責真實來源

系統目錄
= 快速定位與關係索引
```

## 九、穩定引用的外部比對

Backstage 的 entity reference 使用穩定識別方式連接不同實體，而不是單純依賴顯示名稱。其 catalog entity 也將 metadata、status、owner、system 等關係分開管理。這支持本專案使用 System ID 與 metadata 分離的做法。citeturn0search1turn0search3

## 十、分離控制責任的外部比對

Kubernetes 將控制迴路拆成多個 controller，各自處理特定資源或狀態面向，而不是由單一 controller 管理所有事情。這支持本專案把「觸發匹配」與「系統／方案管理」分成不同責任。citeturn0search7

## 十一、主要失效風險

### 1. 觸發條件過度集中

如果 Trigger Registry 開始保存完整執行流程，它會逐漸變成第二個系統引擎。

### 2. 目錄與真實文件脫節

如果系統改名、移動、廢棄後沒有更新 catalog，路由就可能指向錯誤目標。

### 3. 多重觸發競爭

同一事件可能同時匹配多個系統，需要明確處理歧義。

### 4. 觸發條件爆炸

每新增一個例外就增加一條規則，最終可能失去可理解性。

### 5. 目錄資料重複

如果各方案、各系統都各自保存一份系統身份，可能產生多份互相衝突的資料。

因此正式 System ID 應只有一個身份來源，其餘文件引用它。

## 十二、目前採用的最小原則

```text
先有 System ID
↓
再有 System Catalog
↓
再有 Trigger Registry
↓
觸發只做匹配
↓
方案負責協作
↓
系統負責執行
```

不因外部產品功能完整，就直接複製企業級 CMDB、Service Catalog 或事件平台。
