# 系統目錄分層與資料規模管理原理

版本：v1.0
狀態：【已建立；待本專案實測】
日期：2026-09-17

## 一、目的

處理系統數量增加後的搜尋、維護與一致性問題，但避免過早建立大量分支目錄或重複資料。

## 二、分層原則

先粗略分類，再依實際問題細分。

第一階段只需要能回答：

- 這是哪一類系統？
- 我要找哪一類能力？
- 系統目前在哪裡？

分類不是執行層級，也不是新的方案層。

## 三、推薦資料模型

```text
全域 System Registry
├─ 核心系統視圖
├─ 管理系統視圖
├─ 搜尋／研究視圖
├─ 驗證視圖
├─ 問題解決視圖
└─ 其他視圖
```

各視圖引用同一 System ID，不複製系統身份資料。

## 四、何時才需要實體拆分

不是以「系統數量達到 N」作為固定門檻，而是觀察：

- 搜尋是否變慢或容易取錯。
- 單一檔案是否難以維護。
- 更新責任是否開始分化。
- 不同資料的更新頻率是否明顯不同。
- 不同分類是否需要不同驗證流程。
- AI 是否頻繁受到無關內容干擾。
- 單一索引是否已經難以理解。

出現上述實際問題後，才考慮物理分片。

## 五、分片後的原則

即使物理拆分，也必須維持：

`一個 System ID = 一個正式系統身份`

全域索引可引用分片；分片不能各自創造另一份相同系統身份。

## 六、外部比對

Backstage Catalog 使用 metadata、Kind、Type、Lifecycle、Namespace 等欄位進行分類與篩選，並提供搜尋；其官方設計同時提醒 Catalog 的範圍應適當，不應把所有即時動態關係都塞進目錄。

ServiceNow CMDB 則顯示大型系統在規模化後需要資料治理、資料品質、責任與關係管理，但本專案目前不需要直接採企業級 CMDB 複雜度。

## 七、採用結論

目前採：

> 全域索引 + 粗分類 + metadata + 搜尋／篩選 + 同一身份多視圖。

只有在實測證明單一索引造成實際效率或維護問題時，才進行物理分片。
