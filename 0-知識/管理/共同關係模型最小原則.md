# 共同關係模型最小原則

版本：v1.0
狀態：【候選知識；已完成外部方法比對；待實際案例驗證】

## 一、目的

本知識定義四方案共同需要的 Relationship（關係）最小語義，避免每個方案自行保存一套互不相容的「所屬、依賴、引用、取代、來源」清單。

核心問題：

> 關係應該描述什麼、由誰指向誰，以及如何避免把關係誤當成對象本身？

## 二、外部方法比較

Backstage Software Catalog 使用有方向的 Relation 表達 Entity 之間的關係，例如 `ownedBy / ownerOf`、`providesApi / apiProvidedBy`。官方文件強調 Relation 有 source、target、type 三個核心概念，而且關係可以由不同來源推導；Catalog 中形成的 relation 可作為該關係資料的權威表示。citeturn0search4turn0search5

Kubernetes 則使用 OwnerReference、ObjectReference 等方式以明確對象身份連接資源，說明關係引用應指向可識別的對象，而不是單純依賴檔案位置。citeturn1search0turn1search12

## 三、最小關係結構

一條關係至少具有：

```text
Source
↓
Relationship Type
↓
Target
```

例如：

```text
AI知識管理系統
↓ belongsTo
AI知識管理方案
```

或：

```text
系統 A
↓ dependsOn
系統 B
```

## 四、關係是有方向的

不得只保存：

```text
A ↔ B
```

而應保留：

```text
A → relation → B
```

因為：

```text
A dependsOn B
```

與：

```text
B dependsOn A
```

語義完全不同。

需要反向查詢時，可以由關係模型推導，而不是重複保存兩份獨立真實資料。

## 五、目前優先支援的關係類型

第一階段只保留確實在 Repository 中反覆出現的類型：

| 關係 | 意義 |
|---|---|
| belongsTo | A 屬於 B |
| owns | A 對 B 負主要責任 |
| dependsOn | A 的工作依賴 B |
| references | A 引用 B |
| supports | A 支援 B |
| replaces | A 取代 B |
| derivedFrom | A 由 B 推導／演化而來 |
| validates | A 驗證 B |
| relatedTo | A 與 B 有明確關聯但目前無更精確類型 |

這不是永久完整清單。只有實際案例反覆產生新需求時才增加關係類型。

## 六、Ownership 不等於 Authorization

Backstage 特別將 owner 定位為責任歸屬與聯絡責任，而不是直接用來執行 runtime authorization。citeturn0search4

本專案採用相同邊界：

```text
Ownership
＝ 誰負責維護／處理

Authorization
＝ 誰有權執行某操作
```

兩者不能因為名稱相近就合併。

## 七、Relationship 不等於 Metadata

例如：

```text
owner = A
```

可以作為簡短描述，但真正需要跨對象查詢時，應能表示：

```text
System X
↓ ownedBy
Group A
```

因此 Metadata 可以提供關係提示，但正式 Relationship 應具有可被其他能力引用的語義。

## 八、Relationship 不等於 Dependency

Dependency 是關係的一種，而不是所有關係。

例如：

```text
A references B
```

不代表：

```text
A dependsOn B
```

只有當 B 缺失或改變會實際影響 A 的工作能力時，才應使用 dependency 語義。

## 九、關係與版本

關係可能隨版本演化：

```text
A v1
↓ dependsOn
B v1

A v2
↓ dependsOn
C v1
```

因此不能假設「建立過關係」就代表永久有效。

需要判斷關係目前是否仍成立，以及其適用版本／時間／條件。

## 十、關係與狀態

關係本身也可能有生命週期：

```text
候選
→ 有效
→ 失效
→ 歷史
```

不能只因關係曾經存在，就在目前工作中繼續使用。

## 十一、禁止重複保存權威關係

如果 A 與 B 的關係已由共同 Relationship 模型保存，不應讓四個方案各自建立一份獨立且可能互相衝突的權威關係。

可以建立：

```text
索引
視圖
快取
搜尋結果
```

但必須能回到共同的關係來源。

## 十二、禁止中央關係引擎接管所有業務邏輯

Relationship Registry 可以回答：

```text
誰屬於誰？
誰依賴誰？
誰引用誰？
誰取代誰？
```

但不因此負責：

```text
替方案做決策
替系統執行任務
自動修改所有下游資料
自動解決問題
```

這延續本專案「薄目錄／薄路由、分散責任」原則。

## 十三、最小判斷問題

建立一條新關係前至少確認：

```text
1. Source 是哪一個明確對象？
2. Target 是哪一個明確對象？
3. 關係到底代表什麼？
4. 是否具有方向？
5. 是否需要時間／版本／條件？
6. 是否與既有關係類型重疊？
7. 這是正式關係還是僅供搜尋的標籤？
8. 誰負責維護關係？
9. 關係失效時如何處理？
```

## 十四、驗證方式

使用 Repository 實際案例測試：

1. 系統與方案的所屬關係。
2. 系統與知識的支援／使用關係。
3. 系統依賴另一系統的案例。
4. 舊能力被新能力取代的案例。
5. 知識由來源／證據形成的案例。
6. 關係失效或版本變更後能否避免繼續誤用。

## 十五、核心結論

> Relationship 是「對象與對象之間的有方向語義」，不是一張方便查詢的雜湊表，也不是中央業務流程引擎。

> 先穩定對象 Identity，再建立 Relationship；先定義關係語義，再決定是否需要實體 Registry、資料庫或自動化系統。
