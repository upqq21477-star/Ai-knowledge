# 共同資料最小描述原則

狀態：**【初版建立；待實際案例驗證】**

## 一、目的

本文件定義不同資料類型在未來需要被描述、搜尋、更新或交接時，哪些資訊值得優先保留。

它不是固定 Metadata Schema，也不是要求所有文件都填滿欄位。

核心原則：

> 只保存會影響理解、判斷、搜尋、更新、追溯或目前狀態判定的資訊。

## 二、共同描述維度

目前只建立七個最小描述維度：

| 維度 | English | 解決的問題 | 必要性 |
|---|---|---|---|
| 身份 | Identity | 這是什麼資料？ | 通常必要 |
| 內容 | Content | 它實際說了什麼？ | 必要 |
| 適用範圍 | Scope | 在哪裡使用？ | 條件需要時必要 |
| 適用條件 | Conditions | 什麼情況下成立？ | 條件性內容必要 |
| 時間 | Time | 什麼時候成立／發生？ | 具有時間性的內容必要 |
| 狀態 | State | 目前能否直接採用？ | 需要狀態判定時必要 |
| 形成依據 | Basis / Provenance | 為什麼會有這個內容？ | 需要追溯時必要 |

這七項是描述維度，不代表每份文件都要出現七個固定欄位。

## 三、必要與可選

### 幾乎總是需要

- 能辨識內容的名稱或標題。
- 實際內容。
- 足以理解內容用途的上下文。

### 視內容而定

- 適用範圍。
- 適用條件。
- 時間。
- 狀態。
- 來源與證據。
- 版本。
- 關係。

### 不應預先強制

- 固定信心分數。
- 固定品質分數。
- 複雜權重。
- 人工重複輸入的所有時間欄位。
- 可以從 Git、檔案路徑或內容直接推導的資訊。

## 四、資料類型與描述需求不同

不同資料類型的描述重點不同。

| 資料類型 | 優先描述 |
|---|---|
| 知識 | 定義、適用範圍、條件、形成依據、目前狀態 |
| 記憶 | 對象、背景、時間、目前有效性、歷史關係 |
| 目前狀態 | 時間、範圍、目前採用內容、阻塞、下一步 |
| 來源 | 來源身份、位置、時間、版本、取得方式 |
| 證據 | 支持的主張、證據內容、條件、限制 |
| 主張 | 命題內容、狀態、支持／反駁關係 |
| 決策 | 問題、選項、決定、時間、條件、理由 |
| 觀察 | 發生什麼、觀察時間、環境／條件、結果 |

這只是目前的最小工作矩陣，不是最終 Schema。

## 五、可推導資訊優先不重複保存

如果資訊可以可靠地由其他資料推導，原則上不應要求人工重複維護。

例如：

```text
檔案路徑 → 可以推導承載位置
Git commit → 可以追溯一次程式庫變更
文件修改時間 → 可以作為修改訊號
```

但「可以推導」不代表「永遠不用保存」。如果推導成本高、來源可能消失，或未來工作需要穩定引用，才評估是否保存明確副本。

## 六、描述資訊與內容本身分開

Metadata 的目的不是取代內容。

```text
Metadata
↓
幫助定位、理解、判斷與管理

Content
↓
真正需要被理解與使用的內容
```

如果增加 Metadata 後反而需要閱讀更多文件才能理解資料，就代表管理成本可能已超過收益。

## 七、與狀態模型的關係

狀態不能只靠 Metadata 解決。

例如：

```text
文件：建立中
內容：部分已確認
方案：尚未採用
```

因此狀態需要與內容、決策、時間及適用範圍共同判定。

## 八、與版本的關係

版本不是單純的 Metadata 欄位名稱。

至少需要區分：

```text
內容版本
來源版本
方案版本
軟體版本
Git／檔案變更版本
```

它們可能相關，但不能因為都有「版本號」就視為同一件事。

目前只建立這個邊界，不建立完整版本相容性系統。

## 九、目前不建立的機制

本輪不建立：

- 固定 JSON Schema
- 全資料強制欄位
- Metadata 資料庫
- 自動 Metadata 生成器
- 複雜品質分數
- 固定信心分數
- 所有資料共用完全相同的欄位集合

原因是目前尚未有足夠實際案例證明這些機制能降低成本。

## 十、驗證方式

下一階段使用實際資料案例測試：

1. 能否找到需要的資料。
2. 能否判斷資料目前是否有效。
3. 能否理解資料適用條件。
4. 能否追溯重要結論的形成依據。
5. 能否在資料更新後避免新舊內容混淆。
6. 若某項描述資訊缺失，是否真的造成實際問題。

只有實際問題反覆出現，才把對應描述維度升格為更正式的共同規格。
