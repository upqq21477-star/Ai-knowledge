# 工程狀態與交接紀錄時機規則 v1.0

日期：2026-09-17
狀態：【正式規則建立；待自然工作驗證】

## 一、目的

規定 Ai-knowledge 在長期、多輪、多 AI 接手的工程中，何時必須建立工程狀態紀錄、何時必須更新待辦、何時必須更新交接資料，避免重要決策只存在於對話中。

本規則補充「目前狀態、工程狀態快照、待辦、交接資料、方案規劃」之間的操作時機，不取代各文件自身的責任。

## 二、核心原則

任何具有持續工程影響的討論，不應只停留在對話。

當討論形成可執行的結論時，必須把結論轉換成可讀取的工程紀錄。

基本閉環：

```text
討論
↓
形成結論
↓
判斷是否需要方案／結構性規劃
↓
需要 → 先建立方案規劃或更新既有方案規劃
↓
建立目前工程狀態紀錄
↓
排入待辦
↓
更新交接資料
```

若只是一般問答、暫時性討論、尚未形成可執行結論，則不要求建立正式工程狀態紀錄。

## 三、必須建立紀錄的第一類時機：討論結論形成後

符合以下任一條件時，討論結束後必須進行一次工程紀錄：

- 形成新的正式決策。
- 改變既有責任邊界。
- 確認新的系統、方案、資料結構或工程流程需求。
- 確認原方案需要重製、重構、拆分、融合、取代或保留。
- 確認新的禁止事項或操作規則。
- 確認下一階段工程主線。
- 發現會影響後續 AI 接手的重要狀態差異。
- 發現現有文件之間存在需要處理的責任或語義衝突。

### 紀錄順序

若討論涉及新的系統、方案或結構性能力：

```text
討論結論
↓
方案規劃／方案調整
↓
工程狀態紀錄
↓
待辦更新
↓
交接資料更新
```

「先建立方案規劃」是為了避免直接從討論跳到施工。

若只是既有方案內的正常工程工作，不需要重新建立方案，可直接：

```text
討論結論
↓
工程狀態紀錄
↓
待辦更新
↓
交接資料更新
```

## 四、必須建立紀錄的第二類時機：系統建立／更新到驗收前階段

當一個系統完成建立或一次正式更新，且已經進入「只剩整體實際驗收」的階段時，必須立即建立一次工程狀態紀錄並更新交接資料。

判定條件：

```text
系統設計／施工完成
↓
必要接口完成
↓
最小實作驗收完成或已確認進入整體驗收
↓
剩餘主要工作 = 整體實際驗收／實戰驗證
```

此時紀錄內容至少包括：

- 系統名稱與版本。
- 本次建立／更新完成內容。
- 已完成的驗收層級。
- 尚未完成的整體實際驗收。
- 驗收條件與方法。
- 目前依賴與阻塞。
- 下一步整體實際驗收工作。
- 對應方案與工程主線。
- Git commit 或可追溯版本。

此紀錄不得把「施工完成」寫成「系統正式完成」。

## 五、必須更新交接資料的時機

以下任一條件成立時，必須更新目前交接資料：

1. 形成新的工程主線。
2. 方案責任或接口發生實質變化。
3. 建立或完成重要系統到整體實際驗收階段。
4. 完成重要驗收或實戰驗證。
5. 發現會影響新 AI 接手判斷的狀態衝突。
6. 發生重大架構重整、資料格式重製或責任重新分配。
7. 一輪重要工程工作結束，已形成新的穩定基準。

交接資料不是每一條小修改都必須更新；它保存的是對「接手後如何正確繼續工程」有實質影響的資訊。

## 六、目前工程狀態紀錄的最小內容

每次正式狀態紀錄至少包含：

```text
日期
事件／工作名稱
目前狀態
本次結論
已完成
未完成
目前主線
依賴
阻塞／等待條件
禁止事項（若有）
下一步
相關方案／系統／文件
驗證狀態
Git／版本追溯資訊
```

不要求每次建立完整資料庫格式；第一階段使用可讀 Markdown。

## 七、待辦同步規則

凡是狀態紀錄中存在未完成且需要後續人工或 AI 執行的事項，必須同步進入 `待辦清單.md`。

待辦不得只寫「之後處理」，至少要能回答：

```text
做什麼
為什麼
目前狀態
前置條件
下一步
```

已完成事項不得因完成而從歷史中消失；可標記完成並保留必要結果。

## 八、交接更新與狀態快照的關係

```text
工程狀態快照
= 現在工程在哪裡

交接資料
= 為什麼走到這裡、重要決策與接手背景

待辦清單
= 接下來要做什麼

方案規劃
= 要如何組織與驗證一項較完整的工作
```

四者互補，不建立多份互相競爭的「目前工程狀態」來源。

## 九、與既有文件的衝突處理

若 `目前狀態.md`、工程狀態快照、交接資料或待辦內容不一致：

```text
實際 Repository
>
最新可確認工程紀錄
>
最新方案／系統文件
>
目前工程狀態快照
>
交接資料
>
舊目前狀態／舊交接
```

不得直接猜測；必須建立狀態衝突紀錄，確認責任後再處理。

## 十、禁止事項

- 不把重要決策只留在對話。
- 不因討論結束就直接施工而跳過必要方案規劃。
- 不把施工完成寫成整體驗收完成。
- 不建立第三份互相競爭的目前狀態入口。
- 不用交接資料取代工程狀態紀錄。
- 不用待辦清單取代工程狀態紀錄。
- 不因建立新狀態紀錄就直接刪除舊紀錄。
- 不因單次討論就產生不必要的完整 Schema 或管理系統。

## 十一、目前採用的標準紀錄節點

```text
A. 討論形成正式結論
   → 方案規劃（必要時）
   → 狀態紀錄
   → 待辦
   → 交接

B. 系統建立／更新完成，剩整體實際驗收
   → 狀態紀錄
   → 待辦
   → 交接

C. 整體實際驗收完成／形成新基準
   → 驗收紀錄
   → 狀態紀錄
   → 待辦更新
   → 交接更新
```

## 十二、目前狀態

本規則 v1.0 已建立。

目前先以 Markdown 實際運作；待自然工作驗證後，再決定是否需要進一步系統化。
