# 共同資料契約原則

狀態：**【初版建立；待三方案實際建立後驗證】**

## 一、目的

三個方案會共同使用知識、記憶、狀態、來源、證據、版本與關係等資料。

如果每個方案自行定義同一資料，長期容易出現：

```text
同名不同義
同義不同名
格式不相容
狀態判定不同
版本無法對接
```

因此先建立「共同語義契約」，但不提前建立完整技術 Schema。

## 二、契約的最低內容

共同資料契約至少回答：

1. 這個資料類型是什麼？
2. 什麼情況可以建立？
3. 什麼情況不能當成該類型？
4. 哪些資訊是必要的？
5. 哪些資訊只有特定情況才需要？
6. 哪些其他資料可以引用或關聯？
7. 如何判斷目前是否仍適用？

## 三、共同契約與實作分離

```text
共同語義契約
↓
方案使用
↓
實際需求
↓
必要時建立格式／欄位／工具
```

共同契約不等於：

- 資料庫 Schema
- JSON Schema
- Metadata 平台
- 知識圖譜
- API 規格全集

這些都是後續可能的實作，不應在需求尚未證明前固定。

## 四、方案可以擴充，但不得改變共同核心語義

例如共同定義「知識」後，某方案可以增加自己的使用資訊：

```text
共同部分：知識的基本語義
方案 A：研究用途
方案 B：AI 上下文用途
方案 C：演化判斷用途
```

但方案不得自行把「知識」重新定義成完全不同的東西。

若確實需要不同語義，應建立新的資料類型或提出共同定義修正，而不是偷偷改義。

## 五、最小必要原則

共同契約只固定跨方案真的需要一致的內容。

判斷順序：

```text
兩個以上方案是否需要理解同一概念？
↓
是
↓
是否需要一致語義才能互通？
↓
是
↓
建立共同契約
```

若只有單一方案使用，優先由該方案自行管理，不擴大成全域規則。

## 六、變更原則

共同契約的變更需要檢查受影響方案。

```text
提出變更
↓
確認語義是否改變
↓
分析依賴方案
↓
確認相容性
↓
必要時建立新版本
↓
驗證
```

共同契約不能因單一方案方便就直接修改。

## 七、與治理的邊界

共同資料契約提供共同語義。

治理負責制定與維護共同規則。

方案負責在規則內使用資料。

演化負責處理資料變更與相容性。

```text
共同契約 → 定義共同語義
治理 → 管理共同規則
方案 → 使用共同資料
演化 → 處理變更
驗證 → 確認結果
```

## 八、目前不建立的內容

在三方案尚未完整建立與驗證前，不固定：

- 完整欄位清單
- 全域 Metadata Schema
- 全域 API Schema
- 完整資料庫結構
- 強制所有資料使用同一檔案格式
- 自動資料轉換規則
- 自動相容性判定

## 九、成立條件

本文件目前是共同語義原則，不代表三方案已經完成資料契約整合。

正式契約需要等三方案實際建立後，從真實交互資料中確認哪些內容確實需要跨方案一致。
