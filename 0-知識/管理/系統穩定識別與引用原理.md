# 系統穩定識別與引用原理

日期：2026-09-17
狀態：【候選知識；已完成外部初步比對；待實際案例驗證】

## 一、核心原理

系統名稱、文件路徑與系統身份不是同一件事。

```text
System ID
= 穩定身份

系統名稱
= 人類可讀名稱

文件位置
= 目前定位資訊
```

名稱與位置可以變更，但跨文件關係不應因此失效。

## 二、為什麼不能只用名稱

可能出現：

- 改名。
- 同名系統。
- 版本變更。
- 系統升格。
- 系統整合。
- 歷史檔案與現行檔案並存。

因此正式關聯使用 System ID。

## 三、為什麼不能只用路徑

路徑會因：

- 重新分類。
- 資料夾整理。
- 方案歸屬調整。
- 文件版本化。
- 廢棄／恢復。

而改變。

因此路徑只能作為 locator，不應作為身份本身。

## 四、外部比對

Backstage Software Catalog 的 entity reference 採用穩定的 kind、namespace、name 組合來識別實體，並將 reference 作為跨 entity 關聯方式。citeturn0search1

Backstage 的 catalog entity 同時區分 metadata、status、owner、system 等不同資料責任，顯示「身份」與「狀態／關係 metadata」可以分離。citeturn0search3

本專案因此採更簡化的：

```text
System ID
→ 名稱／位置／狀態／方案／知識／功能
```

## 五、最小資料模型

```text
System ID：SYS-XXX
名稱：……
位置：……
狀態：……
方案：……
```

其他資料依實際需要增加。

## 六、更新規則

系統改名：更新名稱，不改 System ID。

系統移動：更新位置，不改 System ID。

系統改方案歸屬：更新方案關係，不改 System ID。

系統廢棄：保留 System ID 與歷史關係，但狀態改為廢棄。

只有真正代表「不同系統身份」時才建立新的 System ID。

## 七、與觸發管理的關係

```text
Trigger ID
→ System ID

System ID
→ System Catalog
```

這讓觸發條件不必跟著系統文件路徑變更而大量修改。

## 八、目前結論

System ID 是本方案中最值得固定的基礎資料。

但目前仍為候選知識，需透過實際系統移動、改名、方案歸屬變更等案例驗證其維護成本與必要性。
