# 觸發條件管理原理

日期：2026-09-17
狀態：【候選知識；已完成外部初步比對；待實際案例驗證】

## 一、核心定義

觸發條件管理（Trigger Registry）是將「事件／情境」與「可能需要啟動的系統」建立可搜尋關係的管理能力。

它的核心工作是：

```text
輸入事件／情境
→ 條件匹配
→ 找到目標 System ID
→ 轉交後續路由
```

它不是完整的事件處理器，也不是目標系統的執行引擎。

## 二、觸發資料的最低結構

```text
Trigger ID
觸發條件
目標 System ID
狀態
粗略分類
```

名稱、路徑等資訊由 System Catalog 管理；Trigger Registry 不應自己複製完整系統身份資料。

## 三、外部成熟做法比對

Amazon EventBridge 使用 rule 定義事件 pattern，事件符合 pattern 後交給指定 target；事件可以匹配多個 rules。citeturn1search2turn1search11

Azure Event Grid 也將 event type、subject、資料欄位與 operators 作為事件篩選條件，再把符合條件的事件送往 endpoint。citeturn1search0turn1search5

這些成熟做法支持「條件匹配與目標路由」可以獨立成一層，但本專案只需要其中最小的 metadata／matching 能力，不需要直接複製完整事件平台。

## 四、觸發條件應該精確

外部事件系統特別重視 pattern 的精確性。AWS EventBridge 明確提醒過寬或不精確的規則可能造成重複觸發甚至無限迴圈。citeturn1search9

因此本專案的觸發條件至少應包含：

- 事件／情境類型。
- 必要條件。
- 可辨識的上下文。
- 目標 System ID。

不能只寫模糊的「遇到問題就觸發」。

## 五、多重匹配

成熟事件系統允許一個事件匹配多條規則，因此本專案不能假設「一事件永遠只對應一系統」。citeturn1search11

第一版處理：

```text
0 個
→ 無已知能力

1 個
→ 正常轉交

多個
→ 保留所有候選
→ 標記歧義
→ 不自動猜測
→ 交給統御／問題解決流程
```

未經實際案例證明前，不建立複雜分數、優先級或最佳匹配演算法。

## 六、觸發條件生命週期

觸發條件至少應有：

```text
候選
→ 啟用
→ 暫停
→ 廢棄
```

目標系統廢棄、改變責任或觸發情境不再存在時，對應觸發條件必須重新檢查。

## 七、觸發條件與目標系統分離

```text
Trigger Registry
Trigger ID → System ID

System Catalog
System ID → 名稱／位置／狀態／方案／知識
```

這可以避免系統改名或移動時，需要大量修改所有觸發規則。

## 八、禁止事項

第一版禁止：

- 在 Trigger Registry 保存完整系統執行流程。
- 在 Trigger Registry 決定整個方案。
- 用模糊條件大量建立例外。
- 因為多重匹配就自動選一個而不留下歧義。
- 讓 Trigger Registry 直接取代問題解決系統。
- 預先建立複雜事件匯流排。

## 九、目前結論

觸發條件獨立管理具有明確價值：

1. 系統本身不必攜帶大量觸發索引。
2. 所有觸發條件可以集中檢查重複、失效與覆蓋情況。
3. 系統管理統御只需要接收穩定 System ID，再判定方案歸屬。
4. 可以把「找到誰」與「怎麼處理」分開。

但目前仍是候選知識，必須透過實際 Ai-knowledge 工作事件驗證搜尋成本、誤觸發、多重匹配與維護成本。
