# 資料關係類型與語義字典

狀態：**【初版建立；待實際案例驗證】**

## 一、目的

本文件先建立跨方案共用的最小關係語義，避免 AI 知識管理方案、資料演化方案與治理層對同一個「關係」使用不同含義。

目前只固定語義，不建立關係資料庫或完整知識圖譜。

## 二、六類最小關係

目前採用六個最小關係類別：

### 1. 定義（Defines）

A 定義 B 所使用的概念、邊界或語義。

例：

```text
知識定義與邊界
→ 定義 → 知識
```

### 2. 依賴（Depends On）

A 的成立、判斷或使用，需要 B 作為前提或必要能力。

例：

```text
知識更新系統
→ 依賴 → 資料狀態模型
```

「依賴」表示缺少 B 會使 A 無法正常成立或使用，不只是「A 會參考 B」。

### 3. 約束（Constrains）

A 限制 B 可以如何成立、使用或變更。

例：

```text
共同資料規則
→ 約束 → AI 知識管理方案
```

約束不等於執行；治理規則可以約束方案，但不代表治理方案親自執行方案功能。

### 4. 實作（Implements）

A 的原理、規則或方法被 B 落實為可操作的流程、系統、文件結構或工具能力。

例：

```text
搜尋原理
→ 實作 → 資料探索與搜尋系統
```

### 5. 互補（Complements）

A 與 B 沒有上下級或必要依賴，但共同處理一個問題時可以互相補足。

例：

```text
資料探索
↔ 互補 ↔ 搜尋原理
```

### 6. 產生／回饋（Produces / Feeds Back）

實際使用、驗證或事件產生新觀察、新證據、經驗或修正需求，再反向影響既有知識與系統。

例：

```text
實際驗證
→ 產生 → 新觀察
新觀察
→ 回饋 → 知識更新
```

## 三、不能混用的關係

### 使用 ≠ 依賴

A 使用 B，只代表工作過程中會用到 B。

只有在缺少 B 時 A 的功能、判斷或成立條件受到實質影響，才稱為依賴。

### 支撐 ≠ 依賴

某份知識可以支撐某系統的設計，但系統不一定在邏輯上必須依賴該單一知識。

### 來源 ≠ 支持

「來源」描述內容從哪裡來；「支持」描述某內容是否為主張提供證據。

### 比較 ≠ 衝突

兩份資料有差異，不代表兩者不能同時成立。

## 四、演化關係

資料演化需要比六個最小關係更具體的關係，但目前先保留為候選語義：

| 關係 | 定義 |
|---|---|
| 補充 | 新內容增加原內容缺少的資訊，但不否定原內容。 |
| 修正 | 新內容修正原內容中的錯誤或不完整部分。 |
| 部分取代 | 新內容只取代原內容的一部分。 |
| 完全取代 | 新內容成為目前採用內容，原內容不再作為目前規則。 |
| 融合 | 多個內容經整理後形成新的內容。 |
| 拆分 | 原本一個內容被拆成多個較明確的內容。 |
| 廢棄 | 明確判定內容不應再被使用。 |
| 前身／歷史 | 描述演化前後的歷史脈絡。 |

這些關係目前是語義候選，不代表立即建立全部實作。

## 五、來源／證據關係

研究與知識形成至少需要能表達：

```text
來源
↓
內容
↓
主張
↓
支持／反駁／限制
↓
知識結論
```

因此後續若實際案例需要，可能增加：

- 來源（Source Of）
- 支持（Supports）
- 反駁（Refutes）
- 限制（Limits）
- 修正（Corrects）

但目前不預先建立複雜證據圖。

## 六、時間、範圍與條件

關係不能只寫「A 與 B 有關」。

對會隨時間或情境改變的關係，至少需要能表達：

```text
關係類型
＋
來源
＋
目標
＋
時間
＋
適用範圍
＋
適用條件
＋
目前狀態
```

不代表每一條關係都必須人工填滿所有資訊。

## 七、反向關係

許多關係可以由正向關係推導。

例如：

```text
A 依賴 B
```

可以理解為：

```text
B 被 A 依賴
```

因此目前不要求人工同時保存正向與反向兩份關係，以避免資料重複與不一致。

## 八、分類不等於關係

「搜尋」「AI」「已確認」等可以是分類或管理屬性，不應因為能描述資料，就全部建立成關係。

例如：

```text
文件 A
分類：搜尋
```

不代表：

```text
文件 A
→ 關係 → 搜尋
```

分類回答「它屬於哪一類」；關係回答「它與另一個對象如何發生語義連結」。

## 九、目前不建立的機制

本輪不建立：

- 關係資料庫
- 知識圖譜
- 固定 Relationship Schema
- 所有候選關係全部強制使用
- 自動推導所有反向關係
- 複雜關係權重／分數

原因是目前尚未完成實際案例驗證。

## 十、驗證方式

下一階段使用實際文件與方案測試：

1. 是否真的需要顯式關係才能理解資料。
2. 六個最小關係是否足夠描述主要依賴。
3. 哪些演化關係會反覆出現。
4. 哪些關係其實可以由文件內容直接理解，不需要額外保存。
5. 哪些關係缺失會造成搜尋、更新或交接錯誤。

只有反覆出現且有實際成本的關係，才升格為正式共同關係規格。
