# 觸發條件管理與系統路由原理

版本：v1.0
狀態：【已建立；待本專案實測】
日期：2026-09-17

## 一、核心問題

系統越多之後，AI 若必須逐一閱讀所有系統文件才能知道「目前事件可能叫醒哪個能力」，搜尋成本與誤觸發風險會增加。

因此將「觸發條件」從系統目錄中獨立，建立 Trigger Registry／Trigger Management System。

## 二、核心分工

### 觸發條件管理系統

回答：

> 發生什麼事情時，應該找到哪個系統？

只保存第一層觸發索引：

`觸發條件 → System ID → 系統位置`

### 系統管理統御分支

回答：

> 找到這個系統後，它屬於哪個方案、目前狀態如何、應由誰承接？

### 方案／系統

負責第二層精確判斷與實際執行。

## 三、兩層觸發模型

```text
事件／需求
↓
第一層粗觸發
Trigger Registry
↓
找到候選 System ID
↓
系統管理統御分支
↓
確認所屬方案、狀態與路由
↓
方案／系統
↓
第二層精確啟動條件
↓
執行
```

Trigger Registry 不保存系統內部完整決策邏輯。

## 四、最小資料模型

| 欄位 | 用途 |
|---|---|
| Trigger ID | 唯一識別 |
| 觸發條件 | 可被觀察／描述的事件條件 |
| 目標 System ID | 被喚起的系統 |
| 系統位置 | 便於直接定位 |
| 狀態 | 啟用／停用／待驗證 |
| 優先級 | 多重命中時的初步排序，必要時才使用 |
| 備註／來源 | 說明條件依據 |

## 五、不可放入 Trigger Registry 的內容

- 完整系統執行流程
- 複雜業務規則
- 詳細問題解決邏輯
- 所有前置條件的完整判斷樹
- 系統執行結果

否則 Trigger Registry 會演變成第二套巨型控制系統。

## 六、多重命中處理

同一事件可以命中多個 Trigger，但不得默認全部執行。

初步處理順序：

1. 找出候選 Trigger。
2. 去除停用或無效目標。
3. 依明確度／優先級排序。
4. 將候選交給系統管理統御分支確認。
5. 由方案／系統進行最終判斷。

如果兩個 Trigger 都可能成立但責任不清，不自行猜測，標記為路由衝突並進入問題解決流程。

## 七、外部方法比對

Kubernetes Controller 採控制迴圈觀察狀態並針對特定面向採取行動，且由多個 Controller 分工，而非由單一巨型 Controller 處理全部問題。這支持「觸發索引、系統目錄、實際系統邏輯」分離。

Backstage Catalog 則將實體、關係與 metadata 做成可搜尋的中央目錄，實際內容仍保留於來源文件。其 AI Resource Catalog 也採「Catalog 保存引用，實際 skill/rule 內容仍在來源檔案」的方式，與本專案「觸發索引只保存指向，不保存完整邏輯」相符。

## 八、採用結論

採用：

> 獨立 Trigger Registry，負責第一層能力發現與路由候選；系統本身保留完整啟動邏輯。

不採用：

> 把所有系統邏輯集中到觸發條件管理系統。
