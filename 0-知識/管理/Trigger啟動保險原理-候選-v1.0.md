# Trigger 啟動保險原理－候選 v1.0

日期：2026-09-18

性質：P0.5-04 Distillation / Reconstruction Candidate

## 一、定位

Trigger 在本專案中的角色，是正常工作流程之外的第二層啟動保險（Activation Safety Layer）。

正常流程仍是第一啟動路徑。

Trigger 的任務不是接管工作，也不是建立中央事件處理中心，而是在可能漏啟動時提供低侵入的補充檢查。

核心原則：

> Trigger 命中 ≠ 立即啟動；先確認目標系統目前狀態，再決定是否補充啟動。

## 二、最小安全流程

事件
→ Trigger 匹配
→ System ID
→ 查詢最小必要處理狀態
→ 未處理且條件仍成立：補充啟動
→ 已處理／啟動中／執行中：不重啟
→ 狀態不明：不擴大啟動，轉交判定

## 三、冪等性（Idempotency）

重複事件、重試或重複觀察不能因此建立相同的重複工作。

最小識別資訊：

- Event ID
- Trigger ID
- System ID
- 處理／啟動狀態

這些資訊用於判斷同一事件是否已建立相同處理。

## 四、最小處理狀態

啟動保險只需要知道是否可以補啟動，不接管目標系統完整執行狀態。

最小狀態：

- 未啟動
- 啟動中
- 執行中
- 已處理／已完成
- 暫停／失效
- 狀態不明

完整工作狀態仍由目標系統負責。

## 五、主要失效模式

### Duplicate Activation
正常流程已啟動後，保險層再次建立相同工作。

### Re-entrancy
同一事件重複觀察、重試或重新傳遞造成第二份相同工作。

### Trigger Loop
系統執行造成的狀態變更再次命中同一處理鏈並形成循環。

### Multiple Match
同一事件命中多個候選系統，不代表所有系統都應啟動。

### Unknown State
無法確認目標是否已處理時，不得直接擴大啟動。

## 六、Architecture Boundary

Trigger Registry：

- 不保存目標系統完整業務邏輯。
- 不取代方案。
- 不取代問題解決系統。
- 不自行決定多重候選中的最佳方案。
- 不成為中央執行引擎。
- 不要求中央 Event Bus 作為前提。
- 不要求複雜 Rules Engine 作為第一版前提。
- 不以系統名稱或文件路徑取代 System ID。

Trigger 命中本身也不得成為第一啟動來源。

## 七、自然工作案例驗證

正式採用前至少確認：

1. 正常流程已啟動時，保險層不二次啟動。
2. 正常流程漏啟動時，保險層能補充啟動。
3. 同一事件重複出現時，不產生重複處理。
4. 多重匹配時，不會無條件大量啟動。
5. 執行後狀態變更不形成無限循環。
6. Event ID 重複時具備可判定的冪等行為。
7. Trigger 暫停／失效時不應被當成有效補啟動來源。
8. 不依賴大型事件總線或複雜規則引擎即可完成最小安全流程。

沒有實際工作案例的啟動與結果，不得判定此能力已驗證成立。
