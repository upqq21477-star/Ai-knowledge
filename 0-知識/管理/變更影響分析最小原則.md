# 變更影響分析最小原則

版本：v1.0  
狀態：【候選知識；已完成外部方法比對；待實際案例驗證】  
日期：2026-09-17

## 一、目的

定義「影響分析（Impact Analysis）」的最小共同語義，回答：

```text
如果 A 改變，哪些東西可能需要重新檢查、遷移、驗證或停止使用？
```

影響分析不是預測所有未來問題，也不是自動決定是否應該修改。

## 二、最小影響鏈

影響分析首先依共同 Identity 與 Relationship 找候選影響範圍：

```text
變更對象
  ↓
直接關係
  ↓
直接使用者／依賴者
  ↓
下游關係
  ↓
版本／相容性
  ↓
驗證案例／實際工作
```

再依變更種類、關係強度、生命週期、版本與實際使用狀態縮小範圍。

## 三、影響分析至少檢查的維度

```text
1. Identity      是否其實是另一個對象
2. Relationship  有哪些直接／間接關係
3. Dependency    哪些能力依賴它
4. Usage         哪些實際工作使用它
5. Version       哪些版本會受影響
6. Compatibility 舊用法能否繼續
7. Validation    哪些驗證案例需要重跑
8. Lifecycle     是否造成 deprecated / retired / invalid
9. Data          是否需要遷移或重算
10. History      是否需要保留舊版本與變更依據
```

不是每次變更都需要完整檢查十項；檢查深度應依變更風險與影響範圍決定。

## 四、直接影響與間接影響

應明確區分：

```text
Direct Impact
= 變更對象的直接使用者／關係者

Indirect Impact
= 透過關係或依賴鏈傳遞的下游對象
```

不能因為圖上存在很長的關係鏈，就把所有節點都標成「必然受影響」。

影響分析輸出的語義應至少區分：

```text
Candidate Impact = 可能受影響
Confirmed Impact = 已由實際關係／測試確認
No Impact        = 已檢查且沒有需要處理的影響
Unknown          = 缺少必要資料，無法判定
```

## 五、影響分析不是變更裁決

```text
Impact Analysis
      ↓
提供影響範圍與風險資訊
      ↓
Change Decision
      ↓
決定是否修改、如何修改
```

影響分析本身不能推出「一定要改」或「一定不能改」。

同樣地：

```text
影響大 ≠ 不准修改
影響小 ≠ 可以直接修改
```

最終決策仍需考慮目標、證據、驗收方法、成本、可逆性與實際工作需求。

## 六、外部方法比對

Backstage Software Catalog 以實體與 relations 建立 catalog graph，並將 dependency mapping、ownership、inventory、lifecycle 等資訊作為可查詢結構。這支持「影響分析需要可追蹤的關係與依賴資訊」的方向。

Backstage 也把 System 作為較高層抽象，使消費者可以忽略部分實作細節；這可降低不必要的跨層耦合，但不能直接推導出本專案必須採用相同粒度。

Microsoft 與 AWS 的應用現代化方法也把 dependency、complexity、requirements、cost、risk 等資訊納入重構／遷移決策，而不是只看單一檔案是否需要修改。

參考：
- Backstage System Model： https://backstage.io/docs/features/software-catalog/system-model/
- Backstage Creating the Catalog Graph： https://backstage.io/docs/features/software-catalog/creating-the-catalog-graph/
- Microsoft Azure Architecture Center - Modernization： https://learn.microsoft.com/azure/architecture/guide/
- AWS Prescriptive Guidance - Migration strategies： https://docs.aws.amazon.com/prescriptive-guidance/latest/migration-retiring-refactoring-replatforming/strategies.html

## 七、與現有四方案的責任關係

影響分析是共同能力，不應在四個方案各自重新建立一套。

```text
整體資料治理
→ 提供 Identity / Relationship / State / Version 等共同資料

AI知識管理
→ 使用影響資訊協助任務搜尋、Context 組裝與結果判斷

資料迭代演化
→ 在一般變更前後使用 Impact Analysis

能力蒸餾與系統重構
→ 在 Merge / Split / Replace / Rebuild / Retire 前使用 Impact Analysis
```

共同能力提供分析基礎，但不承擔四方案各自的變更策略與執行責任。

## 八、最小驗證方法

第一次實際驗證不建立完整 Impact Engine。

選擇一個真實變更案件，手工依序記錄：

```text
變更對象
→ Identity
→ 直接 Relationship
→ 實際 Usage
→ 依賴／下游
→ 版本／相容性
→ 驗證案例
→ 最終實際影響
```

比較「預測影響」與「實際影響」。

若人工流程已能穩定產生價值，再決定哪些步驟值得系統化。

## 九、禁止事項

- 不因存在 Relationship 就宣稱所有下游都必然受影響。
- 不把 Impact Analysis 直接當成 Change Decision。
- 不建立四套互相重複的影響分析器。
- 不在沒有真實案例前建立大型全域 Impact Graph Engine。
- 不把文件引用數量直接當成實際依賴強度。
- 不因影響範圍大就自動否決變更。
