# 變更影響分析共同語義基準-候選-v1.0

## 狀態

【DISTILL-CANDIDATE／MEDIUM；待實際案例驗證】

## 1. 定義

Impact Analysis（影響分析）是：當某一對象發生變更時，依目前可證明的 Identity、Relationship、Dependency、Usage、Version、Compatibility 等資訊，找出需要重新檢查、驗證、遷移、停止使用或進一步確認的候選影響範圍。

Impact Analysis 不等於 Change Decision（變更裁決），也不保證能找全所有影響。

## 2. 最小影響鏈

```
變更對象
→ 直接關係
→ 直接使用者／依賴者
→ 下游關係
→ 版本／相容性
→ 驗證案例／實際工作
```

分析深度依變更風險、關係強度與實際使用狀態調整，不要求每次完整檢查所有維度。

## 3. 最小共同檢查維度

可依案件選擇檢查：

- Identity
- Relationship
- Dependency
- Usage
- Version
- Compatibility
- Validation
- Lifecycle
- Data
- History

「至少檢查的共同維度」不代表每次都必須完整執行十項。

## 4. 影響結果

至少應能區分下列語義：

- Candidate Impact：目前證據支持可能受影響。
- Confirmed Impact：已由實際關係／測試等證據確認。
- No Impact：已檢查且目前沒有需要處理的影響。
- Unknown：缺少必要資料，暫時無法判定。

存在關係不等於必然需要更新；主題相似也不等於依賴。

## 5. Impact Analysis 與 Change Decision

```
Impact Analysis
↓
提供影響範圍與風險資訊
↓
Change Decision
↓
決定是否修改、如何修改
```

影響大不等於禁止修改；影響小也不等於可以直接修改。最終裁決仍需考慮目標、證據、驗收方法、成本、可逆性與實際工作需求。

## 6. 最小操作模型

第一版以人工案例驗證為主：

```
Change Set
→ Identity
→ Direct Relationship
→ Usage
→ Dependency / Downstream
→ Version / Compatibility
→ Validation
→ Actual Impact
```

可以使用 Markdown 表格、清單或簡單文字圖，不以建立大型 Impact Graph Engine、Graph DB 或自動化分析器為前提。

## 7. 邊界

- 不因 Relationship 存在就宣稱所有下游必然受影響。
- 不把 Impact Analysis 當成 Change Decision。
- 不以文件引用數量直接代表依賴強度。
- 不宣稱影響分析能保證找全所有影響。
- 不把影響項目數量直接等同變更成本。
- 未有真實案例前，不建立大型全域 Impact Engine。
- 不因共同能力存在，就在四個方案各自重建一套影響分析器。

## 8. 與專案應用層的關係

本候選只保留共同語義。具體的 Change Set 建立格式、逐層追蹤流程、停止條件、影響範圍輸出表等，可由更新流程文件作為操作層實作，不在此文件重複完整流程。

## 9. 驗證

候選尚未升級 CURRENT。需要真實變更案件驗證：

1. 能否穩定找出合理的第一層影響。
2. 能否合理停止傳播。
3. 能否區分已確認、可能、無影響與未知。
4. 預測影響與實際影響是否可比較。
5. 人工流程是否已產生足夠價值。
6. 是否存在值得系統化的重複步驟。

## 10. 來源定位

本候選由以下兩份原始文件進行語義蒸餾：

- `0-知識/管理/變更影響分析最小原則.md`

原始文件不因本候選建立而刪除、合併或改寫。
