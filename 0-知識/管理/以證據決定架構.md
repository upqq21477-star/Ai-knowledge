# 以證據決定架構

> 一句話：架構機制應由實際痛點觸發，而不是因為未來可能需要就預先建立。

## 核心原理
架構本身有維護成本。對單人工作室而言，尚未發生的問題不應自動轉化成新的資料結構、流程或工具。

```text
實際使用 → 發現問題 → 確認成本 → 建立最小解法 → 實際驗證 → 必要時擴張
```

## 適用情境
知識庫、工具鏈與個人工程系統設計，以及面對大型架構提案時。

## 不適用情境
已經發生明確且持續的維護瓶頸時，不應以避免過度工程化為理由拒絕必要改進。

## 實務方法／注意事項
任何新機制先問：現在真的有問題嗎？是否造成可觀察成本？最小解法能否解決？使用後是否仍有問題？

## 我的補充
真正有效的架構應該從使用中長出來。第一批知識同時也是觀察知識大小、邊界、重複、搜尋與維護成本的實驗資料。
