# 系統目錄與系統登錄原理

版本：v1.0
狀態：【已建立；待本專案實測】
日期：2026-09-17

## 一、目的

建立一個薄型 System Catalog／System Registry，集中保存所有正式系統的最小識別與定位資訊，讓 AI 能快速回答：

- 這個系統是什麼？
- 系統文件在哪裡？
- 屬於哪個方案？
- 目前狀態如何？
- 與哪些知識書有關？
- 它負責什麼？

目錄不是系統內容本身，也不是所有動態狀態的唯一真實來源。

## 二、核心原則

1. 一個系統只有一個正式 System ID。
2. 系統目錄保存索引與高階 metadata，不複製完整系統內容。
3. 系統詳細規則仍以系統文件為準。
4. 所屬方案是關係資料，不把方案內容複製進系統目錄。
5. 知識書以引用關係保存，不把知識全文塞入目錄。
6. 狀態只保存足以協助路由與判斷的高階狀態；詳細施工狀態留在原系統／工作紀錄。
7. 分類先粗後細，以搜尋與實際維護成本決定是否拆分。
8. 不因資料量增加就自動建立多份互相獨立的系統表；優先維持單一身份、不同視圖。

## 三、建議最小欄位

| 欄位 | 用途 |
|---|---|
| System ID | 唯一識別 |
| 系統名稱 | 人類可讀名稱 |
| 系統位置 | 系統文件路徑 |
| 系統分類 | 粗略分類與篩選 |
| 所屬方案 | 方案關係 |
| 關聯知識書 | 知識依賴／來源關係 |
| 功能摘要 | 一句話說明用途 |
| 狀態 | 候選／建立中／驗證中／穩定／停用等 |
| 版本 | 系統版本 |

## 四、資料邊界

系統目錄管理「找得到、看得懂、知道歸屬」；不管理：

- 完整觸發邏輯
- 完整執行流程
- 詳細問題判斷
- 詳細驗證證據
- 所有動態執行資料

## 五、外部方法比對

Backstage Software Catalog 採中央 Catalog 保存系統／元件的 metadata、owner、lifecycle、關係與搜尋資訊，實際內容仍由來源文件維護；其官方文件也明確區分 Catalog 與即時動態真實來源。這與本知識庫的「薄型目錄」設計一致。

ServiceNow CMDB 則以中央資料庫管理 configuration items 與關係，並強調資料治理、資料品質與責任歸屬。可借鑑其「單一識別、關係、資料治理」概念，但本專案不直接複製企業級 CMDB 複雜度。

Kubernetes Controller 採多個控制器各自處理特定狀態面向，而不是建立一個巨型控制器。此原則支持本專案將「系統目錄」與「觸發條件」分開。

## 六、可採用結論

本專案採用：

> 單一 System ID + 薄型中央目錄 + 關係引用 + 粗分類 + 搜尋／篩選 + 詳細內容回原系統文件。

不採用：

> 巨型中央資料庫、完整系統內容複製、預先建立多層資料分片、把所有動態狀態集中到目錄。
