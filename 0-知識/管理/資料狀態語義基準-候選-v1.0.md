# 資料狀態語義基準－候選 v1.0

日期：2026-09-18
狀態：【候選；尚未升格 CURRENT】
性質：P0.5-04 Distillation / Reconstruction Candidate

## 一、定位

本文件是 P0.5-04 對既有「資料狀態與生命週期」相關知識進行語義蒸餾後形成的候選基準。

它不是新的 State Engine、State Database 或複雜狀態機，也不是以單一 State Enum 取代原有不同語義。

本文件的目的，是讓後續工作能先分清楚「不同種類的狀態」，避免把文件進度、內容確認、採用、決策、有效性與歷史關係混成一個欄位。

## 二、核心原則

1. 內容 ≠ 狀態。
2. State ≠ Version ≠ Time。
3. 最新 ≠ 有效。
4. 文件完成 ≠ 內容已確認。
5. 已確認 ≠ 已採用。
6. 歷史 ≠ 目前規則。
7. 已失效 ≠ 單純歷史。
8. 已否決 ≠ 沒有追溯價值。
9. AI 輸出預設是候選內容，不直接成為 CURRENT。
10. 狀態變更需要可追溯的依據。
11. 「CURRENT」是綜合工作判定，不是單一內容狀態。

## 三、語義維度

### 1. Asset / Governance State

描述此資產在知識庫治理中的處置狀態。

目前工程治理使用的資產 State 與本文件的內容語義必須分開理解。不得因兩者都使用「State」一詞而直接合併。

### 2. Document / Work State

描述文件或工作本身的進度，例如建立中、待審查等。

文件正在建立，不代表其中所有內容都未確認。

### 3. Content Confirmation State

描述內容是否已經過足夠比較、驗證或明確決策。

「待確認」與「已確認」屬此維度。

### 4. Adoption State

描述內容是否已被實際採用。

已確認不必然等於已採用；已採用也不代表永遠正確。

### 5. Decision State

描述方案或主張的決策結果，例如已採用、已否決等。

已否決資料仍可保留其決策與追溯價值。

### 6. Applicability / Validity

描述內容在特定時間、範圍與條件下是否仍適用。

「已失效」與「歷史」不得直接視為同義。

### 7. Historical Relation

描述內容與過去決策、版本或演化的關係。

歷史資料可以不是目前依據，但仍可能用於理解演變、追溯原因與避免重複研究。

## 四、目前判定原則

判斷「目前可用內容」時，至少同時考慮：

- 語義內容
- 狀態
- 版本
- 時間
- 適用範圍
- 適用條件
- 採用／否決決策
- 驗證證據

不能只依檔案修改時間或單一狀態名稱判定。

## 五、AI 輸出

AI 新輸出預設為候選內容。

最小流程：

AI 輸出
→ 待確認
→ 比較／查證／驗證
→ 確認
→ 決定是否採用

AI 第二次輸出較新，不代表它自動取代第一次內容，也不代表它自動成為 CURRENT。

## 六、禁止的簡化

本基準不授權：

- 建立單一混合 State Enum
- 建立複雜 State Engine
- 建立 State Database
- 依「最新文件」自動判定真實性
- 依文件完成狀態推定內容確認
- 把 Historical、Deprecated、Invalid 視為同義
- 因資料重複就直接刪除歷史與否決證據

## 七、自然案例驗證要求

正式採用前至少檢查：

1. 文件建立中，但其中部分內容已確認。
2. 內容已確認，但尚未採用。
3. 已採用內容被新內容取代。
4. 歷史資料仍有追溯價值。
5. 已否決資料被搜尋時能辨識其決策結果。
6. 已失效資料不被誤判為目前有效內容。
7. AI 新輸出不會直接成為 CURRENT。
