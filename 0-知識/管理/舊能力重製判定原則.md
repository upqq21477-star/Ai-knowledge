# 舊能力重製判定原則

## 狀態

【候選知識；已完成外部方法比對；待實際重製案例驗證】

## 一、目的

本知識用於整體系統大重製、架構整併、能力去重與舊系統退役時，判斷既有能力應：

- 保留（Keep）
- 融合（Merge / Consolidate）
- 重構（Refactor）
- 取代（Replace）
- 重建（Rebuild）
- 暫留（Retain）
- 淘汰（Retire）

核心原則不是判斷「舊文件好不好」，而是判斷：

> 舊能力是否仍然有價值、是否與其他能力重疊、是否仍符合新架構責任、以及移除或重製它的風險與成本。

## 二、最重要的判斷順序

不得看到舊系統名稱就直接決定保留、融合或淘汰。

固定採用：

```text
舊能力盤點
↓
確認實際能力
↓
確認實際使用／依賴
↓
確認價值
↓
確認證據與驗證狀態
↓
確認與其他能力的重疊程度
↓
確認新架構責任邊界
↓
確認資料與關係是否可遷移
↓
分析風險／成本／收益
↓
比較候選處置方式
↓
決定 Keep / Merge / Refactor / Replace / Rebuild / Retain / Retire
↓
建立遷移與驗證條件
```

禁止：

```text
舊 → 新名稱
舊 → 新系統
舊系統過時 → 淘汰
兩個功能相似 → 融合
新架構比較漂亮 → 取代
```

以上都不足以形成正式判定。

## 三、先判斷「能力」，再判斷「文件」

重製單位優先是 Capability（能力），不是 Markdown 文件、目錄或系統名稱。

同一能力可能散落在：

- 知識書
- 系統
- 方案
- 模板
- 管理文件
- 實測紀錄
- 多個舊系統

因此必須先回答：

```text
這些文件實際提供了什麼能力？
誰使用？
在什麼條件下觸發？
輸入什麼？
輸出什麼？
依賴什麼？
是否真的被使用？
```

文件數量不能代表能力數量。

## 四、七種處置方式

### 1. 保留 Keep

適用於：

- 能力仍有明確用途。
- 與新架構責任相容。
- 沒有必要改變核心行為。
- 已有實際驗證或可靠證據。
- 重製成本高於可獲得收益，或改動沒有明顯價值。

保留不代表永遠不改；只是目前沒有足夠理由重製。

### 2. 融合 Merge / Consolidate

適用於：

- 多個舊能力處理相同或高度相鄰問題。
- 各自保留會造成資料、責任、狀態或觸發重複。
- 融合後可以形成更清楚的單一能力邊界。
- 被融合能力中的有效部分可以被完整保留。

融合不是把兩份文件複製到一起，而是：

```text
A能力 + B能力
↓
拆出各自有效部分
↓
去除重複
↓
重新定義責任
↓
建立共同能力
↓
驗證新能力覆蓋舊需求
```

### 3. 重構 Refactor

適用於：

- 核心能力仍正確。
- 現有實作方式造成維護、效率或邊界問題。
- 外部行為可大致保持不變。
- 沒有必要重新定義能力本身。

重構的對象主要是實作／結構，不是能力目的。

### 4. 取代 Replace

適用於：

- 舊能力仍有需求，但現有實作無法合理滿足新需求。
- 新能力可以覆蓋舊能力的必要行為。
- 新能力的資料、責任與驗證條件已明確。
- 已證明取代後不會遺失必要能力。

必須先證明「需求仍存在」，才能判斷為取代，而不是直接淘汰。

### 5. 重建 Rebuild / Re-architect

適用於：

- 核心能力仍重要。
- 舊架構邊界已無法合理維持。
- 需要重新定義資料、責任、關係或執行方式。
- 簡單重構不足以解決問題。

重建不是因為「新架構比較漂亮」，而是舊結構已無法合理支撐目標。

### 6. 暫留 Retain

適用於：

- 能力仍有價值。
- 目前沒有足夠條件安全重製。
- 依賴、風險、成本或驗證不足使立即遷移不合理。

暫留必須有理由，不得變成「沒人處理所以永遠留下」。

### 7. 淘汰 Retire

適用於：

- 需求已消失；或
- 能力完全由其他已驗證能力覆蓋；或
- 能力造成的成本／複雜度已沒有合理價值；且
- 沒有未被識別的重要依賴。

淘汰前必須確認：

```text
誰還在使用？
誰還依賴？
是否有隱性觸發？
是否保存重要歷史證據？
是否仍是唯一資料來源？
是否有替代能力？
替代能力是否已驗證？
```

## 五、融合與取代的核心差異

### 融合

```text
A + B
↓
共同能力 C
```

A、B 都有可保留價值，只是邊界重疊或過度拆分。

### 取代

```text
A
↓
B
```

A 的需求仍存在，但 B 成為新的承載方式。

### 淘汰

```text
A
↓
無
```

A 的需求不存在，或已完全由其他已驗證能力承接。

三者不可混用。

## 六、判斷「是否重疊」

不能只比較名稱。

至少比較：

| 維度 | 要回答的問題 |
|---|---|
| 目的 | 是否解決同一問題？ |
| 輸入 | 是否接收相同／高度重疊資料？ |
| 輸出 | 是否產生相同或可替代結果？ |
| 觸發 | 是否由相同事件或條件啟動？ |
| 責任 | 是否對同一責任負責？ |
| 狀態 | 是否維護同一狀態？ |
| 資料 | 是否保存或修改相同資料？ |
| 使用者 | 是否由同一類工作使用？ |
| 依賴 | 是否依賴相同上游／下游？ |
| 驗證 | 是否用相同方式判定成功？ |

只有名稱相似，不得判定重疊。

## 七、重疊程度

採用四級判定：

### R0 無實質重疊

能力目的、責任與輸出不同。

→ 分開保留。

### R1 局部重疊

有部分相同功能，但各自仍有不可替代部分。

→ 保留並重新劃界，必要時建立關係。

### R2 高度重疊

主要目的與責任高度相同，但實作、資料或歷史來源不同。

→ 優先評估融合或取代。

### R3 完全重疊

同一能力、同一責任、同一主要輸出，沒有必要同時存在。

→ 優先選擇一個正式承載能力，其餘融合、取代或淘汰。

## 八、判斷「保留」不能只看能力是否有用

還要看四個條件：

```text
價值
×
必要性
×
架構相容性
×
證據可靠度
```

例如：

- 有用但與新架構責任衝突 → 不能直接保留原結構。
- 有用但尚未驗證 → 可以保留為候選能力，但不能宣稱已成立。
- 已驗證但已完全被新能力覆蓋 → 不代表必須繼續保留實作。
- 很少使用但屬唯一關鍵能力 → 不能因使用頻率低而淘汰。

## 九、證據優先級

重製判定優先使用：

```text
實際運作結果
>
可重現實測
>
明確使用紀錄
>
已驗證方案／系統規則
>
外部成熟方法
>
設計文件
>
單次討論／構想
>
名稱與直覺
```

外部方法可以支持架構選擇，但不能取代本 Repository 的實際驗證。

## 十、效率判斷

「新架構比較好」不能只看執行速度。

至少比較：

- AI 理解成本
- 搜尋成本
- 更新成本
- 維護成本
- 資料重複成本
- 狀態同步成本
- 責任衝突成本
- 觸發錯誤成本
- 驗證成本
- 遷移成本
- 失敗回復成本
- 未來擴充成本

因此：

> 效率是總體生命週期成本，而不是單次操作速度。

## 十一、保留／融合／取代／淘汰的判定問題

每個舊能力至少回答：

```text
1. 這個能力實際解決什麼問題？
2. 目前還需要這個問題的解決能力嗎？
3. 目前真的有人／系統／方案使用嗎？
4. 有哪些證據證明它有效？
5. 是否與其他能力重疊？
6. 重疊是 R0 / R1 / R2 / R3？
7. 是否存在唯一責任或唯一資料？
8. 新架構是否已有候選承接能力？
9. 候選承接能力是否已驗證？
10. 若融合，哪些部分必須保留？
11. 若取代，舊能力的哪些行為必須保持？
12. 若淘汰，需求由誰承接？
13. 若暫留，阻塞條件是什麼？
14. 遷移失敗時如何回復？
15. 判定所依據的證據在哪裡？
```

## 十二、禁止「先決定，再找理由」

不得採用：

```text
我想重製
↓
找舊能力問題
↓
證明舊能力應淘汰
```

正確方式：

```text
能力事實
↓
證據
↓
需求
↓
重疊
↓
候選方案
↓
成本／風險
↓
比較
↓
判定
```

## 十三、重製映射最低資料格式

每個能力至少保存：

| 欄位 | 內容 |
|---|---|
| Legacy Capability | 舊能力 |
| Source | 舊檔案／系統來源 |
| Actual Function | 實際功能 |
| Usage | 實際使用狀態 |
| Evidence | 證據 |
| Overlap Level | R0–R3 |
| Candidate Capability | 新候選能力 |
| Disposition | Keep / Merge / Refactor / Replace / Rebuild / Retain / Retire |
| Preserve | 必須保留內容 |
| Remove | 可以移除內容 |
| Reason | 判定理由 |
| Risk | 遷移風險 |
| Validation | 驗證要求 |
| Dependencies | 依賴 |
| Migration Condition | 遷移條件 |

## 十四、重製不是一次性判定

一個能力可以經歷：

```text
候選
↓
暫留
↓
實測
↓
融合
↓
驗證
↓
正式採用
↓
舊能力退役
```

因此「重製判定」與「重製完成」必須分開。

只有完成遷移、驗證、依賴切換與舊路徑退役，才能把舊能力正式標記為 Retired。

## 十五、與整體重製的關係

本知識是「舊能力 → 新架構」的判定基礎，不直接負責執行整體重製。

重製流程應由更高層流程／方案決定：

```text
舊能力盤點
↓
本判定原則
↓
重製映射
↓
候選新能力
↓
共同資料契約檢查
↓
架構設計
↓
最小建立
↓
實測
↓
遷移
↓
回寫
↓
舊能力退役判定
```

## 十六、外部方法比對

外部現代化實務普遍不是把整個舊環境套用單一處置方式，而是先盤點、理解依賴與複雜度，再逐項選擇 Retain、Retire、Refactor、Rebuild、Replace 等不同路徑。AWS 的 7R 明確把 Retire、Retain、Rehost、Relocate、Repurchase、Replatform、Refactor/Re-architect 分開；Microsoft 的現代化指南也把 6R 作為依據複雜度、需求、依賴與成本進行選擇的分析框架。citeturn0search1turn0search9turn0search11

能力映射比單純應用程式清單更重要：現代化研究也指出，不能只因某個舊應用看起來重複就淘汰，必須先確認它實際提供哪些能力及下游影響。citeturn0search13

對需要降低一次性大爆炸風險的重製，AWS 與 Microsoft 的 Strangler Fig 模式都採用新舊能力並存、逐步轉移、驗證後退役的思路。citeturn0search19turn0search20

## 十七、本知識目前的限制

目前這套判定原則尚未在 Ai-knowledge 的完整大型重製案例中實際驗證。

因此目前只能稱為：

【候選知識；外部方法已比對；待實際重製驗證】

不可因本文件建立，就把目前重製映射中的所有 Keep / Merge / Replace / Retire 判定視為永久正確。

未來實際重製時，若發現本判定原則造成：

- 不必要融合
- 錯誤淘汰
- 重複能力未被發現
- 遷移成本低估
- 驗證條件不足
- 舊能力隱性依賴遺漏

應回寫本知識，進行迭代。
