# 觸發條件管理與啟動保險原理

日期：2026-09-17
狀態：【候選知識；已完成外部比對；待自然工作案例驗證】

## 一、核心定義

觸發條件管理在本專案中的主要用途，不是建立中央事件處理中心，而是作為「第二層啟動保險（Activation Safety Layer）」。

正常工作流程仍是第一啟動路徑。觸發系統只在可能漏掉應啟動系統時提供補充路徑。

核心原則：

> Trigger 命中 ≠ 立即啟動；先確認目標系統目前是否已處理，再決定是否補充啟動。

## 二、為什麼需要啟動保險

AI 工作流程可能因上下文遺漏、流程轉換、系統索引失效或判斷疏漏而沒有啟動原本應使用的系統。

因此需要一個低侵入的第二層檢查，但此檢查本身不能成為新的主要流程。

## 三、四個核心安全問題

### 1. 二次啟動（Duplicate Activation）

正常流程已啟動目標系統後，保險層再次看到相同事件時，不得再次建立相同處理。

### 2. 重入（Re-entrancy）

同一事件被重複觀察、重試或重新傳遞時，不應因此產生第二份相同工作。

### 3. 循環觸發（Trigger Loop）

系統執行產生的狀態變更，不得無限制重新觸發同一處理鏈。

### 4. 多重匹配（Multiple Match）

多個候選系統不等於多個系統都應啟動。若沒有已驗證的協作規則，應保留歧義而非擴大啟動。

## 四、最小安全判斷

```text
事件
↓
Trigger 匹配
↓
System ID
↓
目前處理狀態
↓
已處理／執行中 → 不重啟
未處理 → 確認條件仍成立 → 補充啟動
不確定 → 不擴大啟動，轉交判定
```

## 五、冪等性（Idempotency）

事件驅動系統通常必須面對重複事件或重試，因此事件處理需要具備冪等性。Microsoft 的事件架構文件明確指出，事件可能以至少一次（at-least-once）方式傳遞，同一事件可能被重複接收，因此消費端需要使用事件識別資訊去重，並使重複處理不產生額外副作用。citeturn1search0turn1search1turn1search2

本專案採最小化做法：

```text
Event ID
Trigger ID
System ID
處理／啟動狀態
```

用於判斷同一事件是否已經建立相同處理。

## 六、狀態不是執行引擎

啟動保險需要知道目標系統是否已經處理，但不應因此接管目標系統完整執行狀態。

因此只保存或查詢最小必要狀態：

```text
未啟動
啟動中
執行中
已處理／已完成
暫停／失效
狀態不明
```

完整工作狀態仍由目標系統負責。

## 八、禁止事項

- 不把 Trigger Registry 變成第一啟動源。
- 不因 Trigger 命中就直接啟動。
- 不因多重匹配就全部啟動。
- 不把完整問題解決邏輯放入 Trigger。
- 不建立中央事件總線作為本系統前提。
- 不建立複雜規則引擎作為第一版前提。
- 不以系統名稱或文件路徑取代 System ID。

## 九、驗證要求

至少透過自然工作案例確認：

1. 正常流程已啟動時，保險層不二次啟動。
2. 正常流程漏啟動時，保險層能補充啟動。
3. 同一事件重複出現時，不產生重複處理。
4. 多重匹配時，不會無條件大量啟動。
5. 執行後的狀態變更不形成無限循環。

沒有實際啟動與結果，不得判定此能力已驗證成立。
