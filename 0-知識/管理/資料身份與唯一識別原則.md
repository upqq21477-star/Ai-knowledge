# 資料身份與唯一識別原則

版本：v1.0
狀態：【候選知識；已完成外部方法比對；待實際案例驗證】

## 一、目的

本知識處理四方案共同的 Identity（身份）問題：

> 如何確認「這是不是同一個對象」，而不把檔名、路徑、名稱或版本誤當成對象本身？

身份是後續 Metadata、Relationship、State、Version、Traceability 的基礎。

## 二、外部方法比較

### Backstage Software Catalog

Backstage 將 Catalog Entity 視為可識別對象，使用 Kind、Namespace、Name 組合形成唯一識別；同時把 Owner、Lifecycle、Relations 等資訊分開處理。官方模型也強調 System 是一組協作 Entity 的抽象層，而不是單純等於某個檔案。這對本專案的重要啟示是：

```text
對象身份
≠
承載檔案
≠
目前狀態
≠
關係
```

來源：Backstage Software Catalog / Entity References / System Model。

### Kubernetes Object Identity

Kubernetes 將 Name、Kind／Resource Type、Namespace 等用於識別對象，同時提供系統產生的 UID，用來區分不同生命週期中曾使用相同名稱的物件。這說明「人類可讀名稱」與「穩定身份」可以是兩個不同概念。

來源：Kubernetes Object Names and IDs、ObjectMeta。

## 三、採用原則

### 1. Identity 是對象，不是位置

不得採用：

```text
檔案路徑 = 身份
檔名 = 身份
Git commit = 身份
目前版本 = 身份
```

檔案路徑是承載位置；Git commit 是變更歷史；版本描述內容演化；Identity 用來回答「是哪一個對象」。

### 2. 人類名稱與穩定識別應分離

建議至少概念上區分：

```text
Stable Identity
＋
Human-readable Name
＋
Type / Kind
```

名稱可以因可讀性、重命名或結構調整而改變；Identity 不應因單純改名就被視為新對象。

但如果實際工作無法證明需要獨立 ID，不能為了形式先建立大量 ID 系統。

### 3. 不同層級的對象必須分開

至少區分：

```text
Knowledge
Memory
Data
System
Solution
Tool / Software
Application
```

「AI知識管理系統」與承載它的 Markdown 文件不是同一個 Identity。

## 四、Identity 與 Version

```text
Identity A
├─ Version 1
├─ Version 2
└─ Version 3
```

版本是同一對象的演化，不應因版本變更就自動建立新的 Identity。

但若一次變更實際產生不同責任、不同對象或不同生命週期，則可能形成新 Identity；這必須由實際語義判定，而不能只看版本號。

## 五、Identity 與 State

```text
Identity A
＋ State：建立中
```

狀態描述目前處境，不改變對象本身。

因此：

```text
建立中 → 已驗證
```

通常是 State 改變，不是 Identity 改變。

## 六、Identity 與 Relationship

關係應引用對象 Identity，而不是依賴目前檔案位置。

例如：

```text
System A
   │ belongsTo
   ↓
Solution B
```

如果 System A 的文件從一個目錄移到另一個目錄，關係本身不應因此失效。

## 七、Alias 與重命名

人類名稱可能出現：

```text
正式名稱
舊名稱
簡稱
別名
歷史名稱
```

Alias 的作用是協助搜尋與追溯，不應創造多個正式 Identity。

因此：

```text
同一 Identity
├─ current name
├─ alias
└─ historical name
```

比「每次改名就建立新對象」更適合需要長期追溯的資料。

## 八、目前不建立的機制

本知識目前不直接建立：

- 全 Repository UUID 平台。
- 自動 ID 生成服務。
- 複雜 Identity Resolver。
- 自動判斷兩份資料是否同一對象的 AI 分類器。
- 強制所有 Markdown 都新增 ID 欄位。

原因是目前需要先用真實案例確認：哪些對象確實需要跨檔案、跨版本、跨目錄保持穩定身份。

## 九、最小判斷問題

遇到身份問題時依序問：

```text
1. 我們要識別的是什麼對象？
2. 名稱是否可能改變？
3. 承載位置是否可能改變？
4. 版本是否會演化？
5. 是否需要跨歷史追溯同一對象？
6. 是否存在同名不同物件？
7. 是否需要其他系統引用它？
8. 不建立穩定 Identity 是否會造成實際錯誤？
```

只有最後一項答案確實為「會」，才提高 Identity 機制的正式程度。

## 十、驗證方式

使用實際 Repository 案例驗證：

1. 系統文件改名後是否仍能辨識同一系統。
2. 文件搬移後關係是否仍能維持。
3. 同名不同對象能否區分。
4. 同一對象跨版本能否追溯。
5. 歷史名稱是否仍能搜尋到目前對象。
6. 不建立額外 ID 時是否真的產生錯誤。

## 十一、核心結論

> Identity 用來穩定識別「對象」，而不是穩定保存「檔案位置」。

> 名稱、路徑、版本、狀態、Git commit 與 Identity 必須保持語義分離；是否需要真正的穩定 ID，應由實際使用與錯誤案例證明，而不是預先建造大型身份系統。
