# 相容性與遷移最小原則

版本：v1.0  
狀態：【候選知識；已完成外部方法比對；待實際案例驗證】  
日期：2026-09-17

## 一、目的

定義資料、知識、系統與方案在變更時的「相容性（Compatibility）」與「遷移（Migration）」最小語義。

本原則不建立獨立遷移系統，也不要求所有變更都採用相同遷移流程。

## 二、核心區分

```text
Change        = 發生了什麼變更
Compatibility = 舊使用方式能否繼續工作
Migration     = 如何把舊資料／舊使用方式轉移到新狀態
Validation    = 如何確認變更與遷移後仍符合預期
```

四者不可互相取代。

## 三、相容性不是單一二元值

至少需要區分：

- 完全相容：既有使用者不需要改動。
- 條件相容：在明確條件下仍可使用。
- 不相容：既有使用方式會失效或語義改變。
- 未知：目前證據不足，不能判定。

必要時應再區分：

```text
資料相容性
介面／格式相容性
語義相容性
行為相容性
流程相容性
```

不能因格式仍能讀取，就直接判定語義與行為也相容。

## 四、遷移不是單純「搬資料」

遷移可能包含：

```text
資料轉換
名稱／身份映射
關係映射
版本轉換
使用方式轉換
相容層
驗證
切換
回復／保留舊版
```

因此 Migration 應以「從舊工作狀態安全進入新工作狀態」理解，而不是只指檔案搬移。

## 五、最小安全變更模式

當變更可能破壞既有使用方式時，優先考慮將變更拆開：

```text
Expand
↓
建立新能力／新格式，同時維持舊使用方式
↓
Migrate
↓
轉換資料與使用者／依賴者
↓
Validate
↓
確認新舊結果符合預期
↓
Contract
↓
在確認無必要依賴後移除舊能力
```

這與業界常見的 Parallel Change / Expand and Contract 模式一致；AWS 的資料庫遷移實務也建議盡可能採用 backward-compatible 變更，必要時將不相容變更拆成多個階段。citeturn0search5turn0search0turn0search1

## 六、不能把相容性當成永久包袱

相容層、雙格式、舊版本並存都有成本。

因此：

```text
建立相容層
↓
標記保留原因
↓
追蹤仍有哪些依賴
↓
遷移完成
↓
重新驗證
↓
判斷是否可以移除
```

不能因為「舊版還能跑」就永久保留。

也不能因為「新格式比較乾淨」就直接刪除舊格式。

## 七、遷移判定至少需要

```text
來源 Identity / Version
目標 Identity / Version
相容性判定
受影響 Relationship
受影響 Dependency
受影響 Usage
轉換方式
保留／並存期限（若有）
驗證方法
失敗後處理
```

若上述資訊不足，只能標記為未知或候選遷移，不應假設遷移安全。

## 八、外部方法比對

AWS Database Migration Service 將 migration、schema conversion、assessment 與 validation 分開，並對異質資料庫轉換明確區分「可自動轉換」與「需要人工處理」的項目。這支持遷移前先評估、再轉換、再驗證，而不是把 migration 視為一次性複製。citeturn0search2turn0search6turn0search8

AWS 的 schema migration 文件也區分 backward-compatible 與 backward-incompatible 變更，並指出不相容變更可拆成多次更新，以降低一次切換的風險。citeturn0search0

## 九、與現有知識的關係

```text
Version
  ↓
Change
  ↓
Impact Analysis
  ↓
Compatibility
  ↓
Migration
  ↓
Validation
  ↓
新狀態／新版本
```

其中：

- Version 說明演化位置。
- Change 說明發生的變更。
- Impact 說明可能受影響的對象。
- Compatibility 判斷舊使用方式是否仍可工作。
- Migration 處理從舊狀態到新狀態的轉換。
- Validation 確認實際結果。

因此本知識不取代既有「版本與演化邊界」「變更影響分析」「實測結果回寫」等知識。

## 十、目前不建立

在實際案例證明之前，不建立：

- 全域 Migration Engine
- 自動 Compatibility Engine
- 強制所有資料使用 Expand / Migrate / Contract
- 全域自動資料轉換器
- 永久雙格式策略
- 自動判定「可以刪除舊版」的規則

## 十一、最小驗證方法

等待正常工作自然產生至少一個真實變更案例，觀察：

1. 是否能辨識舊版與新版身份。
2. 是否能判斷受影響的關係與依賴。
3. 是否能區分格式相容與語義相容。
4. 是否需要舊／新版本並存。
5. 是否能記錄遷移條件與驗證結果。
6. 遷移完成後是否能判斷舊能力可以保留、退役或移除。

若自然工作無法產生足夠證據，不另外製造大型測試工作。

## 十二、禁止事項

- 不把「可以讀」直接等同於「完全相容」。
- 不把 Migration 等同於檔案搬移。
- 不因新版本建立就立即刪除舊版本。
- 不因舊版本仍可運作就永久保留。
- 不在沒有 Impact / Dependency / Usage 證據時判定遷移安全。
- 不因成熟工具存在 migration 能力，就直接建立本專案的 Migration Engine。
