# 變更影響分析與影響範圍

## 狀態
【建立中；已完成外部方法比對；待更新方案實測】

## 一、目的

當一項知識、規則、參數或系統內容發生變更時，判斷這項變更可能影響哪些其他資料、系統、方案與應用，並建立可追蹤的影響範圍。

這裡的「影響」不是只找直接引用，而是沿著已知關係逐層追蹤變更可能傳播的位置。

軟體工程中的 Change Impact Analysis（CIA）也是以變更元素為起點，推導需要注意或維護的影響集合；相關研究指出，依賴分析是常見的影響分析方法，並可用於估算維護工作與測試優先級。citeturn1search0turn0search2turn1search10

## 二、基本模型

```text
變更起點
↓
直接引用／依賴／約束／使用
↓
第一層受影響項目
↓
檢查這些項目的依賴與使用者
↓
第二層受影響項目
↓
……
↓
沒有新的可合理追蹤影響
↓
影響範圍結束
```

可將結果分為：

- 直接影響：直接使用被變更內容。
- 間接影響：透過其他項目傳播。
- 潛在影響：關係不完整，但存在合理風險。
- 無需更新：雖然存在關係，但變更不影響其語義或使用條件。
- 待確認：關係或影響不足以做出確定判斷。

## 三、影響關係

優先追蹤實際存在的關係：

- 定義／引用。
- 依賴。
- 約束。
- 實作。
- 使用。
- 輸入／輸出。
- 上下游關係。
- 方案使用系統。
- 系統使用知識。

不因「主題相近」就視為依賴。

## 四、影響分析流程

### 1. 建立變更集

先記錄：

- 哪些檔案變更。
- 哪些段落、規則、參數或結論變更。
- 舊內容與新內容的差異。
- 變更原因。
- 變更是否改變定義、邊界、條件、輸出或行為。

### 2. 建立第一層影響

調閱直接使用變更內容的：

- 知識。
- 系統。
- 方案。
- 應用資料。

### 3. 逐層擴散

對每個受影響項目再檢查：

> 這個項目是否被其他項目使用、依賴或約束？

如果是，加入下一層影響範圍。

### 4. 每一層重新判斷

不是找到關係就必定標記「需要更新」。必須判斷：

```text
存在關係
↓
變更是否進入該項目的使用範圍？
↓
是否改變該項目的有效條件／輸出／判斷？
↓
是 → 受影響
否 → 保留關係但停止該分支
```

## 五、停止條件

影響分析不能無限擴散。

一個分支在以下情況停止：

- 沒有新的依賴或使用者。
- 新項目只有主題相關，沒有實際關係。
- 變更不會改變該項目的有效條件或輸出。
- 關係已經回到已分析項目。
- 繼續追蹤只會產生大量低可信度的潛在關係。
- 分析成本已經高於預期能降低的錯誤風險，且該分支不是高風險核心路徑。

因此影響範圍不是「所有可能相關資料」，而是「有足夠理由認為需要注意的資料集合」。

## 六、影響範圍圖

最小可用表示法：

```text
[變更]
  │
  ├─→ [直接受影響 A]
  │      ├─→ [A 的使用者 C]
  │      └─→ [A 的約束 D]
  │
  └─→ [直接受影響 B]
         └─→ [B 的使用者 E]
```

不要求建立圖形資料庫。Markdown 表格、清單或簡單文字圖即可支撐第一版。

## 七、輸出

至少產生：

| 項目 | 內容 |
|---|---|
| 變更集 | 本次真正變更的內容 |
| 直接影響 | 第一層受影響項目 |
| 間接影響 | 逐層傳播後的項目 |
| 不受影響 | 已檢查但不需要更新的項目 |
| 待確認 | 關係或影響尚不足以判斷的項目 |
| 影響邊界 | 本次追蹤停止的位置與原因 |
| 更新建議 | 哪些項目需要一起更新 |

## 八、重要限制

CIA 本身可能產生 false positive 與 false negative，因此「影響集合」不是絕對真實集合，而是目前證據下的分析結果。相關實證研究也指出，單純由影響結果直接推導變更成本並不一定準確。citeturn1search2

因此本知識禁止：

- 宣稱影響分析可以保證找全所有影響。
- 把所有依賴都直接判成必須更新。
- 把影響項目數量直接當成成本。
- 用單一固定倍率估算所有變更。

## 九、與既有知識的關係

與 `0-知識/更新/知識更新原理.md` 的差異：

- `知識更新原理`：判斷知識何時、如何更新。
- 本文件：判斷一個變更會沿哪些關係影響其他內容。

與 `0-知識/系統/系統依賴.md` 的差異：

- `系統依賴`：描述依賴關係本身。
- 本文件：把變更放進依賴關係中，分析影響如何傳播。

本文件因此不直接取代既有知識。
