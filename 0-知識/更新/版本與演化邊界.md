# 版本與演化邊界

狀態：**【初版建立；待實際案例驗證】**

## 一、目的

版本管理用來區分不同時間或不同內容狀態，演化管理則處理內容如何從舊版本變成新版本。

本文件只建立共同語義邊界，不建立完整版本控制平台或自動遷移系統。

## 二、版本的基本概念

版本代表同一個可識別物件在不同時間或變更階段的不同內容狀態。

```text
物件 A
├─ v1.0
├─ v1.1
└─ v2.0
```

版本號本身不是品質分數，也不代表新版本一定比舊版本正確。

## 三、版本與狀態不同

```text
版本 ≠ 狀態
```

例如：

```text
v2.0 + 待驗證
v2.0 + 已驗證
v1.0 + 歷史
```

同一版本可以具有不同管理狀態，不能用版本號取代狀態。

## 四、版本與時間不同

```text
版本 ≠ 建立時間
版本 ≠ 有效時間
```

一份資料可以今天建立，但描述過去發生的事件。

一個版本也可能在建立後才於某個日期開始正式採用。

因此版本、建立時間與有效時間應保持語義分離。

## 五、最小演化類型

目前只保留實際最常見且容易辨識的演化類型：

```text
新增
修改
補充
部分取代
完全取代
融合
拆分
廢棄
```

這些描述「內容如何變化」，不是固定的工作流程。

## 六、演化關係

```text
舊物件
↓ 演化
新物件
```

必要時進一步說明：

```text
v1.0
↓ 修改
v1.1
```

或：

```text
知識 A + 知識 B
↓ 融合
知識 C
```

或：

```text
知識 A
↓ 拆分
知識 B
知識 C
```

融合與拆分尤其需要保存來源與結果之間的追溯關係。

## 七、版本相容性

版本相容性只有在實際使用不同版本時才需要判斷。

至少可能出現：

```text
完全相容
部分相容
不相容
尚未確認
```

不能因版本號連續就推定相容。

## 八、語義變更與文字修改

不是所有文字修改都需要升級主要版本。

基本原則：

```text
文字／格式小修
→ 不一定改變核心語義

核心定義／判斷／適用條件改變
→ 可能構成重大版本變更
```

目前採語義優先原則：版本判定應根據內容是否產生實質影響，而不是單純依修改行數判定。

## 九、演化與治理的邊界

演化處理「內容怎麼變」。

治理處理「什麼規則下可以變、如何共同管理」。

```text
治理
↓ 定義共同規則
演化
↓ 執行內容變更
驗證
↓ 確認變更結果
```

三者不能混成單一能力。

## 十、禁止的做法

目前不得因為建立版本語義就直接建立：

- 自動版本遷移平台
- 完整相容性矩陣
- 自動融合系統
- 自動拆分系統
- 自動刪除舊版本
- 複雜版本評分模型

這些能力必須等實際案例證明需求後再建立。

## 十一、後續驗證

待實際案例驗證：

- 一次小幅知識修正
- 一次核心定義變更
- 一次方案版本變更
- 一次文件格式變更
- 一次引用位置變更
- 一次舊資料被新資料部分取代
- 一次歷史資料廢棄
