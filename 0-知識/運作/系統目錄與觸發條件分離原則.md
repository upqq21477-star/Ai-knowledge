# 系統目錄與觸發條件分離原則

版本：v1.0
日期：2026-09-17
狀態：正式建立；待實際運作驗證

## 一、目的

將「系統是什麼、在哪裡、屬於什麼」與「什麼事件會叫醒哪個系統」分離，避免系統目錄逐漸承擔完整觸發邏輯，也避免系統之間各自保存重複的觸發索引。

## 二、核心原則

1. 系統目錄負責系統身分、位置、狀態、所屬方案與高階關係。
2. 觸發條件管理系統負責事件到系統的第一級匹配與路由索引。
3. 觸發條件管理系統不保存目標系統的完整業務邏輯。
4. 方案負責多系統之間的工作協作與處理方法。
5. 系統負責自身的詳細判斷與實際執行邏輯。
6. 一個系統只能有一個正式 System ID，不因不同分類或方案視圖而複製系統身分。
7. 目錄是索引，不取代系統本體；動態詳細狀態仍以實際系統或其正式來源為準。

## 三、最小責任邊界

```text
觸發條件管理系統
= 發生什麼事，可能叫醒誰？

系統管理統御分支
= 這個系統是誰、在哪裡、屬於哪個方案？

方案
= 這些系統如何協作處理？

系統
= 實際如何判斷與執行？
```

## 四、禁止事項

- 不把完整系統流程搬進觸發條件管理系統。
- 不在不同目錄建立同一系統的多份正式身分資料。
- 不因系統數量增加就預先建立大量分層管理系統。
- 不把目錄中的摘要狀態當成所有動態資料的唯一真實來源。
- 不讓觸發系統直接取代方案的工作協調責任。

## 五、觸發條件的兩級結構

### 第一級：觸發索引

由觸發條件管理系統保存，用於快速找到候選系統。

例如：

```text
發現流程異常 → 問題解決系統
需要重新驗證 → 驗證相關系統
發現模型重大變更 → 更新相關系統
```

### 第二級：精確啟動判斷

由被找到的系統或方案自行判定。

例如問題解決系統仍需自行確認：問題是否成立、是否值得處理、是否已有既有能力、是否需要外部研究等。

## 六、資料規模原則

初期採「全域索引＋粗略分類＋搜尋／篩選」。

不以資料筆數作為拆分依據。只有當搜尋成本、更新成本、責任邊界、資料同步或維護複雜度實際出現分化時，才建立分支索引或其他分片結構。

分片後仍維持唯一 System ID；分類檔案應是索引或視圖，不應形成互相競爭的正式資料來源。

## 七、驗證要求

本原則成立後，至少需要透過實際工作驗證：

1. 觸發事件能找到正確候選系統。
2. 多個系統同時符合時不會產生無法處理的衝突。
3. 系統搬移、改名、升級或廢棄後，觸發索引仍能維持一致。
4. 觸發索引不會逐漸膨脹成第二套完整控制邏輯。
5. AI 能透過系統目錄快速取得系統與方案關係。
