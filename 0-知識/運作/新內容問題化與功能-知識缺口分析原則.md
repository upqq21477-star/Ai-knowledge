# 新內容問題化與功能－知識缺口分析原則

## 狀態
【已建立；已完成外部方法研究與比較；待實際任務驗證】

## 一、目的

本知識處理一個容易被忽略、但會直接造成「跳過研究而直接建立方案／系統」的上游問題：

> 新內容、新要求、新發現、新限制或新主張進入工程後，不能直接被當成方案或系統需求；必須先判定它是否構成工程問題，列出問題所需的完整功能，再逐項確認這些功能需要哪些知識，以及既有知識是否足以支撐。

本原則位於「問題理解」與「方案／系統建立」之間，並且在正式建立前強制形成一個可追溯的：

```text
新內容
→ 問題識別
→ 問題拆解
→ 完整功能盤點
→ 功能 → 知識需求映射
→ 既有知識書盤點
→ 知識缺口分類
→ 外部研究／比較
→ 知識建立或更新
→ 系統能力重新盤點
→ 判斷是否需要新系統／修改既有系統
→ 方案規劃
→ 正式建立流程
```

## 二、核心定義

### 1. 新內容不是問題

新內容可能是：

- 問題
- 需求
- 限制
- 新資訊
- 證據
- 假設
- 使用者建議
- 候選解法
- 架構構想
- 回饋
- 失敗案例

因此不能看到「使用者提出一個架構」就直接進入建立。

### 2. 問題不是方案

問題回答「什麼需要被解決或理解」。

方案回答「多個系統如何為固定目的組合」。

在問題尚未完成拆解、功能尚未完整盤點、知識尚未確認前，不得把候選解法直接升格成方案。

### 3. 功能不是系統

功能盤點回答「這個問題完整處理需要哪些能力」。

只有在功能、知識、既有能力與邊界都確認後，才判斷哪些功能需要系統承擔。

## 三、功能盤點原則

功能盤點不是列出使用者腦中想到的功能，而是從問題的完整生命週期反推能力需求。

至少檢查：

| 功能類別 | 要回答的問題 |
|---|---|
| 輸入接收 | 新內容從哪裡進入？ |
| 問題識別 | 哪些新內容真正構成問題、需求或工程變更？ |
| 問題理解 | 真正要解決、判斷或查明的是什麼？ |
| 問題拆解 | 是否包含多個不同子問題？ |
| 功能盤點 | 解決完整問題需要哪些功能？ |
| 知識需求 | 每項功能依賴哪些原理、規則、方法或證據？ |
| 既有知識盤點 | 哪些知識書已經存在？ |
| 知識狀態判定 | 知識是完整、不完整、缺失、過時還是互相矛盾？ |
| 外部研究 | 缺口需要查哪些外部方法、標準、案例？ |
| 比較 | 不同方法、工具、產品、案例各自怎麼處理？ |
| 知識形成 | 研究結果哪些可蒸餾成可重複使用的知識？ |
| 能力盤點 | 現有系統已經能做什麼？ |
| 缺口判定 | 哪些能力仍沒有承擔者？ |
| 系統判定 | 是否真的需要建立或修改系統？ |
| 方案判定 | 是否需要多系統組合成方案？ |
| 施工入口 | 若需要建立，下一步如何進入正式建立流程？ |
| 驗證 | 如何證明知識、系統與方案實際有效？ |

## 四、功能 → 知識需求映射

每項重要功能都必須先問：

```text
功能是什麼？
↓
完成此功能需要知道什麼？
↓
這些內容屬於可重複原理、方法、規則、分類、證據還是一次性資料？
↓
既有知識書是否已經提供？
```

不能只做「功能 → 系統」映射，否則容易直接跳過知識層。

## 五、既有知識書盤點

知識盤點必須以實際檔案內容為準，不以「資料夾存在」、「以前討論過」或「已有相關方案」視為知識已建立。

對每項知識需求至少判定五種狀態：

| 狀態 | 定義 |
|---|---|
| 已有 | 已有正式知識，內容足以支撐目前功能。 |
| 不完整 | 有相關知識，但缺少目前功能所需的重要部分。 |
| 缺失 | 找不到可直接支撐該功能的正式知識。 |
| 過時 | 曾可使用，但適用條件、外部環境或工程決策已改變。 |
| 矛盾 | 現有知識之間存在未解決的衝突。 |

「已有相關文件」不能直接等於「已有足夠知識」。

## 六、外部研究觸發

只有完成知識盤點後，才能精確知道搜尋缺口。

外部研究至少分三層：

1. 外部方法／原理研究：確認領域如何理解問題。
2. 工具／產品／開源專案比較：確認實際系統如何承擔能力。
3. 標準／案例／實務流程比較：確認成熟工程環境如何處理相同或相近問題。

研究結果不能直接變成系統規格；必須先判斷哪些內容具有可重複性，才能形成知識。

## 七、本次實際問題的功能－知識盤點結果

本次問題為：

> AI 面對新內容時，沒有先把新內容視為待分析問題，也沒有執行「完整功能盤點 → 功能所需知識 → 既有知識書檢查 → 缺口 → 外部研究／比較 → 知識建立」，而直接進入方案建立。

### 既有知識已覆蓋的部分

- `0-知識/搜尋/問題理解與研究問題定義.md`：已處理問題理解、研究問題形成、範圍與條件。
- `0-知識/搜尋/資訊需求建立.md`：已處理從研究問題建立資訊需求。
- `0-知識/搜尋/查詢策略建立.md`：已處理資訊需求到查詢策略。
- `0-知識/搜尋/搜尋拆分.md`：已處理複合搜尋問題拆分。
- `0-知識/比較/知識比較原理.md`：已有知識比較基礎。
- `0-知識/運作/小系統建立原則.md`：已有問題／需求 → 現有能力 → 外部搜尋 → 比較 → 知識書 → 最小規格 → 實測的建立原則。
- `0-知識/系統/系統定義與邊界.md`：已有系統成立與邊界判斷原則。
- `0-知識/運作/系統建立流程失效原因與防止提前建系統.md`：已有防止提前建立系統的失效分析。

### 本次確認的核心缺口

既有知識分別處理了問題理解、搜尋、比較、知識形成與系統建立，但缺少一個明確的上游整合原則，強制要求：

```text
完整功能盤點
→ 每項功能的知識需求
→ 逐項檢查既有知識書
→ 判定已有／不完整／缺失／過時／矛盾
→ 形成知識缺口清單
→ 研究缺口
```

這正是本知識書新增的能力邊界。

## 八、外部方法比較後的設計判斷

### AWS Architecture Decision Records（ADR）

AWS 將重大架構決策要求放入具有狀態與生命週期的決策記錄，至少記錄背景、決策與後果；若決策改變，建立新的記錄並取代舊決策。這證明「重要決策必須留下可追溯理由」，但 ADR 主要處理架構決策，不負責本系統的完整「功能 → 知識」盤點。citeturn0search0turn0search6

### Microsoft Azure Well-Architected ADR

Microsoft 要求 ADR 記錄問題背景、考慮過的選項、決策、取捨、狀態與理由，並將 ADR 視為系統如何形成目前結構的累積記錄。這與本系統的決策追溯一致，但仍沒有取代前置的功能－知識缺口盤點。citeturn0search5turn0search9

### Atlassian Product Discovery / PRD

Atlassian 的產品發現流程先處理問題、價值、可用性、可行性與策略，再進入交付；PRD 則要求目的、功能、行為、假設、問題、問題外範圍與待研究問題保持可追蹤。這支持「先問題、再需求／功能、再研究與交付」的方向。citeturn1search0turn1search6

### IEEE Software Requirements

IEEE 將軟體需求工程定義為識別、文件化與管理系統必須滿足的條件與能力，並把需求工程視為後續設計、實作與驗證的基礎。這支持「功能／能力必須在建立前被識別」，但本專案進一步增加了「功能 → 知識需求 → 知識書盤點」這一層。citeturn1search12

## 九、與既有知識的關係

本知識不是取代：

- 問題理解
- 資訊需求建立
- 查詢策略
- 搜尋拆分
- 知識比較
- 小系統建立原則
- 系統定義與邊界
- 問題解決與新系統建立流程

而是把它們串成建立前的必要依賴鏈。

因此：

```text
問題理解
→ 功能盤點
→ 知識需求
→ 知識盤點
→ 缺口研究
→ 知識形成
→ 系統能力盤點
→ 系統／方案判定
```

## 十、建立前禁止事項

在以下任一項未完成時，不得把候選架構直接視為正式方案或系統：

- 問題尚未明確。
- 完整功能尚未盤點。
- 功能所需知識尚未映射。
- 既有知識書尚未實際檢查。
- 知識缺口尚未分類。
- 必要外部研究尚未完成。
- 外部方法／工具／案例尚未完成必要比較。
- 研究結果尚未形成可重用知識。
- 既有系統能力尚未重新盤點。
- 尚未證明需要新的系統或方案。

## 十一、與方案建立流程的接口

本知識完成後，正式方案流程才允許進入：

```text
方案建立規劃
→ 【規劃完成／未建立／未完善】
→ 正確成立方案與系統方案 Preflight
→ 完整功能／能力／外部研究／比較／反方案
→ Gate LOCK / ALLOW
→ 正式建立
```

也就是：

> 「建立規劃」不是跳過問題與知識研究的捷徑；它只是研究與判定完成後，正式施工前的管理階段。

## 十二、驗證狀態

目前知識內容已完成：

- 既有知識書盤點。
- 功能需求拆解。
- 功能 → 知識需求映射。
- 缺口分類。
- 外部方法研究。
- 外部工具／產品／實務方法比較。
- 與現有知識邊界確認。

尚未完成：

- 在下一個自然方案建立案例中完整執行一次。
- 驗證是否能實際阻止 AI 跳過「功能 → 知識書」階段。
- 驗證新增的研究成本是否低於直接建立後返工的成本。

因此目前狀態是「知識已建立、能力尚待實戰驗證」，不可寫成「流程已驗證」。

## 十三、最小執行檢查

每次新內容可能導致方案／系統變更時，至少完成：

```text
[ ] 新內容分類
[ ] 問題識別
[ ] 問題拆解
[ ] 完整功能盤點
[ ] 功能 → 知識需求
[ ] 實際檢查既有知識書
[ ] 缺口分類
[ ] 必要外部研究
[ ] 工具／方法／案例比較
[ ] 建立／更新知識書
[ ] 重新盤點既有系統能力
[ ] 判斷是否需要新系統／修改既有系統
[ ] 再進入方案規劃
```

## 十四、核心原則

> 不因為「想到一個方案」就開始建立；先確認它解決什麼問題。
>
> 不因為「列出功能」就開始建立；先確認每項功能需要什麼知識。
>
> 不因為「已有相關文件」就認定知識存在；必須實際檢查知識書內容與適用範圍。
>
> 不因為「外部已有做法」就直接複製；必須比較、分析限制與適用條件。
>
> 不因為「知識書已建立」就認定系統成立；必須重新盤點既有能力並證明新增系統具有必要性。
