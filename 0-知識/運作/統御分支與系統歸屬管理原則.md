# 統御分支與系統歸屬管理原則

日期：2026-09-17  
狀態：【候選知識；已完成外部方法比對；待實際施工驗證】

## 一、核心原則

統御分支需要知道目前有哪些系統、系統目前屬於哪個方案，以及哪些小系統尚未有方案歸屬。

這個資訊首先是「狀態索引」，不是另一套功能定義，也不是重新管理每個系統的內部流程。

核心資料：

```text
系統 ID
系統名稱
方案歸屬
目前狀態
極短功能說明
是否為小系統
觸發管理者
```

## 二、方案歸屬

### 已有方案歸屬

系統已被某一方案正式納入時：

```text
方案
└─ 系統
   └─ 功能簡述
```

統御分支只保留其狀態與功能索引，不再管理該系統的觸發條件。

### 尚無方案歸屬的小系統

```text
統御分支
└─ 未歸屬小系統
   ├─ 功能簡述
   ├─ 觸發條件
   └─ 目前狀態
```

這些觸發條件暫由統御分支管理，讓小系統不會因沒有正式方案歸屬而失去實際觸發入口。

## 三、觸發權歸屬原則

同一個觸發責任在同一時間應有單一主要管理者。

```text
未歸屬小系統
→ 統御分支管理觸發

已納入方案的小系統
→ 所屬方案管理觸發
```

統御分支可以知道該系統存在，但不應同時繼續管理已移交給方案的觸發條件。

## 四、移交條件

當未歸屬小系統後來被納入某一方案時，檢查：

1. 新方案是否正式承擔該系統功能。
2. 新方案是否已建立該系統在方案中的系統歸類。
3. 新方案已有的觸發條件是否與原統御觸發條件重疊或完全涵蓋。
4. 新方案是否具備實際執行與驗證該觸發的能力。

若以上條件成立：

```text
統御分支的未歸屬小系統
        ↓
移入方案的系統歸類
        ↓
統御分支只保留功能／狀態索引
        ↓
觸發條件管理權移交方案
```

若只有部分重疊，不能提前移交。應保留統御觸發管理，直到方案能力能完整覆蓋原觸發需求；必要時拆分觸發條件後再移交。

## 五、禁止重複管理

不得形成：

```text
方案管理一次觸發
+
統御分支又管理一次相同觸發
```

這會造成雙重觸發、責任不清與狀態不一致。

## 六、與小系統列表的關係

小系統列表是基礎索引。統御分支使用它辨識：

- 哪些小系統存在。
- 哪些尚未歸屬方案。
- 哪些仍待驗證。
- 哪些有自然觸發條件。
- 哪些可能需要整合到方案。

因此小系統列表不是另一套統御方案，而是統御分支的重要輸入。

## 八、邊界

本知識不規定：

- 每個系統必須屬於正式方案。
- 統御分支可以接管所有系統內部功能。
- 統御分支可以取代方案。
- 方案與系統的實際責任必須由本原則直接裁決。

它只處理「系統目前在哪裡、誰負責其觸發」的最小歸屬問題。
