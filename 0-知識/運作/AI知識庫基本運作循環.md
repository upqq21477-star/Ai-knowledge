# AI知識庫基本運作循環

## 定位
【新建立；運作知識候選；待系統實測】

本知識描述 Ai-knowledge 最小可運作循環，不是完整的知識書分類規格，也不取代各正式系統文件。

## 核心結論

一個 AI 知識庫不能只有「儲存知識」。它至少需要一個持續循環：

```text
目前狀態
↓
目標／工作
↓
執行
↓
預期狀態 vs 實際狀態
↓
正常 → 記錄 → 繼續
異常 → 警報 → 問題分析 → 嚴重程度 → 影響分析 → 處理建議
↓
必要時進入問題解決
↓
解法實測
↓
結果驗證
↓
更新狀態／決策／知識
↓
重新開始循環
```

## 為什麼需要這個循環

如果只有知識與方案文件，AI 仍可能出現以下情況：

- 知道很多，但不知道現在應該做什麼。
- 發現異常，但沒有明確回報。
- 發現問題，但沒有判斷問題大小。
- 問題會影響後續工作，卻仍照原計畫繼續。
- 找到解法後，沒有重新驗證系統狀態。
- 大量研究資料存在，但沒有轉化為可重用知識。

因此「可運作」本身也是知識庫工程的基本要求。

## 異常處理的最低要求

異常至少要回答五件事：

1. 發生什麼問題？
2. 為什麼判斷它是問題？
3. 嚴重程度是多少？
4. 對目前與後續工作的影響是什麼？
5. 現在應該怎麼處理？

最小回報：

```text
【異常】
問題：____

【分析】
____

【嚴重程度】
L0 / L1 / L2 / L3

【影響】
____

【建議】
繼續／修正後繼續／暫停／進入問題解決
```

L2 以上不能只顯示一般提示；如果後續計畫受到實質影響，應明確提出先處理的建議。L3 若破壞施工 Gate 或資料／狀態可信度，應明確指出阻斷性。

外部事件管理實務也採用「偵測 → 分流（triage）→ 嚴重程度 → 影響評估 → 回應／升級 → 解決 → 驗證」的結構；嚴重程度會決定回應層級，而不是單純作為標籤。citeturn0search0turn0search2

## 與知識的關係

一次工作產生的所有資訊不能都叫 Knowledge：

```text
Observation
→ 實際發生的結果

Evidence / Source
→ 結果的依據

Claim
→ 根據證據可以提出的主張

Decision
→ 本次採取的決定

Current State
→ 現在系統的狀態

Knowledge
→ 經驗證、可重用、條件清楚的內容
```

因此「知識產出」不是把每次對話全部存起來，而是從工作循環中篩選可重用內容。

## 重要邊界

```text
警報 ≠ 問題解決
問題解決 ≠ 狀態恢復
狀態恢復 ≠ 知識產生
研究資料 ≠ 知識
文件存在 ≠ 系統成立
系統建立 ≠ 系統驗證
```

## 適用範圍

目前適用於 Ai-knowledge 自身的施工、驗證、研究與架構演化。

後續若經實測證明此循環具有穩定、跨系統、可重用的能力，再提升為正式 Knowledge Book / Knowledge Unit 規格中的核心運作知識。

## 驗證要求

至少以以下案例驗證：

- 正常施工。
- 小型異常。
- 影響後續規劃的異常。
- 破壞 Gate 的阻斷異常。
- 問題解決後恢復。
- 無歷史記憶 AI 重新執行。

目前不得因本文件建立而宣稱以上能力全部成立。
