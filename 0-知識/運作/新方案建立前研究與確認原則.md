# 新方案建立前研究與確認原則

日期：2026-09-17
狀態：【候選知識；已建立；待實際新方案案例驗證】

## 一、核心原則

新方案的「提出」不等於「確認建立」。

任何新的方案構想，在正式建立方案、知識書或其核心系統前，必須先完成問題分析、既有能力盤點、外部研究、同類產品／工具／方法比較、優缺點與漏洞分析，經過必要的討論與修正後，才進入方案確認與建立階段。

## 二、方案狀態

```text
方案構想
→ 候選方案
→ 研究中
→ 討論／修正中
→ 待確認
→ 已確認
→ 建立中
→ 實測
→ 運作／持續改善
```

只有「已確認」才能進入正式建立。

## 三、建立前必要工作

1. 確認要解決的問題與目的。
2. 盤點現有知識、系統、方案與可重用能力。
3. 搜尋外部成熟方法、工具、產品、案例與相關標準。
4. 比較外部做法與本專案需求。
5. 分析候選架構的優點、缺點、限制與成本。
6. 主動尋找架構漏洞、責任重疊、重複能力與可能失效情境。
7. 判斷是否真的需要新增方案，而不是現有方案／系統即可處理。
8. 與使用者討論候選架構。
9. 依討論結果修正並在必要時再次研究、比較與攻擊檢查。
10. 明確確認方案邊界、系統邊界、責任與觸發歸屬。
11. 完成方案確認後，才建立正式方案。

## 四、外部研究最低要求

外部研究不是為了證明候選方案正確，而是用來降低盲點。

至少應尋找與問題本質相近的成熟做法，不應只搜尋與候選方案名稱相同的產品。

例如治理／統御類問題，可比較 AI Governance、System Inventory、Service Catalog、CMDB、Capability Catalog、Workflow Orchestration、Event-driven Trigger Management 等相關做法，再判斷哪些概念適用。

## 五、反方案檢查

正式建立前必須回答：

- 現有方案能否處理？
- 現有系統能否處理？
- 是否只需要增加一個小系統？
- 是否只需要增加一個橫向能力？
- 是否只是缺少狀態索引？
- 是否只是缺少觸發管理？
- 新增方案是否會產生重複管理？
- 新增方案是否會增加不必要的協調複雜度？

如果不需要新方案，不建立新方案。

## 六、漏洞攻擊

候選方案至少應檢查：

- 責任是否重疊。
- 同一事件是否可能被多個系統重複觸發。
- 方案與系統的邊界是否模糊。
- 小系統是否可能被重複納管。
- 方案之間是否可能互相爭奪管理權。
- 狀態索引是否可能與實際狀態脫節。
- 方案本身是否需要被另一個方案管理。
- 方案是否因持續加入例外而失去清楚邊界。

## 七、建立 Gate

```text
□ 問題已確認
□ 目標已確認
□ 既有能力已盤點
□ 外部研究已完成
□ 外部產品／工具／方法已比較
□ 優缺點已分析
□ 主要漏洞已分析
□ 是否需要新方案已判斷
□ 候選架構已形成
□ 已完成必要討論
□ 已完成必要修正
□ 方案邊界已確認
□ 系統／小系統邊界已確認
□ 責任與觸發歸屬已確認
□ 方案已正式確認
```

核心條件未完成，不得直接建立正式方案。

## 八、建立後仍須驗證

通過建立 Gate 只代表「允許建立」，不代表方案成立。

後續仍須：

```text
建立
→ 系統建立／調整
→ 實際觸發
→ 實際執行
→ Expected / Actual
→ 實測結果
→ 狀態重新驗證
→ 方案修正
```

文件存在、方案建立完成與實際有效必須分開判定。

## 九、與問題解決系統的關係

如果新方案構想本身暴露出未知問題，應進入既有問題解決流程，而不是直接靠新增方案文件掩蓋問題。

## 十、與後續工作觸發式驗證的關係

方案建立前的研究與確認屬於建立 Gate，不得用「後續工作順便驗證」取代。

「順便驗證」只適用於已經形成、但等待自然工作事件驗證的能力；不能用來跳過方案成立前的研究與決策。

## 十一、核心判斷

```text
構想 ≠ 候選方案
候選方案 ≠ 已確認方案
已確認方案 ≠ 已成立方案
已成立方案 ≠ 已驗證有效
```

本知識目前為候選知識，須在下一次真實新方案建立案例中確認 AI 是否確實先研究、比較、討論、修正，再建立。
