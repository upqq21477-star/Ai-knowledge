# 知識定義與邊界

> 狀態：**【已完成外部比對；待實際資料驗證】**
>
> 本文件定義 Ai-knowledge 中「知識」的工作邊界，不試圖宣稱知識在哲學或所有學科中只有唯一正確定義。

## 一、目的

本文件要解決的問題是：

> 在 Ai-knowledge 中，什麼內容值得被整理成可長期保存、重複使用的知識；什麼內容應該留在來源、研究資料、討論、決策或應用資料中。

這個定義服務的是「降低未來重新理解、研究與判斷成本」，因此必須兼顧知識本身的性質與本系統的實際用途。

## 二、外部研究結論

目前沒有一個可以直接套用於所有知識管理情境的單一定義。ISO 30401 將 knowledge 定義為能支援**在特定情境中有效決策與行動的理解（understanding）**，並指出知識可以存在於個人、團隊與組織之間，也可以是默會、可表達、編碼或嵌入式知識。citeturn1search0turn1search2

知識管理研究也長期存在不同定義；其中一類實務定義強調知識不只是資訊，而是結合經驗、情境資訊、價值與專業洞見，能用來評估與吸收新的經驗與資訊。citeturn1search1turn1search6

成熟知識工具也沒有把「一個檔案」直接等同於「一個知識單位」。例如 Capacities 將 object 與 object type 分開，並以 properties 描述結構；Obsidian 則以 Markdown 筆記搭配 properties 與內部連結建立結構與關聯。citeturn0search1turn0search0turn0search5turn0search9

因此，本系統原本的「知識＝可跨場景重用的基本原理、判斷或方法」方向是有用的，但過於狹窄；它把知識過度限定成文件化、可獨立理解、跨場景重用的內容，沒有充分涵蓋情境性知識、經驗形成的判斷、程序性／方法性知識，以及尚未高度抽象但仍具有重複決策價值的知識。

## 三、Ai-knowledge 的工作定義

在 Ai-knowledge 中：

> **知識（Knowledge）是經過理解、整理或驗證後，能在明確情境與適用條件下支持後續理解、判斷、決策或行動的可重用內容。**

這個定義有四個核心條件：

1. **具有理解或判斷內容**：不是單純保存原始資料。
2. **具有適用情境**：知道它在哪些條件下成立；不要求所有知識都跨越所有情境。
3. **具有可重用價值**：未來再次遇到相同或相似問題時，可以直接使用、參考或縮短重新研究。
4. **具有可追溯的形成基礎**：視知識性質，可以來自來源、經驗、實作、推理、比較或驗證；不能僅因 AI 說得合理就視為已成立。

## 四、知識不等於文件

「文件」是保存內容的媒介；「知識」是內容本身及其可使用的理解、判斷或方法。

因此：

```text
一份文件 ≠ 一個知識
一個知識 ≠ 必須只有一份文件
一個來源 ≠ 一個知識
一個搜尋結果 ≠ 知識
一段 AI 輸出 ≠ 已驗證知識
```

同一份文件可以包含多個知識，也可能只有研究資料而沒有形成可重用的知識。

## 五、知識與資料、資訊的工作區分

本系統不採用「資料 → 資訊 → 知識 → 智慧」必然線性升級的說法作為硬規則。這種階梯模型在知識管理討論中存在爭議，不能拿來取代實際判斷。citeturn1search12turn1search13

在 Ai-knowledge 中只做較實用的區分：

| 類型 | 工作判定 |
|---|---|
| 資料（Data） | 原始事實、紀錄或觀測內容，尚未形成可供本系統直接重用的理解。 |
| 資訊（Information） | 已具備意義與情境的資料，可被閱讀、查詢或傳遞。ISO 也將 information 與 data、knowledge 分開定義。citeturn1search0 |
| 知識（Knowledge） | 已形成可支持後續理解、判斷、決策或行動的可重用內容，並具有適用情境。 |
| 決策（Decision） | 在特定時間、目標與條件下採取的選擇，不因為曾經合理就自動成為普遍知識。 |
| 經驗／案例（Experience / Case） | 實際發生過的事件與結果；經整理後可以產生知識，但案例本身不必然就是知識。 |

這些是本系統的工作分類，不宣稱它們是世界上唯一正確的認知層級。

## 六、知識可以是情境性的

原本「知識必須跨場景重複使用」的條件過強，現在取消。

知識可以只適用於某一明確領域、任務或條件，只要它在該範圍內能反覆支持理解、判斷或行動。

例如：

- 某種特定遊戲引擎的效能最佳化規則。
- 某一小說系統的固定寫作流程。
- 某種資料格式的解析規則。

它們不必適用於所有領域，仍然可以是知識。

真正重要的是：

> **適用範圍是否清楚，而不是適用範圍是否足夠廣。**

## 七、知識可以是不同形式

外部標準指出知識可以是默會（tacit）、可表達（expressible）、編碼（codified）或嵌入流程的知識。citeturn1search0

因此 Ai-knowledge 不應把「能完整寫成 Markdown」當成知識成立的必要條件。

但本專案的核心媒介是 AI 可讀取與交接的文件，因此目前優先保存**可被明確表達與檢索的知識**。

這是一項系統設計選擇，不是對知識本體的哲學判定。

## 八、知識的證據與可信程度

「是知識」與「我們有多大把握相信它」是兩個不同問題。

因此不能使用「尚未完全確定」作為唯一理由，把所有暫時性知識都排除。

應分開處理：

```text
內容是什麼
↓
適用於什麼情境
↓
為什麼形成這個結論
↓
目前證據／經驗／來源是什麼
↓
哪些部分仍不確定
```

後續由「來源與證據」「狀態」「更新」等知識與系統處理可信程度及生命週期，而不是把所有問題壓進「知識／非知識」二分法。

## 九、什麼通常不直接建立為基礎知識

以下內容通常先保留在其他資料層，而不是直接寫成穩定的基礎知識：

- 完全沒有解釋或來源的原始搜尋結果。
- 尚未理解的資料堆積。
- 單次聊天中的未整理討論。
- 明確只代表某一次臨時操作的紀錄。
- 沒有適用條件、卻被寫成普遍規則的結論。
- AI 單方面生成、尚未經外部研究或實際驗證的重要架構原理。

但「暫時未確認」不代表永遠不能保存。它可以先以假設、研究結果、候選結論或其他適當狀態保存，待後續驗證。

## 十、知識成立的實用判定

新增內容時至少回答：

1. 這是在描述什麼？
2. 它解決什麼理解、判斷或行動問題？
3. 適用於哪些情境與條件？
4. 它是來源資料、整理資訊、案例、決策，還是可重用知識？
5. 為什麼目前可以把它當作知識？
6. 哪些部分仍然不確定？
7. 未來再次遇到類似問題時，能否降低重新研究或判斷成本？

若只能回答「這資料很重要」，但無法說明如何被理解或使用，通常還沒有完成知識化。

## 十一、與本系統其他概念的邊界

```text
來源（Source）
→ 告訴我們內容從哪裡來

證據（Evidence）
→ 支持或反駁某個主張的依據

資訊（Information）
→ 已具意義、可傳遞的內容

知識（Knowledge）
→ 可在明確情境中支持理解、判斷、決策或行動的可重用內容

決策（Decision）
→ 某一時間與條件下採取的選擇

記憶（Memory）
→ 為了延續後續互動而保存的背景或歷史資訊
```

這些概念可以互相轉換或互相引用，但不應視為同一層東西。

## 十二、目前採用的最小模型

目前不建立複雜的知識類型樹，也不預先建立完整知識圖譜。

先使用：

```text
內容
＋
適用情境／條件
＋
形成依據
＋
可重用目的
＋
目前狀態
```

當實際資料證明這個模型不足，再增加結構。

## 十三、外部比對後的設計決定

**修改原文件。**

主要修正：

1. 取消「必須跨場景」作為知識必要條件。
2. 取消「知識必須能獨立理解」這種過度絕對化表述，改為要求內容與適用條件足以支援使用。
3. 將「知識」與「文件」分離。
4. 將「知識成立」與「可信程度／驗證狀態」分離。
5. 納入情境性、程序性與經驗形成的知識概念。
6. 不採用資料→資訊→知識→智慧的必然階梯作為系統硬規則。
7. 保留「降低未來重新理解、研究與判斷成本」作為 Ai-knowledge 的核心工程目的。

## 十四、尚未驗證

目前完成的是**外部理論與成熟工具的概念稽核**，尚未用 Ai-knowledge 的全部實際文件進行分類測試。

下一步需要拿現有文件做案例測試，尤其檢查：

- 一份文件包含多個知識時如何處理。
- 情境性很強的知識是否會被錯誤排除。
- 尚未完全驗證但值得保存的內容如何標記。
- 一次性決策與可重用經驗如何區分。
- 知識與來源／證據／記憶是否會在實際操作中混淆。
