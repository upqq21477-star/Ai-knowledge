# 上下文管理原理

## 狀態
【建立中】

## 定義

上下文管理是根據目前任務，決定 AI 在有限上下文資源中「讀取什麼、先讀什麼、讀到什麼程度，以及什麼時候停止讀取」的方法。

上下文不是單純的文字容量，而是包含讀取、理解、比較與維持注意力所需的有限工作資源。

## 核心目標

上下文管理不是追求一次提供最多資料，而是：

> 用足夠的資料支撐目前任務，同時避免不必要的理解成本。

## 基本流程

```text
目前任務
↓
判斷需要什麼資訊
↓
搜尋／探索候選資料
↓
依相關性與必要性排序
↓
先讀最重要資料
↓
判斷資訊是否足夠
├─ 足夠 → 停止
└─ 不足 → 擴大搜尋／深入閱讀
```

## 資料優先級

一般可以先考慮：

1. 直接回答目前問題的資料。
2. 定義目前使用概念的資料。
3. 決定目前狀態的資料。
4. 重要歷史背景。
5. 間接相關資料。
6. 與目前任務無關的資料。

這不是永久固定的排序；任務不同時優先級也可能不同。

## 最小充分上下文

理想狀態不是「最少資料」，而是「最小充分資料」。

```text
資料太少
→ 無法正確理解

資料適量
→ 可以完成任務

資料過多
→ 增加閱讀與判斷成本
```

因此上下文管理需要在「資訊不足」與「資訊過量」之間調整。

## 分層讀取

大型資料庫不應每次完整載入。

可以採用：

```text
第一層：目錄／索引
第二層：文件名稱與摘要
第三層：相關段落
第四層：完整文件
第五層：相關歷史資料
```

只有在上一層資訊不足時才深入下一層。

## 上下文與搜尋

搜尋與上下文管理是互相依賴但不同的能力。

```text
搜尋
→ 找到可能有用的資料

上下文管理
→ 決定哪些資料值得讀、讀多少
```

搜尋結果越多，不代表上下文管理越成功。

## 上下文與記憶

長期記憶可以降低重新提供背景資料的成本，但不是所有記憶都應永久載入上下文。

應根據目前任務判斷：

```text
記憶存在
≠
目前一定需要讀取
```

## 上下文與交接

AI 交接的目的不是把所有歷史對話全部交給下一個 AI，而是提供完成下一步所需的最小充分背景。

因此交接資料也需要上下文管理。

## 資訊不足時

如果目前上下文不足，不應靠猜測補足。

應：

```text
發現缺口
↓
確認缺口屬於什麼類型
↓
搜尋／讀取相關資料
↓
重新判斷是否足夠
```

## 資訊衝突時

如果不同資料互相矛盾，增加更多資料不一定能解決問題。

應先判斷：

- 是否為不同時間的狀態？
- 是否為不同方案？
- 是否為不同條件？
- 是否真正衝突？
- 哪個資料代表目前狀態？

這需要結合「目前狀態判定」與「知識衝突判定」。

## 上下文停止條件

應在以下情況之一成立時考慮停止：

- 已能回答目前問題。
- 剩餘資料只會增加背景，不會改變結論。
- 進一步搜尋的成本高於可能帶來的價值。
- 目前已進入低相關資料區域。

停止不是偷懶，而是上下文成本管理的一部分。

## 未來上下文系統的最低功能

未來的上下文系統至少需要：

1. 確認目前任務。
2. 判斷需要的資料類型。
3. 控制搜尋與讀取範圍。
4. 提供資料優先順序。
5. 發現資訊缺口。
6. 決定是否繼續擴張上下文。
7. 在資訊足夠時停止。

## 暫不建立的機制

目前不預先建立：

- 自動永久記憶全部內容
- 複雜上下文權重模型
- 全自動上下文壓縮
- 大型向量記憶系統
- 完全自動決定所有上下文

這些都應等實際使用產生明確成本後再考慮。
