# 語意壓縮與分層責任 Knowledge

版本：v1.0
狀態：【候選 Knowledge；由研究建立】

## 1. 分層責任原理

Knowledge：保存原理、規則、事實、證據與判定依據。
System：保存可重複的能力、固定依賴與結果契約。
Solution：保存特定任務的目的、路由、組合、邊界與驗收。

原則：
> 同一語意不應在多層重複保存，除非該層需要自己的最小表達才能正確執行。

## 2. 最小充分語意

壓縮目標不是最短文字，而是最小仍能保持：
- 正確身份
- 正確決策
- 正確執行
- 正確結果解讀
- 正確驗收

的語意集合。

## 3. 語意四分類

### A｜不可刪
刪除會改變身份、路由、功能、依賴、結果解讀或驗收。

### B｜可移交
本層不必保存，但另一層應明確保存。
例如方案專屬驗收由 System 移交 Solution。

### C｜可合併
多段語意可由短契約、代碼或固定結構表示。

### D｜冗餘
刪除後不影響決策、執行、結果解讀與驗收。

## 4. System 最小語意

至少需要：
身份、功能、必要依賴、結果。

若缺少其中任一項而導致模型無法執行或解讀結果，不得繼續壓縮。

## 5. Solution 最小語意

至少需要：
目的、路由、邊界、依賴、驗收。

其中路由身份尤其重要；若存在正式組／對照組同名能力，必須明確指定身份。

## 6. Knowledge 最小語意

至少需要：
原理、規則、證據、判定依據。

Knowledge 不應變成只有索引名稱，否則 System／Solution 會被迫自行推測依據。

## 7. 結果語意原理

結果名稱不一定等於結果語意。

例如「Context Profile」本身不足以保證模型知道必要判定項。
凡會影響結果分類的最低語意必須存在於可被執行鏈可靠取得的位置。

對方案專屬結果分類，可由 Solution 保存。
對所有使用者皆成立的固定結果契約，應保留於 System。

## 8. 壓縮判定

刪除語意前依序問：
1. 是否影響身份？
2. 是否影響路由？
3. 是否影響功能？
4. 是否影響依賴？
5. 是否影響結果解讀？
6. 是否影響驗收？

任一為「是」：
- 若屬固定能力契約 → 保留於 System。
- 若屬本次方案情境 → 移至 Solution。
- 若屬事實／原理／證據 → 保留於 Knowledge。

## 9. 壓縮效能判定

不可只用 compression ratio 判定成功。
至少同時檢查：
- Token／Context 成本
- 任務成功
- Grounding
- 關鍵資訊保存
- 路由正確率
- 語意失真
- 幻覺／Unsupported 分類
- 結果驗收正確率

外部研究同樣指出，Prompt Compression 必須同時考慮成本與資訊保存／任務表現，而不能只追求壓縮率。

## 10. 最小修正原理

發生錯誤時：
問題 → 定位缺失語意 → 判定責任層 → 只補最小語意 → 重測。

禁止因單一錯誤直接恢復完整原文。

## 11. 既有實驗證據

本專案 50 次結構化模擬顯示：
- Solution 增加明確路由身份後，路由錯誤由 3/50 降至 0/50。
- Solution 增加驗收結果定義後，語意失真由 1/50 降至 0/50。
- 壓縮組 Context 成本估算仍約低於正式組 66%～67%。

以上屬專案內部模擬證據，不等同真實模型 benchmark。
