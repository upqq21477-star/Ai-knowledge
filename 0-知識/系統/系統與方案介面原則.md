# 系統與方案介面原則

狀態：**【初版建立；待三方案實際建立後驗證】**

## 一、目的

三個新方案完成後，需要能重用既有系統，也需要讓新建立的系統可以被不同方案使用。

因此必須先區分：

```text
系統（System）
↓ 提供可重用能力
方案（Solution）
↓ 組合能力完成特定目的
應用（Application）
↓ 使用方案解決具體問題
```

本文件只建立介面語義，不提前固定技術 API。

## 二、系統的輸入與輸出

一個系統至少應能說明：

```text
輸入
↓
處理／判斷
↓
輸出
```

輸入與輸出可以是：

- 知識
- 來源
- 證據
- 主張
- 狀態
- 使用者問題
- 搜尋結果
- 驗證結果
- 其他明確定義的資料

系統不應只用「功能名稱」描述，而要能說明它實際產生什麼結果。

## 三、方案如何使用系統

方案不是重新實作所有系統能力。

例如：

```text
方案：搜尋研究
├─ 問題理解系統
├─ 搜尋系統
├─ 證據分析系統
└─ 結果整合系統
```

方案負責決定：

- 使用哪些系統
- 使用順序
- 使用條件
- 系統之間如何傳遞結果
- 最終如何驗證

## 四、介面最低要求

系統被方案重用時，至少需要明確：

1. 能接受什麼輸入。
2. 會產生什麼輸出。
3. 需要哪些前置條件。
4. 哪些情況不能使用。
5. 輸出由誰負責驗證。

這些是語義要求，不代表必須做成程式 API。

## 五、系統之間的組合

系統可以形成串接：

```text
系統 A
↓ 輸出
系統 B
↓ 輸出
系統 C
```

也可以形成分支：

```text
             ┌→ 系統 B
系統 A ──────┤
             └→ 系統 C
```

方案應只保留對完成目標必要的組合，不因「可能有用」而加入所有系統。

## 六、介面錯誤與責任邊界

當系統組合失敗時，必須能區分：

```text
輸入錯誤
系統本身失效
系統輸出不足
介面理解錯誤
方案組合錯誤
驗證不足
```

否則容易把方案問題誤判成系統問題，或反過來把系統缺口藏在方案流程中。

## 七、系統與方案的邊界

如果一項能力只在單一方案內使用，而且沒有穩定重用需求，可以先保留為方案內部能力。

只有當它具備：

```text
可重用
＋
邊界清楚
＋
輸入／輸出穩定
＋
實際案例證明需要獨立
```

才適合正式建立成系統。

## 八、與共同資料契約的關係

```text
共同資料語義
↓
系統介面
↓
方案組合
```

共同資料契約解決「資料是什麼」。

系統介面解決「能力如何交換資料」。

方案解決「為什麼以及如何組合能力」。

三者不可混為一層。

## 九、目前不建立的內容

在三方案實際建立前，不固定：

- API endpoint
- JSON Schema
- 資料庫介面
- 自動工作流引擎
- 跨系統訊息匯流排
- 強制所有系統使用相同實作框架

## 十、後續驗證

待三方案建立後，以實際案例確認：

- 哪些系統真的被多方案重用
- 哪些輸入／輸出需要統一
- 哪些介面需要正式化
- 哪些能力其實不值得獨立成系統
- 哪些方案組合會產生新的介面需求
