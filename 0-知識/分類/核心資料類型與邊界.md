# 核心資料類型與邊界

狀態：**【初版建立；待實際案例驗證】**

## 一、目的

本文件建立 Ai-knowledge 目前三個方案共同使用的最小資料語義集合。

目的不是建立完整資料庫 Schema，而是先避免不同方案對同一名稱產生不同含義。

核心原則：

> 先固定「這個概念是什麼」，再決定未來是否需要欄位、格式、資料庫或自動化實作。

## 二、核心資料類型

目前先建立以下八種主要語義資料：

| 類型 | English | 核心問題 | 最小定義 |
|---|---|---|---|
| 知識 | Knowledge | 我們現在知道什麼？ | 經理解、整理或驗證後，可在明確情境中支持理解、判斷、決策或行動的可重用內容。 |
| 記憶 | Memory | 過去發生過什麼？ | 為延續未來工作而保存的使用者、專案、決策、歷史或重要背景。 |
| 目前狀態 | Current State | 現在實際處於什麼狀態？ | 指定時間、範圍與條件下，目前有效的工作狀態、採用狀態或進度。 |
| 來源 | Source | 內容從哪裡來？ | 資訊、觀察、主張或其他內容的取得位置、產生者或形成過程。 |
| 證據 | Evidence | 為什麼支持或質疑這個主張？ | 能支持、限制、反駁或協助判斷某項主張的內容、觀察、測試、紀錄或理由。 |
| 主張 | Claim | 到底提出了什麼可判斷的命題？ | 可以被支持、反駁、限制或比較的具體命題。 |
| 決策 | Decision | 在當時條件下選了什麼？ | 在特定時間、目標與條件下做出的選擇及其理由。 |
| 觀察 | Observation | 實際看到了什麼？ | 透過實際使用、測試、研究或事件取得的觀察結果，尚未必形成一般化知識。 |

## 三、能力物件不是上述資料類型

以下是另一個層次：

```text
知識
↓
系統
↓
方案
↓
軟體／工具
↓
應用
```

它們描述「能力如何形成與使用」，不能與知識、記憶、來源等語義資料混為同一資料類型。

例如：

```text
知識 → 支撐 → 系統
系統 → 組成 → 方案
方案 → 應用於 → 應用
```

## 四、重要邊界

### 知識 ≠ 記憶

知識主要為重用理解；記憶主要為延續背景。

一項記憶中的經驗可以被抽象成知識，但轉換後仍應保留必要的歷史脈絡。

### 知識 ≠ 目前狀態

「目前採用方案 A」是目前狀態或決策，不等於通用知識。

### 來源 ≠ 證據

來源回答「從哪裡來」，證據回答「為什麼支持或質疑主張」。一個來源可能只有部分內容具有證據作用。

### 證據 ≠ 主張

證據是判斷依據；主張是被判斷的命題。

### 主張 ≠ 知識

主張可能尚未確認，也可能被反駁。只有經過適當理解、比較、驗證並具備可重用價值後，才可能形成知識。

### 觀察 ≠ 知識

一次測試結果首先是觀察。當結果被理解、重複驗證或抽象成可重用規則後，才可能形成知識。

### 決策 ≠ 永久規則

決策受當時目標、時間、條件與限制影響。後續條件改變時可以重新決策。

## 五、目前狀態的特殊性

「目前狀態」不能被簡化成單一 `status` 欄位。

目前狀態至少需要考慮：

```text
時間
＋
範圍
＋
適用條件
＋
目前採用內容
＋
必要的歷史脈絡
```

因此「狀態」是管理維度，而不是核心內容類型本身；「目前狀態」則是為了解決跨工作階段恢復目前實況而保留的語義資料。

## 六、最小轉換關係

資料類型之間可以形成轉換，但不是固定升級階梯：

```text
來源
↓
內容／觀察
↓
主張
↓
證據判斷
↓
知識
```

另一條常見路徑：

```text
實際使用
↓
觀察
↓
決策／經驗
↓
抽象與驗證
↓
知識
```

而記憶則可能保存整個過程中的背景與歷史：

```text
專案／使用者背景
↓
記憶
↓
延續後續工作
```

## 七、資料類型與承載形式

資料類型不等於檔案格式。

同一份 Markdown 可以同時保存：

- 知識
- 主張
- 證據說明
- 決策
- 歷史
- 目前狀態

因此目前不建立「一種資料類型＝一種檔案格式」的硬規則。

## 八、目前不建立的內容

本輪只建立語義邊界，不建立：

- 完整 Metadata Schema
- 固定資料庫欄位
- 知識圖譜
- 向量資料庫
- 自動資料類型判定
- 複雜資料物件 ID 系統
- 全自動資料轉換

這些都必須由實際案例證明存在必要性後再建立。

## 九、成立判定

本文件第一版建立後，下一步不是繼續增加資料類型，而是用實際案例檢查：

1. 是否能用這八種語義清楚描述目前 repository 中的主要資料。
2. 是否出現無法歸類但確實需要保存的內容。
3. 是否有兩個類型實際上無法清楚區分。
4. 是否某些類型只是管理屬性，不應獨立存在。
5. 三個方案是否能使用相同語義而不產生衝突。

只有實際案例暴露缺口，才增加或修改資料類型。
